## 0. 先记住六件事

1. **并发 ≠ 并行。** 并发是"同时处理多件事"（可以轮流做），并行是"同一时刻真的在多核上跑"。
2. **`counter += 1` 不是一条指令**，是"读—算—写"；有没有竞态取决于这三步会不会被切开（1.5）。
3. **Windows 上多进程用 `spawn`，没有 `fork`。** 裸代码必须放进 `if __name__ == "__main__":`，
   交给子进程的函数**必须是模块顶层函数**（2.3 / 2.4 有真实报错原文）。
4. **`await` 才是执行。** `async def` 函数不 `await` / 不 `create_task` / 不交给 `asyncio.run`，
   函数体一行都不跑（3.5）。
5. **正则的模式一律写 `r"..."`。** 不写的话 `"\b"` 会变成退格符，匹配**静默地永远失败**（4.8）。
6. **计时用 `time.perf_counter()`**，不用 `time.time()`——后者会被系统校时改动（5.6）。

## 1. 多线程 `threading`（覆盖 10.1）

官方入口 <https://docs.python.org/3/library/threading.html>——`threading` 全部 API 都在这一页；
本章只用 `Thread` / `Lock` / `RLock` / `Semaphore` / `Event`。

### 1.1 最小例子

```python
import threading, time


def work(name, n):
    for i in range(n):
        print(f"  [{name}] 第 {i + 1} 次")
        time.sleep(0.1)


t = threading.Thread(target=work, args=("A", 3))
t.start()          # 交给操作系统，立刻返回
print("主线程继续往下走")
t.join()           # 主线程在这里停下等 t
```

`target=` 传的是**函数对象本身**（没有括号），`args=` 必须是元组。
`start()` 立刻返回、不等待；`join()` 才是"等它"。

### 1.2 不 `join` 会怎样（实测）

很多人以为"不 join 线程就被杀了"，**不对**：

```python
result = []


def work():
    time.sleep(0.5)
    result.append("子线程的成果")


t = threading.Thread(target=work)
t.start()
print(result)      # []                    ← start() 刚返回，子线程还没干完
t.join()
print(result)      # ['子线程的成果']       ← join() 之后才拿到结果
```

不 join 的后果是**主线程不等它，看到的是半成品**。那主线程先跑完呢？另一个实测
（子线程 `sleep(1.0)`，主线程直接走到末尾，用 `atexit` 记录进程真正退出的时刻）：
非 daemon 线程时主线程自己用了 `0.00s`，但**进程 `1.00s` 才退出**；
`daemon=True` 时进程 `0.00s` 退出，子线程没干完就被掐掉。
**结论：只要还有非 daemon 线程活着，进程就等它；daemon 线程不享受这个待遇。**

### 1.3 两种写法：`target=` 还是继承 `Thread`

```python
class MyThread(threading.Thread):
    def __init__(self, name, n):
        super().__init__(name=name)     # 名字交给基类
        self.n = n

    def run(self):                      # 线程要干的事写在 run() 里
        for i in range(self.n):
            print(f"  线程 {self.name} 第 {i + 1} 次")
            time.sleep(0.1)


t = MyThread("工人-1", 3)
t.start(); t.join()
print(t.is_alive())                     # False
```

只是把函数丢到后台跑 → 用 `Thread(target=f, args=(...))`；
线程要携带状态、要复用 → 继承 `Thread`，状态就是实例属性。

> ⚠️ **坑**：继承了 `Thread` 之后写 `t.run()` 而不是 `t.start()`。现象：不报错，
> 但**一点并发都没有**，退化成普通函数调用。原因：`run()` 是"线程体"，直接调用就在当前线程里同步执行。
> 处理：启动永远是 `t.start()`。

### 1.4 daemon 线程

```python
import threading, time


def lazy_worker():
    for i in range(20):                  # 本来要打印 20 次、跑 2 秒
        print(f"  daemon 还在跑 {i}")
        time.sleep(0.1)


d = threading.Thread(target=lazy_worker, daemon=True)
d.start()
time.sleep(0.35)
print("主线程结束，daemon 被强制终止")
# 真实输出：daemon 还在跑 0 / 1 / 2 / 3 三行之后，就是"主线程结束，daemon 被强制终止"
#          第 4 轮之后被掐掉，20 轮永远不会跑完
```

**daemon = 主线程一退，不管你干到哪，直接掐掉**，`finally` 不保证执行。
用在心跳上报、状态轮询这种"丢了无所谓"的活；**不要**用在写文件、提交事务上。

### 1.5 竞态条件：教科书说法在本机不复现（**本章最重要的一节**）

**教科书版本**是下面这段，配一句"结果会小于两万"，依据是 `counter += 1` 不是原子操作：

```python
import threading

counter = 0
TIMES = 10000


def add():
    global counter
    for _ in range(TIMES):
        counter += 1


ts = [threading.Thread(target=add) for _ in range(2)]
for t in ts: t.start()
for t in ts: t.join()
print("期望 20000，实际", counter)      # 期望 20000，实际 20000   ← 一次都不丢
```

我把能想到的变量都调了一遍，**全部不丢**：

| 试过的写法 | 结果 |
|---|---|
| 2 线程 × 1 万 / 10 万 / 100 万 | 精确（20000 / 200000 / 2000000） |
| 4 线程 × 10 万；加 `sys.setswitchinterval(1e-6)` | 400000，还是不丢 |
| `lst[0] += 1` / `d["k"] += 1` / `box.count += 1` / 闭包 `nonlocal` | 400000，全不丢 |
| **`counter += one()`（右边是一次函数调用）** | **223327，丢了 44%** |

**原因看反汇编**（`dis.dis(demo)`，`demo` 里就一句 `counter += 1`）：

```
 12           LOAD_GLOBAL              0 (counter)
              LOAD_CONST               1 (1)
              BINARY_OP               13 (+=)
              STORE_GLOBAL             0 (counter)
              RETURN_CONST             0 (None)
```

**四条直线指令，中间没有任何检查点。** CPython 的线程切换不是"随时可以发生"，
它只在特定位置（eval breaker 检查点）检查要不要让出 GIL，主要是**函数调用**（字节码 `CALL`）
和**循环回边**（`JUMP_BACKWARD`，一次迭代的末尾）。上面四条里一个都没有。
循环回边确实是检查点，但它在"这一轮 `+=` 已经做完"之后才出现，在那儿切换不会损坏已完成的自增。
再看 `counter += one()` 的字节码：
`LOAD_GLOBAL counter | LOAD_GLOBAL one + NULL | CALL | BINARY_OP += | STORE_GLOBAL counter | JUMP_BACKWARD`
——中间多了 `CALL`：执行 `one()` 期间线程可能被切走，另一个线程读走同一个旧值，自增就丢了。

**判据**：对任何一条语句问两个问题——① 字节码里有没有 `CALL`？
② 它会不会跑到别的 Python 字节码上去（`@property` 的 getter/setter、自己定义的 `__setattr__`）？
**只要有一条是"会"，这条语句就可能被切开，共享状态就必须加锁**；
全是纯 C 快路径的直线指令（`LOAD` / `LOAD_CONST` / `BINARY_OP` / `STORE`），本机实测切不开。
第 ② 条不是推演，是实测——换成 `@property` 或加一层 Python 的 `__setattr__`，
字节码里**依然没有 `CALL`**，照样丢（4 线程 × 10 万，期望 400000）：
普通属性 `box.count += 1` → 400000；换成 `@property` 的 getter/setter → **157488**；
类里定义了 Python 层的 `__setattr__` → **188995**。

**这一节真正的教训**：

> **竞态是时序依赖的，不会因为在你的机器上没复现就不存在。**
> 上面那张表就是活证据：同一个 `+=`，换个写法就丢一半；这台机器不丢，
> 换台更慢的 CPU、换个 Python 版本、换成 3.14 的自由线程构建、甚至挂上调试器
> （调试器会插入额外检查点），行为都可能变。
> 所以：**"我跑了一万次都对"永远不能证明没有竞态**，只能证明"这一万次恰好没被切开"。

**稳定的最小反例**（读写之间夹一次调用）：

```python
import sys, threading

TIMES = 100_000
counter = 0


def one(): return 1


def add():
    global counter
    for _ in range(TIMES):
        counter += one()            # 读写之间夹了一次调用


def add_locked(lock):
    global counter
    for _ in range(TIMES):
        with lock:
            counter += one()


def trial(target, use_lock):
    global counter
    counter = 0
    sys.setswitchinterval(1e-6)     # 人为放大切换窗口，好复现
    if use_lock:
        lock = threading.Lock()
        ts = [threading.Thread(target=target, args=(lock,)) for _ in range(2)]
    else:
        ts = [threading.Thread(target=target) for _ in range(2)]
    for t in ts: t.start()
    for t in ts: t.join()
    sys.setswitchinterval(0.005)
    return counter


for i in range(3):
    print(f"不加锁 第 {i+1} 次：期望 200000，实际 {trial(add, False)}")
# （把最后一行换成 trial(add_locked, True) 再跑 3 次：200000 / 200000 / 200000）
```

```
不加锁 第 1 次：期望 200000，实际 141939
不加锁 第 2 次：期望 200000，实际 143574
不加锁 第 3 次：期望 200000，实际 143621
```

**"三次数字都不一样"本身就是竞态的特征**——它是概率性 bug，不能靠"重跑一遍看看"排查。
代码里 `sys.setswitchinterval(1e-6)` 是**人为放大切换窗口**，只是让它更容易出现，不是"制造"了 bug；
去掉它丢失比例会小些，但依然会丢。`time.sleep(0)` 有同样效果（主动让出），
但那已经是"你显式告诉解释器这里可以切"，用它举例要说清这一点。

### 1.6 用 `Lock` 修掉竞态

```python
lock = threading.Lock()


def add_with_lock():
    global counter
    for _ in range(TIMES):
        with lock:              # 同一时刻只有一个线程能进这块
            counter += 1
```

实测结论已在上面的输出里：**加锁后 3 次全是 200000。**

- 用 `with lock:`，不要手写 `acquire()` / `release()`——后者中途抛异常就不会释放，直接死锁。
- **锁保护的是"代码块"，不是"变量"**。同一变量有多处修改，漏掉任何一处加锁，那处照样丢。
- 临界区要尽可能小：别把 `sleep`、网络请求、文件读写塞进 `with lock:`。

> ⚠️ **坑**：两个线程各持一把锁，又都去要对方那把 → 死锁。现象：CPU 接近 0、
> 日志停在某行再也不动、不报错也不退出。处理：约定多把锁的获取顺序（永远先 A 再 B），或只用一把锁。

### 1.7 `RLock` / `Semaphore` / `Event`（简要）

| 工具 | 语义 | 用在哪 |
|---|---|---|
| `Lock` | 一把钥匙，只能一个人拿 | 保护共享变量 |
| `RLock` | 同一线程可重复拿，内部记次数 | 加锁的函数互相调用（A 在锁里调 B，B 也要锁） |
| `Semaphore(n)` | 最多 n 个同时进 | 限制并发数，如"最多 5 个连接" |
| `Event` | 一个开关，等的人一起醒 | 一个线程通知多个线程"开始吧" |

`Lock` 的硬限制是"同一线程重复获取会死锁"（实测 `lock.acquire()` 之后再
`lock.acquire(timeout=1)` 返回 `False`；不加 `timeout` 就永久卡住）；
`RLock` 允许同线程重入：`with rlock:` 里再套 `with rlock:` 不卡。
`Semaphore(2)` 开 5 个工人，实测输出 `历史最高同时在场人数： 2`，说明限流生效。
`Event` 实测：等待者 `ev.wait(timeout=1)`，主线程 0.4 秒后 `ev.set()`，等待者打印
`1 秒内等到信号了吗？True`，然后 `ev.wait()`（不带 timeout）立刻返回。
**`wait(timeout=...)` 超时返回 `False`、等到信号返回 `True`**——很多人忽略返回值，
结果"等超时"和"等到信号"走了同一条路。`set()` 之后可以用 `clear()` 复位。

### 1.8 `ThreadPoolExecutor` 与 `Future`

手写一堆 `Thread` 有三个麻烦：数量不可控、结果拿不到、异常会丢。`concurrent.futures` 解决这个：
<https://docs.python.org/3/library/concurrent.futures.html>（同一页管线程池和进程池，两者 API 一样）。

```python
from concurrent.futures import ThreadPoolExecutor, as_completed


def job(n):
    time.sleep(0.2)
    return n * n


with ThreadPoolExecutor(max_workers=3) as pool:
    fut = pool.submit(job, 5)
    print(fut.done())          # False        ← 刚提交，还没算完
    print(fut.result())        # 25           ← 会阻塞到算完
    print(fut.done())          # True
    # repr(fut) → <Future at 0x21aaf78f230 state=finished returned int>
```

`submit()` 返回的不是结果，是 **`Future`**（"期货"）：查状态 `done()`、取结果 `result()`（会阻塞）。
`as_completed` 按**完成顺序**给（实测 6 个任务输出顺序是 `0 1 3 2 5 4`，和提交顺序不同）；
要按提交顺序拿结果用 `pool.map()`：`list(pool.map(job, range(5)))` → `[0, 1, 4, 9, 16]`。

> ⚠️ **坑**：`submit()` 之后不取 `result()`，**任务里抛的异常会被完全吞掉**。实测 repr 是
> `<Future ... state=finished raised ValueError>`，但我没调 `result()`，所以**什么都没报**，
> 退出 `with` 也没报。原因：异常存在 `Future` 里，只有 `result()` 会重新抛出来。
> 处理：**每个 `submit()` 都要有对应的 `result()`**，或者用 `map`（迭代时会抛）。
> 手动起的线程更糟：异常只由 `threading.excepthook` 打到 stderr（以 `Exception in thread 炸弹:` 开头），
> 主线程完全不知情，连"重抛"的机会都没有。

`with ThreadPoolExecutor(...) as pool:` 退出时自动 `shutdown(wait=True)`，等所有任务跑完：
实测 4 个 0.2 秒的任务总共 `0.20s`（不是 0.80s），证明它们确实同时跑。
另外记住：**线程池解决的是"管理"，不是"同步"**——池里的共享变量照样要加锁
（实测 4 个任务各加 5 万次，带锁得 200000；去掉锁立刻退回 1.5 节的竞态）。

### 1.9 GIL 的后果：实测数据

GIL 的讲解在第 11 章（覆盖表 9.6）；官方术语表
<https://docs.python.org/3/glossary.html#term-global-interpreter-lock>——一句话：
**同一时刻只有一个线程能执行 Python 字节码**。这里只回答"它让你损失了什么"：

```python
N = 3_000_000


def cpu_task(n=N):
    total = 0
    for i in range(n):
        total += i * i
    return total


def io_task(seconds=0.5):
    time.sleep(seconds)          # 模拟"等网络/等磁盘"
```

```
解释器 3.13.15，CPU 任务 = 循环 3,000,000 次累加 i*i
=== CPU 密集：串行 vs 多线程 ===
2 个任务：串行 0.24s    2 线程 0.23s    加速比 1.02x
4 个任务：串行 0.48s    4 线程 0.46s    加速比 1.04x
=== IO 密集（每个任务 sleep 0.5s）：串行 vs 多线程 ===
2 个任务：串行 1.00s    2 线程 0.50s    加速比 2.00x
4 个任务：串行 2.00s    4 线程 0.50s    加速比 3.99x
```

**IO 能快**：`sleep`、`recv`、`read` 在等的期间会**主动释放 GIL**，别的线程趁机跑，
所以四个 0.5 秒的任务总共还是 0.5 秒。**CPU 不能快**：纯计算循环不释放 GIL，
四个线程抢同一把锁轮流跑（4 线程只有 **1.04x**），还多出切换开销。

> 这条结论决定选型：任务在"等外部"→ 线程或 asyncio；任务在"烧 CPU"→ 只能多进程。
> 判断方法：问自己"这段代码 90% 的时间是在等，还是在算"。

### 1.10 `concurrent.futures` 的统一接口

```python
def run(pool_class):
    with pool_class(max_workers=4) as pool:
        for f in as_completed([pool.submit(job, i) for i in range(8)]):
            print(f.result())


run(ThreadPoolExecutor)      # 换这一行，整个程序从多线程变多进程
```

两者共享 `submit` / `map` / `shutdown` / `as_completed` / `wait` 和 `Future` 的 `result()` `done()`。
**限制不一样，这才是真区别**：

| | `ThreadPoolExecutor` | `ProcessPoolExecutor` |
|---|---|---|
| 并行能力 | 受 GIL 限制，只有 IO 有效 | 真并行，CPU 密集有效 |
| lambda / 局部函数 | **能** | **不能**（要 pickle，见 2.4） |
| 参数、返回值 | 任意对象，直接共享 | **必须能 pickle**，且是拷贝过去的 |
| 共享变量 | 直接共享（要加锁） | **不共享**（要显式通信） |
| 启动开销 | 很小 | **很大**（2.9 实测每进程 806ms） |

所以开发流程是：**先用 `ThreadPoolExecutor` 把逻辑写对**，性能测试发现瓶颈在 CPU 而不是 IO，
再把类名换成 `ProcessPoolExecutor`，其余代码基本不动。

> ⚠️ **未实测**：上表 `ProcessPoolExecutor` 那一整列在本机跑不起来（沙箱禁命名管道，见 2.6）；
> 内容来自文档 + 2.4 节用 `Process` 复现的等价限制。

## 2. 多进程 `multiprocessing`（覆盖 10.2）

官方入口 <https://docs.python.org/3/library/multiprocessing.html>——用子进程代替线程，
接口刻意做得和 `threading` 很像。

### 2.1 为什么需要多进程

1.9 节实测 CPU 密集 4 线程只有 1.04x，因为 GIL 让字节码永远只有一个线程在跑。
**多进程绕开它的方式很直接：每个进程有自己的解释器、自己的 GIL、自己的内存空间**，
操作系统把它们调到不同核上，于是真的同时算（**前提是机器有闲置核心——2.8 节的多次实测显示，
机器一忙这个"真的同时算"就消失了**）。代价：

| 代价 | 说明 |
|---|---|
| 创建慢 | 要启动新解释器、重新 import 你的模块（2.9 实测 806 ms/个） |
| 内存不共享 | 子进程改了变量，父进程看不见（2.5） |
| 数据要序列化 | 参数和返回值都 pickle 一份，传大对象很亏 |
| Windows 没有 `fork` | 只能用 `spawn`，多出两条硬规矩（2.3 / 2.4） |

### 2.2 `Process` 最小例子

```python
import multiprocessing, os


def work():
    print(f"  子进程在跑，pid={os.getpid()}")


if __name__ == "__main__":
    print(f"主进程 pid={os.getpid()}")
    p = multiprocessing.Process(target=work)
    p.start(); p.join()
    print(f"主进程结束，子进程 exitcode={p.exitcode}")
```

```
  子进程在跑，pid=36512
主进程 pid=39812
主进程结束，子进程 exitcode=0
```

两行 pid 不一样 = 真的开了另一个进程。`p.exitcode` 是子进程退出码（`0` 正常、`1` 出错），
线程没有这个——线程失败了只能从 stderr 里翻 traceback。

> ⚠️ **不要混用**：`queue.Queue` 是线程队列，跨进程用不了；`threading.Lock` 也管不了别的进程。
> 跨进程要用 `multiprocessing.Queue` / `multiprocessing.Lock`。名字像不代表能换。

### 2.3 Windows 的 `spawn`：为什么必须写 `if __name__ == "__main__"`

实测 `get_start_method(), get_all_start_methods()` → `spawn ['spawn']`。**Windows 只有 `spawn`。**
它做的事是：新起一个 Python 解释器，**把你的主模块当成一个模块重新 import 一遍**，
再把目标函数和参数反序列化过去。"重新 import"就是坑的来源：**你的模块顶层代码会再跑一次**。

把 2.2 节的代码摊在顶层（去掉那个 `if`），真实 stdout：

```
顶层代码被执行，pid=37440, __name__=__mp_main__
顶层代码被执行，pid=12844, __name__=__main__
结束，pid=12844, 子进程 exitcode=1
```

子进程的 stderr（真实 traceback，中间省略）：

```
Traceback (most recent call last):
  File "<string>", line 1, in <module>
    from multiprocessing.spawn import spawn_main; spawn_main(parent_pid=12844, pipe_handle=324)
  File "...\multiprocessing\spawn.py", line 297, in _fixup_main_from_path
    main_content = runpy.run_path(main_path, run_name="__mp_main__")
  File "mp02_no_guard.py", line 11, in <module>
    p.start()
  File "...\multiprocessing\spawn.py", line 140, in _check_not_importing_main
    raise RuntimeError('''
RuntimeError:
        An attempt has been made to start a new process before the
        current process has finished its bootstrapping phase.
        ...
        section in https://docs.python.org/3/library/multiprocessing.html
```

连起来读：主进程（`__name__ == "__main__"`）跑到 `p.start()` → `spawn` 出子进程 →
子进程把主模块当 `__mp_main__` **重新执行一遍**，又跑到 `p.start()` →
`multiprocessing` 发现"还在 bootstrap 就想开新进程"，抛 `RuntimeError`，子进程 exitcode=1 →
主进程这边 `join()` 正常返回，只是 `exitcode=1`。

所以那个 `if` 不是风格建议，是**机械必需**：`__name__` 在主进程是 `"__main__"`，
在 spawn 出的子进程是 `"__mp_main__"`，这句判断正好把顶层启动代码从子进程排除掉。

> ⚠️ **坑**：这个错误在 Linux/macOS 上可能**根本不出现**——那边默认 `fork`，
> 子进程直接复制父进程内存，不重新 import，于是"Mac 上能跑、Windows 上报错"的代码满地都是。
> 处理：**不管在什么平台开发，多进程代码一律写 `__main__` 保护。**
> 顺带：Windows 上想改回 `fork` 也不行，实测 `set_start_method("fork", force=True)` 报
> `ValueError: cannot find context for 'fork'`——Windows 没有这个系统调用。

### 2.4 `spawn` 的三条硬规矩（真实报错）

子进程要**反序列化**目标函数，所以函数必须"能被名字找到"（实测输出）：

```
--- 1. 用 lambda 当 target ---
[FAIL] PicklingError: Can't pickle <function <lambda> at 0x000001AD11AD3E20>: attribute lookup <lambda> on __main__ failed
--- 2. 用局部函数当 target ---
[FAIL] AttributeError: Can't get local object 'local_inside.<locals>.inner'
--- 3. 用顶层函数当 target ---
[OK]
```

> 细节：case 1/2 旁边子进程还会额外打一段 `EOFError: Ran out of input`。因为 `start()`
> 是**先创建进程、再 pickle 参数发过去**：父进程 pickle 失败直接抛异常，子进程已起来、
> 正等数据，发现管道空了就报 `EOFError`。两种报错同时出现不是两个 bug，是同一个原因。
>
> 还有一个变体值得记住：把函数定义在 `if __name__ == "__main__":` 块**里面**（看起来很"顶层"），
> 报的是 `AttributeError: Can't get attribute 'child' on <module '__mp_main__' from '...'>`。
> 同一个原因——spawn 是在子进程里**按模块属性**去找那个函数的，写在 `if` 块里的定义不是模块属性。
> （这条是我自己写 2.8 节的重叠实验时踩出来的真实报错。）

**规矩一**：目标函数必须是模块顶层函数（lambda、局部函数都不行）。
**规矩二**：参数和返回值必须能 pickle（socket、文件对象、`threading.Lock` 都不行）。
**规矩三**：不要依赖模块里的可变全局状态（见 2.5）。
这条限制和线程池正好相反：`pool.map(lambda x: x * x, range(10))` 在线程池可以，
进程池必须换成模块顶层的 `def square(x): return x * x`。

> ⚠️ **未实测**：`ProcessPoolExecutor` 的上述行为在本机沙箱跑不起来（2.6）；
> 但"函数必须能被 pickle"是和 `Process` 共用的同一套 `spawn` 机制，报错就是上面那两条。

### 2.5 进程间不共享内存（实测）

```python
import multiprocessing

counter = 0
items = []


def child_work():
    global counter
    counter += 100
    items.append("子进程加的")
    print(f"  子进程里：counter={counter}, items={items}")


if __name__ == "__main__":
    print(f"启动前：counter={counter}, items={items}")
    p = multiprocessing.Process(target=child_work)
    p.start(); p.join()
    print(f"子进程结束后：counter={counter}, items={items}")
```

```
  子进程里：counter=100, items=['子进程加的'], pid=38880
启动前：counter=0, items=[]
子进程结束后：counter=0, items=[]
```

**子进程里 `counter` 是 100，父进程看到的还是 0。** 这不是"没生效"，
是**根本没有同一个 counter**：`spawn` 的子进程从零构造，import 你的模块得到**自己那份** `counter = 0`。
要共享必须显式来做：`multiprocessing.Value("i", 0)`（共享标量）、
`multiprocessing.Array("i", [1, 2, 3])`（共享定长数组，实测打印 `0 [1, 2, 3]`）。
类型码常用 `"i"`（int）、`"q"`（long long）、`"d"`（double）；改的时候要
`with n.get_lock():` 自己加锁（除非构造时传 `lock=False` 自己管）。

> ⚠️ **坑**：`Value` / `Array` 有范围限制。我用 `Array("q", 4)` 存 40,000,000 以内整数的
> 平方和（约 2.1×10²²）时直接溢出，因为 `"q"` 也只到 2⁶³≈9.2×10¹⁸。
> 处理：共享内存只放小数据（计数、标志、状态码），大结果用队列传，或先取模再放。

### 2.6 `Queue` / `Pipe`：进程之间怎么说话

```python
import multiprocessing, queue


def producer(q):
    for i in range(3):
        q.put(f"消息{i}")


def consumer(q):
    while True:
        try:
            item = q.get(timeout=1)      # 没数据就超时，用来判断"生产完了"
        except queue.Empty:
            break
        print("  消费者取出", item)


if __name__ == "__main__":
    q = multiprocessing.Queue()
    ps = [multiprocessing.Process(target=producer, args=(q,)),
          multiprocessing.Process(target=consumer, args=(q,))]
    for p in ps: p.start()
    for p in ps: p.join()
```

`Pipe` 是一对一的管道（`parent_end, child_end = multiprocessing.Pipe()`，
两端各用 `conn.send()` / `conn.recv()`），比 Queue 轻：
`Queue` 给多生产者多消费者用（任务分发、结果汇总），`Pipe` 给父子进程一对一握手用。

> ⚠️ **本节未实测（沙箱限制）**：本机 DSH 沙箱禁止创建 Windows 命名管道，而
> `Queue` / `Pipe` / `SimpleQueue` / `Pool` / `Manager` / `ProcessPoolExecutor`
> 在 Windows 上**全部**靠命名管道实现。真实拒绝信息：
>
> ```

>     h2 = _winapi.CreateFile(address, access, 0, _winapi.NULL, _winapi.OPEN_EXISTING, ...)
> PermissionError: [WinError 5] 拒绝访问。
> ```
>
> 我逐个探测了可用性：`[OK] Process` / `[OK] Value` / `[OK] Array` /
> `[FAIL] Pipe` / `[FAIL] Queue` / `[FAIL] SimpleQueue` / `[FAIL] Pool` / `[FAIL] ProcessPoolExecutor`

### 2.7 `Pool` 与 `ProcessPoolExecutor`

```python
with multiprocessing.Pool(4) as pool:               # 老写法
    print(pool.map(square, [1, 2, 3]), pool.apply_async(square, (9,)).get())

from concurrent.futures import ProcessPoolExecutor   # 新写法（推荐）

with ProcessPoolExecutor(max_workers=4) as pool:
    print(list(pool.map(square, range(5))))
```

**推荐新的**：它和 `ThreadPoolExecutor` 共用一套 `Future` 接口（1.10），换线程池只改类名；
`Pool` 是另一套接口（`apply_async` / `map_async` / `imap`），等于学两遍。
两者都适用同样两条规矩：**放在 `__main__` 保护里** + **函数是模块顶层函数**。

> ⚠️ **未实测**：两者在本机沙箱下都是 `PermissionError: [WinError 5]`。有个反直觉的细节——
> `ProcessPoolExecutor` 会**在构造函数里**就失败，因为它建实例时就要创建内部唤醒管道：
> `process.py, line 726, in __init__ → _ThreadWakeup() → mp.Pipe(duplex=False) → PermissionError`。

### 2.8 多进程计时：能不能更快，取决于机器有没有空闲核（多次实测）

这是第 11 章 GIL 那节的正面答案。沙箱禁掉了进程池（2.6），我改用
**`Process` + 共享 `Array` 收集结果**——这一路**不需要命名管道，所以在沙箱里能跑**，
工作量与进程池完全相同：

```python
MOD = 1_000_000_007
N = 40_000_000


def cpu_task(n):
    total = 0
    for i in range(n):
        total += i * i
    return total % MOD          # 取模，避免超出共享内存 64 位的范围


def cpu_task_to_array(n, out, idx):
    out[idx] = cpu_task(n)


if __name__ == "__main__":
    t0 = time.perf_counter()
    for _ in range(4):
        cpu_task(N)
    serial = time.perf_counter() - t0

    out = multiprocessing.Array("q", 4, lock=False)
    t0 = time.perf_counter()
    ps = [multiprocessing.Process(target=cpu_task_to_array, args=(N, out, i)) for i in range(4)]
    for p in ps: p.start()
    for p in ps: p.join()
    parallel = time.perf_counter() - t0
    print(f"串行 4 个：{serial:.2f}s   4 个进程：{parallel:.2f}s   加速比 {serial / parallel:.2f}x")
```

**同一段代码，我在同一天里跑了 5 次，结果差 5 倍以上：**

| 跑的时候的机器状态 | 串行 4 个 | 4 个进程 | 加速比 |
|---|---|---|---|
| 较早、机器较闲 | 8.14s | 2.33s | **3.49x** |
| 晚些、本机同时跑着 16 个 python 进程 | 6.98s | 7.23s | 0.96x |
| 同上 | 9.06s | 14.54s | 0.62x |
| 同上 | 6.92s | 6.37s | 1.09x |
| 同上 | 9.57s | 9.41s | 1.02x |

同一时段的 **4 线程**加速比：`1.02x / 1.04x / 0.79x / 1.06x / 1.01x / 1.13x`——
**稳定在 1.0 附近，和机器忙不忙无关**（这是 GIL 的性质，不是负载的性质）。

两条结论：

1. **4 线程拿不到 CPU 加速，这一条可复现**（1.9 节和这里都是 ~1.0x）。
2. **4 进程的加速比不是程序的性质，是机器状态的性质。** 只有在"任务足够长 + 机器有闲置核心"
   时才拿得到：较闲时实测 `3.49x`，机器一忙就掉到 `1.0`，甚至 `0.62x`（**比串行还慢**）。
   （把差异归因到机器负载是我的**解释**，不是实测到的因果；我能确证的是"同一段代码、同一天、结果差 5 倍"。）

**而且总耗时被 spawn 开销污染，不能靠它判断"到底并行没有"。** 更硬的证据是让每个子进程
把自己的起止时间写进共享内存——`perf_counter()` 在 Windows 上走 `QueryPerformanceCounter`，
是全机单调时钟，跨进程可比：

```python
def child(n, ts, te, res, idx):     # 必须在模块顶层，否则 spawn 找不到它（见 2.4）
    ts[idx] = time.perf_counter()
    total = 0
    for i in range(n):
        total += i * i
    res[idx] = total % 1_000_000_007
    te[idx] = time.perf_counter()


if __name__ == "__main__":
    starts = multiprocessing.Array("d", 4, lock=False)
    ends = multiprocessing.Array("d", 4, lock=False)
    results = multiprocessing.Array("q", 4, lock=False)
    ps = [multiprocessing.Process(target=child, args=(20_000_000, starts, ends, results, i))
          for i in range(4)]
    for p in ps: p.start()
    for p in ps: p.join()
    span = max(ends) - min(starts)                    # 第一个开工到最后一个收工
    busy = sum(e - s for s, e in zip(starts, ends))   # 四个子进程干活时间之和
    print(f"干活之和 {busy:.2f}s / 墙钟跨度 {span:.2f}s = 重叠度 {busy / span:.2f}x")
```

```
三次实测：
  干活之和 3.06s / 墙钟跨度 4.01s = 重叠度 0.76x
  干活之和 3.11s / 墙钟跨度 2.79s = 重叠度 1.11x
  干活之和 3.21s / 墙钟跨度 5.37s = 重叠度 0.60x
```

**重叠度 ≈1 说明四个子进程基本是一个接一个跑的（等于串行），≈4 才是真并行。**
我前后一共跑了 6 次，重叠度落在 **0.32x ～ 1.11x** 之间，**从来没有接近过 4x**——
也就是说：在这台机器当时的状态下，**多进程并没有拿到并行**。

所以这一节的**诚实结论**（比"3.49x"这个数字本身重要得多）：

1. **想真并行 CPU，只有多进程这条路**（线程被 GIL 锁死，实测恒 ~1.0x）；
2. **但多进程不保证给你加速**：任务要够长（≥1 秒/个）、机器要有空闲核、启动开销要摊得薄；
3. **判断自己的程序有没有真并行，不要看总耗时**（会被 spawn 开销和负载掩盖），
   用上面那个**重叠度**去量。

> ⚠️ **一个反例也必须说**：任务太短时多进程**必定更慢**。实测（N=1000 万，单个约 0.4 秒）：
> `2 个任务：串行 0.79s / 2 进程 2.70s（0.29x）`、`4 个任务：串行 1.62s / 4 进程 1.92s（0.84x）`。
> 4 进程跑了 1.92 秒，大部分是启动。**结论：单个任务不到一秒的，别上多进程。**

> ⚠️ **一处我没能解释的差异**：在重叠实验里，子进程自己量到的单任务耗时（约 `0.75s`/2000 万次）
> 明显短于父进程里量同一个任务（`1.5～1.9s`）。我没确定原因，所以**重叠度只用子进程自己的
> 时间戳算、不引用父进程的基准**——这样即使基准不可比，"干活之和 / 墙钟跨度"这个比值仍然成立。

### 2.9 进程创建开销比线程大多少（实测）

空 `noop()` 各起 20 个：**20 个线程 `0.003s`（每个 0.2 ms），20 个进程 `16.124s`（每个 806 ms）。**

> ⚠️ **诚实标注**：`806 ms` 明显受本机沙箱拖累（沙箱会介入进程创建）。
> 普通 Windows 上一个空 `spawn` 子进程通常几十到一百多毫秒，Linux 上默认 `fork` 可快到几毫秒。
> **但"进程创建比线程贵一到三个数量级"这个结论是稳的**，而且进程还要重新 import 你的整个模块，
> **模块越大越慢**。处理：① 用**池**复用进程，不要每个任务 `Process()` 一次；
> ② 让每个任务干足够久（≥1 秒）摊薄启动成本；③ `if __name__ == "__main__":` 里别放重活。

## 3. 异步 `asyncio`（覆盖 10.3）

官方入口 <https://docs.python.org/3/library/asyncio.html>——整套异步编程的入口，
本章只用 `run` / `gather` / `as_completed` / `TaskGroup` / `Queue` / `sleep`。

### 3.1 为什么还需要第三种并发

线程有三个摆脱不掉的负担：**每个线程都贵**（创建 0.2 ms，还要占独立栈）、
**GIL**（1000 个线程也不会让 CPU 快一点）、**竞态**（有共享状态就要加锁，加锁就要小心死锁）。
**协程（coroutine）**走另一条路：**一个线程、一个事件循环、协作式调度**。

- "协作式"= **没有一个协程能被打断**，只有它自己 `await` 时才交还控制权。
  于是**不需要锁**——没有抢占，就没有"读到一半被切走"。
- "每个协程很便宜"是真的：它就是一个对象，不用系统调用。
  实测起 200 个协程并跑完用 `1.42 ms`，200 个线程用 `24.36 ms`，**差 17 倍**。

代价：**一个协程不 `await`，别的协程一行都跑不了**（3.4 的反例）。

### 3.2 最小例子：`async def` / `await` / `asyncio.run`

```python
import asyncio, time


async def brew(name, seconds):
    print(f"  开始泡 {name}")
    await asyncio.sleep(seconds)      # 不阻塞线程，只是"让出"给事件循环
    return f"{name}好了"


async def main():
    t0 = time.perf_counter()
    await brew("红茶", 1); await brew("绿茶", 1); await brew("乌龙", 1)
    print(f"顺序 await 总耗时 {time.perf_counter() - t0:.2f}s")      # 3.02s

    t0 = time.perf_counter()
    results = await asyncio.gather(brew("红茶", 1), brew("绿茶", 1), brew("乌龙", 1))
    print(f"gather 总耗时 {time.perf_counter() - t0:.2f}s", results)
    # 1.00s ['红茶好了', '绿茶好了', '乌龙好了']，三个"开始泡"是连着打印的


asyncio.run(main())
```

- **`await` 是"等这个做完"**：顺序三次 = 3.02 秒；`gather` 三个一起 = **1.00 秒**。
- **总耗时约等于"最慢的那一个"**，这是本节的核心事实。
- **`asyncio.run()` 是入口**：创建事件循环、跑完这个协程、关掉循环，并把返回值返回出来。

### 3.3 事件循环是什么（概念级）

一个**死循环**，每轮做三件事：① 推进可以继续跑的协程；② 看有没有定时器到期；
③ 问操作系统"我等的那些 IO 好了吗"。

```python
async def show_loop():
    loop = asyncio.get_running_loop()
    print(loop)            # <ProactorEventLoop running=True closed=False debug=False>
    print(loop.time())     # 262388.18...（和 perf_counter 同一套单调时钟）
    await asyncio.sleep(0.01)
    return "协程的返回值"

print(asyncio.run(show_loop()))     # 协程的返回值
```

- Windows 上默认是 **`ProactorEventLoop`**（Linux 上是 `SelectorEventLoop`，**未实测**）。
- **一个线程同时只能有一个正在跑的循环**：协程里再 `asyncio.run()` 报
  `RuntimeError: asyncio.run() cannot be called from a running event loop`；
  循环外调 `asyncio.get_running_loop()` 报 `RuntimeError: no running event loop`（都实测）。
- 事件循环是**单线程**的，所以"循环卡住了"永远只有一个原因：**有你没 `await` 的阻塞代码**。

### 3.4 `await asyncio.sleep()` vs `time.sleep()`：阻塞调用会卡死整个循环

```python
async def blocking_worker(name):
    print(f"  {name} 开始（用 time.sleep 阻塞）")
    time.sleep(1)                 # ← 整个事件循环被这里卡住
    print(f"  {name} 结束")


async def good_worker(name):
    print(f"  {name} 开始（用 await asyncio.sleep）")
    await asyncio.sleep(1)
    print(f"  {name} 结束")


async def main():
    t0 = time.perf_counter()
    await asyncio.gather(blocking_worker("A"), blocking_worker("B"), blocking_worker("C"))
    print(f"阻塞写法总耗时 {time.perf_counter() - t0:.2f}s")     # 3.00s
    t0 = time.perf_counter()
    await asyncio.gather(good_worker("A"), good_worker("B"), good_worker("C"))
    print(f"非阻塞写法总耗时 {time.perf_counter() - t0:.2f}s")   # 1.01s
```

`time.sleep` 版的真实输出是 **A 开始 → A 结束 → B 开始 → B 结束 → C 开始 → C 结束**（3.00s）：
**一个 `time.sleep(1)` 把整个事件循环按住了 1 秒**，另外两个协程连"开始"都没打印，只能排队。
`await asyncio.sleep` 版三个"开始"连在一起打出，**1.01s** 结束。

> ⚠️ **坑**：在协程里调用任何阻塞函数——`time.sleep`、`requests.get`、`open().read()`、
> 重的 `json.loads`、纯计算循环——**整个程序都会停**。现象：并发 10 个请求，
> 耗时等于 10 个请求之和，和"顺序执行"一模一样。
> 处理：换成异步库（`httpx` / `aiohttp` / `aiofiles`）；没有异步版本就
> `await asyncio.to_thread(阻塞函数, 参数)` 把它丢进线程池（至少能挪出主线程）。
> 这是本节最常在生产里踩的坑。

### 3.5 "async 函数不 await 就不会执行"（初学者最常踩的坑，实测）

```python
async def hello():
    print("  你好，我是协程体")


result = hello()
print(result, type(result))     # <coroutine object hello at 0x...> <class 'coroutine'>
print("→ 协程体里的 print 一个字都没出现")

asyncio.run(hello())            # 你好，我是协程体      ← 这才是执行

import gc
forgot = hello()
del forgot
gc.collect()                    # RuntimeWarning: coroutine 'hello' was never awaited
```

**调用 `async def` 函数得到的是一个"协程对象"，不是执行结果。**
它必须被 `await`、被 `asyncio.run()`、或被 `create_task` 交给事件循环，才会真正跑。
忘了的话 Python 只在**对象被垃圾回收时**给一条 `RuntimeWarning`，
而且这条警告经常出现在程序最后，很容易被日志冲掉。

> 顺带：`await` 只能跟"可等待对象"。`await` 一个普通函数返回的 `int` 会报
> `TypeError: object int can't be used in 'await' expression`（实测）——
> 这条报错本身就是提示："你 await 了一个根本不是协程的东西"。

### 3.6 `gather` / `as_completed` / `TaskGroup` / `Queue`

```python
async def worker(name, delay):
    await asyncio.sleep(delay)
    return f"{name}({delay}s)"


async def main():
    tasks = [asyncio.create_task(worker(f"任务{i}", d)) for i, d in enumerate([0.3, 0.1, 0.2])]
    for fut in asyncio.as_completed(tasks):
        print("  完成：", await fut)     # 任务1(0.1s) → 任务2(0.2s) → 任务0(0.3s)

    async with asyncio.TaskGroup() as tg:            # TaskGroup（3.11+，本机 3.13 可用）
        t1 = tg.create_task(worker("甲", 0.2))
        t2 = tg.create_task(worker("乙", 0.1))
    print(t1.result(), t2.result())                  # 甲(0.2s) 乙(0.1s)

    async def boom():
        await asyncio.sleep(0.05)
        raise ValueError("我炸了")

    try:
        async with asyncio.TaskGroup() as tg:        # 一个任务炸了，整组一起炸
            tg.create_task(worker("陪葬的", 1))
            tg.create_task(boom())
    except* ValueError as eg:
        print("  捕获到异常组：", eg.exceptions)      # (ValueError('我炸了'),)


asyncio.run(main())
```

| 工具 | 语义 | 什么时候用 |
|---|---|---|
| `gather(*aws)` | 一起跑，**按传入顺序**返回结果列表 | 结果要一一对应 |
| `as_completed(tasks)` | **按完成顺序**产出 | 谁快先用谁 |
| `TaskGroup` | `with` 退出 = 全部完成；一个失败整组取消 | 一组任务要么全成、要么全不算（3.11+） |
| `asyncio.Queue` | 异步队列，`await q.put()` / `await q.get()` | 生产者-消费者流水线 |

`asyncio.Queue` 和线程版用法几乎一样，只是 `put`/`get` 都要 `await`；
消费者靠 `await q.put(None)` 这种**哨兵值**判断结束（实测：生产者放 `货物0..2`，
消费者逐个拿走，收到哨兵后退出）。
超时用 `asyncio.wait_for(协程, timeout=0.3)` 或 `async with asyncio.timeout(0.3):`，
两个都抛 `TimeoutError`（实测 `wait_for` 在 0.31 秒时抛出）。
**`TaskGroup`、`asyncio.timeout`、`except*` 都属于 3.11 新增**——本机 3.13.15 实测可用；
"3.11 新增"这个版本号我没在 3.11 上实测过。

### 3.7 `asyncio` 不加速 CPU 计算

```python
def cpu_task(n=4_000_000):
    total = 0
    for i in range(n):
        total += i * i
    return total


async def main():
    t0 = time.perf_counter(); cpu_task(); one = time.perf_counter() - t0
    t0 = time.perf_counter()
    for _ in range(3): cpu_task()
    serial = time.perf_counter() - t0
    t0 = time.perf_counter()
    await asyncio.gather(*[asyncio.to_thread(cpu_task) for _ in range(3)])
    threaded = time.perf_counter() - t0
    print(f"单个 {one:.2f}s 串行 3 个 {serial:.2f}s to_thread(3 个) {threaded:.2f}s")
    # 实测：单个 0.16s   串行 3 个 0.60s   to_thread(3 个) 0.53s
```

`to_thread` 把计算挪进了线程池，但**有 GIL**，所以 3 个任务还是 0.53 秒，
和串行的 0.60 秒基本一样，绝不会变成 1/3。**要真并行 CPU，只有多进程一条路**（2.8 实测 3.49x）。

### 3.8 什么时候用 asyncio / 线程 / 进程

| | 线程 `threading` | 进程 `multiprocessing` | 协程 `asyncio` |
|---|---|---|---|
| 并行能力 | 只有 IO 有效（GIL） | **有闲置核时 CPU 真并行**（2.8 实测不稳定） | 只有 IO 有效（单线程） |
| 单个开销 | 0.2 ms + 独立栈 | **806 ms**（2.9） | **约 7 µs**（200 个 1.42ms） |
| 能同时跑多少 | 几百个就吃力 | 约等于 CPU 核数 | **几万个没问题**（10 万个 `sleep(0)` 0.835s） |
| 共享状态 | 直接共享，**要加锁** | 不共享，要显式通信 | 直接共享，**不需要锁**（协作式，不抢占） |
| 生态要求 | 任何库都能用 | 函数要能 pickle | **必须用异步库**，同步库会卡死循环 |
| 适合 | 少量、混合、老库 | CPU 密集 | 大量并发网络 IO |

**选的顺序**：先问"是不是在等外部"——不是（烧 CPU）就去多进程；是的话再问"并发量有多大"——
几十个用线程（生态最省心），几百上千个连接用 asyncio（否则内存和切换成本吃不消）。

## 4. 正则表达式 `re`（覆盖 10.4）

官方入口 <https://docs.python.org/3/library/re.html>（API 参考）与
<https://docs.python.org/3/howto/regex.html>（HOWTO，讲思路的那篇）。

### 4.1 `match` / `search` / `fullmatch`：只匹配开头 vs 扫描全文（实测）

```python
import re

text = "我的电话是 13812345678，备用电话 13987654321"
print(re.match(r"电话", text))          # None                    ← 只从位置 0 试
print(re.match(r"我的", text))          # <re.Match object; span=(0, 2), match='我的'>
print(re.search(r"电话", text))         # <re.Match object; span=(2, 4), match='电话'>  ← 全文扫描
print(re.fullmatch(r"\d+", "12345"))    # <re.Match ... match='12345'>   ← 要求整串匹配
print(re.fullmatch(r"\d+", "12345abc")) # None
print(re.match(r"\d+", "12345abc"))     # <re.Match ... span=(0, 5), match='12345'>  ← 不要求到结尾
```

| 函数 | 从哪开始找 | 要求匹配到结尾吗 | 失败返回 |
|---|---|---|---|
| `match` | **只试位置 0** | 不要求 | `None` |
| `search` | **全文扫描**，返回第一个 | 不要求 | `None` |
| `fullmatch` | 只试位置 0 | **要求整个字符串都匹配** | `None` |

最常踩的是把 `match` 当 `search` 用（"电话"不在开头就是 `None`）。
"失败返回 `None`"也要当心：`None.group()` 报
`AttributeError: 'NoneType' object has no attribute 'group'`（实测）——
取结果前要么判空，要么用 `if m := re.search(...)`（海象运算符）。

### 4.2 元字符速查

| 符号 | 含义 | 例 |
|---|---|---|
| `.` | 任意一个字符（默认不含换行） | `a.c` 匹配 `abc`、`a c` |
| `^` `$` | 串首 / 串尾（`MULTILINE` 下是行首 / 行尾） | `^ab` |
| `*` `+` `?` | 0+ 次 / 1+ 次 / 0 或 1 次 | `ab*`、`ab+`、`ab?` |
| `{m}` `{m,n}` `{m,}` | 正好 m 次 / m 到 n 次 / 至少 m 次 | `\d{4}`、`a{2,3}` |
| `[...]` | 字符集合；里面大多数字符失去特殊含义 | `[abc]`、`[0-9]`、`[^0-9]` |
| `\` | 转义，或引入预定义类 | `\.` 匹配真正的点 |
| `\|` | 或（**优先级最低**） | `cat\|dog` |
| `( )` | 分组 + 捕获 | `(ab)+` |
| 量词后跟 `?` | 变成**非贪婪** | `.*?` |

### 4.3 字符类与预定义类

| 写法 | 等价于 | 含义 |
|---|---|---|
| `\d` / `\D` | `[0-9]` / `[^0-9]` | 数字 / 非数字 |
| `\w` / `\W` | `[a-zA-Z0-9_]` + Unicode 字母 / 取反 | 单词字符 |
| `\s` / `\S` | `[ \t\n\r\f\v]` / 取反 | 空白 |
| `\b` | —— | **单词边界**（零宽，不消耗字符） |
| `.` | —— | 任意字符，`DOTALL` 下含换行 |

> ⚠️ `\d` `\w` `\s` 在 **Unicode 模式（默认）**下能匹配中文：`re.findall(r"\w+", "中文abc")`
> 会把汉字也算进 `\w`。只想匹配 ASCII 就加 `re.ASCII`。

### 4.4 贪婪 vs 非贪婪（实测）

```python
html = "<b>加粗</b> 和 <i>斜体</i>"
tag = "<a href='x' title='y'>点我</a>"
print(re.search(r"<.*>", html).group())          # <b>加粗</b> 和 <i>斜体</i>   ← 贪婪：吞到底
print(re.search(r"<.*?>", html).group())         # <b>                          ← 非贪婪
print(repr(re.search(r"'(.*)'", tag).group(1)))  # "x' title='y"                ← 贪婪坏掉
print(repr(re.search(r"'(.*?)'", tag).group(1))) # 'x'                          ← 非贪婪正确
```

**量词默认贪婪**（能吞多少吞多少），后面加 `?` 变成非贪婪（能少吞就少吞）。
`?` 有两种身份：单独出现（跟在字符后）是量词"0 或 1 次"（`colou?r` 匹配 color 和 colour）；
**跟在另一个量词后面**才是"非贪婪"（`.*?`、`+?`、`{2,5}?`）。

### 4.5 `findall` / `finditer` / `sub` / `split`

```python
log = "2026-01-05 10:00:01 INFO 启动完成\n2026-01-05 10:00:03 ERROR 连接超时"
print(re.findall(r"\d{4}-\d{2}-\d{2}", log))                  # ['2026-01-05', '2026-01-05']
print(re.findall(r"(\d{4}-\d{2}-\d{2}) (\d+:\d+:\d+)", log))  # [('2026-01-05','10:00:01'), ...]
for m in re.finditer(r"(\d{2}:\d{2}:\d{2}) (\w+)", log):
    print(m.group(1), m.group(2), m.span())                   # 10:00:01 INFO (11, 24)
print(re.sub(r"(INFO|ERROR)", "[级别]", log).splitlines()[0])  # 2026-01-05 10:00:01 [级别] 启动完成
print(re.sub(r"\d{11}", lambda m: m.group()[:3] + "****" + m.group()[-2:], "打 13812345678 找我"))
                                                              # 打 138****78 找我
print(re.split(r"[,;]", "a,b;c,,d"))                          # ['a', 'b', 'c', '', 'd']
```

**`findall` 和 `finditer` 的区别就是"要不要 Match 对象"**：`findall` 直接给字符串/元组列表
（**有 1 个组就返回组、有多个组就返回元组，整个匹配反而丢了**——这是它最容易误解的地方）；
`finditer` 给 `Match` 对象，能拿 `group()`、`span()`。要位置信息、要多个组，就用 `finditer`。
`re.sub` 的第二个参数可以是函数，这是"按规则改文本"的标准写法（掩码、查表替换）。
`re.split` 和 `str.split` 的区别在"分隔符能不能有多种/变长"：`"a,b;c".split(",")` 做不到按逗号**或**分号切。

### 4.6 分组与命名分组

```python
line = "2026-01-05T10:00:01 用户=wang 动作=login"
m = re.search(r"用户=(?P<user>\w+)\s+动作=(?P<action>\w+)", line)
print(m.groupdict())      # {'user': 'wang', 'action': 'login'}
print(m.group("user"), m.groups())        # wang ('wang', 'login')
print(re.search(r"((\d{4})-(\d{2}))-(\d{2})", "2026-01-05").groups())
                          # ('2026-01', '2026', '01', '05')
print(re.search(r"(?:ab)(cd)", "abcd").groups())                # ('cd',)  非捕获组不占编号
print(re.search(r"(\w+) \1", "hello hello world").group())      # hello hello  反向引用
```

`group(0)` 是整个匹配，`group(1)` 起是各组；**组的编号按"左括号出现的顺序"**（嵌套时外层的编号小）；
`(?:...)` 是"只分组不捕获"；`\1` 反向引用第 1 个组（命名组用 `(?P=name)`）；
**没参与匹配的可选组值是 `None`**，不是空字符串——拼接前要判空。

### 4.7 `re.compile` 预编译与 `flags`

```python
phone = re.compile(r"1[3-9]\d{9}")
print(phone.findall("13812345678 和 13987654321"))    # ['13812345678', '13987654321']
# 10 万次实测：每次现写模式 0.041s，预先 compile 0.020s  ← 快一倍
print(re.findall(r"^abc", "ABC\nabc", re.IGNORECASE | re.MULTILINE))   # ['ABC', 'abc']
print(re.findall(r"(?i)abc", "ABC abc"))                               # ['ABC', 'abc']
```

- **`re` 内部有缓存**，所以模块级函数不是"每次都重新编译"；但每次调用都要走一层查表，
  实测 10 万次 `0.041s` vs 预编译 `0.020s`——循环里、热点路径上一定要 `compile` 一次反复用。
- flags 可以按位置传、按关键字传（`flags=`）、按位或组合（`re.I | re.M`），也能在模式里内联
  （`(?i)` / `(?m)` / `(?x)`）。常用：`IGNORECASE`(`I`)、`MULTILINE`(`M`，让 `^$` 匹配每行)、
  `DOTALL`(`S`，让 `.` 匹配换行)、`VERBOSE`(`X`，忽略空白和 `#` 注释)、`ASCII`(`A`)。
- `VERBOSE` 是让复杂正则变可读的救星，可以写成多行 + 行尾 `# 注释`：

```python
pattern = re.compile(r"""
    (?P<year>  \d{4} ) -      # 年
    (?P<month> \d{2} ) -      # 月
    (?P<day>   \d{2} )        # 日
""", re.VERBOSE)
pattern.search("今天是 2026-01-05").groupdict()   # {'year': '2026', 'month': '01', 'day': '05'}
```

（上面最后一行写成 `print(pattern.search("今天是 2026-01-05").groupdict())` 就能看到输出。）

> ⚠️ **坑**：`VERBOSE` 下**空格会被忽略**，想匹配空格要写 `\s` / `[ ]` / 转义 `\ `。
> 实测 `re.search(r"(?x) a b", "ab")` 能匹配（匹配到的就是 `ab`）。

### 4.8 原始字符串 `r""` 为什么几乎必须（实测反例）

```python
print("\d", len("\d"), "\d" == r"\d")     # \d 2 True   ← 原样保留，但有 SyntaxWarning
print(repr("\b"), len("\b"))              # '\x08' 1    ← \b 是退格符！
print(re.search("\bcat\b", "a cat here")) # None        ← 静默失败，不报任何错
print(re.search(r"\bcat\b", "a cat here"))# <re.Match object; span=(2, 5), match='cat'>
```

`"\d"` 被当成"未知转义"，保持原样但**送你一条
`SyntaxWarning: invalid escape sequence '\d'`**（实测），所以它"碰巧能跑"。
而 `"\b"` **不报任何警告**，它变成退格符 `\x08`，于是匹配**静默地永远失败**——
同类还有 `\n` `\t` `\a` `\f` `\v` `\0`，它们在 Python 字符串里先被解释成控制字符，
正则引擎根本看不到那个反斜杠。原始字符串还有一个副作用：不能以奇数个反斜杠结尾，
**`r"\d+\"` 是语法错误**（实测 `SyntaxError: unterminated string literal ... perhaps you escaped the end quote?`）；
想匹配一个真的反斜杠写 `r"\\"` 或用字符类 `[\\]`。**所以：正则的模式一律 `r"..."`。**

### 4.9 前瞻 / 后顾断言（简要）

```python
print(re.findall(r"\d+(?=元)", "苹果 5元 香蕉 3元 橘子 4个"))   # ['5', '3']
print(re.search(r"\d+(?=元)", "苹果 5元").span())               # (3, 4) ← 没吃掉"元"
print(re.findall(r"\d+(?!元)", "苹果 5元 香蕉 3元 橘子 4个"))   # ['4']
print(re.findall(r"(?<=价格:)\d+", "价格:100 数量:3"))          # ['100']
re.compile(r"(?<=ab+)c")     # re.error: look-behind requires fixed-width pattern
```

**断言只"看一眼"，不消耗字符**（`span()` 是 `(3, 4)` 证明"元"没被吃掉）。
`(?=...)` 正前瞻、`(?!...)` 负前瞻、`(?<=...)` 正后顾、`(?<!...)` 负后顾。
**后顾必须是定长**，里面不能写 `*` `+`（实测报上面那条 `re.error`）。
想连"元"一起取出来，用组 `(\d+元)` 而不是前瞻。

### 4.10 回溯灾难：一个能被正则卡死的例子（实测）

```python
pat = re.compile(r"(a+)+$")
for n in (18, 20, 22, 24):
    s = "a" * n + "b"
    t0 = time.perf_counter(); pat.search(s)
    print(f"n={n} 耗时 {(time.perf_counter() - t0) * 1000:.2f} ms")
```

```
n=18 耗时 12.31 ms     n=20 耗时 50.02 ms
n=22 耗时 198.18 ms    n=24 耗时 772.71 ms        ← 每加两个字符，耗时乘 4
```

**指数级**。原因：`(a+)+` 里两层量词让引擎有**指数多条**切分方式，末尾那个 `b` 又让每条路
都"差一点成功"，于是它把所有组合都试一遍才敢说"不匹配"。
更可怕的是**看起来人畜无害的模式也会平方级爆炸**：实测 `r"a+$"` 处理 `"a"*10000+"b"` 要 `244 ms`、
`"a"*20000+"b"` 要 `921 ms`、`"a"*40000+"b"` 要 `5279 ms`——输入 ×2，耗时 ×4。

**处理办法（按优先级）**：① **把模式写具体**（用 `\d{4}-\d{2}-\d{2}` 而不是 `.*-.*-.*`）；
② **别嵌套量词**（`(a+)+`、`(.*)*` 几乎总能重写成 `a+`、`.*`）；
③ Python 3.11+ 支持**占有量词**和**原子组**（本机 3.13 实测可用，版本号未逐版本实测）：
`a++` 不让回溯（实测 `"a"*40000+"b"` 从 `5279 ms` 降到 `465 ms`），
`(?>a+)+` 直接掐断指数爆炸（同样输入 `0.00 ms`）；
④ **限制输入长度**（对用户输入先 `if len(s) > 1000: raise`，最便宜的保险）；
⑤ 真要处理不可信输入，换成手写解析循环或专注此问题的库。

### 4.11 `str` 方法 vs 正则：能用 `str.startswith` 就别上正则

```python
urls = ["https://a.com/x", "http://b.com/y", "ftp://c.com/z"]
print([u.startswith(("https://", "http://")) for u in urls])      # [True, True, False]
print([bool(re.match(r"https?://", u)) for u in urls])            # [True, True, False]
# 10 万轮实测：startswith 0.026s，正则 0.100s  ← 正则慢 3.8 倍
```

| 你要做的事 | 用什么 |
|---|---|
| 固定前缀 / 后缀 | `str.startswith` / `endswith` / `removeprefix` |
| 固定子串在不在 | `in` / `str.find` / `str.index` |
| 固定分隔符切分 | `str.split` / `str.rsplit` |
| 固定字符替换 | `str.replace` |
| 变长模式、多分支、跨位置、要分组提取 | `re` |

判据只有一条：**"这个模式是不是固定不变的字符串"**。是 → `str` 方法（更快、更可读、
不会被正则元字符坑）；不是（比如"一个大写字母 - 四位 - 四位 - 四位"这种形状）→ 才上 `re`。
正则的第一原则是**尽量不要用**：每多一层正则，代码的可维护性就掉一档。

## 5. 日期时间 `datetime`（覆盖 10.5）

官方入口：<https://docs.python.org/3/library/datetime.html>（四个类都在这里）｜
格式符对照表：<https://docs.python.org/3/library/datetime.html#strftime-and-strptime-format-codes>｜
时区库：<https://docs.python.org/3/library/zoneinfo.html>｜计时：<https://docs.python.org/3/library/time.html>。

### 5.1 四个类 + `now()`/`today()` + `str()`/`isoformat()`

```python
import datetime
d = datetime.date(2026, 1, 5)
t = datetime.time(10, 30, 15)
dt = datetime.datetime(2026, 1, 5, 10, 30, 15)
delta = datetime.timedelta(days=1, hours=2, minutes=3)
print(str(d), "|", str(t), "|", str(dt), "|", str(delta))
# 2026-01-05 | 10:30:15 | 2026-01-05 10:30:15 | 1 day, 2:03:00
print(dt.year, dt.month, dt.day, dt.weekday(), dt.isoweekday(), dt.date(), dt.time())
# 2026 1 5 0 1 2026-01-05 10:30:15     ← weekday 0=周一，isoweekday 1=周一
print(datetime.datetime.now(), "|", datetime.datetime.today(), "|", datetime.datetime.now(datetime.UTC))
# 2026-10-05 22:32:15.779178 | 2026-10-05 22:32:15.779187 | 2026-10-05 14:32:15.779191+00:00
print(str(dt), "|", dt.isoformat())     # 2026-01-05 10:30:15 | 2026-01-05T10:30:15
dt2 = datetime.datetime(2026, 1, 5, 10, 30, 15, 123456)
print(str(dt2), "|", dt2.isoformat(), "|", dt2.isoformat(timespec="seconds"))
# 2026-01-05 10:30:15.123456 | 2026-01-05T10:30:15.123456 | 2026-01-05T10:30:15
```

- **`now()` 和 `today()` 只差一处**：`now()` 能带时区参数（`datetime.now(datetime.UTC)` 返回 aware），
  `today()` 永远返回 naive。
- **`str()` 和 `isoformat()` 只差中间那个字符**：`str` 用空格，`isoformat` 用 `T`
  （写进 JSON / 数据库用 `isoformat()`，两者都能被 `fromisoformat` 解回来）；
  带微秒时都会带上 `.123456`，不想要就 `timespec="seconds"`。
- 构造非法日期直接报错（实测）：`date(2026, 2, 30)` → `ValueError: day is out of range for month`；
  `date(2026, 13, 1)` → `ValueError: month must be in 1..12`。

### 5.2 naive vs aware：有没有时区（最容易出事的地方）

```python
naive = datetime.datetime(2026, 1, 5, 10, 30)
aware = datetime.datetime(2026, 1, 5, 10, 30, tzinfo=datetime.UTC)
print(naive.tzinfo, aware.tzinfo, naive.utcoffset())      # None UTC None
try: naive - aware
except TypeError as e: print(e)     # can't subtract offset-naive and offset-aware datetimes
try: naive < aware
except TypeError as e: print(e)     # can't compare offset-naive and offset-aware datetimes
print(naive.astimezone(datetime.UTC))   # 2026-01-05 02:30:00+00:00 ← 把 naive 当本地时间
print(datetime.datetime.now().astimezone().tzinfo)   # 中国标准时间（本机 +8）
```

**naive = 没有时区信息的"裸时间"，aware = 带 `tzinfo` 的时间。**
Python 用报错阻止你混用它们——这是好事，但报错信息没告诉你该给哪个加时区。

> ⚠️ **坑**：`naive.astimezone(...)` **不报错**，它会默默把 naive 当成"本机时间"。
> 上面 `10:30` 被当成北京时间，转成 UTC 变成 `02:30`。如果那个 naive 其实是 UTC 存的
> （从数据库、从 API 读出来的经常是），你就得到一个**差了 8 小时的错误时间，而且没有任何异常**。
> 处理：只在"确实是本机时间"或"只做本地日期运算"时用 naive；一旦要存、要传、要跨时区比较，
> 一律用 aware。判断标准：这个时间要不要跟别的时区/别的机器的时钟对齐？要 → aware。

### 5.3 `ZoneInfo` 与夏令时（含 Windows 特有坑）

```python
from zoneinfo import ZoneInfo, ZoneInfoNotFoundError, available_timezones
print(len(available_timezones()), "Asia/Shanghai" in available_timezones())   # 598 True
try: ZoneInfo("Not/AZone")
except ZoneInfoNotFoundError as e: print(e)   # 'No time zone found with key Not/AZone'
utc = datetime.datetime(2026, 6, 1, 12, 0, tzinfo=datetime.UTC)
for name in ("Asia/Shanghai", "America/New_York", "Asia/Tokyo"):
    z = utc.astimezone(ZoneInfo(name)); print(name, z, z.utcoffset())
# Asia/Shanghai     2026-06-01 20:00:00+08:00  8:00:00
# America/New_York  2026-06-01 08:00:00-04:00  -1 day, 20:00:00
# Asia/Tokyo        2026-06-01 21:00:00+09:00  9:00:00
w = datetime.datetime(2026, 1, 15, 12, tzinfo=ZoneInfo("America/New_York"))
s = datetime.datetime(2026, 7, 15, 12, tzinfo=ZoneInfo("America/New_York"))
print(w.utcoffset(), s.utcoffset())   # -1 day, 19:00:00  -1 day, 20:00:00   冬 vs 夏（夏令时）
for h in (1, 2, 3):
    print(h, datetime.datetime(2026, 3, 8, h, 30, tzinfo=ZoneInfo("America/New_York")).astimezone(datetime.UTC))
# 1 → 06:30 UTC   2 → 07:30 UTC   3 → 07:30 UTC  ← 本地 2:30 被跳过，和 3:30 同一个 UTC
```

三个真实现象：① **同一瞬间不同时区显示不同**（UTC 12:00 = 上海 20:00 / 纽约 08:00 / 东京 21:00）；
② **同一时区冬夏偏移不一样**（纽约冬 `-05:00`、夏 `-04:00`）——所以"偏移固定是 -5 小时"这种假设
一定会出问题，也不能自己拿 `timedelta(hours=-5)` 手动算时区；
③ **夏令时切换那天有些本地时间不存在**（2026-03-08 凌晨 2:30 被跳过，和 3:30 有同一个 UTC 时刻）；
秋天回拨那天反过来有本地时刻出现两次，用 `fold=0/1` 区分（实测 `2026-11-01 01:30` 的
fold=0 → `05:30 UTC`、fold=1 → `06:30 UTC`）。

> ⚠️ **坑（Windows 特有）**：`ZoneInfo` 需要一份**时区数据库**。Linux/macOS 用系统的，
> **Windows 没有，必须额外装 `tzdata`**，否则连 `ZoneInfo("Asia/Shanghai")` 都报
> `ZoneInfoNotFoundError`。本机实测 `tzdata 2026.4` 已装所以上面能跑；
> **"没装 tzdata 时的报错"我没实测**（不能为了测试去卸载它），按文档是同一个异常。
> 处理：`python -m pip install tzdata`，并写进 `requirements.txt` / `pyproject.toml`。

### 5.4 `strftime` / `strptime` 格式符对照表（含一次实测往返）

| 格式符 | 含义 | `2026-01-05 14:30:09` 的输出 |
|---|---|---|
| `%Y` / `%y` | 四位年 / 两位年 | `2026` / `26` |
| `%m` / `%d` | 月 / 日（补零） | `01` / `05` |
| `%H` / `%I` | 24 小时 / 12 小时 | `14` / `02` |
| `%M` / `%S` / `%p` | 分 / 秒 / AM-PM（跟 `%I` 配） | `30` / `09` / `PM` |
| `%A` / `%a` / `%B` / `%b` | 星期全名/缩写 / 月名全名/缩写 | `Monday`/`Mon`/`January`/`Jan` |
| `%j` / `%U` / `%w` | 一年第几天 / 第几周（周日为首）/ 周几（0=周日） | `005` / `01` / `1` |
| `%%` | 一个百分号 | `%` |
| `%z` / `%Z` | UTC 偏移 / 时区名（aware 才有） | `+0800` / `中国标准时间` |

```python
dt = datetime.datetime(2026, 1, 5, 14, 30, 9)
text = dt.strftime("%Y-%m-%d %H:%M:%S")
back = datetime.datetime.strptime(text, "%Y-%m-%d %H:%M:%S")
print(repr(text), back, back == dt)   # '2026-01-05 14:30:09' 2026-01-05 14:30:09 True ← 往返成功
print(datetime.datetime.fromisoformat(dt.isoformat()) == dt)     # True
try: datetime.datetime.strptime("2026/01/05", "%Y-%m-%d")
except ValueError as e: print(e)   # time data '2026/01/05' does not match format '%Y-%m-%d'
print(datetime.datetime.strptime("2026-1-5", "%Y-%m-%d"))        # 2026-01-05 00:00:00
print(repr(datetime.date(2026, 1, 5).strftime("%H")))            # '00'（date 没有时分秒）
```

注意三点：① 分隔符必须完全对得上（`/` 配 `-` 报 `ValueError`）；
② **`%m`/`%d` 能接受不补零的写法**（`2026-1-5` 也解析成功），所以别用 `strptime` 做格式校验；
③ `date.strftime("%H")` 在 Windows 上返回 `'00'`（不报错，但结果是假的），**日期类不要用时间格式符**。

### 5.5 `timedelta`：加减、`total_seconds()` 的坑、不可变

```python
d = datetime.date(2026, 1, 5)
print(d + datetime.timedelta(days=30), d - datetime.timedelta(days=30))   # 2026-02-04 2025-12-06
print(datetime.datetime(2026, 1, 5, 23, 30) + datetime.timedelta(minutes=45))  # 2026-01-06 00:15:00
print(repr(datetime.timedelta(hours=-1)))   # datetime.timedelta(days=-1, seconds=82800)
span = datetime.datetime(2026, 1, 6, 1, 0) - datetime.datetime(2026, 1, 5, 0, 0)
print(type(span).__name__, repr(span), span.total_seconds())   # timedelta ... 90000.0
try: float(span)
except TypeError as e: print(e)   # float() argument must be ... not 'datetime.timedelta'
print(datetime.timedelta(minutes=90) > datetime.timedelta(hours=1))     # True
dt0 = datetime.datetime(2026, 1, 5, 10, 0)
print(dt0.replace(hour=12), dt0.hour)      # 2026-01-05 12:00:00 10   ← replace 返回新对象
try: dt0.hour = 12
except AttributeError as e: print(e)   # attribute 'hour' of ... objects is not writable
```

> ⚠️ **坑**：**两个 `datetime` 相减得到的是 `timedelta`，不是秒数**。想直接 `float(span)` /
> `int(span)` 都报 `TypeError`（实测），必须写 `span.total_seconds()`。
> 而且它返回 **float**（`timedelta(microseconds=1).total_seconds()` 是 `1e-06`），
> 浮点大数有精度问题，要整数秒用 `span // datetime.timedelta(seconds=1)` 或 `round()`。

> ⚠️ **坑**：负的 `timedelta` 会被"规范化"成 `days` 为负、`seconds` 为正
> （`timedelta(hours=-1)` 是 `days=-1, seconds=82800`）。
> **永远不要直接读 `.seconds` 当"总秒数"**——它只是"去掉整天之后剩下的秒数"。
> 要总秒数用 `total_seconds()`，要天数用 `.days`。

`datetime` 是**不可变**的：`replace()` 返回新对象、原对象不变，直接 `dt0.hour = 12` 报
`AttributeError`（实测）。好处是天生线程安全、可以当 `dict` 的键；代价是每次"修改"都要接住返回值，
别写成 `dt.replace(hour=12)` 然后继续用 `dt`。

### 5.6 `time` 模块：计时该用 `perf_counter`，以及时间戳的转换陷阱

```python
t0 = time.time()
print(t0, datetime.datetime.fromtimestamp(t0), datetime.datetime.fromtimestamp(t0, datetime.UTC))
# 1791210757.9325147  2026-10-05 22:32:37.932515  2026-10-05 14:32:37.932515+00:00
p0 = time.perf_counter(); time.sleep(0.05); print(time.perf_counter() - p0)   # 0.05009919998701662
for name in ("time", "monotonic", "perf_counter"):
    i = time.get_clock_info(name)
    print(f"{name:<12} monotonic={i.monotonic} adjustable={i.adjustable} resolution={i.resolution}")
# time         monotonic=False adjustable=True  resolution=1e-07
# monotonic    monotonic=True  adjustable=False resolution=1e-07
# perf_counter monotonic=True  adjustable=False resolution=1e-07
ts = 1767600000
print(datetime.datetime.fromtimestamp(ts), "|", datetime.datetime.fromtimestamp(ts, datetime.UTC))
# 2026-01-05 16:00:00 | 2026-01-05 08:00:00+00:00      ← 同一个时间戳差 8 小时
```

**为什么计时必须用 `perf_counter`**：`get_clock_info("time")` 实测是
**`monotonic=False, adjustable=True`**——它会被 NTP 校时、手动改系统时间影响，**可能倒退**
（"倒退"本身我没法在不改系统时间的前提下复现，**未实测**；但 `adjustable=True` 就是
"允许被调整"的官方声明）。`perf_counter` 是 `monotonic=True, adjustable=False`，只增不减。
注意：**两者在这台机器上的分辨率实测一样**（都是 `1e-07`），所以"`time.time()` 精度不够"
这个常见说法 **在 Windows 11 上不成立**（实测最小非零差约 `2.4e-07` vs `1.0e-07`）——
真正的理由是**单调性**，不是精度。补充：`perf_counter()` 每次调用约 60 ns
（`datetime.now()` 约 169 ns，实测 20 万次），量微秒级代码时别把它算进去。

**Unix 时间戳的转换陷阱**：**`fromtimestamp()` 不写时区参数时，按"本地时间"解释**。
实测同一个时间戳 `1767600000`：本地是 `2026-01-05 16:00:00`，UTC 是 `2026-01-05 08:00:00+00:00`。

> ⚠️ **坑**：把时间戳存进数据库 / 传给别的服务时，一定明确"这个数字是 UTC 还是本地"。
> 推荐：时间戳统一按 UTC 理解，转换时永远写 `datetime.fromtimestamp(ts, datetime.UTC)`，
> 或用 aware 的 `dt.timestamp()`（走绝对时刻，不会歧义）。
> 老写法 `utcfromtimestamp()` / `utcnow()` 已废弃，用 `fromtimestamp(ts, datetime.UTC)` /
> `datetime.now(datetime.UTC)` 代替（**"已废弃"这个状态我没实测**，只实测了新写法可用）。

## 6. 网络编程 `socket`（覆盖 10.6）

官方入口 <https://docs.python.org/3/library/socket.html>（API）与
<https://docs.python.org/3/howto/sockets.html>（HOWTO，讲概念的）；
一行起服务那个在 <https://docs.python.org/3/library/http.server.html>。

### 6.1 概念：TCP/IP 分层与"socket 是什么"

| 层 | 干什么 | 你在这层看到的 |
|---|---|---|
| 应用层 | HTTP / DNS / SMTP…… | `requests`、浏览器 |
| 传输层 | TCP（可靠、有序）/ UDP（快、可能丢） | **端口号**、`socket` |
| 网络层 | IP，负责把包送到哪台机器 | **IP 地址** |
| 链路层 | 网卡、网线、Wi-Fi | 网卡驱动 |

**socket 就是"一个通信端点"**，用三样东西唯一确定：**协议 + IP + 端口**。
（一条 TCP 连接其实是**四元组**：源 IP、源端口、目的 IP、目的端口——所以服务端能同时服务很多人。）
`(IP, 端口)` 这个二元组在 Python 里就是一个元组，贯穿整节。
角色只有两种：**服务端**（`bind` → `listen` → `accept`）和**客户端**（`connect`）。

### 6.2 最小可跑例子（本机 `127.0.0.1` 实测）

```python
import socket, threading


def serve(listener):
    conn, addr = listener.accept()          # 阻塞，直到有客户端连进来
    with conn:
        print(f"服务端：收到来自 {addr} 的连接")
        data = conn.recv(1024)
        print(f"服务端：收到 {data!r}（{len(data)} 字节）")
        conn.sendall(b"ECHO: " + data)


with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as listener:
    listener.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
    listener.bind(("127.0.0.1", 0))          # 端口写 0 = 让系统挑一个空闲的
    listener.listen(1)
    host, port = listener.getsockname()
    print(f"服务端：正在监听 {host}:{port}")
    t = threading.Thread(target=serve, args=(listener,)); t.start()
    with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as client:
        client.connect((host, port))
        client.sendall("你好，服务端".encode("utf-8"))
        reply = client.recv(1024)
        print(f"客户端：收到 {reply!r}")
        print("客户端：解码后 =", reply.decode("utf-8"))
    t.join()
```

```
服务端：正在监听 127.0.0.1:58619
服务端：收到来自 ('127.0.0.1', 58620) 的连接
服务端：收到 b'\xe4\xbd\xa0\xe5\xa5\xbd\xef\xbc\x8c\xe6\x9c\x8d\xe5\x8a\xa1\xe7\xab\xaf'（18 字节）
客户端：收到 b'ECHO: \xe4\xbd\xa0\xe5\xa5\xbd...'
客户端：解码后 = ECHO: 你好，服务端
```

| 调用 | 谁用 | 作用 |
|---|---|---|
| `socket(AF_INET, SOCK_STREAM)` | 两边 | 建一个 TCP socket（`SOCK_DGRAM` 是 UDP） |
| `bind((host, port))` | 服务端 | 占住"本机哪个 IP 的哪个端口" |
| `listen(n)` | 服务端 | 开始监听，`n` 是等待队列长度 |
| `accept()` | 服务端 | **阻塞**直到有人连上来，返回 `(新 socket, 对端地址)` |
| `connect((host, port))` | 客户端 | 主动连过去 |
| `sendall(bytes)` / `recv(n)` | 两边 | 发字节 / 收字节；**对方关闭后 `recv` 返回 `b""`** |
| `getsockname()` | 两边 | 看自己这一端的 `(IP, 端口)` |

三个必须记住的点：① **`send`/`recv` 只认 `bytes`**，字符串要 `encode("utf-8")`、
收到要 `decode("utf-8")`（输出里的 `\xe4\xbd\xa0...` 就是"你好，服务端"的 UTF-8 字节——
**网络上传的是字节，不是文本**）；② **端口写 `0` 表示"随便给我一个空闲端口"**，
再用 `getsockname()` 问出来；③ **`accept()` 返回的是一个新 socket**，专门服务这个连接，
`listener` 继续用来 `accept` 下一个——所以"一个服务端服务多个人"要用循环 + 线程/协程。

### 6.3 `recv(1024)` **不等于**"收 1024 字节"（TCP 没有消息边界）

```python
# 服务端：连着发三次，逻辑上是三条"消息"
for chunk in (b"AAA", b"BBB", b"CCC"):
    conn.sendall(chunk)
# 客户端：睡 0.3 秒后第一次 recv(1024)
first = c.recv(1024)
```

```
A. 客户端第一次 recv(1024) 拿到 1024 字节，开头是 b'AAABBBCCCxxxxxxxxxxx'
   这 1024 字节里同时包含 AAA、BBB、CCC 吗：True        ← 粘包
B. 服务端发了 5000 字节，客户端再 recv(1024)：只拿到 1024 字节（不是 5000）   ← 短读
   收到 b'' → 对端关闭，这才是"读完了"
C. 全程一共收到 5009 字节（服务端总共发了 9 + 5000 = 5009 字节）
```

**两件事同时被证明了**：① **粘包**——服务端 `send` 三次，客户端第一次 `recv` 就把三条全收到了。
TCP 是**字节流**，它只保证"字节按顺序到、不丢不重"，**不保证"你 send 一次、我 recv 一次"**；
② **短读**——服务端发了 5000 字节，`recv(1024)` 只给 1024。参数 `1024` 是
"**我这次最多要这么多**"，不是"我要正好这么多"，剩下 3985 字节还在内核缓冲区里，要**循环 `recv`**。
**判断"读完了"的唯一正确方式**：`recv` 返回 `b""`（空 bytes），这才是对端**关闭了连接**。
在那之前，任何一次 `recv` 都可能给你 0～1024 之间的任何字节数。

> ⚠️ **坑**：`if len(data) == 1024: 说明还没收完`——**错**。一次 `recv` 返回多少
> **只和"当时内核缓冲区里有多少"有关**：可能刚好 1024，也可能只有 3。
> 想按"消息"收发必须**自己在应用层定协议**：① "先发 4 字节长度，再发正文"；
> ② 用固定分隔符（如 `\n`）自己切；③ 用现成的协议库。这就是实际项目里几乎不写裸 socket 的原因。

### 6.4 端口被占用、连不上：真实报错

```python
a = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
a.bind(("127.0.0.1", 0)); port = a.getsockname()[1]; a.listen(1)
b = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
try: b.bind(("127.0.0.1", port))          # 同一个端口再来一次
except OSError as e: print(e, e.winerror)
# [WinError 10048] 通常每个套接字地址(协议/网络地址/端口)只允许使用一次。 10048
c = socket.socket(socket.AF_INET, socket.SOCK_STREAM); c.settimeout(3)
try: c.connect(("127.0.0.1", 1))          # 没人监听的端口
except OSError as e: print(type(e).__name__, e)
# ConnectionRefusedError [WinError 10061] 由于目标计算机积极拒绝，无法连接。
```

| WinError | 含义 | 通常怎么办 |
|---|---|---|
| 10048 | 地址已被占用（**实测**） | 换端口；或 `netstat -ano \| findstr :端口` 找占用进程 |
| 10061 | 连接被拒绝（对面没监听，**实测**） | 检查服务启动没有、端口对不对 |
| 10060 / 10054 / 10013 | 超时 / 被对端重置 / 权限不足（绑 80 等） | **未实测**，按含义排查（防火墙、特权端口） |

> ⚠️ **坑（Windows 特有）**：`SO_REUSEADDR` 在 **Linux 和 Windows 上语义完全不同**。
> Linux 上它是"复用 TIME_WAIT 状态的地址"，两个进程同时 bind 还是失败；
> **Windows 上它允许两个 socket 绑同一个端口**。实测：不开它第二次 bind 报 `WinError 10048`；
> **开了之后第二次 bind 成功，两个 socket 同时监听 `127.0.0.1:59919`**。
> 后果很具体：**`python -m http.server 8765` 起第二遍不报错**，两个服务都"在监听"，
> 请求却全被第一个接收——你会以为"我改了代码怎么没生效"（实测就是这样，
> 第二个服务的日志一行都没有）。处理：端口被占时**别只看有没有报错**，
> 用 `netstat -ano | findstr :8765` 确认，或换个端口试。

### 6.5 `python -m http.server`：一行起一个静态服务

```bash
python -m http.server 8766 --bind 127.0.0.1    # PowerShell / Git Bash 都一样
```

用 `urllib` 请求本机（不算外部网络），实测：

```
/index.html → 200 OK | text/html  | '<h1>hello from python -m http.server</h1>\n'
/a.txt      → 200 OK | text/plain | 'plain text file\n'
/nope.html  → 404 File not found
```

服务端往终端打的访问日志（真实输出，`http.server` 的官方页在
<https://docs.python.org/3/library/http.server.html>）：

```
127.0.0.1 - - [05/Oct/2026 22:34:03] "GET /index.html HTTP/1.1" 200 -
127.0.0.1 - - [05/Oct/2026 22:34:03] "GET /a.txt HTTP/1.1" 200 -
```

它做四件事，正好把 6.2 节那串 API 用全了：`bind` + `listen` + 循环 `accept` + 解析 HTTP +
按路径找文件。**要传文件给自己/同事，这是最快的方式**（`--bind 0.0.0.0` 时局域网别人也能访问，
**注意那等于把你这个目录公开了**）。它自己也是标准库里"怎么用 `socketserver` 写服务端"的范例：
<https://docs.python.org/3/library/socketserver.html>。

### 6.6 为什么写网络程序几乎不用裸 socket

上面几段已经暴露了裸 socket 的全部麻烦：字节编码、消息边界、循环收发、超时重试、重定向、压缩、
cookie、TLS、HTTP 解析……**每一样都要你自己写对**，而它们全都被别人写对过很多次了。

| 你要做的事 | 用什么 |
|---|---|
| 发 HTTP 请求、调 API | `requests` / `httpx`（**本笔记不展开**，见 `00_知识点总览.md` 第四节"不展开"边界） |
| 高并发爬取 | `aiohttp` / `httpx.AsyncClient`（同上，不展开） |
| 写 HTTP 服务端 | Flask / FastAPI（同上，不展开） |
| 自定义二进制协议、端口探测 | **裸 socket 在这里是合理的** |
| 学"网络到底怎么工作" | 裸 socket（本节的目的） |

**学会裸 socket 的价值不是"以后用它写业务"**，而是：出问题时你知道
`ConnectionRefusedError` 是 TCP 层的事、`read timeout` 是应用层的事，
以及为什么"我明明 send 了一次，对面收到两次"根本不是 bug。

<summary>答案</summary>

1. 实测**正好 20000，一次都不丢**。因为 `counter += 1` 编译成
   `LOAD_GLOBAL / LOAD_CONST / BINARY_OP / STORE_GLOBAL` 四条直线指令，
   CPython 只在**函数调用**和**循环回边**这些 eval breaker 检查点切换线程，这四条中间没有检查点。
   换成 `counter += one()`（读写之间夹一次调用）就一定会丢——实测 2 线程 10 万次跑出
   141939 / 143574 / 143621。要点：这是**实现细节**，不是语言保证，"跑了一万次都对"不能证明没有竞态。
2. 不写 `join()` 不会杀线程，只是主线程不等它——后果是主线程读到半成品（实测不 join 时 `result` 还是 `[]`）。
   非 daemon 线程会让**进程**等它（实测进程 1.00 秒才退出）；daemon 线程主线程一退就被掐掉（0.00 秒）。
3. 因为 Windows 只有 `spawn`：子进程会**把你的主模块重新 import 一遍**。
   不写 `__main__` 保护 → 子进程又执行顶层启动代码 → 报
   `RuntimeError: An attempt has been made to start a new process before the current process has finished its bootstrapping phase.`
   函数不是顶层（lambda / 局部函数）→ 子进程反序列化不到目标函数，报
   `PicklingError: Can't pickle <function <lambda> ...: attribute lookup <lambda> on __main__ failed`
   或 `AttributeError: Can't get local object '...<locals>.inner'`。
4. 4 线程稳定在 **1.0x 附近**（实测 1.02 / 1.04 / 0.79 / 1.06 / 1.01 / 1.13x）：GIL 让纯计算
   不释放锁，线程只能轮流跑，"快不了"是**语言层面确定的**，所以和机器负载无关。
   4 进程只是**有机会**真并行（各有自己的解释器和 GIL，能被调到不同核），能不能拿到取决于
   "有闲置核心 + 任务够长 + 启动开销摊得薄"：机器较闲时 3.49x，机器繁忙时同一段代码变成
   0.96 / 0.62 / 1.09 / 1.02x——所以**没有一个可复现的倍数**。
   判断有没有真并行不能看总耗时（被 spawn 开销和负载掩盖），要看**重叠度**：
   让每个子进程把自己的起止 `perf_counter()` 写进共享内存，`干活时间之和 / 墙钟跨度` ≈1 就是串行、
   ≈4 才是真并行（2.8 节 6 次实测在繁忙机器上只有 0.32～1.11x，从没接近 4x）。
5. `time.sleep` 阻塞的是**整个事件循环**（单线程），三个任务只能排队，实测 **3.00s**；
   `await asyncio.sleep` 只是"让出"，三个任务一起等，实测 **1.01s**。
6. `match` 返回 `None`（它**只从位置 0 开始试**，"电话"不在开头）；
   `search` 返回匹配对象 `span=(2, 4)`（它**全文扫描**，找第一个）。
7. 返回 `None`。因为普通字符串 `"\b"` 被 Python 解释成**退格符** `'\x08'`
   （实测 `repr` 是 `'\x08'`，长度 1），正则引擎看到的是退格符而不是"单词边界"，
   所以永远匹配不上，而且**不报任何错**。正确写法：`re.search(r"\bcat\b", "a cat here")`。
8. `recv(1024)` **只保证"最多给我 1024 字节"**（一次系统调用的缓冲区上限），其余什么都不保证：
   TCP 是字节流、没有消息边界，所以既可能把多次 `send` 粘成一次 `recv`
   （实测三条 `AAA`/`BBB`/`CCC` 一次就到齐），也可能只给你一部分（实测 5000 字节只先拿到 1024）。
   要读全必须循环 `recv` 直到返回 `b""`。
9. 得到 `datetime.timedelta`。想拿秒数写 `span.total_seconds()`
   （`float(span)` / `int(span)` 都会报 `TypeError`）。注意 `.seconds` 只是"去掉整天后剩下的秒数"，
   负数还会被规范化（`timedelta(hours=-1)` 是 `days=-1, seconds=82800`）。
10. 因为 `perf_counter` 是**单调时钟**：实测 `time.get_clock_info("time")` 是
    `monotonic=False, adjustable=True`，而 `perf_counter` 是 `monotonic=True, adjustable=False`。
    `time.time()` 会被系统校时改动，量出来的耗时可能不对甚至为负。
    （注意：在这台机器上两者分辨率实测都是 `1e-07`，所以理由**不是**精度。）
