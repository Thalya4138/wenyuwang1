## 0. 先记住三件事

1. **`python` 是一个可执行程序**（解释器），不是一个"语言"。
   你写的 `.py` 文件本身不能运行，是解释器读了它才会执行。
2. **`pip` 装东西装进某一个具体的 Python 里**。
   机器上有几个 Python，就有几个互不相干的包仓库。装错地方 = 明明装了却 `import` 不到。
3. **`open()` 不写 `encoding` 时用的是系统区域编码**，不是 UTF-8。
   这台机器上是 `cp936`（GBK），这是中文乱码的头号来源。

## 1. 安装 Python 与解释器（覆盖 0.1）

### 1.1 装的是什么

从 <https://www.python.org/downloads/> 下载的安装包，装出来的东西有三部分：

| 部分 | 是什么 | 在哪 |
|---|---|---|
| 解释器 `python.exe` | 真正读代码、执行代码的程序 | 安装目录根下 |
| 标准库 | 几百个随 Python 一起发布的模块 | `Lib\` |
| `pip` | 第三方包安装器 | `Scripts\` |

**注意**：解释器和标准库是绑死的。你升级 Python，标准库跟着换，但**第三方包不会跟着搬**（见第 4 节）。

### 1.2 验证装好了

打开终端（Windows 上是 PowerShell 或 Git Bash），敲：

```bash
python --version
```

这台机器上的输出：

```
Python 3.13.15
```

再问它自己"你是谁、在哪"：

```bash
python -c "import sys; print(sys.version); print(sys.executable)"
```

```python
import sys

print(sys.version)      # 3.13.15 (tags/v3.13.15:4061bc4, Aug  5 2026, 13:05:39) [MSC v.1944 64 bit (AMD64)]
print(sys.version_info) # sys.version_info(major=3, minor=13, micro=15, releaselevel='final', serial=0)
print(sys.executable)   # C:\Users\Wang\AppData\Local\Programs\Python\Python313\python.exe
```

`sys.version_info` 比 `sys.version` 好用，因为它是**结构化的、能比较**：

```python
import sys

if sys.version_info >= (3, 10):
    print("支持 match/case")
```

> **为什么重要**：写笔记、写库、贴 issue 时，第一条永远是"你哪个 Python、哪条路径"。
> 很多"我照抄了却报错"的根因就是版本不同。

### 1.3 Windows 的 `python` vs `python3`

- **Windows**：官方安装包只提供 `python.exe`，没有 `python3.exe`。
  敲 `python3` 通常报"不是内部或外部命令"——这不是你装错了。
- **Linux / macOS**：`python3` 是标准名，`python` 可能指向 Python 2 或根本不存在。

所以网上教程里命令不一致是正常的，跟平台走。

### 1.4 PATH 是什么，以及为什么"装了但敲 python 没反应"

`PATH` 是一串目录列表。你在终端敲一个命令，系统**按顺序**在这些目录里找同名程序，找到就执行。

Python 安装时如果没勾 "Add python.exe to PATH"，就出现"明明装了，敲 `python` 却找不到"。

排查顺序：

```bash
# 1. 系统到底找到的是哪个 python（Windows）
where.exe python

# 2. Linux / macOS / Git Bash
which -a python python3

# 3. 如果完全找不到，但你知道装在哪，直接全路径调用
"C:\Users\Wang\AppData\Local\Programs\Python\Python313\python.exe" --version
```

> **`where` / `which -a` 的用法值得养成习惯**：它让你看见"实际被调用的那个"，
> 而不是"你以为的那个"。凡是遇到"装了却不行"，第一个动作都是它。

### 1.5 Python 版本怎么选（2026 年的现实）

| 版本 | 状态 | 判断 |
|---|---|---|
| 3.9 | 已停止维护 | 不要用。很多现代库已不支持 |
| 3.10 | 安全修复期尾声 | `match/case` 从这版开始有 |
| 3.11 | 安全修复期 | 明显更快，异常信息更详细 |
| 3.12 | 安全修复期 | f-string 语法放宽、类型参数语法（PEP 695） |
| **3.13** | **安全修复期（本机版本）** | 实验性自由线程构建；`cgi` 等模块被移除（PEP 594） |
| 3.14 | 稳定版 | `t` 字符串模板（PEP 750）、延迟注解（PEP 649）等新特性 |

**结论：新项目用 3.12 以上；这台机器上的 3.13 完全够用。**

> ⚠️ **诚实标注**：上表里 3.12 之后的具体特性，我**没有在这台机器上逐条实测**
> （本机只有 3.13.15，`.venv` 是 3.14.7，拿不到 3.12 去对照）。
> 需要精确到"哪个 PEP 改了哪个行为"时，请查官方 What's New：
> <https://docs.python.org/3/whatsnew/index.html>
>
> 关于"官方文档能不能打开"这件事，本仓库踩过一次错，这里说准确：
> **命令行 `curl` / PowerShell 取不到 `docs.python.org`（SSL 失败、HTTP 000），
> 但 AI 的抓取工具能取到（实测 HTTP 200）**。详见
> [`01a_三源交叉核对.md`](01a_三源交叉核对.md) 第 1 节——那份文件就是靠抓官方文档做出来的。

## 2. REPL 交互模式（覆盖 0.2）

### 2.1 怎么进

```bash
python
```

看到 `>>>` 就进去了。**REPL** = Read-Eval-Print Loop：读一行 → 求值 → 打印结果 → 再来一次。

```
>>> 1 + 1
2
>>> name = "王"
>>> print("你好，" + name)
你好，王
```

### 2.2 REPL 与脚本的核心区别

| | REPL | 脚本文件 |
|---|---|---|
| 输入方式 | 敲一行执行一行 | 一次读完整个文件再执行 |
| **表达式结果自动打印** | ✅ 会 | ❌ 不会，只有 `print` 才输出 |
| 状态 | 关掉就全没了 | 关掉文件还在 |

**这是初学者最容易踩的坑**：

```
>>> 1 + 1
2
```

写进文件里：

```python
# demo.py
1 + 1
```

运行 `python demo.py` —— **什么都不输出**。

因为脚本模式下，表达式算出来的值如果没人接住，就直接被丢掉了。
REPL 会自动帮你 `print`，文件不会。

```python
# 想看到结果，必须显式打印
print(1 + 1)   # 2
```

### 2.3 下划线 `_`：REPL 的专用变量

```
>>> 100 * 3
300
>>> _ + 1
301
>>> _ * 2
602
```

`_` 永远保存**上一次表达式的结果**。临时算几步很方便。

> **实测细节**：`_` 只在**真正的交互会话**里生效。
> 本机验证方式是 `python -i` 后逐行输入，输出依次是 `300` `/` `301` `/` `602`——
> 符合预期。但如果把这几行**一次性管道喂给 `python`**（不带 `-i`），
> 会得到 `NameError: name '_' is not defined`：
> 那种情况下 Python 不是按交互模式逐条求值的，`_` 这个机制没被激活。
> 讲这件事是因为**"我照抄了却报错"经常是执行方式不同，而不是代码不同**。

⚠️ 但一旦你自己给 `_` 赋了值，这个魔法就没了：

```
>>> _ = "别覆盖我"
>>> 1 + 1
2
>>> _
'别覆盖我'
```

### 2.4 退出与中断

| 操作 | 效果 |
|---|---|
| `exit()` 或 `quit()` | 正常退出 |
| `Ctrl+Z` 再回车（Windows）/ `Ctrl+D`（Linux/macOS） | 发送文件结束符，正常退出 |
| `Ctrl+C` | 中断**当前正在执行**的代码，REPL 本身还活着 |

`Ctrl+C` 这一条很重要：如果你不小心写了个死循环：

```
>>> while True:
...     pass
```

`Ctrl+C` 能救你出来，不用关窗口。

### 2.5 比裸 REPL 好用的东西

裸 `>>>` 有几个硬缺点：不能上下翻历史（Windows 下依赖 `pyreadline` 之类的补丁）、
不能多行编辑、不能补全、粘贴多行代码容易乱。

**在本机实测可用的升级选项**（不必都装，挑一个）：

```bash
# 选项 1：Python 自带的 IDLE（装 Python 时就有，不用装）
idle

# 选项 2：IPython，交互体验提升最大
pip install ipython
ipython

# 选项 3：本仓库已经在用的 Jupyter
pip install jupyterlab
jupyter lab
```

本仓库根目录里就有 `.venv` 和 `pyproject.toml`（依赖里有 `ipykernel`），
`Practice/` 与 `Resources from class/` 下有 `.ipynb` 文件——那些就是 notebook 环境。

## 3. 运行脚本文件（覆盖 0.3）

### 3.1 最小流程

新建 `hello.py`：

```python
# hello.py
print("hello, python")
```

运行：

```bash
python hello.py
```

> 注意：`python hello.py` 里的 `hello.py` 是**传给解释器的参数**，
> 不是"双击运行"。解释器读这个文件、逐行执行。

### 3.2 执行顺序：自上而下

```python
print("第 1 行")
print("第 2 行")
x = 1 / 0        # ← 这里炸了
print("第 3 行")  # 永远不会执行
```

```
第 1 行
第 2 行
Traceback (most recent call last):
  File "demo.py", line 3, in <module>
    x = 1 / 0
    ~~^~~
ZeroDivisionError: division by zero
```

**Python 不是编译型语言，但也不是"读一行执行一行"（那是 REPL）。**
它是：先把整个文件编译成字节码，再从第一条语句开始执行。
所以**语法错误会在任何代码执行之前就报出来**：

```python
print("你会看到我吗")
if True        # ← 少了冒号，语法错误
    pass
```

```
  File "demo.py", line 2
    if True
           ^
SyntaxError: expected ':'
```

**"你会看到我吗" 一个字都没打印**。语法错误就是整个文件都不跑。

而运行时错误（`ZeroDivisionError`、`NameError`）只会在执行到那一行时才炸，
**前面的代码已经执行过了**——这可能已经改了文件、发了请求。这个区别在调试时很关键。

### 3.3 `-m`：把模块当脚本跑

```bash
python -m json.tool somefile.json    # 格式化 JSON
python -m http.server 8000           # 当前目录起一个 HTTP 服务
python -m venv .venv                 # 建虚拟环境（下一节）
python -m pip install requests       # 用当前 Python 的 pip
python -m this                       # 彩蛋：The Zen of Python
```

**`-m` 和直接跑文件的区别**：`-m` 会让这个模块在"包"的语境下运行
（它的 `__name__` 是 `__main__`，但 `sys.path` 的首项是当前目录而不是模块文件所在目录）。

**强烈建议用 `python -m pip` 而不是直接 `pip`**：

```bash
pip install requests          # 这个 pip 是哪个 Python 的？不确定
python -m pip install requests # 明确：就是当前这个 python 的
```

在有多份 Python 的机器上，"`pip` 装上了但 `python` 导入不到"几乎全是这个原因。

### 3.4 常见运行方式速查

```bash
python script.py                 # 常规
python -i script.py              # 跑完不退出，进入 REPL，变量都还在（调试神器）
python -c "print('一行代码')"     # 直接执行一段字符串
python -X utf8 script.py         # 强制 UTF-8 模式（见第 6 节）
python -u script.py              # 关掉输出缓冲，日志实时刷出
python -OO script.py             # 去掉文档字符串（省内存，慎用）
```

`-i` 值得单独记一下：脚本跑完（哪怕中途出错）直接落到交互模式，
可以直接检查当时的变量状态：

```bash
python -i crash.py
# 报错退出到 >>> 提示符
>>> print(x)   # 看看炸的时候 x 是什么
```

### 3.5 脚本怎么读取"参数"

命令行参数在 `sys.argv` 里，它是一个列表：

```python
# args_demo.py
import sys

print("程序名：", sys.argv[0])
print("收到的参数：", sys.argv[1:])
print("参数个数：", len(sys.argv) - 1)
```

```bash
python args_demo.py a b c
```

```
程序名： args_demo.py
收到的参数： ['a', 'b', 'c']
参数个数： 3
```

`sys.argv[0]` 是**脚本名本身**，所以真正的参数从 `sys.argv[1]` 开始。
参数复杂时改用 `argparse`（见 `99_标准库索引.md`）。

## 4. `venv` 虚拟环境（覆盖 0.4）

> **这一节是本章最重要的。** 跳过它，后面一定会遇到"版本冲突"和"装了半天白装"。

### 4.1 先看问题，再看解法

假设你机器上只有一个全局 Python，然后：

```bash
# 项目 A 需要 requests 2.25
python -m pip install "requests==2.25.0"

# 三个月后，项目 B 需要 requests 2.32
python -m pip install "requests==2.32.0"
```

**问题来了**：pip 把全局那份 `requests` **覆盖**成了 2.32。
现在你回去跑项目 A —— 它拿到的是 2.32，可能就跑不通了。

这就是**依赖地狱（dependency hell）**：全局只有一份包，
所有项目被迫共享同一套版本。

还有两个连带问题：

- **权限**：装到系统目录可能需要管理员权限，装完污染整个系统。
- **升级 Python 会丢包**：`site-packages` 在解释器目录里，换版本 = 全没了。

### 4.2 虚拟环境干什么

`venv` 给你每个项目一份**独立的 `site-packages`**（装第三方包的地方）。
不同项目可以有不同版本的同一个包，互不影响。

```
项目A/
  .venv/            ← 只属于项目A的 Python 环境
  main.py

项目B/
  .venv/            ← 只属于项目B的 Python 环境
  main.py
```

> **它不是虚拟机，不是容器，也不复制一个 Python。**
> `venv` 造出来的 `python.exe` 只是**一个小跳板**，它转发给真正的解释器，
> 但把"去哪找包"这条路径改了。所以它创建极快（几秒），占空间极小。

### 4.3 完整操作流程（Windows）

```bash
# 1. 进入项目目录
cd C:\Users\Wang\Desktop\git

# 2. 创建虚拟环境（放到 .venv 子目录，这是约定俗成的名字）
python -m venv .venv

# 3. 激活
#    PowerShell：
.\.venv\Scripts\Activate.ps1
#    Git Bash：
source .venv/Scripts/activate
#    传统 cmd：
.venv\Scripts\activate.bat

# 4. 确认激活成功（路径应该指向 .venv）
python -c "import sys; print(sys.executable)"
# C:\Users\Wang\Desktop\git\.venv\Scripts\python.exe   ← 看到 .venv 就对了

# 5. 退出
deactivate
```

**激活成功的标志**：终端提示符前面多出 `(.venv)`。

> ⚠️ **PowerShell 常见报错**：`无法加载文件 Activate.ps1，因为在此系统上禁止运行脚本`
>
> 这是 PowerShell 的执行策略（ExecutionPolicy）默认拦住了 `.ps1`。
> 两种处理：
> ```powershell
> # 方案一（推荐，只影响当前用户，风险小）
> Set-ExecutionPolicy -Scope CurrentUser RemoteSigned
>
> # 方案二（临时，只对当前这个窗口生效）
> Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
> ```
> 或者干脆用 Git Bash 激活，就绕开了这个问题。

### 4.4 不想"激活"怎么办

激活只是**把 `.venv\Scripts` 临时加到 PATH 前面**。不激活也能用，直接调全路径：

```bash
.venv\Scripts\python.exe main.py
.venv\Scripts\python.exe -m pip install requests
```

**这个写法其实更安全**，因为不存在"忘了激活，结果装到全局去了"的风险。
写脚本、写 CI、写文档时推荐用全路径。

### 4.5 `venv` 造出来了什么

```
.venv/
├── pyvenv.cfg          ← 关键文件，记录"我基于哪个 Python 建的"
├── Scripts/
│   ├── python.exe      ← 跳板程序
│   ├── pip.exe
│   └── Activate.ps1    ← 激活脚本
└── Lib/
    └── site-packages/  ← 这个环境的第三方包都在这
```

`pyvenv.cfg` 长这样：

```ini
home = C:\Users\Wang\AppData\Local\Programs\Python\Python313
include-system-site-packages = false
version = 3.13.15
```

`include-system-site-packages = false` 是默认值，意思是**不继承全局的包**——
这正是"隔离"的实现方式。

> **⚠️ 不要提交 `.venv/` 到 git。**
> 它是**本地生成物**，路径里写死了你机器的绝对路径，换台机器就废了。
> 本仓库的 `.gitignore` 已经忽略 `.venv/`，这是对的。
> 别人拿到你的代码后，靠 `requirements.txt` / `pyproject.toml` 自己重建环境。

### 4.6 建环境时的选项

```bash
python -m venv .venv --system-site-packages   # 允许看到全局包（一般不要）
python -m venv .venv --clear                  # 先清空再建
python -m venv .venv --upgrade-deps           # 顺便把 pip/setuptools 升级到最新
```

### 4.7 本仓库实际用了什么

看一眼本仓库根目录：

```
.venv/               ← 存在的虚拟环境（本机实测：里面是 Python 3.14.7）
.python-version      ← 写着 3.14
pyproject.toml       ← 依赖声明：ipykernel、numpy；dev 组有 ruff
uv.lock              ← 锁文件，记录每个包的精确版本
```

**这说明本仓库用的是 `uv`，不是裸 `pip`。** 对比一下：

| | 裸 `venv` + `pip` | `uv` |
|---|---|---|
| 建环境 | `python -m venv .venv` | `uv venv` |
| 装包 | `python -m pip install numpy` | `uv add numpy` |
| 装开发依赖 | `pip install ruff` | `uv add --dev ruff` |
| 记录依赖 | 手动维护 `requirements.txt` | 自动写进 `pyproject.toml` + `uv.lock` |
| 速度 | 慢（逐个下载安装） | 快很多（并行 + 全局缓存） |

`uv` 是近几年流行起来的替代品，**它做的事和 pip 一样，只是更快、更会把依赖关系记下来**。
（历史渊源：`uv` 由 Astral 开发，同一家做的 `ruff` 就是本项目 dev 依赖里那个 linter。）

如果哪天要重建这个仓库的环境：

```bash
uv sync          # 按 uv.lock 精确还原
```

**但要先确认 `uv` 装着**（本机 `uv 0.12.15` 可用）：

```bash
uv --version
```

> ⚠️ **注意一个不一致**：`pyproject.toml` 里写 `requires-python = ">=3.14"`，
> `.python-version` 写 `3.14`，`.venv` 里实际是 3.14.7（`pyvenv.cfg` 实测），
> 但**本机系统装的 `python` 是 3.13.15**。
> 也就是说 `uv sync` 走 `.venv` 里的 3.14.7，而你在终端直接敲 `python` 用的是 3.13。
> 这个不一致不算 bug（`uv` 自己管理 Python 版本），
> 但**跑代码时要知道自己用的是哪个**——这正是第 1.2 节那条 `sys.executable` 的用处。

## 5. `pip` 安装包（覆盖 0.5）

### 5.1 核心操作

```bash
python -m pip install requests              # 装最新版
python -m pip install "requests==2.32.0"    # 精确版本
python -m pip install "requests>=2.30,<3"   # 版本区间

python -m pip install -r requirements.txt   # 按文件批量装
python -m pip list                          # 当前环境装了哪些包
python -m pip show requests                 # 某个包的详细信息（版本、依赖、位置）
python -m pip uninstall requests            # 卸载
python -m pip install --upgrade requests    # 升级
```

`pip show` 特别值得记住，它直接回答"我装的到底是哪个、装到哪去了"：

```bash
python -m pip show requests
```

```
Name: requests
Version: 2.32.3
Location: C:\Users\Wang\Desktop\git\.venv\Lib\site-packages
Requires: certifi, charset-normalizer, idna, urllib3
```

看 `Location` —— 一眼就知道装进了哪个环境。

### 5.2 第一原则：先确认环境，再装包

```bash
python -c "import sys; print(sys.executable)"   # 我现在是哪个 Python？
python -m pip install 某包                        # 再装
```

**"装了却 import 不到" 的排查三步**：

```bash
# 1. 确认解释器是谁
python -c "import sys; print(sys.executable)"

# 2. 确认包在不在这个解释器的视角里
python -m pip list | findstr 某包      # Windows PowerShell 用 findstr 或 Select-String
python -m pip list | grep 某包          # Git Bash

# 3. 确认 import 时到底找到的是哪个文件（有时候是本地同名文件抢了）
python -c "import 某包; print(某包.__file__)"
```

第 3 步很关键：如果你项目里有个文件叫 `json.py`，那 `import json` 会导入**你那个文件**，
而不是标准库。这种问题用 `__file__` 一眼看穿。

### 5.3 国内镜像源（本机实测：本环境直连 PyPI 可用，但慢时该换）

```bash
# 单次使用
python -m pip install requests -i https://pypi.tuna.tsinghua.edu.cn/simple

# 永久配置
python -m pip config set global.index-url https://pypi.tuna.tsinghua.edu.cn/simple
python -m pip config list    # 查看当前配置
```

常用镜像：

| 镜像 | 地址 |
|---|---|
| 清华 TUNA | `https://pypi.tuna.tsinghua.edu.cn/simple` |
| 阿里云 | `https://mirrors.aliyun.com/pypi/simple/` |
| 中科大 | `https://pypi.mirrors.ustc.edu.cn/simple/` |

### 5.4 `requirements.txt` 与"可复现"

```bash
python -m pip freeze > requirements.txt   # 导出当前环境的完整包清单
python -m pip install -r requirements.txt # 照着装
```

导出来长这样：

```
certifi==2026.2.25
charset-normalizer==3.4.1
idna==3.10
requests==2.32.3
urllib3==2.3.0
```

**为什么必须写死版本（`==`）**：不写死的话，半年后别人（或你自己）重建环境
会装到"当时的最新版"，而依赖升级可能带来行为变化。
写死版本 = 把"当时能跑"这件事**固定下来**。

> **⚠️ `pip freeze` 的坑**：它导出的是"**这个环境里现在装着的所有东西**"，
> 不是"你项目真正需要的"。如果你在同一个环境里顺手装过别的工具，
> 那些也会被写进去，别人装了会莫名其妙。
> 干净做法：**一个项目一个环境**，环境里只装这个项目要的东西。

### 5.5 现代做法：`pyproject.toml`

`requirements.txt` 只是"一列包"，不区分"项目真正依赖"和"依赖的依赖"，
也不区分"运行时需要"和"只是开发时用"。

`pyproject.toml` 是现在的事实标准，看本仓库的实际内容：

```toml
[project]
name = "git"
version = "0.1.0"
requires-python = ">=3.14"
dependencies = [
    "ipykernel>=7.3.0",
    "numpy>=2.5.3",
]

[dependency-groups]
dev = [
    "ruff>=0.16.8",
]
```

读法：

| 段落 | 含义 |
|---|---|
| `[project]` | 这个项目本身：名字、版本、要求的最低 Python |
| `dependencies` | **运行时依赖**：跑这个项目必须有的包 |
| `[dependency-groups] dev` | **开发依赖**：写代码时用、发布时别人不需要（这里是 linter `ruff`） |
| `requires-python` | 低于这个版本直接拒绝安装，而不是装完再莫名其妙报错 |

配合 `uv.lock`，`uv sync` 就能在任何机器上还原出一模一样的环境。
这就是"可复现环境"的完整形态。

### 5.6 装包时的常见坑

| 现象 | 原因 | 处理 |
|---|---|---|
| `pip: command not found` | PATH 里没有 `Scripts`，或没激活环境 | 用 `python -m pip` |
| 装完 `import` 还是失败 | 装到了另一个 Python | `python -m pip show` 看 Location |
| 装到一半报权限错误 | 往系统目录装 | 建虚拟环境 |
| 编译类包安装失败（如需要 C 编译器） | 没有构建工具链 | 优先找有没有预编译 wheel；本机是 Windows，很多包直接给 wheel |
| `import` 到本地同名文件 | 自己项目里有个 `xxx.py` | `python -c "import xxx; print(xxx.__file__)"` |

## 6. 编码与 `.py` 文件规范（覆盖 0.6）

### 6.1 源文件编码：这代 Python 不用操心

Python 3 规定：**源文件默认按 UTF-8 解码**。

```python
# 这个文件存成 UTF-8，就能直接写中文，不需要任何声明
名字 = "王"
print("你好，世界")
```

只有在文件不是 UTF-8 时，才需要在**前两行**加编码声明：

```python
# -*- coding: gbk -*-
```

**这行在现代代码里基本绝迹了。** 见到它，说明那份文件很老，或者作者环境有问题。

⚠️ Windows 上有个隐患：很多老编辑器默认把 `.py` 存成 GBK。
现在 VS Code、PyCharm 默认都是 UTF-8，正常用不会有问题，
但如果文件里中文变成 `锟斤拷` 或直接 `SyntaxError`，先怀疑文件编码。

### 6.2 `open()` 的默认编码不是 UTF-8（**本机实测**）

这是**这台机器上真实存在的坑**，我在本机跑过：

```python
import locale
print(locale.getpreferredencoding(False))   # cp936

with open("test.txt", "w") as f:
    print(f.encoding)                        # cp936  ← 不是 UTF-8！
```

**结论：`open()` 不写 `encoding` 时，用的是系统区域编码。**
这台机器上是 `cp936`（GBK）。

后果：

- 你写了 UTF-8 的文件，别人用默认设置读 → 乱码
- 你把别人给的 UTF-8 文件用默认设置读 → `UnicodeDecodeError`

**唯一正确的做法：读写文本文件时永远显式指定 `encoding`。**

```python
# ✅ 永远这样写
with open("data.txt", "w", encoding="utf-8") as f:
    f.write("中文内容\n")

with open("data.txt", "r", encoding="utf-8") as f:
    text = f.read()

print(text)   # 中文内容
```

三种全局解法（改环境而不是改代码，优先级从高到低）：

```bash
# 方案一：环境变量（推荐，一次设置长期有效）
setx PYTHONUTF8 1        # Windows，设完要重开终端

# 方案二：每次运行加参数（等价于方案一）
python -X utf8 script.py

# 方案三：只影响当前这个终端会话
$env:PYTHONUTF8 = "1"    # PowerShell
export PYTHONUTF8=1      # Git Bash
```

**开了 UTF-8 模式之后，`open()` 的默认编码真的会变。本机实测对照：**

| 运行方式 | `open("x.txt","w").encoding` | `sys.stdout.encoding` | `locale.getpreferredencoding(False)` |
|---|---|---|---|
| 默认（什么都没设） | **`cp936`** | `gbk` | `cp936` |
| `PYTHONUTF8=1` 或 `-X utf8` | **`utf-8`** | `utf-8` | `utf-8` |

**这是本节最值得记住的一条**：同一份代码，在开与不开 UTF-8 模式的两台机器上
**默认行为不同**——不开的时候它按 GBK 读写文件，开了之后按 UTF-8。
所以"我这跑得好好的"不能证明"换台机器也对"。

**但即使开了 UTF-8 模式，代码里显式写 `encoding="utf-8"` 仍然是必须的**，两个理由：

1. 读你代码的人机器上不一定开着这个开关（默认行为就回到 `cp936`）
2. `PYTHONUTF8` 是**运行环境**的属性，而 `encoding="utf-8"` 是**代码**的属性——
   代码应该自己说明自己的意图，而不是依赖别人配好环境

> 详细展开（文本 vs 二进制、各类编码错误）见 `10_文件与IO.md`。

### 6.3 终端输出的编码

编码问题有两层，别混：

| 层 | 管什么 | 这台机器上 |
|---|---|---|
| 源文件编码 | Python 怎么读你的 `.py` | UTF-8（Python 3 固定） |
| 标准输出编码 | Python 往终端写字节时用什么编码 | 取决于环境，见下表 |

```python
import sys
print(sys.stdout.encoding)
```

**本机实测数据**（同一台机器，只差一个环境变量）：

| 运行方式 | `sys.stdout.encoding` |
|---|---|
| `python -c "..."`（默认） | `gbk` |
| `python -X utf8 -c "..."` | `utf-8` |

> ⚠️ **一个反直觉的点：`sys.stdout.encoding` 不能用来推断 `open()` 的默认编码。**
> 它们是**两套独立机制**：
>
> - `sys.stdout.encoding` 由**终端/控制台**决定（所以你在 Windows Terminal 里可能是 `utf-8`）
> - `open()` 的默认编码由**区域设置 locale** 决定（所以同一台机器上仍然是 `cp936`）
>
> 也就是说完全可能同时出现「终端是 utf-8 所以 `print` 正常」而
> 「`open()` 还是 cp936 所以写文件埋了雷」。**别拿一个去推另一个。**

所以会出现：**文件里是对的，`print` 出来是乱码**——反过来也一样，
**`print` 正常不代表文件读写正常**。

处理方式：

```bash
# 让 Python 的 I/O（含 open 默认编码、stdin/stdout）全面走 UTF-8
python -X utf8 script.py
# 或者把终端本身设成 UTF-8（Windows Terminal 默认已经是）
chcp 65001
```

`PYTHONUTF8=1` 与 `-X utf8` **等价**，本机实测两者都把
`open()` 默认编码、`sys.stdout.encoding`、`locale.getpreferredencoding()` 一起变成 `utf-8`。

### 6.4 `.py` 文件的书写规范（PEP 8 里最要紧的几条）

> 完整规范：<https://peps.python.org/pep-0008/>

| 项目 | 规范 | 例子 |
|---|---|---|
| 缩进 | **4 个空格**，不要用 Tab |  |
| 行长 | 建议 ≤ 79，宽松些 ≤ 88（ruff/black 默认） |  |
| 变量/函数名 | 小写下划线 | `user_name`、`get_data()` |
| 类名 | 大驼峰 | `class UserProfile:` |
| 常量 | 全大写下划线 | `MAX_RETRY = 3` |
| 模块名 | 短小写，可含下划线 | `data_utils.py` |
| 运算符两侧 | 各留一个空格 | `a = b + c` |
| 逗号后 | 留一个空格 | `f(a, b, c)` |

**关于 Tab 和空格混用**：Python 3 直接禁止混用，报 `TabError`。
所以从一开始就用 4 个空格，并让编辑器把 Tab 键转成空格。

**关于命名哲学**：

```python
_内部变量        # 单个下划线开头：这是内部用的，请别直接依赖
__很私有         # 双下划线开头：类里会被改名（name mangling），见 08_面向对象.md
__init__        # 双下划线首尾：Python 的魔术方法，不要自己造这种名字
```

这些都是**约定**，不是强制。但它们被整个生态遵守，"不按约定写"的代价是别人读不懂你的代码。

### 6.5 自动守规范：`ruff`

人肉守 PEP 8 不现实。本仓库已经配了 `ruff`（`pyproject.toml` 的 dev 组）。

```bash
ruff check .        # 检查
ruff check --fix .  # 自动修能修的
ruff format .       # 格式化代码（类似 black）
```

**建议**：把它设成保存时自动运行。这样你不用记规范，工具替你记。

### 6.6 顺便记住这个套路：`if __name__ == "__main__"`

每个 `.py` 文件都可能在两种场合被使用：
**被直接运行**，或者**被别的文件 `import`**。这两者需要区分。

```python
# utils.py
def add(a, b):
    return a + b


if __name__ == "__main__":
    # 只有直接运行 utils.py 时才执行
    # 被别人 import 时不执行
    print(add(1, 2))
```

| 运行方式 | `__name__` 的值 | `if` 里会执行吗 |
|---|---|---|
| `python utils.py` | `"__main__"` | ✅ |
| `import utils` | `"utils"` | ❌ |

**为什么必须写**：如果不写，任何 `import utils` 都会顺带执行你写在底部的测试代码。
展开见 `07_模块与包.md`。

6. 在 PowerShell 里激活 venv 报"禁止运行脚本"，怎么处理？

8. 为什么 `.venv/` 不能提交到 git？

<details>
<summary>答案</summary>

1. 输出当前解释器的绝对路径。它回答"我现在用的到底是哪个 Python"——
   多版本机器上不确认这一步，后面所有装包/导入问题都无从排查。
2. REPL 会自动打印表达式结果；脚本模式不会，表达式值没人接住就丢弃，必须 `print`。
3. 语法错误。Python 先把整个文件编译成字节码再执行，编译不过就一行都不跑。
   运行时错误发生在执行到那一行时，之前的语句已经生效了。
4. 明确指定"用哪个解释器的 pip"。裸 `pip` 在多 Python 机器上指向不确定，
   会出现"装上了却 import 不到"。
5. 隔离的是 `site-packages`（第三方包目录）和"去哪找包"的路径。
   不复制 Python，`.venv\Scripts\python.exe` 只是个转发到真解释器的跳板，所以创建极快。
6. PowerShell 执行策略拦了 `.ps1`。`Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`，
   或 `-Scope Process -ExecutionPolicy Bypass` 临时放行，或改用 Git Bash 激活。
7. 系统区域编码，这台机器是 `cp936`（GBK），不是 UTF-8。
   坑在于写代码的人以为默认是 UTF-8，换机器/换人读就乱码或报 `UnicodeDecodeError`。
8. 它是本地生成物，`pyvenv.cfg` 里写死了本机绝对路径，换机器不可用；
   而且包体积大、含二进制。正确做法是提交依赖声明（`pyproject.toml` / `requirements.txt`）让别人重建。

</details>
