## 0. 先记住的七件事

**这一章的主分类轴是"一次失败从产生到被处理要走的阶段"**，所以分部不是按语法特性排的，而是按流程排的：

```text
一次失败
├─ 阶段 0：它属于哪一类？                      第 1 节
├─ 路线 A：走异常（让它自己往上找 handler）
│   ├─ 阶段 1 抛出与捕获：怎么抛出、怎么接住      第 2 节
│   ├─ 阶段 2 传播途中：谁负责清理              第 3 节  ← 本章核心
│   ├─ 阶段 3 抛什么类型：异常类体系            第 4 节
│   └─ 阶段 4 代价与契约：noexcept、三级保证     第 5 节
├─ 路线 B：不走异常（就地报给调用方或就地检查）
│   ├─ 报给调用方：错误码 / optional / expected  第 6 节
│   └─ 就地检查：assert（运行期）/ static_assert（编译期）  第 7 节
└─ 事后：已经崩了，从什么线索倒推                第 8 节
```

1. **先分类再选手段。** 编译错误要改代码；**可预期的失败**要报给调用方；**违反不变量**是 bug，该崩就崩。选错手段的代价不是"慢一点"，而是代码变长且不可靠。
2. **抛出点不需要知道谁处理。** 这是异常相对错误码唯一的、也是决定性的优势：中间的每一层都不用写"把错误往上转发"的代码。
3. **栈展开（stack unwinding）是异常能用的前提。** 异常向匹配处理器传播并进行栈展开时，沿途**已经构造完成**的自动局部对象会按构造的逆序被析构；`std::terminate` 路径不保证完成这种清理。
4. **所以 RAII 和异常是一对。** 资源交给对象持有之后，异常路径上的释放**不需要你写一行代码**。C++ 没有也不需要 `finally`——析构函数就是 `finally`。
5. **`catch` 一律写 `const T&`。** 按值捕获会**切片**：本机实测自定义异常层次按值捕获后调到的是基类版本。多个 `catch` 之间**必须从最派生写到最基类**，写反了 MSVC 只给一条 `C4286` 警告，程序照样跑。
6. **`noexcept` 有两副面孔**：说明符（`void f() noexcept`）和运算符（`noexcept(f())`）。最实际的影响是**它决定 `std::vector` 扩容时搬旧元素用移动还是用拷贝**——本机实测，同一个类去掉 `noexcept` 就从"移动 1 / 移动 2"变成"拷贝 1 / 拷贝 2"。
7. **崩溃排查的第一课是"别把线索留在缓冲区里"。** 本机实测：未捕获异常的例子里，抛出前 `std::cout` 打印的那行一个字都没留下（stdout 空、stderr 也空），只有退出码 `0xC0000409`。**换 `std::cerr` 或加 `std::flush` 就能留下。**

> 如果只记一条，记第 3 条。**它解释了 C++ 为什么不需要 `finally`，也解释了为什么"裸 `new`"在异常面前一定会泄漏。**

## 1. 四种"出错"：先分类，再选手段

在动手写处理代码之前，先判断这次失败属于哪一类。判错的后果是具体的：

- 把**程序员自己的 bug** 当业务失败 `catch` 住然后继续跑 → 程序带着已经损坏的状态运行
- 把**可预期的失败**写成返回值 → 每个调用点都堆 `if (!ok) return -1;`

| 类别 | 什么时候暴露 | 例子 | 正确手段 |
|---|---|---|---|
| **编译错误** | 编译期 | 类型不匹配、名字拼错、访问私有成员 | 改代码。**这不是"错误处理"，是"还没写完"** |
| **可预期的失败** | 运行期，但**可能发生**且调用方**有办法应对** | 文件不存在、输入格式错、网络断开 | **异常**，或**错误码 / `std::optional`**（第 6 节） |
| **违反不变量** | 运行期，**不该发生** | 数组下标越界、内部状态自相矛盾 | **`assert`**（第 7 节）；release 下就让它崩 |
| **未定义行为** | 什么都可能 | 悬垂指针、重复释放、越界读 | **没有手段能"处理"它，只能避免**（第 06 章第 10 节） |

### 1.1 判别"可预期失败"还是"bug"的一句话测试

> **这段代码在生产环境出错时，调用方除了记日志和放弃这次操作，还能做什么？**
>
> - **能**（重试、换一个文件、提示用户重新输入）→ **可预期的失败**，用异常或错误码报出去
> - **不能**（说明程序内部逻辑已经坏了）→ **bug**，用断言，让它尽早暴露

**为什么这个区分值一节**：如果把 bug 当成"可预期失败"来"处理"，你会带着已经被破坏的状态继续算下去。
比如越界写之后内部计数已经乱了，你"处理"掉错误码继续跑，最后输出一个**看起来正常、其实全错**的结果——**这比直接崩溃危险得多**。

### 1.2 三类手段的最小对照

下面这段代码把"可预期的失败"用返回值报了出去（错误码路线的最小形态，第 6 节展开）：

<!-- example:ch08_classify -->
```cpp
#include <iostream>

int checked_divide(int a, int b, int& out) {
    if (b == 0) { return -1; }
    out = a / b;
    return 0;
}

int main() {
    int r = 0;
    std::cout << checked_divide(6, 2, r) << ' ' << r << '\n';
    std::cout << checked_divide(1, 0, r) << ' ' << r << '\n';
}
```

<!-- result:ch08_classify -->
```text
0 3
-1 3
```

**注意第二行**：除法失败了，但 `r` 里还留着上一次的 `3`。
**"失败时输出参数是什么状态"这件事，返回值方案没有保证**——这是错误码路线两个固有问题之一（第 6 节给出另一个）。

### 1.3 一个必须提前说的坑

> ⚠️ **不要把 `assert` 用来校验用户输入 / 文件内容 / 网络数据。**
> `assert` 在 release 构建（定义 `NDEBUG`）里会被**整段去掉**，于是"校验"消失了。本机实测：加 `/DNDEBUG` 后断言的表达式**连求值都不会发生**。
> **来自程序外部的数据永远要用运行期检查（异常或错误码）。** 第 7 节展开。

## 2. 异常的抛出与捕获：`throw` / `try` / `catch`

### 2.1 先交代这一节的符号

| 符号 / 关键字 | 位置 | 作用 |
|---|---|---|
| `throw 表达式;` | 语句 | **抛出**：把表达式的值拷贝/移动进一个"异常对象"，然后开始找 handler |
| `throw;` | `catch` 块内 | **重新抛出当前正在处理的异常**（不产生新对象，动态类型保留） |
| `try { ... }` | 语句 | 圈出一段"这里的异常归我管"的代码 |
| `catch (类型 名字) { ... }` | 接在 `try` 后 | **handler**：声明它能接住哪种类型 |
| `catch (...)` | 同上 | 接住**任何**异常，代价是拿不到任何信息 |
| `noexcept` | 函数声明 / 表达式 | 两副面孔，第 5 节专讲 |

### 2.2 最小闭环

<!-- example:ch08_try_catch -->
```cpp
#include <iostream>
#include <stdexcept>

double divide(double a, double b) {
    if (b == 0.0) { throw std::invalid_argument("除数为 0"); }
    return a / b;
}

int main() {
    try {
        std::cout << divide(6, 2) << '\n';
        std::cout << divide(1, 0) << '\n';
        std::cout << "这一行不会执行\n";
    } catch (const std::invalid_argument& e) {
        std::cout << "捕获：" << e.what() << '\n';
    }
    std::cout << "继续执行\n";
}
```

<!-- result:ch08_try_catch -->
```text
3
捕获：除数为 0
继续执行
```

**执行轨迹**（本讲义的规矩：讲清程序到底先做什么、再跳到哪里）：

```text
1. divide(6, 2) 正常返回 3                        → 打印 3
2. divide(1, 0) 进入 if 分支
3.   throw std::invalid_argument("除数为 0")
       ├─ 拿这个表达式构造一个"异常对象"（它不放在 divide 的栈帧里，见 3.4）
       └─ 开始栈展开：拆掉 divide 的栈帧
4.   回到 main 里从这个 try 块往外找 handler：
       catch (const std::invalid_argument&) 能匹配 → 进入
       ※ try 块里抛出点之后的语句（"这一行不会执行"）被跳过
5.   执行 catch 体                                 → 打印"捕获：除数为 0"
6.   catch 体结束；异常对象在这里被销毁
7.   继续执行 try 语句之后的那一行                  → 打印"继续执行"
```

**三个关键点**：

1. 抛出点 `divide` **不需要知道**谁处理它，也不需要 `return` 一个错误值。
2. 中间的每一层**不需要写"转发"代码**（对比第 6 节的错误码，那里每层都要检查并传递）。
3. `try` 块中抛出点**之后的语句不会再执行**。

### 2.3 `throw` 什么都能抛，但只有异常类值得抛

`throw` 的表达式可以是**任何类型**：

<!-- example:ch08_throw_any_type -->
```cpp
#include <iostream>

int main() {
    try {
        throw 42;
    } catch (int v) {
        std::cout << "接到 int: " << v << '\n';
    }

    try {
        throw "一段字符串字面量";
    } catch (const char* s) {
        std::cout << "接到 const char*: " << s << '\n';
    }
}
```

<!-- result:ch08_throw_any_type -->
```text
接到 int: 42
接到 const char*: 一段字符串字面量
```

**能编过、能跑通，但这是坏实践**，因为：

| 问题 | 说明 |
|---|---|
| 接不住 | `catch (const std::exception&)` 接不住 `int`，项目的**顶层兜底 handler 会漏掉它** |
| 无法携带信息 | `int` 只能是一个码；`const char*` 是指针，指向的字符串在哪、活多久都得你自己保证 |
| 无语义层次 | 无法用"基类接住派生类"来表达"这类错误我都能处理" |

> **规范**：**只抛（或继承）标准异常类的对象**，或者你自己定义的、**从 `std::exception` 派生的**类。第 4 节展开。

### 2.4 没人接住会怎样：一个"看不见输出"的实测

<!-- example:ch08_uncaught -->
```cpp
#include <iostream>
#include <stdexcept>

int main() {
    std::cout << "开始\n";
    throw std::runtime_error("没人接住我");
}
```

**编译成功，警告 0 条**。本机实测的真实结果：

```text
stdout：空
stderr：空
退出码：-1073740791（即无符号的 3221226505，十六进制 0xC0000409）
```

**"开始"这两个字没有出现。** 程序确实执行了 `std::cout << "开始\n"`，但那行字还在**输出缓冲区**里；异常没人接住时标准要求调用 `std::terminate`，MSVC 的实现用 `__fastfail` 直接结束进程，**缓冲区不会被冲洗**。

> ⚠️ **坑（本章最实用的一条）**：崩溃时 stdout 里"少了几行"，于是你以为程序没执行到那里。**其实它执行了，只是没写出来。**
> **处理**：在关键位置写 `std::cout << ... << std::flush;`，或者把诊断信息改走 `std::cerr`（它默认不缓冲）。
>
> **另一个实测结论**：MSVC 这里**不打印任何说明**（stderr 是空的）。GCC 通常会往 stderr 打一行 `terminate called after throwing an instance of ...`——**那条本机未实测**（本机没有 GCC）。

### 2.5 异常是"拷贝出来"的：抛出的是什么对象

`throw 表达式` 会**用那个表达式构造一个异常对象**，之后传播的是**那个对象**，不是原来那个局部变量。
这解释了三件事：为什么 `throw std::runtime_error("x")` 里那个临时对象析构了也不影响；为什么 `catch` 里改它能被外层看到；为什么 `throw e;` 和 `throw;` 不一样。

#### 2.5.1 `catch` 里改异常对象，外层能看到

<!-- example:ch08_exception_object_lifetime -->
```cpp
#include <iostream>
#include <stdexcept>

int main() {
    try {
        try {
            throw std::runtime_error("原始消息");
        } catch (std::runtime_error& e) {          // 注意：非 const 引用
            std::cout << "catch 里读到: " << e.what() << '\n';
            e = std::runtime_error("catch 里改过的消息");
            throw;                                  // 抛回同一个对象
        }
    } catch (const std::exception& e) {
        std::cout << "外层读到: " << e.what() << '\n';
    }
}
```

<!-- result:ch08_exception_object_lifetime -->
```text
catch 里读到: 原始消息
外层读到: catch 里改过的消息
```

**异常对象的生存期**是"从抛出到最后一个 handler 结束"——它独立于任何栈帧，所以 `throw` 的那一层栈帧被拆掉了它还在。
第 3.4 节会解释它被放在哪里。

> **这也是"不要写 `catch (T& e)` 然后改它"这条建议的由来**：改是有效的，会让外层看到一个措手不及的值。**默认写 `const T&`。**

#### 2.5.2 `throw e;` 与 `throw;` 的区别（有实测）

| 写法 | 抛出去的是什么 |
|---|---|
| `throw;` | **原来那个异常对象**，动态类型完整保留 |
| `throw e;` | **在 `e` 的静态类型上拷贝一份新的**，动态类型被切掉 |

<!-- example:ch08_rethrow_copy -->
```cpp
#include <iostream>
#include <stdexcept>

class Detail : public std::runtime_error {
public:
    explicit Detail(const char* m) : std::runtime_error(m) {}
    const char* tag() const { return "Detail"; }
};

int main() {
    try {
        try {
            throw Detail("原始对象");
        } catch (const std::exception& e) {
            throw e;                     // 拷贝，且在静态类型 std::exception 上切片
        }
    } catch (const Detail& d) {
        std::cout << "throw e;   接到了 Detail: " << d.what() << '\n';
    } catch (const std::exception& e) {
        std::cout << "throw e;   接到了 std::exception: " << e.what() << '\n';
    }

    try {
        try {
            throw Detail("原始对象");
        } catch (const std::exception&) {
            throw;                       // 重新抛出原来那个，动态类型不变
        }
    } catch (const Detail& d) {
        std::cout << "throw;     接到了 Detail: " << d.what() << '\n';
    } catch (const std::exception& e) {
        std::cout << "throw;     接到了 std::exception: " << e.what() << '\n';
    }
}
```

<!-- result:ch08_rethrow_copy -->
```text
throw e;   接到了 std::exception: 原始对象
throw;     接到了 Detail: 原始对象
```

**同一个 `throw`，一个丢掉了 `Detail` 类型，一个没有。**
这就是 `throw;`（不带表达式）存在的唯一理由——**它是唯一能"原样再抛"的写法**。

**什么时候用 `catch (...)` + `throw;`**：中间某层想记一笔日志、或者做一次转换，但不打算处理：

<!-- example:ch08_rethrow -->
```cpp
#include <iostream>
#include <stdexcept>

void work() {
    try {
        throw std::runtime_error("底层出错");
    } catch (...) {
        std::cout << "底层记录了一下\n";
        throw;
    }
}

int main() {
    try {
        work();
    } catch (const std::runtime_error& e) {
        std::cout << "上层处理: " << e.what() << '\n';
    }
}
```

<!-- result:ch08_rethrow -->
```text
底层记录了一下
上层处理: 底层出错
```

### 2.6 `catch` 怎么匹配：两条规则，第二条会咬人

| 规则 | 说明 |
|---|---|
| **按类型匹配，允许派生类 → 基类的转换** | `catch (const std::exception&)` 能接住 `std::out_of_range` |
| **先匹配到的赢** | 同一个 `try` 的多个 `catch` **按书写顺序**依次尝试，第一条能匹配的就执行 |

第二条会制造一个安静的陷阱：

<!-- example:ch08_catch_order -->
```cpp
#include <iostream>
#include <stdexcept>

int main() {
    try {
        throw std::out_of_range("越界了");
    } catch (const std::exception& e) {
        std::cout << "先被 std::exception 接住: " << e.what() << '\n';
    } catch (const std::out_of_range& e) {
        std::cout << "永远到不了这里: " << e.what() << '\n';
    }
}
```

<!-- result:ch08_catch_order -->
```text
先被 std::exception 接住: 越界了
```

**这次 MSVC 给了警告**（本机实测原文）：

```text
main.cpp(9): warning C4286: “const std::out_of_range &”: 由基类(“const std::exception &”)在行 7 上捕获
```

> **规律**：**`catch` 必须从"最派生"写到"最基类"。**
> 好消息是 MSVC 会用 `C4286` 提醒你；坏消息是**这只是一条警告，程序照样跑**——那个更具体的 handler 变成了死代码。

### 2.7 按值捕获会切片（自定义异常上是致命的）

这是异常处理里最经典的一个坑。用自定义的异常层次看最清楚：

<!-- example:ch08_slicing_custom -->
```cpp
#include <iostream>

class Base {
public:
    virtual const char* name() const { return "Base"; }
    virtual ~Base() = default;
};

class Derived : public Base {
public:
    const char* name() const override { return "Derived"; }
};

int main() {
    try {
        throw Derived();
    } catch (Base b) {
        std::cout << "按值: " << b.name() << '\n';
    }

    try {
        throw Derived();
    } catch (const Base& b) {
        std::cout << "按引用: " << b.name() << '\n';
    }
}
```

<!-- result:ch08_slicing_custom -->
```text
按值: Base
按引用: Derived
```

**程序实际怎么解释它**：`catch (Base b)` 的 `b` 是一个**货真价实的 `Base` 对象**——异常对象的 `Derived` 部分被切掉了（第 07 章第 9.2 节讲的"切片"），虚函数表也是 `Base` 的，所以 `b.name()` 调到 `Base::name`。

> **规则：`catch` 参数写成 `const T&`，不要写 `T`。**
> 为什么不用 `T&`：处理期间你通常不想改它，加 `const` 更贴切（2.5.1 节给了反例）。

### 2.8 一个"看起来违反上面规则"的实测

上面那条规则有一个反直觉的现象，本机测到了，必须单独说清楚：

<!-- example:ch08_catch_by_value -->
```cpp
#include <iostream>
#include <stdexcept>

int main() {
    try {
        throw std::runtime_error("这是真正的信息");
    } catch (std::exception e) {
        std::cout << "按值: " << e.what() << '\n';
    }

    try {
        throw std::runtime_error("这是真正的信息");
    } catch (const std::exception& e) {
        std::cout << "按引用: " << e.what() << '\n';
    }
}
```

<!-- result:ch08_catch_by_value -->
```text
按值: 这是真正的信息
按引用: 这是真正的信息
```

**两行一样，按值捕获也拿到了消息。** 这和第 2.7 节的结论矛盾吗？

**不矛盾，但要看清楚是为什么**：切片**确实发生了**——`e` 是一个真正的 `std::exception` 对象。但 MSVC 的 `std::exception` 实现里存的是**指向消息的指针**，它的拷贝构造函数把那个指针一起复制了过去，于是 `what()` 还能取到同一段文本。

**这是实现的细节，不是标准保证。** 标准只保证 `what()` 是虚函数、返回一个可读字符串。
一个自定义异常子类如果**多存了自己的成员**（比如 4.5 节 `ParseError` 里的行号），按值捕获时那些成员**真的会丢**。

> **结论不变：`catch` 一律写 `const T&`。** 上面这个"看起来没事"的例子只是让你不要依赖运气。

## 3. 栈展开：异常路径上谁来清理

**这一节是本章的核心。** 第 07 章第 3.3 节说"RAII 让异常路径也安全"，第 12 章第 7.1 节用 `enter/exit` 证明了**析构发生在 `catch` 之前**。
这里要讲清的是**机制本身**：控制流怎么沿调用栈往回走、每一层清理什么、清到什么程度才轮到 `catch`。

### 3.1 定义

> **栈展开（stack unwinding）**：异常从抛出点向匹配处理器传播并展开时，途经的每一个函数（以及同一个函数里的每一个已经进入的块作用域），它**已经构造完成**的局部对象都会**按构造的逆序**被析构；清完之后，控制流才继续向匹配的 handler 转移。无匹配处理器或违反 `noexcept` 时调用 `std::terminate`，不保证完成栈展开；这与第 07 章第 3.3 节及第 12 章第 7 节的边界一致。

**三个词要抠准**：

| 词 | 含义 |
|---|---|
| "已经构造完成" | **还没构造的对象根本不会被析构**（它压根没存在过）——见 3.3 |
| "逆序" | 后构造的先析构。这保证"依赖别人构造出来的东西"先死 |
| "清完之后才找 handler" | 所以 `catch` 第一行执行时，沿途资源**已经**释放干净了 |

### 3.2 实测：调用栈 + 块作用域一起展开

一个三层结构：`main` 的 `try` → `outer()` → `outer` 内的嵌套块，最内层抛出。

<!-- example:ch08_unwind_nested_scopes -->
```cpp
#include <iostream>
#include <stdexcept>

class Tracer {
    const char* name_;
public:
    explicit Tracer(const char* n) : name_(n) { std::cout << "构造 " << name_ << '\n'; }
    ~Tracer() { std::cout << "析构 " << name_ << '\n'; }
};

void outer() {
    Tracer a("a");
    {
        Tracer b("b");
        Tracer c("c");
        throw std::runtime_error("从最内层抛出");
    }
    std::cout << "这一行不会执行\n";
}

int main() {
    try {
        outer();
    } catch (const std::exception& e) {
        std::cout << "捕获: " << e.what() << '\n';
    }
}
```

<!-- result:ch08_unwind_nested_scopes -->
```text
构造 a
构造 b
构造 c
析构 c
析构 b
析构 a
捕获: 从最内层抛出
```

**本机编译时还给了这条警告**（原文）：

```text
main.cpp(19): warning C4702: 不可访问代码
```

**它就是"这一行不会执行"那句话的机器证明**——编译器自己算出来 `std::cout << "这一行不会执行\n"` 永远到不了。

**完整执行轨迹**：

```text
1. main 调用 outer
      → 构造 a                                    → 打印"构造 a"
2. 进入嵌套块
      → 构造 b                                    → 打印"构造 b"
      → 构造 c                                    → 打印"构造 c"
3. throw std::runtime_error(...)
      ├─ 构造异常对象
      └─ 栈展开开始
4.   先拆最内层块作用域：c 后构造 → 先析构 c        → 打印"析构 c"
                          b 先构造 → 后析构 b        → 打印"析构 b"
5.   再拆 outer 的函数体作用域：析构 a              → 打印"析构 a"
6.   回到 main，从 try 块往外找 handler → 匹配成功
7.   执行 catch 体                                  → 打印"捕获: 从最内层抛出"
```

**注意第 4 步和第 5 步的关系**：展开不是"简单地把对象的析构倒着调一遍"，而是**按作用域一层层往外退**，
每一层内部再按逆序。这就是为什么输出是 `c, b, a` 而不是别的顺序。

**八个字总结机制**：

> **谁构造的谁负责，谁后构造谁先死，清完才轮到 `catch`。**

### 3.3 展开只处理"已经走到的那一步"：抛点之后的代码等于不存在

这一条看起来显然，但它解释了一整类 bug：

<!-- example:ch08_unwind_partial -->
```cpp
#include <iostream>
#include <stdexcept>

class Tracer {
    const char* name_;
public:
    explicit Tracer(const char* n) : name_(n) { std::cout << "构造 " << name_ << '\n'; }
    ~Tracer() { std::cout << "析构 " << name_ << '\n'; }
};

void f(bool early_throw) {
    if (early_throw) { throw std::runtime_error("提前抛出"); }
    Tracer late("抛点之后才构造的对象");
    std::cout << "这一行到不了\n";
}

int main() {
    try {
        f(true);
    } catch (const std::exception& e) {
        std::cout << "第一次捕获: " << e.what() << '\n';
    }
    std::cout << "--- 第二次 ---\n";
    try {
        f(false);
    } catch (const std::exception& e) {
        std::cout << "不该到这里: " << e.what() << '\n';
    }
}
```

<!-- result:ch08_unwind_partial -->
```text
第一次捕获: 提前抛出
--- 第二次 ---
构造 抛点之后才构造的对象
这一行到不了
析构 抛点之后才构造的对象
```

**第一次调用的输出里完全没有 `Tracer` 的痕迹**——因为 `throw` 在它构造之前就发生了，**它从来没存在过，所以没有什么需要清理**。

**第二次调用（`early_throw = false`）**正常返回，`late` 在函数末尾析构。**同一份输出里刚好有了对照**：正常路径和异常路径调用的是同一个析构函数，只是触发的时刻不同。

**实践推论**：

> **要清理的东西，必须在可能失败的那一步之前就构造好。**
> 反过来说：**"先获取资源 A，再获取资源 B，然后才让它们被对象管起来"这种写法本身就是错的**——中间任何一步抛异常，前面已经获取的东西没人管。

### 3.4 异常对象不放在栈帧里

3.1 节说"清完之后 `catch` 才能执行"，但 2.5.1 节又说"`catch` 里能改那个异常对象，外层还能看到"。
二选一的话，异常对象显然**不能住在 `outer` 的栈帧里**——那个栈帧在第 5 步已经被拆掉了。
（这也是它和普通返回值最大的实现差异：返回值住在调用者给的存储里，异常对象住在**实现为它准备的、与你无关的存储**里。标准只要求它活到最后一个 handler 结束。）

### 3.5 临时的、没名字的对象也归栈展开管

上面几个例子里的对象都有名字。**没名字的临时对象呢？**

<!-- example:ch08_unwind_temp -->
```cpp
#include <iostream>
#include <stdexcept>

class Tracer {
    const char* name_;
public:
    explicit Tracer(const char* n) : name_(n) { std::cout << "构造 " << name_ << '\n'; }
    ~Tracer() { std::cout << "析构 " << name_ << '\n'; }
};

void consume(const Tracer& a, const Tracer& b) {
    std::cout << "consume 开始\n";
    throw std::runtime_error("consume 里抛出");
}

int main() {
    try {
        consume(Tracer("临时1"), Tracer("临时2"));
    } catch (const std::exception& e) {
        std::cout << "捕获: " << e.what() << '\n';
    }
}
```

<!-- result:ch08_unwind_temp -->
```text
构造 临时2
构造 临时1
consume 开始
析构 临时1
析构 临时2
捕获: consume 里抛出
```

**本机编译时给了两条警告**（原文）：

```text
main.cpp(12): warning C4100: “a”: 未引用的形参
main.cpp(12): warning C4100: “b”: 未引用的形参
```

**这个例子里有两件事必须分开说**：

| 现象 | 属于哪一类 |
|---|---|
| `构造 临时2` 出现在 `构造 临时1` **之前** | ⚠️ **未指定行为**。C++ 不规定函数实参的求值顺序，MSVC 这次从右往左求值。**换成别的编译器/别的调用就会变** |
| `析构 临时1` 出现在 `析构 临时2` **之前**（即逆序） | ✅ **标准保证**：临时对象在"完整表达式"结束时按构造的逆序销毁 |

**结论**：**"谁先构造"这件事在函数实参上是不确定的，但"逆序销毁"是确定的。**
这两条要分清楚——把未指定的求值顺序当成约定去依赖，是另一种 bug。

> `C4100` 的两条警告是因为 `consume` 只接收引用、从不读它们。真实项目里这条警告通常意味着"这个参数忘了用"。

### 3.6 构造函数抛出：只回滚已经构造好的那部分

一个对象的构造过程如果中途失败，已经构造好的部分怎么办？

<!-- example:ch08_ctor_throw -->
```cpp
#include <iostream>
#include <stdexcept>

class Part {
    const char* name_;
public:
    explicit Part(const char* n) : name_(n) { std::cout << "构造 " << name_ << '\n'; }
    ~Part() { std::cout << "析构 " << name_ << '\n'; }
};

class Whole {
    Part a_;
    Part b_;
public:
    Whole() : a_("a"), b_("b") {
        std::cout << "Whole 构造体\n";
        throw std::runtime_error("构造失败");
    }
    ~Whole() { std::cout << "~Whole\n"; }
};

int main() {
    try {
        Whole w;
        (void)w;
    } catch (const std::exception& e) {
        std::cout << "捕获: " << e.what() << '\n';
    }
}
```

<!-- result:ch08_ctor_throw -->
```text
构造 a
构造 b
Whole 构造体
析构 b
析构 a
捕获: 构造失败
```

| 发生了什么 | 有没有发生 |
|---|---|
| 成员 `a_`、`b_` 的析构 | ✅ **发生了**（逆序：`b_` 先、`a_` 后） |
| `Whole` 自己的析构 `~Whole` | ❌ **没有**（输出的 6 行里找不到 `~Whole`） |

**规则**：**"构造成功"才算这个对象存在。** 构造没完成的对象，它的析构函数不会被调用——语言认为"那个对象根本不存在"。

基类也是同一条规则：

<!-- example:ch08_ctor_term -->
```cpp
#include <iostream>
#include <stdexcept>

class Base {
public:
    Base() { std::cout << "Base 构造\n"; }
    ~Base() { std::cout << "Base 析构\n"; }
};

class Derived : public Base {
public:
    Derived() {
        std::cout << "Derived 构造体\n";
        throw std::runtime_error("派生类构造失败");
    }
    ~Derived() { std::cout << "Derived 析构\n"; }
};

int main() {
    try {
        Derived d;
        (void)d;
    } catch (const std::exception& e) {
        std::cout << "捕获: " << e.what() << '\n';
    }
}
```

<!-- result:ch08_ctor_term -->
```text
Base 构造
Derived 构造体
Base 析构
捕获: 派生类构造失败
```

**基类子对象已经构造完成 → 它被回滚析构；派生类自己的析构函数没跑。**
（顺序规律与第 07 章第 8.3 节"析构：自己的函数体 → 成员逆序 → 基类"完全一致，只是这里最后一步只走到"基类"。）

> **实践推论**：**如果构造函数里已经获取了资源、然后才抛异常，那份资源就会泄漏。**
> 正确做法是**把每个资源都放进一个成员对象**（成员对象的析构会被回滚调用），
> 或者用"函数 try 块"（入门阶段知道有这回事即可）。
>
> **这是 RAII 的一个重要边界**：RAII 保证的是"**已经构造完成的对象**会被正确销毁"，
> 它不保证"构造到一半的东西"会被清理——**除非那东西本身就是个成员对象**。

### 3.7 析构函数里抛异常：这是禁止的，原因在这里

第 07 章第 3.4 节给过结论，这里补上机制。

<!-- example:ch08_dtor_throw -->
```cpp
#include <iostream>
#include <stdexcept>

class Bad {
public:
    ~Bad() noexcept(false) { throw std::runtime_error("析构里抛出"); }
};

void f() {
    Bad b;
    (void)b;
    throw std::runtime_error("先抛一个");
}

int main() {
    try { f(); }
    catch (const std::exception& e) { std::cout << "捕获 " << e.what() << '\n'; }
}
```

**编译成功，警告 0 条**。本机实测的真实结果：

```text
stdout：空
stderr：空
退出码：-1073740791（0xC0000409）
```

**为什么**：`f()` 里已经有一个异常正在传播，此时栈展开要析构 `b`，而 `~Bad()` **又抛出一个异常**。
C++ 规定**同一时刻只能有一个"正在传播的异常"**，出现第二个就调用 `std::terminate`，**没有商量余地**。

**必须区分的一个反例**：如果**没有**别的异常在传播，析构函数抛出是**可以接住的**：

<!-- example:ch08_dtor_throw_alone -->
```cpp
#include <iostream>
#include <stdexcept>

class Bad {
public:
    ~Bad() noexcept(false) { throw std::runtime_error("析构里抛出"); }
};

int main() {
    try {
        Bad b;                  // 正常构造，正常离开作用域
        (void)b;
        std::cout << "作用域结束前\n";
    } catch (const std::exception& e) {
        std::cout << "捕获 " << e.what() << '\n';
    }
    std::cout << "继续执行\n";
}
```

<!-- result:ch08_dtor_throw_alone -->
```text
作用域结束前
捕获 析构里抛出
继续执行
```

**所以"析构函数不能抛异常"不是因为语言禁止这一句 `throw`，而是因为它的后果不可控**：
同一个析构函数，在正常离开作用域时没事，在栈展开途中被调用时**直接终止进程**。
**你无法保证它每次都在安全的那条路径上被调用**——所以规则是干脆不要抛。

> ⚠️ **规则：析构函数里不要抛异常。**
> C++11 起析构函数**默认是 `noexcept` 的**，所以上面两个例子都必须显式写 `noexcept(false)` 才能编过——
> **这个默认值就是语言在替你堵这个洞**。
>
> **如果析构里确实可能失败（比如关闭文件失败）怎么办**：
> 把失败信息**吞掉并记录**（写日志），或者提供一个**显式的 `close()` 函数**让调用方主动调用并处理失败。
> **绝不要让异常从析构函数里逃出去。**
>
> **归属**：这是**控制流类**的错误——不是语法错，也不是类型错，而是"异常传播机制被破坏了"。

### 3.8 与 RAII 的关系：一张对照表

| | 正常返回 | 抛出异常 | 手写 `new`/`delete`（资源没交给对象） |
|---|---|---|---|
| 局部对象被析构吗 | ✅ | ✅ **栈展开保证** | ✅ 指针变量本身是局部对象，会销毁 |
| 指针**指向的堆对象**被释放吗 | 要看有没有写 `delete` | **❌ 没有**——`delete` 那一行根本到不了 | ❌ |
| 你需要写释放代码吗 | 不需要（对 RAII 类型） | **不需要** | 要，而且异常一来就漏了 |

**这一节最实在的一句话**：

> **把资源交给对象持有（RAII），异常路径就自动安全了。**
> **手写 `new`/`delete` 没有这个保证**——异常从中间穿过时，`delete` 那一行根本没被执行到。

（第 12 章第 7 节有这条的完整实测与自定义 RAII 类的写法，这里不重复。）
**C++ 没有 `finally`，也不需要它——析构函数就是 `finally`。**

## 4. 标准异常类体系：抛什么类型的对象

### 4.1 层次结构

标准异常类分散在几个头文件里（`<stdexcept>`、`<new>`、`<typeinfo>`、`<system_error>`…），
它们构成一棵以 `std::exception` 为根的树：

```text
std::exception                        ← 根；what() 是虚函数
├─ std::logic_error                   ← "程序逻辑写错了"（理论上运行前能发现）
│   ├─ std::invalid_argument          参数不合法
│   ├─ std::domain_error              定义域错误
│   ├─ std::length_error              超出长度上限
│   └─ std::out_of_range              越界（at()、substr() 等会抛它）
├─ std::runtime_error                 ← "运行期才知道的失败"（外部条件）
│   ├─ std::range_error               结果超出可表示范围
│   ├─ std::overflow_error            上溢
│   └─ std::underflow_error           下溢
├─ std::bad_alloc                     ← new 失败（在 <new> 里）
├─ std::bad_cast                      ← 对引用做 dynamic_cast 失败（在 <typeinfo> 里）
├─ std::bad_optional_access           ← optional::value() 没有值（在 <optional> 里）
├─ std::system_error                  ← 带错误码的异常（在 <system_error> 里）
└─ std::bad_typeid
```

**`logic_error` 与 `runtime_error` 的分界**（标准里的分类，实际使用中是一条约定）：

| 基类 | 含义 | 例子 |
|---|---|---|
| `logic_error` | **理论上可以在运行前发现**的错误，通常是调用方违反了前置条件 | 给 `at()` 传了越界下标 |
| `runtime_error` | **只有运行时才知道**的外部条件导致的失败 | 文件读不出来、网络断开 |

**为什么要分**：它会影响"这个异常该不该在同一层被处理"。`logic_error` 通常意味着**调用方写错了**，
外面那个 `catch` 往往修不了它；`runtime_error` 才是"这次运气不好，重试/换个输入"这一类。

### 4.2 各异常类的 `what()` 说什么（实测）

<!-- example:ch08_hierarchy -->
```cpp
#include <iostream>
#include <stdexcept>
#include <string>
#include <vector>

int main() {
    try { throw std::runtime_error("runtime_error 的信息"); }
    catch (const std::exception& e) { std::cout << e.what() << '\n'; }

    try { throw std::logic_error("logic_error 的信息"); }
    catch (const std::exception& e) { std::cout << e.what() << '\n'; }

    try { throw std::out_of_range("out_of_range 的信息"); }
    catch (const std::logic_error& e) { std::cout << "被 logic_error 接住: " << e.what() << '\n'; }

    std::vector<int> v{1, 2, 3};
    try { std::cout << v.at(10) << '\n'; }
    catch (const std::out_of_range& e) { std::cout << "at(): " << e.what() << '\n'; }

    try { std::stoi("abc"); }
    catch (const std::invalid_argument& e) { std::cout << "stoi(): " << e.what() << '\n'; }
}
```

<!-- result:ch08_hierarchy -->
```text
runtime_error 的信息
logic_error 的信息
被 logic_error 接住: out_of_range 的信息
at(): invalid vector subscript
stoi(): invalid stoi argument
```

**编译时有这条警告**（原文）：

```text
main.cpp(20): warning C4834: 放弃具有 [[nodiscard]] 属性的函数的返回值
```

| 现象 | 说明 |
|---|---|
| 第三行能被 `catch (const std::logic_error&)` 接住 | `out_of_range` **继承自** `logic_error`，所以基类的 handler 能接住派生类异常 |
| 后两行的消息是**英文**的 | 那是**库自己写的消息**（`"invalid vector subscript"`、`"invalid stoi argument"`），不是你传的 |
| `warning C4834` | `std::stoi` 标了 `[[nodiscard]]`，这里故意丢掉了返回值——**真实项目里这条警告通常意味着"忘了用结果"** |

> ⚠️ **坑**：以为 `e.what()` 里的文字是**固定的**、可以拿去解析。
> **它是给人看的**：不同实现、不同版本可以改写措辞（上面两行就是 MSVC 的原文）。
> **要判断"是哪种失败"，请用异常的类型或你自己的错误码，不要解析消息文本。**

### 4.3 几个不继承自 `logic_error` / `runtime_error` 的（实测）

| 异常 | 什么时候抛 | 本机实测的 `what()` |
|---|---|---|
| `std::bad_alloc` | `new` 申请不到内存 | `bad allocation` |
| `std::bad_cast` | 对**引用**做 `dynamic_cast` 失败（**指针版返回 `nullptr`，不抛**） | `Bad dynamic_cast!` |
| `std::bad_optional_access` | `optional::value()` 而它没有值 | `Bad optional access` |

<!-- example:ch08_bad_alloc -->
```cpp
#include <iostream>
#include <new>

int main() {
    try {
        int* p = new int[1000000000000ull];
        std::cout << "不该成功 " << p << '\n';
    } catch (const std::bad_alloc& e) {
        std::cout << "bad_alloc: " << e.what() << '\n';
    }
    std::cout << "程序继续\n";
}
```

<!-- result:ch08_bad_alloc -->
```text
bad_alloc: bad allocation
程序继续
```

<!-- example:ch08_bad_cast -->
```cpp
#include <iostream>
#include <typeinfo>

class Base { public: virtual ~Base() = default; };
class Derived : public Base { public: void only_derived() {} };

int main() {
    Base b;
    Base* pb = &b;

    Derived* d = dynamic_cast<Derived*>(pb);
    std::cout << "指针版: " << (d == nullptr ? "nullptr" : "非空") << '\n';

    try {
        Derived& rd = dynamic_cast<Derived&>(*pb);
        rd.only_derived();
        std::cout << "不该到这里\n";
    } catch (const std::bad_cast& e) {
        std::cout << "引用版抛: " << e.what() << '\n';
    }
}
```

<!-- result:ch08_bad_cast -->
```text
指针版: nullptr
引用版抛: Bad dynamic_cast!
```

**`bad_cast` 这一对有实用价值**：`dynamic_cast` 到**指针**类型时失败返回 `nullptr`（可以 `if` 判空），
到**引用**类型时失败**必须抛**——因为引用没有"空"这个状态可以返回。这是第 06 章第 4 节「引用 vs 指针：一张对比表」那条区别的一个直接后果。

### 4.4 `std::system_error`：异常和错误码的合体

有些失败天然带着一个**来自操作系统的错误码**。`std::system_error` 把"异常"和"码"装到一起：

<!-- example:ch08_system_error -->
```cpp
#include <iostream>
#include <system_error>

int main() {
    try {
        throw std::system_error(2, std::system_category(), "打不开文件");
    } catch (const std::system_error& e) {
        std::cout << "what(): " << e.what() << '\n';
        std::cout << "code(): " << e.code().value() << '\n';
    }
}
```

<!-- result:ch08_system_error -->
```text
what(): 打不开文件: The system cannot find the file specified.
code(): 2
```

**看出结构了吗**：`what()` 是 `<你写的说明> + <系统给的说明>`，而 `code()` 是**可以拿去比较和判断的码**。

> **这是"文本 vs 码"那条规矩的最佳范例**（4.2 节那条坑）：
> **判断用什么看码，给人看用文本。** `system_error` 两个都给你。

### 4.5 自定义异常：继承 `runtime_error`

标准异常类不够用时（比如你还要带上"第几行"），**继承 `std::runtime_error`**：

<!-- example:ch08_custom_exception -->
```cpp
#include <iostream>
#include <stdexcept>
#include <string>

class ParseError : public std::runtime_error {
    int line_;
public:
    ParseError(int line, const std::string& msg)
        : std::runtime_error(msg), line_(line) {}
    int line() const { return line_; }
};

int main() {
    try {
        throw ParseError(12, "缺少右括号");
    } catch (const ParseError& e) {
        std::cout << "行 " << e.line() << ": " << e.what() << '\n';
    }

    try {
        throw ParseError(12, "缺少右括号");
    } catch (const std::exception& e) {      // 顶层兜底
        std::cout << "兜底接到: " << e.what() << '\n';
    }
}
```

<!-- result:ch08_custom_exception -->
```text
行 12: 缺少右括号
兜底接到: 缺少右括号
```

**为什么继承标准异常类**：

| 做法 | 结果 |
|---|---|
| 继承 `std::runtime_error` | 白拿"存消息 + `what()`"的实现；**自动进得了 `catch (const std::exception&)` 的兜底** |
| 继承 `std::exception` | 要自己实现 `what()`（本机实测：不重写时默认返回 `Unknown exception`，见下） |
| **不继承任何标准异常** | ❌ 你的异常会漏掉所有 `catch (const std::exception&)`，**整个项目的错误处理出现一个洞** |

`std::exception::what()` 的默认返回值，以及自己重写它：

<!-- example:ch08_what_default -->
```cpp
#include <iostream>
#include <exception>

class My : public std::exception {
public:
    const char* what() const noexcept override { return "My::what() 说的"; }
};

int main() {
    try { throw std::exception(); }
    catch (const std::exception& e) { std::cout << "基类默认: " << e.what() << '\n'; }

    try { throw My(); }
    catch (const std::exception& e) { std::cout << "重写之后: " << e.what() << '\n'; }
}
```

<!-- result:ch08_what_default -->
```text
基类默认: Unknown exception
重写之后: My::what() 说的
```

> **一条规范**：**自定义异常一定要能从 `std::exception` 接住。**
> 这条约定让"顶层兜底 handler"这个模式成立——不管下面抛出什么，顶层都能记录并优雅退出。
> **`what()` 的签名要带 `const noexcept`**（上面那样写），否则不算重写（第 07 章第 8.2 节「多态：同一句话，不同对象有不同行为」里的 `override`）。

### 4.6 一份"标准库检查 vs 不检查"的对照：`at()` 与 `[]`

标准库里同一个操作常常有两种版本，一个**报错**、一个**不检查**：

| 写法 | 越界时 |
|---|---|
| `v.at(i)` | **抛 `std::out_of_range`**（4.2 节实测过） |
| `v[i]` | **不做检查，未定义行为** |

<!-- example:ch08_vec_oob -->
```cpp
#include <iostream>
#include <vector>

int main() {
    std::vector<int> v{1, 2, 3};
    std::cout << v.size() << '\n';
    std::cout << v[10] << '\n';
}
```

**编译成功，警告 0 条**。本机对**同一份源码**在不同开关下各跑一次，得到：

```text
（探针 v2，无附加开关）      3 / -1414022928
（探针 v3，无附加开关）      3 / 0
（探针 v4，/Od）             3 / 6029370
（探针 v4，/O2）             3 / 1
（探针 v4，/Od /DEXTRA_WORK）3 / 7274612
```

**五个数字，退出码全是 0，警告全是 0 条。**
这不是"越界被处理了"，而是**未定义行为恰好没发作**——它打印什么完全不保证，`0` 只是其中一次巧合。
**"这次跑出来是 0，所以没事"是最危险的推理方式**：它下次可能推翻你。

| 需求 | 用哪个 |
|---|---|
| 下标来自程序内部、已经保证合法 | `v[i]`（快） |
| 下标来自外部输入 / 不确定 | **`v.at(i)`**，把越界变成可捕获的异常 |

**这一对是第 1 节"四种出错"分类的完美样本**：`at()` 把越界当**可预期的失败**报出来；
`[]` 把越界当**程序员的责任**，不检查。

## 5. `noexcept` 与异常安全保证

### 5.1 `noexcept` 的两副面孔

| 用法 | 位置 | 含义 | 什么时候算 |
|---|---|---|---|
| **说明符** | `void f() noexcept;` | "这个函数承诺不抛异常" | 编译期写进函数类型 |
| **运算符** | `noexcept(f())` | "算一下 `f()` 这个表达式会不会抛" | **编译期常量**，可直接用在 `static_assert` 里 |

<!-- example:ch08_noexcept_operator -->
```cpp
#include <iostream>
#include <type_traits>

void plain() {}
void safe() noexcept {}

int main() {
    std::cout << std::boolalpha;
    std::cout << "noexcept(plain()) = " << noexcept(plain()) << '\n';
    std::cout << "noexcept(safe())  = " << noexcept(safe()) << '\n';
    std::cout << "noexcept(1 + 1)   = " << noexcept(1 + 1) << '\n';
    std::cout << "noexcept(new int) = " << noexcept(new int) << '\n';
    std::cout << "is_nothrow_invocable<plain> = "
              << std::is_nothrow_invocable<decltype(&plain)>::value << '\n';
}
```

<!-- result:ch08_noexcept_operator -->
```text
noexcept(plain()) = false
noexcept(safe())  = true
noexcept(1 + 1)   = true
noexcept(new int) = false
is_nothrow_invocable<plain> = false
```

**读第 3、4 行**：`noexcept(1 + 1)` 是 `true`（不可能抛），`noexcept(new int)` 是 `false`（**可能抛 `bad_alloc`**，4.3 节实测过）。
**运算符看的是表达式里所有可能抛的操作**，这是它和 `is_nothrow_*` 系列 traits 的分工：

| 工具 | 问的问题 |
|---|---|
| `noexcept(表达式)` | "**这一个表达式**会不会抛？" |
| `std::is_nothrow_move_constructible<T>` | "**类型 T** 的移动构造会不会抛？" |
| `std::is_nothrow_invocable<F>` | "**可调用对象 F** 调用时会不会抛？" |

### 5.2 违反 `noexcept` 说明符会怎样

<!-- example:ch08_noexcept_throw -->
```cpp
#include <iostream>
#include <stdexcept>

void f() noexcept { throw std::runtime_error("在 noexcept 里抛出"); }

int main() {
    std::cout << "开始\n";
    try { f(); }
    catch (...) { std::cout << "抓不到\n"; }
    std::cout << "结束\n";
}
```

**编译时有这条警告**（原文）：

```text
main.cpp(5): warning C4297: “f”: 假定函数不引发异常，但确实发生了
```

**真实运行结果**（本机实测）：

```text
stdout：空
stderr：空
退出码：-1073740791（0xC0000409）
```

**`try { f(); } catch (...) { }` 完全不起作用**——`noexcept` 函数里抛出时，标准要求立刻调用 `std::terminate`，
异常**不会**向外传播。

> **"承诺"是要兑现的**：`noexcept` 不是"优化提示"，是**契约**。
> 违反了不会得到一个可处理的异常，而是**直接终止进程**。
> 那条 `C4297` 是唯一的编译期线索——它说的就是"你这里会有麻烦"。

### 5.3 `noexcept` 最实际的影响：容器决定"搬旧元素时走快路还是慢路"

这是本章最值得记住的一段实测。先看**移动构造带 `noexcept`** 的版本：

<!-- example:ch08_move_noexcept -->
```cpp
#include <iostream>
#include <type_traits>
#include <utility>
#include <vector>

class Tracer {
    int id_;
public:
    explicit Tracer(int i) : id_(i) {}
    Tracer(const Tracer& o) : id_(o.id_) { std::cout << "拷贝 " << id_ << '\n'; }
    Tracer(Tracer&& o) noexcept : id_(o.id_) { std::cout << "移动 " << id_ << '\n'; }
};

int main() {
    std::cout << std::boolalpha;
    std::cout << "nothrow_move=" << std::is_nothrow_move_constructible<Tracer>::value << '\n';
    std::cout << "cond_move   =" << noexcept(std::declval<std::vector<Tracer>&>()
                                             .push_back(std::declval<Tracer>())) << '\n';
    std::vector<Tracer> v;
    v.reserve(2);
    v.push_back(Tracer(1));
    v.push_back(Tracer(2));
    std::cout << "--- 扩容 ---\n";
    v.push_back(Tracer(3));
    std::cout << v.size() << '\n';
}
```

<!-- result:ch08_move_noexcept -->
```text
nothrow_move=true
cond_move   =false
移动 1
移动 2
--- 扩容 ---
移动 3
移动 1
移动 2
3
```

现在**只把 `noexcept` 去掉**，其它一个字不改：

<!-- example:ch08_move_noexceptless -->
```cpp
#include <iostream>
#include <type_traits>
#include <utility>
#include <vector>

class Tracer {
    int id_;
public:
    explicit Tracer(int i) : id_(i) {}
    Tracer(const Tracer& o) : id_(o.id_) { std::cout << "拷贝 " << id_ << '\n'; }
    Tracer(Tracer&& o) : id_(o.id_) { std::cout << "移动 " << id_ << '\n'; }
};

int main() {
    std::cout << std::boolalpha;
    std::cout << "nothrow_move=" << std::is_nothrow_move_constructible<Tracer>::value << '\n';
    std::cout << "cond_move   =" << noexcept(std::declval<std::vector<Tracer>&>()
                                             .push_back(std::declval<Tracer>())) << '\n';
    std::vector<Tracer> v;
    v.reserve(2);
    v.push_back(Tracer(1));
    v.push_back(Tracer(2));
    std::cout << "--- 扩容 ---\n";
    v.push_back(Tracer(3));
    std::cout << v.size() << '\n';
}
```

<!-- result:ch08_move_noexceptless -->
```text
nothrow_move=false
cond_move   =false
移动 1
移动 2
--- 扩容 ---
移动 3
拷贝 1
拷贝 2
3
```

**逐行对比"扩容"之后那两行**：

| 例子 | `is_nothrow_move_constructible<Tracer>` | 扩容时搬走已有元素用的操作 |
|---|---|---|
| 移动构造带 `noexcept` | `true` | **移动 1 / 移动 2** |
| 移动构造**不带** `noexcept` | `false` | **拷贝 1 / 拷贝 2** |

**为什么 `vector` 要这么做**：扩容时它要把旧元素搬到新存储。
如果**移动**过程中抛异常，旧存储里的元素可能已经被改了一半，新的又没建成——容器进入无法回退的状态。

所以标准库用一条保守策略（`std::move_if_noexcept` 的思路）取舍：

> **移动构造是 `noexcept` → 用移动（快，且抛了也能保证安全）。
> 移动构造可能抛 → 退回用拷贝（慢，但拷贝抛了原对象还在，容器不变）。**

**这就是 `noexcept` 真正的分量**：它不是一个装饰，**它是容器选路的依据**。漏了它，你的类型在所有标准容器里都会退化成"扩容时拷贝"。

> **实践规则**：**只要移动构造函数确实不会抛，就标上 `noexcept`。**
> （移动构造本身是第 12 章第 2 节的主题；这里先记住这条因果关系。）

### 5.4 一处必须纠正的直觉：`cond_move` 那两行为什么是 `false`

上面两个例子里，`cond_move` **都是 `false`**——即使 `Tracer` 的移动构造是 `noexcept`。这不是笔误。

`push_back` 的行为取决于**元素搬进新存储时**用的是什么操作（移动还是拷贝），
而这条路径上的条件包含 `is_nothrow_move_constructible<T>`；
但 `noexcept(表达式)` 看的是**你写出的那个表达式**里所有可能抛的操作，
`push_back(Tracer&&)` 这一整条路径上还有别的东西（比如构造新元素本身）也不是 `noexcept` 的。
**所以不能拿 `noexcept(v.push_back(x))` 去推断"扩容会不会用移动"**——要直接看 `is_nothrow_move_constructible<T>`，或者看实际打印。

**顺便纠正另一个直觉**：`std::vector<T>` **自己的**移动构造函数**是** `noexcept` 的，**即使 `T` 的移动构造不是**：

<!-- example:ch08_vector_move -->
```cpp
#include <iostream>
#include <type_traits>
#include <vector>

class Throwing {
    int id_;
public:
    explicit Throwing(int i) : id_(i) {}
    Throwing(const Throwing& o) : id_(o.id_) {}
    Throwing(Throwing&& o) : id_(o.id_) {}          // 故意不标 noexcept
};

class Safe {
    int id_;
public:
    explicit Safe(int i) : id_(i) {}
    Safe(const Safe& o) : id_(o.id_) {}
    Safe(Safe&& o) noexcept : id_(o.id_) {}
};

int main() {
    std::cout << std::boolalpha;
    std::cout << "vector<int>                     移动 noexcept = "
              << std::is_nothrow_move_constructible<std::vector<int>>::value << '\n';
    std::cout << "vector<Safe>                    移动 noexcept = "
              << std::is_nothrow_move_constructible<std::vector<Safe>>::value << '\n';
    std::cout << "vector<Throwing>                移动 noexcept = "
              << std::is_nothrow_move_constructible<std::vector<Throwing>>::value << '\n';
    std::cout << "Throwing 自己                   移动 noexcept = "
              << std::is_nothrow_move_constructible<Throwing>::value << '\n';
    std::cout << "is_move_constructible<Throwing> = "
              << std::is_move_constructible<Throwing>::value << '\n';
}
```

<!-- result:ch08_vector_move -->
```text
vector<int>                     移动 noexcept = true
vector<Safe>                    移动 noexcept = true
vector<Throwing>                移动 noexcept = true
Throwing 自己                   移动 noexcept = false
is_move_constructible<Throwing> = true
```

**读第 3、4 行**：`vector<Throwing>` 的移动是 `true`，`Throwing` 自己却是 `false`。
**因为 `vector` 的移动构造只是"把三个指针接过来"**（不搬元素），所以它自己不抛——
**这和"扩容时怎么搬元素"是两件不同的事**。5.3 节讲的是后者。

> **区分这两个问题，是这一节最容易混的地方**：
>
> | 问题 | 由谁决定 |
> |---|---|
> | `vector` 对象**自己** move 时抛不抛 | `vector` 的实现（只有指针转移） |
> | `vector` **扩容**时搬旧元素用移动还是拷贝 | **元素类型**的移动构造是不是 `noexcept` |

### 5.5 异常安全的三级保证

"异常安全"不是一个开关，而是三个等级。**写库代码时必须说明自己提供哪一级**：

| 级别 | 承诺 | 出异常后对象处于 | 典型代价 |
|---|---|---|---|
| **不抛保证**（nothrow） | 这个操作**绝不抛** | 操作成功完成 | 要用不分配、不调用户代码的实现方式 |
| **强保证**（strong） | **要么成功，要么完全回到操作前的状态**（"事务性"） | 原样不变 | 常常要"先做副本，成功后再交换" |
| **基本保证**（basic） | 不泄漏、不破坏不变量，但对象可以处于任何**合法**状态 | 合法但内容未指定 | 最低要求，几乎所有代码都该做到 |
| （无保证） | 什么都没承诺 | 可能泄漏、不变量可能被破坏 | ❌ 不可接受 |

**强保证的一个实测**：

<!-- example:ch08_strong_guarantee -->
```cpp
#include <iostream>
#include <stdexcept>
#include <vector>

class Item {
    int id_;
public:
    explicit Item(int id) : id_(id) {
        if (id == 3) { throw std::runtime_error("构造失败"); }
        std::cout << "构造 " << id_ << '\n';
    }
};

int main() {
    std::vector<Item> v;
    v.emplace_back(1);
    v.emplace_back(2);
    std::cout << "size=" << v.size() << " capacity=" << v.capacity() << '\n';
    try {
        v.emplace_back(3);
    } catch (const std::exception& e) {
        std::cout << "捕获: " << e.what() << '\n';
    }
    std::cout << "size=" << v.size() << " capacity=" << v.capacity() << '\n';
}
```

<!-- result:ch08_strong_guarantee -->
```text
构造 1
构造 2
size=2 capacity=2
捕获: 构造失败
size=2 capacity=2
```

**第三行和第五行完全一样**：`emplace_back` 抛异常之后，容器的 `size` 和 `capacity` **都没变**。
标准要求 `vector::emplace_back` / `push_back` 提供**强保证**——本机实测它确实做到了。

**怎么自己判断一段代码提供哪一级**：

```text
1. 它会不会分配内存 / 调用用户提供的代码（拷贝构造、比较、析构……）？
      不会 → 它可能提供"不抛保证"
2. 出异常时，它有没有可能已经改了 this 的一部分成员？
      会   → 只有"基本保证"（要升到强保证就得改成"先副本再交换"）
      不会 → 强保证
```

**"先副本再交换"为什么能升到强保证**：改动全部发生在副本上。
副本改到一半抛异常 → 扔掉副本，`this` 一个字节都没动过（强保证）。
副本改完了 → 用不会抛的 `swap` 一次交换（这一步是不抛保证）。**三个级别就这样组合起来了。**

## 6. 不抛异常的错误报告：错误码 / `std::optional` / `std::expected`

异常不是唯一的路。这一节把三种"不走异常"的方式摆在一起，和异常对比。

### 6.1 错误码：把失败当成返回值传出去

<!-- example:ch08_error_code -->
```cpp
#include <iostream>

enum class Err { ok, not_found, bad_input };

const char* name_of(Err e) {
    switch (e) {
        case Err::ok:        return "ok";
        case Err::not_found: return "not_found";
        case Err::bad_input: return "bad_input";
    }
    return "?";
}

Err find(int key, int& out) {
    if (key < 0) { return Err::bad_input; }
    if (key != 7) { return Err::not_found; }
    out = 700;
    return Err::ok;
}

int main() {
    int value = 0;
    Err e = find(7, value);
    std::cout << name_of(e) << ' ' << value << '\n';
    e = find(1, value);
    std::cout << name_of(e) << ' ' << value << '\n';
}
```

<!-- result:ch08_error_code -->
```text
ok 700
not_found 700
```

**执行轨迹**：

```text
find(7, value)：
  1. key >= 0，不返回
  2. key == 7 → out = 700
  3. 返回 Err::ok                          → 调用方必须自己检查
find(1, value)：
  1. key >= 0
  2. key != 7 → 直接返回 Err::not_found     ← value 没有被写
  3. 调用方看到 not_found，但仍要自己判断"value 能不能用"
```

**错误码的两个固有问题**（第二行输出就是证据）：

| 问题 | 说明 |
|---|---|
| **调用方可以无视返回值** | 写成 `find(1, value);` 也编得过，`value` 就是上次的旧值 |
| **失败时的"输出"是什么状态没保证** | 上面 `value` 保留了上一次的 `700`——这是隐患 |

### 6.2 `std::optional`：把"可能没有值"写进类型里（C++17）

第二个问题在现代写法里用 `std::optional` 解决——让"没有值"这件事**在类型系统里**表达出来：

<!-- example:ch08_optional -->
```cpp
#include <iostream>
#include <optional>
#include <string>

std::optional<int> parse_positive(const std::string& s) {
    try {
        int v = std::stoi(s);
        if (v > 0) { return v; }
    } catch (...) {
    }
    return std::nullopt;
}

int main() {
    std::cout << std::boolalpha;
    auto a = parse_positive("42");
    std::cout << a.has_value() << ' ' << a.value_or(-1) << '\n';
    auto b = parse_positive("-1");
    std::cout << b.has_value() << ' ' << b.value_or(-1) << '\n';
    auto c = parse_positive("abc");
    std::cout << c.has_value() << ' ' << c.value_or(-1) << '\n';
}
```

<!-- result:ch08_optional -->
```text
true 42
false -1
false -1
```

| 用法 | 含义 |
|---|---|
| `std::optional<T>` | "要么有一个 `T`，要么什么都没有" |
| `return v;` | 有值 |
| `return std::nullopt;` | 没有值 |
| `.has_value()` / `if (opt)` | 有没有值 |
| `.value()` | 取出来；**没有值时抛 `std::bad_optional_access`** |
| `.value_or(d)` | 取出来，没有值就用默认值 `d`（**最常用**） |
| `*opt` | 取出来，**不检查**（没有值时是未定义行为） |

最后两行的区别要实测才看得清：

<!-- example:ch08_optional_throw -->
```cpp
#include <iostream>
#include <optional>
#include <string>

int main() {
    std::optional<int> empty;
    std::cout << std::boolalpha << empty.has_value() << '\n';
    try {
        std::cout << empty.value() << '\n';
    } catch (const std::exception& e) {
        std::cout << "value() 抛: " << e.what() << '\n';
    }
    // *empty 不检查：下面是未定义行为，故意不执行
}
```

<!-- result:ch08_optional_throw -->
```text
false
value() 抛: Bad optional access
```

> ⚠️ **`optional` 表达不了"为什么失败"**：它只有"有 / 没有"两种状态。
> 需要携带原因时，就是异常（或下一个）。
> **另外**：`.value()` 会抛，`*opt` 不会——**这也是"检查版 / 不检查版"那一对**（4.6 节的 `at()` vs `[]`）。

### 6.3 `std::expected`：要么是值，要么是错误原因（**C++23**）

`std::expected<T, E>` 同时装"值"和"错误原因"，是很多人等了很久的东西。**但它是 C++23 的。**

<!-- example:ch08_expected_cxx17_FAIL -->
```cpp compile-fail
#include <expected>

int main() {
    std::expected<int, int> e{42};
    (void)e;
}
```

```text
main.cpp(4): error C2039: "expected": 不是 "std" 的成员
main.cpp(4): error C2065: “expected”: 未声明的标识符
main.cpp(4): error C2062: 意外的类型“int”
main.cpp(4): error C2143: 语法错误: 缺少“;”(在“{”的前面)
main.cpp(4): error C2143: 语法错误: 缺少“}”的前面
main.cpp(5): error C2065: “e”: 未声明的标识符
```

**这份诊断本身就是一个知识点**：`std::expected` 在当前基线（`/std:c++17`）里**不存在**。
第一条 `error C2039: "expected": 不是 "std" 的成员` 是真正的原因；后面五条全是它引起的连锁错误
（名字不存在 → 后面的语法都解析不了）。

> **读多错误诊断的方法**：**只看前两条，尤其是第一条。**
> 后面的错误往往是"因为前面那个名字不存在"衍生出来的；修好第一个，它们会一起消失。

**本章基线是 C++17，所以：`std::expected` 只标注为「C++23 起」，不进正文主干。**
它在 C++17 下的替代方案就是 6.1 的错误码加一个输出参数，或者 6.2 的 `optional`（如果不需要携带原因）。
**本机是否在 `/std:c++latest` 下支持 `std::expected`，本轮未实测**（见第 12 节）。

### 6.4 四条路怎么选：一张对比表

| | 异常 | 错误码 | `std::optional` | `std::expected`（C++23） |
|---|---|---|---|---|
| 传播方式 | **自动**沿调用栈向上找 handler | 调用方**手动**检查并逐层传递 | 手动检查 | 手动检查 |
| 调用方忽略会怎样 | **不会静默**——不接住就终止程序 | **静默继续跑**（最危险） | 编译上能忽略；`*opt` 取错是 UB | 编译上能忽略 |
| 能不能带失败原因 | ✅ 类型 + 消息 | ✅ 码 | ❌ 只有"有/没有" | ✅ 值 + 原因 |
| 成功路径开销 | 零开销（现代实现的零成本异常） | 零开销 | 零开销 | 零开销 |
| 能不能用在 | 有异常机制的地方 | **任何地方**（含 `noexcept` 函数、C 接口、嵌入式） | 同左 | 同左 |
| 调用方要写多少代码 | 只在能处理的那一层写 `try` | **每个调用点**都要写检查 | 要写检查 | 要写检查 |
| C++ 版本 | C++98 起 | 一直有 | **C++17** | **C++23** |

**实用的判断顺序**：

```text
1. 这个失败是"可预期的、调用方要处理的"吗？
      不是 → 是 bug → 用 assert（第 7 节）
      是   → 继续
2. 这个函数能抛异常吗？（跨 C 接口 / 标了 noexcept / 无异常环境）
      不能 → 错误码 或 optional
      能   → 继续
3. 需要携带失败原因吗？
      不需要 → std::optional
      需要   → 异常（C++17 基线下的默认选择）
```

**社区默认倾向**：**异常用于"真正异常的情况"，不是控制流。**
用一个异常表示"遍历到了末尾"是滥用；用一个异常表示"文件打不开"是合适的。

## 7. 断言：`assert` 与 `static_assert`

这一节对应第 1 节的第三类："**违反不变量**——不该发生的事"。

### 7.1 `assert`：运行期检查，且 release 下整段消失

```cpp
#include <cassert>
assert(n > 0);
```

<!-- example:ch08_assert -->
```cpp
#include <cassert>
#include <iostream>

int main() {
    int n = 5;
    assert(n > 0);
    std::cout << "断言通过\n";
    assert(n > 10);
    std::cout << "不会到这里\n";
}
```

**编译成功，警告 0 条**。本机实测的真实结果：

```text
stdout：空
stderr：Assertion failed: n > 10, file main.cpp, line 8
退出码：-1073740791（0xC0000409）
```

**三件事同时发生了**：

1. 第一个断言**通过**了（所以"断言通过"这一行本该打印——但它也丢了，因为 stdout 没 flush，2.4 节讲过）
2. 第二个断言失败，**诊断信息去了 `stderr`**（所以它留下来了），格式是
   `Assertion failed: <表达式原文>, file <文件名>, line <行号>`
3. 进程被终止，退出码 `0xC0000409`

**`stderr` 上的这行文本是本机最好用的崩溃线索**——它有**表达式、文件、行号**三样信息，
比任何手写 `printf` 都准。**可惜它只在断言上，不在访问违规上。**

### 7.2 `NDEBUG`：定义它，断言就成了一段空气

**这是 `assert` 最重要也最危险的性质。** 定义宏 `NDEBUG`（通常在 release 构建里）后，
`assert(...)` 变成**什么也不做**——**连里面的表达式都不会求值**。

"不会求值"这一条必须实测才敢说：

<!-- example:ch08_assert_ndebug -->
```cpp
#include <cassert>
#include <iostream>

int tick() {
    std::cout << "tick() 被调用了\n";
    return 1;
}

int main() {
    assert(tick() == 1);          // NDEBUG 下整行消失，tick() 根本不会被调用
    std::cout << "断言之后的代码\n";
}
```

**加 `/DNDEBUG` 编译后，本机实测的真实输出**：

```text
断言之后的代码
```

**`tick() 被调用了` 那一行没有出现**——不是"输出丢了"，而是**这个函数根本没被调用**。
在探针里我把调用次数打了出来，加 `/DNDEBUG` 后是 `calls=0`。**这行 `assert` 连同它的副作用一起消失了。**

**还有一条"断言被去掉"的旁证**（探针单独跑的例子，本机实测原文）：

```text
main.cpp(5): warning C4189: “n”: 局部变量已初始化但不引用
```

`n` 只在 `assert` 里被用到，断言没了之后它就变成了一个没用的变量。**编译器用 `C4189` 把这件事说了出来。**

> ⚠️ **坑（这条会造成真实事故）**：**把有副作用的表达式放进 `assert`。**
>
> ```cpp
> assert(open_file("a.txt") == 0);     // ❌ release 下这行整个消失，文件根本不会打开
> ```
>
> **为什么危险**：debug 构建一切正常，release 构建行为完全不同，
> 而且**可能一条警告都没有**——上面那条 `C4189` 只在"变量没有别的用处"时才出现；
> 如果 `n` 在别处也被用到，编译器什么都不会说。
>
> **规则**：`assert` 里的表达式**只能读取状态，不能改变状态**。

### 7.3 `assert` 的正确用途

| 该用 `assert` | 不该用 `assert` |
|---|---|
| 检查"程序自己保证的不变量" | **校验用户输入 / 文件内容 / 网络数据** |
| 检查函数入口的前置条件（调用方应当保证） | 检查**可预期的失败**（用异常或错误码） |
| 检查某段逻辑"不可能走到这里" | 做**有副作用**的操作 |
| 在开发期尽早暴露 bug | 作为**唯一**的输入校验手段 |

**判据还是第 1.1 节那句话**：**"出错了调用方还能做什么？"**
调用方什么也做不了，说明这是程序内部的 bug——**那就该用断言，而且该让它崩得越早越好。**

### 7.4 `static_assert`：编译期检查

`static_assert` 的条件必须是**编译期常量**，检查发生在**编译期**：

<!-- example:ch08_static_assert -->
```cpp
#include <iostream>
#include <type_traits>

static_assert(sizeof(int) == 4, "本机 int 不是 4 字节");
static_assert(std::is_integral<int>::value, "int 必须是整型");

int main() {
    std::cout << "两个静态断言都通过\n";
}
```

<!-- result:ch08_static_assert -->
```text
两个静态断言都通过
```

失败时是**编译错误**，而且消息就是你写的那句话：

<!-- example:ch08_static_assert_FAIL -->
```cpp compile-fail
static_assert(sizeof(int) == 8, "本机 int 不是 8 字节");

int main() {}
```

```text
main.cpp(1): error C2338: static assertion failed: '本机 int 不是 8 字节'
```

### 7.5 两者对比

| | `assert` | `static_assert` |
|---|---|---|
| 检查时机 | **运行期** | **编译期** |
| 条件要求 | 任意表达式 | **必须是编译期常量** |
| 失败后果 | 打印诊断（走 stderr）+ 终止进程 | **编译失败**（`error C2338`） |
| release（定义 `NDEBUG`） | **整段被去掉**，**连表达式都不求值** | **永远生效** |
| 能不能带消息 | ❌ 只打印表达式原文 | ✅ 第二参数就是消息（C++17 起可省略） |
| 典型用途 | 运行期不变量、前置条件 | 类型假设、平台假设、模板约束 |

**一句话**：**能在编译期检查的，一律用 `static_assert`。**
编译期发现的错误，代价是"改一行"；运行期发现的错误，代价是"发一次版"。

> `static_assert` 在模板里的用法（检查类型参数是否符合要求）是第 11 章「模板与泛型」的内容——
> 那里它才真正发挥威力。第 13 章还会回到 `constexpr` 与编译期计算。

### 8.2 手段一：看退出码

进程怎么结束的，退出码会告诉你。**这是没有调试器时最可靠的第一手线索。**

**本机实测的退出码对照表**（全部来自本轮探针的真实运行）：

| 程序怎么结束的 | 退出码（十六进制） | 本机出处 |
|---|---|---|
| 正常返回（示例里 `return 7`） | `0x7` | `ch08_exit_code` |
| 正常返回 | `0x0` | 大多数示例 |
| **未捕获的异常** | **`0xC0000409`** | `ch08_uncaught` |
| **`assert` 失败** | **`0xC0000409`** | `ch08_assert` |
| **`noexcept` 函数里抛出** | **`0xC0000409`** | `ch08_noexcept_throw` |
| **栈展开中析构函数又抛出** | **`0xC0000409`** | `ch08_dtor_throw` |
| 自定义 `terminate` 处理器 + `abort` | `0xC0000409` | `ch08_terminate_cerr` |
| **空指针解引用** | **`0xC0000005`** | 第 06 章 `ch06_null_deref` |
| **重复释放** | **`0xC0000374`** | 第 06 章 `ch06_double_delete` |
| 栈溢出 | ⚠️ **本轮未实测** | （Windows 常见值是 `0xC00000FD`，**未验证**） |

**注意十进制与十六进制的换算**：`0xC0000409` 按无符号读是 `3221226505`，按**有符号**读就是 `-1073740791`。
本机在批处理里用 `%ERRORLEVEL%` 读出来是**有符号**的那个；两种写法指的是**同一个**值。

**读这张表的方法**：

- `0xC0000409`：**"程序主动自杀"**。未捕获异常、断言失败、`noexcept` 里抛出、`terminate` 都会走这条路。
  MSVC 用的是 `__fastfail`，所以它**不会冲洗缓冲区，也不会打印消息**（2.4 / 3.7 节都实测到 stdout、stderr 双空）。
- `0xC0000005`：**访问违规**。通常是空指针解引用或野指针。
- `0xC0000374`：**堆结构被破坏**。通常是重复释放或越界写堆。

**怎么在命令行看到退出码**：

```bat
main.exe
echo %ERRORLEVEL%
```

一条最小验证（本机实测输出）：

<!-- example:ch08_exit_code -->
```cpp
#include <iostream>

int main() {
    std::cout << "即将以 7 退出\n";
    return 7;
}
```

<!-- result:ch08_exit_code -->
```text

```

（程序本身只打印一行；`echo %ERRORLEVEL%` 读到的是 **7**。这就是"退出码是一条可用的线索"的最简证明。）

**注意**：`%ERRORLEVEL%` 必须**紧接着**那条命令读，中间插了别的命令它就被覆盖了。

### 8.3 手段二：把诊断信息送去 `stderr`，并 `flush`

由 2.4 节和 3.7 节的实测可知：**崩溃时 stdout 里没 flush 的内容会丢，写到 `stderr` 的内容会留下。**

| 做法 | 崩溃时还能看到吗 |
|---|---|
| `std::cout << "..."` | ❌ 可能丢 |
| `std::cout << "..." << std::flush;` | ✅ |
| `std::cout << "..." << std::endl;` | ✅（`endl` = `'\n'` + flush） |
| `std::cerr << "..."` | ✅（**默认不缓冲**） |
| `assert` 的输出 | ✅（走 `stderr`） |

**同一个例子里两种写法对比**：

<!-- example:ch08_flush_compare -->
```cpp
#include <iostream>
#include <stdexcept>

int main() {
    std::cout << "这一行被 flush 了\n" << std::flush;
    std::cout << "这一行还在缓冲区里\n";
    throw std::runtime_error("没人接住我");
}
```

<!-- result:ch08_flush_compare -->
```text
这一行被 flush 了
```

（进程以 `0xC0000409` 终止；"这一行还在缓冲区里"**没有出现**。）

**为什么 `cout` 要缓冲**：一次一字节地写系统调用太慢，标准库先攒着，攒够或遇到 `flush` 才真正写出去。
**平时这是纯收益，崩溃时它变成"线索丢失"。**

### 8.4 手段三：换掉 `terminate` 处理器，让"自杀"留下遗言

`std::terminate` 默认什么都不打印。**可以换掉它**——注意这里必须用 `std::cerr`：

<!-- example:ch08_terminate_cerr -->
```cpp
#include <cstdlib>
#include <exception>
#include <iostream>
#include <stdexcept>

void my_terminate() {
    std::cerr << "terminate 被调用：异常没人接住\n";
    std::abort();
}

int main() {
    std::set_terminate(my_terminate);
    std::cerr << "开始\n";
    throw std::runtime_error("没人接");
}
```

**本机实测的真实结果**（stderr 内容）：

```text
开始
terminate 被调用：异常没人接住
```

**按 `std::cout` 写会怎样**？本机也测了——**同一段代码，只把那两条 `std::cerr` 换成 `std::cout`**：

<!-- example:ch08_terminate_cout -->
```cpp
#include <cstdlib>
#include <exception>
#include <iostream>
#include <stdexcept>

void my_terminate() {
    std::cout << "terminate 被调用：异常没人接住\n";
    std::abort();
}

int main() {
    std::set_terminate(my_terminate);
    std::cout << "开始\n";
    throw std::runtime_error("没人接");
}
```

**本机实测的真实结果**：

```text
stdout：空
stderr：空
退出码：-1073740791（0xC0000409）
```

**一个字都看不到。** 两个例子只差 `cout`/`cerr`，可观测性差了一个数量级。

（这一段故意**不加** `<!-- result: -->` 标记：它要展示的东西是"**空白**"，
而空输出用标记反而没法说明"这里是空的、不是漏写"。）

> **`set_terminate` 是"没有调试器时的断点"**：在处理器里打印、记录最后处理的请求、
> 把状态写进日志文件，然后再 `abort()`。
> **注意**：处理器里**不能抛异常**（它就是来处理异常的），也不要指望它能正常返回。

### 8.5 手段四：用二分法缩小范围

如果异常是你自己 `throw` 的，最直接的办法是**缩小范围**：

```text
1. 在 main 最外层套 try { ... } catch (const std::exception& e) { std::cerr << e.what(); }
     ——先确认"它确实是个 C++ 异常"，而不是 0xC0000005 那种硬崩溃
2. 在可疑函数的入口/出口各打一条 cerr
     ——确定是"哪个函数里抛的"
3. 在那个函数里继续对半切
```

**为什么用 `cerr` 而不是 `cout`**：见 8.3 节（本机实测）。
**为什么先区分异常和硬崩溃**：两者的退出码不同（`0xC0000409` vs `0xC0000005`），能处理的手段也不同。

### 8.7 手段六：调试堆查内存问题

第 06 章第 9.3 节给了本机实测的做法（`/MDd` + `_CrtSetReportMode` + `_CrtDumpMemoryLeaks`）。
对本章的意义是：**如果崩溃是堆引起的（`0xC0000374`），那是本机唯一可用的排查手段。**

### 8.8 一份排查流程

```text
程序异常结束
├─ 1. 记下退出码
│     0xC0000409 → 程序"自杀"：未捕获异常 / assert / terminate / noexcept 里抛 → 走第 2 步
│     0xC0000005 → 访问违规：查空指针、野指针（第 06 章第 10 节）
│     0xC0000374 → 堆被破坏：查重复释放、越界写堆
├─ 2. 看 stderr
│     assert 的 "Assertion failed: ... line N" 直接给出行号
│     没有 stderr 信息 → 说明是未捕获异常且没装 terminate 处理器 → 去第 3 步
├─ 3. 装一个 terminate 处理器（写 cerr），重跑
├─ 4. 还是定位不到 → 用 cerr 打点做二分
├─ 5. 怀疑内存 → 用 /MDd 的调试堆
└─ 6. 全程开着 /W4 看警告
```

> **最重要的一条经验**：**崩溃点往往不是出错点。**
> 尤其是 `0xC0000374`（堆被破坏）——破坏可能发生在很久之前，
> 分配器只是**在下次分配或释放时才发现**，于是报错位置和真正的错误位置隔了很远。
> 这与第 06 章第 10.5 节讲的越界是同一个道理。

## 10. 本章自测

**1.** 下面这段代码，`delete p;` 会不会执行？为什么？

```cpp
void f() {
    int* p = new int(5);
    might_throw();          // 假设这个函数可能抛异常
    std::cout << *p << '\n';
    delete p;
}
```

<details><summary>答案</summary>

**不会执行**（`might_throw()` 抛出时）。

**为什么**：异常从 `might_throw()` 抛出后开始栈展开。栈展开销毁 `f` 的**局部对象**——
`p` 这个指针变量**确实**被销毁了。但 `p` 指向的那块**堆内存不是局部对象**，
没有任何机制会去 `delete` 它。于是它是**泄漏**。见本章 3.8 节。

**修法**：把资源交给一个对象持有。

```cpp
void f() {
    auto p = std::make_unique<int>(5);   // 第 12 章第 6.1 节
    might_throw();
    std::cout << *p << '\n';
}                                        // 栈展开会调用 unique_ptr 的析构函数
```

**这一题就是"RAII 为什么是 C++ 最核心的设计"的最短证明**：
`delete p;` 这一行代码本身没错，错在它**必须被执行到**，而异常让它执行不到。

</details>

**2.** 下面这段代码会输出几行？顺序是什么？（每个 `Tracer` 构造和析构各打印一行）

```cpp
void inner() { Tracer b("b"); throw std::runtime_error("x"); }
void outer() { Tracer a("a"); inner(); }
int main() {
    try { outer(); } catch (const std::exception& e) { std::cout << "caught\n"; }
}
```

<details><summary>答案</summary>

共 **5 行**：

```text
构造 a
构造 b
析构 b
析构 a
caught
```

**顺序就是栈展开的顺序**：先拆 `inner` 的栈帧（析构 `b`），再拆 `outer` 的栈帧（析构 `a`），
**逆序**，清完之后才进入 `main` 的 `catch`。

**注意最后一行是 `caught` 而不是别的**——本机实测（第 12 章第 7.1 节 `ch12_raii_exception`）
证实"**异常路径上的析构发生在 `catch` 之前**"。本章 3.2 节的实测（`ch08_unwind_nested_scopes`）
进一步证明**同一个函数里的嵌套块也按同样的规则一层层退**。

</details>

**3.** 下面两次捕获的结果一样吗？为什么？编译器会说什么？

```cpp
try { throw std::out_of_range("越界"); }
catch (const std::exception& e) { /* A */ }
catch (const std::out_of_range& e) { /* B */ }
```

<details><summary>答案</summary>

**会走 A，B 永远不会执行。**

因为 `catch` **按书写顺序**尝试匹配，而 `std::out_of_range` **继承自** `std::exception`，
所以 A 能匹配上，后面的 B 成了死代码。见本章 2.6 节。

**本机实测会给出警告**：

```text
main.cpp(9): warning C4286: “const std::out_of_range &”: 由基类(“const std::exception &”)在行 7 上捕获
```

**规则**：**`catch` 必须从最派生写到最基类。**

</details>

**4.** 下面两段都在析构函数里抛异常。哪一段会终止进程？为什么？

```cpp
// 第一段
void f() {
    Bad b;
    throw std::runtime_error("先抛一个");   // b 在栈展开中被析构 → ~Bad 抛出
}
// 第二段
int main() {
    try { Bad b; }                            // 正常离开作用域 → ~Bad 抛出
    catch (const std::exception& e) { std::cout << "捕获\n"; }
}
```

<details><summary>答案</summary>

**第一段终止进程（本机实测退出码 `0xC0000409`，stdout 空、stderr 空）；
第二段能正常捕获（本机实测输出 `作用域结束前` / `捕获 析构里抛出` / `继续执行`）。**

**原因**：C++ 规定**同一时刻只能有一个"正在传播的异常"**。

- 第一段：已经有一个异常在传播（`"先抛一个"`），栈展开要析构 `b` 时 `~Bad()` **又抛出一个** → 两个异常同时传播 → `std::terminate`。
- 第二段：**没有别的异常在传播**，所以这只是一个普通异常，可以被正常接住。

**所以"析构函数不能抛异常"的真正理由不是"这一句 `throw` 非法"，而是"它的后果取决于它被调用的时机"**——
同一个析构函数，正常路径上没事，栈展开途中的那次就**直接终止**。你无法保证它每次都在安全的那条路径上。

**另外**：两段都必须写 `noexcept(false)` 才能编过，因为 **C++11 起析构函数默认是 `noexcept` 的**。
那个默认值就是语言在替你堵这个洞。见本章 3.7 节。

</details>

**5.** 本机实测：移动构造函数加 `noexcept` 时 `std::vector` 扩容打印"移动 1 / 移动 2"；
去掉 `noexcept` 后同一个位置打印"拷贝 1 / 拷贝 2"。为什么 `vector` 要这么做？

<details><summary>答案</summary>

**因为扩容时它必须先把旧元素搬到新存储，而搬运可能失败。**

- 用**移动**：第 1 个元素已经搬走（源对象被改），第 2 个元素的移动**抛了异常**——
  旧存储是"一半被改过、一半没动"，新存储也没建成。**容器回不到扩容前的状态**，强保证就破了。
- 用**拷贝**：拷贝过程中抛异常，**旧存储里的元素全都还在**，新存储丢掉即可，容器状态完全没变——**强保证成立**。

所以标准库用 `std::move_if_noexcept` 的思路取舍：

> **移动构造是 `noexcept` → 用移动（快且安全）；可能抛 → 退回拷贝（慢但能回退）。**

**实践规则**：**移动构造函数只要确实不抛，就标 `noexcept`。**
漏了它，你的类型在所有标准容器里扩容都会退化成拷贝。

**本机实测输出**：`ch08_move_noexcept` 里 `is_nothrow_move_constructible` 为 `true`、扩容是"移动"；
`ch08_move_noexceptless` 里变成 `false`、扩容是"拷贝"。见本章 5.3 节。

**追问一下**：`noexcept(v.push_back(x))` 在**两个**例子里都是 `false`（本机实测）。
所以**不能用它去推断"扩容会不会用移动"**——见 5.4 节。

</details>

**6.** `assert(x > 0);` 和 `static_assert(x > 0, "msg");` 有什么本质区别？什么时候该用哪个？

<details><summary>答案</summary>

| | `assert` | `static_assert` |
|---|---|---|
| 检查时机 | **运行期** | **编译期** |
| 条件要求 | 任意表达式 | **必须是编译期常量** |
| 失败后果 | `Assertion failed: ... file ... line ...`（**走 stderr**）+ 终止进程 | **编译失败**（`error C2338`） |
| release（定义 `NDEBUG`） | **整段被去掉**，**连表达式都不求值** | **永远生效** |

**选择**：**能在编译期检查的一律用 `static_assert`**（代价从"发版"降到"改一行"）。

**两个必须记住的坑**：

1. **绝不能把有副作用的表达式放进 `assert`**——release 下它整个消失。
   本机实测：`assert(tick() == 1);` 加 `/DNDEBUG` 后 **`tick()` 根本没有被调用**（探针里打印是 `calls=0`）。
2. **`assert` 不能用来校验用户输入**。用户输入属于"可预期的失败"，而 `assert` 在 release 下会被去掉——校验随之消失。

**本机实测**：断言失败时 `stderr` 上是 `Assertion failed: n > 10, file main.cpp, line 8`，退出码 `0xC0000409`。

</details>

**7.** ⚠️ **考实现定义 / 未定义行为**：本机对**同一份**越界读代码在不同开关下各跑了一次，得到五个不同的值：

```text
（无附加开关）3 / -1414022928     （无附加开关）3 / 0
（/Od）       3 / 6029370        （/O2）       3 / 1
（/Od /DEXTRA_WORK）3 / 7274612
```

**五次运行的退出码全是 0，编译警告全是 0 条。** `v[10]` 越界读属于哪一类错误？这个实验说明了什么？
如果一定要"读到能报错"，应该怎么写？

<details><summary>答案</summary>

**属于未定义行为（UB）**，而且是**运行期**的、**无法被处理**的那一类（第 1 节的第四类）。

**这个实验说明三件事**：

1. **UB 不是"结果随机"，而是"标准对结果没有任何要求"。** 五次不同的值之间没有规律，也没有"正确答案"。
2. **`0` 只是巧合。** 某一次跑出 `0` 会让人误以为"越界读到的是 0，所以我可以用 `0` 来判断越界"——
   **这个推理是错的**，换一个开关就变成 `1`。
3. **编译器和编译器开关都会改变 UB 的表现**（这里 `/O2` 是 `1`，`/Od` 是 `6029370`）。
   所以"我这边没崩"从来不是"这段代码没问题"的证据。

**"要读到能报错"应该用检查版**：

| 写法 | 越界时 |
|---|---|
| `v[10]` | **不检查**，UB（上面这五次） |
| `v.at(10)` | **抛 `std::out_of_range`**，消息 `invalid vector subscript`（本机实测） |

**这一对就是"不检查版 / 检查版"的样本**（4.6 节）：
`operator[]` 把越界当**程序员的责任**，`at()` 把它当**可预期的失败**报出来。
**"什么时候能用不检查版"的判据只有一条：下标是否已经完全由程序自己保证合法。**

</details>

**8.** 本机 `cdb` / `gdb` / `lldb` / `windbg` **都不存在**（本轮用 `where` 逐个查过）。给你一个刚崩掉的 `main.exe`，你怎么定位？

<details><summary>答案</summary>

按第 8.8 节的流程，**先用不需要调试器的手段缩小范围**：

1. **读退出码**（`main.exe` 之后立刻 `echo %ERRORLEVEL%`）：
   - `0xC0000409`（有符号读作 `-1073740791`）→ 程序"自杀"：未捕获异常 / `assert` / `noexcept` 里抛出 / `terminate`
   - `0xC0000005`（`3221225477`）→ 访问违规：空指针、野指针
   - `0xC0000374`（`3221226356`）→ 堆被破坏：重复释放、越界写堆
2. **看 `stderr`**：`assert` 会给出**表达式、文件名、行号**。
3. **装 `std::set_terminate` 处理器**，在里面用 `std::cerr` 打印线索再 `abort()`。
   本机实测：处理器里用 `cout` **一个字都看不到**，用 `cerr` 就能看到。
4. **用 `std::cerr` 打点做二分**定位抛出点。
5. **全程开 `/W4`**：本章实测的 `C4286` / `C4834` / `C4297` / `C4189` / `C4702` 每一条都指向真实缺陷。

**重要提醒**：**崩溃点往往不是出错点**，尤其是 `0xC0000374`——
堆被破坏发生在很久之前，分配器只是**下次分配/释放时才发现**。

**也要说清边界**：本机也可以装 WinDbg 或 Visual Studio 图形调试器，
**但本轮没有安装、也没有验证**，所以本节不写那些操作步骤。

**⚠️ 本条里唯一"未实测"的是栈溢出对应的退出码**（Windows 常见值 `0xC00000FD`）——
本轮没写无限递归，见第 12 节。

</details>

**9.** `std::optional<int>` 和抛 `std::invalid_argument` 都能表达"解析失败"，什么时候用哪个？
`std::expected` 能不能用？

<details><summary>答案</summary>

**核心差别是"要不要说明为什么失败"和"调用方忽略的代价"。**

| | `std::optional<int>` | 抛异常 |
|---|---|---|
| 携带失败原因 | ❌ 只有"有 / 没有" | ✅ 类型 + 消息 |
| 调用方忽略会怎样 | 拿到 `nullopt` 后可能在别处出错，或者 `.value_or(d)` **静默取默认值** | **不会静默**：不接住就终止进程 |
| 适合 | **"没有值"是这个函数的正常结果之一**（查不到、可选字段缺失） | **"不该发生但发生了"**，且调用方必须处理 |

**判断顺序**（6.4 节）：

```text
1. 是不是 bug？        → 是 bug 用 assert
2. 这个函数能抛异常吗？  → 不能（跨 C 接口 / noexcept / 无异常环境）用 optional 或错误码
3. 需要携带原因吗？     → 不需要 → optional；需要 → 异常
```

**一个具体建议**：`optional` 最适合"**查找**"这类语义——`find` 没找到是**正常结果**，不是异常情况。
而"配置文件格式错误"通常**需要说明哪里错了**，异常更合适。

**`std::expected` 不能用**：它是 **C++23**，不在本章基线（C++17）里。
本机用 `/std:c++17` 实测的原文是 `error C2039: "expected": 不是 "std" 的成员`（6.3 节）。
**本机在 `/std:c++latest` 下是否可用，本轮未实测。**

**另**：`optional` 也不是"绝对不抛"——`.value()` 在没有值时**会抛** `std::bad_optional_access`
（本机实测消息是 `Bad optional access`），而 `*opt` 是**不检查**的 UB。**它内部依然是那一对"检查版 / 不检查版"。**

</details>

**10.** 本机实测的五条警告里，挑一条说明"如果忽略它会发生什么"。

<details><summary>答案</summary>

以 **`C4702`**（不可访问代码）为例——它是本章 3.2 节那条实测警告，原文是：

```text
main.cpp(19): warning C4702: 不可访问代码
```

它指的是 `outer()` 里 `throw` 之后那句 `std::cout << "这一行不会执行\n";`。
**编译器自己算出来那句话永远到不了。**

**忽略它的后果**：如果那句话不是打印，而是**一句真正有副作用的代码**（比如 `commit();`、`unlock();`），
那么这段逻辑**永远不会执行**——而程序能编过、能跑，只是在异常路径上悄悄跳过了它。
**这正是"资源必须交给对象持有"的另一种说法**：写在 `throw` 之后的清理代码等于没写。

**其它四条同样的性质**：

| 警告 | 忽略的后果 |
|---|---|
| `C4286`（基类先捕获） | 那个更具体的 handler 从来没执行过，**错误处理行为和写的不一样** |
| `C4834`（丢掉 `[[nodiscard]]` 返回值） | 结果没被使用——很可能是"忘了用"，逻辑静默走错 |
| `C4297`（`noexcept` 里确实抛了） | 抛出时直接 `terminate`，**`try`/`catch` 拦不住**（本机实测 `0xC0000409`） |
| `C4189`（变量初始化后未引用） | 说明那段代码（通常是断言）被整段去掉了，**校验消失了** |

**共同点**：**这五条都不会让编译失败，都只在"能编过但行为和你以为的不一样"这一层报警。**
这就是 `/W4` 存在的理由。

</details>

   MSVC 上按值捕获 `std::exception` 仍然拿得到 `what()` 的消息，因为它的实现把消息指针一起拷贝了。
   **这是实现细节，不是标准保证**——凡是"按值捕获会切片"的结论，请以自定义异常那个例子（`ch08_slicing_custom`）为准。
2. **`v[10]` 那五次不同的输出（`-1414022928` / `0` / `6029370` / `1` / `7274612`）是 UB，一个都不保证重现。**
   它被写进正文，正是因为"同一个东西能跑出完全不同的结果"这一事实**才是知识点**。
3. **`0xC0000409` 这个退出码覆盖了本章多种"主动终止"的情形**
   （未捕获异常、`assert` 失败、`noexcept` 里抛出、析构抛出）。
   它是 MSVC 用 `__fastfail` 的结果，**别把它当成"未捕获异常"的唯一标志**——判定要结合 `stderr` 的内容。
4. **本轮有一处主动纠正了自己的直觉**：一开始我写下"`vector<Throwing>` 的移动是不是 `noexcept` 取决于元素"，
   实测（`ch08_vector_move`）证明**不是**——`vector` 自己的移动只转移指针。
   **5.4 节保留了这个纠正过程**，因为它是"不要凭直觉断言"的一个现成样本。
