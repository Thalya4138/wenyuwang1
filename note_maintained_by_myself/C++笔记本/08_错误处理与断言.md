## 0. 先记住的七件事

**这一章的分部**（按"失败的传播路径"这条轴排）：

```text
一次失败
├─ 先分清它是哪一类            第 1 节
├─ 走异常的传播路径
│   ├─ 怎么抛出、怎么接住        第 2 节
│   ├─ 传播路上怎么清理          第 3 节  ← 本章核心
│   ├─ 传什么类型的对象          第 4 节
│   └─ 契约与代价               第 5 节
├─ 不走异常的传播路径
│   ├─ 错误码 / optional / expected   第 6 节
│   └─ 就地检查：断言            第 7 节
└─ 传播失败之后的最后手段：排查    第 8 节
```

1. **先分类再选手段**：编译错误要改代码；**可预期的失败**要报给调用方；**违反不变量**是 bug，该崩就崩。选错了手段，代码会变得又长又不可靠。
2. **异常是"沿着调用栈向上找 handler"**：抛出点不需要知道谁处理，中间的每一层也不需要写"转发"代码。
3. **栈展开（stack unwinding）是异常能用的前提**：异常穿过一个函数时，那个函数的**局部对象按构造的逆序被析构**。
4. **所以 RAII 和异常是一对**：只要资源被对象持有，异常路径上的释放就不需要你写一行代码。**C++ 不需要 `finally`，因为析构函数就是 `finally`。**
5. **`catch` 要按 `const` 引用捕获**：按值捕获会发生**切片**，丢失动态类型。本机实测：自定义异常层次按值捕获后调的是基类版本。
6. **`noexcept` 最实际的意义是"告诉 `std::vector` 扩容时可以用移动"**：本机实测，移动构造有 `noexcept` 时扩容打印"移动"，去掉之后打印"拷贝"。
7. **程序异常终止时，还没写出的 stdout 会丢**。本机实测：未捕获异常的例子里，抛出前打印的那行一个字都没留下。**崩溃排查的第一课是"别把线索留在缓冲区里"。**

> 如果只记一条，记第 3 条。**它解释了 C++ 为什么不需要 `finally`，也解释了为什么"裸 `new`"在异常面前一定会泄漏。**

## 1. 先分清三种出错：改代码、报给调用方、崩溃

在选手段之前必须先把"出错"分类，否则会出现两种典型错误：
**用异常处理程序员自己的 bug**（把越界当业务失败catch住然后继续跑），
或者**用返回值报告"不可能发生"的事**（每个调用点都写 `if (!ok) return -1;`）。

| 类别 | 什么时候被发现 | 例子 | 正确手段 |
|---|---|---|---|
| **编译错误** | 编译期 | 类型不匹配、名字拼错、访问私有成员 | 改代码。**这不是"错误处理"，是"还没写完"。** |
| **可预期的失败** | 运行期，但**可能发生**且**调用方有办法应对** | 文件不存在、用户输入格式错、网络断开、除数为 0 | **异常** 或 **错误码 / `optional`** |
| **违反不变量（bug）** | 运行期，**不该发生** | 数组越界、空指针解引用、内部状态自相矛盾 | **`assert`**；release 下就让它崩 |
| **未定义行为** | 什么都可能 | 悬垂指针、重复释放 | **没有手段能"处理"它，只能避免**（第 06 章第 10 节） |

**判别"可预期的失败"还是"bug"的一句话测试**：

> **"这段代码在生产环境里出错时，调用方除了记录日志和放弃这次操作，还能做什么？"**
>
> - 能（重试、换一个文件、提示用户重新输入）→ **可预期的失败**，用异常或错误码报出去
> - 不能（说明程序内部逻辑已经坏了）→ **bug**，用断言，让它尽早暴露

**为什么这个区分重要**：如果把 bug 当成"可预期失败"来"处理"，
程序会带着已经被破坏的状态继续运行——**这比直接崩溃危险得多**。
比如数组越界后读到垃圾值，你"处理"了这个错误码继续算，最后输出一个看起来正常但完全错误的结论。

> ⚠️ **坑**：把 `assert` 用来校验用户输入。`assert` 在 release 构建里会被整个去掉，
> 于是"校验"消失了。**用户输入永远要用运行期的检查（异常或错误码），不是断言。** 第 7 节展开。

## 2. 异常：`throw` / `try` / `catch`

### 2.1 最小闭环

<!-- example:ch08_try_catch -->
```cpp
#include <iostream>
#include <stdexcept>

double divide(double a, double b) {
    if (b == 0.0) { throw std::invalid_argument("除数为 0"); }
    return a / b;
}

int main() {
    try {
        std::cout << divide(6, 2) << '\n';
        std::cout << divide(1, 0) << '\n';
        std::cout << "这一行不会执行\n";
    } catch (const std::invalid_argument& e) {
        std::cout << "捕获：" << e.what() << '\n';
    }
    std::cout << "继续执行\n";
}
```

<!-- result:ch08_try_catch -->
```text
3
捕获：除数为 0
继续执行
```

**执行轨迹**（异常的传播过程）：

```text
1. divide(6, 2) → 返回 3            → 打印 3
2. divide(1, 0) → 进入 if 分支
3.   throw std::invalid_argument("除数为 0")
       ├─ 构造一个异常对象（这块对象不放在栈帧里，见 2.5）
       └─ 开始"栈展开"：把 divide 的栈帧拆掉
4.  回到 main 的 try 块里找 catch：
       catch (const std::invalid_argument&) 能匹配 → 进入
       ※ try 块里剩下的语句（"这一行不会执行"）被跳过
5.  执行 catch 体 → 打印"捕获：除数为 0"
6.  catch 体结束，异常对象被销毁
7.  继续执行 try 语句之后的那一行 → 打印"继续执行"
```

**三个关键点**：抛出点不需要知道谁处理；中间的每一层不需要写"转发"代码；
`try` 块中抛出点之后的语句**不会再执行**。

### 2.2 没人接住会怎样

<!-- example:ch08_uncaught -->
```cpp
#include <iostream>
#include <stdexcept>

int main() {
    std::cout << "开始\n";
    throw std::runtime_error("没人接住我");
}
```

**编译成功，警告 0 条**。真实运行结果（本机实测）：

```text
stdout：空
stderr：空
退出码：3221226505（0xC0000409）
```

**注意"开始"这两个字没有出现**。程序确实执行了 `std::cout << "开始\n"`，
但那行字还在**输出缓冲区**里，而异常没人接住时标准要求调用 `std::terminate`，
MSVC 的实现是用 `__fastfail` 直接结束进程——**缓冲区不会被冲洗**。

> ⚠️ **坑（这是本章最实用的一条）**：崩溃时 stdout 里"少了最后几行"，
> 于是你以为程序没执行到那里。**其实它执行了，只是没写出来。**
> **处理**：在关键位置写 `std::cout << ... << std::flush;`，或者改用 `std::cerr`（它默认不缓冲）。
> 第 8 节会给出实测对比。

**另一个实测结论**：MSVC 这里**不打印任何说明**。GCC 通常会往 stderr 打一行
`terminate called after throwing an instance of ...`——**那一条本机未实测**（没有 GCC）。

### 2.3 `catch` 怎么匹配

`catch` 的匹配规则和函数参数类似，但有两条特别重要：

| 规则 | 说明 |
|---|---|
| **按类型匹配，允许派生→基类的转换** | `catch (const std::exception&)` 能接住 `std::out_of_range` |
| **先匹配到的赢** | 同一个 `try` 的多个 `catch` **按书写顺序**尝试，第一条能匹配的就执行 |

第二条会制造一个安静的陷阱：

<!-- example:ch08_catch_order -->
```cpp
#include <iostream>
#include <stdexcept>

int main() {
    try {
        throw std::out_of_range("越界了");
    } catch (const std::exception& e) {
        std::cout << "先被 std::exception 接住: " << e.what() << '\n';
    } catch (const std::out_of_range& e) {
        std::cout << "永远到不了这里: " << e.what() << '\n';
    }
}
```

<!-- result:ch08_catch_order -->
```text
先被 std::exception 接住: 越界了
```

**这次 MSVC 给了警告**（本机实测）：

```text
main.cpp(9): warning C4286: “const std::out_of_range &”: 由基类(“const std::exception &”)在行 7 上捕获
```

> **规律**：**`catch` 必须从"最派生"写到"最基类"。**
> 把 `catch (const std::exception&)` 写在最前面，后面所有更具体的 `catch` 都是死代码。
> 好消息是 MSVC 会用 `C4286` 告诉你；坏消息是**这只是一条警告，程序照样能跑**。

### 2.4 按值捕获会切片

这是异常处理里最经典的一个坑。用自定义的异常层次看最清楚：

<!-- example:ch08_slicing_custom -->
```cpp
#include <iostream>

class Base {
public:
    virtual const char* name() const { return "Base"; }
    virtual ~Base() = default;
};

class Derived : public Base {
public:
    const char* name() const override { return "Derived"; }
};

int main() {
    try {
        throw Derived();
    } catch (Base b) {
        std::cout << "按值: " << b.name() << '\n';
    }

    try {
        throw Derived();
    } catch (const Base& b) {
        std::cout << "按引用: " << b.name() << '\n';
    }
}
```

<!-- result:ch08_slicing_custom -->
```text
按值: Base
按引用: Derived
```

**程序实际怎么解释它**：`catch (Base b)` 的 `b` 是一个**货真价实的 `Base` 对象**
（第 07 章第 9.2 节的"切片"）。异常对象的 `Derived` 部分被切掉了，
虚函数表也是 `Base` 的，所以 `b.name()` 调到 `Base::name`。

**按 `const` 引用捕获（`catch (const Base& b)`）不拷贝，动态类型保留。**

> **规则：`catch` 参数写成 `const T&`，不要写 `T`。**
> 顺便也说清为什么不用 `T&`：异常处理期间你通常不想改它，加 `const` 更贴切。

### 2.5 一个"标准库例外"：MSVC 上 `std::exception` 按值捕获仍然拿得到消息

上面那条规则有一个**看起来像是反例**的现象：

<!-- example:ch08_catch_by_value -->
```cpp
#include <iostream>
#include <stdexcept>

int main() {
    try {
        throw std::runtime_error("这是真正的信息");
    } catch (std::exception e) {
        std::cout << "按值: " << e.what() << '\n';
    }

    try {
        throw std::runtime_error("这是真正的信息");
    } catch (const std::exception& e) {
        std::cout << "按引用: " << e.what() << '\n';
    }
}
```

<!-- result:ch08_catch_by_value -->
```text
按值: 这是真正的信息
按引用: 这是真正的信息
```

**两行一样，按值捕获也拿到了消息。** 这和 2.4 节的结论矛盾吗？

**不矛盾，但要看清楚是为什么**：切片**确实发生了**——`e` 是一个真正的 `std::exception` 对象。
但 MSVC 的 `std::exception` 实现里存了一个**指向消息的指针**，
而它的拷贝构造函数把那个指针一起复制了过去，于是 `what()` 还能取到同一段文本。

**这是实现的细节，不是标准保证的。** 标准的保证只有"`what()` 是虚函数、返回一个可读的字符串"。
一个自定义的异常子类如果**多存了自己的成员**（比如一个错误码），按值捕获时那些成员就真的丢了。

**结论**：**`catch` 一律写 `const T&`。** 上面这个"看起来没事"的例子只是让你不要依赖运气。
（第 12 节「诚实标注」把这一条单独列了出来。）

### 2.6 兜底与重新抛出

| 写法 | 含义 |
|---|---|
| `catch (...)` | 接住**任何**异常。代价是拿不到任何信息（连 `what()` 都没有） |
| `throw;`（不带表达式） | **重新抛出当前正在处理的异常**，继续往外传播 |

<!-- example:ch08_catch_all -->
```cpp
#include <iostream>
#include <stdexcept>

void work() {
    try {
        throw std::runtime_error("底层出错");
    } catch (...) {
        std::cout << "底层记录了一下\n";
        throw;
    }
}

int main() {
    try {
        work();
    } catch (const std::runtime_error& e) {
        std::cout << "上层处理: " << e.what() << '\n';
    }
}
```

<!-- result:ch08_catch_all -->
```text
底层记录了一下
上层处理: 底层出错
```

**`throw;` 和 `throw e;` 完全不同**：

| 写法 | 含义 |
|---|---|
| `throw;` | 重新抛出**原来那个异常对象**（动态类型完整保留） |
| `throw e;` | **拷贝一份 `e`** 再抛——如果 `e` 是 `std::exception&`，就又切片了 |

**这是 `throw;` 存在的唯一理由**，也是它容易写错的地方。

**异常对象什么时候销毁**：它活在"被抛出"到"最后一个 handler 结束"之间。
退出 handler 时销毁。`throw;` 不产生新对象，所以还是原来那个。

## 3. 栈展开：为什么异常路径上资源也安全

**这一节是本章的核心。** 第 07 章第 3 节说"RAII 让异常路径也安全"，
这里要讲清**它是怎么做到的**。

### 3.1 定义

**栈展开（stack unwinding）**：异常从抛出点向外传播时，
**沿途每一个被退出的函数，它的局部对象都会按构造的逆序被析构**。

### 3.2 实测：清理顺序

<!-- example:ch08_stack_unwinding -->
```cpp
#include <iostream>
#include <stdexcept>

class Tracer {
    const char* name_;
public:
    explicit Tracer(const char* n) : name_(n) { std::cout << "构造 " << name_ << '\n'; }
    ~Tracer() { std::cout << "析构 " << name_ << '\n'; }
};

void inner() {
    Tracer b("inner 的局部对象");
    throw std::runtime_error("从 inner 抛出");
}

void outer() {
    Tracer a("outer 的局部对象");
    inner();
    std::cout << "这一行不会执行\n";
}

int main() {
    try {
        outer();
    } catch (const std::exception& e) {
        std::cout << "捕获：" << e.what() << '\n';
    }
    std::cout << "结束\n";
}
```

<!-- result:ch08_stack_unwinding -->
```text
构造 outer 的局部对象
构造 inner 的局部对象
析构 inner 的局部对象
析构 outer 的局部对象
捕获：从 inner 抛出
结束
```

**这就是栈展开的完整过程**：

```text
1. main 调用 outer      → 构造 a
2. outer 调用 inner     → 构造 b
3. inner 里 throw
      ├─ inner 的栈帧被拆：先析构 b          → 打印"析构 inner 的局部对象"
      ├─ "这一行不会执行" 被跳过
      └─ outer 的栈帧被拆：先析构 a          → 打印"析构 outer 的局部对象"
4. 到达 main 的 catch，匹配成功
5. 执行 catch 体                            → 打印"捕获：从 inner 抛出"
6. 继续执行                                  → 打印"结束"
```

**两个对象都是自己析构的，没有一行"清理"代码。**

### 3.3 与 RAII 的关系：一张对照表

| | 普通返回 | 抛出异常 | 手写 `new`/`delete` + 异常 |
|---|---|---|---|
| 局部对象被析构吗 | ✅ | ✅ **栈展开保证** | ❌ 指针变量是局部对象，会被销毁；**它指向的堆对象不会** |
| 需要写释放代码吗 | ❌ | ❌ | ✅ 而且异常一来就漏了 |

**这就是"异常安全"最实在的一层含义**：

> **把资源交给对象持有（RAII），异常路径就自动安全了。**
> **手写的 `new`/`delete` 没有这个保证——异常从中间穿过时，`delete` 那一行根本不会被执行到。**

对比一下（伪代码，两段都不可独立编译）：

```cpp
// ❌ 异常一来就泄漏
void bad() {
    File* f = open_file("a.txt");     // 手写资源
    process(f);                       // ← 如果这里抛异常
    close_file(f);                    //    这一行不会执行
}

// ✅ 交给对象
void good() {
    FileHandle f("a.txt");            // 构造函数里打开
    process(f);                       // ← 这里抛异常也没关系
}                                     //    栈展开会调用 ~FileHandle 关闭文件
```

**C++ 没有 `finally`，也不需要它——析构函数就是 `finally`。**

### 3.4 构造函数抛出：已构造的成员会回滚，本对象不会

一个对象的构造过程如果中途失败，已经构造好的那部分怎么办？

<!-- example:ch08_ctor_throw -->
```cpp
#include <iostream>
#include <stdexcept>

class Part {
    const char* name_;
public:
    explicit Part(const char* n) : name_(n) { std::cout << "构造 " << name_ << '\n'; }
    ~Part() { std::cout << "析构 " << name_ << '\n'; }
};

class Whole {
    Part a_;
    Part b_;
public:
    Whole() : a_("a"), b_("b") {
        std::cout << "Whole 构造体\n";
        throw std::runtime_error("构造失败");
    }
    ~Whole() { std::cout << "~Whole\n"; }
};

int main() {
    try {
        Whole w;
        (void)w;
    } catch (const std::exception& e) {
        std::cout << "捕获: " << e.what() << '\n';
    }
}
```

<!-- result:ch08_ctor_throw -->
```text
构造 a
构造 b
Whole 构造体
析构 b
析构 a
捕获: 构造失败
```

| 发生了什么 | 有没有发生 |
|---|---|
| 成员 `a_`、`b_` 的析构函数 | ✅ **发生了**（逆序：`b_` 先、`a_` 后） |
| `Whole` 自己的析构函数 `~Whole` | ❌ **没有**（这个对象从来没构造完成） |

**规则**：**"构造成功"才算这个对象存在。** 构造没完成的对象，它的析构函数不会被调用——
因为语言认为"那个对象根本不存在"。

> **实践推论**：**如果构造函数里已经获取了资源、然后才抛异常，那份资源就会泄漏。**
> 正确做法是**把每个资源都放进一个成员对象**（成员对象的析构会被回滚调用），
> 或者用"函数 try 块"（入门阶段可以先不用，知道有这个情况即可）。
>
> **这是 RAII 的一个重要边界**：RAII 保证的是"**已经构造完成的对象**会被正确销毁"，
> 它不保证"构造到一半的东西"会被清理。

### 3.5 析构函数抛出：会直接终止程序

<!-- example:ch08_dtor_throw -->
```cpp
#include <iostream>
#include <stdexcept>

class Bad {
public:
    ~Bad() noexcept(false) { throw std::runtime_error("析构里抛出"); }
};

void f() {
    Bad b;
    (void)b;
    throw std::runtime_error("先抛一个");
}

int main() {
    try { f(); }
    catch (const std::exception& e) { std::cout << "捕获 " << e.what() << '\n'; }
}
```

**编译成功，警告 0 条**。真实运行结果：

```text
stdout：空
退出码：3221226505（0xC0000409）
```

**为什么**：`f()` 里已经有一个异常正在传播，此时栈展开要析构 `b`，
而 `~Bad()` **又抛出一个异常**。C++ 规定**同一时刻只能有一个"正在传播的异常"**，
出现第二个就调用 `std::terminate`，**没有商量余地**。

> ⚠️ **坑**：**析构函数里不要抛异常。**
> C++11 起析构函数**默认是 `noexcept` 的**（所以上面那个例子必须显式写 `noexcept(false)` 才能编过），
> 这个默认值就是语言在替你堵这个洞。
>
> **如果析构里确实可能失败（比如关闭文件失败）怎么办**：
> 把失败信息**吞掉并记录**（写日志），或者提供一个**显式的 `close()` 函数**让调用方主动调用。
> **绝不要让异常从析构函数里逃出去。**
>
> **归属**：这是**控制流类**的错误——不是语法错，也不是类型错，而是"异常传播机制被破坏了"。

### 3.6 崩溃时输出会丢：这是排查时最重要的一条

回头看 2.2 节那个例子：`std::cout << "开始\n"` 明明执行了，输出里却没有。
下面这个例子把这件事变成可对比的两行：

<!-- example:ch08_uncaught_flush -->
```cpp
#include <iostream>
#include <stdexcept>

int main() {
    std::cout << "这一行被 flush 了\n" << std::flush;
    std::cout << "这一行还在缓冲区里\n";
    throw std::runtime_error("没人接住我");
}
```

<!-- result:ch08_uncaught_flush -->
```text
这一行被 flush 了
```

（进程以 `0xC0000409` 终止；"这一行还在缓冲区里"**没有出现**。）

| 写法 | 崩溃时还在吗 |
|---|---|
| `std::cout << "..." << std::flush;` | ✅ 已经交给操作系统了 |
| `std::cout << "..."`（默认） | ❌ 留在缓冲区，进程被强杀时不冲洗 |
| `std::cerr << "..."` | ✅ **默认就不缓冲**，适合放诊断信息 |
| `std::endl` | ✅ 它等价于 `'\n'` 加 **flush** |

**为什么 `cout` 要缓冲**：一次一字节地写系统调用太慢，所以标准库先攒着，攒够或遇到 `flush` 才真正写出去。
**平时这是纯收益，崩溃时它变成"线索丢失"。**

> **一条实用习惯**：**在容易崩的临界点后面立刻 `<< std::flush`**，
> 或者把诊断信息全部走 `std::cerr`。这一个习惯能省下大量"我明明打印了怎么没有"的时间。

## 4. 标准异常类体系

### 4.1 层次结构

标准库的异常类都在 `<stdexcept>`（以及 `<new>`、`<typeinfo>` 等）里，
它们构成一棵以 `std::exception` 为根的树：

```text
std::exception                        ← 根，what() 是虚函数
├─ std::logic_error                   ← "程序逻辑写错了"（可以在运行前发现的）
│   ├─ std::invalid_argument          参数不合法
│   ├─ std::domain_error              定义域错误
│   ├─ std::length_error              超出长度上限
│   └─ std::out_of_range              越界（at() / .substr() 等会抛它）
├─ std::runtime_error                 ← "运行期才知道的失败"（外部条件）
│   ├─ std::range_error               结果超出可表示范围
│   ├─ std::overflow_error            上溢
│   └─ std::underflow_error           下溢
├─ std::bad_alloc                     ← new 失败（在 <new> 里）
├─ std::bad_cast                      ← dynamic_cast 失败（在 <typeinfo> 里）
└─ std::bad_typeid
```

**`logic_error` 与 `runtime_error` 的分界**（这条分界现在是"约定"而非"强制"的）：

| 基类 | 含义 | 例子 |
|---|---|---|
| `logic_error` | **理论上可以在运行前发现**的错误，通常是调用方违反了前置条件 | 给 `substr` 传了超长的起始位置 |
| `runtime_error` | **只有运行时才知道**的外部条件导致的失败 | 文件读不出来、网络断开 |

### 4.2 各异常的 `what()` 说什么

<!-- example:ch08_exception_hierarchy -->
```cpp
#include <iostream>
#include <stdexcept>
#include <string>
#include <vector>

int main() {
    try { throw std::runtime_error("runtime_error 的信息"); }
    catch (const std::exception& e) { std::cout << e.what() << '\n'; }

    try { throw std::logic_error("logic_error 的信息"); }
    catch (const std::exception& e) { std::cout << e.what() << '\n'; }

    try { throw std::out_of_range("out_of_range 的信息"); }
    catch (const std::logic_error& e) { std::cout << "被 logic_error 接住: " << e.what() << '\n'; }

    std::vector<int> v{1, 2, 3};
    try { std::cout << v.at(10) << '\n'; }
    catch (const std::out_of_range& e) { std::cout << "at(): " << e.what() << '\n'; }

    try { std::stoi("abc"); }
    catch (const std::invalid_argument& e) { std::cout << "stoi(): " << e.what() << '\n'; }
}
```

<!-- result:ch08_exception_hierarchy -->
```text
runtime_error 的信息
logic_error 的信息
被 logic_error 接住: out_of_range 的信息
at(): invalid vector subscript
stoi(): invalid stoi argument
```

编译时会有**一条警告**（本机实测）：

```text
main.cpp(20): warning C4834: 放弃具有 [[nodiscard]] 属性的函数的返回值
```

**三条值得注意的**：

| 现象 | 说明 |
|---|---|
| 第三行能被 `catch (const std::logic_error&)` 接住 | `out_of_range` **继承自** `logic_error`，所以基类的 handler 能接住派生类异常 |
| 后两行的消息是英文的 | **那是库自己写的消息**（`"invalid vector subscript"`、`"invalid stoi argument"`），不是你传的 |
| `warning C4834` | `std::stoi` 标了 `[[nodiscard]]`，我们故意丢掉了返回值——**真实项目中这条警告通常意味着"忘了用结果"** |

> ⚠️ **坑**：以为 `e.what()` 里的文字是**固定的**、可以拿去解析。
> **它是给人看的**：不同实现、不同版本可能改写它的措辞（上面两行就是 MSVC 的原文）。
> **要判断"是哪种失败"，请用异常的类型或你自己的错误码，不要解析消息文本。**

### 4.3 `at()` 与 `[]`：一个抛异常，一个不检查

| 写法 | 越界时 |
|---|---|
| `v.at(i)` | **抛 `std::out_of_range`** |
| `v[i]` | **不做检查，未定义行为** |

上面第 4 行输出就是 `v.at(10)` 抛出来的。下面是 `operator[]` 的对照组：

<!-- example:ch08_vec_oob -->
```cpp
#include <iostream>
#include <vector>

int main() {
    std::vector<int> v{1, 2, 3};
    std::cout << v.size() << '\n';
    std::cout << v[10] << '\n';
}
```

**编译成功，警告 0 条**。本机一次运行的真实结果：

```text
3
0
```

**`v[10]` 打印了 `0`，程序正常退出**——这不是"越界被处理了"，而是**未定义行为恰好没发作**。
换一次编译、换一个容器内容，它可能打印别的值，也可能直接崩。

| 需求 | 用哪个 |
|---|---|
| 下标来自程序内部、已经保证合法 | `v[i]`（快） |
| 下标来自外部输入 / 不确定 | **`v.at(i)`**，把越界变成可捕获的异常 |

**这一对是"三种出错"分类的完美样本**：`at()` 把越界当**可预期的失败**报出来；
`[]` 把越界当**程序员的责任**，不检查。

### 4.4 自定义异常

标准异常类不够用时，**继承 `std::runtime_error`**（或 `logic_error`）：

```cpp
#include <stdexcept>
#include <string>

class ParseError : public std::runtime_error {
    int line_;
public:
    ParseError(int line, const std::string& msg)
        : std::runtime_error(msg), line_(line) {}
    int line() const { return line_; }
};
```

**为什么要继承标准异常类**（而不是继承 `std::exception`）：

| 做法 | 好处 |
|---|---|
| 继承 `std::runtime_error` | 白拿"存消息 + `what()`"的实现；能自动放进 `catch (const std::exception&)` 的兜底 |
| 继承 `std::exception` | 要自己实现 `what()`，容易写错 |
| **不继承任何标准异常** | ❌ 你的异常会漏掉所有 `catch (const std::exception&)`，整个项目的错误处理出现一个洞 |

> **一条规范**：**自定义异常一定要能从 `std::exception` 接住。**
> 这条约定让"顶层兜底 handler"这个模式成立——不管抛出什么，顶层都能记录并优雅退出。

## 5. `noexcept` 与异常安全保证

### 5.1 `noexcept` 的两种用法

| 用法 | 位置 | 含义 |
|---|---|---|
| **说明符** | `void f() noexcept;` | "这个函数承诺不抛异常" |
| **运算符** | `noexcept(f())` | "算一下 `f()` 这个表达式会不会抛"（**编译期常量**） |

**违反说明符会怎样**：

<!-- example:ch08_noexcept_throws -->
```cpp
#include <cstdlib>
#include <iostream>
#include <stdexcept>

void f() noexcept { throw std::runtime_error("在 noexcept 里抛出"); }

int main() {
    std::cout << "开始\n";
    try { f(); }
    catch (...) { std::cout << "抓不到\n"; }
    std::cout << "结束\n";
}
```

编译时有**一条警告**（本机实测）：

```text
main.cpp(5): warning C4297: “f”: 假定函数不引发异常，但确实发生了
```

真实运行结果：

```text
stdout：空
退出码：3221226505（0xC0000409）
```

**`try { f(); } catch (...) { }` 完全不起作用**——`noexcept` 函数里抛出时，
标准要求立刻调用 `std::terminate`，异常**不会**向外传播。

**那条 `C4297` 警告是唯一的编译期线索**，它说的就是"你这里会有麻烦"。

### 5.2 `noexcept` 最实际的意义：`std::vector` 扩容时用移动还是拷贝

这是本章最值得记住的一段实测。先看**移动构造带 `noexcept`** 的版本：

<!-- example:ch08_noexcept_move -->
```cpp
#include <iostream>
#include <type_traits>
#include <vector>

class Tracer {
    int id_;
public:
    explicit Tracer(int i) : id_(i) {}
    Tracer(const Tracer& o) : id_(o.id_) { std::cout << "拷贝 " << id_ << '\n'; }
    Tracer(Tracer&& o) noexcept : id_(o.id_) { std::cout << "移动 " << id_ << '\n'; }
};

int main() {
    std::cout << std::boolalpha
              << std::is_nothrow_move_constructible<Tracer>::value << '\n';
    std::vector<Tracer> v;
    v.reserve(2);
    v.push_back(Tracer(1));
    v.push_back(Tracer(2));
    std::cout << "--- 扩容 ---\n";
    v.push_back(Tracer(3));
    std::cout << v.size() << '\n';
}
```

<!-- result:ch08_noexcept_move -->
```text
true
移动 1
移动 2
--- 扩容 ---
移动 3
移动 1
移动 2
3
```

现在**只把 `noexcept` 去掉**，其它一个字不改：

<!-- example:ch08_noexcept_move_copy -->
```cpp
#include <iostream>
#include <type_traits>
#include <vector>

class Tracer {
    int id_;
public:
    explicit Tracer(int i) : id_(i) {}
    Tracer(const Tracer& o) : id_(o.id_) { std::cout << "拷贝 " << id_ << '\n'; }
    Tracer(Tracer&& o) : id_(o.id_) { std::cout << "移动 " << id_ << '\n'; }
};

int main() {
    std::cout << std::boolalpha
              << std::is_nothrow_move_constructible<Tracer>::value << '\n';
    std::vector<Tracer> v;
    v.reserve(2);
    v.push_back(Tracer(1));
    v.push_back(Tracer(2));
    std::cout << "--- 扩容 ---\n";
    v.push_back(Tracer(3));
    std::cout << v.size() << '\n';
}
```

<!-- result:ch08_noexcept_move_copy -->
```text
false
移动 1
移动 2
--- 扩容 ---
移动 3
拷贝 1
拷贝 2
3
```

**逐行对比"扩容"之后那两行**：

| 例子 | `is_nothrow_move_constructible` | 扩容时搬走已有元素用的操作 |
|---|---|---|
| 移动构造带 `noexcept` | `true` | **移动 1 / 移动 2** |
| 移动构造**不带** `noexcept` | `false` | **拷贝 1 / 拷贝 2** |

**`std::vector` 为什么要这么做**：扩容时它要把旧元素搬到新存储。
如果移动过程中抛异常，**旧存储里的元素可能已经被改了一半，新的又没建成**——
容器就进入了一个无法恢复的状态。

所以标准库采用一条保守策略（`std::move_if_noexcept` 的思路）：

> **移动构造是 `noexcept` → 用移动（快，且安全）。
> 移动构造可能抛且拷贝可用 → 退回用拷贝；若拷贝不可用，仍可能移动，此时强异常保证有边界（第 12 章第 2.2 节「移动构造/移动赋值的签名」）。**

**这就是 `noexcept` 真正的分量**：它不是一个装饰，
**它是容器决定"走快路还是走慢路"的依据。**

> **实践规则**：**只要你的移动构造函数确实不会抛，就标上 `noexcept`。**
> 漏了它，你的类型在所有标准容器里都会退化成"扩容时拷贝"。
> （移动构造本身是第 12 章的主题；这里先记住这条因果关系。）

### 5.3 异常安全的三级保证

"异常安全"不是一个开关，而是三个等级。写库代码时**必须说明自己提供哪一级**：

| 级别 | 承诺 | 出异常后对象处于 | 代价 |
|---|---|---|---|
| **不抛保证**（nothrow） | 这个操作**绝不抛异常** | 操作成功完成 | 要用不分配、不调用户代码的实现方式 |
| **强保证**（strong） | **要么成功，要么完全回到操作前的状态**（"事务性"） | 原样不变 | 常常要"先做副本，成功后再交换" |
| **基本保证**（basic） | 不泄漏、不破坏不变量，但对象可以处于任何**合法**状态 | 合法但内容未指定 | 最低要求，几乎所有代码都该做到 |
| （无保证） | 什么都没承诺 | 可能泄漏、可能不变量被破坏 | ❌ 不可接受 |

**强保证的一个实测**：

<!-- example:ch08_strong_guarantee -->
```cpp
#include <iostream>
#include <stdexcept>
#include <vector>

class Item {
    int id_;
public:
    explicit Item(int id) : id_(id) {
        if (id == 3) { throw std::runtime_error("构造失败"); }
        std::cout << "构造 " << id_ << '\n';
    }
};

int main() {
    std::vector<Item> v;
    v.emplace_back(1);
    v.emplace_back(2);
    std::cout << "size=" << v.size() << " capacity=" << v.capacity() << '\n';
    try {
        v.emplace_back(3);
    } catch (const std::exception& e) {
        std::cout << "捕获: " << e.what() << '\n';
    }
    std::cout << "size=" << v.size() << " capacity=" << v.capacity() << '\n';
}
```

<!-- result:ch08_strong_guarantee -->
```text
构造 1
构造 2
size=2 capacity=2
捕获: 构造失败
size=2 capacity=2
```

**第三行和第五行完全一样**：`emplace_back` 抛异常之后，容器的 `size` 和 `capacity` **都没变**。
标准要求 `vector::emplace_back` / `push_back` 提供**强保证**——它确实做到了。

**怎么自己判断一段代码提供哪一级**：

```text
1. 它会不会分配内存 / 调用用户提供的代码（拷贝构造、比较、析构……）？
     不会 → 它可能提供"不抛保证"
2. 出异常时，它有没有可能已经改了 this 的一部分成员？
     会   → 只有"基本保证"（要升到强保证就得改成"先副本再交换"）
     不会 → 强保证
```

## 6. 不抛异常的错误报告：错误码 / `std::optional` / `std::expected`

异常不是唯一的路。这一节把三种"不走异常"的方式摆在一起看。

### 6.1 错误码：把失败当成返回值传出去

<!-- example:ch08_error_code -->
```cpp
#include <iostream>

enum class Err { ok, not_found, bad_input };

const char* name_of(Err e) {
    switch (e) {
        case Err::ok:        return "ok";
        case Err::not_found: return "not_found";
        case Err::bad_input: return "bad_input";
    }
    return "?";
}

Err find(int key, int& out) {
    if (key < 0) { return Err::bad_input; }
    if (key != 7) { return Err::not_found; }
    out = 700;
    return Err::ok;
}

int main() {
    int value = 0;
    Err e = find(7, value);
    std::cout << name_of(e) << ' ' << value << '\n';
    e = find(1, value);
    std::cout << name_of(e) << ' ' << value << '\n';
}
```

<!-- result:ch08_error_code -->
```text
ok 700
not_found 700
```

**执行轨迹**：

```text
find(7, value)：
  1. key >= 0，不返回
  2. key == 7，于是 out = 700
  3. 返回 Err::ok                          → 调用方必须自己检查
find(1, value)：
  1. key >= 0
  2. key != 7 → 直接返回 Err::not_found     ← value 没有被写
  3. 调用方看到 not_found，但仍要自己判断"value 能不能用"
```

**错误码的两个固有问题**（看第二行输出就明白了）：

| 问题 | 说明 |
|---|---|
| **调用方可以无视返回值** | `find(1, value);` 这样写也编得过，`value` 就是上次的旧值 |
| **失败时的"输出"是什么状态没保证** | 上面 `value` 保留了 `700`（上一次的值）——这是隐患 |

**第二个问题在现代写法里用 `std::optional` 解决**：让"没有值"这件事**在类型里表达出来**。

### 6.2 `std::optional`：可能没有值（C++17）

<!-- example:ch08_optional -->
```cpp
#include <iostream>
#include <optional>
#include <string>

std::optional<int> parse_positive(const std::string& s) {
    try {
        int v = std::stoi(s);
        if (v > 0) { return v; }
    } catch (...) {
    }
    return std::nullopt;
}

int main() {
    std::cout << std::boolalpha;
    auto a = parse_positive("42");
    std::cout << a.has_value() << ' ' << a.value_or(-1) << '\n';
    auto b = parse_positive("-1");
    std::cout << b.has_value() << ' ' << b.value_or(-1) << '\n';
}
```

<!-- result:ch08_optional -->
```text
true 42
false -1
```

| 用法 | 含义 |
|---|---|
| `std::optional<T>` | "要么有一个 `T`，要么什么都没有" |
| `return v;` | 有值 |
| `return std::nullopt;` | 没有值 |
| `.has_value()` / `if (opt)` | 有没有值 |
| `.value()` | 取出来；**没有值时抛 `std::bad_optional_access`** |
| `.value_or(d)` | 取出来，没有值就用默认值 `d`（**最常用**） |
| `*opt` | 取出来，**不检查**（没有值是未定义行为） |

**`optional` 表达不了"为什么失败"**：它只有"有/没有"两种状态。
需要携带原因时，就看下一个。

### 6.3 `std::expected`：要么是值，要么是错误原因（C++23）

`std::expected<T, E>` 同时装"值"和"错误原因"，是很多人等了很久的东西。**但它是 C++23 的。**

<!-- example:ch08_expected_cxx17_FAIL -->
```cpp compile-fail
#include <expected>

int main() {
    std::expected<int, int> e{42};
    (void)e;
}
```
```text
main.cpp(4): error C2039: "expected": 不是 "std" 的成员
main.cpp(4): error C2065: “expected”: 未声明的标识符
main.cpp(4): error C2062: 意外的类型“int”
main.cpp(4): error C2143: 语法错误: 缺少“;”(在“{”的前面)
main.cpp(4): error C2143: 语法错误: 缺少“}”的前面
main.cpp(5): error C2065: “e”: 未声明的标识符
```

**这份诊断本身就是一个知识点**：`std::expected` 在当前基线（`/std:c++17`）里**不存在**。
第一条 `error C2039: "expected": 不是 "std" 的成员` 是真正的原因；
后面五条全是它引起的连锁错误（名字不存在 → 后面的语法都解析不了）。

> **读多错误诊断的方法**：**只看前两条，尤其是第一条。**
> 后面的错误往往是"因为前面那个名字不存在"衍生出来的，修好第一个，它们会一起消失。

**本章基线是 C++17，所以：`std::expected` 标注为「C++23 起」，不进正文主干。**
它在 C++17 下的替代方案就是 6.1 的错误码加一个输出参数，或者 6.2 的 `optional`
（如果不需要携带原因）。**本机是否在 `/std:c++latest` 下支持 `std::expected`，本轮未实测。**

### 6.4 三条路怎么选

| | 异常 | 错误码 | `optional` | `expected`（C++23） |
|---|---|---|---|---|
| 传播方式 | 自动沿调用栈向上 | 调用方**手动**检查并传递 | 手动检查 | 手动检查 |
| 调用方忽略会怎样 | 不会——不接住就终止程序 | **静默继续跑**（最危险） | 编译上能忽略 | 编译上能忽略 |
| 能不能带原因 | ✅ 类型 + 消息 | ✅ 码 | ❌ | ✅ |
| 性能 | 成功路径**零开销**（现代实现） | 零开销 | 零开销 | 零开销 |
| 能不能用在 | 有异常机制的地方 | **任何地方**（含 `noexcept` 函数、嵌入式、C 接口） | 同左 | 同左 |
| 复杂度 | 展开栈；要写 `try` | 每个调用点都要写检查 | 要写检查 | 要写检查 |

**实用的判断顺序**：

```text
1. 这个失败是"可预期的、调用方要处理的"吗？
     不是 → 是 bug → 用 assert（第 7 节）
     是   → 继续
2. 这个函数能抛异常吗？（跨 C 接口 / 标了 noexcept / 嵌入式无异常）
     不能 → 错误码 或 optional
     能   → 继续
3. 需要携带失败原因吗？
     不需要 → std::optional
     需要   → 异常（C++17 基线下的默认选择）
```

**C++ 社区的默认倾向**：**异常用于"真正异常的情况"，而不是控制流。**
用一个异常表示"遍历到了末尾"是滥用；用一个异常表示"文件打不开"是合适的。

## 7. 断言：`assert` 与 `static_assert`

### 7.1 `assert`：运行期检查，release 下会被去掉

```cpp
#include <cassert>
assert(n > 0);
```

<!-- example:ch08_assert -->
```cpp
#include <cassert>
#include <iostream>

int main() {
    int n = 5;
    assert(n > 0);
    std::cout << "断言通过\n";
    assert(n > 10);
    std::cout << "不会到这里\n";
}
```

**编译成功，警告 0 条**。真实运行结果（本机实测）：

```text
stdout：空
stderr：Assertion failed: n > 10, file main.cpp, line 8
退出码：3221226505（0xC0000409）
```

**三件事同时发生了**：

1. 第一个断言通过（所以"断言通过"这一行**本该**打印——但它也丢了，因为 stdout 没 flush，见 3.6 节）
2. 第二个断言失败，**诊断信息去了 `stderr`**（所以它留下来了），格式是
   `Assertion failed: <表达式原文>, file <文件名>, line <行号>`
3. 进程被终止，退出码 `0xC0000409`

**`stderr` 上的这行文本是本机最好用的崩溃线索**——它有**表达式、文件、行号**三样信息，
比任何 `printf` 调试都准。**可惜它只在断言上，不在段错误上。**

### 7.2 `NDEBUG`：定义它，断言就整段消失

**这是 `assert` 最重要也最危险的性质。** 定义宏 `NDEBUG`（通常在 release 构建里）后，
`assert(...)` 变成**什么也不做**——连里面的表达式都不会求值。

同一段代码，加 `/DNDEBUG` 编译后：

```cpp
#include <cassert>
#include <iostream>

int main() {
    int n = 5;
    assert(n > 10);
    std::cout << "断言被去掉了，程序继续跑\n";
}
```

真实输出（本机实测，`/DNDEBUG`）：

```text
断言被去掉了，程序继续跑
```

同时有一条警告：

```text
main.cpp(5): warning C4189: “n”: 局部变量已初始化但不引用
```

**这条 `C4189` 是"断言被去掉"的直接证据**：`n` 只在 `assert` 里被用到，
断言没了之后它就变成了一个没用的变量。

> ⚠️ **坑（这条会造成真实事故）**：**把有副作用的表达式放进 `assert`。**
>
> ```cpp
> assert(open_file("a.txt") == 0);     // ❌ release 下这行整个消失，文件根本不会打开
> ```
>
> **为什么危险**：debug 构建一切正常，release 构建行为完全不同，
> 而且**没有任何编译警告**（如果那个返回值被别处用到，连 `C4189` 都不会有）。
>
> **规则**：`assert` 里的表达式**只能读取状态，不能改变状态**。

### 7.3 `assert` 的正确用途

| 该用 `assert` | 不该用 `assert` |
|---|---|
| 检查"程序自己保证的不变量" | **校验用户输入 / 文件内容 / 网络数据** |
| 检查函数入口的前置条件（调用方应当保证） | 检查**可预期的失败**（用异常或错误码） |
| 检查某段逻辑"不可能走到这里" | 做**有副作用**的操作 |
| 在开发期尽早暴露 bug | 作为**唯一**的输入校验手段 |

**判据还是第 1 节那句话**：**"出错了调用方还能做什么？"**
调用方什么也做不了，说明这是程序内部的 bug——**那就该用断言，而且该让它崩得越早越好。**

### 7.4 `static_assert`：编译期检查

`static_assert` 的条件必须是**编译期常量**，检查发生在**编译期**：

<!-- example:ch08_static_assert -->
```cpp
#include <iostream>
#include <type_traits>

static_assert(sizeof(int) == 4, "本机 int 不是 4 字节");
static_assert(std::is_integral<int>::value, "int 必须是整型");

int main() {
    std::cout << "两个静态断言都通过\n";
}
```

<!-- result:ch08_static_assert -->
```text
两个静态断言都通过
```

失败时是**编译错误**，而且消息是你自己写的那句话：

<!-- example:ch08_static_assert_FAIL -->
```cpp compile-fail
static_assert(sizeof(int) == 8, "本机 int 不是 8 字节");

int main() {}
```
```text
main.cpp(1): error C2338: static assertion failed: '本机 int 不是 8 字节'
```

### 7.5 两者对比

| | `assert` | `static_assert` |
|---|---|---|
| 检查时机 | **运行期** | **编译期** |
| 条件要求 | 任意表达式 | **必须是编译期常量** |
| 失败后果 | 打印诊断 + 终止进程 | **编译失败** |
| release 下 | **被去掉**（定义 `NDEBUG` 时） | **永远生效** |
| 能不能带消息 | ❌ 只打印表达式原文 | ✅ 第二参数就是消息（C++17 起可省略） |
| 典型用途 | 运行期不变量、前置条件 | 类型假设、平台假设、模板约束 |

**一句话**：**能在编译期检查的，一律用 `static_assert`。**
编译期发现的错误，代价是"改一行"；运行期发现的错误，代价是"发一次版"。

> `static_assert` 在模板里的用法（检查类型参数是否符合要求）是第 11 章
> 「模板与泛型」的内容——那里它才真正发挥威力。

### 8.1 先说清楚这台机器上有什么、没有什么

**本机实测（本轮）**：


按本讲义的规矩不能写进正文。下面给的是**在本机真的能用的办法**。

**另外一条必须说清的**：Windows 上还可以装 WinDbg / Visual Studio 的图形调试器来解决这个问题，
**但那是"安装"而不是"写代码"，本轮没有做，也没有验证，所以不展开。**

### 8.2 手段一：看退出码

进程怎么结束的，退出码会告诉你。**这是没有调试器时最可靠的第一手线索。**

**本机实测的退出码对照表**（全部来自本轮探针的真实运行）：

| 程序怎么结束的 | 退出码（十进制） | 退出码（十六进制） | 本机出处 |
|---|---|---|---|
| 正常返回 | `0` | `0x0` | 大多数示例 |
| 未捕获的异常 | `3221226505` | `0xC0000409` | `ch08_uncaught` |
| `assert` 失败 | `3221226505` | `0xC0000409` | `ch08_assert` |
| `noexcept` 函数里抛出 | `3221226505` | `0xC0000409` | `ch08_noexcept_throws` |
| 栈展开中析构函数又抛出 | `3221226505` | `0xC0000409` | `ch08_dtor_throw` |
| 自定义 `terminate` 处理器 + `abort` | `3221226505` | `0xC0000409` | `ch08_terminate_cerr` |
| **空指针解引用** | `3221225477` | **`0xC0000005`** | 第 06 章 `ch06_null_deref` |
| **重复释放** | `3221226356` | **`0xC0000374`** | 第 06 章 `ch06_double_delete` |
| 栈溢出 | ⚠️ **本轮未实测** | （Windows 常见值是 `0xC00000FD`，**未验证**） | — |

**读这张表的方法**：

- `0xC0000409`：**"程序主动自杀"**。未捕获异常、断言失败、`terminate` 都会走这条路。
  MSVC 用的是 `__fastfail`，所以它**不会冲洗缓冲区，也不会打印消息**（见 3.6 节）。
- `0xC0000005`：**访问违规**。通常是空指针解引用或野指针。
- `0xC0000374`：**堆结构被破坏**。通常是重复释放或越界写堆。

**怎么在命令行看到退出码**：

```bat
main.exe
echo %ERRORLEVEL%
```

**注意**：`%ERRORLEVEL%` 必须**紧接着**那条命令读，中间插了别的命令就被覆盖了。

### 8.3 手段二：把诊断信息送去 `stderr`，并 `flush`

由 3.6 节的实测可知：**崩溃时 stdout 里没 flush 的内容会丢，`stderr` 的内容会留**。
所以排查期的第一件事是**把线索挪到安全的地方**。

| 做法 | 崩溃时还能看到吗 |
|---|---|
| `std::cout << "..."` | ❌ 可能丢 |
| `std::cout << "..." << std::flush;` | ✅ |
| `std::cerr << "..."` | ✅（默认不缓冲） |
| `assert` 的输出 | ✅（走 `stderr`） |

### 8.4 手段三：换掉 `terminate` 处理器，让"自杀"留下遗言

`std::terminate` 默认什么都不打印。**可以换掉它**：

<!-- example:ch08_terminate_cerr -->
```cpp
#include <cstdlib>
#include <exception>
#include <iostream>
#include <stdexcept>

void my_terminate() {
    std::cerr << "terminate 被调用：异常没人接住\n";
    std::abort();
}

int main() {
    std::set_terminate(my_terminate);
    std::cerr << "开始\n";
    throw std::runtime_error("没人接");
}
```

**真实运行结果**（本机实测）：

```text
stdout：空
stderr：开始
        terminate 被调用：异常没人接住
退出码：3221226505（0xC0000409）
```

**按 `std::cout` 写会怎样**？本机也测了——**同一段代码，只把那两条 `std::cerr` 换成 `std::cout`**：

```text
stdout：空
stderr：空
退出码：3221226505（0xC0000409）
```

**一个字都看不到。** 两个例子代码只差 `cout`/`cerr`，可观测性差了一个数量级。

> **`set_terminate` 是"没有调试器时的断点"**：在处理器里打印、
> 记录最后处理的请求、把状态写进日志文件，然后再 `abort()`。
> **注意**：处理器里不能抛异常（它就是来处理异常的），也不要指望它能正常返回。

### 8.5 手段四：二分法定位

如果异常来自你自己的 `throw`，最直接的办法是**缩小范围**：

```text
1. 在 main 最外层套一个 try { ... } catch (const std::exception& e) { std::cerr << e.what(); }
   ——先确认"它确实是个 C++ 异常"，而不是 0xC0000005 那种硬崩溃
2. 在可疑函数的入口/出口各打一条 cerr
   ——确定是"哪个函数里抛的"
3. 在那个函数里继续对半切
```

**为什么用 `cerr` 而不是 `cout`**：见 8.3 节。

### 8.6 手段五：打开全部警告

```powershell
$vcvars = "C:\Program Files (x86)\Microsoft Visual Studio\18\BuildTools\VC\Auxiliary\Build\vcvars64.bat"
cmd /c "`"$vcvars`" >nul 2>&1 && cl /nologo /std:c++17 /EHsc /W4 /utf-8 main.cpp /Fe:main.exe"
```

**本章实测到的那几条警告，每一条都直接指向一个真实缺陷**：

| 警告 | 说的什么 | 出现在 |
|---|---|---|
| `C4286` | 基类先于派生类被 `catch`，后面的 handler 是死代码 | 2.3 节 |
| `C4834` | 丢掉了 `[[nodiscard]]` 函数的返回值 | 4.2 节 |
| `C4297` | `noexcept` 函数里确实抛了 | 5.1 节 |
| `C4189` | 变量已初始化但没被引用（断言被去掉的痕迹） | 7.2 节 |

**"能编过"和"写对了"是两件事，`/W4` 是中间那条缝里唯一的提示。**

### 8.7 手段六：调试堆查内存问题

第 06 章第 9.3 节给了本机实测的做法（`/MDd` + `_CrtSetReportMode` + `_CrtDumpMemoryLeaks`）。
对本章的意义是：**如果崩溃是堆引起的（`0xC0000374`），那是查它的唯一本机可用手段。**

### 8.8 一份排查流程

```text
程序异常结束
├─ 1. 记下退出码
│     0xC0000409 → 程序"自杀"：未捕获异常 / assert / terminate → 走第 2 步
│     0xC0000005 → 访问违规：查空指针、野指针（第 06 章第 10 节）
│     0xC0000374 → 堆被破坏：查重复释放、越界写堆
├─ 2. 看 stderr
│     assert 的 "Assertion failed: ... line N" 直接给出行号
│     没有 stderr 信息 → 说明是未捕获异常且没装 terminate 处理器 → 去第 3 步
├─ 3. 装一个 terminate 处理器（写 cerr），重跑
├─ 4. 还是定位不到 → 用 cerr 打点做二分
├─ 5. 怀疑内存 → 用 /MDd 的调试堆
└─ 6. 全程开着 /W4 看警告
```

> **最重要的一条经验**：**崩溃点往往不是出错点。**
> 尤其是 `0xC0000374`（堆被破坏）——破坏发生在很久之前，
> 分配器只是**在下次分配或释放时才发现**，于是报错位置和真正的错误位置隔了很远。
> 这与第 06 章第 10.5 节讲的越界是同一个道理。

## 9. 知识结构回收

**它从哪里来**

- 第 07 章第 3 节建立了 RAII，并留下一个问题："为什么异常路径也安全？"
  **本章第 3 节回答：栈展开。**
- 第 06 章第 8 节的"离开作用域就析构"，在本章第 3 节变成了"异常穿过函数时也析构"。
- 第 07 章第 8 节的继承，在本章第 4 节变成了异常类型体系（`catch` 靠继承匹配）。

**它和什么并列**

- **异常 / 错误码 / `optional` / `expected`** 是"一次失败怎么传出去"的四种做法（6.4 节给了选择顺序）。
- **`assert` / `static_assert` / 异常** 是"什么时候检查"的三种答案：运行期 bug / 编译期假设 / 运行期可预期失败。
- **基本保证 / 强保证 / 不抛保证** 是"出异常后对象处于什么状态"的三个等级。
- **`noexcept` 说明符**与**栈展开**是互相挤压的：标了 `noexcept` 就不允许展开出去。

**它通向哪里**

| 后面的章节 | 用到了本章的什么 |
|---|---|
| 第 09 章「字符串与 IO」 | `fstream` 的失败处理；`std::stoi` 的异常（本章 4.2 节实测过） |
| 第 10 章「容器与算法」 | `at()` vs `[]`；容器的强保证；扩容时 `noexcept` 决定移动还是拷贝（本章 5.2 节） |
| 第 12 章「移动语义与资源管理」 | 移动构造为什么要标 `noexcept`（本章 5.2 节留下的问题） |
| 第 13 章「进阶主题」 | UB 清单；并发下异常不能跨线程传播 |

## 10. 本章自测

**1.** 下面这段代码，`delete p;` 会不会执行？为什么？

```cpp
void f() {
    int* p = new int(5);
    might_throw();          // 假设这个函数可能抛异常
    std::cout << *p << '\n';
    delete p;
}
```

<details><summary>答案</summary>

**不会执行**（`might_throw()` 抛出时）。

**为什么**：异常从 `might_throw()` 抛出后开始栈展开。栈展开会销毁 `f` 的**局部对象**——
`p` 这个指针变量**确实**被销毁了。但 `p` 指向的那块**堆内存不是局部对象**，
没有任何机制会去 `delete` 它。于是它是**泄漏**。

**修法**：把资源交给一个对象持有。

```cpp
void f() {
    auto p = std::make_unique<int>(5);   // 第 12 章
    might_throw();
    std::cout << *p << '\n';
}                                        // 栈展开会调用 unique_ptr 的析构函数
```

**这一题就是"RAII 为什么是 C++ 最核心的设计"的最短证明**：
`delete p;` 这一行代码本身没错，错在它**必须被执行到**，而异常让它执行不到。

</details>

**2.** 下面这段代码会输出几行？顺序是什么？

```cpp
void inner() { Tracer b("b"); throw std::runtime_error("x"); }
void outer() { Tracer a("a"); inner(); }
int main() {
    try { outer(); } catch (const std::exception& e) { std::cout << "caught\n"; }
}
```

<details><summary>答案</summary>

（每个 `Tracer` 构造和析构各打印一行）共 **5 行**：

```text
构造 a
构造 b
析构 b
析构 a
caught
```

**顺序就是栈展开的顺序**：抛出后先拆 `inner` 的栈帧（析构 `b`），
再拆 `outer` 的栈帧（析构 `a`），**逆序**，然后才进入 `main` 的 `catch`。

**本机实测版本见 `ch08_stack_unwinding`**（那个例子多了两条打印，但顺序规律一样）。

</details>

**3.** 下面两次捕获的结果一样吗？为什么？

```cpp
try { throw std::out_of_range("越界"); }
catch (const std::exception& e) { /* A */ }
catch (const std::out_of_range& e) { /* B */ }
```

<details><summary>答案</summary>

**会走 A，B 永远不会执行。**

因为 `catch` **按书写顺序**尝试匹配，而 `std::out_of_range` **继承自** `std::exception`，
所以 A 能匹配上，后面的 B 成了死代码。

**本机实测会给出警告**：

```text
main.cpp(9): warning C4286: “const std::out_of_range &”: 由基类(“const std::exception &”)在行 7 上捕获
```

**规则**：**`catch` 必须从最派生写到最基类。**

</details>

**4.** 下面两段代码非常像。第二段为什么必须写 `noexcept(false)`？第一段的问题是什么？

```cpp
class Bad { public: ~Bad() { throw std::runtime_error("x"); } };              // 第一段
class Bad2 { public: ~Bad2() noexcept(false) { throw std::runtime_error("x"); } }; // 第二段
```

<details><summary>答案</summary>

**第二段必须写 `noexcept(false)`**，因为 **C++11 起析构函数默认是 `noexcept` 的**——
不写这个，里面的 `throw` 会让编译器报错（或者直接导致 `terminate`）。

**第一段的问题不是"能不能编过"，而是"析构函数抛异常本身就是错的"**：

- 如果这个析构是在**栈展开过程中**被调用的（已经有一个异常在传播），
  再抛一个就会**立刻 `std::terminate`**。
- 本机实测（`ch08_dtor_throw`）：进程以 `0xC0000409` 终止，**stdout 一个字都没有**。

**规则：析构函数里不要抛异常。** 确实可能失败的操作（关文件、提交事务）
应该提供**显式的 `close()` / `commit()`** 让调用方主动调用并处理失败。

</details>

**5.** 本机实测：移动构造函数加 `noexcept` 时，`std::vector` 扩容打印"移动 1 / 移动 2"；
去掉 `noexcept` 后，同一个位置打印"拷贝 1 / 拷贝 2"。为什么 `vector` 要这么做？

<details><summary>答案</summary>

**因为扩容时要先把旧元素搬到新存储，而搬运可能会失败。**

如果用的是移动：第 1 个元素已经搬走（源对象被改），第 2 个元素的移动**抛了异常**——
此时旧存储里是"一半被改过、一半没动"的状态，新存储里也没建成。
**容器无法回退到扩容前的状态**，强保证就破坏了。

如果用的是拷贝：拷贝过程中抛异常，**旧存储里的元素全都还在**，新存储丢掉即可，
容器状态完全没变——**强保证成立**。

所以标准库用 `std::move_if_noexcept` 的思路做取舍：

> **移动构造是 `noexcept` → 用移动（快且安全）；可能抛且拷贝可用 → 可退回拷贝；拷贝不可用时仍可能移动，异常保证需另查。**

**实践规则**：**移动构造函数只要确实不抛，就标 `noexcept`。**
漏了它，你的类型在所有标准容器里扩容都会退化成拷贝。

**本机实测输出**（`ch08_noexcept_move`）：`is_nothrow_move_constructible` 为 `true`，
扩容时是"移动"；去掉 `noexcept` 后（`ch08_noexcept_move_copy`）变成 `false`，扩容时是"拷贝"。

</details>

**6.** `assert(x > 0);` 和 `static_assert(x > 0, "msg");` 有什么本质区别？什么时候该用哪个？

<details><summary>答案</summary>

| | `assert` | `static_assert` |
|---|---|---|
| 检查时机 | **运行期** | **编译期** |
| 条件要求 | 任意表达式 | **必须是编译期常量** |
| 失败后果 | 打印 `Assertion failed: ... file ... line ...`（**走 stderr**）+ 终止进程 | **编译失败**（`error C2338`） |
| release（定义 `NDEBUG`） | **整段被去掉**，连表达式都不求值 | **永远生效** |

**选择**：**能在编译期检查的一律用 `static_assert`**（代价从"发版"降到"改一行"）。

**两个必须记住的坑**：

1. **绝不能把有副作用的表达式放进 `assert`**——release 下它整个消失。
   `assert(open_file(...) == 0);` 在 release 里文件根本不会打开，而且**没有任何警告**。
2. **`assert` 不能用来校验用户输入**。用户输入是"可预期的失败"，
   而 `assert` 在 release 下会被去掉——校验随之消失。

**本机实测**：断言失败时 `stderr` 上是
`Assertion failed: n > 10, file main.cpp, line 8`，退出码 `0xC0000409`。

</details>

**7.** 本机实测：`ch08_uncaught` 里 `std::cout << "开始\n"` 执行了，但输出里一个字都没有。为什么？怎么避免？

<details><summary>答案</summary>

**因为 `std::cout` 是带缓冲的，而未捕获异常会调用 `std::terminate` → `__fastfail` 直接结束进程，
缓冲区不会被冲洗。**

MSVC 在未捕获异常时**不打印任何消息**（本机实测 stderr 也是空的），所以看起来"程序什么都没做"。

**避免办法**（按推荐程度）：

| 做法 | 效果 |
|---|---|
| 诊断信息走 `std::cerr` | ✅ `cerr` 默认不缓冲 |
| `std::cout << ... << std::flush;` | ✅ 主动冲洗 |
| `std::cout << ... << std::endl;` | ✅ `endl` = `'\n'` + flush |
| 什么都不做 | ❌ 崩溃时丢线索 |

**本机实测对比**（`ch08_uncaught_flush`）：加了 `std::flush` 的那一行留下了，
没加的"这一行还在缓冲区里"没了。

**这一条的实际价值**：它能解释"我明明打印了，怎么会没输出"这个最常见的困惑。

</details>

**8.** 本机 `cdb` / `gdb` / `lldb` / `windbg` **都不存在**。给你一个刚崩掉的 `main.exe`，你怎么定位？

<details><summary>答案</summary>

按第 8.8 节的流程，**先用不需要调试器的手段缩小范围**：

1. **读退出码**（`main.exe` 后立刻 `echo %ERRORLEVEL%`）：
   - `0xC0000409`（3221226505）→ 程序"自杀"：未捕获异常 / `assert` / `terminate`
   - `0xC0000005`（3221225477）→ 访问违规：空指针、野指针
   - `0xC0000374`（3221226356）→ 堆被破坏：重复释放、越界写堆
2. **看 `stderr`**：`assert` 会给出表达式、文件名、行号。
3. **装 `std::set_terminate` 处理器**，在里面用 `std::cerr` 打印线索再 `abort()`。
   本机实测：用 `cout` 写处理器**一个字都看不到**，用 `cerr` 就能看到。
4. **用 `std::cerr` 打点做二分**定位抛出点。
5. **全程开 `/W4`**：本章实测的 `C4286` / `C4834` / `C4297` / `C4189` 每一条都指向真实缺陷。

**重要提醒**：**崩溃点往往不是出错点**，尤其是 `0xC0000374`——
堆被破坏发生在很久之前，分配器只是**下次分配/释放时才发现**。

**也顺便说清边界**：本机也可以装 WinDbg 或 Visual Studio 图形调试器来解决，
**但本轮没有安装、也没有验证**，所以本节不写那些操作步骤。

</details>

**9.** `std::optional<int>` 和抛 `std::invalid_argument` 都能表达"解析失败"，什么时候用哪个？

<details><summary>答案</summary>

**核心差别是"要不要说明为什么失败"和"调用方忽略的代价"。**

| | `std::optional<int>` | 抛异常 |
|---|---|---|
| 携带失败原因 | ❌ 只有"有/没有" | ✅ 类型 + 消息 |
| 调用方忽略会怎样 | 拿到 `nullopt` 后在某个地方出错，或者用 `value_or` 静默取默认值 | **不会静默**：不接住就终止进程 |
| 适合 | **"没有值"是这个函数的正常结果之一**（查不到、可选字段缺失） | **"不该发生但发生了"**，且调用方必须处理 |

**判断顺序**（6.4 节的流程）：

```text
1. 是不是 bug？        → 是 bug 用 assert
2. 这个函数能抛异常吗？  → 不能（跨 C 接口 / noexcept / 无异常环境）用 optional 或错误码
3. 需要携带原因吗？     → 不需要 → optional；需要 → 异常
```

**一个具体建议**：`std::optional` 最适合"**查找**"这类语义——
`find` 没找到是**正常结果**，不是异常情况。
而"配置文件格式错误"通常**需要说明哪里错了**，异常更合适。

**另**：`std::expected<T, E>`（C++23）能同时带值和原因，
**但它不在 C++17 基线里**（本机 `/std:c++17` 实测报 `error C2039: "expected": 不是 "std" 的成员`）。

</details>

**10.** 本机实测的四条警告里，挑一条说明"如果忽略它会发生什么"。

<details><summary>答案</summary>

以 **`C4286`** 为例（2.3 节，本机实测原文）：

```text
main.cpp(9): warning C4286: “const std::out_of_range &”: 由基类(“const std::exception &”)在行 7 上捕获
```

**忽略它的后果**：程序能编过、能跑、看起来"错误被捕获了"——但**那个更具体的 handler 从来没执行过**。
如果 `catch (const std::out_of_range&)` 里写的是"越界了，用默认值继续"，
而实际执行的是 `catch (const std::exception&)` 里的"记录并退出"，
**程序的错误处理行为和你写的完全不一样**，而且没有任何运行期提示。

**其它三条同样的性质**：

| 警告 | 忽略的后果 |
|---|---|
| `C4834`（丢掉 `[[nodiscard]]` 返回值） | 结果没被使用——很可能是"忘了用"，逻辑静默走错 |
| `C4297`（`noexcept` 里确实抛了） | 抛出时直接 `terminate`，**`try`/`catch` 拦不住**（本机实测 `0xC0000409`） |
| `C4189`（变量初始化后未引用） | 说明那段代码（通常是断言）被整段去掉了，校验消失了 |

**共同点**：**这四条都不会让编译失败，都只在"能编过但行为和你以为的不一样"这一层报警。**
这就是 `/W4` 存在的理由。

</details>

**三条必须单独点名的**：

1. **`ch08_catch_by_value` 是一个"看起来违反了规则"的实测结果**：
   MSVC 上按值捕获 `std::exception` 仍然拿得到 `what()` 的消息，
   因为它的实现把消息指针一起拷贝了。**这是实现细节，不是标准保证**——
   凡是"按值捕获会切片"的结论，请以自定义异常那个例子（`ch08_slicing_custom`）为准。
2. **`ch08_vec_oob` 那次越界读打印了 `0` 并且正常退出**。这是**未定义行为恰好没发作**，
   不是"越界被处理了"。这个值不保证重现。
3. **`0xC0000409` 这个退出码覆盖了本章多种"主动终止"的情形**
   （未捕获异常、`assert` 失败、`noexcept` 里抛出、析构抛出）。
   它是 MSVC 用 `__fastfail` 的结果，**别把它当成"未捕获异常"的唯一标志**——
   判定要结合 `stderr` 的内容。
