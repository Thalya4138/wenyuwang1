## 0. 先记住的六件事

1. **未定义行为不是"结果随机"，而是"程序已经不合规"。** 标准对它的全部要求是：**实现可以做任何事**。
   ——包括让程序看起来正常。
2. **编译器通常不对 UB 报警。** 本机实测：有符号溢出、数组越界、双重释放，
   在 `/W4` 下**一条警告都没有**（它只报了"变量没用"）。
3. **优化器不会"制造" bug，它只是不再替你兜底。** 你的代码本来就有 UB，
   优化只是让它有机会表现出另一种样子。
4. **`constexpr` 让计算发生在编译期，`static_assert` 让它在编译期就失败。**
   这两个加起来是"零开销抽象"的主要来源。
5. **数据竞争在标准里就是未定义行为**，不是"可能出错"。所以共享数据必须同步——
   这不是风格问题，是正确性问题。
6. **本讲义到 C++17 为止。** C++20/23 的东西这一章只给地图和"以后去哪看"，不假装教过。

> 如果只记一条，记第 2 条。**"编译器没报错"从来不是正确性的证据。**

## 1. 未定义行为：本书最大的一类坑，一次说清

前面每一章都在提"未定义行为"（undefined behavior，UB）。它是 C++ 里唯一一类
**不需要产生任何错误、也就不会有任何提示**的问题。这一节把它一次性说清。

### 1.1 三种"标准没规定死"的行为，别混

这是最该分清的一张表：

| 类别 | 英文 | 标准怎么要求 | 例子 |
|---|---|---|---|
| **未定义行为** | undefined behavior | **不要求做任何事**。程序失去全部保证 | 有符号溢出、越界、空指针解引用、双重释放、数据竞争 |
| **实现定义行为** | implementation-defined | **必须选一种并记录在案** | `char` 是否有符号、`sizeof(int)`、整数右移负数 |
| **未指定行为** | unspecified | **可以是几种之一，但不必记录是哪种** | 函数参数的求值顺序 |

**为什么要分**：

- **未定义** → **你的程序错了**，要改代码
- **实现定义** → 程序没错，但**换编译器可能不同**，跨平台代码要注意
- **未指定** → 程序没错，但**别依赖某一种顺序**

> **一句话判据**：
> **UB 是"你的错"；实现定义是"标准的自由"；未指定是"实现的自由"。**

### 1.2 UB 清单（现在要知道的）

| UB | 在哪一章讲过 | 典型触发 |
|---|---|---|
| 读**未初始化**的变量 | 第 02 章 5.4 | `int x; std::cout << x;` |
| **有符号**整数溢出 | 第 02 章、第 03 章 | `INT_MAX + 1` |
| 数组**越界**访问 | 第 06 章 | `a[10]` 而数组只有 4 个 |
| **空指针**解引用 | 第 06 章 | `*p` 而 `p == nullptr` |
| **悬垂**指针访问 | 第 06 章第 10.2 节「悬垂：指向已经死掉的对象的指针」 | 对象已销毁还在读 |
| **重复释放** | 第 06 章第 10.4 节「重复释放：`delete` 两次」 | 两次 `delete` 同一指针 |
| **数据竞争** | 第 13 章第 5 节 | 两个线程写同一变量且无同步 |
| 函数**不写 `return`** 就到达末尾（`main` 除外） | 第 01 章、第 05 章 | 非 `main` 的返回值函数 |
| 除零（整数） | 第 03 章 | `1 / 0` |
| 移位量 ≥ 类型位宽或为负 | 第 03 章 | `1 << 100` |
| 移动/拷贝到重叠内存（`memcpy` 语义） | 进阶 | `memcpy(dst, dst+1, n)` |

**对照**：**无符号**溢出**不是** UB（第 02 章 10.1 实测过回绕），
**双重释放在我的实测里编译器一声不响**，但它确实是 UB。

> **注意这张表的用途**：它不是让你去背，而是让你在遇到"程序时对时错"时，
> **知道往这里查**。UB 最坑的地方就是它**没有固定症状**。

## 2. 实测：编译器对 UB 到底说不说话

这一节记录一段代码的**编译诊断**。它列出六类风险，但**声明未初始化变量而不读取、保存空指针而不解引用，本身不触发这两类 UB**。越界读取、有符号溢出和重复释放则是执行时会触发的 UB；不能用这份代码检验未初始化读取、空指针解引用的诊断能力。
下面是编译用完整源码的节选，使用 `/W4`：

```cpp
int main() {
    int uninit;                        // ① 未初始化
    int a[4] = {1, 2, 3, 4};           // ② 越界访问
    int* null_p = nullptr;             // ③ 空指针解引用
    int big = 2147483647;
    int overflowed = big + 1;          // ④ 有符号溢出
    int* dangling = make_dangling();   // ⑤ 悬垂指针
    int* raw = new int{1};
    delete raw;
    delete raw;                        // ⑥ 双重释放
    std::cout << overflowed << '\n';
}
```

**`/W4` 下的全部诊断（本机实测，逐字照贴）：**

```text
main.cpp(10): warning C4101: "uninit": 未引用的局部变量
main.cpp(18): warning C4189: "null_p": 局部变量已初始化但不引用
main.cpp(5): warning C4172: 返回局部变量的地址或临时 : local
```

**只有三条，而且两条说的是"变量没用"。**

| 风险类别及这份代码实际做的事 | 编译器说了什么 |
|---|---|
| ① 未初始化 | ⚠️ `C4101` —— 但说的是"**未引用**"，因为我没有真去读它 |
| ② 数组越界 | ❌ **一个字都没说** |
| ③ 只保存空指针，**未解引用** | 没有对应解引用操作，不能据此判断诊断能力 |
| ④ 有符号溢出 | ❌ **没说** |
| ⑤ 悬垂指针 | ✅ `C4172` —— **唯一一条真正相关的警告** |
| ⑥ 双重释放 | ❌ **没说** |

**结论（这一节的落点）：**

> **编译器不保证诊断所有 UB。** 这份样本中，若干真正危险的操作没有得到相关警告；不能推广为所有编译器都不提醒。**编译通过或一次运行正常，都不能证明程序正确。**

这也回答了第 01 章第 8 节留下的那句话："警告不是噪音，但**也不能只看警告**"——
**警告能抓到的 UB 只是其中一小部分。**

### 2.1 那真触发会怎样：空指针解引用的实测退出码

上面的组合代码只用于编译诊断，**没有运行**；若运行会执行其中的 UB，不能说代码本身没有触发条件。
另一个空指针解引用示例的历史实测记录如下（本轮审计没有重新运行 UB 程序）：

```cpp
int main() {
    int* p = nullptr;
    std::cout << "before\n";
    std::cout << *p << '\n';
    std::cout << "after\n";
}
```

**本机实测结果**：

```text
退出码 = -1073741819   （也就是 0xC0000005，访问冲突）
```

程序**在 `before` 之后、`after` 之前就死了**（`after` 一行都没打印）。

| 你看到的现象 | 归属 |
|---|---|
| 编译通过、无警告 | UB 的"静默" |
| 运行时访问冲突 `0xC0000005` | **本机**的表现 |
| `after` 没打印 | 进程已终止 |

> ⚠️ **关键认识**：**"空指针解引用会崩溃"只是本机的表现，不是标准的保证。**
> 标准对 UB 的全部要求是"实现可以做任何事"——**它也可以不崩溃**。
> 在另一个编译器、另一个优化级别下，同一段代码可能：
> 打出垃圾值、跳过整段逻辑、或者在优化后**看起来完全正常**。
>
> **所以千万不要用"它崩溃了"来判定某个写法是 UB，
> 也不要用"它没崩溃"来判定它不是 UB。** 只能查标准。

## 3. 优化为什么能"改变"程序行为

第 12 章第 4.2 节我实测过一个正面的结论：**十组示例在 `/Od` 与 `/O2` 下输出逐字相同**——
这个观察不能推出所有良定义程序在不同选项下都必须有相同输出；标准特别允许的拷贝省略可能改变构造打印次数，见该章第 4.3 节的 NRVO 对照。

那为什么大家又说"UB 在优化下会爆炸"？两句话都对，关键在于**前提不同**：

| 前提 | 优化器能做什么 |
|---|---|
| 程序**没有** UB | 必须符合标准允许的行为；一般优化受可观察行为约束，**允许的拷贝省略等特殊规则另计** |
| 程序**有** UB | 优化器可以**假设 UB 不会发生**，于是做出任何推论 |

**为什么可以假设**：因为标准说 UB 的行为"不需要任何保证"。
编译器于是有了逻辑上的自由：**"如果这段代码真的执行到这里，那程序就不是合法程序，
我对它做什么都不算违约。"** 于是它可以把你写的判断直接当成恒真、把分支删掉、
把整个循环消掉。

> **最常见的误解**："优化器把我的 `if` 优化没了，所以是优化器的 bug。"
>
> **准确的因果**：你的代码里有 UB，于是优化器**合法地**做出了改变。
> **修法是消除 UB，不是关优化。**

### 3.1 但我必须诚实说一句

**本机实测中，我没能复现出"MSVC 因 UB 而改变可观察行为"的例子。**

我试了两类候选：

| 候选 | `/Od` | `/O1` | `/O2` |
|---|---|---|---|
| 有符号溢出 `INT_MAX + 1` 后判断回绕 | `-2147483648` / `wrap detected` | — | **相同** |
| 越界访问后推断 `i` 必在界内 | `1` / `0` | `1` / `0` | **相同** |

**这些测试配置下的输出相同**，只能说没有观察到输出差异；仅凭 stdout 不能判断编译器内部是否利用了 UB，也不能推广到这个版本的所有程序。

**这说明了什么**（这一点比"UB 会爆炸"更重要）：

> **UB 的危险不在于"它一定会出事"，而在于"它有时会，有时不会"。**
> 同一段代码在你的机器上可能永远正常，在别人机器上、在另一个编译器上、
> 在下一次版本升级后突然出问题——**而中间没有任何提示**。
>
> 这比"必然崩溃"难查得多：**必然崩溃至少会告诉你哪里错了。**

所以正确的态度不是"UB 一定会咬我"，而是：

> **不依赖任何未定义的行为**，即使它现在看起来工作正常。
> 因为"现在正常"不是标准给的保证，只是这一次的巧合。

## 4. 编译期计算：`constexpr` / `static_assert` / `consteval`

第 02 章第 7 节分了 `const` 与 `constexpr`。这一节把 `constexpr` 用起来。

<!-- example:ch13_constexpr -->
```cpp
#include <iostream>

constexpr int factorial(int n) {
    return n <= 1 ? 1 : n * factorial(n - 1);
}

int main() {
    constexpr int f5 = factorial(5);        // 编译期求值
    static_assert(f5 == 120, "factorial(5) should be 120");
    std::cout << f5 << '\n';

    int n = 3;
    std::cout << factorial(n) << '\n';      // 运行期求值（同一个函数）
}
```

<!-- result:ch13_constexpr -->
```text
120
6
```

### 4.1 同一个函数，两种求值时机

这是 `constexpr` 最该理解的一点：**它标记的是"这个函数有能力在编译期求值"，不是"只能在编译期求值"。**

| 调用 | 求值时机 | 为什么 |
|---|---|---|
| `constexpr int f5 = factorial(5);` | **编译期** | 参数是常量，且结果赋给 `constexpr` 变量 → 编译器必须算 |
| `factorial(n)` 其中 `n` 是运行期变量 | **运行期** | 参数编译期不知道 |

**所以 `constexpr` 不产生"两套代码"**——只有一个函数，编译器根据上下文决定什么时候算。
（代价是 `constexpr` 函数体内能用什么受限制，C++14 起放宽了很多。）

### 4.2 `static_assert`：把断言提前到编译期

`static_assert` 的条件必须是**编译期常量表达式**，失败时**编译就过不去**。
这比运行期的 `assert` 更好——**错误在最早的时刻被抓住**。

<!-- example:ch13_size_assert -->
```cpp
#include <cstdint>
#include <iostream>

static_assert(sizeof(std::int32_t) == 4, "int32_t must be 4 bytes");
static_assert(sizeof(std::uint64_t) == 8, "uint64_t must be 8 bytes");

int main() {
    std::cout << "assumptions hold\n";
}
```

<!-- result:ch13_size_assert -->
```text
assumptions hold
```

**失败时长什么样**（这是**故意让编译失败**的示例，本机实测诊断）：

<!-- example:ch13_static_assert_fail -->
```cpp compile-fail
#include <cstdint>

static_assert(sizeof(void*) == 4, "this program assumes 32-bit pointers");

int main() {}
```

真实诊断：

```text
main.cpp(3): error C2338: static assertion failed: 'this program assumes 32-bit pointers'
```

> **`static_assert` 的三个实际用途**：
> ① 断言平台假设（"这个程序假定 32 位指针"）；
> ② 在模板里给出可读的错误信息（模板报错本来极难懂，这是救命的）；
> ③ 保证类型布局满足协议/文件格式的要求。

### 4.3 C++14/17 起 `constexpr` 能做什么

<!-- example:ch13_constexpr_if -->
```cpp
#include <iostream>

constexpr int abs_value(int n) {
    if (n < 0) {          // C++14 起允许在 constexpr 函数里用 if
        return -n;
    }
    return n;
}

int main() {
    constexpr int a = abs_value(-7);
    static_assert(a == 7, "abs_value(-7) should be 7");
    std::cout << a << ' ' << abs_value(3) << '\n';
}
```

<!-- result:ch13_constexpr_if -->
```text
7 3
```

**能力的演进（版本标注必须写清，因为这是基线问题）**：

| 特性 | 起点 |
|---|---|
| `constexpr` 变量、简单的 `constexpr` 函数 | **C++11** |
| `constexpr` 函数里允许 `if`、循环、多个 `return`、局部变量 | **C++14** |
| `constexpr` lambda | **C++17** |
| `if constexpr`（编译期分支） | **C++17**（第 11 章讲） |
| `consteval`（必须在编译期求值）、`constinit` | **C++20** ⚠️ 超出本讲义基线 |

> **本讲义基线是 C++17**，所以第 4 行以上都是直接能用的；
> `consteval` / `constinit` 属于 C++20，**只标位置，不展开**。

## 5. 并发基础：为什么共享数据必须同步

### 5.1 先看一个能正确工作的最小例子

<!-- example:ch13_thread -->
```cpp
#include <iostream>
#include <mutex>
#include <thread>

int counter = 0;
std::mutex m;

void add_many() {
    for (int i = 0; i < 1000; ++i) {
        std::lock_guard<std::mutex> lock{m};   // RAII：出作用域自动解锁
        ++counter;
    }
}

int main() {
    std::thread t1{add_many};
    std::thread t2{add_many};
    t1.join();
    t2.join();
    std::cout << counter << '\n';
}
```

<!-- result:ch13_thread -->
```text
2000
```

**读这段程序，关注四件事：**

| 语法 | 作用 |
|---|---|
| `std::thread t1{add_many};` | **启动**一个线程执行 `add_many`（注意：是**启动**，不是"声明"） |
| `t1.join();` | **等待** `t1` 结束。**不 join 就析构 `thread` 会导致程序终止** |
| `std::lock_guard<std::mutex> lock{m};` | 构造时加锁，**析构时自动解锁** —— 又一个 RAII（第 12 章） |
| `++counter;` | 读-改-写三步。**没有锁的话两个线程可能交错，导致丢失更新** |

**为什么必须是 2000**：两个线程各加 1000 次。如果结果小于 2000，说明发生了**丢失更新**——
某个线程读到的 `counter` 已经被另一个线程改过，但自己写回了旧值加一。

### 5.2 不用锁也能安全累加：`std::atomic`

<!-- example:ch13_atomic -->
```cpp
#include <atomic>
#include <iostream>
#include <thread>

std::atomic<int> counter{0};

void add_many() {
    for (int i = 0; i < 1000; ++i) {
        counter.fetch_add(1);        // 默认 memory_order_seq_cst
    }
}

int main() {
    std::thread t1{add_many};
    std::thread t2{add_many};
    t1.join();
    t2.join();
    std::cout << counter.load() << '\n';
}
```

<!-- result:ch13_atomic -->
```text
2000
```

**`atomic` 与 `mutex` 的分工**（这张表要记住）：

| | `std::mutex` + `lock_guard` | `std::atomic<T>` |
|---|---|---|
| 保护范围 | **一段代码**（临界区） | **单个变量** |
| 能否保护多个变量的不变式 | ✅ 可以 | ❌ 不行 |
| 开销 | 通常更大 | 通常更小 |
| 什么时候用 | 需要保证"多个操作整体原子" | 只需要"单个变量读改写原子" |

> ⚠️ **坑：以为 `atomic` 能保护一段逻辑。**
> `counter++` 换成 `counter.fetch_add(1)` 是安全的，但如果你要"读两个变量并保证它们一致"，
> **`atomic` 做不到**——那需要 `mutex` 把整段圈起来。
> **判据**：`atomic` 保证的是**单个变量**的原子性，不是**一段代码**的。

### 5.3 为什么"数据竞争"是未定义行为

标准的规定是：**两个线程访问同一内存位置，其中至少一个是写，且没有同步 → 数据竞争 → 未定义行为。**

**所以它不是"可能算错"，而是"程序已经不合规"。** 这比"结果可能不对"严重得多，
因为它允许编译器做出**超出你想象**的优化（第 3 节）。

> **本节的立场（与本讲义一致）**：
> 并发是**独立的、深的**领域。这一节给的是**能安全写出的最小模式**（锁保护 / 原子变量），
> 不是并发教程。**内存序（memory order）、无锁编程、条件变量、线程池都在本讲义范围之外**——
> 它们属于"知道存在、以后专门学"的层。
>
> **现在的实用规则**：① 优先用 `mutex` 而不是 `atomic`（除非确实只需要单变量原子）；
> ② 一个 `atomic` 变量的默认内存序是 `seq_cst`（最安全，**别急着改成 `relaxed`**）；
> ③ 不要共享可变数据是最好的并发策略。

## 6. 构建系统：从一行编译命令到 CMake

第 01 章第 7.3 节给过一个 `build.ps1` 脚本。项目一大，一行命令就不够了。

### 6.1 三层的演化

| 层 | 工具 | 解决的问题 | 本讲义状态 |
|---|---|---|---|
| 0 层 | **手敲 `cl` 命令** | 单文件编译 | ✅ 第 01 章已教 |
| 1 层 | **脚本**（`.bat` / `.ps1`） | 把一堆开关固化下来 | ✅ 第 01 章给过 |
| 2 层 | **Make / Ninja** | 只重编改动的文件；描述依赖关系 | ⚠️ 只给位置（本机未安装） |
| 3 层 | **CMake** | 跨平台描述工程；生成 Make/Ninja/VS 工程 | ⚠️ 只给位置（本机未安装） |

**为什么要分层而不是直接上 CMake**：因为 **CMake 生成的就是第 2 层的东西**，
而第 2 层调用的就是第 0 层的编译器。**跳过下面两层，CMake 出错时你完全看不懂它在干什么。**

### 6.2 一个最小 `CMakeLists.txt`（**本机未实测**）

```cmake
cmake_minimum_required(VERSION 3.16)
project(cpp_learn CXX)

set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

add_executable(app main.cpp util.cpp)
```

**逐行读**：

| 行 | 作用 |
|---|---|
| `cmake_minimum_required` | 声明"我需要至少这个版本的 CMake 的行为" |
| `project(... CXX)` | 声明工程名与语言（`CXX` = C++） |
| `set(CMAKE_CXX_STANDARD 17)` | **对应第 01 章的 `/std:c++17`** |
| `CMAKE_CXX_STANDARD_REQUIRED ON` | 不支持就报错，而不是悄悄降级 |
| `add_executable(app ...)` | 把这些源文件编成一个叫 `app` 的可执行文件 |

> ⚠️ **本机没有安装 CMake**（实测：`cmake`、`make`、`ninja` 全部不在 PATH），
> **所以上面这段没有在本机跑过**，它是"知道长什么样"级别的材料，不是已验证的示例。

### 6.3 什么时候该上构建系统

| 项目规模 | 建议 |
|---|---|
| 1–3 个文件 | 手敲命令或一个 `.bat`/`.ps1` 就够，**别上 CMake** |
| 5–20 个文件 | 值得用 Makefile 或 CMake |
| 需要跨平台 / 引第三方库 / 别人要能编 | **用 CMake** |
| 用 IDE（Visual Studio / CLion / VS Code） | IDE 通常自己管，但**要能读懂它生成的 CMake** |

> **为什么入门阶段不用急着上 CMake**：因为**编译错误和构建系统错误是两回事**。
> 一个手敲 `cl` 就能编过的小程序，套上 CMake 后报错，你分不清是代码问题还是配置问题。
> **先把第 01 章那条链走熟**，再上工具。

## 7. 性能与优化入门

### 7.1 一条最重要的判断：先测量，再优化

> **不要靠"感觉"优化 C++。** 编译器的优化能力远超你的直觉，
> 而你"觉得慢"的地方，多半不是真正的瓶颈。

第 12 章十组输出相同，**不能证明中间对象或构造调用在机器码中被消除了**，也不是性能测量。
C++17 的保证省略和允许的 NRVO 需要分别按规则判断；若要判断实际开销，应另看测量结果或生成代码。

### 7.2 三个有实际收益的习惯

<!-- example:ch13_pass_by_ref -->
```cpp
#include <iostream>
#include <string>

int by_value(std::string s) { return static_cast<int>(s.size()); }
int by_cref(const std::string& s) { return static_cast<int>(s.size()); }

int main() {
    std::string big(1000, 'x');
    std::cout << by_value(big) << ' ' << by_cref(big) << '\n';
}
```

<!-- result:ch13_pass_by_ref -->
```text
1000 1000
```

**输出一样，但代价不同**：

| 写法 | 发生了几次拷贝 |
|---|---|
| `int by_value(std::string s)` | **1 次**（传参时拷贝整个字符串） |
| `int by_cref(const std::string& s)` | **0 次**（只传引用） |

**三个习惯**：

| 习惯 | 为什么 |
|---|---|
| 只读的"大"参数用 `const T&` | 避免拷贝 |
| 循环里传参、返回都避免无谓的拷贝 | 同样的理由，效果好 |
| 能用 `std::move` 的地方用上（第 12 章） | 但**先确认它真的移动了** |

> ⚠️ **坑：`const T&` 不是无脑好。**
> 对**小类型**（`int`、`double`、指针），传值可能**更快**，因为引用本质也是指针，
> 多一层间接访问。**"小传值、大传 const 引用"** 是个够用的规则。
>
> 另外：**`const T&` 会阻止移动**（第 12 章 5.2 实测过 `const` 导致退回拷贝）。
> 所以"这个参数我要拿走"时，不能是 `const T&`。

### 7.3 优化开关

| 开关 | 作用 | 什么时候用 |
|---|---|---|
| `/Od` | 不优化 | **调试**（能单步、变量不被优化掉） |
| `/O2` | 常用优化 | **发布** |
| `/O1` | 小幅度优化 | 少见 |
| `/Ox` | 最大优化 | 少见，可能触发 UB 暴露 |

**判据**：**开发用 `/Od`（方便调试），发布用 `/O2`（性能）。**
但**两个级别都要跑测试**——因为如果行为不同，那就说明有 UB（第 3 节的用法）。

> **本机这一个月的实测结论**：我在这本讲义里**对每个示例都跑了 `/Od` 与 `/O2`**，
> **没有一组输出不同**。这说明：**本讲义里的示例全部没有可观察的 UB。**
> ——这本身就是一份质量证据。

## 8. C++20/23 的地图：现在知道存在即可

**这一节的任务是防止你把过时的知识当全部**，不是教你新特性。本讲义基线是 **C++17**。

### 8.1 C++20 里影响最大的几件事

| 特性 | 解决什么问题 | 为什么值得知道 |
|---|---|---|
| **概念 `concepts`** | 模板参数的约束，把"报错在第 200 行模板内部"变成"报错在调用处" | **模板可用性的最大改善**。见 `11_模板与泛型.md` 第 9 节「`concepts`：同一个问题的现代答案（C++20，只标位置）」 |
| **范围 `ranges`** | 算法可以直接吃容器（`sort(v)` 而不是 `sort(v.begin(), v.end())`），并可组合 | 写法变化很大 |
| **`std::format`** | 替代 `printf`/流，类型安全 + 位置参数 + 快 | 格式化终于有了现代方案（见 `09_字符串与IO.md` 第 6 节「格式化：`printf`、流与 `std::format` 的位置」） |
| **三路比较 `<=>`** | 一个运算符生成全部六个比较 | 手写比较运算符的时代结束了 |
| **模块 `modules`** | 替代 `#include`，解决第 01 章讲的那些预处理问题 | **第 01 章的坑终于有解了**，但生态还在推进 |
| **`std::span`** | 非拥有的连续序列视图 | `string_view` 的"通用容器版" |
| **`constexpr` 大扩张 / `consteval` / `constinit`** | 编译期计算能力进一步扩大 | 第 4.3 节标过 |

### 8.2 C++23 里与你有关的几个

| 特性 | 说明 |
|---|---|
| **`std::print`** | 直接打印（含格式化），比 `cout` 简洁 |
| **`std::expected`** | 表达"要么有值、要么有错误"，是错误处理的新选项（第 08 章第 6.3 节「`std::expected`：要么是值，要么是错误原因（C++23）」只列进阶位置） |
| **`std::flat_map` / `flat_set`** | 基于有序数组的映射，缓存友好 |
| **`std::mdspan`** | 多维视图（科学计算/机器学习相关） |

### 8.3 现在该怎么做

> **不要现在学 C++20。** 理由：
>
> ① 本讲义覆盖的**语义模型**（值类别、RAII、`const` 正确性、生命周期）**是 C++20 的前提**，
> 它们从 C++11 起就是基线，不学它们学不懂新特性；
> ② **判题机和很多既有工程还是 C++17**（第 01 章 7.1 讲过），
> 现在写 C++20 会在这些环境里编不过；
> ③ 新特性的**语法很短，语义依赖很长**——`concepts` 一行能用，但它背后是模板实例化和重载决议。
>
> **正确顺序**：把本讲义吃透 → 找一个小项目真写 → 然后再看 C++20。
> 到那时你会发现新特性是**对已懂知识的简化**，而不是全新的东西。

## 10. 本章自测

**1.** "未定义行为"、"实现定义行为"、"未指定行为"三者的区别是什么？各举一例。

<details><summary>答案</summary>

| 类别 | 标准的要求 | 例子 |
|---|---|---|
| **未定义行为** | **不要求做任何事**，程序失去全部保证 | 有符号溢出、越界、空指针解引用、数据竞争 |
| **实现定义** | **必须选一种并记录在案** | `char` 是否有符号、`sizeof(int)` |
| **未指定** | **可以是几种之一，不必记录是哪种** | 函数参数的求值顺序 |

**一句话判据**：**UB 是"你的错"；实现定义是"标准的自由"；未指定是"实现的自由"。**

**实际意义**：UB 要改代码；实现定义要注意跨平台；未指定不要依赖某一种顺序。
</details>

**2.** 第 2 节那段列出六类风险的代码，在 `/W4` 下编译器报了什么？这个结果说明了什么？

<details><summary>答案</summary>

只报了**三条**，而且两条说的是"变量没用"：

```text
warning C4101: "uninit": 未引用的局部变量        ← 说的是"未引用"，不是"未初始化"
warning C4189: "null_p": 局部变量已初始化但不引用  ← 又一次"没用"
warning C4172: 返回局部变量的地址或临时 : local     ← 唯一真正相关的
```

数组越界、有符号溢出和双重释放没有相关警告；空指针在该样本中未被解引用，不能据此评价解引用诊断。

**说明：编译器不保证诊断所有 UB。** 这份样本不足以说明所有 UB 都没有警告。
所以**"编译过了、跑起来了"完全不能证明程序是对的**。

**这也回答了第 01 章那句话**："警告不是噪音，但也不能只看警告"——
警告能抓到的 UB 只是其中一小部分。
</details>

**3.** 我在第 12 章实测了"`/Od` 与 `/O2` 下十组输出逐字相同"，本章又实测"MSVC 没能利用有符号溢出/越界的 UB 改变行为"。这两条加起来，是不是说明"UB 其实不危险"？

<details><summary>答案</summary>

**恰恰相反，它说明 UB 更难查。**

**UB 的危险不在于"它一定会出事"，而在于"它有时会，有时不会"。**

同一段代码在你机器上可能永远正常，在别人机器上、在另一个编译器上、
在下一次编译器版本升级后突然出问题——**而中间没有任何提示**。

**这比"必然崩溃"难查得多**：必然崩溃至少会告诉你哪里错了。
本机实测空指针解引用确实崩溃在 `0xC0000005`——但那**只是本机的表现**，
标准对 UB 的全部要求是"实现可以做任何事"，**它也可以不崩溃**。

**所以正确态度是**：不依赖任何未定义行为，**即使它现在看起来工作正常**。
"现在正常"不是标准给的保证，只是这一次的巧合。
</details>

**4.** `constexpr int f5 = factorial(5);` 与 `factorial(n)`（`n` 是运行期变量）有什么区别？

<details><summary>答案</summary>

前者在**编译期**求值，后者在**运行期**求值——**但是同一个函数**。

`constexpr` 标记的是"**这个函数有能力**在编译期求值"，**不是"只能在编译期求值"**。

判据是**上下文**：参数是常量且结果赋给 `constexpr` 变量 → 编译器必须编译期算；
参数运行期才知道 → 只能运行期算。

本机实测输出 `120` 和 `6`：`factorial(5)` 编译期算出 120，
`factorial(3)` 运行期算出 6。

**它不产生"两套代码"**——只有一个函数。代价是 `constexpr` 函数体内能用什么受限制
（C++14 起放宽，允许 `if`、循环、局部变量）。
</details>

**5.** `std::atomic` 和 `std::mutex` 该怎么选？`atomic` 有一个很大的局限是什么？

<details><summary>答案</summary>

| | `mutex` + `lock_guard` | `atomic<T>` |
|---|---|---|
| 保护范围 | **一段代码**（临界区） | **单个变量** |
| 开销 | 通常更大 | 通常更小 |

**`atomic` 的大局限：它只保证单个变量的原子性，不能保护"一段逻辑"。**

所以如果你需要"读两个变量并保证它们互相一致"，`atomic` **做不到**——必须用 `mutex` 把整段圈起来。

**选择判据**：只需要单变量读改写原子 → `atomic`；需要多个操作整体原子 → `mutex`。

**本机实测**：两线程各加 1000 次，`mutex` 版和 `atomic` 版都得到 `2000`。

⚠️ 另外：`atomic` 默认内存序是 `seq_cst`（最安全），**别急着改成 `relaxed`**——
那属于本讲义范围外的并发专门知识。
</details>

**6.** 为什么说"数据竞争"比"结果可能算错"严重得多？

<details><summary>答案</summary>

因为标准规定数据竞争是**未定义行为**，不是"结果不确定"。

**"结果可能算错"**暗示程序还在规则内运行，只是结果不可预测。
**而 UB 意味着程序已经不合规**，编译器可以基于"UB 不会发生"做出任何推论——
包括把整个循环消掉、把你写的判断当成恒真。

所以数据竞争的危险不只是"数值不对"，而是**整个程序的语义都失去了保证**。

**本机实测的反面证据**：两个线程各加 1000 次，**有锁**时稳定得到 `2000`。
如果去掉锁，结果可能小于 2000（丢失更新），而这**已经是 UB 了**，不只是"算错"。
</details>

**7.** 本章第 4 节「编译期计算：`constexpr` / `static_assert` / `consteval`」这条轴，和前面哪些章节的内容连在一起？

<details>
<summary>答案</summary>

它把三处知识串成了一条线：

1. **第 01 章的翻译单元**：编译期计算发生在预处理/编译阶段，与"链接"无关。
   `static_assert` 失败是**编译错误**（本机实测 `error C2338`），程序根本不会生成。
2. **第 02 章的 `const` vs `constexpr`**：`const` 是"不能改"，`constexpr` 是"编译期已知"。
   第 4 节把后者用起来了。
3. **第 11 章的 `if constexpr`**：把"编译期分支"写进控制流，是模板里按类型分支的唯一可读写法。

**为什么这条轴重要**：C++ 的"零开销抽象"很大程度来自"能在编译期做的事就不要留到运行期"。
`static_assert` 是这个思想的**极端形式**——错误在编译期就被抓住，运行时零成本。
</details>

**8.** 为什么本讲义不让你现在学 C++20？给三条理由。

<details><summary>答案</summary>

1. **语义模型是前提**：本讲义覆盖的值类别、RAII、`const` 正确性、生命周期
   **从 C++11 起就是基线**，不学它们学不懂 `concepts` / `ranges` 背后的东西。
2. **环境限制**：判题机和很多既有工程还是 **C++17**（第 01 章 7.1），
   现在写 C++20 会在这些环境里编不过。
3. **语法短、语义长**：`concepts` 一行能用，但它背后是模板实例化和重载决议。
   不懂那些，出了问题你没法查。

**正确顺序**：吃透 C++17 → 找一个小项目真写 → 再看 C++20。
到那时新特性是**对已懂知识的简化**，不是全新东西。
</details>

### 13.2 三条贯穿全书的线（比任何一个知识点都重要）

**线一：文本 → 机器码 → 运行。**（01 章建立，全书的底色）

这条线解释了：为什么 `#include` 是文本替换、为什么声明定义要分离、
为什么模板必须写在头文件里、为什么 `static_assert` 是编译错误而不是运行时错误。
**遇到"莫名其妙"的问题，先问它在链条的哪一环。**

**线二：所有权与生存期。**（06 → 07 → 12 章）

这条线解释了：为什么裸指针危险、为什么 RAII 是核心设计、为什么需要智能指针、
为什么移动语义存在、为什么异常也安全。
**看到"需要成对操作"的资源（new/delete、open/close、lock/unlock），就该想到它。**

**线三：什么是保证的、什么不是。**（贯穿全书，13 章收口）

这条线解释了：标准保证 vs 实现定义 vs 未指定 vs 未定义行为；
`constexpr` 保证编译期、拷贝省略在 C++17 是保证的、`noexcept` 影响容器选择。
**这条线是"能不能信这段代码"的判据——它是本书最实用的一条。**

### 13.4 下一步是什么、为什么是下一步

```text
现在：
  能读懂 C++17 代码，能写出不踩经典坑的程序，
  知道每个结论"是标准保证还是本机现象"。

下一步（按顺序）：
  1. 用真项目把语义用起来     ← 因为"会写"和"学过"是两件事
  2. 补调试器与 CMake        ← 因为本机没装，本书给不了实测
  3. 把标准库用熟（不是背）   ← 因为 99 索引是按需查的工具，不是读物
  4. 读别人的代码            ← 因为很多设计理由只在真实代码里显形
  5. 然后再看 C++20          ← 因为新特性是"对已懂知识的简化"
```

**为什么是这个顺序**：因为这五步的**依赖关系**是硬的——
没有项目经验，你读不懂标准库为什么要那样设计；
不懂标准库，你读别人的代码只能看到语法；
不懂 C++17 的语义模型，C++20 的新特性对你只是新语法。

### 13.5 最后一句

这份讲义的目标从来不是"让你觉得 C++ 很难"或"让你背下来"。
它的目标是**让你知道每一句话的可信度**：

- 哪些是**标准保证**的（换编译器也成立）
- 哪些是**本机实测**的（标了"本轮实测"，附了复现方式）
- 哪些是**实现定义**的（本机这样，别处可能不同）
- 哪些是**未定义行为**（现在正常不代表对）

**章末那张「诚实标注」表就是这份可信度的清单。**
会查这张表，比记住任何一个语法点更有用。
