## 一、为什么需要这份文件（本机实测事实，不是设想）

### 1.1 Codex 无法在 DSH 沙箱内运行 —— 已实测，且绕不过去

| 尝试 | 命令 | 结果 |
|---|---|---|
| 直接非交互执行 | `codex exec --sandbox read-only "..."` | ❌ `failed to initialize in-process app-server client: 拒绝访问 (os error 5)` |
| 放宽沙箱 | `codex exec --sandbox danger-full-access ...` | ❌ 同上（**放宽沙箱无用**，说明不是文件权限问题） |
| 分离进程 + 文件重定向 | `Start-Process codex.cmd ... -RedirectStandardOutput` | ❌ 同上 |
| 启动常驻 daemon | `codex app-server daemon start` | ❌ `failed to open daemon operation lock C:\Users\Wang\.codex\app-server-daemon\daemon.lock — 拒绝访问 (os error 5)` |
| 诊断工具 | `codex doctor` | ✅ **能跑**，并自行报告 `app-server background server socket is stale or unreachable` |

**结论（根因）**：Codex 的运行模型要求写 `C:\Users\Wang\.codex\`（daemon 锁 + socket 状态）并建立本机 RPC 命名管道；
而 DSH 沙箱对本会话的写权限**只限工作区** `C:\Users\Wang\Desktop\git`。
两者要求不相交，**不是配置能解决的问题**。同理此前已记录：Git 自带 `ssh.exe`、`bash -lc`、Python `multiprocessing.Pipe` 在本沙箱内一律失败——同一个成因。

### 1.2 但 C++ 侧的验证能力是完整的 —— 这决定了分工

| 能力 | 状态 | 实测证据 |
|---|---|---|
| C++ 编译器 | ✅ 可用 | VS Build Tools 2026 · MSVC **14.51.36231** · Windows SDK **10.0.26100** |
| 编译 + 运行 | ✅ 可用 | `cl /nologo /std:c++17 /EHsc /W4 /utf-8 hello.cpp /Fe:hello.exe && hello.exe` → 输出 `7`，exit 0 |
| C++17 完整标准库头 | ✅ 可用 | 上例含 `<iostream>`；Windows SDK 头已就位 |
| 控制台编码 | ⚠️ 活动代码页 **936（GBK）** | 必须加 `/utf-8`，否则中文源码/输出乱码 |
| 编译器初始环境 | ⚠️ 不在 PATH | 每次须先跑 `vcvars64.bat` |

> **这解决了上一轮失败的根本原因。** `tmp/build_cpp_notes.py`（上一轮留下的生成脚本，只写完第 1～3 章即中止）
> 里的示例**没有真实编译输出支撑**。现在这条短板补上了：本仓库已能对每个 `cpp` 块做编译+运行+逐字比对。

### 1.3 由此确定的分工原则

> **谁在哪一侧有独占能力，谁就负责那一侧；交接只走仓库里的文件，不依赖两个 agent 直接通话。**

沙箱外（你的普通终端）能跑 Codex；沙箱内（我）能调编译器和跑全量审计脚本。
两侧通过 `_handoff/` 目录交换**自包含的任务书与验收单**——这是本协议的核心机制。

## 二、分工表

| 角色 | 谁 | 独占能力 | 负责 |
|---|---|---|---|
| **A · 结构与验收** | DSH agent（我） | 编译器全量实跑、结构审计脚本、跨章引用核对、覆盖表维护 | 覆盖表、三源核对、章首目录/对账表机检、**编译验证**、缺口审计、协作调度 |
| **B · 正文写作** | Codex（沙箱外终端） | 长文连续写作、不同模型视角 | 按任务书写正文、按验收单修缺陷 |
| **C · 对抗评审** | A 与 B **互相** | 各自模型的独立判断 | 逐条攻击对方章的：C++17 覆盖缺口、UB 说法、编译器依赖断言、混层结构 |

**为什么要对抗**：这两类错误自己审不出来——

1. **"我这能编过" ≠ "标准规定如此"**：MSVC 编过的写法可能依赖实现定义，甚至本身就是 UB，只是恰好没炸。
2. **混层**：写作者天然按"我想到的顺序"排，同一级标题混了入口/机制/用途三根轴，自己看着很顺。

A 有编译器（能证伪"这写法没问题"），B 有另一个模型的先验（能证伪"这讲法讲清了"）。**互相攻击比互相确认有用。**

## 三、协作机制：`_handoff/` 文件协议

```text
note_maintained_by_myself/C++笔记本/
├─ AGENTS.md            ← Codex 进入本目录自动读到的规则
├─ _协作规范.md          ← 本文件
├─ _handoff/
│  ├─ TASK-<章号>.md     ← A 产出：自包含任务书（B 只读这个就能开工，不需要对话历史）
│  ├─ REVIEW-<章号>.md   ← A 产出：编译验证 + 结构审计的真实结果
│  ├─ FIX-<章号>.md      ← A 产出：逐条缺陷清单（B 按条修，不要自由发挥）
│  └─ ATTACK-<章号>.md   ← A 产出：要求 B 以"敌对方"身份攻击本章的清单
├─ 00_知识点总览.md       ← 覆盖表（A 维护，B 只读）
├─ 01a_三源交叉核对.md
├─ 01_*.md … NN_*.md      ← 正文（B 写，A 验）
└─ 99_标准库索引.md
```

### 3.1 任务书模板（A 产出 → B 消费）

```markdown
# TASK-<章号>：<章标题>

## 本章在知识网络中的位置
- 前置：<前哪些章/节的哪些能力>
- 本章解决：<一句话核心问题>
- 通向：<后面哪一章、为什么自然接上>

## 唯一主分类轴
<选定哪一根轴，为什么其它轴不能当主轴>

## 必须覆盖的覆盖表条目
| 条目 | 知识点 | 展开程度 |
|---|---|---|

## 允许的组织自由度 / 硬约束
- 允许：<可以合并哪些节、可以调整的顺序>
- 硬约束：C++17 基线；每个 cpp 块必须实跑；章末四件验收物齐全；跨章引用写实际节号

## 明确不要写进本章的内容（防止和别章重叠）
| 内容 | 归哪一章 |
|---|---|

## 交回标准
<B 交付时要一并报告的实测数字：编译了几个块、哪些块是故意失败的>
```

### 3.2 验收单模板（A 产出，附真实数字）

```markdown
# REVIEW-<章号>

## 编译实跑
- 命令：<原样贴>
- 块数：N ｜ 编译通过 M ｜ 预期编译失败 K ｜ 输出不符 J ｜ 警告 W
- 逐块结果表：<键 | 状态 | 差异>

## 结构审计
- [ ] 章首目录与正文 `##` 标题逐字一致（机检）
- [ ] 章末对账表覆盖全部条目，无幽灵条目
- [ ] 跨章引用全部命中目标章真实节号
- [ ] 同一级标题分类轴一致性（人工，逐节列判定）

## 实测缺口
<按覆盖表逐条列"这条没讲/没讲清/讲错了">
```

### 3.3 缺陷清单模板（A 产出 → B 修）

每条**必须**包含五要素，否则 B 会自由发挥、越修越偏：

```markdown
### FIX-<n>：<一句话现象>
- **位置**：文件 + 节号 + 约第几行
- **现象**：<编译器/脚本的真实输出，原样贴>
- **判据**：<为什么这是缺陷——引标准、引规范条目、或贴编译诊断>
- **修法**：<最小修改，不要顺手重写整节>
- **不许动**：<这一节里是对的、别一起改掉的部分>
```

### 3.4 对抗清单模板（A 产出 → B 攻击）

```markdown
# ATTACK-<章号>：请以审查者身份攻击这一章
不要确认它对，要**证伪**它。每个结论必须给可复现的依据。

1. 找出正文里所有"依赖具体实现才成立"的说法，逐条标注：
   - 哪些是**标准保证**（可移植）
   - 哪些是**实现定义**（换个编译器可能不同）
   - 哪些是**未定义行为**（程序已失去任何保证，不是"结果随机"）
2. 找出文中混层的小节：同一级标题里混了入口/机制/用途的，列出来并给重组方案。
3. 找出 C++17 范围内**该讲但整段缺失**的知识点，按重要性排序。
4. 找出文中"看起来等价但其实不同"的对比缺失（引用vs指针、初始化形式、值类别…）。
5. 检查每条断言能否被 MSVC 复现；不能复现的标出来。
```

### 3.5 `_handoff/` 的入库规矩

**任务书与验收单归档入库**（它是这套讲义"可追溯"的一部分：以后能看见哪一章是谁验的、当时数字多少）。
**临时编译产物不入库**：`.obj` / `.exe` / `.pdb` / 编译日志一律丢到仓库根 `tmp/`（已被 `.gitignore` 覆盖）。

## 四、三条可用的协作路径（按你的实际情况选）

### 路径 ①：Codex 外部终端 + 我内部验收（**推荐，本机唯一能跑通 Codex 的路**）

你在**普通 PowerShell 窗口**（不经 DSH）里让 Codex 写；我在 DSH 里编译验收。

```powershell
# 在普通 Windows PowerShell 里执行（不是 DSH 会话里）
cd C:\Users\Wang\Desktop\git\note_maintained_by_myself\C++笔记本

codex exec --sandbox workspace-write -C . `
  --output-last-message _handoff\RESULT-02.md `
  (Get-Content _handoff\TASK-02.md -Raw)
```

要点：

- `-C .` 把工作根指向正文目录，**Codex 会自动读到本目录的 `AGENTS.md`**，规则自动注入，你不需要每次贴规范。
- `--output-last-message` 把它的收尾报告落盘，我下一轮直接读文件，不占你的转述成本。
- 写完后你说一句"验收第 2 章"，我就跑编译+结构审计并产出 `REVIEW-02.md` / `FIX-02.md`，你再丢回给 Codex 修。
- **这构成闭环**：A 出任务书 → B 写 → A 验收 → B 按清单修 → A 复验。每轮只交换文件。

### 路径 ②：我全包（不依赖 Codex）

我在 DSH 内直接写正文并当轮实跑编译。**优点**：验证与写作同轮完成，不产生"没编译过的正文"。
**代价**：只有一个模型视角，对抗评审要显式安排（见路径 ③）。

### 路径 ③：用 DSH 子 agent 做对抗评审

我派子 agent 独立通读某一章，**只做攻击不做确认**（按 3.4 清单），我再把它报出的每条用编译器复核 ——
**复核不通过的 accusation 一律作废**。子 agent 的结论只有经过编译验证才允许进正文。

> ⚠️ 注意：子 agent 与我同源，观点相关性高，"独立视角"价值低于 Codex。
> 所以路径 ③ 是**兜底**，不是首选。
>
> ⚠️ 另注：**不能**把 Codex 换成"在 DSH 里起一个 codex 子进程"——见 1.1，那条路已实测封死。

## 五、交接的硬规矩

> **两条是实际跑过一轮之后补的**（2026-10-08，见 [`_handoff/REVIEW-01.md`](_handoff/REVIEW-01.md) 第八节）。
> 它们不是设想，是这一轮真出的问题。

1. **任务书必须自包含。** 假设 B 没有任何对话上下文，只给了它 `TASK-<章号>.md`。
2. **验收必须给数字。** "看起来没问题"不是验收结论；要说"37 块编译通过、2 块预期失败、0 块输出不符、4 条 `/W4` 警告"。
3. **缺陷清单只列事实，不列情绪。** 每条给可复现命令 + 真实输出。
4. **B 只改 `FIX` 清单里列出的位置**，不许顺手重排整章、不许顺手"优化"无关段落——那会让 A 的验收基线失效。
5. **每轮结束更新 `../_HANDOFF.md`**：新踩的坑、新的编译基线数字、覆盖表核销进度。这份文件是下一轮唯一的环境记忆。
6. **不提交、不推送**，等用户确认。

### 5.1 ⚠️ 交付物不全 = 本轮未完成（**新增，实战教训**）

**已真实发生**：一轮协作里 B 改了正文（改动是好的、验证全绿），但 **`RESULT-<章号>.md` 与
`ATTACK-<章号>-REPLY.md` 都没产出**。结果是：

> **正文变好了，但没人知道 B 发现了什么、攻击到了什么。**

这比"什么都没做"更麻烦——因为**验收方会以为一切正常**（数字全绿），
而实际上**对抗评审的结论整个丢失了**，下一轮还会重复踩同一个盲区。

**所以判据是：**

| 交付物 | 缺了怎么办 |
|---|---|
| `RESULT-<章号>.md` | ❌ **本轮不算完成**，即使正文全绿 |
| `ATTACK-<章号>-REPLY.md` | ❌ **本轮不算完成**（这份是"另一个模型的价值"所在） |
| 正文修改 | 可以有，但**不能替代上面两份** |

**为什么这么严**：A 侧的验证只能证明"没写错"，**证明不了"没漏掉该讲的"**。
后者只有 B 的独立视角能给。所以**报告不是形式主义，它是协作的全部产出**。

> **给 A 的提醒**：看到 `verify_cpp.py` 全绿就结案，是这一轮的真实错误倾向。
> **全绿只说明"已写的没写错"，不说明"该写的都写了"。** 这两件事必须分开核。

### 5.2 ⚠️ 中间产物一律放 `tmp/`，不得落在正文目录（**新增，实战教训**）

**已真实发生**：B 把正文备份写成 `C++笔记本/ch01_before_B.md`，
在正文目录里进进出出，导致链接检查间歇性报出"失效链接"的噪声。

- 那个文件内部的相对链接**本身没错**（它假设自己与 `00_知识点总览.md` 同级）
- **但它不该在正文目录里**——按 3.5 节，中间产物属于 `tmp/`（已被 `.gitignore` 覆盖）

**规矩**：备份、探针脚本、编译产物、日志、`results.json` 之类**一律写进仓库根 `tmp/`**。
**正文目录里只允许出现"讲义内容 + 规范文件 + `_handoff/`"**。

**为什么**：正文目录混进非正文文件后，所有"文件清单类"检查（链接、锚点、代码块扫描）
都会产生假阳性——**而假阳性会训练人忽略警告**，那比没有检查更糟。

## 五点五、⚠️ 阶段闸：审计必须针对冻结的快照（**新增，实战教训**）

**已真实发生**：B 在 A **正在写第 03–11 章的时候**启动了审计。后果：

- 它审计到的几章**随后又被改过**（它审的那一版已经不是最新版）
- 它要审计的另外几章**当时根本还不存在**
- 它的报告有一部分注定要返工——**不是因为 B 做错了，而是因为审计对象还在动**

**所以协议增加一条**：

> **审计必须针对一个冻结的快照。** 如果被审计的文件在审计期间还在变，
> 「你审的是哪一版」就成了无法回答的问题。

**落实方式**：`_handoff/RUN-STATE.md` 是**红绿灯**，
**优先级高于任何 `TASK-*.md`**：

| 灯 | 含义 | 外部 agent 该做什么 |
|---|---|---|
| 🔴 写作中 | 还有章节没写完 | **不要开工**，即使任务书已经发了 |
| 🟡 待审计 | 全部章节落地且通过编译验证 | 可以开工 |
| 🟢 审计轮 | 本轮专门请它审计 | 开工 |

**A 的职责**：每批章节落地后更新 `RUN-STATE.md` 第一节并**注明快照时间**。
**快照时间不是装饰**——它定义了「这次审的是哪一版」。

**同理**：B 开工时应**先记下各文件的修改时间**；万一期间有人改了文件，它能说清自己审的是哪一版。

## 六点五、⚠️ 不得覆盖已有交付物（**新增，2026-10-09 真实数据丢失事故**）

**已真实发生**：

| 时间 | 事件 |
|---|---|
| 2026-10-08 21:43 | Codex 写出 `_handoff/RESULT-02.md`，**104 747 字节**（含附录的完整第二轮审计） |
| 2026-10-09 10:22 | Codex 新一轮启动后**遭遇工具故障**，把同一个文件名**覆盖**成 547 字节的失败说明 |

**后果**：那份 104 KB 的审计报告被冲掉。
DSH 侧从 git 提交 `121cf58`（21:33 的快照）恢复了 **22 815 字节**的版本，
**结构完整但差额丢失**——损失的主要是「独立提取附录与最终验证」那一节的大型清单。
**已永久丢失，无法恢复。**

### 六点五.1 规矩

> **外部 agent 不得用同一个文件名覆盖已有交付物。**
>
> **写之前先看一眼目标文件有多大。**
> 如果它**明显大于**你要写的东西（比如你要写 500 字节的摘要，而目标有 100 KB），
> 那说明**那里面是别人的成果**——应当：
> ① 换一个文件名（如 `RESULT-02-<日期>-<轮次>.md`），或
> ② 先把它归档，再写。

### 六点五.2 更根本的教训：**工具故障也要保护已有成果**

那次事故的直接起因不是"写错了"，而是**会话在工具故障后仍去写了文件**。
所以规矩再加一条：

> **一轮开工时，如果目标交付物已存在，第一件事是「不覆盖」——
> 先读它、或先改名，再决定写什么。**

**"我这一轮没产出成果" 不应该以 "抹掉上一轮成果" 为代价。**

## 六、协作的第一条判据（先看这个，再看文笔）

每轮交接后，A 只问一个问题：

> **这一章的单块编译通过率是多少，输出比对是否 100% 一致？**
