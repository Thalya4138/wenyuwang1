# C++ 讲义 · Agent 协作规范

2026-10-10 按 v5 通用正式规范整合。仅在用户或适用任务明确要求协作时启用；单 Agent 维护也遵守成果保护要求。

## 一、现行原则与历史环境

2026-10 旧 DSH 会话曾尝试五种启动 Codex 方式，失败于 daemon 锁或命名管道访问。
该事实留作排障记录，不能推出永久不可运行或唯一协作路线；完整旧规范保留于本次备份。
本轮先核对权限、工具和可独立执行的能力，不依模型名称固定谁能编译。
分工目的在于独立检查与避免覆盖，多个模型同意不能代替标准、证明或实测证据。

## 二、角色与写入范围

| 角色 | 职责 |
|---|---|
| 本轮协调者 | 将用户授权写成自包含任务，指定文件、快照、验收和交付物 |
| 写作者 | 只改授权范围，实测受影响示例，提交完整结果记录 |
| 独立评审者 | 在冻结范围核对事实、结构、覆盖及证据，不静默扩大修改范围 |
| 验收负责人 | 独立复核缺陷与修复，更新状态；不因代码全绿而省略内容完整性检查 |

角色可由 DSH、Codex 或其他获授权 Agent 承担；同一轮同一文件只有一个写入者。
未明确授权时不发消息给其他聊天，也不创建用户可见的新聊天。

## 三、`_handoff/` 文件协议

- `RUN-STATE.md`：本轮任务、模式、范围、阶段、准确时间与快照。
- `TASK-NN.md`：自包含任务；写明目标读者、模式、来源、分类轴、前置知识、必须覆盖、允许及禁止文件。
- `RESULT-NN-日期-轮次.md`：改动、结构取舍、真实命令及统计、未验证项和剩余问题。
- `REVIEW-NN-日期-轮次.md` / `FIX-NN.md`：缺陷位置、依据、复现方式、最小修法及验收条件。
- `ATTACK-NN.md` 与 `ATTACK-NN-REPLY.md`：本轮明确要求对抗评审时交回；普通维护不强制制造两份报告。

任务书给出链接文件的相对位置和验收所用工作目录，不能假设接手者已有旧聊天。
验收分别列源码块数、输出一致、稳定前缀、预期失败、无预期、跳过、超时和意外失败；退出状态单独确认。
缺陷不能复现时记录“待核对”和双方依据，不以一次失败直接作废；语言保证查版本依据。

## 四、协作路径

可采用单方完成、文件交接、独立评审或按章隔离写作；以用户授权与本轮工具支持选择。
共享正文不允许互相覆盖；并行写作按文件、分支或 worktree 隔离，交接前检查任务边界。
不把启动另一产品作为完成笔记的必要条件，不因旧启动失败无限重试。

## 五、交接的硬规矩

1. 本轮任务自包含，未读来源不声称已核对。
2. 证据对应主张，真实统计与历史结果分开；正文完整性和运行正确性分别验收。
3. 修改局限于用户授权及任务清单，重排后同步目录、对账和入站引用。
4. 重要结果绑定快照，状态与任务模式一致；完成后销账，不让旧“待执行”继续生效。
5. 更新共用 `_HANDOFF.md` 时保留历史，并标明时间、环境与本轮验证范围。
6. 提交、推送、发布按用户明确授权；未授权不执行，已有授权不重复询问。

### 5.1 交付物完整性

用户要求的 RESULT、复核及对抗回复缺一件就是任务未完成；明确未安排对抗的维护不强制 ATTACK 文件。
报告要能独立说明范围、证据、已解决与未验证部分。代码全绿不证明应讲内容全部覆盖，更不证明无 UB。

### 5.2 中间产物位置

仓库任务的探针、源码备份、编译产物及日志放 Git 根 `tmp/` 的本轮独立子目录。
正文目录只承载讲义、规范与 `_handoff/` 正式交付物，避免备份被扫描造成误报。
外部 projectless 会话整理规范时使用该会话 `work/` 和 `outputs/`，不把临时成果放入正文目录。

## 五点五、任务闸与冻结快照

先读 [`_handoff/RUN-STATE.md`](_handoff/RUN-STATE.md)，再读相同编号及模式的任务书。
写作中只阻止针对该范围最终版的审计；放行对应任务后才能按其范围执行；已完成任务不再自动启动。
闸只约束对应任务，不能跨范围阻止用户明确授权的新任务；更换任务时先保护旧记录并更新状态。
用户授权的负责人更新状态，不固定某产品只读；同轮只由一人写状态。
冻结清单包含 HEAD 或逐文件 SHA256、准确时间与范围。审计中发现变化，重新限定报告或重建快照。
旧事故教训：边写边审使部分报告针对过期版本；仅记录修改时间不如保存哈希可靠。

## 六点五、⚠️ 不得覆盖已有交付物（**新增，2026-10-09 真实数据丢失事故**）

**已真实发生**：

| 时间 | 事件 |
|---|---|
| 2026-10-08 21:43 | Codex 写出 `_handoff/RESULT-02.md`，**104 747 字节**（含附录的完整第二轮审计） |
| 2026-10-09 10:22 | Codex 新一轮启动后**遭遇工具故障**，把同一个文件名**覆盖**成 547 字节的失败说明 |

**后果**：那份 104 KB 的审计报告被冲掉。
DSH 侧从 git 提交 `121cf58`（21:33 的快照）恢复了 **22 815 字节**的版本，
**结构完整但差额丢失**——损失的主要是「独立提取附录与最终验证」那一节的大型清单。
**已永久丢失，无法恢复。**

### 六点五.1 规矩

> **外部 agent 不得用同一个文件名覆盖已有交付物。**
>
> **写之前先看一眼目标文件有多大。**
> 如果它**明显大于**你要写的东西（比如你要写 500 字节的摘要，而目标有 100 KB），
> 那说明**那里面是别人的成果**——应当：
> ① 换一个文件名（如 `RESULT-02-<日期>-<轮次>.md`），或
> ② 先把它归档，再写。

### 六点五.2 更根本的教训：**工具故障也要保护已有成果**

那次事故的直接起因不是"写错了"，而是**会话在工具故障后仍去写了文件**。
所以规矩再加一条：

> **一轮开工时，如果目标交付物已存在，第一件事是「不覆盖」——
> 先读它、或先改名，再决定写什么。**

**"我这一轮没产出成果" 不应该以 "抹掉上一轮成果" 为代价。**

## 六、完成判据

来源与覆盖成立、结构及引用一致、示例按类别有证据、真实数字符合当前快照、所需报告齐全。
未验证项明确列出；不以“双方无异议”“输出一致”代替完整验收。
