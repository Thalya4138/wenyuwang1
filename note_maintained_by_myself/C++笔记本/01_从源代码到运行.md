## 0. 先记住的六件事

这一章信息量不小，但真正要带走的只有六条。后面所有内容都是它们的展开。

1. **C++ 程序不是"直接运行"的。** 你写的 `.cpp` 文件要先经过四个阶段，才变成操作系统能装载的东西。
2. **`#include` 是"把那个文件的全部内容原样复制到这里"。** 它不是"导入模块"，没有运行时开销，也没有名字空间概念。理解这一条，后面很多怪现象就通了。
3. **编译出错和链接出错是两类不同的错误。** 编译器逐个翻译单元地看代码；链接器才负责把它们拼起来。错误信息里出现 `LNK`（MSVC）或 `undefined reference`（GCC）就是链接阶段的错。
4. **警告不是"编译器太啰嗦"。** C++ 里大量"能编过但错了"的写法只有警告会提醒你。开 `/W4` 是习惯，不是洁癖。
5. **`main` 的返回值会变成程序的退出码**，`return 0;` 表示成功。这不是装饰，脚本和构建系统真的会读它。
6. **本机写 C++ 有一个必开的开关：`/utf-8`。** 不加它，源码里的中文会让编译器直接报错。原因在第 12 节。

> 如果只记一条，记第 2 条。它是本章其余内容的钥匙。

## 1. 一行文字是怎么变成一次运行的

先看一个最小事实。下面这个文件叫 `main.cpp`：

<!-- example:ch01_first -->
```cpp
#include <iostream>

int main() {
    std::cout << 3 + 4 << '\n';
}
```

<!-- result:ch01_first -->
```text
7
```

**先不用管任何语法**，只看它经历了什么：

```text
main.cpp （你写的文本文件，几个字节）
   │
   │ ① 预处理：把 #include 换成那个头文件的全部内容
   ↓
一个"展开后"的完整翻译单元（几万行）
   │
   │ ② 编译：把 C++ 翻译成汇编
   ↓
汇编代码（.asm，人类勉强能读）
   │
   │ ③ 汇编：把汇编翻译成机器指令
   ↓
目标文件 main.obj（含机器码，但还不能运行）
   │
   │ ④ 链接：把 main.obj 和标准库拼起来
   ↓
main.exe（操作系统能装载执行的文件）
   │
   │ ⑤ 运行
   ↓
终端打印 7
```

**这条链就是本章的主线。** 它回答的问题不是"怎么写 C++"，而是"我写的 C++ 到底发生了什么"。

为什么必须先讲这条链？因为后面几乎所有"莫名其妙"的现象都出在链的某一环：

| 现象 | 出在哪一环 |
|---|---|
| 头文件改一行，编出来的东西全变了 | ① 预处理——它是文本替换 |
| 报错说"找不到 `cout`"，但我明明 `#include <iostream>` 了 | ② 编译——`cout` 的名字在 `std` 里 |
| 报错说 `LNK2019: 无法解析的外部符号` | ④ 链接——声明有了，定义没找到 |
| 改了代码，运行结果没变 | ⑤ 运行——你跑的是上一次编出来的 `.exe` |
| 一个变量在两个 `.cpp` 里都定义了，报"重复定义" | ④ 链接——两个目标文件带了同名符号 |

**这条链不是 C++ 特有的**，C 也一样，Rust 和 Go 大体类似。区别在于 C++ 把这条链**暴露给你**了——很多语言把它藏起来（Python 直接 `python a.py`，中间步骤你看不见）。暴露有利有弊：你能控制每一环，也就必须理解每一环。

## 2. 拆分这条链：五个阶段各自在做什么

上面那张图把流程画成了一条线。现在把每个阶段拆开，说清它的**输入、输出、和边界**——因为初学者最常犯的错，就是把两个阶段的错误混为一谈。

| 阶段 | 输入 | 输出 | 它"看得见"什么 | 它的错误长什么样 |
|---|---|---|---|---|
| ① 预处理 | `.cpp` + 被 `#include` 的文件 | 展开后的翻译单元 | 只认 `#` 开头的指令，**不懂 C++ 语法** | `fatal error C1083: 无法打开源文件` |
| ② 编译 | 翻译单元 | 汇编 `.asm` | 一个翻译单元里的全部语法和类型 | `error C2065: 未声明的标识符` |
| ③ 汇编 | `.asm` | 目标文件 `.obj` | 汇编指令 | 极少出错，通常是编译器 bug |
| ④ 链接 | 若干 `.obj` + 库 | `.exe` | **符号表**，不是源码 | `error LNK2019: 无法解析的外部符号` |
| ⑤ 运行 | `.exe` | 输出 + 退出码 | 什么都不"看"，它就在跑 | 崩溃、输出不对、退出码非 0 |

**最关键的一行是第 ④ 行的最后一格。** 链接器**看不到你的源码**，它只看目标文件里的符号表：谁定义了 `main`、谁定义了 `std::cout` 相关的东西、谁引用了没定义的符号。

这就解释了 C++ 里一个反复出现的现象——**同一个名字要写两遍**：

```cpp
// 这是"声明"：告诉编译器有这么一个函数，参数和返回类型是什么
int add(int a, int b);

// 这是"定义"：真正给出函数体
int add(int a, int b) { return a + b; }
```

编译器（阶段 ②）只需要看到**声明**就能编过——它相信你后面会给定义。
链接器（阶段 ④）才去找**定义**；找不到就报 `LNK2019`。

> **为什么语言要这样设计？**
> 因为编译是**逐个翻译单元独立进行**的。编译器处理 `a.cpp` 时不会去看 `b.cpp`，它只知道"有这么个函数存在"。
> 这个设计带来了编译速度（可以并行编译不同文件）和增量构建（只重编改过的文件），
> 代价就是：**你必须手动维护"声明在哪、定义在哪"的一致性**。
> C++20 的模块（modules）想解决的正是这个代价，但它超出了本讲义的基线。

## 3. 预处理：在编译器看代码之前发生了什么

### 3.1 最小例子：看着 `#include` 真的展开一次

**不要凭想象理解"展开"**。本机可以直接让它把展开结果打出来。用这个文件 `expand.cpp`：

<!-- example:ch01_expand_src -->
```cpp
#include <iostream>

int main() {
    std::cout << "hi\n";
}
```

<!-- result:ch01_expand_src -->
```text
hi
```

MSVC 的 `/P` 开关表示"预处理完就停，把结果写出来"：

```powershell
cl /nologo /std:c++17 /utf-8 /P expand.cpp
```

它生成一个 `expand.i`。**这个文件的体积会告诉你一切**（本机实测）：

```text
expand.cpp  : 61 字节
expand.i    : 2 522 251 字节（约 2.4 MiB），85 972 行
膨胀倍数    : 约 41 000 倍
```

**一个 61 字节的文件，展开成 2.4 MB。** `#include <iostream>` 做的事情就是把那个头文件里的所有文本原样插进这里，
而 `<iostream>` 又包含了别的头文件，层层展开。**"文本替换"不是比喻，是字面事实。**

> ⚠️ **坑**：以为 `#include` 像 Python 的 `import`。
> 它**不是**"导入一个模块、获得它的名字"。它是**纯文本替换**——
> 预处理阶段结束后，`#include` 这一行就不存在了，取而代之的是被包含文件的全部内容。
> 所以头文件里写什么，就等于你在那一行手打了什么。这也意味着**头文件的顺序会影响编译结果**。

### 3.2 预处理指令：真正由预处理处理的只有这些

C++ 里以 `#` 开头的东西都由**预处理器**处理。常用的就几个：

| 指令 | 作用 | 现在要掌握吗 |
|---|---|---|
| `#include` | 文本插入 | ✅ 必须 |
| `#define` | 宏定义（文本替换） | ✅ 认识即可，**别用它定义常量** |
| `#ifdef` / `#ifndef` / `#endif` | 条件编译 | ✅ 认识，头文件保护要用 |
| `#pragma` | **标准指令**，但具体效果由实现定义 | ⚠️ 见下方说明 |
| `#undef` / `#error` / `#line` | 少见 | 以后再说 |

> ⚠️ **`#pragma` 是标准指令，不是"非标准的东西"。**
> 标准规定了它的**语法**，但**具体效果由实现定义**；遇到它不认识的 `#pragma`，实现**应当忽略**。
> 所以 `#pragma once` 本身是"某个实现提供的具体语义"——**它很常见，但不是标准的头文件保护方式**。
> 标准的做法是头文件保护宏（`#ifndef` / `#define` / `#endif`），第 05 章会讲。
>
> **本讲义初稿曾把 `#pragma` 写成"非标准"，这是错的**（由另一个 agent 的对抗评审指出，
> 见 [`_handoff/RESULT-01.md`](_handoff/RESULT-01.md)）。**标准与"实现约定"的边界要分清**——
> 这正是第 13 章那张"标准保证 / 实现定义 / 未指定 / 未定义"对照表的用途。

**`#define` 的坑值得现在就说清**，因为它是"看起来等价、实际不同"的典型。下面这段本机实跑过：

<!-- example:ch01_macro -->
```cpp
#define SQUARE(x) x * x
#include <iostream>

int main() {
    std::cout << SQUARE(1 + 2) << '\n';
    std::cout << SQUARE((1 + 2)) << '\n';
}
```

<!-- result:ch01_macro -->
```text
5
9
```

**两行只差一对括号，结果从 5 变成 9。** 用 `/P` 把展开结果打出来，真相一目了然：

```text
std::cout << 1 + 2 * 1 + 2 << '\n';        ← SQUARE(1 + 2) 展开成这个
std::cout << (1 + 2) * (1 + 2) << '\n';    ← SQUARE((1 + 2)) 展开成这个
```

第一行按 C++ 优先级算是 `1 + (2*1) + 2 = 5`。**这不是编译器出错，是宏做了它被要求做的事**：
纯文本替换，它不懂运算优先级、不懂类型、不懂作用域。

正确写法要加括号 `#define SQUARE(x) ((x) * (x))`，但更好的做法是根本别用它——

```cpp
// 这是 C++ 的写法：有类型、有作用域、能被调试器看见
constexpr int square(int x) { return x * x; }
```

**为什么这样更好**：宏在预处理阶段就被替换掉了，所以在调试器和错误信息里
**你只看得到展开后的样子**（上面那两行就是证据）；而 `constexpr` 函数是真正参与编译的代码，有类型检查。
**能用语言设施就别用预处理器**——这是现代 C++ 的共识。

> **顺带一个观察**：上面输出里的 `5` 和 `9` 会让人以为"宏有时候对有时候错"。
> 准确说法是**宏从来没错，是人的预期错了**——它一直是文本替换，只是这次替换出的表达式恰好不是你想算的那个。

## 4. 编译与汇编：从 C++ 到机器指令

这一阶段做两件主要的事：

1. **语法与语义检查**——你的代码是不是合法的 C++，类型对不对，名字有没有声明过。
2. **生成代码**——翻译成目标架构的汇编，再做优化。

### 4.1 让编译器把汇编打出来看看

MSVC 用 `/FA` 让编译器留下汇编：

```powershell
cl /nologo /std:c++17 /utf-8 /FA /c simple.cpp
```

看一个极小的例子：

```cpp
int add(int a, int b) {
    return a + b;
}
```

**本机实跑** `cl /nologo /std:c++17 /utf-8 /FA /c simple.cpp` 之后，`simple.asm` 里这个函数长这样：

```asm
PUBLIC	?add@@YAHHH@Z					; add
; Function compile flags: /Odtp
_TEXT	SEGMENT
a$ = 8
b$ = 16
?add@@YAHHH@Z PROC					; add
; File ...\simple.cpp
; Line 1
	mov	DWORD PTR [rsp+16], edx
	mov	DWORD PTR [rsp+8], ecx
; Line 2
	mov	eax, DWORD PTR b$[rsp]
	mov	ecx, DWORD PTR a$[rsp]
	add	ecx, eax
	mov	eax, ecx
; Line 3
	ret	0
?add@@YAHHH@Z ENDP					; add
_TEXT	ENDS
```

**这段汇编里有四件事值得注意**，它们都验证了本节的说法：

1. **函数名不是 `add`，是 `?add@@YAHHH@Z`。** 这叫**名字修饰**（name mangling）——
   C++ 把参数类型编进了符号名（`YAHHH` 大致表示"返回 `int`，接受两个 `int`"）。
   **这就是 C++ 支持函数重载的底层机制**：两个同名但参数不同的函数，在符号表里是不同的名字。
   第 05 章「函数」会展开讲重载。

2. **参数不是"传进函数"，而是先被搬到栈上再取回来**：
   `mov DWORD PTR [rsp+16], edx` 把第二个参数存到栈，`mov DWORD PTR [rsp+8], ecx` 存第一个，
   然后 `mov eax, ...` / `mov ecx, ...` 又把它们取回寄存器。
   **这是未优化（`/Odtp`）的结果**。开优化后这几条会被消掉。

3. **`/Odtp` 是"调试用、不优化"的标记。** 因为这里没写优化开关，编译器默认按调试模式生成。
   所以**你现在看到的汇编不代表程序"真实的效率"**。

4. **源码行号被写进了汇编**（`; Line 1`、`; Line 2`）。这是后面调试器能把机器指令对应回源码行的依据。

> **这一段的教学目的不是让你看懂汇编**，而是建立一个判断：
> **你写的 C++ 和你最终执行的机器码之间，隔着一个会做大量改写的编译器。**
> 所以"我这样写性能不好"这类判断，不能靠猜——`13` 章会讲怎么看。

### 4.2 编译的边界：一个翻译单元

关键概念在这里出现：

> **编译是以「翻译单元」(translation unit，简称 TU) 为单位进行的。**
> 一个 `.cpp` 经过预处理后，就是一个翻译单元。
> **在普通的分别编译下，编译器一次只处理一个翻译单元，不靠另一个 `.cpp` 的源码
> 来完成当前翻译单元的名字查找。**
>
> ⚠️ **为什么不说「永远看不到」**：MSVC 的 `/GL`（全程序优化）与 GCC/Clang 的 LTO
> 能让**优化器跨翻译单元**看代码。但它改变的是**优化能力**，**不改变名字查找规则**——
> 该写声明的地方仍然必须写，否则照样 `LNK2019`。
> **所以「必须写声明」的原因不是「编译器绝对看不见」，而是语言规定分别编译。**

这个事实的直接后果：

```cpp
// ===== a.cpp =====
int add(int a, int b) { return a + b; }

// ===== b.cpp =====
int main() {
    int x = add(1, 2);   // ← 编译 b.cpp 时，add 是什么？
}
```

编 `b.cpp` 会报"未声明的标识符 `add`"。不是 `add` 不存在，而是**编译器处理 `b.cpp` 时根本不知道 `a.cpp` 里有什么**。

修法是给 `b.cpp` 一个**声明**：

```cpp
// ===== b.cpp =====
int add(int a, int b);   // 声明：承诺"有这么个函数，长这样"

int main() {
    int x = add(1, 2);    // 编译能过了；链接时再去 a.obj 里找定义
}
```

**这就是"声明与定义分离"的出发点。** 它不是为了好看，而是被"编译器一次只看一个翻译单元"这个约束逼出来的。

⚠️ 注意：这里演示的是**概念**。真正把两个文件编到一起需要链接命令，本章第 10 节会完整做一遍；两个 `.cpp` 一起编译的完整流程在第 05 章「函数」里实跑。

### 4.3 目标文件里有什么

编译完得到 `.obj`（MSVC）或 `.o`（GCC/Clang）。它不是"半个程序"，而是一个**带符号表的结构化文件**：

| 部分 | 内容 |
|---|---|
| 机器码 | 函数体翻译后的指令 |
| 符号表 | 我**定义**了哪些名字（`add`），我**引用**了哪些名字（`std::cout` 相关） |
| 重定位信息 | "这个位置现在填的是占位符，链接时要改成真正的地址" |
| 调试信息 | 需要显式开关（`/Zi` 或 `/Z7`）才有**完整**的源码级调试信息 |

链接器就是靠**符号表**工作的。所以链接错误的信息里总是有名字（符号），而不是源码行号。

## 5. 链接：把目标文件拼成可执行文件

链接器拿到一组目标文件和库，做三件事：

1. **符号解析**——每个"引用"找到唯一的"定义"。
2. **重定位**——把占位符地址换成真实地址。
3. **合并**——把各段拼成最终的可执行文件布局。

### 5.1 两类链接错误，认准它们

| 错误形态 | 含义 | 常见原因 |
|---|---|---|
| `LNK2019: 无法解析的外部符号`（MSVC）<br>`undefined reference to 'xxx'`（GCC） | **引用了但没人定义** | 忘了把某个 `.cpp` 加进编译；函数只写了声明；拼错了库名 |
| `LNK2005: 已经在 xxx.obj 中定义`（MSVC）<br>`multiple definition of 'xxx'`（GCC） | **定义了不止一次** | 把函数定义写进了头文件，而这个头文件被多个 `.cpp` 包含 |

**第二条特别值得记**：这是"头文件里能写什么"这个问题的核心。

```cpp
// ===== util.h =====
int add(int a, int b) {    // ⚠️ 函数体写在头文件里
    return a + b;
}
```

```cpp
// ===== a.cpp =====
#include "util.h"          // 展开后：a.cpp 里有了 add 的定义

// ===== b.cpp =====
#include "util.h"          // 展开后：b.cpp 里也有了 add 的定义
```

两个翻译单元各自都有一个 `add` 的定义。**预处理是文本替换，它不知道"这个函数应该只有一个"**。链接器一看有两个同名定义，报错。

这是 C++ 里**最经典的"直觉与实际不符"**：你脑子里"头文件是一份共享的代码"，而在预处理器眼里"头文件是要被复制进每个包含它的文件的一段文本"。

修法有两种，第 05 章会展开：

```cpp
// 修法一：头文件只放声明，定义放某个 .cpp
// util.h
int add(int a, int b);
// util.cpp
int add(int a, int b) { return a + b; }
```

```cpp
// 修法二：加 inline，告诉编译器"允许多个翻译单元有同一份定义"
// util.h
inline int add(int a, int b) { return a + b; }
```

> ✅ **哪来的信心说这是真问题**：`LNK2005` / `multiple definition` 是 C++ 教学中复现率最高的错误之一，
> 成因就是上面这条链路。本章第 10 节会用真实文件复现这两类错误并贴真实诊断——
> **本节现在只讲机制，实测证据在第 10 节。**

## 6. 正式动手：写、编译、运行第一个程序

前面五节都在讲"会发生什么"。现在真的做一遍。

### 6.1 第一步：创建源文件

新建一个目录（比如 `cpp_learn`），在里面建 `main.cpp`，内容：

<!-- example:ch01_first_program -->
```cpp
#include <iostream>

int main() {
    std::cout << 3 + 4 << '\n';
}
```

<!-- result:ch01_first_program -->
```text
7
```

### 6.2 第二步：理解这个程序在说什么

先逐个符号交代清楚，**不默认你已经知道**（这是本讲义的规矩）：

| 符号 | 在这里的作用 |
|---|---|
| `#include` | 预处理指令，不是运行时调用。把 `<iostream>` 的内容插进来 |
| `<iostream>` | 标准头文件，`std::cout` 等输入输出设施声明在这里 |
| `int` | `main` 返回整数，这个整数会成为程序退出码 |
| `main` | **你自己代码的入口**。注意：操作系统装载 `.exe` 后先进的是**运行库的启动函数**，它再来调 `main` |
| `()` | 参数列表。这里是空的，表示不接受参数 |
| `{}` | 函数体，围住要执行的东西 |
| `std` | 命名空间（namespace）。标准库的东西都放在 `std` 里 |
| `::` | 作用域解析。`std::cout` 读作"`std` 里的 `cout`" |
| `cout` | 标准输出流（character output） |
| `<<` | **在这里是"流插入"运算符**，不是左移 |
| `3 + 4` | 表达式，先算出 7 |
| `'\n'` | 一个字符字面量，表示换行 |
| `;` | 表达式语句结束 |

**两个最容易误解的地方：**

**(1) `<<` 在这里不是位左移。** 同一个符号在不同上下文有不同含义：
- 两个整数之间：`1 << 3` 是位左移（得 8）
- 左边是流、右边是值：`std::cout << 8` 是"把 8 送进输出流"

编译器靠**左边的类型**来选。这叫运算符重载，第 07 章讲。

**(2) `std::` 不能省。** 你也可以写 `using namespace std;` 然后直接用 `cout`，但**入门阶段不建议**：
标准库里有很多短名字（`count`、`distance`、`size`、`data`），`using namespace std;` 会把你自己的同名变量卷进冲突里，
报出的错误会非常难懂。**先养成写 `std::` 的习惯**，理由在 07 章讲完名字查找后你会更认同。

### 6.3 第三步：编译并运行

本机（Windows 11）装的是 **Visual Studio Build Tools 2026**：工具集目录版本是 **14.51.36231**，
`cl /Bv` 自报的编译器内部版本是 **19.51.36256.0**。这是两套编号，不是哪个写错了。
它的编译环境**不在 PATH 里**，必须先"初始化"一次：

```powershell
# PowerShell 里，先初始化编译环境，再编译运行
$vcvars = "C:\Program Files (x86)\Microsoft Visual Studio\18\BuildTools\VC\Auxiliary\Build\vcvars64.bat"
cmd /c "`"$vcvars`" >nul 2>&1 && cd /d . && cl /nologo /std:c++17 /EHsc /W4 /utf-8 main.cpp /Fe:main.exe && main.exe"
```

输出：

```text
main.cpp
7
```

第一行 `main.cpp` 是 `cl` 报告"我编译了哪个文件"。第二行 `7` 是程序自己的输出。

**这里要建立的第一条判断**：`main.cpp` 那行**不是程序的输出**，是编译器的输出。区分这两者很重要——
以后遇到"输出里多了奇怪的东西"，先问"这是谁打的"。

### 6.4 注释：两种形式，以及一个不能嵌套的坑

C++ 只有两种注释：

<!-- example:ch01_comments -->
```cpp
#include <iostream>

// 单行注释：从 // 到本行末尾
int main() {
    std::cout << 1 << '\n';   /* 块注释：可以写在一行中间 */
    /* 也可以
       跨很多行 */
    std::cout << 2 << '\n';
}
```

<!-- result:ch01_comments -->
```text
1
2
```

| 形式 | 范围 | 常见用途 |
|---|---|---|
| `//` 单行注释 | 到本行末尾 | 解释一行代码；**临时注释掉一行** |
| `/* */` 块注释 | 从 `/*` 到最近的 `*/` | 跨行说明；注释掉一整段 |

> ⚠️ **坑：块注释不能嵌套。**
> `/* ... /* ... */ ... */` 里，**第一个 `*/` 就结束了整个注释**，
> 后面剩下的 `... */` 又变成了代码，于是报出一堆和注释毫无关系的语法错误。
>
> **为什么**：注释不是"括号配对"结构，词法阶段的做法是"找到第一个 `*/` 就收工"。
> 所以**要临时屏蔽一大段代码，正确做法是逐行用 `//`**，
> 或者用条件编译（`#if 0` / `#endif`，第 3 节讲过预处理指令）。
>
> 这类错误的判别属于**词法/语法类**，不是类型错误——但报错位置往往离真凶很远。

**注释不参与编译**：它在**翻译阶段 3**（词法分析之前的处理）就被替换成一个空格。
所以 `int/*x*/a;` 和 `int a;` 等价——注释的作用是"分词时不把它当记号"，
而不是"编译时忽略"。第 3.1 节介绍的 `/P` 展开结果里看不到注释，也是同一个原因。

### 6.5 三个"没发生的事"，也要说清

- **没有 `return 0;`。** `main` 是特殊的：到达函数体末尾等价于 `return 0;`。**别的返回 `int` 的函数没有这个待遇**——不写 `return` 是未定义行为。
- **没有先"编译"再"运行"两条命令。** 上面用 `&&` 串起来了，是一条命令。分开写也完全可以，而且调试时更好：
  ```powershell
  cl /nologo /std:c++17 /EHsc /W4 /utf-8 main.cpp /Fe:main.exe   # 只编译
  .\main.exe                                                      # 只运行
  ```
- **生成的 `main.exe` 不会自己跑。** 它只是一个文件，静静躺在那儿。**这是"忘记重新编译"这个坑的来源**，第 12.4 节讲。

### 6.6 一次真实的完整编译输出

上面贴的输出是 `cl` 正常情况下的样子（只有文件名 + 程序输出）。
**实际编译时经常还会看到警告**——`/W4` 的价值就在这里。真实例子：

<!-- example:ch01_unused_warn -->
```cpp
#include <iostream>

int main() {
    int unused = 5;          // 定义了但从未使用
    std::cout << 1 << '\n';
}
```

<!-- result:ch01_unused_warn -->
```text
1
```

**程序照跑不误**（输出 `1`），但编译时你会看到：

```text
unused.cpp
unused.cpp(4): warning C4189: "unused": 局部变量已初始化但不引用
```

注意三点：

1. **这是 `warning` 不是 `error`**，程序照样编译出来并正常运行。**"跑起来了"和"写对了"是两件事。**
2. **警告编号是 `C4189`**。顺带说清：**未初始化的**未使用变量是另一个编号 `C4101`（"未引用的局部变量"）——
   两个码不一样，别记混。
3. **行号 `(4)` 指的是变量声明那一行**，不是文件里的绝对位置——你在自己文件里写的行号可能不同。

> **这就是为什么 `/W4` 不是洁癖。** 一个"定义了但没用"的变量通常意味着**你忘了用它**
> （比如想赋值却写成了新变量），编译器是唯一会提醒你的东西。

`warning C4101` 是 MSVC 的警告编号。**记住这个格式**：`文件(行号): warning 编号: 描述`。
`error` 也是同样的格式，第 8 节专门讲怎么读它。

## 7. 编译器开关：四个你必须认识的选项

编译器开关（option/flag）很多，但入门只需要先认清四个。以下都给出 MSVC 与 GCC/Clang 的对应写法——
**⚠️ 本机只装了 MSVC，GCC/Clang 那一列未经本机实测**，是从文档对照来的，我会在需要时标明。

| 目的 | MSVC | GCC / Clang | 为什么必须认识 |
|---|---|---|---|
| 选语言标准 | `/std:c++17` | `-std=c++17` | 不写就可能用到比目标标准更新的特性，换环境编不过 |
| 开警告 | `/W4` | `-Wall -Wextra -pedantic` | C++ 里"能编过但错了"太多，警告是主要防线 |
| 指定源与执行字符集 | `/utf-8` | 默认即 UTF-8 | **本机不写它，中文源码直接编译失败**（第 12 节实测） |
| 输出文件名 | `/Fe:main.exe` | `-o main.exe` | 显式指定，避免"我运行的到底是哪个文件" |

### 7.1 为什么"选语言标准"这条容易踩坑

C++ 有好几个版本，**语法和库都在变**：

| 标准 | 常用新东西 |
|---|---|
| C++11 / 14 | `auto`、范围 `for`、lambda、智能指针、`nullptr` |
| **C++17（本讲义基线）** | 结构化绑定、`std::optional` / `variant` / `string_view`、`if constexpr`、折叠表达式 |
| C++20 | 概念 `concepts`、范围 `ranges`、`std::format`、`<=>`、模块 |
| C++23 | `std::print`、`std::expected`、`<flat_map>` 等 |

**不写 `/std:` 会怎样**：MSVC 默认不一定是最新标准，而 GCC 历史上默认过 `gnu++14` / `gnu++17`。
后果是**同一份代码在你机器上能编、在判题机上编不过**（或反过来）。这在算法竞赛里极其常见。

> 本讲义以 **C++17** 为基线。C++20/23 的特性只在明确标注「C++20 起」的地方出现，
> 并且会说明"本机支持但基线不含"。理由：C++17 是课程、判题机、企业既有代码的共同交集。

### 7.2 `/EHsc` 是什么

上面命令里还有个 `/EHsc`。它选择**标准 C++ 异常处理模型**。在 MSVC 里不写它会得到警告
`C4530: 使用了 C++ 异常处理程序，但未启用展开语义`。

**入门阶段照抄就行**，第 08 章「错误处理」会解释异常、栈展开是什么。

### 7.3 一个可复用的编译脚本

每次打一长串命令很烦。把这些开关固化下来是好习惯。**但注意工具链的差别**——同一个脚本换机器就不通用了。

```powershell
# build.ps1 —— 放在源码目录里，以后用 .\build.ps1 编译
param([string]$Src = "main.cpp", [string]$Out = "main.exe", [string]$Std = "c++17")

$vcvars = "C:\Program Files (x86)\Microsoft Visual Studio\18\BuildTools\VC\Auxiliary\Build\vcvars64.bat"
if (-not (Test-Path $vcvars)) { throw "找不到 vcvars64.bat，先改这个脚本里的路径" }

cmd /c "`"$vcvars`" >nul 2>&1 && cd /d `"$PWD`" && cl /nologo /std:$Std /EHsc /W4 /utf-8 $Src /Fe:$Out"
```

> ⚠️ **坑**：这个脚本把 `vcvars64.bat` 的路径写死了。
> VS 版本一变（2022 → 2026）、装的版本不同（Community / BuildTools），路径就不同。
> 更稳的做法是用 `vswhere.exe` 去问，但那是 `13` 章「构建系统」的内容。
> **现在知道"路径会变"这件事本身，就够了。**

## 8. 读诊断信息：error 和 warning 不是一回事

### 8.1 格式

MSVC 的诊断有固定格式：

```text
文件名(行号): error C####: 描述
文件名(行号): warning C####: 描述
```

GCC/Clang 是：

```text
文件名:行号:列号: error: 描述
```

**先看文件与行号，再看编号，最后才读描述。** 描述偶尔会误导（尤其模板错误），但位置几乎从不骗人。

### 8.2 error 与 warning 的本质区别

| | 含义 | 编译器会怎么做 |
|---|---|---|
| `error` | **这个翻译单元不能形成合法的程序** | 停止，不生成目标文件 |
| `warning` | 编译器**选择继续**，但代码**不一定合法或正确** | 继续，生成目标文件 |

> ⚠️ **别把 `warning` 读成「这段代码没问题」。**
> `error` 的含义很明确：**这个翻译单元不合格，标准不要求实现接受它。**
> 但反过来不成立——**实现可以在代码不合格、甚至是未定义行为的地方，只给个警告就放过去。**
> `13` 章第 2 节会实测：一段同时踩了六个未定义行为的代码，`/W4` 下只报了三条无关警告。
>
> **准确的说法是**：`error` = 实现拒绝；`warning` = 实现接受了，但认为你该看一眼。
> **被接受和正确之间没有等号** —— 这就是本章反复强调「能编过不等于对了」的原因。

**建议**：入门阶段把所有警告当作错误处理。MSVC 可以用 `/WX`（warning as error）做到这一点：

```text
/WX      把警告当错误
/W4      最高常用警告等级（/Wall 太吵，不实用）
```

**本机实测**：对上面那段"未初始化变量"的代码加 `/WX`，警告确实被拦下了：

```text
C:\...\uninit.cpp(4) : error C2220: 以下警告被视为错误
C:\...\uninit.cpp(4) : warning C4700: 使用了未初始化的局部变量"x"
```

注意两件事：**它变成 `error C2220`**（"以下警告被视为错误"），
**但原来的 `warning C4700` 仍然打出来**——因为编译器要把原因告诉你。
**而且目标文件不再生成**（实测：`uninit_wx.exe` 不存在）。这就是"把警告当错误"的实际效果。

### 8.3 三行诊断里的"洋葱"：一次报很多错

编译器出错后**常常继续报下去**，于是你看到 20 个 error。其中绝大多数是第一个错误的**连锁反应**。

> ⚠️ **坑**：从第一个错误开始看。
> 一个漏掉的分号、一个拼错的名字，可能让编译器在之后每一行都报"语法错误"。
> **不要从最后一条开始改**——你会发现改完最后一条，前面 19 条还在。
>
> 具体做法：只处理最上面一条，重编，再看还剩几条。数字会很快降下来。

## 9. 程序的退出码与命令行参数

### 9.1 退出码：`main` 的返回值真的有人读

`return 0;` 不只是形式。程序结束时返回的整数叫**退出码**（exit code），操作系统和调用它的东西都看得到。

```powershell
.\main.exe
echo "退出码 = $LASTEXITCODE"
```

> ⚠️ **注意**：`$LASTEXITCODE` 是 **PowerShell 变量**，写 `echo "退出码 = $LASTEXITCODE"` 时
> 它会被替换成数字。如果你在 `.bat` 里写，那要用 `%ERRORLEVEL%`；在 Git Bash 里是 `echo $?`。

约定：

| 退出码 | 惯例含义 |
|---|---|
| `0` | 成功 |
| 非 0 | 失败（具体值由程序自己定义） |

**为什么这件事重要**：构建系统、脚本、CI 全靠它。一个"看起来跑完了"的程序如果返回非 0，
自动化流程会认为它失败。反过来，一个明明出错却 `return 0` 的程序会**静默地骗过所有自动化检查**。

本机的实测事实（在编译验证脚本里已经用到）：**编译失败时 `cl` 返回非 0**。
所以脚本里可以用 `&&` 串联"编译成功才做下一步"：

```powershell
cl ... && main.exe      # 只有编译返回 0，才运行
```

### 9.2 命令行参数：`argc` 与 `argv`

`main` 可以接受参数：

<!-- example:ch01_main_args_shape -->
```cpp
int main(int argc, char* argv[]) {
    // argc: 参数个数（标准保证非负）
    // argv: 参数字符串数组；argv[0] 是程序名，argv[argc] 是空指针
}
```

<!-- result:ch01_main_args_shape -->
```text
```

**这段的 `result` 是空的**——它只验证"这个签名能编过"，不产生输出。关于这两个参数，标准保证的是下面四条
（**本机实测过前两条**）：

| 保证 | 内容 |
|---|---|
| ① | **`argc` 非负** —— ⚠️ **不是"至少为 1"** |
| ② | **`argv[argc]` 是空指针**（这是个哨兵，所以能写 `for (char** p = argv; *p; ++p)` 遍历） |
| ③ | `argc > 0` 时 `argv[0]` 是程序名（**取不到名字时是空串，不是空指针**） |
| ④ | `argv[0]` 到 `argv[argc-1]` 指向的字符串**是可以修改的** |

**本机实测这两个可直接观察的事实**：

```cpp
#include <cstdio>
int main(int argc, char** argv) {
    std::printf("argc=%d\n", argc);
    std::printf("argv[argc]==nullptr: %d\n", argv[argc] == nullptr);
    if (argc > 0) std::printf("argv[0]=%s\n", argv[0]);
}
```

真实输出：

```text
argc=1
argv[argc]==nullptr: 1
argv[0]=argc.exe
```

**改写参数字符串也是允许的**（本机实测）：

```cpp
#include <cstdio>
int main(int argc, char** argv) {
    if (argc > 1) { argv[1][0] = 'X'; std::puts(argv[1]); }
}
```

用 `argc.exe abc` 运行时真实输出：

```text
Xbc
```

**编译 0 警告、运行退出码 0。** 所以"`argv` 里的字符串不能改"是个常见但错误的说法——
**能改的是字符内容；不能做的是让 `argv` 各元素指向别处**（那个数组本身由实现管理）。

> ⚠️ **这一节曾经写错过，值得留个记录**：本讲义初稿写的是"`argc` 至少是 1"，
> 那是**错的**——标准只保证**非负**，`argc == 0` 是允许的（宿主环境不提供程序名时）。
> 这个错误是被另一个 agent 的对抗评审抓出来的（见 [`_handoff/RESULT-01.md`](_handoff/RESULT-01.md)）。
> **留在这里是为了说明一件事：连"总觉得就是这样"的常识也要去查标准。**

> ⚠️ **坑**：拿别的语言的经验套 C++。
> 很多语言（包括某些教材）说"`argv[0]` 一定是程序名、字符串不能改"。
> 标准给的是上表那四条**精确**保证，**比"常识版"要弱、也更绕**。
> 遇到这类"大家都这么说"的断言，值得去 cppreference 上核一眼。

### 9.3 命令行参数怎么读出来（放到第 09 章）

参数的具体内容、怎么解析（`std::string` / `std::string_view` / `std::stoi`）属于字符串那部分，
第 09 章会合起来讲。**这里只需要知道"入口处能拿到参数，以及标准对它们保证了什么"。**

## 10. 源文件、头文件、翻译单元：它们不是同一件事

这三个词经常被混着用，但它们是三个不同层次的概念：

| 词 | 是什么 | 谁看得见 |
|---|---|---|
| **源文件** (source file) | 磁盘上的 `.cpp` 文本 | 人、编辑器、预处理器 |
| **头文件** (header) | 通常 `.h` / `.hpp`，被 `#include` 的文本 | 人、编辑器、预处理器 |
| **翻译单元** (TU) | **一个 `.cpp` 预处理展开后的完整内容** | 编译器 |

**关系**：

```text
main.cpp ──┐
           ├─ #include "util.h" 的展开内容
util.h ────┘
           ↓
      翻译单元（编译器看到的全部）
           ↓ 编译
       main.obj
```

所以"头文件"和"翻译单元"不是并列关系：**头文件是翻译单元的组成部分**。

### 10.1 亲手复现两类链接错误

这是本章最值得动手的一节，因为它把第 3 节的"文本替换"讲成了可验证的事实。

**准备四个文件：**

```cpp
// ===== util.h =====
int add(int a, int b);          // 只声明

// ===== util.cpp =====
#include "util.h"
int add(int a, int b) { return a + b; }   // 定义

// ===== main.cpp =====
#include <iostream>
#include "util.h"
int main() { std::cout << add(1, 2) << '\n'; }
```

**正确编译（两个 `.cpp` 都参与）：**

```powershell
cl /nologo /std:c++17 /EHsc /W4 /utf-8 main.cpp util.cpp /Fe:app.exe
.\app.exe
```

真实输出：

```text
main.cpp
util.cpp
正在生成代码...
3
```

（前两行与"正在生成代码..."是**编译器**的输出，`3` 才是**程序**的输出——回到第 6.3 节那个判断。）

**错误一：忘了把 `util.cpp` 交给编译器。**

```powershell
cl /nologo /std:c++17 /EHsc /W4 /utf-8 main.cpp /Fe:app.exe
```

**编译成功，链接失败**——这就是"声明与定义分离"的代价。真实诊断：

```text
main.cpp
main.obj : error LNK2019: 无法解析的外部符号 "int __cdecl add(int,int)" (?add@@YAHHH@Z)，函数 main 中引用了该符号
  已定义且可能匹配的符号上的提示:
    "bool __cdecl __crt_strtox::add(struct __crt_strtox::big_integer &,unsigned int)" (?add@__crt_strtox@@YA_NAEAUbig_integer@1@I@Z)
app_bad.exe : fatal error LNK1120: 1 个无法解析的外部命令
```

注意三点：**错误前缀是 `LNK`**（不是 `C`，那是编译器）；
**报的是符号名 `?add@@YAHHH@Z`**（第 4 节讲的名字修饰）；
而且链接器还好心提示了一个**名字相似但不匹配**的符号——**这种"提示"经常把人带偏**，
它只是列出符号表里长得像的，不是"你可能想用这个"。

**错误二：把头文件里的声明改成定义。**

```cpp
// ===== util_noinline.h =====
int add(int a, int b) { return a + b; }   // 定义写在头文件里
```

让 `main2.cpp` 和 `util2.cpp` **都** `#include` 这个头文件，然后一起编译。真实诊断：

```text
main2.cpp
util2.cpp
正在生成代码...
util2.obj : error LNK2005: "int __cdecl add(int,int)" (?add@@YAHHH@Z) 已经在 main2.obj 中定义
app_dup.exe : fatal error LNK1169: 找到一个或多个多重定义的符号
```

**注意编译阶段一声不响就过了**（两个翻译单元各自都是合法的 C++），
问题只在链接阶段暴露：两个目标文件都带了 `?add@@YAHHH@Z` 这个符号。

修法有两种，第 05 章会展开：

```cpp
// 修法一：头文件只放声明，定义放某个 .cpp
// util.h
int add(int a, int b);
// util.cpp
int add(int a, int b) { return a + b; }
```

```cpp
// 修法二：加 inline，告诉编译器"允许多个翻译单元有同一份定义"
// util.h
inline int add(int a, int b) { return a + b; }
```

> **这两条真实诊断是本讲义"可验证"的最直接证据**——
> 它们不是从别处抄来的错误信息，是按上面命令在本机跑出来的。
> 你完全可以自己复现一遍：文件内容、命令、预期诊断都在这一节里。

## 11. 调试：没有图形界面时怎么办

先说清楚本机的现实：**这台机器没有安装命令行调试器 `cdb`，也没有 `gdb`。**
（实测：`C:\Program Files (x86)\Windows Kits\10\Debuggers\x64\cdb.exe` 不存在。）
所以本节**不提供调试器实操的实测输出**——给不了的东西不假装给。

那还能做什么？有三件事现在就能用，而且它们覆盖了初学者 80% 的调试需求。

### 11.1 第一件：看退出码（已实测可用）

**先看一个正常返回的例子。** 下面这个程序把 `argc`、`argv[0]` 打出来，然后 `return 3;`：

```cpp
#include <iostream>

int main(int argc, char* argv[]) {
    std::cout << "argc = " << argc << '\n';
    std::cout << "argv[0] = " << (argv[0] ? argv[0] : "(null)") << '\n';
    return 3;
}
```

```text
argc = 1
```

> **这个块保留为手动运行示例，不加自动验证标记。** 它打印 `argv[0]`，输出随启动方式和构建目录变化，
> 不满足本轮任务要求的「完整输出确定」。下面保留 A 的真实运行样例；它不计入确定输出的单块验证基线。

在 PowerShell 里再看它交出的退出码：

```powershell
& .\main.exe
"退出码 = $LASTEXITCODE"
```

本机真实结果（路径依你的构建目录而变）：

```text
argc = 1
argv[0] = C:\Users\Wang\Desktop\git\tmp\cppenv\exitprobe.exe
退出码 = 3
```

**这次实测顺便演示了第 9.2 节那几条标准的区别**——这里要小心区分"标准保证"与"本机现象"：

| 观察 | 归属 |
|---|---|
| `argc = 1` | ⚠️ **本机这次调用**的结果（没有额外参数）。**标准不保证它一定是 1**，只保证非负 |
| `argv[0]` **不是 null** | ✅ 这次调用满足 `argc > 0`，所以 `argv[0]` 是程序名（标准保证） |
| `argv[0]` 是**完整路径** | ⚠️ **实现定义**——标准只说它是"程序名"，**没说含不含路径**。换个启动方式可能只有文件名 |

**这正是第 9.2 节那张表的用途**：同一次运行里，"标准保证的"和"本机碰巧如此的"混在一起，
**必须分开看**。写跨平台代码时，只有第一列右边有 ✅ 的才能依赖。

**再看一次崩溃。** 让程序解引用空指针：

```cpp
int main() {
    int* p = nullptr;
    *p = 1;               // 空指针解引用：未定义行为，本机表现为访问冲突
    return 0;
}
```

运行后 PowerShell 里的 `$LASTEXITCODE` 是：

```text
-1073741819
```

**这个数字的三种写法是同一个值**（本机实测换算）：

| 形式 | 值 |
|---|---|
| 有符号十进制 | `-1073741819` |
| 无符号十进制 | `3221225477` |
| 十六进制 | `0xC0000005` |

`0xC0000005` 是 Windows 的 **访问冲突**（access violation）状态码——最典型的指针/数组越界症状。

> ⚠️ **坑**：**不要以为"崩溃码是个固定数字"。**
> 它是**平台特定的**：`0xC0000005` 是 Windows 的说法，Linux 上同样的错误是被信号杀死（`SIGSEGV`，
> shell 报告为 `139`），而你根本拿不到 `$LASTEXITCODE` 这种变量。
> 更要紧的是——**空指针解引用是未定义行为，不是"一定会产生这个码"**。
> 标准只保证"程序已失去任何保证"，具体表现（崩溃、静默继续、打出垃圾值）由实现和环境决定。
> `13` 章会给一张常见崩溃码对照表，并解释 UB 与"崩溃"的关系。

### 11.2 第二件：把中间状态打出来

最古老也最有效的方法。加临时输出：

<!-- example:ch01_debug_print -->
```cpp
#include <iostream>

int main() {
    int value = 42;
    std::cout << "[debug] value = " << value << '\n';   // ← 临时
}
```

<!-- result:ch01_debug_print -->
```text
[debug] value = 42
```

**两个注意事项**：

- **输出流是有缓冲的。** 如果程序崩溃，缓冲区里的内容可能还没打出来，你会以为"没执行到"。
  用 `std::cerr`（无缓冲）或加 `std::endl` 可以强制刷新。
  ```cpp
  std::cout << "[debug] before crash" << std::endl;   // endl 会刷新缓冲
  ```
  > `std::endl` 与 `'\n'` 的区别（一个会刷新缓冲区、一个是纯换行字符）在第 09 章展开。
- **`#ifdef` 包起来**，发布时能一次关掉：
  ```cpp
  #ifdef DEBUG_TRACE
      std::cout << "[debug] value = " << value << '\n';
  #endif
  ```

## 12. Windows 特有的坑

这一节全部是本机（Windows 11 + 代码页 936）实测的。**换系统这些坑会变，所以标清楚环境。**

### 12.1 坑一：中文源码不加 `/utf-8` 直接编译失败

**现象**：源文件里有中文注释或中文字符串，编译报错：

```text
warning C4819: 该文件包含不能在当前代码页(936)中表示的字符。请将该文件保存为 Unicode 格式以防止数据丢失
error C2001: 字符串字面量中的换行符
error C3688: 文本后缀"..."无效
error C2143: 语法错误: 缺少";"
```

**原因**：这是本章最值得理解的一个坑，因为它把"预处理是文本处理"讲成了可复现的事实。

- 本机控制台的活动代码页是 **936（GBK）**。
- **MSVC 默认按系统代码页解释源文件**，即它以为你的 `.cpp` 是 GBK 编码的。
- 但你的文件实际是 **UTF-8**（现代编辑器默认）。
- 于是一段 UTF-8 的中文注释，在 GBK 眼里是**另一串字节**。如果这串字节里恰好含有 `\` 这样的字符，
  它就和后面的内容凑成了"续行"或"转义"，把整行结构打乱——所以报的错是"字符串字面量中的换行符"，
  **看起来和中文毫无关系**。

**处理**：加 `/utf-8`，告诉编译器"源文件是 UTF-8，执行字符集也用 UTF-8"。

```powershell
cl /nologo /std:c++17 /EHsc /W4 /utf-8 main.cpp /Fe:main.exe
```

> ⚠️ **这个坑的教训比修法更重要**：编译器报错的位置和原因**可能离真正的问题很远**。
> 报 `C2001` 说"字符串里换行"，真因却是"编码标注错了"。
> 遇到"这个错误在这行根本没道理"时，先怀疑**环境/编码/包含关系**，别死磕那一行。

### 12.2 坑二：控制台输出的中文乱码

**现象**：程序编译运行成功，但输出到终端的中文是乱码。

**原因**：程序按一种编码写出字节，终端按另一种编码解释。这是**两端的编码不一致**，
和源文件编码是两件独立的事。

**判断方法**：如果加了 `/utf-8` 后源码能编过、输出也正常，说明这条链是通的；
如果编过但输出乱码，问题在**运行时**的终端侧，不在编译期。

> **本机实测**：加 `/utf-8` 后，中文源代码 + 中文字符串输出**正常显示**，
> 即使控制台代码页仍是 936。完整例子与真实输出在第 09 章「字符串与 IO」里给（那里才是讲编码的地方）。

### 12.3 坑三：路径与反斜杠

Windows 路径用反斜杠 `\`，而 `\` 在 C++ 字符串里是**转义字符**：

```cpp
const char* p = "C:\new\test.txt";   // ⚠️ \n 变成换行，\t 变成制表符
```

`\n` 是换行、`\t` 是制表符，所以这个字符串根本不是你以为的路径。三种处理：

```cpp
const char* a = "C:\\new\\test.txt";       // 转义反斜杠（C 风格）
const char* b = R"(C:\new\test.txt)";      // 原始字符串字面量（C++11 起，推荐）
```

第三种 `R"(...)"` 是**原始字符串字面量**：里面的反斜杠不再转义。第 09 章会完整讲字符串字面量。

### 12.4 坑四：`.exe` 扩展名与运行方式

- Windows 下可执行文件必须有 `.exe`，而且在 PowerShell 里运行当前目录的程序**必须写 `.\`**：
  ```powershell
  .\main.exe      # ✅
  main.exe        # ❌ PowerShell 不会在当前目录找
  ```
  这是因为 PowerShell 出于安全考虑不把当前目录放进搜索路径。**Git Bash 里则要写 `./main.exe`。**

- **改了源码忘了重新编译**，跑的还是旧 `.exe`。这是本章第 1 节第五行的那个现象，也是初学者最常"见鬼"的原因。
  **判断方法**：看 `.exe` 的修改时间是不是早于 `.cpp`。

## 13. 本章自测

> 答案折叠在下面。**题目是验收工具，不是练习册**——做不出来说明对应小节需要重读。

**1.** 下面这条命令里，`main.cpp` 和 `7` 分别是谁输出的？

```text
main.cpp
7
```

<details><summary>答案</summary>

`main.cpp` 是**编译器 `cl`** 输出的（它在报告"我编译了哪个文件"）；`7` 是**程序自己**输出的。

这个区分很重要：以后看到"输出里多了奇怪的东西"，先问"这是谁打的"。
</details>

**2.** 为什么 `#include <iostream>` 不是 Python 的 `import`？请从"哪个阶段处理它"和"它做了什么"两方面说。

<details><summary>答案</summary>

- **阶段**：它由**预处理器**处理，在编译器看到代码之前。Python 的 `import` 是运行时（或至少是编译期模块系统）行为。
- **做了什么**：它是**纯文本替换**——把 `<iostream>` 的全部内容原样插入到这一行的位置。

所以预处理结束后，`#include` 这行就不存在了，取而代之的是几万到上百万字节的文本。
推论：头文件里的内容就等于你在那一行手打的；头文件的顺序会影响编译结果。
</details>

**3.** 报错 `LNK2019: 无法解析的外部符号 "int __cdecl add(int,int)"`，属于哪个阶段？可能的原因是什么（说两个）？

<details><summary>答案</summary>

属于**链接阶段**（第 ④ 环）。`LNK` 是 MSVC 链接器的错误前缀。

可能原因：
1. **忘了把定义所在的 `.cpp` 加进编译命令**——声明有了，定义没进目标文件。
2. **函数只写了声明，没写定义**（或者定义的签名和声明不一致，比如参数类型不同，那就是另一个符号了）。
3. 定义在某个库里，但忘了把这个库交给链接器（更进阶的情形）。
</details>

**4.** 头文件里写了 `int add(int a, int b) { return a + b; }`，两个 `.cpp` 都 `#include` 它，会出什么错？为什么？

<details><summary>答案</summary>

链接时报**重复定义**（MSVC：`LNK2005`；GCC：`multiple definition of 'add'`）。

**因为预处理是文本替换，它不知道"这个函数应该只有一个"。**
两个 `.cpp` 各自的翻译单元里都出现了 `add` 的定义，于是两个目标文件都带上同一个符号，
链接器发现同一符号有多个定义，报错。

两种修法：① 头文件只放声明、定义放某个 `.cpp`；② 加 `inline`。
</details>

**5.** 下面这段代码有什么问题？编译会不会通过？

```cpp
#include <iostream>
int main() {
    int x;
    std::cout << x << '\n';
}
```

<details><summary>答案</summary>

**编译会通过**（`x` 是合法声明的 `int`，类型正确），但**行为是错的**：`x` 没有被初始化，
读它的值是**未定义行为**——结果不可预测，不是"随机数"，而是**程序已失去任何保证**。

开 `/W4` 时 MSVC 会给 `warning C4700: 使用了未初始化的局部变量"x"`。
**这就是"警告不是噪音"的典型例子**：它是标准规定的合法行为和你实际意图之间的唯一提示。

正确写法：`int x{};`（值初始化为 0）或 `int x = 0;`。第 02 章第 5 节会对照常见初始化形式。
</details>

**6.** 源文件里写了中文注释，编译报 `error C2001: 字符串字面量中的换行符`，但那一行根本没有字符串。为什么？

<details><summary>答案</summary>

因为**真因是编码，不是那一行**。

本机控制台代码页是 936（GBK），而 **MSVC 默认按系统代码页解释源文件**。你的文件实际是 UTF-8，
于是 UTF-8 的中文字节在 GBK 眼里是另一串字节；这串字节里若含 `\` 之类字符，就会和后面内容凑成
"续行"或"转义"，把整行结构打乱——报出来的错就成了"字符串字面量中的换行符"。

**处理**：编译时加 `/utf-8`。

**教训**：编译器报错的位置和原因可能离真正的问题很远。遇到"这错误在这行根本没道理"，先怀疑环境/编码/包含关系。
</details>

**7.** 在 PowerShell 里敲 `main.exe` 报"无法将...识别为 cmdlet"，但文件明明就在当前目录。为什么？该怎么写？

<details><summary>答案</summary>

因为 **PowerShell 出于安全考虑，不把当前目录放进命令搜索路径**——它只在 `PATH` 里找。
所以裸名 `main.exe` 找不到，**必须写 `.\main.exe`**。

**本机实测三种写法**（`main.exe` 确实存在于当前目录）：

| 写法 | 结果 |
|---|---|
| `main.exe` | ❌ `术语 'main.exe' 不会被识别为 cmdlet、函数、脚本文件或可执行程序的名称。` |
| `.\main.exe` | ✅ 输出 `ok` |
| `cmd /c main.exe` | ✅ 输出 `ok`（**cmd.exe 会搜当前目录**） |

**所以"要不要加 `.\`"是 shell 的查找规则差异，不是 C++ 语言规则。**
Git Bash 里对应写 `./main.exe`。

（这是平台/工具差异，不是你的代码问题。）
</details>

**8.** 为什么 C++ 里同一个函数常常要写两遍（一次声明、一次定义）？这个设计换来了什么？

<details><summary>答案</summary>

因为**编译是以「翻译单元」为单位独立进行的，编译器一次只看一个 `.cpp`**。
处理 `b.cpp` 时它看不到 `a.cpp` 里有什么，所以需要**声明**告诉它"有这么个东西、长什么样"；
真正的**定义**由链接器在阶段 ④ 去找。

换来的是：
- **可并行编译**不同 `.cpp`
- **增量构建**——只重编改过的文件

代价是：你必须手动维护"声明与定义一致"，否则就是 `LNK2019`。
C++20 的模块想解决这个代价，但超出了本讲义基线。
</details>
