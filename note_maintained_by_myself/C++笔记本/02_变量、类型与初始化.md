## 0. 先记住的六件事

1. **C++ 是静态类型语言。** 每个对象在**编译期**就有一个确定的类型，类型决定了它占多少字节、能做哪些运算。
2. **"变量"这个词在 C++ 里的正式叫法是对象。** 对象 = 一块存储 + 一个类型 + 一个当前值。
3. **初始化不是赋值。** `int a = 5;` 和 `int b; b = 5;` 看着结果一样，但前者叫初始化、后者叫赋值，两者对类类型的行为完全不同（第 07 章会看到）。
4. **花括号初始化 `{}` 更安全**，因为它会**拒绝窄化转换**（把可能丢信息的转换变成编译错误）。这是 C++11 起推荐它的唯一理由。
5. **不写初始化的局部变量，值是不确定的。** 读它是未定义行为——**不是"随机数"**。这是初学者最常见的 UB 来源。
6. **有符号和无符号混用会比较出反直觉的结果**，因为编译器会做类型转换。第 10 节有可复现的例子。

> 如果只记一条，记第 5 条。它会真实地让程序时对时错。

## 1. 对象、类型、值：三个最基础也最容易被含糊过去的词

先把三个词定死，因为后面所有内容都在它们之上。

| 词 | 英文 | 在 C++ 里指什么 |
|---|---|---|
| **对象** | object | 一块**存储区域**，有类型、有当前值、有名字（也可以没名字） |
| **类型** | type | 规定这块存储**怎么解释**、**能做哪些运算**、**可能取哪些值** |
| **值** | value | 那块存储里**此刻**装的东西 |

三者的关系是：**类型给存储加了一层解释规则。** 同一串二进制位，按 `int` 解释是一个整数，按 `float` 解释是一个小数，按 `char` 解释是一个字符——**位没变，解释变了**。

### 1.1 最小例子：一个对象的一生

<!-- example:ch02_object -->
```cpp
#include <iostream>

int main() {
    int count = 3;             // 声明并初始化一个对象
    std::cout << count << '\n';
    count = 5;                 // 改它的值，不换对象
    std::cout << count << '\n';
}
```

<!-- result:ch02_object -->
```text
3
5
```

**执行轨迹**（本章的规矩：讲清程序到底先做什么）：

```text
1. main 开始
2. 在栈上分配一块够装 int 的存储，起名 count      ← 这一步叫"声明"
3. 把 3 写进那块存储                              ← 这一步叫"初始化"
4. 读出 count 的值，交给 cout                     → 打印 3
5. 把 5 写进同一块存储（不是新建一块）             ← 这一步叫"赋值"
6. 再读出来                                       → 打印 5
7. main 结束，那块存储自动回收（栈对象的生存期到此为止）
```

**第 2 步和第 5 步的区别是关键**：声明只发生一次（创建对象），赋值可以发生无数次（改值）。
很多初学者把两者混为一谈，到第 07 章学类的时候就会撞墙——因为**类对象的初始化会调用构造函数，赋值会调用赋值运算符，是两个不同的函数**。

### 1.2 为什么必须是静态类型

C++ 在**编译期**就要知道每个对象的类型。这带来两个直接后果：

**好处：**
- 运算在编译期就能检查（`"abc" + 1` 这种错误编译期就报）
- 类型信息可用于生成更快的代码（不需要运行时查类型）
- 很多错误不用等到运行才发现

**代价：**
- 你必须**显式写出类型**（或者用 `auto` 让编译器推导）
- 类型不匹配时要处理转换问题（第 9、10 节专门讲）

对比一下你熟悉的 Python：Python 的对象在**运行期**才知道类型，`x = 1` 之后还能 `x = "s"`。
C++ 里 `int x = 1;` 之后 **`x` 永远装整数**，装不下别的。

> **这不是"C++ 更死板"，而是"错误发生在哪个阶段"的选择。**
> 静态类型把错误提前到编译期；动态类型把灵活性留到运行期。两者都有代价，只是代价不同。

## 2. 基本类型：计算机能直接摆弄的几种东西

C++ 的基本类型（fundamental types）分四组：

| 组 | 类型 | 用途 |
|---|---|---|
| 整数 | `short` `int` `long` `long long`（各有 `unsigned` 版本） | 计数、下标、位操作 |
| 字符 | `char` `signed char` `unsigned char` `wchar_t` `char16_t` `char32_t` | 单个字符、字节 |
| 布尔 | `bool` | 真假 |
| 浮点 | `float` `double` `long double` | 小数、科学计算 |

### 2.1 `int` 家族：为什么有四种大小

直觉上"整数就是整数"，为什么要分四种？

> **因为 C++ 不规定每种类型的确切宽度，只规定"不小于"和"相对大小"。**
> 这是 C++ 为了适配不同硬件架构做的设计：有的机器 16 位运算最自然，有的 64 位。

标准的要求是（大意）：

```text
sizeof(char) == 1                      ← 恒成立，char 是"一个字节"的定义
sizeof(short) <= sizeof(int) <= sizeof(long) <= sizeof(long long)
sizeof(int) >= 2 字节
```

**"`sizeof(char) == 1` 恒成立"这件事值得停下来想一下**：它不是说"字符占 8 位"，
而是说 **`char` 的大小被定义为"一个字节"**——而"字节"在 C++ 里就是"`char` 那么大的存储单位"。
大多数平台上它确实是 8 位，但**标准只说"一个字节"**。

### 2.2 字符类型：`char` 是最容易误解的一个

| 类型 | 装什么 |
|---|---|
| `char` | 一个"窄字符"。**它是有符号还是无符号由实现决定**（MSVC 上默认有符号） |
| `signed char` | 明确有符号，范围至少 −127…127 |
| `unsigned char` | 明确无符号，范围至少 0…255。**常用来表示"原始字节"** |
| `wchar_t` | 宽字符（Windows 上 16 位） |
| `char16_t` / `char32_t` | UTF-16 / UTF-32 码元（C++11 起） |

> ⚠️ **坑**：以为 `char` 一定是无符号的，于是写 `char c = 200;` 再 `c > 0`。
> **`char` 的有符号性由实现决定**——MSVC 上默认是**有符号**，200 存进去会变成负数。
> 要表示 0–255 的字节，用 `unsigned char`（或 C++17 的 `std::byte`，第 10 章讲）。
> 这类错误的判别属于**类型类**，而且它**不会报错**，只是结果不对。

### 2.3 `bool`：不是"0 和 1 的别名"

`bool` 是独立类型，只有 `true` 和 `false` 两个字面量。但**它能隐式转换成整数**（`true` → 1，`false` → 0），
反过来整数也能隐式转成 `bool`（**非 0 转 `true`，0 转 `false`**）。

**这个双向隐式转换是很多"看起来对"的代码的根源**——第 9、10 节会展开。

### 2.4 浮点：`float` / `double` / `long double`

| 类型 | 典型宽度 | 什么时候用 |
|---|---|---|
| `float` | 4 字节 | 大量数据、精度要求不高（图形、机器学习张量） |
| `double` | 8 字节 | **默认选择**。字面量 `1.5` 就是 `double` |
| `long double` | 8 或 16 字节（依实现） | 特殊精度需求，跨平台行为差异大 |

**浮点精度问题是独立话题**，第 03 章会专门讲为什么 `0.1 + 0.2 != 0.3`。这里只需要建立一条判断：

> **能用整数就别用浮点。** 计数、下标、货币（换算成最小单位）都应该用整数。
> 浮点只用在"本质上就是连续量"的地方。

## 3. 宽度、范围与 `sizeof`：类型到底占多少

### 3.1 本机实测：每种类型多大

<!-- example:ch02_sizes -->
```cpp
#include <iostream>

int main() {
    std::cout << sizeof(char) << ' ' << sizeof(short) << ' '
              << sizeof(int) << ' ' << sizeof(long long) << '\n';
    std::cout << sizeof(bool) << ' ' << sizeof(float) << ' '
              << sizeof(double) << ' ' << sizeof(long double) << '\n';
    std::cout << sizeof(int*) << ' ' << sizeof(unsigned) << '\n';
}
```

<!-- result:ch02_sizes -->
```text
1 2 4 8
1 4 8 8
8 4
```

**读这张输出表**（单位是字节）：

| 表达式 | 本机结果 |
|---|---|
| `sizeof(char)` | 1 |
| `sizeof(short)` | 2 |
| `sizeof(int)` | 4 |
| `sizeof(long long)` | 8 |
| `sizeof(bool)` | 1 |
| `sizeof(float)` | 4 |
| `sizeof(double)` | 8 |
| `sizeof(long double)` | **8**（⚠️ 注意这条） |
| `sizeof(int*)` | 8（64 位程序里指针都是 8 字节） |
| `sizeof(unsigned)` | 4（和 `int` 一样，只是解释方式不同） |

> ⚠️ **坑**：`sizeof(long double)` 在这台机器上是 **8**，和 `double` 一样。
> 这意味着**在本机 MSVC 上 `long double` 并不比 `double` 精度高**。
> 这不是 bug——标准只要求它"不小于 `double`"。**在 Linux/GCC 上它通常是 16 字节。**
>
> **所以千万别把"`long double` 精度更高"当成可移植的事实来依赖。**
> 这段输出本身就是"平台差异"最好的例子。
>
> **怎么自己确认真实精度**：用 `std::numeric_limits<long double>::digits10`，而不是看 `sizeof`。

> ⚠️ **另一个坑**：`sizeof` 的结果是 **`std::size_t` 类型（无符号）**。
> 所以 `sizeof(int) - 5` 不会得到 `-1`，而会回绕成一个巨大的正数。
> 这正是第 10 节要讲的"有符号/无符号混用"。

### 3.2 范围：类型能装下哪些值

宽度决定了**能表示多少个不同的值**。整数的范围算法很简单：

```text
无符号 n 字节：  0                      … 2^(8n) − 1
有符号 n 字节：  −2^(8n−1)              … 2^(8n−1) − 1
```

4 字节 `int` 就是 −2 147 483 648 … 2 147 483 647（约 ±21 亿，这就是"`int` 会溢出"的常见话题）。

**不要手算这些数**——用标准库查：

```cpp
#include <limits>
std::numeric_limits<int>::max()        // int 的最大值
std::numeric_limits<int>::min()        // int 的最小值
std::numeric_limits<unsigned>::max()   // unsigned 的最大值
```

> **一条经验**：算法题里 `n` 最大到 10^5、答案最大到 10^18 这类判断，
> 不能靠"我用 `int` 应该够吧"，要**按类型的范围去算**。这是 `13` 章错误排查的常见起因。

### 3.3 定宽类型：需要确切宽度时怎么办

如果代码**必须**用 8 位、32 位这种确切宽度（写二进制文件格式、做位运算协议、跨平台数据交换），
基本类型不够可靠——因为标准没定死宽度。这时用 `<cstdint>`：

| 类型 | 含义 |
|---|---|
| `std::int8_t` / `uint8_t` | 确切 8 位 |
| `std::int16_t` / `uint16_t` | 确切 16 位 |
| `std::int32_t` / `uint32_t` | 确切 32 位 |
| `std::int64_t` / `uint64_t` | 确切 64 位 |

**什么时候该用它们**：

- ✅ 需要确切宽度时（文件格式、网络协议、硬件寄存器）
- ✅ 需要无符号且宽度明确时（哈希、位掩码）
- ❌ **不要**因为"看起来更精确"就到处用它。日常计数用 `int`、索引用 `std::size_t` 更自然，
  而且 `int8_t`/`uint8_t` 参与运算时会被**整型提升**成 `int`，反而带来意外（第 9 节讲提升）。

## 4. 声明与定义：为什么同一个名字要写两遍（入门版）

第 01 章讲过这条链的**机制**（编译器逐个翻译单元工作）。这里补上**语法层面**的样子。

### 4.1 两种语句

<!-- example:ch02_decl_vs_def -->
```cpp
#include <iostream>

// 这是定义：分配了存储，有初值
int counter = 0;

// 这是声明，不是定义（extern 说明"定义在别处"）
extern int elsewhere;

int main() {
    counter = 7;
    std::cout << counter << '\n';
}
```

<!-- result:ch02_decl_vs_def -->
```text
7
```

| | 声明 | 定义 |
|---|---|---|
| 告诉编译器"有这么个名字、它是什么类型" | ✅ | ✅ |
| 真正**分配存储**（变量）或**给出函数体**（函数） | ❌ | ✅ |
| 一个翻译单元里能有几个 | 可以重复多次 | **只能有一次** |

**判据（变量）**：**没有 `extern` 且没有初始化器的就是定义吗？** 不对——这条规则要小心：

```cpp
int a;              // 定义（默认初始化，对全局变量是全零）
extern int b;       // 声明（不是定义）
extern int c = 5;   // 定义！（有初始化器就不算"纯声明"）
```

**判据（记住这个）**：**带 `extern` 且不带初始化器 → 声明；其余情况 → 定义。**

### 4.2 为什么入门阶段就要知道这个

因为它直接决定**你能不能把代码拆到多个文件**：

```cpp
// 头文件里写：            ← 所有包含它的 .cpp 都会看到这句
extern int counter;        // ✅ 声明，可以出现在多个翻译单元

// 头文件里写：
int counter = 0;           // ❌ 定义，多个 .cpp 包含就会"重复定义"（第 01 章 LNK2005）
```

**读法**：第 01 章讲的是"为什么会报 `LNK2005`"（机制），这里讲的是"怎么写才不报"（写法）。
两节合起来才是完整的。

> **一个更省事的办法**：C++17 起可以用 `inline` 变量，直接写在头文件里也不会重复定义。
> 这是 C++17 的新增能力，第 `12` 章讲。**现在先记住"头文件放声明、定义放 .cpp"这条基本规则。**

## 5. 初始化：C++ 里最容易踩的一处"看起来一样"

**这一节是本章的核心。** 同规格的 Python 笔记里，这一节的对应物是"可变 vs 不可变"——
都是那种"看着无所谓、其实决定程序对不对"的基础概念。

### 5.1 先看现象：四种写法，一个输出

<!-- example:ch02_init_forms -->
```cpp
#include <iostream>

int main() {
    int a = 42;        // 拷贝初始化
    int b(42);         // 直接初始化
    int c{42};         // 列表初始化（花括号）
    int d{};           // 空花括号：值初始化为 0
    int e;             // ⚠️ 默认初始化：值不确定
    std::cout << a << ' ' << b << ' ' << c << ' ' << d << '\n';
}
```

<!-- result:ch02_init_forms -->
```text
42 42 42 0
```

编译时会有**一条警告**（本机实测）：

```text
main.cpp(8): warning C4101: "e": 未引用的局部变量
```

**先注意一件事**：警告说的是 `e` **未被引用**，不是"未初始化"。
因为编译器发现 `e` 从头到尾没被读过，所以它没抱怨未初始化——**它只是提醒你写了个没用的东西**。
一旦你真的去读 `e`，警告就会变成 `C4700`（第 01 章出现过）。**这就是"警告要看，但不能只看警告"的例子。**

### 5.2 六种初始化形式（覆盖表说的"多种"到底是哪些）

cppreference 的「初始化」一栏列了九种。入门阶段需要分清的是这六种：

| # | 名称 | 写法 | 关键点 |
|---|---|---|---|
| 1 | 默认初始化 | `int a;` | **局部变量：值不确定**；全局/静态：全零 |
| 2 | 值初始化 | `int a{};` `int a = int();` | **一定被初始化**（基本类型得 0） |
| 3 | 拷贝初始化 | `int a = 42;` | 用 `=`。名字不表示一定调用拷贝构造；类类型还要看重载与 C++17 的保证省略规则（第 12 章第 4 节） |
| 4 | 直接初始化 | `int a(42);` | 用 `()`。**允许窄化转换** |
| 5 | 列表初始化 | `int a{42};` | 用 `{}`。**拒绝窄化转换**，最安全 |
| 6 | 聚合初始化 | `Point p{1, 2};` | 用 `{}` 按顺序初始化成员（第 07 章讲） |

**为什么 3 和 4 要分开**：对基本类型它们没区别；但对**类类型**，
拷贝初始化要求"能从右边构造出左边"（可能涉及隐式转换），直接初始化则直接调构造函数。
**这个差别在第 07 章学类的时候会变得非常重要**，现在只需要知道"它们是两种形式"。

### 5.3 列表初始化的价值：拒绝窄化

这是 `{}` 存在的**唯一硬理由**。所谓**窄化转换**（narrowing conversion），
就是"可能丢信息"的隐式转换——比如把 `double` 塞进 `int`、把大整数塞进小整数。

<!-- example:ch02_narrow -->
```cpp
#include <iostream>

int main() {
    double pi = 3.14159;
    // int lossy{pi};     // ← 取消注释会编译失败
    int explicit_cast = static_cast<int>(pi);
    std::cout << explicit_cast << '\n';
}
```

<!-- result:ch02_narrow -->
```text
3
```

**把注释那行取消，会发生什么**（这是本节最该记住的实验，请自己试一次）：

```cpp
int lossy{pi};      // ❌ error C2397: 从 "double" 到 "int" 的转换需要收缩转换
int lossy(pi);      // ✅ 能编过，值变成 3——小数点后的信息静默丢失
int lossy = pi;     // ✅ 也能编过，同样静默丢失
```

**那条错误有实测原文**（由另一个 agent 的独立验证补上）：

```text
narrow_fail.cpp(1): error C2397: 从"double"转换到"int"需要收缩转换
```

> **注意它说的是"需要收缩转换"（requires a narrowing conversion），不是"丢精度"。**
> 编译器在提醒你："这里有一个你可能没意识到的信息损失，请显式写出来。"
> 而且这是 **`error` 不是 `warning`**——**编译直接不通过**，所以你不会"不小心"跑起来一个静默截断的程序。

**三种写法同一个意图，两种命运**：

| 写法 | 结果 | 为什么 |
|---|---|---|
| `int x{pi}` | **编译错误** | `{}` 拒绝窄化 |
| `int x(pi)` | 编过，值截断 | `()` 允许窄化 |
| `int x = pi` | 编过，值截断 | `=` 允许窄化 |

> **这就是为什么现代 C++ 推荐默认用 `{}`**：
> **它把"我可能要丢精度"这件事变成编译期错误，逼你显式写出意图**（`static_cast<int>(pi)`）。
> 用 `()` 或 `=`，你得到的是一份能编过、但结果悄悄变了的程序。

> ⚠️ **但 `{}` 不是万能的**：`std::vector<int> v{1, 2}` 和 `std::vector<int> v(1, 2)` **语义完全不同**
> （前者是两个元素 `1, 2`，后者是 **1 个值为 `2` 的元素**）。这类初始化列表与其他构造函数的选择问题第 10 章会专门讲。
> **所以规则是"默认用 `{}`，遇到容器构造要格外小心"，不是"一律用 `{}`"。**

### 5.4 默认初始化：未初始化变量这个坑

**这是本章最该记住的一条。**

```cpp
int a;              // 局部变量：值不确定
std::cout << a;     // ⚠️ 未定义行为
```

**关键认识：这不是"随机数"。**

| 说法 | 对不对 |
|---|---|
| "`a` 会得到一个随机数" | ❌ 错。这暗示"每次不同但都是数"，其实**程序已经失去任何保证** |
| "`a` 的值取决于栈上原来剩什么" | ⚠️ 通常是这个现象，**但标准不保证** |
| "读未初始化的值是未定义行为，编译器可以做任何事" | ✅ **对** |

**为什么这个区别重要**：如果是"随机数"，那你的程序至少还在按规则运行，只是结果不可预测。
而**未定义行为意味着"程序已经不合规"**——优化器有权假设它不会发生，
于是可能把你没写过的代码删掉、把判断直接当成真。

> ⚠️ **坑（可复现）**：本机实测 `warning C4700: 使用了未初始化的局部变量"x"`，
> 但**开了优化（`/O2`）之后，同一段代码可能连警告都没有**——因为优化器把整个读取都消掉了。
> **所以"没警告"不等于"没问题"。** 处理办法只有一个：**声明时就初始化**。

**默认初始化和值初始化的对照表**（这张表要背下来）：

| 写法 | 局部变量 | 全局 / `static` 变量 |
|---|---|---|
| `int a;` | ⚠️ **值不确定** | ✅ 全零 |
| `int a{};` | ✅ 0 | ✅ 0 |
| `int a = 0;` | ✅ 0 | ✅ 0 |
| `std::string s;` | ✅ 空串（类类型自己保证） | ✅ 空串 |

**读法**：这张表只比较基本类型局部对象、静态存储期对象和所列标准库类型。**类类型会调用构造函数，却不保证每个基本类型成员都有确定值**；自己写的默认构造函数若漏掉成员初始化，仍可能留下不确定值（第 07 章第 2 节「构造函数与成员初始化列表」）。
这也解释了为什么老代码里全局变量看起来"很安全"——**不是安全，是恰好被初始化为零了**。

## 6. `auto`：让编译器替你写类型，以及它的三个退化

`auto` 让编译器**从初始化器推导类型**。它不是"动态类型"，类型仍然是**编译期**确定的。

<!-- example:ch02_auto -->
```cpp
#include <iostream>
#include <vector>

int main() {
    auto i = 42;               // int
    auto d = 3.14;             // double
    auto s = "text";           // const char*（不是 std::string！）
    std::vector<int> v{1, 2, 3};
    auto copy = v;             // 拷贝一份
    std::cout << i << ' ' << d << ' ' << s << ' ' << copy.size() << '\n';
}
```

<!-- result:ch02_auto -->
```text
42 3.14 text 3
```

### 6.1 三个必须知道的退化

`auto` 的推导规则**不是"照抄右边"**，它会去掉一些东西。这三条最容易踩：

| 你写的 | 你以为是 | `auto` 实际推成 | 后果 |
|---|---|---|---|
| `const int ci = 5; auto x = ci;` | `const int` | **`int`** | 丢掉了 `const`，`x` 可改 |
| `int n = 5; int& r = n; auto x = r;` | `int&` | **`int`** | 变成**拷贝**，改 `x` 不影响 `n` |
| `const int ci = 5; auto& r = ci;` | — | **`const int&`** | 用 `auto&` 时 `const` **会**保留 |

**一句话概括**：**`auto` 按值推导会去掉引用和顶层 `const`，不会去掉指针所指对象的底层 `const`。** `auto&` 可以保留被引用对象的限定；顶层与底层的区别见第 06 章第 5 节「`const` 与引用/指针的组合：顶层 const 与底层 const」。

> ⚠️ **坑**：`auto s = "text";` 得到的**不是 `std::string`，而是 `const char*`**。
> 这个坑在初学者代码里非常常见：以为 `auto` 会"智能地"选个好类型，结果拿到一个 C 风格字符串指针，
> 后面想做 `s + "more"` 就会报错（那是指针加法，不是字符串拼接）。
> **要 `std::string` 就写 `std::string` 或 `std::string s = "text";`，别指望 `auto` 猜对意图。**
>
> **判据**：`auto` 只能从**表达式的类型**推导，它**读不出你的意图**。

### 6.2 什么时候该用 `auto`

| 场景 | 建议 |
|---|---|
| 类型很长很啰嗦（迭代器、模板类型） | ✅ 用 `auto`，这是它的主要价值 |
| 类型一目了然（`auto n = 0;`） | ⚠️ 可以，但写 `int` 更明确 |
| 需要明确类型才能看懂代码 | ❌ 别用。`auto` 用过头会让代码读不出类型 |
| 想要引用 / 不想拷贝 | ✅ 用 `auto&` 或 `const auto&` |

> **一条实用判断**：**如果读代码的人光看这一行猜不出类型，就别用 `auto`。**
> `auto it = m.begin();` 很好（类型本来就啰嗦）；`auto x = f();` 就糟（`f` 返回什么谁知道）。

## 7. `const` 与 `constexpr`：只读和编译期

这两个词都跟"不能改"有关，但**它们管的是两件不同的事**。

<!-- example:ch02_const -->
```cpp
#include <iostream>

constexpr int square(int x) { return x * x; }

int main() {
    const int runtime_value = 5;        // const：不可改；此处也能用于整型常量表达式
    constexpr int compile_time = square(6);  // constexpr：编译期就能算出来
    std::cout << runtime_value << ' ' << compile_time << '\n';
}
```

<!-- result:ch02_const -->
```text
5 36
```

### 7.1 两者的分工

| | `const` | `constexpr` |
|---|---|---|
| 保证 | **这个对象不能被改** | **这个对象在编译期就确定了值** |
| 值何时确定 | 可以运行期定 | **必须**编译期定 |
| 能否用于内建数组长度 | 满足常量表达式要求的整型常量可以；运行期输入初始化的不行 | 满足长度的类型、正值等要求时可以 |
| 能否用于整型非类型模板参数 | 满足相应常量表达式要求时可以 | 满足参数类型与常量表达式要求时可以 |
| 初始化器要求 | 任意表达式 | **必须是编译期常量表达式** |

**关系**：`constexpr` **蕴含** `const`（编译期常量当然也不能改），反之不成立。

**为什么需要区分**：因为"不能改"和"编译期已知"对不同场景有用。

```cpp
int n;
std::cin >> n;
const int limit = n;        // ✅ 合法：运行期确定，之后不能改
// constexpr int bad = n;   // ❌ 错误：n 在编译期不知道
```

### 7.2 入门阶段怎么用

| 想干什么 | 用哪个 |
|---|---|
| 定义不会改的常量（数组大小、循环上限、配置值） | **`constexpr`**（首选） |
| 只读参数、只读成员（防止被改） | **`const`** |
| 值要运行时才能知道，但之后不该改 | **`const`** |

> **一条简单规则**：**能写 `constexpr` 就写 `constexpr`，写不了再退到 `const`。**
> 因为 `constexpr` 的要求更强——它逼你在编译期就把值定下来，这通常意味着设计更干净。

> ⚠️ **坑**：以为所有 `const` 都能用于常量表达式，或以为所有 `const` 都不能。
> `const int n = 5;` 的 `n` 满足整型常量表达式要求，`int arr[n];` 是 **C++17 标准允许的写法**，并非编译器扩展。
> 但由输入初始化的 `const int limit = n;` 不因此成为常量表达式。
> 定义编译期数组长度时首选 `constexpr`，是为了直接表达并检查意图，**不是因为 `const int` 一律不合法**。

## 8. 作用域与遮蔽：一个名字指的是哪一块内存

### 8.1 实测：三层同名对象

<!-- example:ch02_scope -->
```cpp
#include <iostream>

int value = 1;              // 全局

int main() {
    std::cout << value << '\n';     // 全局的 1
    int value = 2;                  // 遮蔽（shadowing）外层同名对象
    std::cout << value << '\n';     // 现在是 2
    {
        int value = 3;              // 再遮蔽一层
        std::cout << value << '\n';
    }
    std::cout << value << '\n';     // 回到 2
    std::cout << ::value << '\n';   // :: 显式指名全局
}
```

<!-- result:ch02_scope -->
```text
1
2
3
2
1
```

**编译时会有两条警告**（本机实测，这正是"遮蔽是个坑"的证据）：

```text
main.cpp(7): warning C4459: "value"的声明隐藏了全局声明
main.cpp(10): warning C4456: "value"的声明隐藏了上一个本地声明
```

**MSVC 主动告诉你"你在遮蔽"** —— 因为这件事**太容易写错**，
编译器认为值得专门提醒。

### 8.2 执行轨迹：名字怎么解析

```text
进入 main
  ├─ 读 value → 先在 main 的作用域找：还没有 → 去外层找 → 全局的 1     → 打印 1
  ├─ 声明 int value = 2   （从这一行起，main 作用域里的 value 就是它）
  ├─ 读 value → main 作用域找到了 → 2                                → 打印 2
  ├─ 进入内层块 { int value = 3; }
  │    └─ 读 value → 内层块找到了 → 3                                → 打印 3
  ├─ 内层块结束（它的 value 被销毁）
  ├─ 读 value → main 作用域的那个 → 2                                → 打印 2
  └─ 读 ::value → :: 表示"全局作用域"，跳过所有局部 → 1               → 打印 1
```

**关键规则**：**名字查找从最内层往外找，找到就停。** 内层同名对象会**完全遮住**外层，
不是"覆盖值"——它俩是**两个不同的对象**，各自有自己的存储。

### 8.3 名字解析的正式顺序（`::` 的意义）

C++ 的名字查找比"从内往外"要复杂（涉及命名空间、类作用域、ADL 等，第 07 章与 `13` 章展开）。
入门阶段够用的模型是：

```text
不带 :: 的名字：  当前块 → 外层块 → … → 全局
带 :: 的名字：    从 :: 开始（全局作用域），跳过所有局部
std:: 前缀：      在 std 命名空间里找
```

`::value` 里的 `::` 叫**作用域解析运算符**（scope resolution operator），
第 01 章见过它出现在 `std::cout` 里。**同一个符号，两种用法**：

| 写法 | 含义 |
|---|---|
| `std::cout` | 在命名空间 `std` 里找 `cout` |
| `::value` | 在最外层（全局）作用域找 `value` |

## 9. 隐式转换：编译器在你没要求的时候做了什么

**隐式转换**（implicit conversion）是编译器**自动**插入的类型转换。这是 C++ 里"方便"和"危险"同时存在的地方。

### 9.1 常见的隐式转换

| 从 | 到 | 会发生什么 |
|---|---|---|
| `int` → `double` | ✅ 安全 | 精度基本不丢（极大整数除外） |
| `double` → `int` | ⚠️ **丢小数部分**（截断，不是四舍五入） | 静默丢失 |
| `int` → `bool` | 非 0 → `true`，0 → `false` | 常见于 `if (x)` |
| `bool` → `int` | `true` → 1，`false` → 0 | 有时是笔误 |
| 有符号 ↔ 无符号 | ⚠️ **按位重新解释** | 见第 10 节 |
| 小整数 → `int` | ✅ **整型提升**（integer promotion） | 见 9.3 |

### 9.2 浮点转整数是**截断**，不是四舍五入

```cpp
int a = 3.9;    // a == 3   （不是 4！）
int b = -3.9;   // b == -3  （向零截断，不是 -4）
```

**要四舍五入就用 `std::lround` / `std::round`，别指望隐式转换。**

### 9.3 整型提升：小类型参与运算时会先"变大"

`char`、`short`、`bool` 这些比 `int` 小的类型，在参与算术运算前会**先提升成 `int`**。

```cpp
char c = 'A';        // 假设是 65
auto n = c + 1;      // n 的类型是 int，不是 char！
```

**为什么这样设计**：因为 CPU 的算术单元按 `int` 宽度工作最自然，提升能让运算更快。

**它带来的坑**：`uint8_t` 也逃不过提升。

```cpp
std::uint8_t a = 200, b = 100;
auto sum = a + b;    // sum 的类型是 int（不是 uint8_t），值是 300
std::uint8_t c = a + b;   // ⚠️ 塞回 8 位会截断
```

> **这就是 3.3 节说"不要到处用定宽小类型"的原因**：
> 它们在运算时会被提升，你以为在算 8 位，其实在算 32 位，回存时才截断。

### 9.4 怎么避免被隐式转换咬

三个办法，按推荐程度排：

1. **默认用 `{}` 初始化**——窄化会变成编译错误（5.3 节）
2. **显式写 `static_cast<T>(x)`**——把意图写出来（第 03 章详讲）
3. **开警告**——`/W4` 会报出很多可疑的隐式转换（比如 `C4244`）

> **判据**：**如果一个转换是你有意做的，就写出来；如果是不小心的，就该报错。**
> 隐式转换的问题不是"存在"，而是它**让你分不清这两者**。

## 10. 有符号与无符号：两个真会咬人的坑

<!-- example:ch02_signed_unsigned -->
```cpp
#include <iostream>

int main() {
    unsigned int u = 0;
    u = u - 1;                       // 回绕到最大值
    std::cout << u << '\n';

    int n = -1;
    // 混合比较时 n 会被转成 unsigned，于是"负数大于 0"
    std::cout << (n < u) << '\n';
}
```

<!-- result:ch02_signed_unsigned -->
```text
4294967295
0
```

**编译时有一条警告**（本机实测）：

```text
main.cpp(10): warning C4018: "<": 有符号/无符号不匹配
```

### 10.1 坑一：无符号数的回绕

`u = u - 1` 在 `u == 0` 时**不会得到 −1**，而是回绕到**最大值**（`4294967295`）。

**为什么**：无符号整数的算术**按模 2^N 运算**——这是**标准规定的行为**（不是未定义行为）。
4 字节 `unsigned` 的模是 2^32，所以 `0 − 1` 的结果是 `2^32 − 1`。

> ⚠️ **坑**：写 `for (unsigned i = n - 1; i >= 0; --i)`。
> 这是一个**永远不会结束**的循环：`i` 是无符号的，`i >= 0` **恒为真**，
> 而 `i` 减到 0 之后再减会回绕到最大值。**这是教科书级的死循环。**
>
> **正确写法**：用有符号的 `int` 做倒序下标，或者改成 `for (unsigned i = n; i-- > 0; )` 这种明确处理边界的写法。

### 10.2 坑二：混合比较时的类型转换

`n < u` 里 `n = -1`、`u = 4294967295`。直觉上 −1 应该小于 4294967295，所以该打印 `1`。
**实际打印 `0`。**

**为什么**：当有符号和无符号类型参与同一个运算时，标准规定的规则会**把有符号的那个转成无符号**。
于是 `n = -1` 被解释成 `4294967295`，两边相等，所以 `n < u` 是**假**。

**这一条特别危险**，因为它：

- ✅ 编译通过
- ✅ 有警告（但只在 `-1` 是字面量时？不一定）
- ❌ 结果完全反直觉

> ⚠️ **判据**：这类错误的归属是**类型类**，不是逻辑类。
> 你写的比较条件逻辑上没错，错在**两边类型不同时标准会插入一个你没写的转换**。
>
> **处理办法**：
> 1. **别混用**——一个变量该不该无符号，一开始就定好
> 2. 需要无符号时，**先显式转成有符号再比较**，或反过来
> 3. 把 `-Wsign-compare`（GCC）/ `/W4`（MSVC 的 `C4018`）当错误看

### 10.3 那到底什么时候该用无符号

| 场景 | 建议 |
|---|---|
| 计数、下标 | ❌ 用**有符号**（`int`）。标准库的 `size()` 返回无符号，这是个历史包袱 |
| 位运算、位掩码、哈希 | ✅ 用**无符号**（回绕是你要的行为） |
| 表示"不可能为负的量" | ⚠️ 听起来合理，但**比较时的转换风险更大**，慎用 |
| 与硬件/协议打交道 | ✅ 用**定宽无符号**（`uint32_t` 等） |

> **标准库自己的教训**：`std::vector::size()` 返回 `size_type`（无符号），
> 所以 `for (int i = 0; i < v.size(); ++i)` 会触发 `C4018` 警告。
> C++20 为此引入了 `std::ssize()` 返回有符号大小。**这说明连标准库都认为当年的选择是个负担。**

## 11. 命名空间：`std::` 到底是什么

<!-- example:ch02_namespace -->
```cpp
#include <iostream>

namespace mine {
    int value = 10;
}

int main() {
    std::cout << mine::value << '\n';   // 用限定名访问
}
```

<!-- result:ch02_namespace -->
```text
10
```

### 11.1 命名空间解决什么问题

想象两个人各写了一个 `print` 函数，都放进同一个程序。编译器看到 `print(x)` 时不知道调哪个。
**命名空间就是给名字加一层前缀**：

```cpp
namespace alice { void print(int); }
namespace bob   { void print(int); }

alice::print(1);    // 明确指名
bob::print(1);
```

**`std` 就是标准库的命名空间。** 所以：

| 写法 | 含义 |
|---|---|
| `std::cout` | `std` 命名空间里的 `cout` |
| `::value` | **全局**作用域里的 `value`（`::` 前面没有名字） |

### 11.2 `using namespace std;` 为什么不该用

你会在很多教程里看到：

```cpp
using namespace std;      // ⚠️ 把 std 里所有名字"倒"进当前作用域
int main() { cout << 1; }
```

它能让代码短一点，但**代价很大**：

1. **`std` 里有几百个名字**，其中很多很普通：`count`、`distance`、`size`、`data`、`swap`、`move`、`begin`、`end`
2. 你自己定义的同名函数或变量会**和它们冲突**，而报出的错误**极难看懂**（往往指向标准库头文件内部）
3. **头文件里写 `using namespace std;` 是灾难**——它会污染所有包含这个头文件的文件

> **本讲义的立场：入门阶段不要写 `using namespace std;`。**
> 多打 `std::` 的代价是几秒钟；命名冲突的代价是半小时读一条看不懂的错误。
>
> **例外**：函数内部、很小的作用域里，`using std::cout;` 这种**单个名字**的 `using` 声明是可以的
> （它只引入一个名字，风险可控）。

**为什么标准库要用 `std` 这个短名字**：因为它本来就是个"缩写"。
标准库的名字在 1990 年代定下来时，设计者选了一个尽量不容易和用户代码冲突的短名。
今天看，`count` / `size` / `data` 这些名字恰恰太普通了——**这也是 `using namespace std;` 危险的根本原因**。

## 12. 字面量的类型与后缀

**字面量**（literal）是直接写在代码里的值：`42`、`3.14`、`'a'`、`"text"`。
它们**每一个都有类型**，而类型由**写法**决定。

<!-- example:ch02_literal_suffix -->
```cpp
#include <iostream>
#include <type_traits>

int main() {
    std::cout << std::boolalpha;
    std::cout << std::is_same<decltype(1), int>::value << '\n';
    std::cout << std::is_same<decltype(1u), unsigned int>::value << '\n';
    std::cout << std::is_same<decltype(1L), long>::value << '\n';
    std::cout << std::is_same<decltype(1.0), double>::value << '\n';
    std::cout << std::is_same<decltype(1.0f), float>::value << '\n';
}
```

<!-- result:ch02_literal_suffix -->
```text
true
true
true
true
true
```

**五行全 `true`，证明的就是下面这张表：**

| 字面量 | 类型 | 后缀含义 |
|---|---|---|
| `42` | `int` | 无后缀，整数默认 `int` |
| `42u` / `42U` | `unsigned int` | unsigned |
| `42L` | `long` | long |
| `42LL` | `long long` | long long |
| `42UL` | `unsigned long` | 组合后缀，顺序任意（`LU` 也行） |
| `3.14` | `double` | ⚠️ **无后缀的浮点默认 `double`，不是 `float`** |
| `3.14f` | `float` | float |
| `3.14L` | `long double` | long double |
| `'a'` | `char` | 字符字面量 |
| `"text"` | `const char[5]` | 字符串字面量（含结尾的 `'\0'`，所以是 5 不是 4） |
| `true` / `false` | `bool` | 布尔字面量 |
| `nullptr` | `std::nullptr_t` | 空指针（第 06 章讲） |

> ⚠️ **坑一**：以为 `3.14` 是 `float`。
> **没有后缀的浮点字面量是 `double`。** 所以要 `float` 必须写 `3.14f`，
> 否则 `float x = 3.14;` 会触发"`double` 转 `float` 可能丢精度"的警告（`C4244`）。

> ⚠️ **坑二**：以为 `42` 一定能装下。
> `42` 的类型是 `int`，所以 `long long big = 3000000000;` 里的字面量**本身就是错的**
> （3000000000 超出 `int` 范围，标准会试图当 `long long` 处理，但显式写 `3000000000LL` 更清楚）。
> **大数字面量加后缀**是个好习惯。

> ⚠️ **坑三**：`"text"` 的类型是 `const char[5]`，**不是 `std::string`**。
> 这解释了第 6 节的 `auto s = "text"` 为什么拿到指针。
> **`std::string` 是标准库的类，字符串字面量是内置的字符数组**——两者不是一回事（第 09 章详讲）。

### 12.1 其它常用的字面量写法

| 写法 | 含义 |
|---|---|
| `0x1F` | 十六进制（31） |
| `0b0101` | 二进制（C++14 起，5） |
| `017` | 八进制（15）——⚠️ 前导 0 表示八进制，容易看错 |
| `1'000'000` | 数字分隔符（C++14 起，就是一百万）——**推荐用，长数字更可读** |

> ⚠️ **坑**：`int x = 010;` 你以为写的是 10，实际是 **8**（八进制）。
> **不要用前导 0 写十进制数。** 要写十进制就写 `10`。

## 13. 格式与风格：为什么 C++ 代码长这样

这一节不是"审美"，而是**几条有实际后果的习惯**。

### 13.1 每条语句以 `;` 结束

```cpp
int a = 1;      // ✅
int b = 2       // ❌ 漏了分号
int c = 3;      // 编译器会在这一行报错，但真凶在上一行
```

> ⚠️ **坑**：漏分号的报错**常常出现在下一行**。因为编译器可能把两行拼成一句合法的东西，
> 直到发现接不下去才报错。**看到"这一行莫名其妙报错"时，先看上一行末尾。**

### 13.2 花括号决定块的边界，缩进不影响语义

```cpp
if (x) {
    do_a();
}
```

**缩进只是给人看的。** 但**必须**缩进——因为不缩进的代码，人会看错块边界，
而**编译器不会**。这类错误的归属是**逻辑类**：程序完全按你写的执行，只是你写错了。

### 13.3 命名习惯

约定俗成（不是标准强制）：

| 对象 | 常见写法 |
|---|---|
| 变量、函数 | `snake_case` 或 `camelCase`（**一个项目内统一**） |
| 类型 / 类 | `PascalCase`（如 `MyClass`） |
| 常量 | `kConstant` 或 `ALL_CAPS` |
| 成员变量 | `m_value` 或 `value_`（尾下划线） |

**唯一硬要求**：**别用下划线开头，尤其别用双下划线开头。**
`_foo` 和 `__foo` 是**保留给实现**的（标准库和编译器要用），你自己用会撞上未定义行为。

### 13.4 一条"抄别人代码之前先看格式"的理由

C++ 有很强的"本地惯例"：同一个团队里大括号放哪、用什么缩进、`const` 写左还是写右，
都会统一。**你在一个存在的项目里写代码时，跟它现有的格式走**——
不是因为那个格式更好，而是因为**混着来会让 diff 变得没法读**。

## 14. 本章自测

**1.** `int a = 5;` 和 `int b; b = 5;` 结果一样，但为什么说它们不是一回事？

<details><summary>答案</summary>

前者是**初始化**（对象创建时就有值），后者是**默认初始化 + 赋值**（先创建一个值不确定的对象，再把 5 写进去）。

对 `int` 来说最终结果相同，但对**类类型**两者会调用**不同的函数**：
初始化调**构造函数**，赋值调**赋值运算符**。第 07 章会看到这个区别的实际后果
（比如赋值可能无法处理"对象还没构造好"的情况）。

**判据**：看到 `= 5` 紧跟在类型后面，那是初始化；分开写成两条语句，那是赋值。
</details>

**2.** 下面三种写法，哪一种会在编译期报错？为什么？

```cpp
double pi = 3.14159;
int a{pi};
int b(pi);
int c = pi;
```

<details><summary>答案</summary>

**只有 `int a{pi};` 报错**（MSVC：`error C2397: 从 "double" 到 "int" 的转换需要收缩转换`）。

因为花括号初始化 `{}` **拒绝窄化转换**——`double` 到 `int` 会丢小数部分，属于可能丢信息的转换。
`()` 和 `=` 都允许窄化，所以 `b` 和 `c` 会**编译通过、值被截断成 3**。

**这就是推荐默认用 `{}` 的理由**：它把"我可能要丢精度"变成编译期错误，
逼你显式写出 `static_cast<int>(pi)` 这样的意图。
</details>

**3.** 这个程序有什么问题？编译能过吗？运行结果确定吗？

```cpp
#include <iostream>
int main() {
    int x;
    std::cout << x << '\n';
}
```

<details><summary>答案</summary>

**编译能过**（`x` 是合法声明的 `int`），**但运行结果不确定**——读未初始化的局部变量是**未定义行为**。

**关键**：不是"得到一个随机数"，而是**程序已经失去任何保证**。
优化器有权假设 UB 不会发生，于是可能把这段代码整个删掉，或者把后续判断直接当真。

MSVC `/W4` 会给 `warning C4700: 使用了未初始化的局部变量"x"`。
**但开了 `/O2` 之后可能连警告都没有**，所以"没警告"不等于"没问题"。

**修法**：`int x{};`（值初始化，得 0）或 `int x = 0;`。
</details>

**4.** `auto s = "text";` 得到的 `s` 是什么类型？为什么这是个坑？

<details><summary>答案</summary>

`const char*`，**不是 `std::string`**。

因为 `auto` 只能从**表达式的类型**推导，而字符串字面量 `"text"` 的类型是 `const char[5]`；
`auto` 按值推导时数组会退化成指针，于是得到 `const char*`。

**坑在哪**：`s` 看起来像字符串，但它是**指针**。所以 `s + "more"` 是指针加法（结果无意义），
`s.length()` 直接编译不过。**`auto` 读不出你的意图，它只读类型。**

要 `std::string` 就写 `std::string s = "text";`。
</details>

**5.** 下面这行 `u` 的值是多少？这是未定义行为吗？

```cpp
unsigned int u = 0;
u = u - 1;
```

<details><summary>答案</summary>

`u` 变成 **4294967295**（4 字节 `unsigned` 的最大值）。

**这不是未定义行为**——无符号整数的算术**标准规定按模 2^N 运算**，`0 − 1` 回绕到最大值是**定义良好的行为**。

（对比：**有符号**整数溢出才是未定义行为。这个不对称是 C++ 里一个著名的历史设计。）

**坑在于**：`for (unsigned i = n - 1; i >= 0; --i)` 是**死循环**，因为 `i >= 0` 恒为真。
这类错误的归属是**类型类 + 控制流类**的组合。
</details>

**6.** `n = -1`、`u = 4294967295u`，为什么 `n < u` 打印 `0`？

<details><summary>答案</summary>

因为**有符号与无符号参与同一运算时，标准规定把有符号的那个转成无符号**。

于是 `n = -1` 被按位重新解释成 `4294967295`，两边相等，所以 `n < u` 是**假**，打印 `0`。

MSVC `/W4` 会给 `warning C4018: "<": 有符号/无符号不匹配`。

**这类错误的归属是类型类**：你写的比较逻辑没错，错在两边类型不同时标准插入了一个你没写的转换。
**处理**：别混用；要混就先显式转；把这类警告当错误看。
</details>

**7.** `const` 和 `constexpr` 的区别是什么？要定义数组长度该用哪个？

<details><summary>答案</summary>

- **`const`**：保证"这个对象不能被改"。值可以运行时才确定。
- **`constexpr`**：保证"这个对象的值在编译期就确定"。**蕴含 `const`**。

内建数组长度要求相应的**常量表达式**；首选 **`constexpr`** 表达意图，但满足条件的 `const int` 也可以。

```cpp
int n; std::cin >> n;
const int limit = n;         // ✅ 合法，但 limit 不是编译期常量
// int arr[limit];           // ❌ 标准不保证能编过
constexpr int size = 10;
int arr[size];               // ✅ 没问题
```

> `const int n = 5;` 的 `n` 满足整型常量表达式要求，所以 `int arr[n];` **标准允许**；这与优化器是否折叠表达式无关。
</details>

**8.** 第 8 节那个三层同名 `value` 的例子，为什么 MSVC 会报 `C4459` / `C4456` 警告？

<details><summary>答案</summary>

因为**遮蔽（shadowing）**是一个高频错误来源：写 `int value = 2;` 的人，
往往**以为自己在改外层的 `value`**，实际上创建了一个**全新对象**，外层那个一点没动。

MSVC 用两条不同的警告分别提醒：
- `C4459`：局部声明隐藏了**全局**声明
- `C4456`：局部声明隐藏了**上一个局部**声明

**关键认识**：遮蔽不是"覆盖值"，是"**名字被更内层的新对象接管了**"。
两个对象各自有自己的存储，外层那个要等内层作用域结束后才重新"可见"。

`::value` 可以显式跳过所有局部，直接指名全局。
</details>

**9.** 为什么本讲义建议不要写 `using namespace std;`？给两个具体理由。

<details><summary>答案</summary>

1. **`std` 里有几百个名字，其中很多很普通**：`count`、`distance`、`size`、`data`、`swap`、`move`、`begin`、`end`。
   你自己定义的同名函数或变量会和它们冲突，而报出的错误**往往指向标准库头文件内部**，极难定位。

2. **写在头文件里是灾难**：`using namespace std;` 的作用会传播到**所有包含这个头文件的 `.cpp`**，
   等于把污染扩散到整个项目。

**代价对比**：多打 `std::` 花几秒钟；命名冲突可能花半小时读一条看不懂的错误。

**例外**：函数内部用 `using std::cout;` 这种**单个名字**的 `using` 声明风险可控（只引入一个名字）。
</details>

**10.** `sizeof(long double)` 在这台机器上是多少？由此能得出什么结论？

<details><summary>答案</summary>

**8 字节**——和 `double` 一样。

**结论**：**在这台机器（MSVC / Windows）上，`long double` 并不比 `double` 精度高。**
标准只要求 `sizeof(long double) >= sizeof(double)`，没有要求"更大"。
在 Linux/GCC 上它通常是 16 字节。

**所以"`long double` 精度更高"不是可移植的事实。**
要确认真实精度，用 `std::numeric_limits<long double>::digits10`，**别用 `sizeof` 推断**。

**这一题的更大意义**：它是本章"平台差异"最直接的例子——
同一份代码在不同平台上 `sizeof` 结果不同，**而这不是编译器实现得不好，是标准允许的**。
</details>
