### 标准编译命令

```powershell
$vcvars = "C:\Program Files (x86)\Microsoft Visual Studio\18\BuildTools\VC\Auxiliary\Build\vcvars64.bat"
cmd /c "`"$vcvars`" >nul 2>&1 && cd /d <工作目录> && cl /nologo /std:c++17 /EHsc /W4 /utf-8 main.cpp /Fe:main.exe && main.exe"
```

**`/utf-8` 与 `/W4` 都不能省**：

- 不写 `/utf-8`，源码里任何中文都会让编译**直接失败**（实测 `C4819` + `C2001` + `C3688` + `C2143`）
- 不写 `/W4`，大量"能编过但错了"的写法没有任何提示

### 4.2 ⚠️ 判据是「块数 > 0 且不符合 0」，不是「不符合 0」

**标记写错时，脚本会扫到 0 块，并高高兴兴地报"0 处不符合"。** 这是**静默假通过**。

```text
=== 01_从源代码到运行.md : 0 块 ===
合计 0 块 ｜ 输出一致 0 ｜ 预期编译失败 0 ｜ 无预期输出 0 ｜ 不符合预期 0
```

初稿就是这样：**53 个代码块，0 个进了基线**。所以：

> **看输出时先确认它扫到了合理的块数。** 出现在个位数且该章示例很多，就是标记没加。

### 4.3 当前基线（真实跑出来的）

| 检查 | 命令 | 基线 |
|---|---|---|
| 工具自测样板 | `verify_cpp.py tmp/cppenv/selftest.md -v` | **8 块：输出一致 5、预期编译失败 1、不符合 2**（那 2 个是样板里故意写错的，用来证明脚本能抓假输出） |
| 第 1 章 | `verify_cpp.py "...\01_从源代码到运行.md" -v` | **6 块，全部输出一致，0 不符合**（2026-10-08） |
| 其余章节 | — | **尚不存在** |

### 4.4 工具的三个已知坑（都踩过，别重踩）

| 现象 | 原因 / 做法 |
|---|---|
| `PermissionError [WinError 5]`，且目录**建完删不掉** | **不要用 `tempfile.mkdtemp()`**。它在沙箱下建的目录无法写入子目录。用普通 `os.makedirs()` 建在工作区内被 `.gitignore` 覆盖的路径 |
| 报 `The filename, directory name, or volume label syntax is incorrect.`，`cl` 静默不执行 | **不要用 `subprocess.run(["cmd","/c", 长命令串])`**。列表形式会让 Python 用 Windows 引号规则重新转义，把 `>` 重定向弄坏。**写成 `.bat` 再执行** |
| `) was unexpected at this time.` | **cmd 里不能用 `( ... & )`** 吞退出码——`&` 是语句分隔符，不是 Unix 的后台符 |

### 4.5 `run-expect`（前缀匹配）什么时候用

输出里含**随环境变化**的内容时（如 `argv[0]` 的完整路径），逐字比对会假失败。
这时用 `<!-- run-expect:key -->` 只断言稳定那部分。

**这不是偷懒，是正确处理。** 但**不许**用它来掩盖"输出确实不对"——
如果整个输出都不确定，说明这个示例的设计有问题，应该改成不确定部分不进输出。

## 五、已知陷阱与真实事故

### 5.1 两次"自己证伪自己"（红线 1 的价值）

初稿第 1 章里，作者**猜**了两处，实跑后全部推翻：

| 初稿写的 | 实测真相 |
|---|---|
| `/FA` 汇编里"会有类似 `lea eax, [rcx+rdx]`" | **没有 `lea`**。是 `mov`/`add` 序列，符号被修饰为 `?add@@YAHHH@Z`，标记 `/Odtp`（未优化） |
| `/P` 展开后"约 100 万字节量级" | **2 522 251 字节 / 85 972 行**，61 字节的源文件膨胀 **41 000 倍** |

两处都留着记录，**不要"清理"掉**——它们是这条红线为什么存在的证据。

### 5.2 C++17 与 C++11 的混淆（已纠正一次）

起草覆盖表时把"值类别/RAII/`const` 正确性/lambda/智能指针/UB/ODR/ADL"当成了 C++17 新特性。
**它们从 C++11 起就是基线。** 准确的三分法是：

| 类别 | 怎么摆 |
|---|---|
| 语义模型（C++11 起基线） | 进正文主干，**不要叫"新特性"** |
| C++17 真新增（结构化绑定、`if constexpr`、`optional`/`variant`/`any`、`string_view`、折叠表达式…） | 出现时标注「C++17 起」 |
| C++20/23 | 只在明确标注的地方出现，本讲义不含 |

详见 [`01a_三源交叉核对.md`](01a_三源交叉核对.md) 第七节。

### 5.3 两套编译器版本号，别把其中一个"改对"

- `vcvars` 所在**目录名**：**14.51.36231**（Visual Studio 工具集版本）
- `cl` 自报 **内部版本**：**19.51.36256.0**

**两个都对，只是含义不同。** 写成"其中一个是对的、另一个要改"就错了。

### 5.4 覆盖对账表的"幽灵条目"

第 1 章对账表曾声称 0.3 覆盖了"注释"，但正文没有专节。
**判据永远是"正文里找得到"，不是"表里写了"。** 每章定稿前逐条回正文核对一遍。

### 5.5 跨章引用只能用「章内实际节号 + 标题」

**Python 笔记里已真实错过 5 次。** 危险在于读者无法自行纠正——他会去目标章翻一个不存在的节号，
然后怀疑自己找错了文件。**这比"没写"更伤信任。**

## 六、多 agent 协作（本项目的特殊之处）

**Codex 无法在 DSH 沙箱里运行**——已实测 5 种调用方式，全部失败于同一处：

```text
failed to open daemon operation lock C:\Users\Wang\.codex\app-server-daemon\daemon.lock
Caused by: 拒绝访问。 (os error 5)
```

放宽沙箱（`danger-full-access`）也没有用，**证明不是文件权限问题，而是运行模型冲突**。

**所以协作机制是「文件交接」**，完整协议见 [`_协作规范.md`](_协作规范.md)：

```text
A（DSH 侧，能调编译器）          B（Codex，在沙箱外终端）
   出 TASK-NN.md  ────────────→  按任务书写作
   跑编译 + 结构审计              报 RESULT-NN.md
   出 REVIEW-NN.md / FIX-NN.md ─→ 按缺陷清单修
```

**分工原则**：**谁在哪一侧有独占能力，谁就负责那一侧。**
A 有编译器（能证伪"这写法没问题"），B 有另一个模型的先验（能证伪"这讲法讲清了"）。

**交接的硬规矩**：

1. 任务书必须**自包含**（假设 B 没有任何对话上下文）
2. 验收必须**给数字**（"37 块通过、2 块预期失败、0 块输出不符、4 条警告"）
3. **B 只改 FIX 清单里列出的位置**，不许顺手重排整章
4. **A 对 B 报的每条断言独立复核：能复现的接受，复现不了的作废**

## 七、提交与汇报

```powershell
cd C:\Users\Wang\Desktop\git

# 用户确认后再：
git add <具体文件>          # 不要 git add -A
```

- **一章一个 commit** 是既有习惯。
- `tmp\`、`.venv\`、`git.worktrees\`、`2026fall-cs101yan\` 都已被 `.gitignore` 排除。

**汇报格式**（用户不喜欢空泛总结）：

```text
【改了什么】文件 + 节号 + 一句话
【结构决策】为什么这样切分（依据哪条分类轴）
【实测证据】跑了哪个脚本、数字是多少（改前 → 改后）
【没做的事】哪些判断不该动、为什么
【诚实的空白】哪些没测、怎么测
【下一步】建议做什么，为什么是下一步
```

**不要**写"已全面检查，没有发现问题"。要说"`verify_cpp.py` 第 1 章 6 块、全部一致、0 不符合"。
