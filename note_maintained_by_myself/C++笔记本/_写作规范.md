## 一、硬性要求

### 1. 只用自己话写

- **禁止逐字复制**任何教程、书籍、博客、标准文档的正文。cppreference、cplusplus.com、runoob、标准草案都一样。
- **知识点、结构、语言事实、条款号不受版权保护**，可以照着讲、照引条款号。
- **示例代码必须自己写**，不要照抄别人的例子（哪怕改了变量名）。
- 需要引用原文时：**给链接 + 一句话概括**，不要把正文搬过来。

> ⚠️ **许可风险特别提示**（本轮调研核实）：
> cppreference 的离线镜像仓声明 **CC-BY-SA-4.0（传染性）**，若把它的文字搬进正文，
> 本讲义就得同样以 CC-BY-SA 发布。所以它**只能用来生成你自己的覆盖清单，不能搬文字**。
> 另有若干中文高星仓库在 API 里 `license: null`（**无许可 ≠ 公共领域**），
> 同样只能作结构对照。

### 2. 版本与事实

| 项 | 值 | 说明 |
|---|---|---|
| 编译器 | **MSVC 14.51.36231**（VS Build Tools 2026） | `cl` 自报内部版本 **19.51.36256.0**，**两套编号都别写错** |
| Windows SDK | 10.0.26100 | 标准库头来源 |
| 语言基线 | **C++17** | C++20/23 只标位置，不进正文主干 |
| 控制台代码页 | **936（GBK）** | 编译必须加 `/utf-8` |
| GCC / Clang | **本机未安装** | 涉及它们的说法必须标"未在本机实测" |

- 涉及"某版本新增/移除"的说法，**没实测过的要标注出来**，不要把记忆当事实。
- **C++17 vs C++11 的区分必须做对**：值类别、移动语义、RAII、`const` 正确性、lambda、
  智能指针、`constexpr`、UB、ODR、名字查找与 ADL —— 这些**从 C++11 起就是基线**，
  **不是 C++17 新特性**。把它们说成"C++17 新增"会误导读者低估自己环境的能力。
  详见 [`01a_三源交叉核对.md`](01a_三源交叉核对.md) 第七节。

### 3. 代码块必须能跑

**这是本讲义立身的根据。** 所有示例代码块在写完后**实际编译运行一遍**，把真实输出贴进正文。

运行方式（本机已实测）：

```powershell
$vcvars = "C:\Program Files (x86)\Microsoft Visual Studio\18\BuildTools\VC\Auxiliary\Build\vcvars64.bat"
cmd /c "`"$vcvars`" >nul 2>&1 && cd /d . && cl /nologo /std:c++17 /EHsc /W4 /utf-8 main.cpp /Fe:main.exe && main.exe"
```

- **报错示例也要真跑**，贴真实诊断，不要凭记忆编。
- **故意编译失败的示例**用 ```` ```cpp compile-fail ```` 标注。
- 编译产物（`.obj` / `.exe` / `.pdb` / 日志）一律丢到仓库根 `tmp/`（已被 `.gitignore` 覆盖）。

### 4. 代码块标记约定（与 `tmp/verify_cpp.py` 配套）

**只有"能独立编译、且输出确定"的示例才加标记。** 片段、伪代码、汇编清单、
诊断文本、需要多个 `.cpp` 的例子**保持原样不要加**——加错标记会在基线里制造假失败。

```markdown
<!-- example:ch01_first -->
```cpp
#include <iostream>
int main() { std::cout << 3 + 4 << '\n'; }
```

<!-- result:ch01_first -->
```text
7
```
```

| 标记 | 作用 |
|---|---|
| `<!-- example:key -->` | 声明一个可验证示例（键必须全章唯一） |
| `<!-- result:key -->` | 期望输出，**逐字全等**比对 |
| `<!-- run-expect:key -->` | 期望输出，**前缀匹配**。用于输出里含随环境变化的部分（如 `argv[0]` 的完整路径） |
| `<!-- stdin:key -->` | 喂给程序的输入 |
| ```` ```cpp compile-fail ```` | 断言"必须编译失败"，不比对输出 |

**判断某个块该不该加标记**：**这一段能不能单独存成一个 `main.cpp`，
编译后得到确定的输出？** 能 → 加。不能 → 不加，并在需要时说明它为什么不可独立运行。

**验证命令**：

```powershell
# 全量（只扫章节文件：文件名形如 01_xxx.md）
python tmp/verify_cpp.py note_maintained_by_myself/C++笔记本 -v

# 只验一章
python tmp/verify_cpp.py note_maintained_by_myself/C++笔记本/01_从源代码到运行.md -v
```

> ⚠️ **判据是"块数 > 0 且不符合 0"，不是"不符合 0"。**
> 标记写错时脚本会扫到 0 块并报"0 处不符合"——那是**静默假通过**。
> 本项目已真实发生过一次（第 1 章初稿 53 个代码块、0 个进基线）。

### 5. 平台

- 用户是 **Windows 11 + PowerShell / Git Bash**。
- 命令示例要区分 PowerShell 与 Git Bash 时，明确标注。
- Windows 特有坑（控制台代码页、路径反斜杠、`.exe` 与 `.\`、执行策略）必须写进去。

## 二、风格要求

### 6. 读者是谁

- **编程初学者（实现层面）**，但思维层面能讨论抽象概念；刚用同一套规格学完 Python。
- **先给最小具体例子，再抽象**。不要用纯符号开场。
- 每引入一个新概念，先让读者看到"它解决什么问题"，再给定义。

### 7. 不要空泛

- 禁止"XX 非常重要，要熟练掌握"这类没有信息量的话。
- 每段要么给事实，要么给例子，要么给判断依据。
- 有取舍的地方**给出取舍**（什么场合用哪个、为什么），不要只说"两者都可以"。

### 8. 该有"坑"的地方必须有坑

每章至少要有几处**真实存在的陷阱**，格式：

> ⚠️ **坑**：现象 → 原因 → 处理。

陷阱要具体到能复现，不要讲"要注意细节"这种废话。
**C++ 的坑尤其要说清它属于哪一类**：语法？类型？控制流？作用域？链接？**未定义行为？**

### 9. 结构模板

每个章节文件按这个骨架（可按内容增减小节，但骨架必须在）：

```markdown
# NN · 章节标题

> 覆盖表条目：X.1 xxx ｜ X.2 xxx ｜ ...
>
> 一句话说明这一章要解决什么。

> **本章目录**
>
> - 0. 先记住的 N 件事
> - 1. ...
> - 末几节带 🔧

---

## 0. 先记住的 N 件事        ← 推荐。给整章的"锚点"

## 1. ...                    ← 按覆盖表条目顺序展开

## N. 本章自测               ← 必写。5-10 题 + <details> 折叠答案

## N+1. 本章覆盖对账          ← 必写

## N+2. 诚实标注             ← 必写

**下一章**：`NN_xxx.md` —— 一句话预告。
```

### 9.1 章首目录（必写）

描述块引用和第一个 `---` 之间放一段**章首目录**，把本文所有 `##` 二级标题按顺序列全：

```markdown
> **本章目录**
>
> - [0. 先记住的六件事](#0.%20先记住的六件事)
> - [1. ...](#1.%20...)
> - [13. 本章自测](#13.%20本章自测) 🔧
```

**规则**：

1. **只列 `##` 二级标题**，不列 `###`。
2. **一条不漏、顺序与正文一致。**
3. **带锚点链接，可点击跳转。** 锚点写法：
   - 锚点文本 = `##` 后面的标题原文
   - **空格 → `%20`**
   - **圆括号 → `\(` `\)`**
   - 其余字符（中文、反引号、`/`、`：`、`+`、`|`）**原样保留**，不要整体 `encodeURIComponent`
4. **末几节标 `🔧`**（本章自测 / 覆盖对账 / 诚实标注），`🔧` 必须写在链接**外面**。
5. **改完必须机检**：把每条锚点还原（`%20`→空格、`\(`→`(`）与标题逐字比对。

> ⚠️ **`|` 是个已知难点**：标题里有 `|` 时（如"初始化 / 值初始化"这类含竖线的标题），
> 锚点处理规则**尚未在本讲义中机检验证**。**建议避免在 `##` 标题里使用 `|`**。
> 这条限制是实测缺口，不是惯例——补上机检脚本后回来删掉这个警告。

### 10. 覆盖对账表（必写）

章末必须有这张表，格式固定：

```markdown
| 覆盖表条目 | 本文章节 |
|---|---|
| 0.1 编译器的选择与安装 | 第 1 节、第 6 节、第 7 节 |
```

**这张表是"完整性可验证"的兑现方式。**
读者拿它跟 [`00_知识点总览.md`](00_知识点总览.md) 一对，就知道漏没漏。
**覆盖表里列到的条目，一个都不能少**；没覆盖到的要明确写"本节不展开，原因是什么"。

> ⚠️ **已真实发生过一次**：第 1 章对账表声称 0.3 覆盖了"注释"，
> 但正文**没有专门讲注释的两种形式**。修复：要么补正文，要么改对账表。
> **判据是"正文里找得到"，不是"表里写了"。**

### 10.1 ⚠️ 跨章引用必须用「章内实际节号 + 标题」

**这个错误在 Python 笔记里真实发生过 5 次**，读者无法自行纠正，**比不写更伤信任**。

| 错误写法 | 问题 | 正确写法 |
|---|---|---|
| 见 `03_表达式、运算与转换.md` **2.7 节** | `2.7` 是**覆盖表条目号**，不是那一章的节号 | 见 `03_表达式、运算与转换.md` 第 7 节「显式类型转换」 |

**规矩**：

1. 指别章内容时，写**目标章的实际节号 + 标题**。
2. 不确定就先去看那章的实际标题，**不要拿覆盖表条目号凑**。
3. 每章写完自查一遍：把所有 `N.M 节` 形式的引用抽出来，逐个确认目标存在。

### 11. 本章自测

- 5～10 题，题目要有区分度（能区分"背过"和"懂了"）。
- 答案放 `<details><summary>答案</summary>` 折叠块。
- **至少一题是"为什么会这样"**而不是"是什么"。
- **至少一题针对本章的 UB / 实现定义 / 平台差异**——C++ 里这是最该考的地方。

### 12. 诚实标注

章末必须有这张表，列出**本章哪些话没有当次工具输出支撑**，以及读者怎么自己验。

```markdown
| 说法 | 状态 | 怎么自己验 |
|---|---|---|
| `sizeof(int) == 4` | ✅ 本轮实测 | 编译运行即可 |
| GCC 的警告开关 | ⚠️ 本机无 GCC，未实测 | 装 MinGW-w64 后对照 |
```

**这张表是"哪些话你可以信"的清单。** 有标注比没标注重要得多。

## 三、长度

**参考量级：1200～2500 行。这不是硬指标。**

- 同规格的 Python 笔记实测分布是 960～4457 行，**没有一章是灌水灌出来的**。
- 超出的原因是硬性要求直接产生的成本：**每个代码块都要实跑并贴真实输出**，
  代码块与输出本身占正文一半左右。
- 判定标准：**内容多就长，内容少不要灌水。** 宁可短而实，不要长而空。
  **不要为了凑行数删掉已验证的示例，也不要为了压行数把子条目改成"指路"。**
