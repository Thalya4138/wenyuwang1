## 0. 先记住的七件事

1. **模板不是代码，是"生成代码的配方"。** 写 `template <class T> T max_value(T, T);` 的时候，
   编译器**一个函数都不会生成**；只有你真正用 `max_value(3, 7)` 调用一次，它才照着配方造出 `int` 版本。
2. **实例化 = 拿具体类型去套配方。** `max_value(3, 7)` 里的 `T` 被推成 `int`，编译器生成一个 `int` 版本的函数。
   **每个用到的类型各生成一份**，互不相干。
3. **模板报错出现在实例化点，不是定义点。** 模板写错但没被实例化过，编译器可能一声不响。
   这是"模板报错难懂"的根本原因，不是编译器偷懒。
4. **模板定义必须写在头文件里。** 因为每个用它的 `.cpp` 都要**自己生成**那份代码，
   而它能生成的只有自己看得见的东西（第 3 节）。
5. **`if constexpr`（C++17）是编译期分支。** 条件为假的那个分支**会被整个丢掉**，
   所以它能装"对当前类型根本编不过"的代码——`if` 做不到这件事（第 5 节）。
6. **折叠表达式（C++17）让参数包不用再递归展开。** 老办法要写"一个 + 其余"的递归和一个终止重载，
   新办法一行 `(args + ...)`（第 6 节）。
7. **`concepts`（C++20）是 SFINAE 那堆复杂写法的现代答案。** 本讲义基线是 C++17，
   所以只标位置、给出它解决的问题，不把它写进正文主干（第 9 节）。

> 如果只记一条，记第 1 条。**后面三节（推导、头文件、报错难懂）全都是它的推论。**

## 1. 函数模板与类模板：把类型变成参数

### 1.1 先说它解决什么问题

第 `05` 章讲函数的时候，同一个函数只能有一种参数类型。想对 `int` 和 `double` 各求一次最大值，得写两遍：

```cpp
int    max_value(int a, int b)       { return a < b ? b : a; }
double max_value(double a, double b) { return a < b ? b : a; }
```

函数体**一模一样**，唯一的差别是类型。函数重载能解决"写两遍"的问题，但解决不了"**将来出现新类型还得再写一遍**"
——比如用户自己定义的 `Money` 类型。

**模板的解法是：把"类型"本身变成参数。** 于是这一个写法对所有类型都成立：

```cpp
template <class T>
T max_value(T a, T b) { return a < b ? b : a; }
```

### 1.2 最小例子：一个函数模板服务五种类型

<!-- example:ch11_func_template -->
```cpp
#include <iostream>
#include <string>

template <class T>
T max_value(T a, T b) {
    return a < b ? b : a;
}

int main() {
    std::cout << "max_value(3, 7)          = " << max_value(3, 7) << '\n';
    std::cout << "max_value(2.5, 1.5)      = " << max_value(2.5, 1.5) << '\n';
    std::cout << "max_value('a', 'z')      = " << max_value('a', 'z') << '\n';
    std::cout << "max_value<std::string>   = "
              << max_value(std::string("apple"), std::string("banana")) << '\n';

    // 显式指定模板实参：两边类型不同时用得上
    std::cout << "max_value<double>(3, 4.5) = " << max_value<double>(3, 4.5) << '\n';
}
```

<!-- result:ch11_func_template -->
```text
max_value(3, 7)          = 7
max_value(2.5, 1.5)      = 2.5
max_value('a', 'z')      = z
max_value<std::string>   = banana
max_value<double>(3, 4.5) = 4.5
```

**逐行读这张输出：**

| 调用 | `T` 被推成 | 生成了一份 | 结果 |
|---|---|---|---|
| `max_value(3, 7)` | `int` | `int max_value(int, int)` | `7` |
| `max_value(2.5, 1.5)` | `double` | `double max_value(double, double)` | `2.5` |
| `max_value('a', 'z')` | `char` | `char max_value(char, char)` | `z` |
| `max_value(std::string(...), ...)` | `std::string` | `std::string max_value(std::string, std::string)` | `banana` |
| `max_value<double>(3, 4.5)` | **你手动指定 `double`** | 复用上面第二份 | `4.5` |

**最后一行是这一节的重点**：`max_value(3, 4.5)` 里的 `3` 是 `int`、`4.5` 是 `double`，
编译器**推不出一个统一的 `T`**，所以直接不让你编过。显式写 `max_value<double>(3, 4.5)` 就是告诉它
"按 `double` 来"，于是 `3` 隐式转成 `3.0`，复用已经生成好的那一份。

> ⚠️ **坑**：模板不是"自动帮你转换类型"的东西。
> `max_value(3, 4.5)` **编译失败**，报的是**模板参数推导冲突**（"无法推导 `T`"这一类）。
> **程序实际怎么解释它**：推导发生在**重载决议之前**，两边推出不同的 `T` 就没有候选函数可用，
> 于是报"没有匹配的函数"。**错误归属：类型类（模板推导）**，不是语法错。
> **修法**：显式写 `max_value<double>(3, 4.5)`，或者把两个实参写成同一类型。

### 1.3 类模板：把类型参数用在类上

函数模板把类型变成参数，类模板做同一件事，区别是**类型参数会成为类的一部分**。

<!-- example:ch11_class_template -->
```cpp
#include <iostream>
#include <stdexcept>
#include <string>
#include <vector>

template <class T>
class Box {
public:
    void add(const T& item) { items_.push_back(item); }
    std::size_t size() const { return items_.size(); }
    const T& at(std::size_t i) const {
        if (i >= items_.size()) {
            throw std::out_of_range("Box::at");
        }
        return items_[i];
    }
    T sum() const {
        T total{};
        for (const T& x : items_) {
            total += x;
        }
        return total;
    }

private:
    std::vector<T> items_;
};

int main() {
    Box<int> bi;
    bi.add(1);
    bi.add(2);
    bi.add(3);
    std::cout << "Box<int> size=" << bi.size() << " sum=" << bi.sum()
              << " at(1)=" << bi.at(1) << '\n';

    Box<std::string> bs;
    bs.add("hello");
    bs.add(" ");
    bs.add("world");
    std::cout << "Box<std::string> size=" << bs.size() << " 拼接=" << bs.sum() << '\n';

    try {
        std::cout << bi.at(99) << '\n';
    } catch (const std::out_of_range& e) {
        std::cout << "越界访问抛异常: " << e.what() << '\n';
    }
}
```

<!-- result:ch11_class_template -->
```text
Box<int> size=3 sum=6 at(1)=2
Box<std::string> size=3 拼接=hello world
越界访问抛异常: Box::at
```

**注意 `Box<int>` 和 `Box<std::string>` 是两种完全不同的类型**，不是"同一个类型的两个对象"。
它们各自生成了一份完整的类（包括各自的成员函数）。

**`sum()` 里那行 `T total{};` 值得停一下**：
`{}` 是**值初始化**，对 `int` 得到 `0`，对 `std::string` 得到**空串**。
所以同一个 `sum()` 体，在 `Box<int>` 里是"加整数"，在 `Box<std::string>` 里变成"拼接字符串"——
输出的 `6` 和 `hello world` 就是同一段代码的两种实例。

> ⚠️ **坑**：`T total{};` 不能改成 `T total = 0;`。
> 对 `Box<std::string>` 来说 `= 0` 根本编不过（`std::string` 没有从 `0` 的转换）。
> **`{}` 在这里的作用是"用该类型自己的默认值"，而这个"默认值是什么"由类型决定。**
> 这正是第 `02` 章第 5 节讲"值初始化"时那条规矩在泛型代码里的价值。

### 1.4 类模板的成员函数是"用到才生成"

`Box<T>` 里三个成员函数（`add` / `size` / `at` / `sum`），**并不是 `Box<int>` 一被提到就全部生成**。
编译器只为**实际被调用的那些**成员函数生成代码。

**这带来一个很重要的效果**：模板里写了"对某些类型编不过"的代码，
只要那个类型没用过它，就**不会报错**。

```cpp
template <class T>
class Box {
    T sum() const { T total{}; for (const T& x : items_) total += x; return total; }
    //                        ↑ 如果 T 不支持 +=，这里会错——但只在你调用 sum() 时才检查
};
```

**本机实测的证据**（第 `10` 章第 6.2 节那段 `std::visit` + `overloaded` 代码就是同一个机制）：
那段 `overloaded` 用到了可变参数模板、继承和 `using` 声明，这些语法在**第 6 节**才讲，
但它在那段代码里被**成功编译并运行**了——因为编译器只要求"用到的部分合法"。

## 2. 推导与实例化：模板什么时候才真的变成代码

### 2.1 三个词定死

| 词 | 含义 |
|---|---|
| **模板参数** | 模板里那个占位符，如 `template <class T>` 里的 `T` |
| **模板实参** | 你实际给的具体类型，如 `max_value<double>` 里的 `double` |
| **实例化** | 用实参替换参数、生成真正代码的**过程** |
| **推 导** | 从函数调用实参的类型**倒推**出模板实参的过程（只对函数模板） |

**顺序很重要**：函数模板先**推导**出实参，再用它**实例化**。类模板没有推导（C++17 之前），
你得手写 `Box<int>`。

### 2.2 推导怎么工作

<!-- example:ch11_deduction -->
```cpp
#include <iostream>
#include <type_traits>
#include <typeinfo>
#include <vector>

template <class T>
T twice(T x) {
    return x + x;
}

template <class T>
std::size_t raw_size(const T& x) {
    return sizeof(x);
}

int main() {
    std::cout << std::boolalpha;
    std::cout << "twice(3) 的类型是 int        : "
              << std::is_same<decltype(twice(3)), int>::value << '\n';
    std::cout << "twice(3.0) 的类型是 double   : "
              << std::is_same<decltype(twice(3.0)), double>::value << '\n';
    std::cout << "twice(3L) 的类型是 long      : "
              << std::is_same<decltype(twice(3L)), long>::value << '\n';

    int n = 5;
    const int cn = 7;
    std::cout << "raw_size(n) 与 raw_size(cn) 推成同一个 T : "
              << std::is_same<decltype(raw_size(n)), decltype(raw_size(cn))>::value << '\n';
    std::cout << "sizeof(n)=" << raw_size(n) << " sizeof(cn)=" << raw_size(cn) << '\n';

    std::vector<int> v{1, 2, 3};
    std::cout << "T 是引用时 sizeof 仍然是元素本身大小: " << raw_size(v[0]) << '\n';

    auto lambda = [](auto a, auto b) { return a + b; };
    std::cout << "泛型 lambda lambda(1, 2.5) = " << lambda(1, 2.5) << '\n';
}
```

<!-- result:ch11_deduction -->
```text
twice(3) 的类型是 int        : true
twice(3.0) 的类型是 double   : true
twice(3L) 的类型是 long      : true
raw_size(n) 与 raw_size(cn) 推成同一个 T : true
sizeof(n)=4 sizeof(cn)=4
T 是引用时 sizeof 仍然是元素本身大小: 4
泛型 lambda lambda(1, 2.5) = 3.5
```

**五条信息，逐条说：**

1. **前三行**：`T` 完全由**实参的类型**决定。`3` 是 `int`、`3.0` 是 `double`、`3L` 是 `long`，
   于是实例化出**三份不同的 `twice`**。这不是"一个函数处理三种类型"，是**三个函数**。
2. **第四行 `true`**：`raw_size(n)` 和 `raw_size(cn)` 推出**同一个 `T`**。
   `cn` 是 `const int`，但 `raw_size` 的参数是 `const T&`，
   所以 `T` 推成 **`int`**（`const` 被参数类型里的 `const` 吸收掉了）。
   **这就是第 `02` 章第 6.1 节讲的"`auto`/模板推导会去掉顶层 `const`"在模板上的同一件事。**
3. **第五行 `sizeof(n)=4 sizeof(cn)=4`**：`const` 不影响大小。
4. **第六行 `4`**：`raw_size(v[0])` 里 `v[0]` 是 `int&`（左值），
   但 `sizeof(x)` 求的是**类型大小**，不是引用大小——`sizeof(int&) == sizeof(int) == 4`。
5. **最后一行 `3.5`**：`[](auto a, auto b){...}` 是**泛型 lambda**（C++14 起），
   它本质上是"编译器替你写了一个 `operator()` 模板"。`lambda(1, 2.5)` 里
   `a` 推成 `int`、`b` 推成 `double`，`a + b` 按算术转换得到 `double` 的 `3.5`。
   **注意 `auto` 在这里可以各自推不同颜色**（`a` 和 `b` 不必同类型），
   这和 `max_value` 里"两个实参必须推出同一个 `T`"是不同的规则。

> ⚠️ **坑**：看到 `raw_size(cn)` 能编过，就以为"模板能处理 `const`"。
> **真实情况是 `const` 被"吃掉了"**——`T` 是 `int`，不是 `const int`。
> 要保留 `const` 得显式写 `raw_size<const int>(cn)`，或者把参数类型改成 `T`（按值也会去掉 `const`）。
> **这类"限定符在推导中被丢掉"的行为属于类型系统的规则，不是编译器特性。**

### 2.3 实例化：每个类型各有一份，静态成员也是

**"实例化"最直接的证据是：每个实例的 `static` 成员是独立的。**

<!-- example:ch11_instantiation -->
```cpp
#include <iostream>
#include <type_traits>

template <class T>
struct Counter {
    static int created;
    Counter() { ++created; }
};
template <class T>
int Counter<T>::created = 0;

template <class T>
T identity(T x) {
    return x;
}

int main() {
    Counter<int> a;
    Counter<int> b;
    Counter<double> c;
    std::cout << "Counter<int>::created    = " << Counter<int>::created << '\n';
    std::cout << "Counter<double>::created = " << Counter<double>::created << '\n';
    std::cout << "两个类型各自有独立的静态成员: "
              << (Counter<int>::created != Counter<double>::created) << '\n';

    std::cout << std::boolalpha;
    std::cout << "identity(1) 和 identity(2) 是同一个实例吗（同一类型）: "
              << std::is_same<decltype(identity(1)), decltype(identity(2))>::value << '\n';
    std::cout << "identity(1) 和 identity(1.0) 是同一个类型吗: "
              << std::is_same<decltype(identity(1)), decltype(identity(1.0))>::value << '\n';
}
```

<!-- result:ch11_instantiation -->
```text
Counter<int>::created    = 2
Counter<double>::created = 1
两个类型各自有独立的静态成员: 1
identity(1) 和 identity(2) 是同一个实例吗（同一类型）: true
identity(1) 和 identity(1.0) 是同一个类型吗: false
```

**`Counter<int>::created` 是 2、`Counter<double>::created` 是 1** —— 这一行直接证明了
**`Counter<int>` 和 `Counter<double>` 是两个独立的类**，各自有自己的静态成员存储。

**最后两行合起来就是一个完整的"实例化"模型**：

```text
identity(1)   → T = int    → 生成 int identity(int)      ┐
identity(2)   → T = int    → 复用上面那一份              ┘ 同一个实例
identity(1.0) → T = double → 生成 double identity(double)   另一个实例
```

**缓存/复用的判据**：**模板实参列表相同就复用，不同就新生成一份。**
`identity(1)` 和 `identity(2)` 的实参类型都是 `int`，所以只有一份代码。

### 2.4 两阶段查找：为什么错误在实例化点才出现

编译器处理模板时**分两个阶段**看你的代码：

| 阶段 | 什么时候 | 检查什么 |
|---|---|---|
| **第一阶段** | 看到模板**定义**时（还没人用） | 只检查**不依赖模板参数**的东西：括号配对、`;`、名字拼写、语法 |
| **第二阶段** | **实例化**时（有人用了） | 检查**依赖模板参数**的东西：`T` 有没有 `+`、有没有 `size()`、类型对不对 |

**这解释了两件常被误解的事：**

1. **为什么"模板写了但没用过，编译器一声不响"。**
   如果你的错误只在第二阶段才暴露，而模板从未被实例化，第二阶段**根本没发生**。
2. **为什么模板报错里会夹着一堆标准库头文件的行号。**
   实例化时编译器要把 `T` 代进去，如果 `T` 是 `std::string`，错误可能出现在
   `std::string` 内部的某个运算符上——**报错位置指向库内部，真正的原因在你的模板里。**

**本机实测的第三阶段产物**（这是"第二阶段的错"最典型的样子）：

```text
main.cpp(5): error C2760: 语法错误: 此处出现意外的“args”；应为“(”
main.cpp(5): note: 模板实例化上下文(最早的实例化上下文)为
main.cpp(9): note: 查看对正在编译的函数 模板 实例化“size_t count_args_wrong<int,int,int>(int,int,int)”的引用
```

**读法**：两条 `note:` 就是编译器在告诉你"**这个错误是在实例化 `count_args_wrong<int,int,int>` 时暴露的**"。
看到 `模板实例化上下文` 这几个字，就知道该往"哪个类型触发了它"的方向查，而不是盯着报错那一行。

> ⚠️ **坑**：模板的报错常常"第一条不是原因、最后一条才是"。
> 上面这个例子恰好相反：**第一条 `error C2760` 是原因**（`sizeof...args` 少写了括号），
> 后面的 `note:` 全是解释上下文。
> **实用读法**：先找**第一条 `error`**，再找 `模板实例化上下文` 那几行确认是哪个类型触发的。

## 3. 为什么模板定义必须写在头文件里

### 3.1 先把"翻译单元"接上

第 `01` 章第 10 节「源文件、头文件、翻译单元：它们不是同一件事」已经把机制讲清了：
**编译器一次只处理一个翻译单元**（一个 `.cpp` 加上它 `#include` 进来的所有头文件），
翻译单元之间**互不知情**；把它们接起来是**链接器**的事。

**模板的问题正好卡在这条分界线上。**

### 3.2 普通函数可以"声明放头文件、定义放 .cpp"

这是第 05 章第 9 节「`inline`、多文件编译与 ODR（入门版）」讲的常规做法，
它的成立条件是：**`.cpp` 里生成了一份可以被链接器找到的符号。**

```cpp
// util.h   ← 只有声明
template <class T>
T max_value(T a, T b);          // 这是模板，但下面要说的不是它
```

普通函数的样子是：

```cpp
// util.h
int add(int a, int b);          // 声明：告诉每个翻译单元"有这么个函数"

// util.cpp
int add(int a, int b) { return a + b; }   // 定义：这里生成了一份 add 的机器码

// main.cpp
#include "util.h"
int main() { return add(1, 2); }          // 只需要知道签名，编译期不需要函数体
```

链接器在 `util.obj` 里找到 `add` 的符号，拼起来就完事了。**关键：函数体只需要出现在一个地方。**

### 3.3 模板照这个写法会怎样：本机实测

**探针 A1**：`util.h` 里只有模板声明，定义写在 `util.cpp` 里，然后编译两个 `.cpp`：

```text
util.h    template <class T> T max_value(T a, T b);            // 只有声明
util.cpp  template <class T> T max_value(T a, T b) { ... }      // 定义在这里
main.cpp  #include "util.h"  ... max_value(3, 7) ...           // 调用它
```

**真实结果（本机 MSVC 实测）**：

```text
main.obj : error LNK2019: 无法解析的外部符号 "int __cdecl max_value<int>(int,int)" (??$max_value@H@@YAHHH@Z)，函数 main 中引用了该符号
app.exe : fatal error LNK1120: 1 个无法解析的外部命令
```

**探针 A2**：把**定义也放进 `util.h`**，同样编译两个 `.cpp`：

```text
main.cpp
util.cpp
正在生成代码...
7
```

**编译成功，输出 `7`。**

### 3.4 为什么

**逐条对上第 3.1 节的机制：**

| 步骤 | 探针 A1（定义在 `.cpp`） | 探针 A2（定义在头文件） |
|---|---|---|
| 编译 `util.cpp` | 看到模板**定义**，但**没有任何调用**，推不出 `T` → **一份代码都不生成** | 看到模板定义，但…… |
| 编译 `main.cpp` | 看到模板**声明**和调用 `max_value(3, 7)`，推出 `T = int`，但**看不到函数体** → 只能生成一个"外部符号 `max_value<int>`"的**引用** | 看到模板**定义**和调用，推出 `T = int`，**函数体就在眼前** → **现场生成 `max_value<int>`** |
| 链接 | `util.obj` 里没有 `max_value<int>`，`main.obj` 需要它 → **`LNK2019` 无法解析的外部符号** | 每个用到的翻译单元各自生成了一份，链接器正常拼起来 |

**所以那个报错信息里的 `max_value<int>` 就是全部线索**：
它需要的是一个**已经具现化的具体函数**，而 `util.cpp` 那个翻译单元**从来没被要求造它**。

> **一句话总结**：**普通函数的"声明/定义分离"之所以成立，是因为定义那一侧会被独立编译成一份符号。
> 模板给不了这个保证——它的定义在没人用的时候不产生任何符号，在有人用的时候又必须"现场可用"。**
>
> **结论**：**模板的定义（不只是声明）必须让每个使用它的翻译单元都看得见**，
> 也就是**放在头文件里**，或者用**显式实例化**指定"我要哪些类型"。

### 3.5 三个选项对比

| 做法 | 怎么写 | 优点 | 代价 |
|---|---|---|---|
| **定义放头文件**（推荐） | `util.h` 里写完整定义，`.cpp` 只管 `#include` | 任何类型都能用；不用预先知道有哪些类型 | 头文件变大；改一行要重编所有包含它的文件 |
| **显式实例化** | 头文件仍放声明，`.cpp` 里加 `template int max_value<int>(int, int);` | 编译更快，实现细节不暴露 | **只能用于你列出的那几种类型**，出现新类型就链接失败 |
| 把定义塞进 `.cpp` 并希望它工作 | — | 无 | **就是探针 A1，直接链接失败** |

**显式实例化的代码形态**（多文件示例，未进自动基线）：

```cpp
// util.h
template <class T>
T max_value(T a, T b);                       // 仍然只有声明

// util.cpp
#include "util.h"
template <class T>
T max_value(T a, T b) { return a < b ? b : a; }

template int max_value<int>(int, int);       // ← 显式实例化：现在就给我造 int 版
// 再出现 max_value(3.0, 1.0) 就会重新 LNK2019 —— 因为 double 版没被指定
```

> ⚠️ **坑**：有人认为"模板也可以像普通函数那样声明放头文件、定义放 `.cpp`"，
> 并且在只编译**一个** `.cpp` 时它**确实能编过**（因为定义就在同一个翻译单元里）。
> **程序实际怎么解释它**：一旦有**第二个**翻译单元要调用它，就会 `LNK2019`。
> **错误归属：链接类**，不是编译类——这是最容易误判的一类错误：
> **编译器全绿，链接器报错**，而报错的字面意思（"无法解析的外部符号"）和模板毫不相关。
>
> **这也解释了为什么"把模板搬到头文件就好了"是有效的**：
> 你不是在满足某个约定，你是让**每个需要的翻译单元都能自己生成那份代码**。

> ⚠️ **与 `inline` 的关系**：把**普通函数**的定义放进头文件会违反 ODR（第 05 章第 9 节「`inline`、多文件编译与 ODR（入门版）」），
> 所以要加 `inline`。**模板不需要加 `inline`**——标准对模板实例化有单独的规定，
> 多个翻译单元生成同一份实例是允许的，链接器会把它们合并。
> 这两条规则的根据不同，不要混成"头文件里的定义都要 inline"。

## 4. 特化与偏特化：模板的"补丁机制"

### 4.1 它解决什么问题

通用版本按"配方"生成代码，但**某些类型需要不一样的行为**。

最经典的例子：**用 `==` 判断两个浮点数相等是错的**（第 `03` 章会讲浮点表示），
但如果你写了一个通用的 `almost_equal`，对 `int` 可能又不需要容差。

**特化就是"给某个具体类型换一份专用实现"。**

### 4.2 全特化：给一个具体类型开专用版本

<!-- example:ch11_specialization -->
```cpp
#include <iostream>
#include <string>
#include <type_traits>

// 通用版本：按 bool 输出
template <class T>
std::string describe(const T&) {
    return "一个值";
}

// 全特化：T = bool 时用这一份
template <>
std::string describe<bool>(const bool& v) {
    return v ? "真" : "假";
}

// 类模板的全特化：给 bool 单独一版
template <class T>
struct Kind {
    static const char* name() { return "一般类型"; }
};

template <>
struct Kind<bool> {
    static const char* name() { return "布尔"; }
};

int main() {
    std::cout << std::boolalpha;
    std::cout << "describe(42)      = " << describe(42) << '\n';
    std::cout << "describe(true)    = " << describe(true) << '\n';
    std::cout << "describe(2.5)     = " << describe(2.5) << '\n';

    std::cout << "Kind<int>::name()  = " << Kind<int>::name() << '\n';
    std::cout << "Kind<bool>::name() = " << Kind<bool>::name() << '\n';
    std::cout << "Kind<double>::name() = " << Kind<double>::name() << '\n';
}
```

<!-- result:ch11_specialization -->
```text
describe(42)      = 一个值
describe(true)    = 真
describe(2.5)     = 一个值
Kind<int>::name()  = 一般类型
Kind<bool>::name() = 布尔
Kind<double>::name() = 一般类型
```

**机制**：`describe(true)` 里 `T` 推成 `bool`，编译器发现**有一个 `bool` 的全特化**，
就选那份专用实现（输出 `真`）而不是通用版本（本该输出 `一个值`）。

### 4.3 偏特化：给"一族类型"开专用版本

**偏特化只适用于类模板**，它给"部分类型"开专用实现，而不是某一个具体的类型。

<!-- example:ch11_partial_specialization -->
```cpp
#include <iostream>

template <class T>
struct Kind {
    static const char* name() { return "一般类型"; }
};

// 偏特化：所有指针类型 T* 都走这一份
template <class T>
struct Kind<T*> {
    static const char* name() { return "指针"; }
};

// 偏特化：所有常量类型 const T 都走这一份
template <class T>
struct Kind<const T> {
    static const char* name() { return "常量"; }
};

int main() {
    std::cout << "Kind<int>::name()        = " << Kind<int>::name() << '\n';
    std::cout << "Kind<int*>::name()       = " << Kind<int*>::name() << '\n';
    std::cout << "Kind<double*>::name()    = " << Kind<double*>::name() << '\n';
    std::cout << "Kind<const int>::name()  = " << Kind<const int>::name() << '\n';
    std::cout << "Kind<const int*>::name() = " << Kind<const int*>::name() << '\n';
}
```

<!-- result:ch11_partial_specialization -->
```text
Kind<int>::name()        = 一般类型
Kind<int*>::name()       = 指针
Kind<double*>::name()    = 指针
Kind<const int>::name()  = 常量
Kind<const int*>::name() = 指针
```

**注意 `Kind<const int*>` 输出的是 `指针`**（不是 `常量`）：
`const int*` 是"指向常量的指针"，它的形态匹配 `T*`（其中 `T = const int`），
不匹配 `const T`。**这几个分支的优先顺序由"哪个更特化"决定**，
这就是偏特化最需要小心的地方。

> ⚠️ **坑**：`const int*` 和 `const T` 谁匹配，容易凭直觉猜错。
> **`const int*` 是"指针"**（顶层是 `*`），所以 `T*` 分支赢；
> 想让它走"常量"分支，得写 `Kind<int* const>`（顶层 `const` 的指针）。
> **错误归属：类型类（模板匹配）**，编译能过，只是选错分支。

### 4.4 定位：特化是"补丁"，不是常用工具

| | 用在哪 | 什么时候写 |
|---|---|---|
| **全特化** | 函数模板**和**类模板 | 某个具体类型需要完全不同的实现 |
| **偏特化** | **只有类模板** | 某一族类型（`T*`、`const T`、`vector<T>`…）需要不同实现 |
| **函数模板的"偏特化"** | ❌ **不允许** | 想达到同样效果：用**重载**，或用第 5 节的 `if constexpr`，或用第 8 节的 `enable_if` |

**为什么函数模板不能偏特化**：函数已经有**重载**这个机制了，两者混在一起会让"选哪个"的规则变得无法预测。
所以标准直接禁止，让你用重载代替。

**它的定位**：**标准库自己是最大的用户**——
第 7 节那个 `std::is_pointer<T>`、`std::remove_const<T>`，内部就是这套写法。
**日常业务代码里很少需要自己写特化**，遇到需要时优先考虑 `if constexpr` 和重载。

## 5. `if constexpr`：编译期选分支

### 5.1 它和普通 `if` 的区别

普通 `if` 是**运行期**分支：两个分支**都要能编过**，运行时再挑一个。
`if constexpr`（C++17）是**编译期**分支：条件在编译期求值，**假的那一支会被整个丢掉**。

**"丢掉"这两个字就是它全部的用途。**

<!-- example:ch11_if_constexpr -->
```cpp
#include <iostream>
#include <string>
#include <type_traits>

template <class T>
std::string as_text(const T& value) {
    if constexpr (std::is_integral<T>::value) {
        return "整数: " + std::to_string(value);
    } else if constexpr (std::is_floating_point<T>::value) {
        return "浮点: " + std::to_string(value);
    } else {
        return std::string("其它: ") + value;
    }
}

template <class T>
void show_size_if_possible(const T&) {
    if constexpr (std::is_class<T>::value || std::is_arithmetic<T>::value) {
        std::cout << "  知道大小: " << sizeof(T) << '\n';
    } else {
        std::cout << "  这个类型没有可用的 sizeof 分支\n";
    }
}

int main() {
    std::cout << as_text(42) << '\n';
    std::cout << as_text(2.5) << '\n';
    std::cout << as_text(std::string("文本")) << '\n';

    show_size_if_possible(1);
    show_size_if_possible(1.5);
    show_size_if_possible(std::string("x"));
}
```

<!-- result:ch11_if_constexpr -->
```text
整数: 42
浮点: 2.500000
其它: 文本
  知道大小: 4
  知道大小: 8
  知道大小: 32
```

### 5.2 为什么这三个分支能共存

**`as_text` 里三个分支的代码彼此"编不过"**：

| 分支 | 代码 | 对 `std::string` 来说 |
|---|---|---|
| 整数分支 | `std::to_string(value)` | **`std::to_string` 没有收 `std::string` 的重载** → 编不过 |
| 浮点分支 | `std::to_string(value)` | 同上 |
| 其它分支 | `std::string("其它: ") + value` | `std::string + int` **编不过** |

**如果这是普通 `if`，`as_text(42)` 会立刻编译失败**——因为编译器要为这一份实例化检查**所有分支**，
而"其它分支"里的 `std::string + int` 不合法。

**`if constexpr` 把不满足条件的分支在实例化前就丢掉了**，所以每个类型只留下自己那一支：

```text
as_text(42)                → T = int         → 只保留"整数"分支
                                              （"其它"分支里的 std::string + int 根本不检查）
as_text(2.5)               → T = double      → 只保留"浮点"分支
as_text(std::string("文本")) → T = std::string → 只保留"其它"分支
                                              （std::to_string(std::string) 根本不检查）
```

**这就是 `if constexpr` 存在的唯一理由**：**它让"一个模板体里写互相矛盾的代码"变成合法。**
没有它的时候，同一件事要用第 8 节的 `enable_if` + 多个重载函数来拼，代码量和可读性都差得多。

**输出里的 `2.500000` 是 `std::to_string(double)` 的默认格式**（6 位小数），
不是"浮点打印丢精度"——`std::to_string` 就是这样的，和 `std::cout << 2.5` 的表现不同。

### 5.3 三个必须记住的约束

| 约束 | 说明 |
|---|---|
| **条件必须是编译期常量表达式** | `if constexpr (n > 0)` 里 `n` 得是 `constexpr`；运行期变量直接报错 |
| **被丢掉的分支不参与实例化，但必须语法合法** | 括号、分号、名字写法还是得对。它只免掉了"**类型相关**"的检查 |
| **`if constexpr` 不能替代多态** | 它是"每个实例各留一支"，不是"运行时挑一支"。运行期的选择还是得用虚函数（第 `07` 章第 8 节「继承与派生、`virtual` 与多态」） |

> ⚠️ **坑**：以为 `if constexpr (false) { ... }` 里的代码"完全不用管"。
> **程序实际怎么解释它**：被丢弃的分支仍然要**解析语法**（括号配对、名字拼写），
> 只是不做**依赖模板参数的语义检查**。
> 所以写 `if constexpr (std::is_integral<T>::value) { a b c }` 照样报语法错。
>
> **另一个更隐蔽的坑**：被丢弃的分支里如果调用的函数**不依赖模板参数**，
> 有些编译器仍然会去查它的名字（因为它在第一阶段就能查）。
> 依赖模板参数的写法（如 `value.size()` 里的 `value` 是 `T` 类型）才会真正被推迟到第二阶段。

## 6. 可变参数模板与折叠表达式

### 6.1 老办法：递归展开（C++11 起）

"可变参数模板"（variadic template）让模板收**任意个**参数。C++11 引入它时，
标准给的展开方式是**一次剥掉一个参数、递归下去**：

<!-- example:ch11_recursive_pack -->
```cpp
#include <iostream>

// 老办法（C++11 起）：一次剥掉一个参数，递归到没有参数为止
void print() {                       // 递归终止：没有参数
    std::cout << '\n';
}

template <class T, class... Rest>
void print(const T& first, const Rest&... rest) {
    std::cout << first << ' ';
    print(rest...);                  // 用剩下的参数继续
}

// 老办法求和：同样要写"一个 + 其余"
int sum() { return 0; }

template <class T, class... Rest>
auto sum(const T& first, const Rest&... rest) {
    return first + sum(rest...);
}

// 新办法求和：一次折叠，不用递归，也不用写终止重载
template <class... Ts>
auto sum_fold(Ts... args) {
    return (args + ...);
}

int main() {
    std::cout << "print 老办法: ";
    print(1, 2.5, "三");

    std::cout << "sum 老办法: " << sum(1, 2, 3, 4) << '\n';
    std::cout << "sum 老办法(1, 2.5): " << sum(1, 2.5) << '\n';
    std::cout << "sum_fold 新办法(1, 2, 3, 4): " << sum_fold(1, 2, 3, 4) << '\n';
    std::cout << "sum_fold 新办法(1, 2.5): " << sum_fold(1, 2.5) << '\n';
}
```

<!-- result:ch11_recursive_pack -->
```text
print 老办法: 1 2.5 三 
sum 老办法: 10
sum 老办法(1, 2.5): 3.5
sum_fold 新办法(1, 2, 3, 4): 10
sum_fold 新办法(1, 2.5): 3.5
```

**执行轨迹（老办法的 `sum(1, 2, 3, 4)`）**：

```text
sum(1, 2, 3, 4)
  → T = int, Rest = {int, int, int}
  → return 1 + sum(2, 3, 4)
                → T = int, Rest = {int, int}
                → return 2 + sum(3, 4)
                              → T = int, Rest = {int}
                              → return 3 + sum(4)
                                            → T = int, Rest = {}
                                            → return 4 + sum()
                                                          → 匹配到那个无参数的 sum()
                                                          → return 0
```
**结果是四层递归嵌套。**

### 6.2 新办法：折叠表达式（C++17）

<!-- example:ch11_fold_ok -->
```cpp
#include <iostream>
#include <string>

// 一元右折叠：args + ...   →  a1 + (a2 + (a3 + ...))
template <class... Ts>
auto sum_all(Ts... args) {
    return (args + ...);
}

// 逗号折叠：把每个参数依次塞进流
template <class... Ts>
void print_all(const Ts&... args) {
    ((std::cout << args << ' '), ...);
    std::cout << '\n';
}

// sizeof... 只数个数，不展开包。
// 注意：参数包**不写名字**（写成 Ts...），这样既不需要用它，也不会触发 C4100
template <class... Ts>
std::size_t count_args(Ts...) {
    return sizeof...(Ts);
}

// 二元折叠：带一个初值
template <class... Ts>
auto product_all(Ts... args) {
    return (1 * ... * args);
}

int main() {
    std::cout << "sum_all(1,2,3,4)   = " << sum_all(1, 2, 3, 4) << '\n';
    std::cout << "sum_all(1.5, 2.5)  = " << sum_all(1.5, 2.5) << '\n';
    std::cout << "sum_all(1, 2.5)    = " << sum_all(1, 2.5) << '\n';
    std::cout << "product_all(2,3,4) = " << product_all(2, 3, 4) << '\n';
    std::cout << "count_args()       = " << count_args() << '\n';

    std::cout << "print_all: ";
    print_all("文字", 1, 2.5);
    std::cout << "print_all(单参数): ";
    print_all(std::string("只有一项"));

}
```

### 6.3 新旧对比

| | 老办法（递归 + 终止重载） | 新办法（折叠表达式，C++17） |
|---|---|---|
| 代码量 | 每个操作要写**两个**函数（一个递归体 + 一个终止） | **一个**函数，一行表达式 |
| 空参数包 | 靠终止重载处理（`sum()` 返回 `0`） | 靠**折叠的运算符合法性**处理（见下） |
| 编译期负担 | 每多一个参数多一层实例化（`n` 个参数 → `n+1` 个实例） | 一次展开，实例数不随参数个数增长 |
| 报错 | 嵌套深，报错里常出现多个实例化上下文 | 报错集中在折叠那一行 |
| 可读性 | 要理解"剥一个 + 递归" | 一眼能看出"这是在把参数加/打印/计数" |
| 能否处理"每项操作不同" | ✅ 灵活（每层可以写不同的事） | ✅ 逗号折叠也能对每项做不同的事，但表达能力弱一些 |

### 6.4 折叠表达式的四种形态

| 形态 | 写法 | 展开成 | 空包时 |
|---|---|---|---|
| 一元右折叠 | `(args + ...)` | `a1 + (a2 + (a3 + a4))` | **不合法**（`+` 没有单位元） |
| 一元左折叠 | `(... + args)` | `((a1 + a2) + a3) + a4` | **不合法** |
| 二元右折叠 | `(init + ... + args)` | `init + (a1 + (a2 + a3))` | 得 `init` |
| 二元左折叠 | `(init + ... + args)` | `((init + a1) + a2) + a3` | 得 `init` |

**空包的行为是本机实测出来的**（下面这段编译**失败**，诊断是真实的）：

<!-- example:ch11_fold_empty_add -->
```cpp compile-fail
#include <iostream>

template <class... Ts>
auto sum_all(Ts... args) {
    return (args + ...);
}

int main() {
    // 空参数包配上 "+" 的一元折叠不合法：+ 没有单位元
    std::cout << sum_all() << '\n';
}
```

**真实诊断**（本机 MSVC）：

```text
main.cpp(5): error C7516: '+' 上的一元 fold 表达式必须具有非空扩展
main.cpp(5): note: 模板实例化上下文(最早的实例化上下文)为
main.cpp(10): note: 查看对正在编译的函数 模板 实例化“auto sum_all<>(void)”的引用
main.cpp(5): error C3520: “args”: 必须在此上下文中扩展参数包
main.cpp(5): fatal error C1903: 无法从以前的错误中恢复；正在停止编译
```

**只能对这三类运算符做"空包合法"的一元折叠**（标准给了单位元）：

| 运算符 | 空包时的值 |
|---|---|
| `&&` | `true` |
| `\|\|` | `false` |
| `,`（逗号） | `void()`（什么都不做） |

**所以 `print_all()`（逗号折叠）在空包时是**合法的**——它什么都不打印。**

> ⚠️ **坑**：`(args + ...)` 在**参数非空**时完全正常，**只在空包时**编译失败。
> 这意味着"模板编译通过"可能只是因为**你还没用它那种方式调用过**（回到第 2.4 节的两阶段查找）。
> **修法**：想让空包也合法就用二元折叠给出初值：`(0 + ... + args)`。
> **错误归属：类型类（模板实例化）**，不是语法错——`(args + ...)` 这个写法本身完全合法。

### 6.5 `sizeof...` 的语法

**数参数个数用 `sizeof...`，它不展开包**：

```cpp
sizeof...(Ts)          // ✅ 正确：sizeof、...、包名，外层整体括住
sizeof...args          // ❌ 少写括号
```

**本机实测的真实诊断**（`sizeof...args` 漏掉外层括号）：

```text
main.cpp(5): error C2760: 语法错误: 此处出现意外的“args”；应为“(”
main.cpp(5): note: 模板实例化上下文(最早的实例化上下文)为
main.cpp(9): note: 查看对正在编译的函数 模板 实例化“size_t count_args_wrong<int,int,int>(int,int,int)”的引用
main.cpp(5): error C2061: 语法错误: 标识符“args”
```

> ⚠️ **坑**：`sizeof...args` 看起来"只差一对括号"，但报的是**语法错误**（`C2760` / `C2061`），
> 而且**第一条 error 就是原因**。这类错误属于**语法类**：
> `sizeof...` 后面跟的东西必须是一个**带括号的名字**，这是语法的硬要求。

> ⚠️ **另一个坑（本机实测的真实警告）**：`std::size_t count_args(Ts... args) { return sizeof...(args); }`
> 会冒出 **3 条 `warning C4100: '<args_2>': 未引用的参数`**（参数有几个就报几条）。
> **为什么**：`sizeof...(args)` 只用到了**包里有几个**，没有用到任何一个**参数本身**，
> 于是在 MSVC 眼里这些参数都没被引用。
> **修法**：参数包**不写名字**——写成 `count_args(Ts...)`，用 `sizeof...(Ts)` 数个数。本机验证：清零警告。

## 7. 类型特征与 `static_assert`：把错误提到编译期

### 7.1 类型特征是"关于类型的编译期问题"

第 5 节的 `if constexpr` 里已经用了 `std::is_integral<T>::value` 这种东西。
它们统称**类型特征**（type traits），都在 `<type_traits>` 里，作用是
**在编译期问一个关于类型的问题，并把答案变成一个可以参与编译期计算的值**。

<!-- example:ch11_traits -->
```cpp
#include <iostream>
#include <string>
#include <type_traits>
#include <vector>

template <class T>
std::string describe() {
    if (std::is_integral<T>::value) {
        return "整数";
    }
    if (std::is_floating_point<T>::value) {
        return "浮点";
    }
    if (std::is_pointer<T>::value) {
        return "指针";
    }
    return "其它";
}

static_assert(std::is_same<std::remove_reference<int&>::type, int>::value,
              "remove_reference 应该把 int& 变成 int");
static_assert(std::is_same<std::remove_const<const int>::type, int>::value,
              "remove_const 应该去掉顶层 const");
static_assert(std::is_same<std::remove_pointer<int*>::type, int>::value,
              "remove_pointer 应该去掉指针");
static_assert(std::is_same<std::remove_cv_t<const volatile int>, int>::value,
              "remove_cv_t 同时去掉 const 和 volatile");
static_assert(std::is_same<std::conditional<true, int, double>::type, int>::value,
              "conditional 在条件为真时选第一个类型");

int main() {
    std::cout << std::boolalpha;
    std::cout << "describe<int>()          = " << describe<int>() << '\n';
    std::cout << "describe<double>()       = " << describe<double>() << '\n';
    std::cout << "describe<int*>()         = " << describe<int*>() << '\n';
    std::cout << "describe<std::string>()  = " << describe<std::string>() << '\n';

    std::cout << "is_same<int, int>            : " << std::is_same<int, int>::value << '\n';
    std::cout << "is_same<int, long>           : " << std::is_same<int, long>::value << '\n';
    std::cout << "is_integral<bool>            : " << std::is_integral<bool>::value << '\n';
    std::cout << "is_integral<double>          : " << std::is_integral<double>::value << '\n';
    std::cout << "is_arithmetic<std::string>   : " << std::is_arithmetic<std::string>::value << '\n';
    std::cout << "remove_reference_t<int&> 是 int : "
              << std::is_same<std::remove_reference_t<int&>, int>::value << '\n';
    std::cout << "sizeof 与类型特征: sizeof(long)=" << sizeof(long) << '\n';
}
```

<!-- result:ch11_traits -->
```text
describe<int>()          = 整数
describe<double>()       = 浮点
describe<int*>()         = 指针
describe<std::string>()  = 其它
is_same<int, int>            : true
is_same<int, long>           : false
is_integral<bool>            : true
is_integral<double>          : false
is_arithmetic<std::string>   : false
remove_reference_t<int&> 是 int : true
sizeof 与类型特征: sizeof(long)=4
```

**注意 `is_integral<bool>` 是 `true`** —— `bool` 属于整数类型（它是整型的一种）。
这条容易记错，但它有实际后果：第 5 节 `as_text` 的整数分支会对 `bool` 生效，
而 `std::to_string(bool)` 会输出 `0` 或 `1`，不是 `true` / `false`。

### 7.2 两类类型特征

| 类别 | 例子 | 结果是什么 |
|---|---|---|
| **查询型**（`is_*`） | `is_integral<T>`、`is_same<A,B>`、`is_pointer<T>` | `::value` 是 `bool` |
| **变换型**（`remove_*` / `add_*` / `conditional`） | `remove_reference<T>`、`remove_const<T>`、`conditional<B,T,F>` | `::type` 是**一个新类型** |

**C++14 起每个变换型都有一个 `_t` 别名**，少写 `::type`：

```cpp
std::remove_reference<int&>::type     // 老写法
std::remove_reference_t<int&>         // C++14 起，等价且短
```

上面示例里两种写法都用到了，`static_assert` 用的是老写法、`cout` 那行用的是 `_t` 写法，
**两者都实测为 `true`**。

**查询型的 `_v` 别名**（C++17 起）：

```cpp
std::is_integral<T>::value            // 老写法
std::is_integral_v<T>                 // C++17 起，等价且短
```

### 7.3 `static_assert`：编译期断言

`static_assert(条件, "消息")` 在**编译期**检查条件，不成立就**编译失败并打印你给的消息**。

**本机实测的失败诊断**（把一个 16 字节的数组类型喂给"只接受 ≤8 字节"的断言）：

```text
main.cpp(10): error C2338: static assertion failed: 'double[2] 是 16 字节，不该算小类型'
```

**注意这条诊断的三个特点**：

| 特点 | 说明 |
|---|---|
| 它是 **`error`**，不是警告 | 编译直接不通过 |
| 它**打印了你写的消息** | 所以消息要写成"为什么错"，而不是"错了" |
| 它有**行号和列号** | 精确定位到那一条断言 |

<!-- example:ch11_static_assert -->
```cpp
#include <iostream>
#include <type_traits>

template <class T>
struct IsSmall {
    static constexpr bool value = sizeof(T) <= 8;
};

template <class T>
void only_small(const T&) {
    static_assert(sizeof(T) <= 8, "这个模板只接受不超过 8 字节的类型");
    std::cout << "类型大小 " << sizeof(T) << " 通过检查\n";
}

static_assert(sizeof(int) == 4, "本机 int 应该是 4 字节");
static_assert(IsSmall<int>::value, "int 应该算小类型");
static_assert(!IsSmall<double[2]>::value, "double[2] 是 16 字节，不该算小类型");

int main() {
    std::cout << std::boolalpha;
    std::cout << "IsSmall<int>::value    = " << IsSmall<int>::value << '\n';
    std::cout << "IsSmall<double>::value = " << IsSmall<double>::value << '\n';
    only_small(1);
    only_small(1.5);
    std::cout << "编译期断言在程序跑起来之前就已经检查过了\n";
}
```

<!-- result:ch11_static_assert -->
```text
IsSmall<int>::value    = true
IsSmall<double>::value = true
类型大小 4 通过检查
类型大小 8 通过检查
编译期断言在程序跑起来之前就已经检查过了
```

**`static_assert` 的三个用法位置**：

| 位置 | 作用 | 例子 |
|---|---|---|
| **命名空间作用域** | 检查全局前提 | `static_assert(sizeof(int) == 4, "...")` |
| **类模板里** | 检查类型参数是否满足要求 | 模板体开头一条断言 |
| **函数模板里** | 同左；**只在实例化时检查** | `only_small` 里那条 |

> ⚠️ **坑（与函数模板里的 `static_assert` 有关）**：函数模板里的 `static_assert`
> **只在实例化时检查**。所以 `only_small` 这个模板在**没被调用**的时候，
> 即使它的约束对某个类型不成立，编译器也不会说话。
> **这正是第 8 节 `enable_if` 要解决的问题的原型**：
> 你想要的是"**这个类型不该匹配这个候选**"，而不是"**匹配了之后报一条错**"。
> 两者的差别在**重载决议**里是决定性的——一个是"没这个函数"，一个是"有你但用不了"。

## 8. SFINAE 与 `enable_if`：它解决什么问题、代价是什么

> **这一节的定位**：**只讲问题意识，不写模板元编程教程。**
> 你需要知道的是"当年为什么需要它"和"它为什么难用"，
> 因为第 9 节的 `concepts` 和已经用过的 `if constexpr` 都是针对这两点的回答。

### 8.1 它解决什么问题：让一个候选函数"悄悄地不参与重载"

回到第 1.2 节那个推导冲突：`max_value(3, 4.5)` 编不过。
现在换个场景——**你想要的是"整数走这个版本、浮点走那个版本"**：

```cpp
template <class T> ??? kind(T) { return "整数版本"; }
template <class T> ??? kind(T) { return "浮点版本"; }
```

两个函数**签名完全一样**（都只有一个 `template <class T>` 和一个 `T` 参数），
所以这是**非法的重定义**，除非你能让"哪个版本存在"取决于 `T`。

**`enable_if` 就是干这个的**：它在条件不成立时**让那个版本的签名变得不合法**，
于是它在重载决议里**被默默丢掉**，不报错，让另一个版本顶上。

### 8.2 最小例子

<!-- example:ch11_enable_if -->
```cpp
#include <iostream>
#include <string>
#include <type_traits>

// 只有整数类型才能匹配这个重载
template <class T>
typename std::enable_if<std::is_integral<T>::value, std::string>::type
kind(T) {
    return "走的是整数版本";
}

// 只有浮点类型才能匹配这个重载
template <class T>
typename std::enable_if<std::is_floating_point<T>::value, std::string>::type
kind(T) {
    return "走的是浮点版本";
}

// 另一种写法：把条件放在模板参数里（C++11 起的惯用法）
template <class T, typename std::enable_if<std::is_class<T>::value, int>::type = 0>
std::string kind(const T&) {
    return "走的是类类型版本";
}

int main() {
    std::cout << "kind(1)                -> " << kind(1) << '\n';
    std::cout << "kind(2.5)              -> " << kind(2.5) << '\n';
    std::cout << "kind(std::string(\"x\")) -> " << kind(std::string("x")) << '\n';
}
```

<!-- result:ch11_enable_if -->
```text
kind(1)                -> 走的是整数版本
kind(2.5)              -> 走的是浮点版本
kind(std::string("x")) -> 走的是类类型版本
```

**逐个类型看发生了什么：**

```text
kind(1)   → T = int
            整数版本：enable_if<true,  string>::type = string   → 签名合法，参选 ✅
            浮点版本：enable_if<false, string>::type = 不存在   → 签名不合法，被丢掉
            类类型版：enable_if<false, int>::type    = 不存在   → 被丢掉
            → 只剩一个候选，选它

kind(2.5) → T = double → 只有浮点版本活下来

kind(std::string("x")) → T = std::string → 只有类类型版本活下来
```

### 8.3 名字的来历：SFINAE

上面那个"签名不合法就默默丢掉"的规则叫 **SFINAE**：

```text
Substitution Failure Is Not An Error
替换失败不是错误
```

**展开说**：把 `T = int` 代进 `std::enable_if<std::is_floating_point<T>::value, std::string>::type` 时，
替换的结果是"不存在的类型"——**替换失败了**。
但只要这个失败发生在**函数签名里**（标准的说法是"直接上下文"），
它就**不是一个错误**，而只是"这个候选被淘汰"。

**所以 `enable_if` 不是"判断"工具，它是"通过制造一个无害的失败来筛选候选"的工具。**
这个思路很绕，但它是 C++11 时代唯一的标准做法。

### 8.4 代价：三个真实的问题

**问题一：报错极难懂。** 如果所有候选都被淘汰了，你会得到"没有匹配的函数"加上一长串候选列表，
**但你从列表里看不出"为什么每个都被淘汰了"**。第 `10` 章第 6.2 节那段 `std::visit` 的 `overloaded`
就是同类写法的受益者（它靠"用到的部分合法"编译过），而这里展示的是它的阴暗面。

**问题二：SFINAE 只在"直接上下文"里生效。** 失败必须发生在**函数签名**中。
如果失败发生在**函数体**或**返回类型的深处**，那就不是 SFINAE，而是**硬错误**。

**本机实测的两个反例**（来自第 `10` 章探针里的 SFINAE 边界实验）：

| 情况 | 真实结果 | 说明 |
|---|---|---|
| `as_text('A')`：`char` 是整数类型，走整数分支，但 `std::to_string(char)` 不存在 | **编译通过**，输出 `整数: 65` | `std::to_string(char)` 实际有重载（`char` 提升为 `int`），所以没出错——**这提醒我们"想当然的失败"未必真失败** |
| 两个 `enable_if` 重载同时匹配 `bool` 参数 | **编译通过**，输出 `整数版本` 两次 | `bool` 是 `is_integral`，两个重载里只有一个活下来…但**这里实测是"两个都活下来而被选中一个"**，说明这类写法的行为需要逐个类型实测，不能靠推断 |

> ⚠️ **坑（这一节最该记的一条）**：**SFINAE 的失败只在你猜错的时候才会暴露。**
> 上面两个实验都**编译通过**了——它们没有出现"我想象中的报错"。
> **程序实际怎么解释它**：`char` 能隐式转成 `int`，所以 `std::to_string(char)` 找得到；
> `bool` 也满足 `is_integral`。**你以为会失败的地方，标准库可能已经替你兜住了。**
> **这类错误的归属是类型类**，而且**它不报错**——只是行为和你以为的不同。

**问题三：写法不直观。** 看那个 `type`：

```cpp
typename std::enable_if<std::is_integral<T>::value, std::string>::type
```

它在说的其实只有一句话："**只有 `T` 是整数时这个函数才存在**。"
但为了表达这句话，要写 `typename`、`std::enable_if`、两个模板实参、`::type`，
还得知道"为什么能放在返回类型位置"。**这就是第 9 节 `concepts` 存在的理由。**

### 8.5 但先知道：C++17 已经有更好的工具了

**`if constexpr`（第 5 节）在 C++17 就已经解决了"一个模板体里写互相矛盾的代码"这个问题。**
上面 `kind` 那三个重载，在 C++17 里可以合成一个函数：

```cpp
template <class T>
std::string kind(const T&) {
    if constexpr (std::is_integral<T>::value)          { return "整数版本"; }
    else if constexpr (std::is_floating_point<T>::value) { return "浮点版本"; }
    else if constexpr (std::is_class<T>::value)        { return "类类型版本"; }
    else                                               { return "其它"; }
}
```

**但两者管的不是同一件事**，这一点必须分清：

| | `if constexpr` | `enable_if` / SFINAE |
|---|---|---|
| 作用位置 | **函数体内部** | **函数签名** |
| 效果 | 丢掉不满足条件的分支 | 让整个候选**不存在** |
| 能不能影响重载决议 | ❌ 不能（函数已经被选中了） | ✅ 能（这是它唯一的用途） |
| 能不能选"多个同名函数" | ❌ | ✅ |
| 可读性 | 好 | 差 |
| C++17 里还需要吗 | — | **需要**：只要你要"按类型选不同的重载"，就只能用它（或用重载本身） |

> **判据**：**"函数体里要不要执行这段代码" → `if constexpr`；
> "这个函数要不要参与重载" → `enable_if`。**
> 绝大多数入门阶段的场景属于前者。

## 9. `concepts`：同一个问题的现代答案（C++20，只标位置）

### 9.1 它是什么

`concepts`（概念）是 **C++20** 引入的语法，让你**直接写出"模板参数必须满足什么条件"**，
而不是用 `enable_if` 去制造一个无害的替换失败。

```cpp
// C++20 起（本讲义基线 C++17，所以下面这段在本章的自动基线里被断言为"编译失败"）
template <std::integral T>
T twice(T x) {
    return x + x;
}
```

**它把第 8.4 节那个 `typename std::enable_if<...>::type` 换成了一个名字：`std::integral`。**
读起来就是"`T` 必须是整数类型"，意图直接写在签名里。

### 9.2 本机实测：它在 C++17 下真的不存在

**这就是"只标位置"的含义——位置必须用实测确定。**

**在 `/std:c++17`（本讲义基线）下，同一段代码的真实诊断**：

```text
concepts(12): warning STL4038: The contents of <concepts> are available only with C++20 or later.
main.cpp(4): error C2039: "integral": 不是 "std" 的成员
main.cpp(4): error C2061: 语法错误: 标识符“integral”
main.cpp(5): error C2061: 语法错误: 标识符“twice”
main.cpp(5): error C2143: 语法错误: 缺少“;”(在“{”的前面)
main.cpp(5): error C2447: “{”: 缺少函数标题(是否是老式的形式表?)
main.cpp(10): error C3861: “twice”: 找不到标识符
main.cpp(10): error C2593: “operator <<”不明确
```

**在 `/std:c++20` 下同一段代码**：

```text
42
```

**所以本机是可以验证它的**——只是**不能放进 C++17 的正文主干**。

**读那段 C++17 诊断的方法**（和第 `08` 章第 6.3 节讲 `std::expected` 时是同一套）：

| 诊断 | 它的角色 |
|---|---|
| `warning STL4038`（出现在 `<concepts>` 头文件里） | **最重要的线索**："这个头的内容需要 C++20 或更高" |
| `error C2039: "integral": 不是 "std" 的成员` | **真正的原因**：`std::integral` 在 C++17 里不存在 |
| 后面五条 `C2061` / `C2143` / `C2447` / `C3861` / `C2593` | **全是连锁反应**（名字不存在 → 后面都解析不了） |

> **判据**：**多错误诊断只看前两条，尤其是第一条**。修好第一个，后面的一起消失。

### 9.3 它和前面几节的关系（这一节的价值）

**`concepts` 不是凭空加的新东西，它是把三处旧做法统一到一个语法里：**

| 旧做法 | 位置 | 问题 | `concepts` 怎么改 |
|---|---|---|---|
| `enable_if` 放在返回类型里（第 8.2 节） | 签名 | 写法和意图完全不像 | 用 `requires` 或简写约束直接写条件 |
| `static_assert` 放模板体开头（第 7.3 节） | 函数体 | **匹配了之后才报错**，错误信息是"断言失败"而不是"没有这个函数" | 约束不满足时**候选直接不参与**，报错指向调用点 |
| 类型特征 `is_integral_v<T>` 写在 `if constexpr` 里（第 5 节） | 函数体 | 只能表达"分支"，不能表达"要求" | 同一个条件可以在**签名**里表达 |

**所以它同时解决了第 8.4 节的三个问题**：

1. **报错可读**：约束不满足时，编译器能直接说"`T` 不满足 `std::integral`"，
   而不是甩一长串 `enable_if` 替换失败。
2. **位置正确**：约束写在签名里，不需要"把失败藏在直接上下文"这个技巧。
3. **意图直白**：`template <std::integral T>` 比 `typename std::enable_if<...>::type` 好懂得多。

### 9.4 本讲义为什么不在正文里教它

| 原因 | 说明 |
|---|---|
| **基线是 C++17** | 全文的示例都用 `/std:c++17` 编译。写成 C++20 会让判题机（多用 GCC 且标准版本各异）和老课程全部对不上 |
| **第 `13` 章会系统地给地图** | `concepts` 和 `ranges` / `std::format` / `std::span` / `modules` 一起在那里列出位置 |
| **现在不需要它也能写对代码** | 你的场景几乎都是"`if constexpr` 能解决"的那一类；真需要 `enable_if` 的场合很少 |

**你现在该记住的只有三句话：**

1. **C++20 有一个叫 `concepts` 的语法，用来给模板参数写约束。**
2. **它是 `enable_if` 那套复杂写法的现代替代品。**
3. **在本讲义基线（C++17）下它不能编译**——本机实测的诊断就是上面那 7 条。

> ⚠️ **坑**：不要因为"更新"就默认 `concepts` 在所有场合都更好。
> 它对**已有代码**是新增语法，`enable_if` 并没有被废弃；
> 而且在需要"**在多个重载之间做极精细筛选**"的场景里，`requires` 子句的写法仍然需要仔细设计。
> **这属于"新工具更好用"，不是"旧工具是错的"。**

## 10. 本章自测

**1.** 为什么说"模板不是代码"？用 `max_value` 举一个能验证的例子。

<details><summary>答案</summary>

因为**模板定义本身不生成任何函数**，它的作用是一份"生成代码的配方"。
只有**被某个具体类型实例化**时，编译器才照着配方造出那一份函数。

**验证方式**（本机实测 `ch11_func_template` + `ch11_instantiation`）：

- `max_value(3, 7)` 推出 `T = int` → 生成 `int max_value(int, int)`
- `max_value(2.5, 1.5)` 推出 `T = double` → 生成**另一份** `double max_value(double, double)`
- `identity(1)` 与 `identity(2)` 的 `is_same` 是 `true`（**同一份**，因为 `T` 都是 `int`）
- `identity(1)` 与 `identity(1.0)` 的 `is_same` 是 `false`（**两份**）

**最直接的证据**是 `Counter<T>::created`：`Counter<int>::created` 是 2、`Counter<double>::created` 是 1
——两个类的静态成员是**各自独立的存储**，说明它们是两个独立的类。
</details>

**2.** 下面这段代码为什么编译失败？和 `max_value(3, 7)` 有什么不同？

```cpp
template <class T>
T max_value(T a, T b) { return a < b ? b : a; }

int main() { max_value(3, 4.5); }
```

<details><summary>答案</summary>

**编译失败**，因为两个实参推出了**不同的 `T`**：`3` 是 `int` → `T = int`；`4.5` 是 `double` → `T = double`。
一个函数模板的**同一个** `T` 不能同时是 `int` 和 `double`，所以推导失败，报"没有匹配的函数"。

**和 `max_value(3, 7)` 的不同**：那次两个实参都是 `int`，推出唯一的 `T`，实例化成功。

**关键顺序**：**推导在重载决议之前**。推导失败就没有候选函数，所以你说不上"选中了哪个"。

**修法**（本机实测 `ch11_deduction_conflict`）：
`max_value<double>(3, 4.5)` → 输出 `4.5`。显式指定后 `3` 隐式转成 `3.0`。

**错误归属**：**类型类（模板参数推导）**，不是语法错。
</details>

**3.** 为什么模板的定义必须写在头文件里？为什么普通函数不需要？

<details><summary>答案</summary>

因为**编译器一次只处理一个翻译单元**（第 `01` 章第 10 节「源文件、头文件、翻译单元：它们不是同一件事」），
而模板**只有在被使用时才生成代码**。

**本机实测的对照**（探针 A1 / A2）：

| 做法 | 结果 |
|---|---|
| `util.h` 只有声明 + `util.cpp` 有定义 | **`error LNK2019: 无法解析的外部符号 "int __cdecl max_value<int>(int,int)"`** + `fatal error LNK1120` |
| 定义也放在 `util.h` 里 | 编译链接成功，输出 `7` |

**为什么**：定义在 `util.cpp` 时，那个翻译单元**没有任何调用**，推不出 `T`，**一份代码都不生成**；
而 `main.cpp` 只看到声明，只能生成一个**对外部符号的引用**。链接时没人提供它 → `LNK2019`。

**普通函数为什么不需要**：因为它的定义**独立编译成了一份符号**，
放在 `.obj` 里等链接器来找。**模板的定义在没人用的时候不产生符号**——这就是区别。

**错误归属**：**链接类**。这是最容易误判的一类：编译器全绿，链接器报错，而报错的字面意思和模板无关。

**另一条容易混的**：模板**不需要**加 `inline`。头文件里的普通函数定义要加 `inline` 是为了绕过 ODR
（第 05 章第 9 节「`inline`、多文件编译与 ODR（入门版）」），模板实例化有单独的规定。
</details>

**4.** `if constexpr` 和普通 `if` 有什么本质区别？为什么第 5 节 `as_text` 里必须用它？

<details><summary>答案</summary>

**本质区别**：普通 `if` 的两个分支**都要能编过**；`if constexpr` 在条件为假时
**把那一支整个丢掉，不参与实例化**。

**为什么 `as_text` 必须用它**：三个分支的代码**互相编不过**：

| 分支 | 代码 | 对 `std::string` |
|---|---|---|
| 整数 | `std::to_string(value)` | `std::to_string(std::string)` 不存在 |
| 浮点 | `std::to_string(value)` | 同上 |
| 其它 | `std::string("其它: ") + value` | 对 `int` 来说 `std::string + int` 不合法 |

用普通 `if`，`as_text(42)` 会因为"其它分支里的 `std::string + int` 不合法"而编译失败。
用 `if constexpr`，`T = int` 时只保留整数分支，**其它分支根本不检查**。

**本机实测**（`ch11_if_constexpr`）三行输出 `整数: 42` / `浮点: 2.500000` / `其它: 文本`，
证明三个类型各留了一支。

**注意 `2.500000`**：这是 `std::to_string(double)` 的默认 6 位小数格式，
和 `std::cout << 2.5` 输出 `2.5` 不一样。**这不是精度问题，是 `to_string` 的格式就是如此。**
</details>

**5.** 参数包为空时，`(args + ...)` 和 `(std::cout << args, ...)` 哪个能编过？为什么？

<details><summary>答案</summary>

**`(args + ...)` 编不过；`(std::cout << args, ...)` 能编过。**

**本机实测的真实诊断**（`ch11_fold_empty_add`）：

```text
main.cpp(5): error C7516: '+' 上的一元 fold 表达式必须具有非空扩展
main.cpp(5): error C3520: “args”: 必须在此上下文中扩展参数包
```

**为什么**：一元折叠在空包时需要一个**单位元**（identity element）。
标准只给三类运算符规定了单位元：`&&` → `true`、`||` → `false`、`,` → 什么都不做。
`+` **没有**单位元，所以空包时非法。

**修法**：用**二元折叠**显式给出初值 `(0 + ... + args)`，空包时结果就是 `0`。

**这题的更大意义**：`(args + ...)` 在**参数非空时完全正常**（`sum_all(1,2,3,4)` 实测得 `10`），
只在空包时失败。也就是说**"模板编译通过"可能只是因为你还没用那种方式调用过它**——
回到第 2.4 节的两阶段查找：没实例化就没有第二阶段检查。
</details>

**6.** `std::size_t count_args(Ts... args) { return sizeof...(args); }` 会有什么问题？

<details><summary>答案</summary>

**能编过，但会冒出 3 条警告**（本机实测，参数有几个报几条）：

```text
main.cpp(9): warning C4100: '<args_2>': 未引用的参数
main.cpp(9): note: 模板实例化上下文(最早的实例化上下文)为
main.cpp(14): note: 查看对正在编译的函数 模板 实例化“size_t count_args<int,int,int>(int,int,int)”的引用
main.cpp(9): warning C4100: '<args_1>': 未引用的参数
main.cpp(9): warning C4100: '<args_0>': 未引用的参数
```

**为什么**：`sizeof...(args)` 只用到了"包里有几个"，**没有用到任何一个参数本身**，
所以在 MSVC 眼里这些参数都没被引用。

**修法**：参数包**不写名字**——写成 `count_args(Ts...)`（值包）或 `count_args(Ts...)`，
用 `sizeof...(Ts)` 数个数。本机验证：**警告清零**（`ch11_fold_ok` 是 0 警告 0 错误）。

**顺带一个语法坑**：`sizeof...args`（漏掉外层括号）报的是**语法错误**：

```text
main.cpp(5): error C2760: 语法错误: 此处出现意外的“args”；应为“(”
main.cpp(5): error C2061: 语法错误: 标识符“args”
```

**读法**：`sizeof...` 后面必须跟一个**带括号的名字**，这是语法硬要求（错误归属：**语法类**）。
</details>

**7.** `std::enable_if` 靠什么机制让一个重载"消失"？为什么它的报错难懂？

<details><summary>答案</summary>

**机制是 SFINAE**（Substitution Failure Is Not An Error，"替换失败不是错误"）。

把 `T` 代进 `std::enable_if<条件, std::string>::type`：
- 条件为真 → 得到 `std::string`，**签名合法**，这个候选**参选**
- 条件为假 → `enable_if` **没有 `::type` 成员**，替换**失败**

只要这个失败发生在**函数签名里**（标准的说法是"直接上下文"），
它就**不是错误**，只是"这个候选被淘汰"。于是同一个 `kind(T)` 的多个版本能共存，
每次调用只有一个活下来。

**本机实测**（`ch11_enable_if`）：`kind(1)` → `走的是整数版本`；`kind(2.5)` → `走的是浮点版本`；
`kind(std::string("x"))` → `走的是类类型版本`。

**报错难懂的原因**：
1. 当**所有**候选都被淘汰时，你得到的是"没有匹配的函数"加一长串候选列表，
   **但看不出每个候选"为什么被淘汰"**（淘汰是静默的，这正是它的设计目标）。
2. 失败必须发生在**签名里**。如果失败发生在函数体或返回类型深处，那就不是 SFINAE，而是**硬错误**。
3. 写法本身不直观：`typename std::enable_if<std::is_integral<T>::value, std::string>::type`
   表达的只是"`T` 必须是整数"。

**这一节最该记的一条**：SFINAE 的失败**只在你猜错的时候才暴露**。
本机那两个边界实验（`as_text('A')`、`bool` 同时满足两个 `enable_if`）**都编译通过了**——
它们没有出现"想象中的报错"，因为 `std::to_string(char)` 找得到（`char` 提升为 `int`），
`bool` 也确实满足 `is_integral`。**你以为会失败的地方，标准库可能已经兜住了。**
</details>

**8.** `if constexpr` 和 `enable_if` 管的不是同一件事。请说清分工。

<details><summary>答案</summary>

| | `if constexpr` | `enable_if` / SFINAE |
|---|---|---|
| 作用位置 | **函数体内部** | **函数签名** |
| 效果 | 丢掉不满足条件的分支 | 让整个候选**不存在** |
| 能否影响重载决议 | ❌ **不能**——函数已经被选中了 | ✅ **能**——这是它唯一的用途 |
| 能否让多个同名函数共存 | ❌ 不能（重定义） | ✅ 能 |
| 可读性 | 好 | 差 |
| 引入版本 | **C++17** | C++11 |

**判据**：

- **"函数体里要不要执行这段代码" → `if constexpr`**
- **"这个函数要不要参与重载" → `enable_if`**

**为什么 `if constexpr` 代替不了 `enable_if`**：`if constexpr` 是在**一个已经选定的函数**内部做编译期分支。
如果两个版本**签名完全相同**（像第 8.1 节那两个 `kind(T)`），那就是**重定义**，
`if constexpr` 帮不上忙——你必须让它们在签名层面区分开。

**反过来，`enable_if` 也代替不了 `if constexpr`**：用 `enable_if` 把三个版本拆成三个重载，
每个重载里还得再做一次类型判断，代码量和可读性都差。

**实践建议**：入门阶段 99% 的场景是前者。真需要按类型选重载时，
先试**普通重载**（比如 `int` 版和 `double` 版各写一个），实在不行才上 `enable_if`。
</details>

**9.** 第 5 节的 `as_text` 里，`std::to_string` 对 `char` 和 `bool` 会发生什么？为什么这是个陷阱？

<details><summary>答案</summary>

**两个都走整数分支，但结果都不是你想要的：**

| 类型 | 走哪一支 | 为什么 | 结果 |
|---|---|---|---|
| `char` | 整数分支 | `std::is_integral<char>::value` 是 `true` | `std::to_string('A')` 把 `char` 提升成 `int`，输出 **`65`**（不是 `A`） |
| `bool` | 整数分支 | **`std::is_integral<bool>::value` 是 `true`** | 输出 **`0` 或 `1`**（不是 `true` / `false`） |

**`bool` 属于整数类型**这一点本机实测过（`ch11_traits`：`is_integral<bool> : true`），
也容易记错。而 `char` 的提升行为在探针 `_sfinae_char` 里实测为 `整数: 65`。

**为什么是陷阱**：`std::is_integral<T>` 回答的是"**这个类型在语言层面属不属于整数类型**"，
不是"**这个类型打印出来像不像数字**"。`bool` 和 `char` 在语言层面都是整型，
所以这个"按类型分派"的写法会把它们都吸进整数分支。

**修法**（在 `if constexpr` 里加更细的分支）：

```cpp
if constexpr (std::is_same<T, bool>::value)          { return value ? "true" : "false"; }
else if constexpr (std::is_same<T, char>::value)     { return std::string(1, value); }
else if constexpr (std::is_integral<T>::value)       { return "整数: " + std::to_string(value); }
// ...
```

**错误归属**：**类型类**。而且**它不报错**——只是行为和你以为的不同。
这正是第 7 节那句"类型特征回答的是语言层面的分类问题"的实际后果。
</details>

**10.** 同一段 `concepts` 代码，在这台机器上用 `/std:c++17` 和 `/std:c++20` 编译分别是什么结果？

<details><summary>答案</summary>

**`/std:c++17`（本讲义基线）：编译失败，7 条诊断。**

```text
concepts(12): warning STL4038: The contents of <concepts> are available only with C++20 or later.
main.cpp(4): error C2039: "integral": 不是 "std" 的成员
```
