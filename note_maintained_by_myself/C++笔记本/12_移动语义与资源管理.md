## 0. 先记住的六件事

1. **"移动"这个词有误导性。** 语言层面**没有"把字节从 A 搬到 B"这回事**——那只是拷贝的一种实现方式。
   `std::move` 做的事是**给编译器一个许可**："这个对象我不要了，你可以对它做破坏性操作。"
2. **`std::move` 本身不搬运资源。** 它通过转换得到将亡值表达式，让重载决议有机会选择移动操作；标准不保证某种机器码形式。
   **本机实测**：对 `int` 用 `std::move`，结果就是一次普通拷贝。
3. **移动构造/移动赋值是成员函数，和拷贝版本并列。** 只有类类型才有"移动"的意义（基本类型只能拷）。
4. **`std::move` 不是"保证移动"**，而是"**允许**移动"。类没有移动构造时会**静默退回拷贝**——
   本机实测过这个倒退，而它**不会有任何警告**。
5. **`const` 对象上的 `std::move` 等于没写。** 因为移动构造的参数是 `T&&`，绑不上 `const T`，
   于是又一次**静默退回拷贝**。
6. **智能指针不是"自动内存管理魔法"，它是 RAII 的应用。** 先懂 RAII，才懂它们为什么能工作。

> 如果只记一条，记第 4 条。**"我写了 `std::move`"和"它真的移动了"是两件事**，后者需要条件。

## 1. 值类别：左值、将亡值、纯右值

第 02 章讲对象时留了一个问题：**同一个对象，为什么有时能被"拿走"，有时不能？**
答案在**值类别**（value category）——它描述的是一个**表达式**（不是对象）的性质。

### 1.1 三分法

C++17 的三种基本值类别互斥，再由它们组成两种有交集的类别：

```text
三种基本类别：lvalue（左值） | xvalue（将亡值） | prvalue（纯右值）
glvalue（泛左值） = lvalue ∪ xvalue
rvalue （右值）   = xvalue ∪ prvalue
交集是 xvalue：它同时属于 glvalue 和 rvalue。
```

| 类别 | 中文 | 判据（够用版） | 例子 |
|---|---|---|---|
| **lvalue** | 左值 | 标识对象或函数，且不是 xvalue；按表达式规则判断 | `x`（变量名）、`arr[0]`、`*p` |
| **xvalue** | 将亡值 | **有身份但"可以被拿走"** | `std::move(x)`、`static_cast<T&&>(x)` |
| **prvalue** | 纯右值 | **只是个值，没有持久身份** | `42`、`x + 1`、`f()` 返回非引用 |

再往上归并：

- **glvalue**（泛左值）= lvalue + xvalue → "有身份"
- **rvalue**（右值）= xvalue + prvalue → 参与右值相关的绑定与重载；不保证实际发生移动

### 1.2 为什么要分这个

因为**函数重载靠它选版本**。看这两组签名：

```cpp
void f(int& x);        // 只能接左值
void f(int&& x);       // 只能接右值

int a = 1;
f(a);                  // 选 int&  ← a 是左值
f(1);                  // 选 int&& ← 1 是纯右值
f(std::move(a));       // 选 int&& ← 把 a 转成了将亡值
```

**这就是移动语义的全部机制**：给"我不用了"的对象配一个**单独的、更便宜的重载**。

> **判据**：变量名表达式通常是左值，即使变量声明成 `T&&`；但不能反过来用「有没有名字」给所有表达式分类，`*p` 没有变量名形式却是左值。
> `std::move(x)` 是将亡值，依据是调用返回对象的右值引用的函数时的值类别规则。

> ⚠️ **最容易错的一条**：`int&& r = 5;` 之后，**`r` 这个名字本身是左值**。
> 因为"有名字"。所以 `f(r)` 会选 `f(int&)` 而不是 `f(int&&)`。
> 要往下传它的"右值性"，必须写 `std::move(r)`（这正是第 9 节 `std::forward` 要解决的问题）。
>
> **一句话**：**值类别看的是表达式，不是类型。** `T&&` 只是一个类型，`r` 是一个左值表达式。

## 2. 移动构造与移动赋值：真的被调用了吗

先看一个会**自报家门**的类，把每种操作都打印出来。

<!-- example:ch12_move_calls -->
```cpp
#include <iostream>
#include <utility>

struct Tracker {
    int id;
    Tracker(int i) : id(i) { std::cout << "ctor " << id << '\n'; }
    Tracker(const Tracker& o) : id(o.id) { std::cout << "copy " << id << '\n'; }
    Tracker(Tracker&& o) noexcept : id(o.id) { o.id = -1; std::cout << "move " << id << '\n'; }
    Tracker& operator=(const Tracker& o) { id = o.id; std::cout << "copy= " << id << '\n'; return *this; }
    Tracker& operator=(Tracker&& o) noexcept { id = o.id; o.id = -1; std::cout << "move= " << id << '\n'; return *this; }
    ~Tracker() { std::cout << "dtor " << id << '\n'; }
};

int main() {
    Tracker a{1};
    Tracker b{a};              // 拷贝构造
    Tracker c{std::move(a)};   // 移动构造
    Tracker d{2};
    d = b;                     // 拷贝赋值
    d = std::move(c);          // 移动赋值
}
```

<!-- result:ch12_move_calls -->
```text
ctor 1
copy 1
move 1
ctor 2
copy= 1
move= 1
dtor 1
dtor -1
dtor 1
dtor -1
```

### 2.1 逐行读这段输出

```text
ctor 1      ← a 构造（id=1）
copy 1      ← b{a}：拷贝构造，b.id 也是 1
move 1      ← c{std::move(a)}：移动构造；构造函数体先把 a.id 改成 -1
ctor 2      ← d 构造（id=2）
copy= 1     ← d = b：拷贝赋值，d.id 变成 1
move= 1     ← d = std::move(c)：移动赋值；c.id 被改成 -1
--- 析构，按构造的逆序 ---
dtor 1      ← d（id=1）
dtor -1     ← c（已被移动，id=-1）
dtor 1      ← b（id=1）
dtor -1     ← a（已被移动，id=-1）
```

**两个值得注意的点：**

1. **移动构造函数里我把源对象的 `id` 改成了 `-1`。** 这不是语法要求，是我为了**让"被移动"这件事可见**。
   独占资源类型的常见实现是接管资源指针并清空源对象；**这不是所有类型的统一规则**，具体状态由该类型的契约决定。
2. **`std::move(a)` 之后 `a` 仍然存在、仍然会被析构**，只是它的内部状态被改成了"空"。
   **移动不是"销毁源对象"**——这是个高频误解。

### 2.2 移动构造/移动赋值的签名

```cpp
Tracker(Tracker&& o) noexcept;              // 移动构造
Tracker& operator=(Tracker&& o) noexcept;   // 移动赋值
```

和拷贝版本的差别只有一处：**参数是 `T&&`（右值引用）而不是 `const T&`**。

**`noexcept` 为什么值得检查**：`std::vector` 扩容时，若移动可能抛异常而拷贝可用，通常选择拷贝以维持强异常保证；**若拷贝不可用，仍可能调用会抛异常的移动构造**，此时异常保证有边界。

> ⚠️ **坑**：移动构造忘了写 `noexcept`，于是 `vector` 扩容时**悄悄全在拷贝**，
> 性能差一大截，**而且没有任何错误提示**。
> 判据：**只有实现确实不会抛异常时才承诺 `noexcept`**。移动构造也可以执行用户代码或调用可能抛异常的成员操作；承诺错误会导致 `std::terminate`。

## 3. `std::move` 到底是什么：一个 cast，不是一次搬运

<!-- example:ch12_move_is_cast -->
```cpp
#include <iostream>
#include <utility>

int main() {
    int x = 5;
    int&& r = std::move(x);        // 引用绑定到 x，没有创建另一个 int 对象
    std::cout << x << ' ' << r << '\n';
    r = 9;                          // r 是 x 的右值引用，改它就是改 x
    std::cout << x << '\n';
}
```

<!-- result:ch12_move_is_cast -->
```text
5 5
9
```

**这段输出证明了三件事：**

1. **引用绑定后 `x` 还是 5**：这里没有初始化另一个 `int` 对象，也没有发生一次拷贝。
2. **`r` 引用 `x`**：`r = 9` 之后 `x` 变成 9；引用不是一个新的被引用对象。
3. **输出证明了别名关系，不能证明机器码为零**。`std::move` 的语义可以用下面的转换说明：

```cpp
// 标准库里的实现大意（简化）
template <class T>
constexpr std::remove_reference_t<T>&& move(T&& t) noexcept {
    return static_cast<std::remove_reference_t<T>&&>(t);
}
```

**就是一个 `static_cast`。** 它的作用只有一条：**把表达式的值类别从左值改成右值**，
于是重载决议会去挑 `T&&` 那个版本。

### 3.1 为什么这个"多余的一步"是必要的

因为**重载决议看的是值类别**（第 1 节）。你不写 `std::move`，`a` 就是左值，
编译器只能选 `const T&` 那个（拷贝）版本。写了之后才有资格选移动版本。

> **准确的措辞**：
> - ❌ "`std::move` 把 `a` 移动了" —— 错，它什么都没做
> - ✅ 对对象 `a`，`std::move(a)` 的返回类型是去掉引用后的类型再加 `&&`，保留 `const`；这个调用表达式的值类别是 **xvalue**。类型和值类别需要分别说明。
> - ✅ "`std::move` 是**一个 cast**，它让重载决议有机会选到移动版本"

## 4. 拷贝省略：C++17 起有些"拷贝"根本不发生

<!-- example:ch12_elision -->
```cpp
#include <iostream>

struct Noisy {
    Noisy() { std::cout << "default\n"; }
    Noisy(const Noisy&) { std::cout << "copy\n"; }
    Noisy(Noisy&&) noexcept { std::cout << "move\n"; }
};

Noisy make() {
    return Noisy{};        // C++17 起保证省略
}

int main() {
    std::cout << "--- A ---\n";
    Noisy a = make();
    std::cout << "--- B ---\n";
    Noisy b = Noisy{};
    std::cout << "--- C ---\n";
    Noisy c = std::move(b);
    (void)a; (void)c;
}
```

<!-- result:ch12_elision -->
```text
--- A ---
default
--- B ---
default
--- C ---
move
```

**仔细看这个输出——它是本章最重要的证据之一：**

| 场景 | 输出 | 说明 |
|---|---|---|
| A：`Noisy a = make();` | 只有 `default` | **没有 copy，也没有 move** |
| B：`Noisy b = Noisy{};` | 只有 `default` | **也没有 copy / move** |
| C：`Noisy c = std::move(b);` | `move` | 这个**真的**调用了移动构造 |

**A 和 B 里那些"应该发生"的拷贝/移动，一次都没发生。** 这叫**拷贝省略**（copy elision）。

### 4.1 C++17 做了一件关键的事：把两个场景变成"保证省略"

在 **C++17 之前**，A 和 B 里是否省略由编译器决定（标准允许但不要求）。
**C++17 起，这两个场景是强制的**：

```cpp
T x = T();            // 保证：直接在 x 的存储上构造，没有临时对象
T f() { return T{}; } // 保证：返回值直接在调用者的存储上构造
T x = f();
```

**所以这段程序在 C++17 下不需要 `Noisy` 有可访问的拷贝/移动构造函数**——因为根本没有拷贝/移动发生。
这是 C++17 相对 C++11 的一个**语义变化**，不是优化。

### 4.2 优化级别改变不了语义（本机实测）

我特意把每个示例都**按 `/Od`（不优化）和 `/O2`（优化）各跑了一遍**，
**十组输出逐字相同**。

> **这次输出相同，只是这些示例在这些选项下的观测。** 一般优化受可观察行为约束，但标准特别允许的拷贝省略可以省去有副作用的拷贝/移动构造及相应析构，**NRVO 因而可能合法地改变打印次数**。
> 第 4.3 节的 NRVO 开关对照就是反例；不能从「不同优化选项下输出不同」直接推出 UB。先检查标准允许的省略、未指定行为与实现条件，再排查 UB。

### 4.3 RVO / NRVO 两个名字

| 名字 | 全称 | 指什么 | C++17 状态 |
|---|---|---|---|
| **RVO** | Return Value Optimization | 返回**纯右值**时的省略（如 `return T{};`） | ✅ **保证** |
| **NRVO** | Named RVO | 返回**具名局部变量**时的省略（如 `T t; return t;`） | ⚠️ **允许但不保证** |

**为什么 NRVO 不保证**：因为要不要省略取决于"这条返回语句是不是唯一决定返回值的路径"，
编译器要能证明才行。而**返回纯右值**没有任何歧义，所以能被规定为强制。

> ⚠️ **坑**：写 `return std::move(local);` 想"帮助"编译器。
> **这是错的**——它把一个具名局部变量变成了右值，**反而阻止了 NRVO**，
> 于是变成一次真正的移动（比省略差）。
> **规则：`return local;` 就对了，不要加 `std::move`。**
> （返回成员时可能需要显式 `std::move`；符合 C++17 隐式移动条件的按值参数，即使不能 NRVO，也不需要为了移动而加它。）

**这一条有实测证据**（由另一个 agent 的独立验证补上）。同一份源码，只改编译开关：

| 编译开关 | 真实 stdout | 含义 |
|---|---|---|
| `/Od /Zc:nrvo-` | `ctor` → **`move`** → `done` | NRVO 被关闭 → **真的发生了一次移动** |
| `/O2 /Zc:nrvo` | `ctor` → `done` | NRVO 生效 → **移动被省略，只构造一次** |

**读法**：两行的差别就是**一次移动构造的开销**。
`/Zc:nrvo` 是 MSVC 用来开关 NRVO 的选项（`nrvo-` 表示关掉），
上面这个对照直接展示的是 **NRVO 开关对构造调用次数的影响**；源码没有加入 `std::move`，不能把它当作那种改写的直接对照实验。

> **顺带一条更重要的观察**：这个实验说明 **NRVO 是"允许但不保证"**（第 4.3 节那张表）——
> 它**可以被开关控制**，而 RVO（返回纯右值）是 C++17 保证的、开关动不了。
> **能被编译器选项改变的东西，就不是语言给你的保证。**

## 5. 为什么写了 `std::move` 却还是拷贝

这是本章最实用的一节。**`std::move` 只是"允许"，不是"保证"。** 下面两个实测场景就是它失效的地方。

### 5.1 场景一：类没有移动构造 → 静默退回拷贝

<!-- example:ch12_rule_of_five -->
```cpp
#include <iostream>
#include <utility>

// 只声明析构：移动操作不再隐式生成
struct OnlyDtor {
    int v = 0;
    OnlyDtor() = default;
    ~OnlyDtor() {}
    OnlyDtor(const OnlyDtor& o) : v(o.v) { std::cout << "OnlyDtor copy\n"; }
};

// 显式恢复移动操作
struct WithMove {
    int v = 0;
    WithMove() = default;
    ~WithMove() {}
    WithMove(const WithMove& o) : v(o.v) { std::cout << "WithMove copy\n"; }
    WithMove(WithMove&& o) noexcept : v(o.v) { std::cout << "WithMove move\n"; }
};

int main() {
    OnlyDtor a;
    std::cout << "-- std::move(OnlyDtor) --\n";
    OnlyDtor b{std::move(a)};          // 没有移动构造 → 退回拷贝

    WithMove c;
    std::cout << "-- std::move(WithMove) --\n";
    WithMove d{std::move(c)};          // 有移动构造 → 真的移动
    (void)b; (void)d;
}
```

<!-- result:ch12_rule_of_five -->
```text
-- std::move(OnlyDtor) --
OnlyDtor copy
-- std::move(WithMove) --
WithMove move
```

**`std::move(a)` 明明写了，`OnlyDtor` 还是走了拷贝。** 而且**没有任何警告。**

**为什么**：因为标准规定——**用户声明了析构函数（或拷贝操作、或另一个移动操作）时，
移动操作不会被隐式生成**。这是"三/五法则"的直接后果：

| 你声明了什么 | 编译器还会隐式生成什么 |
|---|---|
| 什么都没声明 | 拷贝构造、拷贝赋值、移动构造、移动赋值、析构（都可能） |
| **析构函数** | 拷贝操作（**弃用**但仍生成）；**移动操作不生成** |
| 拷贝构造或拷贝赋值 | **移动操作不生成** |
| 移动构造或移动赋值 | **拷贝操作被删除** |

**这就是"五法则"**：如果你需要写其中任何一个（析构、拷贝构造、拷贝赋值、移动构造、移动赋值），
**就要考虑把五个都写出来或显式 `= default` / `= delete`**。

> ⚠️ **坑（本机实测过）**：给一个已有的类加了析构函数（比如为了记日志），
> 于是**它的移动操作悄悄消失了**，所有 `std::move` 全部退回拷贝，**性能下降且无任何提示**。
> **修法**：加析构的同时把移动操作 `= default` 出来。

### 5.2 场景二：`const` 对象上的 `std::move` 等于没写

<!-- example:ch12_const_no_move -->
```cpp
#include <iostream>
#include <utility>

struct P {
    P() = default;
    P(const P&) { std::cout << "copy\n"; }
    P(P&&) noexcept { std::cout << "move\n"; }
};

int main() {
    P p;
    const P cp;
    std::cout << "-- from non-const --\n";
    P a{std::move(p)};
    std::cout << "-- from const --\n";
    P b{std::move(cp)};
    (void)a; (void)b;
}
```

<!-- result:ch12_const_no_move -->
```text
-- from non-const --
move
-- from const --
copy
```

**同一个 `std::move`，在 `const` 对象上退回了拷贝。**

**为什么**：移动构造的参数是 `P&&`，而 `std::move(cp)` 得到的是 `const P&&`——
**`const P&&` 绑不到 `P&&` 上**，只能绑 `const P&`，于是选到拷贝构造。

> **这条的实际影响很大**：`const` 是接口设计的默认选择（第 07 章讲过），
> 但**如果某个对象最终要被移走，就不能把它弄成 `const`**。
> 常见症状："我明明用了 `std::move`，性能却没变好"——去检查那个对象是不是 `const`。

## 6. 智能指针：把所有权写进类型里

**先立一条判断**：智能指针解决的不是"忘记 `delete`"这个症状，
而是**"所有权不明确"这个根因**。第 06 章讲过裸指针的四个坑（悬垂、泄漏、重复释放、越界），
智能指针用**类型**把所有权表达出来，于是前三个坑在编译期或运行期被挡住。

### 6.1 `unique_ptr`：独占所有权

<!-- example:ch12_unique_ptr -->
```cpp
#include <iostream>
#include <memory>

struct Res {
    int v;
    Res(int x) : v(x) { std::cout << "acquire " << v << '\n'; }
    ~Res() { std::cout << "release " << v << '\n'; }
};

int main() {
    auto p = std::make_unique<Res>(1);
    std::cout << p->v << '\n';
    auto q = std::move(p);            // 所有权转移
    std::cout << "p is " << (p ? "not null" : "null") << '\n';
    std::cout << q->v << '\n';
}
```

<!-- result:ch12_unique_ptr -->
```text
acquire 1
1
p is null
1
release 1
```

**读这段输出，关注三件事：**

1. **`acquire 1` 在 `p->v` 之前** —— 构造即获取资源（RAII 的"获取"半边）
2. **`auto q = std::move(p);` 之后 `p is null`** —— `unique_ptr` **不可拷贝，只能移动**；
   移动之后源指针变成空
3. **`release 1` 只出现一次，而且在最后** —— 出了作用域自动释放（RAII 的"释放"半边）
   **注意它是在 `q` 的析构里发生的，不是 `p`**，因为所有权已经转移

**`unique_ptr` 的三个关键性质**：

| 性质 | 含义 |
|---|---|
| **不可拷贝** | `auto q = p;` **编译错误**。所有权唯一 |
| **可以移动** | `auto q = std::move(p);` 把所有权交出去 |
| **零开销** | 它就是一个裸指针加一个删除器，不占额外空间、无运行时成本 |

> **判据：默认用 `unique_ptr`。** 只有确实需要共享所有权时才用 `shared_ptr`——
> 因为 `shared_ptr` 有引用计数的开销，而且**循环引用会泄漏**。

### 6.2 `shared_ptr`：共享所有权与引用计数

<!-- example:ch12_shared_ptr -->
```cpp
#include <iostream>
#include <memory>

struct Res {
    ~Res() { std::cout << "destroyed\n"; }
};

int main() {
    auto p = std::make_shared<Res>();
    std::cout << p.use_count() << '\n';
    {
        auto q = p;
        std::cout << p.use_count() << '\n';
    }
    std::cout << p.use_count() << '\n';
    p.reset();
    std::cout << "after reset\n";
}
```

<!-- result:ch12_shared_ptr -->
```text
1
2
1
destroyed
after reset
```

**逐行读：**

```text
1              ← 只有 p 持有
2              ← q = p：计数变 2
1              ← q 出作用域被销毁，计数回到 1
destroyed      ← p.reset() 使计数归零 → 对象被删除
after reset    ← 这行在"destroyed"之后
```

**关键观察**：`destroyed` 出现在 `after reset` **之前**。
说明 `p.reset()` 那一刻引用计数归零、对象立即被销毁——**不是等到程序结束**。

| 三兄弟 | 语义 | 什么时候用 |
|---|---|---|
| `unique_ptr` | 独占 | **默认选择** |
| `shared_ptr` | 共享（引用计数） | 确实多处持有同一对象，且**没有环** |
| `weak_ptr` | 弱引用（不增加计数） | **打破 `shared_ptr` 的循环引用** |

> ⚠️ **坑：`shared_ptr` 循环引用会泄漏。**
> A 持有 `shared_ptr<B>`、B 持有 `shared_ptr<A>`，两者的计数都永远到不了 0，
> 于是**在纯 `shared_ptr` 的世界里这是无法回收的**。修法是把其中一边改成 `weak_ptr`。
> 这类错误的归属：**不是内存管理错误，是设计错误**——所有权本来就不该是双向强引用。

> ⚠️ **坑：不要用同一个裸指针构造两个 `shared_ptr`。**
> ```cpp
> int* raw = new int{1};
> std::shared_ptr<int> a{raw};
> std::shared_ptr<int> b{raw};   // ❌ 两个独立的引用计数，会 double free
> ```
> **正确做法：用 `std::make_shared`**（一次分配，且异常安全）。

## 7. RAII：为什么异常也安全

**RAII**（Resource Acquisition Is Initialization，资源获取即初始化）是 C++ 最核心的设计范式。
它的意思不是"用初始化来获取资源"这么绕，而是：

> **把资源的生命周期绑在对象的生命周期上。**
> 构造时获取，析构时释放。正常离开作用域，或异常栈展开到匹配处理器时，已构造的自动局部对象会被析构。
> **边界**：`std::exit` 不析构自动局部对象；`std::abort` 不执行这些析构，`std::terminate` 也不保证完成栈展开。RAII 不承诺所有进程终止路径都清理资源。

### 7.1 关键证明：异常路径上析构也会被调用

<!-- example:ch12_raii_exception -->
```cpp
#include <iostream>
#include <stdexcept>

struct Guard {
    const char* name;
    explicit Guard(const char* n) : name(n) { std::cout << "enter " << name << '\n'; }
    ~Guard() { std::cout << "exit " << name << '\n'; }
};

void risky() {
    Guard g{"risky"};
    throw std::runtime_error{"boom"};
}

int main() {
    try {
        risky();
    } catch (const std::exception& e) {
        std::cout << "caught: " << e.what() << '\n';
    }
}
```

<!-- result:ch12_raii_exception -->
```text
enter risky
exit risky
caught: boom
```

**注意 `exit risky` 出现在 `caught: boom` 之前。** 这说明：

```text
1. risky() 里构造 Guard g            → enter risky
2. throw 抛出异常
3. 栈展开（stack unwinding）开始：
     沿着调用栈往回走，把每一层的局部对象析构
     走到 risky 这一层 → 析构 g       → exit risky
4. 到达 catch，异常被捕获             → caught: boom
```

**这就是"异常也安全"的机制**：不是靠 `catch` 里写清理代码，
而是**靠栈展开保证每一层的局部对象都被析构**。

> **为什么这件事极重要**：用裸指针的写法，若调用抛出异常，位于它**之后**的 `delete` 就执行不到，资源会泄漏：
> ```cpp
> void bad() {
>     int* p = new int{1};
>     might_throw();      // 这里抛了 → 下面的 delete 永远不执行
>     delete p;           // ❌ 到不了
> }
> ```
> **换成 `unique_ptr` 就自动解决**——析构由栈展开触发，不需要你记得写 `delete`。
> 这就是第 06 章那句"指针错误分类"的最终答案：**根因是所有权没写进类型**。

### 7.2 自己写一个 RAII 类

<!-- example:ch12_raii_custom -->
```cpp
#include <iostream>

class File {
public:
    explicit File(const char* n) : name(n) { std::cout << "open " << name << '\n'; }
    ~File() { std::cout << "close " << name << '\n'; }
    File(const File&) = delete;              // 不可拷贝
    File& operator=(const File&) = delete;
private:
    const char* name;
};

int main() {
    File f{"data.txt"};
    std::cout << "working\n";
}
```

<!-- result:ch12_raii_custom -->
```text
open data.txt
working
close data.txt
```

**两个设计决策值得注意：**

1. **`File(const File&) = delete;`** —— **显式禁止拷贝**。
   因为"文件句柄"是独占资源，拷贝会导致**两个对象析构同一个句柄**（重复释放）。
   **独占句柄的包装类应禁止浅拷贝**，需要转移就实现移动。RAII 本身不排斥拷贝：`std::vector`、`std::string` 可以复制内容，`shared_ptr` 可以共享所有权。
2. **析构里做的事就是"释放"** —— 这里用打印代替真实的 `close()`。
   真实代码里如果 `close()` 可能失败，**析构函数不能抛异常**（第 08 章讲过），
   通常的做法是提供一个显式的 `close()` 让用户调用，析构里只做兜底。

### 7.3 标准库里到处都是 RAII

| 资源 | RAII 包装 | 析构时释放什么 |
|---|---|---|
| 堆内存 | `unique_ptr` / `shared_ptr` | `delete` |
| 文件 | `ifstream` / `ofstream` / `fstream` | 关闭文件 |
| 互斥锁 | `lock_guard` / `unique_lock` | 解锁 |
| 动态数组 | `std::vector` / `std::string` | 释放缓冲区 |
| 任意资源的自定义清理 | 自己写的 RAII 类 | 你定义的清理动作 |

> **判据**：**看到一个需要"成对操作"的资源（new/delete、open/close、lock/unlock），
> 就应该想到 RAII。** 手写成对调用是这个项目里最常见的设计缺陷来源。

## 8. 移后对象：为什么"有效"不等于"有用"

<!-- example:ch12_moved_from -->
```cpp
#include <iostream>
#include <string>
#include <utility>

int main() {
    std::string s = "hello";
    std::string t = std::move(s);
    std::cout << "t = " << t << '\n';
    std::cout << "s.size() = " << s.size() << '\n';
    s = "reused";                 // 移后对象可以重新赋值
    std::cout << "s = " << s << '\n';
}
```

<!-- result:ch12_moved_from -->
```text
t = hello
s.size() = 0
s = reused
```

**除另有规定外，标准库类型的移后对象处于有效但未指定的状态**；这里讨论的是 `std::string`。用户自定义类型的移后状态需要看自己的契约，不能直接套用。逐词解释：

| 词 | 含义 |
|---|---|
| **valid**（有效） | 对象仍然是一个合法的 `std::string`，**可以安全地析构、可以重新赋值** |
| **unspecified**（未指定） | **标准不告诉你它的内容是什么**。本机是空串，但**别的实现可能不是** |

**所以允许做的事：**

- ✅ 重新给它赋值（`s = "reused"`）
- ✅ 析构它（一定会发生）
- ✅ 调用没有额外前置条件的操作（比如 `s.clear()`、`s.size()`、`s.empty()`）；有前置条件的操作须先检查

**不允许做的事：**

- ❌ **假设它是空的**（`s.size() == 0` 在本机成立，但标准不保证）
- ❌ 读取它的内容并当作有意义的业务数据

> **使用规则**：把拷贝改成移动时，必须先确认后续代码不再需要源对象原有的值。移动可以改变源对象状态和可观察行为，不能无条件视为「只改变性能」。

## 9. 完美转发：`std::forward` 解决的问题

第 1 节留了一个问题：`int&& r = 5;` 之后，**`r` 这个名字是左值**。
所以如果把 `r` 继续往下传，它会退回拷贝版本。**`std::forward` 就是解决这个的。**

```cpp
template <class T>
void wrapper(T&& arg) {              // T&& 在这里是"转发引用"
    inner(std::forward<T>(arg));     // 保持 arg 原本的值类别
}
```

| | `std::move` | `std::forward` |
|---|---|---|
| 作用 | **无条件**转成右值 | **有条件**：原本是右值才转成右值，原本是左值就保持左值 |
| 用在哪 | 你确定不再需要这个对象时 | **模板里转发参数**时 |
| 是 cast 吗 | ✅ 是 | ✅ 是；是否留下调用指令属于实现问题 |

**为什么要区分**：`std::move` 会**无条件**把左值也变成右值，
在转发场景里这意味着"把调用者的左值参数也偷掉了"——那是灾难性的 bug。
`std::forward` 只恢复**原本**的值类别，不多不少。

> **入门阶段的处理**：这一节只需要知道**它存在、它和 `std::move` 的区别是什么**。
> 转发引用（`T&&` 在模板里的特殊推导）和引用折叠还需要后续专题补讲；**当前第 13 章没有这些内容**。
> **现在不要自己在模板里手写 `std::forward`**——先学会用标准库（`emplace_back` 之类已经替你做了）。

> ⚠️ **注意**：`T&&` 在**模板参数**里和在**普通函数参数**里含义不同。
> - 普通函数 `void f(T&&)`：右值引用，只能接右值
> - 模板 `template<class T> void f(T&&)`：**转发引用**，左右值都能接
>
> 这个区别属于 C++17 基线；本节尚未给出完整的推导与验证，不能据此视为已经掌握完美转发。

## 10. 本章自测

**1.** `std::move(x)` 到底做了什么？它会产生机器码吗？

<details><summary>答案</summary>

它**只做一件事**：把表达式 `x` 的值类别从左值转成右值（本质是一个 `static_cast`）。
它本身**不搬运资源**；标准描述的是转换语义，不承诺调试版或其他构建下生成零条指令。

**本机实测**佐证：对 `int x = 5;` 用 `std::move` 后，`x` 仍然是 5，输出 `5 5`。
因为 `int` 没有"可偷的资源"，移动**就是拷贝**。

**准确的措辞**：`std::move` 是"**允许**编译器选移动版本"，不是"**执行**移动"。
</details>

**2.** 为什么 `return std::move(local);` 是个错误？正确写法是什么？

<details><summary>答案</summary>

因为**具名局部变量返回时本来可以触发 NRVO（拷贝省略）**，
而 `std::move(local)` 把它变成右值，**反而阻止了省略**，退化成一次真正的移动。

**NRVO 比移动更快**（零次构造），所以加上 `std::move` **是负优化**。

**正确写法**：`return local;` —— 什么都不加。

**例外**：返回的是**成员变量**或**函数参数**时，它们不享受 NRVO，这时才需要显式 `std::move`。
</details>

**3.** 下面这段代码，`b` 是拷贝构造还是移动构造？为什么？

```cpp
struct P {
    P() = default;
    P(const P&) { std::cout << "copy\n"; }
    P(P&&) noexcept { std::cout << "move\n"; }
};
const P cp;
P b{std::move(cp)};
```

<details><summary>答案</summary>

**拷贝构造**（打印 `copy`）。本机实测确认。

**为什么**：移动构造的参数是 `P&&`，而 `std::move(cp)` 得到 `const P&&`。
**`const P&&` 绑不到 `P&&` 上**（那会丢掉 `const`），只能绑 `const P&`，于是选到拷贝构造。

**实际影响很大**：一个对象如果要被移走，**就不能是 `const`**。
症状是"我用了 `std::move` 但性能没变好"——先检查那个对象是不是 `const`。
</details>

**4.** 给一个类加了析构函数，为什么它的 `std::move` 全都退回拷贝了？

<details><summary>答案</summary>

因为标准规定：**用户声明了析构函数（或拷贝操作、或另一个移动操作）时，移动操作不会被隐式生成。**

于是 `P b{std::move(a)}` 找不到移动构造，**静默退回拷贝构造**——**而且没有任何警告**。

本机实测的证据：`OnlyDtor`（只声明了析构）打印 `copy`，`WithMove`（显式写了移动构造）打印 `move`。

**修法**：声明析构的同时把移动操作补上：

```cpp
~OnlyDtor() {}
OnlyDtor(OnlyDtor&&) noexcept = default;
OnlyDtor& operator=(OnlyDtor&&) noexcept = default;
```

**这就是"五法则"**：需要写析构/拷贝/移动中的任一个，就要考虑五个一起写清楚。
</details>

**5.** C++17 对拷贝省略做了什么改变？RVO 和 NRVO 哪个是保证的？

<details><summary>答案</summary>

**C++17 起，两个场景变成"保证省略"（mandatory elision）**：
`T x = T();` 和 `T f() { return T{}; } T x = f();`。
以前只是"允许省略"，现在**必须省略**——所以这些场景**不再要求有可访问的拷贝/移动构造函数**。

**RVO（返回纯右值）→ ✅ 保证；NRVO（返回具名局部变量）→ ⚠️ 允许但不保证。**

本机实测佐证：`Noisy a = make();` 和 `Noisy b = Noisy{};` 都**只打印 `default`**，
既没有 copy 也没有 move；只有 `Noisy c = std::move(b);` 才打印 `move`。

**为什么 NRVO 不保证**：要不要省略取决于编译器能否证明"所有返回路径都返回同一个对象"，
这不是语言能一刀切规定的事。
</details>

**6.** 我把每个示例都按 `/Od` 和 `/O2` 各跑了一遍，十组输出**逐字相同**。这说明了什么？

<details><summary>答案</summary>

只能说明这十组示例在这些构建条件下输出相同。一般优化须遵守可观察行为约束，但**允许的拷贝省略是特殊规则**：NRVO 可以省去有输出的构造调用。
本章第 4.3 节的对照中，`/Od /Zc:nrvo-` 打印 `ctor → move → done`，`/O2 /Zc:nrvo` 打印 `ctor → done`，不需要 UB 就能出现差异。不能把输出差异当作 UB 的充分证据。
</details>

**7.** `unique_ptr` 和 `shared_ptr` 的核心区别是什么？默认该用哪个？

<details><summary>答案</summary>

- **`unique_ptr`：独占所有权。** 不可拷贝、只能移动。**零开销**（就是一个裸指针加删除器）。
- **`shared_ptr`：共享所有权。** 可拷贝，靠**引用计数**决定何时释放。有额外开销。

**默认用 `unique_ptr`。** 只有确实需要"多处持有同一对象"时才用 `shared_ptr`。

本机实测 `shared_ptr` 的计数变化：`1 → 2 → 1 → destroyed`，
且 `destroyed` 出现在 `reset()` 那一刻（不是程序结束），说明**计数归零立即释放**。

**`shared_ptr` 的两个坑**：① **循环引用会泄漏**（要用 `weak_ptr` 打破）；
② **不要用同一个裸指针构造两个 `shared_ptr`**（会 double free），要用 `make_shared`。
</details>

**8.** 为什么 RAII 能保证"异常路径上资源也被释放"？机制是什么？

<details><summary>答案</summary>

机制是**栈展开（stack unwinding）**。

`throw` 之后，控制流沿着调用栈往回走，**每一层的局部对象都会被析构**，
直到遇到能处理它的 `catch`。

本机实测：

```text
enter risky     ← 构造 Guard
exit risky      ← ⚠️ 关键：异常抛出后、被捕获前，Guard 被析构了
caught: boom
```

**`exit risky` 在 `caught: boom` 之前** —— 证明析构发生在栈展开过程中，不是靠 `catch` 里的清理代码。

**这解释了裸指针写法的泄漏路径**：异常调用之后的 `delete` 执行不到。
换成 `unique_ptr` 就自动解决——**析构由栈展开触发，不需要你记得写 `delete`**。

**RAII 的本质**：把资源的生命周期绑在对象的生命周期上；保证的边界是正常作用域退出和通向处理器的异常栈展开，不包括所有进程终止方式。
</details>

**9.** "移后对象处于有效但未指定的状态"——这两半各是什么意思？哪些事是允许做的？

<details><summary>答案</summary>

- **valid（有效）**：它仍然是一个合法的对象，**可以安全析构、可以重新赋值**。
  不是"已损坏的垃圾"。
- **unspecified（未指定）**：**标准不告诉你它的内容**。本机实测 `std::string` 被移后 `size() == 0`，
  但**别的实现可能不是**，所以不能依赖。

**允许做**：重新赋值、析构、调用不依赖具体值的操作（如 `clear()`）。
**不允许做**：假设它是空的、把它的内容当有意义的业务数据读。

本机实测：

```text
t = hello
s.size() = 0        ← 本机是 0，但不是标准保证
s = reused          ← 移后可以重新赋值 ✅
```

**推论**：**移动只应改变性能，不应改变程序语义。** 如果移走之后结果就不对了，
那是设计错误（依赖了移后对象的内容），不是移动语义的坑。
</details>

**10.** `std::move` 和 `std::forward` 的分工是什么？什么时候用哪个？

<details><summary>答案</summary>

| | `std::move` | `std::forward` |
|---|---|---|
| 转换 | **无条件**转成右值 | **有条件**：原本左值就保持左值，原本右值才转右值 |
| 场景 | 你**确定不再需要**这个对象时 | **模板里转发参数**时 |
| 是否自己搬运资源 | 否 | 否 |

**为什么不能用 `std::move` 转发**：它会把调用者传进来的**左值参数也无条件转成右值**，
于是"偷走"了调用者还要用的对象——这是灾难性的 bug。

**入门阶段的建议**：知道它存在、知道区别就够了。**不要自己在模板里手写 `std::forward`**——
标准库的 `emplace_back` / `make_unique` 之类已经替你处理好了。

> ⚠️ 注意 `T&&` 在**普通函数参数**里是右值引用，在**模板参数**里是**转发引用**（左右值都能接）——
> 完整的转发引用推导与引用折叠尚待专题补讲，当前第 13 章没有展开。
</details>
