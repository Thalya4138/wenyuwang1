## 三、它抓到的真问题（我逐条复核）

### 3.1 ✅ 接受：第 03 章值类别的教法是错的（**本轮最有价值的一条**）

它的判断（`ATTACK-02-REPLY` 里选为"最危险的心智模型"）：

> 第 03 章第 2 节的「**有名字就是左值、没名字就是纯右值**」把表达式的语义分类
> **误教成变量命名规则**：`*p` 与字符串字面量没有变量名形式却都是左值；
> 返回对象右值引用的函数调用是将亡值。

**我复核：它完全正确。** 这条错误的危害是具体的——读者会写出：

- 不合法的 `&std::move(x)`（将亡值不能取地址）
- 在模板里把匿名左值错误地强制移动，**意外转走调用者仍需要的资源**

**它给出三处具体错误并已改**：

| 位置 | 原来（错） | 改成 |
|---|---|---|
| `03` 第 33 行 | "有名字的东西是左值；没名字的…是纯右值…能解决九成问题" | 按**表达式形式**分类的规则 |
| `03` 第 171 行 | 将亡值"通常能"取地址、"即将失效" | **不能**取地址；去掉了"即将失效"这个不准确的措辞 |
| `03` 第 272 行 | "prvalue 与 xvalue 在 `decltype` 里都表现为非引用类型" | `decltype` 对左值给 `T&`、**将亡值给 `T&&`**、纯右值给 `T` |

**它新增的可验证反例我实测通过**（`ch03_value_category_rules`，39 块里的第 39 块）：

```cpp
int&& as_rvalue(int& x) { return std::move(x); }   // 返回对象右值引用 → 将亡值
std::cout << std::is_lvalue_reference<decltype((*p))>::value;      // true
std::cout << std::is_lvalue_reference<decltype(("hi"))>::value;    // true（字符串字面量是左值）
std::cout << std::is_rvalue_reference<decltype(as_rvalue(x))>::value;  // true（将亡值）
```

> **这条改动的意义超出"纠错"**：它把一条**看似方便的口诀**换成了**可判定的规则 + 反例**。
> 口诀在入门阶段"能解决九成问题"这句话本身就是危险的——**剩下那一成正好是最容易出 bug 的地方。**

### 3.2 ✅ 接受：它修了我验证脚本里的一个真缺陷（**第二有价值**）

### 6.2 ✅ 修第 10 章 8.2 节的实测口吻（FIX-03 第 2 条，**红线 2**）

**原来的问题有三层**：

1. 表格写"n=64 时 ~32 次 / n=10⁶ 时 ~500 000 次"——**那是复杂度推算，却排得像测过的**
2. 正文写"**两者都是微秒级**"——**本机根本没计时，这句是编的**
3. 整节**只有一个程序跑了一次**（那个例子只打印命中次数），
   却下了"数据量上百万时差别才明显"这种**关于时间的预测**

**改后**：

- 表格标注为"**由复杂度推算的比较次数（不是计量结果）**"
- 明确写出"**本节这个例子证明了什么、没证明什么**"：
  ✅ 证明了结果相同、比较次数量级不同；❌ **没证明任何时间差别**
- **补了一条反直觉提醒**：`vector` 线性扫描内存连续，常数因子可能比红黑树的指针追逐小得多，
  **小 n 时它有时反而更快**——所以"小数据下都差不多"也不能当结论
- 结论收窄为："**要下'谁更快'的结论，只有一条路：自己写计时程序测。**"

**这条修的是本项目的红线 2**（不得把没有当次工具输出支撑的说法写进正文）。
**而它是我自己犯的**——子 agent 写的时候，我没逐句核它的实测口吻。
