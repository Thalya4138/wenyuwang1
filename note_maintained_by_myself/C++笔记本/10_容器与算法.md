## 0. 先记住的七件事

1. **迭代器是容器和算法之间的合同。** 算法不认识 `vector`，它只认识"两个指位置的迭代器"。这就是为什么 `std::sort` 能同时排 `vector`、`array` 和普通数组——它**只要求随机访问迭代器**，不要求具体容器。
2. **每个标准容器都提供 `begin()` / `end()`。** `end()` 指向**最后一个元素之后**，不是最后一个元素。这个"半开区间"约定是标准库所有范围操作的统一口径。
3. **`vector` 是默认选择。** 除非你有具体理由，先用 `vector`；理由必须具体到"我要在头部插入"或"我要按键查值"这个级别。
4. **`vector<int> v{1, 2}` 和 `vector<int> v(1, 2)` 语义完全不同。** 前者是**两个元素** `1`、`2`；后者是**两个 `1`**。这是本章最该动手试一次的地方（第 2 节）。
5. **结构化绑定（C++17）让"取出一对值"不用再写 `.first` / `.second`。** `for (const auto& [k, v] : m)` 是本章出现频率最高的写法。
6. **迭代器失效是这章唯一会让你程序"时对时错"的东西。** `vector` 一旦扩容，**所有**旧迭代器、指针、引用立刻作废——而且多数情况下程序不会立刻崩（第 7 节）。
7. **算法不会替你检查边界。** `std::find` 找不到就返回 `end()`，是否检查由你负责；`std::sort` 的"小于"关系写错也不会报错，只会得到错的顺序。

> 如果只记一条，记第 6 条。它是本章唯一会造成**未定义行为**的地方。

## 1. 迭代器与范围：标准库的地基

### 1.1 先说它解决什么问题

假设没有迭代器。你想写一个"把一串整数求和"的函数，签名只能是：

```cpp
int sum(const std::vector<int>& v);      // 只能收 vector
int sum(const std::array<int, 4>& v);    // 又得写一遍
int sum(const int* p, int n);            // 还得写一遍
```

三个函数体一模一样，只是"怎么走下一步"和"怎么判断结束"不同。**标准库的解法是把"走"和"判结束"抽成两个对象——迭代器。**

于是有了 `std::accumulate` 这种签名：

```cpp
template <class It, class T>
T accumulate(It first, It last, T init);   // 只出现在头文件里的概念性签名
```

它收的**不是容器**，是"起点"和"终点"。容器是谁无所谓。

> **所以迭代器不是"更安全的指针"这么简单**，它是标准库用来把容器和算法**解耦**的那一层。
> 第 11 章会看到：这种"函数只描述需要什么能力、不描述具体类型"的写法正是模板的用途。

### 1.2 最小例子：同一个序列的三种走法

<!-- example:ch10_iter_basic -->
```cpp
#include <iostream>
#include <type_traits>
#include <vector>

int main() {
    std::vector<int> v{1, 2, 3};

    std::cout << "范围 for  :";
    for (int x : v) {
        std::cout << ' ' << x;
    }
    std::cout << '\n';

    std::cout << "begin/end :";
    for (auto it = v.begin(); it != v.end(); ++it) {
        std::cout << ' ' << *it;
    }
    std::cout << '\n';

    std::cout << "反向迭代  :";
    for (auto it = v.rbegin(); it != v.rend(); ++it) {
        std::cout << ' ' << *it;
    }
    std::cout << '\n';

    auto it = v.begin();
    std::cout << "*it        = " << *it << '\n';
    std::cout << "*(it + 2)  = " << *(it + 2) << '\n';
    std::cout << "it[1]      = " << it[1] << '\n';
    std::cout << "end - begin= " << (v.end() - v.begin()) << '\n';
    std::cout << "*v.end() 是越界，这里不比\n";

    std::cout << "begin 的类型是 vector<int>::iterator : "
              << std::is_same<decltype(it), std::vector<int>::iterator>::value << '\n';
}
```

<!-- result:ch10_iter_basic -->
```text
范围 for  : 1 2 3
begin/end : 1 2 3
反向迭代  : 3 2 1
*it        = 1
*(it + 2)  = 3
it[1]      = 2
end - begin= 3
*v.end() 是越界，这里不比
begin 的类型是 vector<int>::iterator : 1
```

**三种走法给出同一组数字，但机制不同：**

| 写法 | 编译器实际做的事 |
|---|---|
| `for (int x : v)` | 展开成 `begin()` / `end()` 的循环，`x` 是**每个元素的拷贝** |
| `for (auto it = ...)` | 你**手动**控制迭代器，`*it` 取出的是元素的**引用** |
| `for (auto it = v.rbegin(); ...)` | 反向迭代器，`++` 是往**前**走 |

**最后一行 `is_same<...>::value` 打印 `1`，说明 `v.begin()` 的类型的确实就是 `std::vector<int>::iterator`**——不是 `int*`，虽然在这台机器上它内部可能就是个指针（这个"内部怎么实现"标准不规定，见章末诚实标注）。

### 1.3 这一节的符号表（后面全要用）

C++ 的迭代器全靠运算符表达，所以先把符号定死：

| 符号 | 名字 | 对迭代器干什么 |
|---|---|---|
| `*it` | 解引用 | 取出 `it` 指向的**那个元素**（左值，可读可写） |
| `++it` / `it++` | 前置 / 后置递增 | 让 `it` 指向下一个元素 |
| `it->member` | 箭头 | 等价于 `(*it).member` |
| `it[n]` | 下标 | 等价于 `*(it + n)`，**只有随机访问迭代器支持** |
| `it1 - it2` | 相减 | 两个迭代器之间隔着几个元素，**只有随机访问迭代器支持** |
| `==` / `!=` | 比较 | 判断是不是同一个位置。**循环条件永远写 `it != last`，不要写 `<`**（有些迭代器不支持 `<`） |
| `v.begin()` / `v.end()` | 范围 | 标准库统一用"**左闭右开**" `[begin, end)` |

### 1.4 为什么 `end()` 指向"最后一个元素的后面"

这是标准库最容易让人在第一次犯错的设计。看一个空容器：

```cpp
std::vector<int> v;             // 空
v.begin() == v.end()            // 成立：空范围就是"起点等于终点"
```

**半开区间 `[first, last)` 的好处**是三个操作全部不用特判：

| 操作 | 半开区间的写法 | 如果改成闭区间会怎样 |
|---|---|---|
| 判空 | `first == last` | 要判断"起点是不是在终点之后" |
| 遍历 | `for (; first != last; ++first)` | `last` 处要单独处理 |
| 长度 | `last - first` | `last - first + 1` |

> ⚠️ **坑**：`*v.end()` 是**越界解引用，未定义行为**。
> 上面示例里我特意没写 `*v.end()`，只写了文字提醒。
> `end()` 的用途**只有一个**：当哨兵比较用。它不是"可以看的最后一个位置"。

## 2. `std::vector`：默认该选的那个顺序容器

### 2.1 它是什么

`std::vector<T>` 是**一段连续内存上的动态数组**。三个关键量要分清：

| 量 | 含义 | 怎么查 |
|---|---|---|
| `size()` | 现在装了几个元素 | `v.size()` |
| `capacity()` | 现在这段内存最多能装几个 | `v.capacity()` |
| `data()` | 这段内存的首地址 | `v.data()` |

**`size` 和 `capacity` 分开，是 `vector` 全部性能特征和全部迭代器失效问题的根源。** 下面这个例子把它们一起打出来。

<!-- example:ch10_vector_ops -->
```cpp
#include <iostream>
#include <vector>

int main() {
    std::vector<int> v;
    std::cout << "起始 size=" << v.size() << " capacity=" << v.capacity() << '\n';

    std::size_t last = v.capacity();
    for (int i = 1; i <= 10; ++i) {
        v.push_back(i);
        if (v.capacity() != last) {
            std::cout << "push_back " << i << " 后 -> size=" << v.size()
                      << " capacity=" << v.capacity() << "  （扩容了）\n";
            last = v.capacity();
        }
    }

    std::cout << "front=" << v.front() << " back=" << v.back()
              << " v[0]=" << v[0] << '\n';

    v.pop_back();
    std::cout << "pop_back 后 back=" << v.back() << " size=" << v.size() << '\n';

    v.resize(3);
    std::cout << "resize(3) 后 size=" << v.size() << " back=" << v.back() << '\n';

    v.clear();
    std::cout << "clear() 后 size=" << v.size() << " capacity=" << v.capacity() << '\n';

    v.shrink_to_fit();
    std::cout << "shrink_to_fit 后 capacity=" << v.capacity() << '\n';

    std::vector<int> w(3);
    std::cout << "vector<int> w(3)      : size=" << w.size() << " 元素=" << w[0] << w[1] << w[2] << '\n';
    std::vector<int> x{3};
    std::cout << "vector<int> x{3}      : size=" << x.size() << " 元素=" << x[0] << '\n';
    std::vector<int> y(3, 7);
    std::cout << "vector<int> y(3, 7)   : size=" << y.size() << " 元素=" << y[0] << y[1] << y[2] << '\n';
    std::vector<int> z{3, 7};
    std::cout << "vector<int> z{3, 7}   : size=" << z.size() << " 元素=" << z[0] << z[1] << '\n';
}
```

<!-- result:ch10_vector_ops -->
```text
起始 size=0 capacity=0
push_back 1 后 -> size=1 capacity=1  （扩容了）
push_back 2 后 -> size=2 capacity=2  （扩容了）
push_back 3 后 -> size=3 capacity=3  （扩容了）
push_back 4 后 -> size=4 capacity=4  （扩容了）
push_back 5 后 -> size=5 capacity=6  （扩容了）
push_back 7 后 -> size=7 capacity=9  （扩容了）
push_back 10 后 -> size=10 capacity=13  （扩容了）
front=1 back=10 v[0]=1
pop_back 后 back=9 size=9
resize(3) 后 size=3 back=3
clear() 后 size=0 capacity=13
shrink_to_fit 后 capacity=0
vector<int> w(3)      : size=3 元素=000
vector<int> x{3}      : size=1 元素=3
vector<int> y(3, 7)   : size=3 元素=777
vector<int> z{3, 7}   : size=2 元素=37
```

**执行轨迹（扩容那几行）**：

```text
push_back(1)：capacity 0 → 不够 → 申请 1 个位置，搬过去，size=1
push_back(2)：capacity 1 → 不够 → 申请 2 个位置，把 1 搬过去，再放 2，size=2
push_back(3)：capacity 2 → 不够 → 申请 3 个位置，把 1 2 搬过去，再放 3，size=3
push_back(4)：capacity 3 → 不够 → 申请 4 个位置，把 1 2 3 搬过去，再放 4，size=4
push_back(5)：capacity 4 → 不够 → 申请 6 个位置，把 1 2 3 4 搬过去，再放 5，size=5
              ↑ 注意这一步：不是 5，是 6。多要的量是实现的策略，标准不说
push_back(6)：capacity 6 → 够 → 直接放，不扩容
push_back(7)：capacity 6 → 不够 → 申请 9 个位置…
```

**三个从这张输出里读出来的事实：**

1. **扩容 = 申请新内存 + 搬元素 + 释放旧内存。** 所以 `push_back` 的**单次成本不固定**：大多数时候是常数，偶尔是一次 O(n) 的搬运。这叫**均摊常数**（amortized O(1)）——把总成本除以操作次数是常数。
2. **本机每次扩容的倍率是 1.5 左右**（1→2→3→4→6→9→13）。**这是 MSVC 实现的策略，不是标准规定的**。GCC 的 `libstdc++` 通常用 2 倍。换编译器你会看到不同数字，但"均摊常数"这个结论不变。
3. **`clear()` 只清元素，不还内存**（`size` 变 0，`capacity` 还是 13）；要真的还回去得显式调 `shrink_to_fit()`。反过来 **`resize(3)` 后 `back()` 是 3**，因为 `resize` 变小不改变前面的值。

### 2.2 最该记的一处"看起来一样"：`{}` 还是 `()`

看上面最后四行输出：

```text
vector<int> w(3)      : size=3 元素=000
vector<int> x{3}      : size=1 元素=3
vector<int> y(3, 7)   : size=3 元素=777
vector<int> z{3, 7}   : size=2 元素=37
```

**同一个 `3`，放在圆括号里是"要几个"，放在花括号里是"元素的值"。** 这两个含义完全不同，但代码看上去只差一对括号。

把这六种写法一次摆出来：

<!-- example:ch10_vec_brace_vs_paren -->
```cpp
#include <iostream>
#include <vector>

void dump(const char* label, const std::vector<int>& v) {
    std::cout << label << " size=" << v.size() << " 内容:";
    for (int x : v) {
        std::cout << ' ' << x;
    }
    std::cout << '\n';
}

int main() {
    std::vector<int> a(3);        // 圆括号：3 个元素，值初始化成 0
    std::vector<int> b{3};        // 花括号：1 个元素，值是 3
    std::vector<int> c(3, 7);     // 圆括号：3 个元素，每个都是 7
    std::vector<int> d{3, 7};     // 花括号：2 个元素，3 和 7
    std::vector<int> e(1, 2);     // 圆括号：1 个元素，值是 2
    std::vector<int> f{1, 2};     // 花括号：2 个元素，1 和 2

    dump("vector<int> a(3)    :", a);
    dump("vector<int> b{3}    :", b);
    dump("vector<int> c(3, 7) :", c);
    dump("vector<int> d{3, 7} :", d);
    dump("vector<int> e(1, 2) :", e);
    dump("vector<int> f{1, 2} :", f);
}
```

<!-- result:ch10_vec_brace_vs_paren -->
```text
vector<int> a(3)    : size=3 内容: 0 0 0
vector<int> b{3}    : size=1 内容: 3
vector<int> c(3, 7) : size=3 内容: 7 7 7
vector<int> d{3, 7} : size=2 内容: 3 7
vector<int> e(1, 2) : size=1 内容: 2
vector<int> f{1, 2} : size=2 内容: 1 2
```

**逐条对照**：

| 写法 | `size()` | 内容 | 括号里那个数是 |
|---|---|---|---|
| `v(3)` | 3 | `0 0 0` | **元素个数** |
| `v{3}` | 1 | `3` | **元素的值** |
| `v(3, 7)` | 3 | `7 7 7` | 个数 + 每个的初值 |
| `v{3, 7}` | 2 | `3 7` | **两个元素的值** |
| `v(1, 2)` | 1 | `2` | 个数 1、初值 2 |
| `v{1, 2}` | 2 | `1 2` | 两个元素 |

**这就是第 `02` 章第 5.3 节那个"`{}` 不是万能的"警告的完整实测。**
第 02 章的结论是"默认用 `{}`"，这里要补上例外：

> ⚠️ **坑**：`std::vector<int> v{1, 2}` 与 `std::vector<int> v(1, 2)` **语义完全不同**
> ——前者是两个元素 `1`、`2`；后者是 **2 个值为 `1` 的元素**。
>
> **程序实际怎么解释它**：`vector` 有一个构造函数专门收 `std::initializer_list<T>`。
> 只要括号里每一项都能放进 `T`，**列表初始化的优先级高于其它所有构造函数**。
> 所以 `{1, 2}` 会去调"用这两个值初始化列表"，而 `(1, 2)` 会去调"个数 + 初值"那个构造函数。
>
> **错误属于哪一类**：**语义类**，不是语法类。**两者都能编过、都不报警告**，只是做的事不同。
> 这类错误没有任何自动检查能抓住你，只能靠"见到 `vector` + `{}` 就多想一秒"这个习惯。
>
> **什么时候必须用 `()`**：想让 `vector` 装"个数"的时候，
> 例如 `std::vector<int> buf(1024);` 想要的是"1024 个 0"，写成 `{1024}` 就变成了"一个 1024"。

> **一条实用规则**：**`vector` 的构造按"我想表达个数还是表达内容"选括号。**
> 表达内容（我有一串初值）→ `{}`；表达大小（我要一块 n 个元素的缓冲区）→ `()`。

### 2.3 `vector` 的常用操作速查

按"你打算干什么"分，不用背完整接口：

| 想干什么 | 写法 | 代价 |
|---|---|---|
| **尾部**加元素 | `v.push_back(x)` | 均摊 O(1)（可能触发扩容） |
| **尾部**删元素 | `v.pop_back()` | O(1)（不还内存） |
| 按下标读/写 | `v[i]` / `v.at(i)` | O(1)。**`[]` 不检查越界；`at` 越界抛 `std::out_of_range`** |
| 改大小 | `v.resize(n)` / `v.resize(n, val)` | 变小时 O(多余元素数)，变大时可能扩容 |
| 预留容量 | `v.reserve(n)` | O(1)（若 n 大于当前 capacity 会申请内存，但**不构造元素**） |
| 清空 | `v.clear()` | O(size)，**不还内存** |
| 还内存 | `v.shrink_to_fit()` | 请求（**非强制**）把 capacity 缩到 size |
| 判空 | `v.empty()` | O(1)。**比 `v.size() == 0` 更表达意图** |
| 首 / 尾元素 | `v.front()` / `v.back()` | O(1)。**空容器上调用是 UB** |
| 在**中间**插入 | `v.insert(v.begin() + k, x)` | **O(n)**：后面的元素全部要后移 |
| 在**中间**删除 | `v.erase(v.begin() + k)` | **O(n)**：后面的元素全部要前移 |

> ⚠️ **坑**：`v.reserve(n)` 和 `v.resize(n)` 是两件事。
> `reserve` 只改 `capacity`（要内存），`resize` 改 `size`（要**元素**）。
> 对含构造函数的类型（如 `std::string`），`resize(1000)` 会真的构造 1000 个对象；
> `reserve(1000)` 不会。**想避免重复扩容就用 `reserve`，想真的有一千个元素就用 `resize`。**

## 3. `array` / `deque` / `list`：vector 之外还有什么能选

`vector` 有两个"天生的弱点"：**头部插入/删除是 O(n)**，以及**容量不够时要整块搬家**。另外它还有一块**堆内存**（分配有成本）。三个替补各治其中一条。

### 3.1 最小例子

<!-- example:ch10_array_deque -->
```cpp
#include <array>
#include <deque>
#include <iostream>
#include <string>

int main() {
    std::array<int, 4> a{10, 20, 30, 40};
    std::cout << "array size=" << a.size() << " a[1]=" << a[1] << '\n';
    std::cout << "array 范围 for:";
    for (int x : a) {
        std::cout << ' ' << x;
    }
    std::cout << '\n';

    std::deque<int> dq;
    dq.push_back(2);
    dq.push_back(3);
    dq.push_front(1);
    dq.push_front(0);
    std::cout << "deque 内容:";
    for (int x : dq) {
        std::cout << ' ' << x;
    }
    std::cout << "  front=" << dq.front() << " back=" << dq.back() << '\n';
    dq.pop_front();
    std::cout << "pop_front 后 front=" << dq.front() << '\n';
}
```

<!-- result:ch10_array_deque -->
```text
array size=4 a[1]=20
array 范围 for: 10 20 30 40
deque 内容: 0 1 2 3  front=0 back=3
pop_front 后 front=1
```

### 3.2 四者分工对照表

| | `std::array<T,N>` | `std::vector<T>` | `std::deque<T>` | `std::list<T>` |
|---|---|---|---|---|
| 大小 | **编译期固定** | 运行期可变 | 运行期可变 | 运行期可变 |
| 内存布局 | 栈/对象内**连续** | 堆上**连续** | 堆上**分段连续** | 堆上**每个元素一个结点** |
| 随机访问 `v[i]` | ✅ O(1) | ✅ O(1) | ✅ O(1) | ❌ **不支持** |
| 尾部插入删除 | ❌（大小固定） | 均摊 O(1) | 均摊 O(1) | O(1) |
| **头部**插入删除 | ❌ | **O(n)** | **均摊 O(1)** | O(1) |
| 中间插入删除 | ❌ | O(n) | O(n) | **O(1)**（已经拿到位置时） |
| 能否和 C 接口对接 | ✅（可 `.data()`） | ✅（可 `.data()`，C++11 起连续保证） | ❌ 不连续 | ❌ |
| 每个元素的额外开销 | 0 | 0（但可能浪费 capacity） | 分段管理开销 | **每个结点 2 个指针** |
| 迭代器失效 | 不适用（不能改大小） | 见第 7 节 | 见第 7 节 | **只有被删的那个失效** |

### 3.3 什么时候真该用它们

| 场景 | 选择 | 理由 |
|---|---|---|
| "一串东西，个数编译期就知道" | **`std::array`** | 没有堆分配；能在栈上；大小信息不丢（不像裸数组会退化成指针） |
| "常态就是顺序存、顺序读" | **`std::vector`** | 连续内存，缓存友好。**这是绝大多数情况** |
| "两头都要频繁进出" | **`std::deque`** | `push_front` 是均摊 O(1)，`vector` 是 O(n) |
| "手里已经有某个位置，要在它旁边插/删" | **`std::list`** | O(1) 插入删除 |
| "我要排序 / 二分查找 / 随机访问" | **`std::vector`** | `list` **没有随机访问，也没有 `std::sort`** |

> ⚠️ **坑（很常见）**：以为 `std::list` 在中间插入快，所以"频繁插入就用 `list`"。
> **程序实际怎么解释它**：`list` 的 O(1) 插入**只在你已经持有那个位置的迭代器时成立**。
> 如果你要"先找到第 k 个"，`list` 得从头走 k 步（**O(k)**），而 `vector` 的 `v.begin() + k` 是 O(1)。
> 更关键的是：`list` **每个元素都带两个指针**，内存不连续，遍历时缓存命中率远低于 `vector`。
> 实践中的经验是**"除非有实测证据，否则 `vector` 在绝大多数场景比 `list` 快"**。
>
> **`list` 也不支持 `std::sort`**——它有自己的 `l.sort()` 成员函数（因为通用 `std::sort` 要求随机访问迭代器）。

> ⚠️ **还有一个坑**：`std::list` / `std::forward_list` 是标准库里**最容易被误用**的容器。
> **本节的"什么时候用哪个"结论没有做性能实测**（见章末诚实标注），它来自复杂度分析，不是本机 benchmark。

## 4. `map` / `set` / `unordered_map` / `unordered_set`：按键找值

前三个容器按**位置**存东西。这四个按**键**存东西——你问它"`"tom"` 对应的年龄是多少"，它自己去查。

### 4.1 先分清四个容器各装什么

| 容器 | 装的东西 | 一句话 |
|---|---|---|
| `std::set<K>` | **只有键** | "这个集合里有没有 5" |
| `std::map<K, V>` | **键 → 值** | "键 `K` 对应哪个 `V`" |
| `std::unordered_set<K>` | 只有键 | 同 `set`，但用哈希不用排序 |
| `std::unordered_map<K, V>` | 键 → 值 | 同 `map`，但用哈希不用排序 |

**"有序"和"无序"是唯一的分水岭。** 有序的那两个内部是**平衡二叉搜索树**（红黑树），无序的那两个内部是**哈希表**。这一个区别决定了它们全部的复杂度、要求和行为差异。

### 4.2 `map` / `set` 的最小例子

<!-- example:ch10_map_set -->
```cpp
#include <iostream>
#include <map>
#include <set>
#include <string>

int main() {
    std::map<std::string, int> age;
    age["tom"] = 20;
    age["amy"] = 22;
    age["bob"] = 19;
    age["tom"] = 21;                       // 覆盖，不新增

    std::cout << "map 大小 " << age.size() << '\n';
    for (const auto& kv : age) {
        std::cout << "  " << kv.first << " -> " << kv.second << '\n';
    }

    std::cout << "age.at(\"amy\") = " << age.at("amy") << '\n';
    std::cout << "count(\"zed\")  = " << age.count("zed") << '\n';
    auto it = age.find("zed");
    std::cout << "find(\"zed\") == end() ? " << (it == age.end()) << '\n';
    std::cout << "age[\"zed\"] 之后 size = " << age["zed"] << ' ' << age.size() << '\n';

    std::set<int> s;
    s.insert(5);
    s.insert(1);
    s.insert(5);                           // 重复插入无效
    s.insert(3);
    std::cout << "set 内容:";
    for (int x : s) {
        std::cout << ' ' << x;
    }
    std::cout << "  size=" << s.size() << " count(5)=" << s.count(5) << '\n';
}
```

<!-- result:ch10_map_set -->
```text
map 大小 3
  amy -> 22
  bob -> 19
  tom -> 21
age.at("amy") = 22
count("zed")  = 0
find("zed") == end() ? 1
age["zed"] 之后 size = 0 4
set 内容: 1 3 5  size=3 count(5)=1
```

**读这张输出，四处信息：**

1. **遍历顺序是 `amy`、`bob`、`tom`** —— 按**键的字典序**，不是我插入的顺序（我插入的是 `tom`、`amy`、`bob`）。**`map` 保证按键有序。**
2. **`age["tom"] = 21` 覆盖了原值**，`size` 还是 3。`[]` 对已存在的键是"取引用并赋值"。
3. **`age["zed"]` 之后 `size` 从 3 变成 4，而打印出来的值是 `0`。** 这就是下面那个坑。
4. **`set` 自动去重并排序**：插入顺序是 5、1、5、3，内容是 `1 3 5`，`size=3`。

> ⚠️ **坑（本节最重要的一个）**：`m[k]` 在**键不存在时会插入一个值初始化的元素**。
> 输出里 `size` 从 3 变成 4 就是证据——我本来只想"看看 `zed` 是多少"。
>
> **`operator[]` 与 `at()` 的分工**：

| 写法 | 键不存在时 | 键存在时 | 何时用 |
|---|---|---|---|
| `m[k]` | **插入** `{k, V{}}` 并返回引用 | 返回引用 | 要**写入**或确认存在 |
| `m.at(k)` | **抛 `std::out_of_range`** | 返回引用 | 只想**读**，不允许偷偷改容器 |
| `m.find(k)` | 返回 `m.end()` | 指向该元素的迭代器 | 要判断"有没有"，不想插入 |
| `m.count(k)` | 返回 `0` | 返回 `1` | 只想知道有没有 |

> **判据**：**读用 `at` 或 `find`，写才有理由用 `[]`。**
> 用 `[]` 读一个可能不存在的键，会在你没察觉的时候改掉 `size`——
> 如果后面代码依赖 `size()`，或者遍历时用了迭代器，就会出问题。
>
> 这个坑有一个经典变体：**`if (m[k] == 0)` 这样的"检查"会无条件插入**，
> 于是"读一次就多一个元素"。这类错误属于**语义类**，编译期毫无提示。

### 4.3 有序 vs 无序：对比表

<!-- example:ch10_four_assoc -->
```cpp
#include <iostream>
#include <map>
#include <set>
#include <string>
#include <unordered_map>
#include <unordered_set>
#include <vector>

int main() {
    std::vector<std::string> words{"pear", "apple", "pear", "fig", "apple", "pear"};

    std::set<std::string> s(words.begin(), words.end());
    std::unordered_set<std::string> us(words.begin(), words.end());

    std::map<std::string, int> counts;
    for (const auto& w : words) {
        ++counts[w];
    }
    std::unordered_map<std::string, int> ucounts;
    for (const auto& w : words) {
        ++ucounts[w];
    }

    std::cout << "set size=" << s.size() << "  内容:";
    for (const auto& w : s) {
        std::cout << ' ' << w;
    }
    std::cout << '\n';
    std::cout << "unordered_set size=" << us.size() << "（内容与 set 相同，顺序不保证）\n";

    std::cout << "map 的 counts[pear]=" << counts["pear"]
              << "  counts[fig]=" << counts["fig"] << '\n';
    std::cout << "unordered_map 的 ucounts[pear]=" << ucounts["pear"]
              << "  ucounts[fig]=" << ucounts["fig"] << '\n';

    const std::string key = "pear";
    std::cout << "同一个键 pear：set=" << s.count(key)
              << " unordered_set=" << us.count(key)
              << " map=" << counts.count(key)
              << " unordered_map=" << ucounts.count(key) << '\n';

    std::cout << "map 查询前 size=" << counts.size();
    std::cout << "  counts[kiwi]=" << counts["kiwi"];
    std::cout << "  查询后 size=" << counts.size() << '\n';
}
```

<!-- result:ch10_four_assoc -->
```text
set size=3  内容: apple fig pear
unordered_set size=3（内容与 set 相同，顺序不保证）
map 的 counts[pear]=3  counts[fig]=1
unordered_map 的 ucounts[pear]=3  ucounts[fig]=1
同一个键 pear：set=1 unordered_set=1 map=1 unordered_map=1
map 查询前 size=3  counts[kiwi]=0  查询后 size=4
```

**这张输出的重点是最后一行**：`counts["kiwi"]` 一读，`size` 就从 3 变成 4。四个容器对同一个键给出的**答案完全一致**（`pear` 都返回 1，计数都是 3），差别只在**顺序**和**代价**。

| | `map` / `set`（有序） | `unordered_map` / `unordered_set`（无序） |
|---|---|---|
| 底层结构 | 平衡二叉搜索树（红黑树） | 哈希表（桶数组 + 链/开放寻址） |
| 查找 / 插入 / 删除 | **O(log n)** | **平均 O(1)**，最坏 O(n) |
| 遍历顺序 | **按键的严格弱序，固定可预测** | **不规定**——同一次运行的两次遍历甚至可能不同 |
| 遍历能否得到有序序列 | ✅ 直接就是有序的 | ❌ 要自己再排一次 |
| 对键的要求 | 必须能比较（`operator<`，或自己传比较器） | 必须能**哈希**（有 `std::hash<K>` 特化）+ 能判等（`operator==`） |
| 能否范围查询（"键在 a 到 b 之间的全给我"） | ✅ `lower_bound` / `upper_bound` | ❌ 做不到 |
| 迭代器稳定性 | 插入**不使任何迭代器失效** | 插入可能触发**重哈希**，使**迭代器**全部失效 |
| 内存开销 | 每个结点带颜色和指针 | 桶数组 + 每元素的链指针/控制字节，**通常更大** |
| 自定义类型的门槛 | 写一个 `operator<` | 写一个 `operator==` + 一个 `std::hash` 特化（**更麻烦**） |

**怎么选（判据，不是口号）**：

| 你的需求 | 选 |
|---|---|
| 只要"有没有 / 对应值"，**不需要顺序** | **`unordered_*`**（平均 O(1) 更快） |
| 需要**按序遍历**，或需要范围查询 | **`map` / `set`** |
| 键的类型是标准类型（`int` / `std::string`） | 两者都方便 |
| 键是自定义类型 | **`map` / `set`**（只需一个比较运算符，门槛更低） |
| n 很小（几十个） | **都可以**，差异测不出来，选读起来清楚的 |
| 对最坏情况耗时敏感（实时系统） | **`map` / `set`**（O(log n) 是**保证**，哈希的 O(1) 只是**平均**） |

> ⚠️ **坑（属于"实现定义/不确定行为"，本机实测过一次）**：**`unordered_*` 的遍历顺序不可依赖。**
> 本机跑一次得到的是 `charlie delta bravo alpha`（这串顺序是**本机、本次**的结果）。
> 它由哈希函数和桶布局决定，**换个标准库实现、换个插入历史、甚至同一次运行的不同时刻都可能不同**。
> **所以：绝不要写依赖 `unordered_map` 遍历顺序的代码**（比如"我取第一个元素当代表"）。
> **`map` 的遍历顺序则可以依赖**——它由键的比较决定，任何实现都一样。

### 4.4 哈希要求的实测

无序容器要求键能被哈希。标准库给标准类型都准备了 `std::hash`：

<!-- example:ch10_unordered -->
```cpp
#include <iostream>
#include <string>
#include <unordered_map>

int main() {
    std::unordered_map<std::string, int> age;
    age["tom"] = 20;
    age["amy"] = 22;
    age["bob"] = 19;
    age["zed"] = 30;

    std::cout << "bucket_count = " << age.bucket_count() << '\n';
    std::cout << "load_factor  = " << age.load_factor() << '\n';
    for (const auto& kv : age) {
        std::cout << "  " << kv.first << " -> " << kv.second
                  << " (bucket " << age.bucket(kv.first) << ")\n";
    }
    std::cout << "age.at(\"amy\") = " << age.at("amy") << '\n';

    std::cout << "std::hash<std::string>{\"tom\"} = " << std::hash<std::string>{}("tom") << '\n';
}
```

<!-- result:ch10_unordered -->
```text
bucket_count = 8
load_factor  = 0.5
  tom -> 20 (bucket 3)
  amy -> 22 (bucket 6)
  zed -> 30 (bucket 4)
  bob -> 19 (bucket 4)
age.at("amy") = 22
std::hash<std::string>{"tom"} = 6267235078542562699
```

**四个量解释清楚：**

| 量 | 含义 |
|---|---|
| `bucket_count()` | 桶的个数（本机 8）。标准不规定初值 |
| `bucket(k)` | 键 `k` 落在哪个桶里 |
| `load_factor()` | `size() / bucket_count()`（本机 4/8 = 0.5） |
| `max_load_factor()` | 阈值，超过就**重哈希**（rehash）——桶更多，全部元素重新分配 |

**注意 `zed` 和 `bob` 都在 bucket 4**：这是**哈希冲突**。同一个桶里的元素靠链表或探测串起来，查找时得在里面再比一遍。**这就是"平均 O(1)、最坏 O(n)"的来源**：如果所有键都撞到一个桶，哈希表退化成一个链表。

> ⚠️ **坑**：`std::hash<std::string>{}("tom")` 打印出的那个大数字（本机 `6267235078542562699`）
> **是实现定义的**——标准只要求"同一个字符串在同一次程序运行里哈希值相同"，
> **不要求跨实现、跨版本、甚至跨进程相同**。
> **所以不要把它写进文件、不要拿它当 ID、不要跨程序比较。**
> 需要稳定哈希时得自己写（或用带种子的算法）。

> ⚠️ **另一个坑**：`std::hash` **不是加密哈希**。它被设计成"快"，不是"防碰撞"。
> 标准明确允许实现使用**每个进程随机的种子**来防止哈希碰撞攻击。
> 依赖哈希值稳定 = 依赖了一件标准没承诺的事。

## 5. `pair` / `tuple` / 结构化绑定：把几个值绑成一个小整体

### 5.1 它们解决什么问题

函数只能返回**一个**值。想返回"成功了吗 + 结果是多少"，老办法是加一个输出参数：

```cpp
bool divide(int a, int b, int& out);      // 老办法：调用方必须先准备 out
```

`std::pair` 和 `std::tuple` 让"返回多个值"变成"返回一个装了几个值的对象"。

<!-- example:ch10_pair_tuple -->
```cpp
#include <iostream>
#include <map>
#include <string>
#include <tuple>
#include <utility>
#include <vector>

std::pair<bool, int> divide(int a, int b) {
    if (b == 0) {
        return {false, 0};
    }
    return {true, a / b};
}

int main() {
    std::pair<int, std::string> p{1, "one"};
    std::cout << "pair: " << p.first << ' ' << p.second << '\n';

    auto q = std::make_pair(2, std::string("two"));
    std::cout << "make_pair: " << q.first << ' ' << q.second << '\n';

    auto r = divide(10, 3);
    auto bad = divide(10, 0);
    std::cout << "divide(10,3): ok=" << r.first << " 值=" << r.second << '\n';
    std::cout << "divide(10,0): ok=" << bad.first << " 值=" << bad.second << '\n';

    // 结构化绑定（C++17 起）
    auto [ok, value] = divide(10, 2);
    std::cout << "结构化绑定: ok=" << ok << " value=" << value << '\n';

    std::tuple<int, double, std::string> t{1, 2.5, "three"};
    std::cout << "tuple: " << std::get<0>(t) << ' ' << std::get<1>(t) << ' '
              << std::get<2>(t) << " 大小=" << std::tuple_size<decltype(t)>::value << '\n';

    auto [a, b, c] = t;
    std::cout << "tuple 结构化绑定: " << a << ' ' << b << ' ' << c << '\n';

    std::pair<int, int> pq{3, 1};
    std::cout << "pair 比较 (3,1)>(1,9) ? " << (pq > std::pair<int, int>{1, 9}) << '\n';

    std::map<std::string, int> m{{"a", 1}};
    for (const auto& [key, val] : m) {
        std::cout << "map 结构化绑定: " << key << '=' << val << '\n';
    }
}
```

<!-- result:ch10_pair_tuple -->
```text
pair: 1 one
make_pair: 2 two
divide(10,3): ok=1 值=3
divide(10,0): ok=0 值=0
结构化绑定: ok=1 value=5
tuple: 1 2.5 three 大小=3
tuple 结构化绑定: 1 2.5 three
pair 比较 (3,1)>(1,9) ? 1
map 结构化绑定: a=1
```

### 5.2 `pair` 与 `tuple` 的分工

| | `std::pair<A, B>` | `std::tuple<...>` |
|---|---|---|
| 装几个 | **固定 2 个** | 任意个（0 个也行） |
| 取元素 | `.first` / `.second` | `std::get<N>(t)`（**N 必须是编译期常量**） |
| 个数查询 | 不用查，就是 2 | `std::tuple_size<decltype(t)>::value` |
| 头文件 | `<utility>` | `<tuple>` |
| 典型用途 | `map` 的元素、返回两个值、`make_pair` | 返回三个以上、**泛型代码里转发任意个参数** |
| 常见来源 | `map` 的迭代器解引用就是 `pair<const K, V>` | 第 11 章的可变参数模板常和它一起用 |

**为什么 `pair` 仍然有用**：它是**库里的通用两元组**，`map` / `unordered_map` / `std::equal_range` 等一大批接口直接以它为元素类型。你不需要 `std::tuple` 的灵活性时，`pair` 的 `.first` / `.second` 比 `std::get<0>` 好读得多。

### 5.3 结构化绑定：C++17 给的语法糖

```cpp
auto [ok, value] = divide(10, 2);        // 而不是 auto r = ...; r.first / r.second
for (const auto& [key, val] : m) { ... } // 而不是 kv.first / kv.second
```

**它做了什么**：给一个**已存在的对象**的各个成员/元素起**新名字**。`auto [a, b, c] = t;` 等价于"先用 `t` 初始化一个隐藏副本，再把 `a`、`b`、`c` 绑定到那个副本的三个元素上"。

| 写法 | 绑到哪 | 能不能改原对象 |
|---|---|---|
| `auto [k, v] = ...` | **副本** | ❌ 改 `v` 不影响原容器 |
| `auto& [k, v] = ...` | 原对象 | ✅ 能改（但注意 `map` 的键是 `const`） |
| `const auto& [k, v] = ...` | 原对象（只读） | ❌ 不能改，**不拷贝**——遍历时用这个 |

> ⚠️ **坑**：`for (auto [k, v] : m)` **每个元素都拷贝一份**（包括 `std::string` 键和值）。
> 遍历 `map` / `unordered_map` 时默认写 **`const auto& [k, v]`**。
> 这与第 `06` 章第 4 节「引用 vs 指针」讲的"传参要不要引用"是同一个判断：
> **只要不打算改、又不想拷，就加 `const&`。**

> ⚠️ **另一个坑**：结构化绑定**不能声明成 `constexpr`，也不能在 lambda 捕获列表里单独捕获某一个名字**（C++17）。
> 需要用到其中一项时，要么捕获整个对象，要么先把它赋给一个普通变量。
> （C++20 起 lambda 的捕获规则放宽了，但本讲义基线是 C++17。）

## 6. `optional` / `variant` / `any`：把「可能没有」「多种可能」「不确定类型」写进类型

这三者是 C++17 加进 `<optional>` / `<variant>` / `<any>` 的一家人。它们的共同目标是：
**把"这个值可能是好几种状态"这件事从注释和约定搬进类型系统，让编译器帮你查。**

### 6.1 三者对比表（先看关系，再看细节）

| | `std::optional<T>` | `std::variant<A, B, ...>` | `std::any` |
|---|---|---|---|
| 能装几种可能 | **两种**：一个 `T`，或"什么都没有" | **列举出来的那几种**（编译期确定） | **任意类型**（运行期才知道） |
| "哪个分支"何时决定 | 运行期 | 运行期（但候选集编译期已知） | 运行期 |
| 取错类型会怎样 | 只有"有/没有"，`value()` 在空时抛异常 | **抛 `std::bad_variant_access`**（编译期就能查出大部分错） | **抛 `std::bad_any_cast`**（错到运行时才发现） |
| 需要类型擦除吗 | 否（`T` 是模板参数） | 否（各分支类型都在类型里） | **是**（这是它唯一的实现方式） |
| 存不下的情况 | — | 编译期就编不过 | 运行期才知道类型 |
| 典型用途 | 可能失败的返回值 | 状态机、JSON 值、多种消息 | 插件参数、脚本桥接、**很少真的该用** |

**一句话概括三者**：

```text
optional<T>        = 「T 或 空」
variant<A,B,C>     = 「A 或 B 或 C 之一，且只有这三种」
any                = 「随便什么，我知道里面是啥，信我」   ← 最弱，最后才选
```

**为什么 `any` 排在最后**：因为它**把类型检查从编译期推到了运行期**。
`any_cast<T>` 取错类型时，编译期不会拦你。这和 C++ 的核心价值（静态类型）是相反的，
所以它只在"类型信息在编译期真的不可能知道"时才有理由出现（比如配置文件驱动、跨语言桥接）。

### 6.2 最小例子

<!-- example:ch10_optional_variant -->
```cpp
#include <any>
#include <iostream>
#include <optional>
#include <string>
#include <typeinfo>
#include <variant>

std::optional<int> parse_int(const std::string& s) {
    if (s.empty()) {
        return std::nullopt;              // 明确表示"没有值"
    }
    try {
        return std::stoi(s);
    } catch (...) {
        return std::nullopt;
    }
}

// 访问 variant 的通用写法：一组重载 + std::visit
template <class... Ts>
struct overloaded : Ts... {
    using Ts::operator()...;
};
template <class... Ts>
overloaded(Ts...) -> overloaded<Ts...>;

int main() {
    std::cout << "parse_int(\"42\") 有值吗: " << parse_int("42").has_value()
              << " 值=" << parse_int("42").value_or(-1) << '\n';
    std::cout << "parse_int(\"\")  有值吗: " << parse_int("").has_value()
              << " value_or(-1)=" << parse_int("").value_or(-1) << '\n';
    std::cout << "parse_int(\"abc\") 有值吗: " << parse_int("abc").has_value() << '\n';

    std::optional<int> oe;
    std::cout << "默认构造的 optional: " << static_cast<bool>(oe) << '\n';
    oe = 5;
    std::cout << "赋值之后: " << *oe << '\n';
    oe.reset();
    std::cout << "reset 之后: " << static_cast<bool>(oe) << '\n';

    // ---------- variant：类型安全的联合体
    std::variant<int, std::string> v;
    v = 10;
    std::cout << "variant 现在装: " << std::get<int>(v) << " index=" << v.index() << '\n';
    v = std::string("文本");
    std::cout << "换一种类型后: " << std::get<std::string>(v) << " index=" << v.index() << '\n';
    std::cout << "holds_alternative<int> : " << std::holds_alternative<int>(v) << '\n';
    std::cout << "get_if<std::string> 拿到了: " << *std::get_if<std::string>(&v) << '\n';
    std::cout << "get_if<int> 是空指针吗: " << (std::get_if<int>(&v) == nullptr) << '\n';

    std::visit(overloaded{
        [](int x) { std::cout << "visit 看见 int " << x << '\n'; },
        [](const std::string& s) { std::cout << "visit 看见 string " << s << '\n'; }
    }, v);

    // ---------- any：运行时保存任意类型
    std::any box = 42;
    std::cout << "any 里是 int 吗: " << box.has_value() << ' ' << (box.type() == typeid(int)) << '\n';
    std::cout << "any_cast<int>  = " << std::any_cast<int>(box) << '\n';
    box = std::string("现在是字符串");
    std::cout << "换之后是 string 吗: " << (box.type() == typeid(std::string)) << '\n';
    std::cout << "any_cast<std::string> = " << std::any_cast<std::string>(box) << '\n';
}
```

### 6.3 `optional`：本节只补"它在类型层的位置"

**`optional` 作为"错误处理的一种方案"已经在第 `08` 章第 6.2 节「`std::optional`：可能没有值（C++17）」讲透了**
（`has_value` / `value` / `value_or` / `*` 的对照表、和错误码/异常/`std::expected` 的四方比较，都在那边）。
本节只从**类型层**补三句：

1. **`optional` 不是"引用"也不是"指针"**——它内部**直接存一个 `T` 加一个布尔标志**（`sizeof(std::optional<int>)` 通常大于 `sizeof(int)`）。
   所以它不会像裸指针那样指向别处。
2. **`optional<T&>` 在 C++17 里是不合法的**（C++20 也不合法）。要"可能没有的引用"，得用 `T*`。
3. **`*opt` 在空的时候是未定义行为**，不是抛异常。想安全就用 `.value()`（抛异常）或 `.value_or(d)`（给默认值）。

> ⚠️ **坑**：`std::optional<bool>` 有**三个状态**（`true` / `false` / 空），
> 而 `if (opt)` 判断的是"**有没有**"而不是"**值是不是真**"。
> 所以 `if (opt)` 对一个装了 `false` 的 `optional<bool>` **会走进分支**。
> 要判值必须写 `if (opt && *opt)`，或者干脆别用 `optional<bool>`（用 `enum class` 三态更清楚）。

### 6.4 `variant`：类型安全的 union

C 的 `union` 只解决"内存复用"，它**不知道现在装的是哪个成员**——读错成员是 UB。
`variant` 把"现在装的是第几个"这件事**记在对象里**（`index()`），并且**在编译期知道候选集**。

| 想干什么 | 写法 | 取错类型时 |
|---|---|---|
| 知道当前是哪个 | `v.index()` | — |
| 判断是不是某个类型 | `std::holds_alternative<T>(v)` | — |
| 取出（确定类型） | `std::get<T>(v)` | **抛 `std::bad_variant_access`** |
| 取出（想处理失败） | `std::get_if<T>(&v)` | 返回 **`nullptr`** |
| 取出（按当前类型分派） | `std::visit(visitor, v)` | 编译期就要求 visitor 覆盖**所有**分支 |

上面示例里 `get_if<int>(&v)` 打印 `1`（是空指针），是因为那时 `v` 里装的是 `std::string`。
**注意 `get_if` 收的是 `&v`（指针），返回的也是指针**——这个"指针进指针出"的形态就是为了把"失败"表达成空指针，而不是异常。

**`std::visit` 那段代码值得单独说**：`overloaded` 是**可变参数模板 + 继承 + using 声明**凑出来的
"把一组 lambda 合成一个重载集"的惯用法。它出现在本章而不是第 11 章，是因为
**它最常用的场景就是 `std::visit`**；它的语法细节（`class... Ts`、`using Ts::operator()...`、
推导指引）在第 11 章第 6 节「可变参数模板与折叠表达式」会重新讲。

> ⚠️ **坑**：`variant` 的**默认构造**不是"空的"——它构造**第一个候选类型**。
> 上面 `std::variant<int, std::string> v;` 之后 `v.index() == 0`，装的是一个值为 0 的 `int`。
> 想让"第一个类型"也能表示空，就把 `std::monostate` 放在候选列表第一位。
> （本机是否可用 `std::monostate` 本轮未单独实测，它在 C++17 的 `<variant>` 里，见章末诚实标注。）

### 6.5 `any`：为什么它排最后

`std::any` 能装任何类型，取的时候用 `std::any_cast<T>`：

| 操作 | 说明 |
|---|---|
| `any a = 42;` | 装进去（会拷贝） |
| `a.has_value()` | 里面有没有东西（**注意：不是"值是不是真"**） |
| `a.type() == typeid(T)` | 里面装的是不是 `T` |
| `std::any_cast<T>(a)` | 取出 `T`；**类型不对抛 `std::bad_any_cast`** |
| `std::any_cast<T>(&a)` | 指针版本；类型不对返回 `nullptr` |

**上面示例的输出里 `any 里是 int 吗: 1 1`** —— 第一个 `1` 是 `has_value()`，第二个 `1` 是 `type() == typeid(int)`。

**为什么它排最后，用一个对比说明**：

```cpp
std::variant<int, std::string> v = 42;
// 写错分支：
//   std::get<std::string>(v)   ← 编译期不拦，运行期抛异常
// 但下面这个编译期就过不去：
//   std::visit([](double d){ ... }, v);   ← 没有 double 分支，编译失败

std::any a = 42;
//   std::any_cast<std::string>(a)        ← 编译期也不拦，运行期抛异常
```

`variant` 的**候选集是类型的一部分**，所以 `std::visit` 能在**编译期**检查你有没有漏掉分支。
`any` 没有候选集，所有检查都推到运行期。**这就是"能早发现就早发现"在这个家族内的排序依据。**

> **选型判据（三选一，按顺序问）**：
> 1. 状态是"**有 / 没有**"两种 → **`std::optional`**
> 2. 状态是"**几种列得出来的可能**" → **`std::variant`**（优先选它，因为它保留编译期检查）
> 3. 状态是"**编译期根本不可能知道类型**" → 才考虑 `std::any`；而且先想一遍"是不是设计错了"

## 7. 迭代器失效规则：手上的迭代器什么时候变成废纸

**这一节是本章唯一会产生未定义行为的地方，也是实际项目里最容易出的一类 bug。**

### 7.1 先看现象：扩容把地址换掉了

`vector` 的 `size` 超过 `capacity` 时，它会**申请一块新内存、把元素搬过去、释放旧内存**。
旧内存一旦释放，**所有指向它的指针、引用、迭代器全部失效**。

下面这个例子**只做能确定结果的比较**（比地址、不解引用），这样它可以自动比对：

<!-- example:ch10_realloc_address -->
```cpp
#include <iostream>
#include <vector>

int main() {
    std::vector<int> v{1, 2, 3};
    v.reserve(4);

    const int* old_p = v.data();          // 记下扩容前的地址
    std::cout << "reserve(4) 之后 : capacity=" << v.capacity() << '\n';
    std::cout << "  push_back 前 data() == old_p ? " << (v.data() == old_p) << '\n';

    v.push_back(4);                       // 容量够，不会重新分配
    std::cout << "push_back(4) 之后: capacity=" << v.capacity() << '\n';
    std::cout << "  data() == old_p ? " << (v.data() == old_p)
              << "   （容量没变 → 没有重新分配 → 旧指针/引用仍然有效）\n";

    v.reserve(64);                        // 强制重新分配
    std::cout << "reserve(64) 之后 : capacity=" << v.capacity() << '\n';
    std::cout << "  data() == old_p ? " << (v.data() == old_p)
              << "   （内存换了 → old_p 与所有旧引用全部失效）\n";
    std::cout << "  注意：此刻用 *old_p 读值就是未定义行为，所以这里只比地址、不解引用。\n";
}
```

<!-- result:ch10_realloc_address -->
```text
reserve(4) 之后 : capacity=4
  push_back 前 data() == old_p ? 1
push_back(4) 之后: capacity=4
  data() == old_p ? 1   （容量没变 → 没有重新分配 → 旧指针/引用仍然有效）
reserve(64) 之后 : capacity=64
  data() == old_p ? 0   （内存换了 → old_p 与所有旧引用全部失效）
  注意：此刻用 *old_p 读值就是未定义行为，所以这里只比地址、不解引用。
```

**执行轨迹**：

```text
v.reserve(4)   → 申请能装 4 个 int 的内存，假设地址是 0x1000；old_p = 0x1000
v.push_back(4) → size 3→4 ≤ capacity 4 → 直接在 0x1000 上写，不搬家
                 data() 还是 0x1000 == old_p              → 打印 "?" 为 1
v.reserve(64)  → 申请能装 64 个 int 的新内存，假设是 0x2000
                 把 1 2 3 4 搬到 0x2000，再释放 0x1000
                 data() 现在是 0x2000 != old_p            → 打印 "?" 为 0
                 ↑ 从这一行起，0x1000 上的任何指针/引用都指向已释放的内存
```

> ⚠️ **坑（本章最危险的一处）**：**用失效的迭代器/引用/指针不是"读到旧值"，是未定义行为。**
>
> **为什么它比"报错"更危险**：旧的 `vector<int>` 示例里我做过一次对比实验——
> 扩容后去读旧地址上的值，本机那次**读出来的还是原来的 `1`**，
> 因为那块内存刚被释放、还没被别人覆盖。**程序看上去完全正常。**
> 但这是 UB，换一个优化档、换一次内存布局、多跑一个线程，结果就会变。
>
> **"这次没崩"不能当成"这里没问题"的证据。** 这类错误的归属是**未定义行为**，
> 不是"逻辑错误"也不是"性能问题"。

### 7.2 完整失效规则表

这张表按**容器**分。**列出的都是标准规定**（不是本机实测，因为"保证"本身就是条款层面的东西）：

| 容器 | 什么操作 | 失效范围 |
|---|---|---|
| **`vector`** | 任何**触发重新分配**的操作（`push_back` 超容量、`resize` 变大超容量、`reserve` 变大、`insert` 超容量） | **全部**迭代器、指针、引用失效 |
| | `push_back` / `emplace_back`（**未**触发重新分配） | 只有 `end()` 失效，其余仍有效 |
| | `insert` / `emplace`（未触发重新分配） | **插入点之后**的全部失效（前面的还有效） |
| | `erase`（删中间/开头） | **删除点之后**的全部失效 |
| | `pop_back` | 只有被删元素和 `end()` 失效 |
| | `clear` / `resize` 变小 | 被删的那些失效；**若没重新分配，其它仍有效** |
| | `swap` | 迭代器**跟着元素走**（仍指向同一元素，但属于另一个容器了） |
| **`deque`** | 在**两端**插入 | **所有迭代器失效**；但**引用和指针仍有效** |
| | 在**中间**插入/删除 | 全部迭代器、引用、指针失效 |
| | `push_back`（未重分配时） | 所有迭代器失效（`deque` 的迭代器比 `vector` 脆弱得多） |
| **`list`** | **插入** | **不使任何迭代器失效** |
| | **删除** | **只有被删元素的迭代器失效** |
| **`map` / `set`**（有序） | **插入** | **不使任何迭代器失效** |
| | **删除** | 只有被删元素的迭代器失效 |
| **`unordered_map` / `unordered_set`** | **插入触发重哈希** | **所有迭代器失效**；**但引用和指针仍有效** |
| | 插入**未**触发重哈希 | 不失效 |
| | **删除** | 只有被删元素的迭代器失效 |

**本机实测的其中两行**（`vector` 的 `end()` 行为，以及 `map` 插入后旧迭代器仍可用）：

<!-- example:ch10_erase_iterator -->
```cpp
#include <iostream>
#include <map>
#include <string>
#include <vector>

int main() {
    std::vector<int> v{10, 20, 30, 40, 50};
    v.reserve(20);                        // 保证下面只发生元素移动，不发生扩容

    const int* p2 = &v[2];                // 指向 30
    auto it3 = v.begin() + 3;             // 指向 40
    std::cout << "erase 前: *p2=" << *p2 << " *it3=" << *it3
              << " &v[2]==p2? " << (&v[2] == p2) << '\n';

    v.erase(v.begin());                   // 删除第一个元素
    // erase 会移动后面的元素：it3 现在指向的元素已经变成了别的值，
    // 但按标准，erase 点之后的迭代器仍然**有效**（不是 UB）
    std::cout << "erase(begin()) 后: *it3=" << *it3
              << " 也就是说 it3 现在指向的值已经不是 40 了\n";
    std::cout << "  *p2=" << *p2 << "  &v[2]==p2? " << (&v[2] == p2)
              << "（指针本身仍指向原地址）\n";

    v.insert(v.begin(), 5);
    std::cout << "insert(begin(),5) 后: 内容:";
    for (int x : v) {
        std::cout << ' ' << x;
    }
    std::cout << '\n';

    // ---------- map：插入不影响已有迭代器
    std::map<std::string, int> m{{"a", 1}, {"c", 3}};
    auto mit = m.find("c");
    std::cout << "map 插入前 it->second=" << mit->second << '\n';
    m["b"] = 2;
    m["d"] = 4;
    std::cout << "插入 b、d 之后 it->first=" << mit->first
              << " it->second=" << mit->second
              << "（map 插入不使任何迭代器失效）\n";

    // 删除只使被删元素的迭代器失效
    auto cit = m.find("b");
    auto other = m.find("d");
    m.erase(cit);
    std::cout << "erase(b) 之后 other->first=" << other->first
              << "->" << other->second << " size=" << m.size() << '\n';
}
```

<!-- result:ch10_erase_iterator -->
```text
erase 前: *p2=30 *it3=40 &v[2]==p2? 1
erase(begin()) 后: *it3=50 也就是说 it3 现在指向的值已经不是 40 了
  *p2=40  &v[2]==p2? 1（指针本身仍指向原地址）
insert(begin(),5) 后: 内容: 5 20 30 40 50
map 插入前 it->second=3
插入 b、d 之后 it->first=c it->second=3（map 插入不使任何迭代器失效）
erase(b) 之后 other->first=d->4 size=3
```

**这张输出里有两个容易看漏的点：**

1. **`*it3` 从 `40` 变成 `50`。** `it3` 本身**仍然有效**（标准保证 `erase` 点之后的迭代器还合法），
   但它指向的**位置**现在装的是别人了。**"迭代器有效"不等于"它还指着原来那个元素"**——这两件事必须分开想。
2. **`*p2` 从 `30` 变成 `40`，而 `&v[2] == p2` 仍然是 `1`。** 指针还指着 `v` 的第 3 个槽位，
   只是那个槽位里的值被前移覆盖了。**这就是"元素移动"而不是"内存搬家"的样子**——和 7.1 那节的失效是两回事。

### 7.3 三条实用规矩

| 规矩 | 为什么 |
|---|---|
| **不在遍历中修改容器的大小** | `push_back` / `erase` 都可能让当前迭代器失效。要在遍历中删元素，用 `it = v.erase(it)` 的返回值（`erase` 返回**下一个**有效迭代器） |
| **手里存迭代器/指针/引用之前，先想"这个容器还会变吗"** | 会变就**存下标或键**，不要存迭代器 |
| **要一批元素时先 `reserve`** | 一次分配好，整段循环都不会失效。这既避免 UB，也避免重复搬运 |

**遍历中删除的正确写法**（片段，不单独编译）：

```cpp
for (auto it = v.begin(); it != v.end(); ) {
    if (*it % 2 == 0) {
        it = v.erase(it);        // ✅ erase 返回下一个有效位置
    } else {
        ++it;                    // ✅ 只有没删的时候才自己前进
    }
}
```

```cpp
for (auto it = v.begin(); it != v.end(); ++it) {
    if (*it % 2 == 0) {
        v.erase(it);             // ❌ it 立刻失效，下一轮 ++it 就是 UB
    }
}
```

> ⚠️ **坑（`vector` 里的经典死法）**：
> ```cpp
> int& r = v[0];
> for (int i = 0; i < 100; ++i) {
>     v.push_back(i);          // 某一轮扩容，v[0] 的内存被释放
>     std::cout << r;          // UB：r 早就悬垂了
> }
> ```
> **程序实际怎么解释它**：`r` 是一个**引用**，它在绑定时就记下了地址。
> `push_back` 触发扩容后那个地址已被释放，之后读 `r` 读到的是"已释放内存的内容"。
> **它通常不会崩，只会给出一个看似合理的错值**——这是最难查的一类 bug。
>
> **修法**：不要在会变大的容器上长期持有引用；或者先 `reserve` 到足够大再循环。

## 8. 复杂度直觉与选型：什么时候该用哪个

### 8.1 先说这一节不做什么

**这一节不列 O 记号表让你背。** O 记号是"n 很大时谁长得快"的结论，
而实际选型要回答的是另一个问题：

> **以我的数据量和访问模式，哪一次操作会被执行最多次？**

因为总时间 ≈ Σ(每种操作的次数 × 每次的代价)，而**次数最多的那种操作才是瓶颈**。
所以这一节给的是**判据**：先问你的访问模式，再推容器。

### 8.2 先看一个"复杂度差 20 倍但感觉不出"的例子

<!-- example:ch10_complexity -->
```cpp
#include <algorithm>
#include <iostream>
#include <set>
#include <vector>

int main() {
    std::vector<int> v;
    for (int i = 0; i < 64; ++i) {
        v.push_back(i * 2);
    }
    std::set<int> s(v.begin(), v.end());

    int hits = 0;
    for (int x : v) {
        if (std::find(v.begin(), v.end(), x) != v.end()) {
            ++hits;
        }
    }
    std::cout << "vector + find     : " << hits << " 次命中（每次都是线性扫描）\n";

    hits = 0;
    for (int x : v) {
        if (s.find(x) != s.end()) {
            ++hits;
        }
    }
    std::cout << "set + find        : " << hits << " 次命中（每次走红黑树）\n";

    std::cout << "对有序 vector 二分 : " << std::binary_search(v.begin(), v.end(), 62) << '\n';
    std::cout << "数据量 64 时两者都能用；数据量上百万时差别才明显。\n";
}
```

<!-- result:ch10_complexity -->
```text
vector + find     : 64 次命中（每次都是线性扫描）
set + find        : 64 次命中（每次走红黑树）
对有序 vector 二分 : 1
数据量 64 时两者都能用；数据量上百万时差别才明显。
```

**两行都打印 64**——它们**结果一样**，复杂度却差一个数量级：

| 做法 | 每次查找代价 | n = 64 时平均比较次数 | n = 1 000 000 时 |
|---|---|---|---|
| `vector` + `std::find` | O(n) 线性扫描 | ~32 次 | ~500 000 次 |
| `set::find`（红黑树） | O(log n) | ~6 次 | ~20 次 |
| `vector` + `binary_search`（有序） | O(log n) | ~6 次 | ~20 次 |

**记住那个真实的结论：数据量小的时候，复杂度选型没有意义。**
n = 64 时两者都是微秒级，此时该优先选**读起来清楚**的那个。
**复杂度是"n 很大时才显形"的判据，不是小数据上的优化依据。**

### 8.3 选型判据：按"你最主要做什么操作"决定

**第一步：问自己三个问题。**

```text
1. 我是按「位置/顺序」访问，还是按「键」访问？
      按位置 → 顺序容器（第 2、3 节）
      按键   → 关联容器（第 4 节）

2. 我最频繁的操作是「查」还是「改」？改的话改哪一头？
      尾部加/删为主         → vector
      两头都要加/删         → deque
      中间随机位置频繁插/删 → list（且必须已有位置迭代器）
      高频按键查           → unordered_map / unordered_set
      需要按键有序遍历/范围查询 → map / set

3. 我有多少数据、主要操作会执行多少次？
      次数最多那种操作决定选型；n 小于几百时优先选简单的
```

**第二步：照表查。**

| 你的主要操作 | 首选 | 次选 | 不要选 | 为什么 |
|---|---|---|---|---|
| 按下标随机读写 | `vector` | `deque` | `list` | `list` 没有随机访问 |
| 尾部进出（栈式） | `vector` | `deque` | `list` | `vector` 均摊 O(1) 且内存连续 |
| 两头进出（队列式） | `deque` | — | `vector` | `vector` 头插是 O(n) |
| 中间频繁插删（已有位置） | `list` | — | `vector` | `vector` 中间插删是 O(n) |
| 排序 + 二分查找 | `vector` | `deque` | `list`/`unordered_map` | `std::sort` 要随机访问；无序容器不能有序遍历 |
| 高频按键查（只要存在性/值） | `unordered_map` / `unordered_set` | `map` / `set` | `vector` + 线性查找 | 平均 O(1) vs O(n) |
| 按键有序遍历 / 范围查询 | `map` / `set` | 有序 `vector` + `lower_bound` | `unordered_*` | 无序容器给不出顺序 |
| 键是自定义类型 | `map` / `set` | 给自定义类型写 `std::hash` 后用 `unordered_*` | — | `map` 只要一个 `operator<` |
| 个数编译期固定 | `array` | `vector` | — | `array` 无堆分配 |
| 要频繁按"第 k 小"取值 | `map` / `set` | 有序 `vector` | `unordered_*` | 只有树结构能 O(log n) 找序位 |

**第三步：给一张"最常被忽略的次选"表。**

有些场景里**有序 `vector` 比 `map` 更好**，这是最容易被漏掉的一条：

| 场景 | 用 `map` | 用「有序 `vector` + `lower_bound`」 |
|---|---|---|
| 建好之后**只读** | 每元素一个树结点 | 一段连续内存，**遍历和缓存都更快** |
| 构建阶段 | 每次插入 O(log n) | 先塞进 `vector`，最后 `sort` 一次（**通常更快**） |
| 插入/删除 | O(log n) | **O(n)**（要搬元素） |
| 内存 | 每结点带指针和颜色 | **最省** |

> **判据**：**"建一次、查很多次"的数据，有序 `vector` 往往比 `map` 更快且更省内存**；
> 只有当"建好之后还要频繁插入删除"时，`map` 的 O(log n) 才真正划算。
> **这一条是本章最实用的选型知识之一**，而它在"背复杂度表"的学法里看不到。

### 8.4 被复杂度表掩盖的三件事

| 被掩盖的事 | 实际影响 |
|---|---|
| **常数因子** | O(log n) 的树查找有指针追逐，O(n) 的 `vector` 线性扫描是顺序内存。n 不大时 `vector` 常常**更快** |
| **缓存友好性** | 连续内存（`vector`/`array`）远好于结点式（`list`/`map`）。这是 8.3 那张"次选"表的根据 |
| **均摊 vs 最坏** | `push_back` 是**均摊** O(1)，单次可能 O(n)。对延迟敏感的场景要 `reserve` 把最坏情况消掉 |

> ⚠️ **坑**：把复杂度当成"性能结论"，于是"为了 O(1) 查表把小数据也用 `unordered_map`"。
> **程序实际怎么解释它**：`unordered_map` 每次插入都可能重哈希、每个元素都要算哈希、
> 内存分布随机。**n = 10 的时候它通常比 10 个元素的 `vector` 线性查找慢得多。**
> **这条结论本轮没有做基准测试**（见章末诚实标注），它是从"内存布局 + 常数开销"推出来的，
> 不是本机计时得出的数字。要自己确认就写个循环计时。

## 9. 本章自测

**1.** `std::vector<int> v{1, 2}` 和 `std::vector<int> v(1, 2)` 各得到什么？为什么会这样？

<details><summary>答案</summary>

- `v{1, 2}` → **2 个元素**：`1` 和 `2`
- `v(1, 2)` → **1 个元素**：值是 `2`

**为什么**：`vector` 有一个收 `std::initializer_list<int>` 的构造函数。
只要花括号里的每一项都能转成 `T`，**列表初始化的优先级高于其它所有构造函数**，
所以 `{1, 2}` 走的是"用这两个值初始化列表"，`(1, 2)` 走的是"个数 = 1、初值 = 2"。

**本机实测**（`ch10_vec_brace_vs_paren`）：`v(1,2)` 打出 `size=1 内容: 2`，`v{1,2}` 打出 `size=2 内容: 1 2`。

**错误归属**：**语义类**。两者都编得过、都不报警告，做的事不同。
</details>

**2.** 下面这段代码有什么问题？它一定会崩吗？

```cpp
std::vector<int> v{1, 2, 3};
int& r = v[0];
for (int i = 0; i < 100; ++i) {
    v.push_back(i);
    std::cout << r << ' ';
}
```

<details><summary>答案</summary>

**问题是 `r` 会悬垂**：`push_back` 迟早触发扩容，扩容 = 申请新内存 + 搬元素 + **释放旧内存**。
`r` 在绑定时记下了旧内存的地址，那块内存被释放后，读 `r` 就是**未定义行为**。

**不一定崩。** 本机做过的对照实验显示：扩容后读旧地址，那次**读出来的还是原来的值**，
因为内存刚释放、还没被别人覆盖。**程序看上去完全正常。**

**这正是 UB 比报错危险的地方**：错误的归属是**未定义行为**，
不是"偶尔读到垃圾值"这么温和——**程序已经不合规**，优化器有权做任何假设。
换个优化档、换个内存布局、多一个线程，结果就可能完全不同。

**修法**：先 `v.reserve(200)`（一次分配，整个循环都不再扩容），或者不长期持有引用、每轮用 `v[0]`。
</details>

**3.** `m[k]` 和 `m.at(k)` 在键不存在时的区别是什么？什么时候必须用 `at`？

<details><summary>答案</summary>

- **`m[k]`：键不存在时插入** `{k, V{}}`（值初始化），并返回新元素的引用。
- **`m.at(k)`：键不存在时抛 `std::out_of_range`**，不修改容器。

**本机实测**（`ch10_four_assoc` / `ch10_map_at`）：
`map 查询前 size=3  counts[kiwi]=0  查询后 size=4`；
`m.at("nope")` 抛出的 `what()` 是 `invalid map<K, T> key`，且 `size` 不变。

**什么时候必须用 `at`**：**只想读、不允许偷偷改容器的时候。**
典型错误是写 `if (m[k] == 0)` 当"检查键存在"用——**这一行会无条件插入**。
后面如果再依赖 `size()` 或正在遍历，就会出问题。

**判据**：读用 `at` / `find` / `count`；写才有理由用 `[]`。
错误归属：**语义类**（不是类型错，也不是语法错）。
</details>

**4.** `std::unordered_map` 的遍历顺序能不能依赖？`std::map` 呢？

<details><summary>答案</summary>

- **`std::map`：能依赖。** 它按键的严格弱序排，遍历就是**有序序列**。任何实现都一样。
- **`std::unordered_map`：不能依赖。** 顺序由哈希函数和桶布局决定，**标准不作规定**。

**本机实测**：同一批 4 个键，`map` 打出 `alpha=1 bravo=3 charlie=2 delta=0`（排序结果，可预测）；
`unordered_map` 打出 `charlie=2 delta=0 bravo=3 alpha=1`（**本机、本次**的结果）。

**必须自己测一遍的原因**：`unordered_map` 的桶数和哈希函数是实现定义的，
**换个标准库、换个插入历史、甚至同一次运行的不同时刻都可能不同**。
所以"取第一个元素当代表"这类写法是 bug，不是风格问题。

**错误归属**：**实现定义 + 未指定行为**。编译不报错，测试也常常过，上线才炸。
</details>

**5.** `std::vector` 的 `size` 和 `capacity` 有什么区别？`clear()` 之后 `capacity` 会变吗？

<details><summary>答案</summary>

- **`size()`**：现在装了**几个元素**。
- **`capacity()`**：现在这块内存**最多能装几个**，不需要重新分配。

**本机实测**（`ch10_vector_ops`）：`clear() 后 size=0 capacity=13` —— **`clear` 只销毁元素，不还内存**。
要让容量真正降下来得显式调 `shrink_to_fit()`（实测之后 `capacity=0`）。

**为什么会这样**：`vector` 的设计假设是"你清空之后大概还会再用"，还内存反而会破坏"均摊 O(1)"的保证。
所以**释放内存必须显式要求**，而且 `shrink_to_fit` 只是"请求"，标准不保证一定缩。

**顺带一个对照**：本机每次扩容的倍率约 1.5（`1→2→3→4→6→9→13`）。
**这是 MSVC 的实现策略，标准不规定**；GCC 的 `libstdc++` 通常用 2 倍。
</details>

**6.** 为什么 `std::list` 中间插入是 O(1)，但实践中经常比 `vector` 慢？

<details><summary>答案</summary>

两个原因，第二个更致命：

1. **那个 O(1) 有前提**：必须**已经持有插入位置的迭代器**。
   如果还要"先找到第 k 个"，`list` 得从头走 k 步（O(k)），而 `vector` 的 `v.begin() + k` 是 O(1)。
2. **缓存**：`list` 每个元素是一个**独立分配的结点**（带两个指针）。
   遍历时每次访问都要跳到一个新地址，缓存命中率极低；
   `vector` 是一段连续内存，顺序遍历对 CPU 预取极其友好。

**还有一条硬限制**：`list` **不支持随机访问**，所以**不能用 `std::sort`**（它要求随机访问迭代器），
只能用成员函数 `l.sort()`。

**诚实说明**：这条"实践中 `vector` 更快"的结论来自复杂度与内存布局分析，
**本轮没有做基准测试**。要自己确认就写个插入 + 遍历的计时程序对比两者。
</details>

**7.** `std::optional<T>`、`std::variant<A,B>`、`std::any` 各自解决什么问题？为什么 `any` 排最后？

<details><summary>答案</summary>

| | 表达的意思 | 状态数 |
|---|---|---|
| `optional<T>` | 「有一个 `T` **或者** 什么都没有」 | 2 |
| `variant<A,B>` | 「**列举出来的那几种**之一」 | 候选集大小 |
| `any` | 「随便什么类型的值」 | 任意（运行期才知道） |

**`any` 排最后的原因**：它**把类型检查从编译期推到运行期**。
`std::any_cast<T>` 取错类型时编译期不拦你，只在运行期抛 `std::bad_any_cast`；
而 `variant` 的候选集是**类型的一部分**，`std::visit` 能在**编译期**检查你有没有漏分支。
这和 C++ 的核心价值（静态类型、错误尽量早发现）相反，所以只在"类型信息编译期真的不可能知道"时才用。

**本机实测**（`ch10_optional_variant`）：`parse_int("")` 返回空（`has_value()==0`）；
`variant` 换类型后 `index()` 从 0 变 1；`any` 从 `int` 换成 `std::string` 后 `typeid` 判断跟着变。

**还有一条要注意**：`optional<bool>` 是**三态**（`true`/`false`/空），
`if (opt)` 判的是"有没有"而不是"值是不是真"。
</details>

**8.** 下面两个循环哪一个正确？错的那个错在哪一类？

```cpp
// A
for (auto it = v.begin(); it != v.end(); ) {
    if (*it % 2 == 0) { it = v.erase(it); } else { ++it; }
}

// B
for (auto it = v.begin(); it != v.end(); ++it) {
    if (*it % 2 == 0) { v.erase(it); }
}
```

<details><summary>答案</summary>

**A 正确，B 是未定义行为。**

`vector::erase(it)` 会让 **`it` 及之后的所有迭代器失效**。B 里 `erase(it)` 之后，
循环的 `++it` 作用在一个**已经失效的迭代器**上——**未定义行为**。

A 的做法是：**用 `erase` 的返回值接管**。`erase` 返回**被删元素之后的下一个有效迭代器**，
所以删了就不该再 `++`，没删才 `++`。这也是 A 的 `for` 头里**故意不写 `++it`** 的原因。

**错误归属**：**未定义行为**（迭代器失效这一类）。

**对照本机实测**：`ch10_erase_iterator` 里 `v.erase(v.begin())` 之后
`*it3` 从 `40` 变成了 `50`——注意这次它**仍然有效**（标准保证 `erase` 点之后的迭代器合法），
但**指向的位置内容变了**。"迭代器有效"和"它还指着原来那个元素"是两件事。
</details>

**9.** 你要处理 100 万个整数，既要频繁按键查值，又需要按键有序输出。选什么？

<details><summary>答案</summary>

**先分清主次**：判据是"**哪种操作执行次数最多**"。

| 情形 | 选择 |
|---|---|
| **查**是主操作，有序输出只是偶尔一次 | **`unordered_map`**；要输出时把键拷进 `vector` 排一次序 |
| **有序遍历/范围查询**是主操作 | **`map`** |
| 数据**建好之后基本只读** | **有序 `vector` + `binary_search` / `lower_bound`**：一段连续内存，最省也最快 |

**为什么第三种常常最好**：这就是第 8.3 节那张"次选表"的意思——
"建一次、查很多次"的数据，`sort` 一次的有序 `vector` 在**遍历速度**和**内存**上通常胜过 `map`。
`map` 的 O(log n) 插入只有在"建好之后还要频繁插删"时才真正划算。

**必须补一句**：无论选哪个，**先 `reserve`**（能用的话）。
一次分配到位，既避免重复搬运，也避免迭代器失效。

**诚实说明**："有序 `vector` 常常更好"这个结论来自内存布局推理，
**本轮没有做基准测试**。用你自己的数据计时才是判据。
</details>

**10.** 下面这段代码编译能过吗？运行结果确定吗？

```cpp
std::vector<int> v{1, 2, 3};
v.reserve(64);
const int* p = v.data();     // 假设这时 data() 是 0x1000
v.push_back(4);
std::cout << *p << '\n';
```

<details><summary>答案</summary>

**能编过，而且这一份的结果是确定的**：因为 `reserve(64)` 已经把容量备到 64，
`push_back(4)` **不会触发重新分配**，`data()` 不变，`p` **仍然有效**，打印 `4`。

**本机实测**（`ch10_realloc_address`）：容量够的时候 `data() == old_p` 打印 `1`；
一旦 `reserve(64)`（从容量 4 变 64）重新分配，`data() == old_p` 打印 `0`。

**所以这题的真正考点是**：**同一个 `push_back`，在容量够和容量不够时行为不同。**
- 容量够 → 指针/引用/迭代器**仍然有效**
- 容量不够 → **全部失效**，此时 `*p` 是未定义行为

**结论**：判断"这里安不安全"不能看**代码长什么样**，要看**运行到这一行时容量够不够**。
这也是为什么"先 `reserve`"是本章最实用的一条操作习惯——
它把"会不会失效"这个运行时问题变成了编译期/代码结构问题。
</details>
