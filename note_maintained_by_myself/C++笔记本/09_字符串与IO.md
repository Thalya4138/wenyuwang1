## 0. 先记住的七件事

1. **C 风格字符串不是一种类型，而是一个约定**：一串 `char`，以一个值为 0 的字节结尾。所以你看到的 `const char*` 只是"首地址"，长度要现场数。
2. **`std::string` 拥有自己的字符缓冲区。** 它自己申请、自己扩容、自己释放——你在第 07 章第 3 节「析构函数与 RAII」学的 RAII，`std::string` 就是标准库最常用的那个例子。
3. **`std::string_view` 不拥有数据。** 它只是"首地址 + 长度"两个字段。**被它指着的那个对象必须先活过它**——这是本章最大的一类未定义行为来源。
4. **流把"内存里的字节"和"外部设备"连起来**，而它比文件描述符多了一样东西：**状态位**。读失败不会抛异常，而是把流置成失败态，**并且让后面所有读取都静默失效**。
5. **读失败不抛异常，它只是把流置成失败态**——而且**失败态是"粘"的**：一旦置起，后面所有读取都静默失效。至于目标变量：数值提取失败会把它写成 `0`，字符串提取失败则不碰它。所以"读到 0"和"读失败"是两件不同的事，只有看流状态才分得清。
6. **`std::format` 是 C++20 起的**，本讲义基线是 C++17：可以知道它、认识它，但**正文里的代码不依赖它**。本机实测在 `/std:c++17` 下 `#include <format>` 连 `std::format` 都找不到（第 6 节有真实诊断）。
7. **本章最容易踩的是 `>>` 与 `getline` 混用**：`cin >> age` 之后紧跟的 `getline` **几乎总是拿到空串**。第 8 节有可复现的真实输出。

> 如果只记一条，记第 7 条。它会让"我明明输入了名字，程序却说名字是空的"这种怪事当场现形。

## 1. 文字在内存里：C 风格字符串

### 1.1 最小例子：三种"看起来都是 abc"的东西

<!-- example:ch09_cstr_repr -->
```cpp
#include <cstring>
#include <iostream>

int main() {
    const char* p = "abc";            // 指针：只记得首地址
    char arr[] = "abc";               // 数组：4 个 char，末尾多一个 '\0'
    char chars[3] = {'a', 'b', 'c'};  // 没有末尾 '\0'，不是字符串

    std::cout << sizeof(p) << ' ' << sizeof(arr) << ' ' << sizeof(chars) << '\n';
    std::cout << std::strlen(arr) << ' ' << std::strlen(p) << '\n';
    std::cout << (arr[3] == '\0') << '\n';
    std::cout << (p == arr) << '\n';
}
```

<!-- result:ch09_cstr_repr -->
```text
8 4 3
3 3
1
0
```

读数（本机 64 位 MSVC）：

| 表达式 | 结果 | 说明 |
|---|---|---|
| `sizeof(p)` | 8 | `p` 是**指针**，大小是地址的大小，和它指向几个字符无关 |
| `sizeof(arr)` | 4 | `arr` 是**数组**，`"abc"` 初始化它时会连结尾的 `'\0'` 一起放进去，所以是 3+1 |
| `sizeof(chars)` | 3 | 逐个字符初始化的数组，**没有** `'\0'`，所以它**不是字符串** |
| `strlen(arr)` / `strlen(p)` | 3 / 3 | 都是从首地址开始**数到第一个 0 字节** |
| `arr[3] == '\0'` | 1（真） | 结尾那个 0 就在数组里 |
| `p == arr` | 0（假） | 比的是**地址**，两者当然不同 |

**这里最重要的一件事是第 3 行**：`chars` 装得下 3 个字符，却不是一个字符串。
把它交给任何 `str*` 函数，那些函数会**继续往数组后面数**，直到撞见某个 0 字节——**越界读，未定义行为**。
这类错误的归属是**边界类**，而且编译器通常一声不吭。

### 1.2 为什么要有这个约定

因为它把"长度"这件事从数据结构里挪到了数据本身。

```text
C 风格字符串在内存里就是这样一串字节：

p ──▶  'a'  'b'  'c'  '\0'  ...
        0x61 0x62 0x63 0x00

"有几个字符" 没有存在任何地方，只能从头数到尾。
```

**代价**：`strlen` 是 O(n)，取长度的操作本身要走一遍内存。
**代价二**：你能拿到长度，但你不知道**缓冲区有多大**——这是溢出问题的根源（第 06 章第 7 节「指针运算、遍历与 `begin`/`end`」讲了指针越界为什么危险）。

**好处**：它和 C 的接口完全兼容，也和操作系统的系统调用完全兼容。
`main(int argc, char** argv)`、`std::fopen`、Windows 的 `CreateFileW` 全都吃这种形式。

### 1.3 常用函数与 `<cstring>`

<!-- example:ch09_cstr_funcs -->
```cpp
#include <cstring>
#include <iostream>

int main() {
    char buf[16] = "abc";
    std::strcat(buf, "def");
    std::cout << buf << ' ' << std::strlen(buf) << '\n';

    char copy[16];
    std::strcpy(copy, buf);
    std::cout << copy << ' ' << std::strcmp(copy, buf) << '\n';
    std::cout << (std::strcmp("abc", "abd") < 0) << '\n';
}
```

<!-- result:ch09_cstr_funcs -->
```text
abcdef 6
abcdef 0
1
```

| 函数 | 干什么 | 返回值 |
|---|---|---|
| `std::strlen(s)` | 数到第一个 `'\0'` | 字符个数（不含 `'\0'`） |
| `std::strcpy(dst, src)` | 把 `src` 连 `'\0'` 一起复制到 `dst` | `dst` |
| `std::strcat(dst, src)` | 把 `src` 追加到 `dst` 的 `'\0'` 处 | `dst` |
| `std::strcmp(a, b)` | 按字典序比内容 | `<0` / `0` / `>0` |

**`strcmp` 返回的不是"差值"**，只保证符号有意义——所以正确用法永远是 `strcmp(a,b) == 0` 或 `< 0`，**不要**写 `== -1`。

> ⚠️ **坑（本机实测有一条真实警告）**：`strcpy` / `strcat` 不检查目标缓冲区大小。
> MSVC 在 `/W4` 下会报：
>
> ```text
> main.cpp(6): warning C4996: 'strcat': This function or variable may be unsafe. Consider using strcat_s instead. To disable deprecation, use _CRT_SECURE_NO_WARNINGS. See online help for details.
> main.cpp(10): warning C4996: 'strcpy': This function or variable may be unsafe. Consider using strcpy_s instead. To disable deprecation, use _CRT_SECURE_NO_WARNINGS. See online help for details.
> ```
>
> **它的建议是"改用 `_s` 版本"，但更好的答案是"改用 `std::string`"**——`_s` 系列是 MSVC 的扩展，
> 换到 GCC 上就没有了。这类错误的归属是**边界类**：写越界不报错，只在运行时咬人。

### 1.4 最经典的一个坑：用 `==` 比字符串

<!-- example:ch09_cstr_vs_string -->
```cpp
#include <cstring>
#include <iostream>
#include <string>

int main() {
    const char* p = "abc";
    const char* q = "abc";
    std::string a = "abc";
    std::string b = "abc";

    std::cout << (p == q) << '\n';                  // 比的是地址：结果由实现决定
    std::cout << (std::strcmp(p, q) == 0) << '\n';  // 比的是内容
    std::cout << (a == b) << '\n';                  // 比的是内容
}
```

<!-- result:ch09_cstr_vs_string -->
```text
0
1
1
```

**三行的含义完全不同**：

| 写法 | 比什么 | 结果确定吗 |
|---|---|---|
| `p == q` | 两个**指针**是否指向同一块内存 | ❌ **实现决定**。本机是 0（两个字面量各有存储），别的编译器可能合并成同一块而给出 1 |
| `strcmp(p, q) == 0` | 两个**字符序列**内容 | ✅ 确定 |
| `a == b` | `std::string` 的**内容**（`operator==` 被重载了） | ✅ 确定 |

> ⚠️ **坑**：以为 `p == q` 在比内容。它比的是地址。这类错误的归属是**类型类 + 语义误解**：
> 语法完全合法、编译零警告、结果看起来还挺"对"（因为它偶尔真的是 1）。
>
> **这一行也说明了为什么 `std::string` 值得存在**：它把"内容比较"变成了默认行为。
> 运算符重载的机制见第 07 章第 7 节「运算符重载：够用为止」。

### 1.5 三者关系：一张表定死

这是本章的总纲。后面每一节都在展开这张表的某一行。

| | `const char*`（C 风格） | `std::string` | `std::string_view`（C++17 起） |
|---|---|---|---|
| **拥有数据吗** | ❌ 不拥有，只是个地址 | ✅ **拥有**一块自己的缓冲区 | ❌ 不拥有，只是"地址 + 长度" |
| **能修改字符吗** | ❌ 不能（指向字面量时） | ✅ 能（`[i]`、`replace`、`+=`…） | ❌ 不能（视图是只读的） |
| **长度怎么得到** | `strlen`，**O(n)**，要走内存 | `size()`，**O(1)**，存在对象里 | `size()`，**O(1)**，存在对象里 |
| **保证以 `'\0'` 结尾吗** | ✅ 是（这就是它的定义） | ✅ `c_str()` 保证 | ❌ **不保证** |
| **谁来保证它活着** | 你自己（或那块字面量的静态存储期） | 对象自己（RAII） | **你**——这是它最大的风险 |
| **本例 `sizeof`** | 8（就是个指针） | 32 | 16 |
| **典型用途** | 调用 C 接口、`main` 参数、字符串字面量 | **默认选择**：需要存、需要改、需要传出去 | 只读的**函数参数**，避免拷贝 |

本机实测的 `sizeof`（`ch09_sv_basic` 那个示例的第 5 行输出）：

| 表达式 | 本机结果 | 含义 |
|---|---|---|
| `sizeof(std::string)` | 32 | 至少包含"指针 + 长度 + 容量（+ 小字符串缓冲）" |
| `sizeof(std::string_view)` | 16 | 就是"指针 + 长度"，比 `std::string` 小一半 |

> ⚠️ **这两个数字是实现细节，不是标准保证的**。标准只要求 `std::string` 能装下那些成员、
> `string_view` 有 `data()` 和 `size()`。**不要写依赖 32 或 16 的代码**，这里给数字是为了让你看清"谁多拿了什么"。

## 2. `std::string`：拥有自己数据的字符串

### 2.1 六种构造写法

<!-- example:ch09_string_construct -->
```cpp
#include <iostream>
#include <string>

int main() {
    std::string a;
    std::string b = "hello";
    std::string c(3, 'x');
    std::string d = b;
    std::string e = b + ", " + "world";
    std::string f(b, 1, 3);

    std::cout << '[' << a << "] " << a.size() << ' ' << a.empty() << '\n';
    std::cout << b << ' ' << c << ' ' << d << '\n';
    std::cout << e << '\n';
    std::cout << f << '\n';
}
```

<!-- result:ch09_string_construct -->
```text
[] 0 1
hello xxx hello
hello, world
ell
```

| 写法 | 得到什么 | 什么时候用 |
|---|---|---|
| `std::string a;` | **空串**（注意不是"值不确定"——类类型自己保证） | 先声明，之后再赋值 |
| `std::string b = "hello";` | 从字符串字面量构造 | 最常用 |
| `std::string c(3, 'x');` | `"xxx"`（重复 n 次字符） | 造填充串、分隔线 |
| `std::string d = b;` | 拷贝一份，**和 `b` 再无关系** | 要独立副本 |
| `std::string e = b + ", " + "world";` | 拼接结果 | 组词 |
| `std::string f(b, 1, 3);` | 从 `b` 的下标 1 起取 3 个字符 → `"ell"` | 从已有串里挖一段（等价于 `b.substr(1,3)`） |

> ⚠️ **`std::string a;` 和 `int a;` 不是一回事。** 第 02 章第 5.4 节说"局部基本类型不写初始化，值不确定"；
> 但 `std::string` 是**类类型**，它的默认构造函数保证给你一个合法的空串。**"类类型自己保证"这条规律从第 07 章第 2 节起就成立。**

### 2.2 查、取、切：`size` / `[i]` / `at` / `find` / `substr`

<!-- example:ch09_string_find -->
```cpp
#include <iostream>
#include <string>

int main() {
    std::string s = "2026-10-08";
    std::cout << s.size() << ' ' << s.front() << ' ' << s.back() << '\n';
    std::cout << s[2] << ' ' << s.at(2) << '\n';
    std::cout << s.find('-') << ' ' << s.rfind('-') << '\n';
    std::cout << s.substr(0, 4) << '|' << s.substr(5, 2) << '|' << s.substr(8, 2) << '\n';
    std::cout << (s.find('z') == std::string::npos) << '\n';
    std::cout << std::string::npos << '\n';
}
```

<!-- result:ch09_string_find -->
```text
10 2 8
2 2
4 7
2026|10|08
1
18446744073709551615
```

逐行读：

| 调用 | 含义 | 边界行为 |
|---|---|---|
| `size()` / `empty()` | 字符个数 / 是否为空 | O(1) |
| `front()` / `back()` | 第一个 / 最后一个字符 | **对空串调用是 UB** |
| `s[i]` | 下标访问 | **不做检查**，越界是 UB（和数组一样） |
| `s.at(i)` | 同 `s[i]`，但**越界抛 `std::out_of_range`** | 安全，代价是一次判断 |
| `find(x)` | 第一次出现的位置 | 找不到返回 `npos` |
| `rfind(x)` | **最后一次**出现的位置 | 找不到返回 `npos` |
| `substr(pos, n)` | 从 `pos` 起取 `n` 个字符 | `pos > size()` 时抛 `std::out_of_range` |

**`npos` 是什么**：一个"不可能的下标"哨兵值。本机打印出来是 `18446744073709551615`，
也就是 64 位无符号数的最大值（`size_t(-1)`）。

> ⚠️ **坑（类型类）**：`npos` 是无符号的。所以 `int idx = s.find('z');`
> 会把一个 64 位无符号值截断进 `int`，`if (idx == -1)` 这种判断在不同平台上结果不同。
> **正确写法**：用 `std::size_t`（或 `auto`）接住结果，再和 `std::string::npos` 比，
> 判据是"**和类型匹配的哨兵比**"，不是"和 -1 比"。
>
> 顺带解释了为什么本讲义在第 02 章第 10 节说"下标尽量用有符号"：
> 标准库偏偏把 `size()` / `find()` 都做成了无符号，**这是它自己的历史包袱**（C++20 才补了 `std::ssize()`）。

### 2.3 改：`+=` / `[]` / `replace` / `insert` / `erase` / `clear`

<!-- example:ch09_string_modify -->
```cpp
#include <iostream>
#include <string>

int main() {
    std::string s = "hello";
    std::cout << s << ' ' << (s.capacity() >= s.size()) << '\n';

    s += " world";
    s[0] = 'H';
    std::cout << s << ' ' << s.size() << '\n';

    s.replace(6, 5, "there");
    std::cout << s << '\n';

    s.insert(5, ",");
    std::cout << s << '\n';

    s.erase(5, 1);
    s.push_back('!');
    std::cout << s << '\n';

    s.clear();
    std::cout << '[' << s << "] " << s.empty() << ' ' << s.size() << '\n';
}
```

<!-- result:ch09_string_modify -->
```text
hello 1
Hello world 11
Hello there
Hello, there
Hello there!
[] 1 0
```

**执行轨迹**（每一步都改的是同一个对象的那块缓冲区）：

```text
s = "hello"                size=5
s += " world"              → "hello world"   size=11   （可能触发扩容：申请更大的块、搬过去、释放旧的）
s[0] = 'H'                 → "Hello world"   size=11   （原地改一个字符）
s.replace(6, 5, "there")   → "Hello there"   （把下标 6 起 5 个字符换成 "there"）
s.insert(5, ",")           → "Hello, there"  （在下标 5 处插入，后面全部后移）
s.erase(5, 1)              → "Hello there"
s.push_back('!')           → "Hello there!"
s.clear()                  → ""              size=0      （只把长度置 0，缓冲区通常留着）
```

| 操作 | 语义 | 会改变长度吗 |
|---|---|---|
| `s += t` / `s.append(t)` | 尾部追加 | 会 |
| `s[i] = c` | 改一个已存在的字符 | 不会 |
| `s.replace(pos, n, t)` | 把 `[pos, pos+n)` 换成 `t` | 通常会 |
| `s.insert(pos, t)` | 在 `pos` 前插入 | 会 |
| `s.erase(pos, n)` | 删掉 `n` 个 | 会 |
| `s.push_back(c)` | 追加一个字符 | 会 |
| `s.clear()` | 变空串 | 会（size 归零） |

**`size()` 和 `capacity()` 是两件事**：`size` 是"现在有几个字符"，`capacity` 是"不重新申请内存的话最多能装几个"。
本程序第一行打印的是 `capacity() >= size()`（一定是 1），**没有打印具体容量**——
具体数值是实现细节，写进正文基线就变成"依赖实现的输出"了。

> ⚠️ **坑（UB 类）**：`s[i] = c` 里的 `i` **必须**在 `[0, size())` 内。用 `s[size()]` 改值是越界。
> （唯一的例外是 C++11 起 `s[size()]` **读**会得到 `'\0'`，但**写**它是 UB。这种"一次合法一次不合法"的边界最容易记错。）

### 2.4 比：内容比较是默认行为

<!-- example:ch09_string_compare -->
```cpp
#include <iostream>
#include <string>

int main() {
    std::string a = "abc";
    std::string b = "abd";
    std::cout << (a == b) << ' ' << (a < b) << '\n';
    std::cout << (a.compare(b) < 0) << '\n';
    std::cout << a.compare("abc") << '\n';
}
```

<!-- result:ch09_string_compare -->
```text
0 1
1
0
```

`std::string` 重载了 `==` `!=` `<` `<=` `>` `>=`，**全部按字典序比内容**。
`compare` 是这些运算符下面那个函数版本，返回负 / 零 / 正——**同样只保证符号，不要和具体数字比**。

> **这就是第 1.4 节那个 `p == q` 的解药**：把字符串存成 `std::string`，"比较内容"就成了默认语义，
> 你不需要记得每次都写 `strcmp`。

### 2.5 一个真实会让人困惑的点：扩容会让指针失效

第 3 节会专门用它来解释 `string_view` 为什么危险。这里先记住一句话：

> **`std::string` 的任何"可能改变长度或容量"的操作，都可能重新分配缓冲区。**
> 一旦重新分配，之前从 `data()` / `c_str()` 拿到的指针、以及指向它的迭代器，**全部作废**。

这不是 bug，是"自己管理缓冲区"的必然结果——和第 06 章第 10 节「常见指针错误分类」里的"悬垂"是同一个机制。

## 3. `std::string_view`：只看一眼，不拥有（C++17 起）

**它解决什么问题**：函数要接收一个"只读的字符串"，你既想让它能接 `const char*`，又想让它能接 `std::string`，
还不想为 `const char*` 构造一个临时 `std::string`（那是一次内存分配 + 拷贝）。

### 3.1 最小例子：一个参数接住三种实参

<!-- example:ch09_sv_basic -->
```cpp
#include <iostream>
#include <string>
#include <string_view>

std::size_t first_word_len(std::string_view sv) {
    return sv.find(' ');
}

int main() {
    std::string owned = "hello world and more";
    std::string_view sv = owned;

    std::cout << sv << ' ' << sv.size() << '\n';
    std::cout << (sv.data() == owned.data()) << '\n';

    std::string_view word = sv.substr(0, 5);
    std::cout << word << ' ' << (word.data() == sv.data()) << '\n';
    std::cout << first_word_len("abc def") << '\n';
    std::cout << sizeof(std::string) << ' ' << sizeof(std::string_view) << '\n';
}
```

<!-- result:ch09_sv_basic -->
```text
hello world and more 20
1
hello 1
3
32 16
```

| 输出行 | 说明 |
|---|---|
| `hello world and more 20` | `string_view` 能像字符串一样 `<<` |
| `1` | `sv.data() == owned.data()`：**没有拷贝**，视图指着原来的缓冲区 |
| `hello 1` | `substr` **也不拷贝**，只是把首地址 +0、长度改成 5（所以 `word.data()` 还是 `sv.data()`） |
| `3` | 同一个函数既接了 `std::string` 又接了字面量 `"abc def"` |
| `32 16` | 视图比拥有者小一半——它没有缓冲区指针之外的负担 |

**`string_view` 的三个主要操作**：

| 操作 | 说明 |
|---|---|
| `sv.size()` / `sv.empty()` | O(1)，长度就存在视图里 |
| `sv[i]` / `sv.front()` / `sv.back()` | 只读访问 |
| `sv.substr(pos, n)` | **返回新的 `string_view`，不拷贝字符** |
| `sv.find` / `rfind` / `starts_with` / `ends_with` | 与 `std::string` 类似的查询 |
| `sv.remove_prefix(n)` / `remove_suffix(n)` | 原地把视图缩短（不碰数据） |

> ⚠️ **注意 `substr` 的语义差别**：`std::string::substr` **返回一份拷贝**（O(n)），
> `std::string_view::substr` **返回一个视图**（O(1)）。同一个名字，一个拷贝一个不拷贝——
> 这正是"拥有 vs 不拥有"最直观的体现。

### 3.2 第一大风险：悬垂

<!-- example:ch09_sv_dangle -->
```cpp
#include <iostream>
#include <string>
#include <string_view>

// 反面教材：返回指向函数内局部对象的 string_view
std::string_view make_view_bad() {
    std::string local = "temporary-local-buffer";
    return std::string_view(local);
}

int main() {
    std::string_view bad = make_view_bad();
    // 函数已经返回，local 已经销毁；下面这行读的是已释放的存储
    std::cout << bad.size() << '\n';
}
```

<!-- result:ch09_sv_dangle -->
```text
22
```

**这个程序打印 `22`，看起来完全正常——这才是它可怕的地方。**

```text
执行轨迹（按标准应有的语义）：

调用 make_view_bad()
  ├─ 在栈上构造 local（"temporary-local-buffer"，22 个字符）
  ├─ 构造一个 string_view，记下 local 的地址和长度 22
  └─ 函数返回 → local 析构 → 它占的那块存储**已经不再是你的了**
回到 main
  ├─ bad 仍然记着那个地址和 22
  └─ bad.size() 读的是"长度字段"，那个字段在被销毁前就抄好了，所以给出 22
```

**长度字段还能读出"合理"的值，不代表数据还在。** 这块存储随时可能被下一次函数调用、下一次分配覆盖掉。
一旦你真去读 `bad[0]` 或者把 `bad` 打印出来，**程序的行为就没有任何保证了**——这是**未定义行为**，不是"读出乱码"。

**同一份探针里的加料实验**（`tmp/ch09_probe_result.txt` 的 `x_sv_temp_string`）：

```text
64 81920 0
```

它把 `make()` 的返回值（一个临时 `std::string`）绑到 `string_view` 上，然后故意在中间做大量分配。
实测 `v[0] == 'x'` 已经是 **0（假）**——那块内存被别的东西覆盖了。
**这个实验的输出不写进自动基线**，因为它本来就是 UB，具体数字换了编译器和优化级别就会变；
它放这里是为了让你看到"悬垂不是理论问题"。

> ⚠️ **判据**：**`string_view` 的生存期必须严格短于它指向的对象。** 三条实用规则：
>
> 1. **不要从函数返回局部对象的 `string_view`**（上面这个例子）。
> 2. **不要把 `string_view` 存成成员**，除非你能证明被指对象活得更久。
> 3. **不要从临时 `std::string` 构造 `string_view`**：
>    `std::string_view v = std::string("abc");` —— 那条语句一结束，临时对象就没了。
>
> 这类错误的归属是**生存期类（UB）**，而且**编译器几乎从不警告**。

### 3.3 第二风险：它不保证以 `'\0'` 结尾

<!-- example:ch09_sv_span -->
```cpp
#include <iostream>
#include <string>
#include <string_view>

int main() {
    std::string text = "x hello y";
    std::string_view sv(text.data() + 2, 5);   // 只想看 "hello"

    std::cout << sv << ' ' << sv.size() << ' ' << (sv == "hello") << '\n';
    std::cout << (sv.data()[sv.size()] == ' ') << '\n';   // 第 6 个字节还在，但不是结尾标记

    std::string owned(sv);                     // 要交给只认 '\0' 的接口就自己造一个
    std::cout << owned << ' ' << owned.size() << '\n';
}
```

<!-- result:ch09_sv_span -->
```text
hello 5 1
1
hello 5
```

| 输出行 | 说明 |
|---|---|
| `hello 5 1` | 视图的"长度"是 5，`== "hello"` 也是按长度比的，所以为真 |
| `1` | 视图后面那个字节恰好是空格——**但它不是 `'\0'`，`string_view` 根本没打算给你一个结尾标记** |
| `hello 5` | 一旦要交给 C 接口（`fopen`、`printf("%s")`…），先 `std::string owned(sv);` 造一个拥有者 |

> ⚠️ **坑**：`sv.data()` 返回的指针**不是** C 字符串。
> 把它交给 `strlen` / `printf("%s")` / `strcmp`，那些函数会**读到你数据的后面**，直到碰上某个 0 字节。
> 这属于**边界类 + UB**。需要 C 字符串就显式造一个 `std::string`（上例最后两行），代价是一次拷贝，换来的是确定性。

### 3.4 第三风险：拥有者一旦重新分配，视图就悬垂了

<!-- example:ch09_sv_owner -->
```cpp
#include <iostream>
#include <string>
#include <string_view>

int main() {
    std::string s = "abcdefghijklmnop";
    std::string_view v = s;
    const char* before = v.data();

    std::cout << v << ' ' << s.size() << ' ' << s.capacity() << '\n';

    s += "qrstuvwxyz012345";   // 可能重新分配缓冲区
    std::cout << (v.data() == before) << '\n';
    std::cout << s.size() << ' ' << s.capacity() << '\n';
}
```

<!-- result:ch09_sv_owner -->
```text
abcdefghijklmnop 16 31
1
32 47
```

| 输出行 | 本机结果 | 含义 |
|---|---|---|
| `abcdefghijklmnop 16 31` | 原始串长 16，容量 31 | 容量够大，是因为本机的扩容策略留了余量 |
| `1` | `v.data() == before` | **本机这一次没有重新分配**，所以指针没变，视图还是安全的 |
| `32 47` | 追加后长 32、容量 47 | 这次扩容了（47 > 31），**但指针仍然没变**——扩容发生在原地之外，视图指向的旧缓冲区的命运由实现决定 |

**这最后一行输出的意义是负面的**：它说明"视图还指着 `before`"**不能证明它是安全的**。
真正安全与否取决于那次 `+=` 有没有重新分配，而**标准不规定什么时候重新分配**（只规定 `capacity` 与失效规则）。

> ⚠️ **判据**：`std::string` 的**长度改变型操作可能使**指向它的指针、引用、迭代器、视图**失效**。
> 本机这一次"没失效"是运气，不是保证。要安全就只有两条路：
> **要么先保证不扩容（`reserve` 之后不再超），要么在每次改动之后重新构造视图。**

### 3.5 什么时候用哪个

| 场景 | 用哪个 | 为什么 |
|---|---|---|
| 要**存下来**、要**改**、要**传出去** | `std::string` | 只有它拥有数据 |
| 函数参数，只读，可能同时接字面量和 `std::string` | `const std::string&` 或 **`std::string_view`** | 前者通用但可能触发临时对象构造；后者零拷贝但**要求调用方保证生存期** |
| 需要 C 接口 / 需要 `'\0'` 结尾 | `const char*`（`s.c_str()`） | C 接口只认这个 |
| 解析大文本、反复切分，且源串活得足够久 | `std::string_view` | `substr` 不拷贝，切分几乎零成本 |
| 跨函数长期保存 | **不要**用 `string_view` | 生存期无法保证 |

第 13 章第 8.1 节「C++20 里影响最大的几件事」还把 `std::span` 列为 `string_view` 的"通用容器版"（C++20 起）。

## 4. 字符序列与其他类型的转换

### 4.1 字符串 → 数：`std::stoi` 家族

<!-- example:ch09_stoi -->
```cpp
#include <iostream>
#include <string>

int main() {
    std::string s = "  -42abc";
    std::size_t used = 0;
    std::cout << std::stoi(s, &used) << ' ' << used << '\n';
    std::cout << std::stoi("1010", nullptr, 2) << '\n';
    std::cout << std::stoi("ff", nullptr, 16) << '\n';
    std::cout << std::stod("3.5e2") << '\n';
}
```

<!-- result:ch09_stoi -->
```text
-42 5
10
255
350
```

| 输出行 | 说明 |
|---|---|
| `-42 5` | 跳过前导空白，解析出 `-42`，**吃掉了 5 个字符**（`"  -42"`）；后面的 `abc` 不管 |
| `10` | 第三个参数是**进制**，`"1010"` 按二进制读 |
| `255` | `"ff"` 按十六进制读 |
| `350` | `stod` 解析浮点，`3.5e2` = 350 |

**家族成员**：`stoi`（int）、`stol`（long）、`stoll`（long long）、`stoul` / `stoull`（无符号）、
`stof` / `stod` / `stold`（浮点）。

**三个要点**：

1. **它会跳过前导空白**（空格、`\n`、`\t` 都算）。
2. **它允许尾部有垃圾**：`"12abc"` → `12`，**不报错**。想知道"吃掉了多少"就传第二个参数。
3. **它靠抛异常报错**，两种：

<!-- example:ch09_stoi_err -->
```cpp
#include <iostream>
#include <string>

int main() {
    try {
        std::stoi("abc");
    } catch (const std::invalid_argument& e) {
        std::cout << "invalid_argument: " << e.what() << '\n';
    }
    try {
        std::stoi("99999999999");
    } catch (const std::out_of_range& e) {
        std::cout << "out_of_range: " << e.what() << '\n';
    }
    std::cout << std::stoi("12abc") << '\n';
    std::cout << "程序继续\n";
}
```

<!-- result:ch09_stoi_err -->
```text
invalid_argument: invalid stoi argument
out_of_range: stoi argument out of range
12
程序继续
```

| 情况 | 抛什么 |
|---|---|
| **一个数字都没解析出来**（`"abc"`、空串、只有空白） | `std::invalid_argument` |
| **解析出来的数超出目标类型范围**（`int` 装不下） | `std::out_of_range` |
| 尾部有垃圾（`"12abc"`） | **不抛**，返回 `12` |

> ⚠️ **坑**：`stoi` 的异常消息（`"invalid stoi argument"`）是**库实现自己写的英文文本**，
> 标准不规定它长什么样。**不要拿它做判断或匹配**，要判类型就 `catch (const std::invalid_argument&)`。
> 第 08 章第 4.2 节已经实测过同一个异常。
>
> ⚠️ **第二个坑（本机实测的真实警告）**：`std::stoi` 标了 `[[nodiscard]]`。
> 丢掉返回值编译给：
>
> ```text
> main.cpp(6): warning C4834: 放弃具有 [[nodiscard]] 属性的函数的返回值
> main.cpp(11): warning C4834: 放弃具有 [[nodiscard]] 属性的函数的返回值
> ```
>
> 这两条警告在这里是**故意的**（我们只想触发异常）。真实项目里看到 `C4834`，
> 通常意味着"你调到一半忘了用结果"。

**还有一个要避开的坑**：`std::stoi` **受当前 locale 影响**（比如某些 locale 下千位分隔符会被吃掉）。
要"完全按 ASCII 数字解析、不受 locale 影响、不分配、不抛异常"的版本，
C++17 有 `<charconv>` 里的 `std::from_chars`——它返回一个"指针 + 错误码"的结构，**但本讲义不在正文展开**（见第 12 节诚实标注）。

### 4.2 数 → 字符串：`std::to_string` 与 `ostringstream`

<!-- example:ch09_tostring -->
```cpp
#include <iomanip>
#include <iostream>
#include <sstream>
#include <string>

int main() {
    std::cout << std::to_string(42) << '\n';
    std::cout << std::to_string(-7) << '\n';
    std::cout << std::to_string(3.14159) << '\n';
    std::cout << std::to_string(1e20) << '\n';

    std::ostringstream out;
    out << std::fixed << std::setprecision(2) << 3.14159;
    std::cout << out.str() << '\n';
}
```

<!-- result:ch09_tostring -->
```text
42
-7
3.141590
100000000000000000000.000000
3.14
```

| 输出行 | 说明 |
|---|---|
| `42` / `-7` | 整数直接转 |
| `3.141590` | ⚠️ **浮点固定按 `%f` 风格输出，默认 6 位小数**——你想要的"3.14159"不会出现 |
| `100000000000000000000.000000` | 大数不转科学计数，直接铺开 |
| `3.14` | 想控精度就得用 `ostringstream` + `setprecision` |

> ⚠️ **坑（格式类）**：`std::to_string(double)` **没有精度参数**，行为等价于 `printf("%f")`（6 位小数）。
> 想要别的精度、想要科学计数、想要去掉末尾的 0——**都得换 `ostringstream`**（或 C++20 的 `std::format`）。

**三种数→字符串方案对照**：

| 方案 | 能力 | 代价 |
|---|---|---|
| `std::to_string` | 一行搞定，整数/浮点都行 | 浮点只能 6 位小数，不受你控制 |
| `std::ostringstream` | 完整复用流的全部格式开关（精度、进制、宽度、填充） | 啰嗦一点，创建对象有一点开销 |
| `std::format`（**C++20 起**） | 一次到位、可读性最好 | **本讲义基线是 C++17，不用它写正文代码** |

### 4.3 什么时候宁可不用它们

| 场景 | 更合适的做法 |
|---|---|
| 只是要把数字输出到屏幕 | **直接 `std::cout << x`**，别先转字符串 |
| 拼一大段文本 | 直接往 `ostringstream` 里 `<<`，最后 `.str()` 取一次 |
| 高频解析大文件里的数字 | `from_chars`（C++17，本讲义不展开） |
| 需要"失败不许抛异常" | 用 `std::optional` 包装（第 08 章第 7 节 / 第 10 章讲 `optional`） |

> **判据**：`std::to_string` / `std::stoi` 是**便利函数**，不是"唯一通道"。
> 它们在图省事时很好，一旦你需要控制格式或错误处理，就该换到流或 `charconv` 那一侧。

## 5. 流：一个统一的输入输出模型

### 5.1 先看现象：同一套 `<<` 既写屏幕又写内存

<!-- example:ch09_stream_model -->
```cpp
#include <iostream>
#include <sstream>
#include <string>

int main() {
    std::stringstream ss;
    ss << "name=" << "tom" << " age=" << 20;
    std::cout << ss.str() << '\n';

    std::istringstream in("weight=65.5 height=1.72");
    std::string token;
    while (in >> token) {
        std::size_t eq = token.find('=');
        std::cout << token.substr(0, eq) << " -> " << token.substr(eq + 1) << '\n';
    }
    std::cout << in.eof() << ' ' << in.fail() << '\n';
}
```

<!-- result:ch09_stream_model -->
```text
name=tom age=20
weight -> 65.5
height -> 1.72
1 1
```

**注意第一行**：`ss << ...` 和 `std::cout << ...` 用的是**同一个 `<<`**，
一个写进了内存里的字符串，一个写到了屏幕。

**这就是"流"这个抽象的价值**：`<<` / `>>` 不关心另一头是屏幕、文件还是内存缓冲区。

### 5.2 模型：流的两个部分

```text
        ┌─────────────── 流对象 ───────────────┐
输入源 →│  ① 缓冲区：一段内存，暂存还没处理的字符  │→ 你的代码（用 >> / getline 取）
(键盘/   │  ② 状态位：记录"上一次操作成功了吗"     │
 文件)   └───────────────────────────────────────┘

输出方向反过来：你的代码（用 << 放）→ 缓冲区 → 屏幕/文件
```

**① 缓冲区**（buffer）是理解第 8 节那个坑的关键：
`cin >> age` **不会**把整行都读走，它只读到"这个数结束"为止，**换行符留在缓冲区里**。

**② 状态位**是流和"裸文件描述符"最大的区别。有四个：

| 状态位 | 含义 | 怎么问 |
|---|---|---|
| `goodbit` | 一切正常 | `in.good()` |
| `eofbit` | 撞到了输入末尾 | `in.eof()` |
| `failbit` | 这次操作失败了（格式不对、要读的东西不存在） | `in.fail()` |
| `badbit` | 流本身坏了（缓冲/设备层面出了大问题） | `in.bad()` |

**读法**：`in` 用在 `if` 或 `while` 里时，等价于 `!in.fail()`。
所以 `while (std::getline(in, line))` 的意思是"这一次读成功了就进循环体"。

> ⚠️ **`eof()` 不是"已经读完了"，而是"上一次读撞到了末尾"。**
> 这个区别决定了循环该怎么写：**先读、再判断**（读失败就不进循环体），
> 而不是**先判断 `eof()` 再读**（那样会多处理一次旧数据）。第 7 节的循环全是前一种形式。

### 5.3 `cout` / `cerr` / `clog` 的分工

| 流 | 用途 | 缓冲 |
|---|---|---|
| `std::cout` | 正常输出 | **有缓冲**，需要时自动冲 |
| `std::cerr` | 错误信息 | **不缓冲**（`unitbuf`），立刻出去 |
| `std::clog` | 日志 | 有缓冲 |

<!-- example:ch09_cerr_endl -->
```cpp
#include <iostream>

int main() {
    std::cout << "cout 1";
    std::cout << " 继续";
    std::cout << std::endl;          // 换行 + 立刻冲出去
    std::cout << "cout 2" << '\n';   // 只换行
    std::cout << "cout 3" << std::flush;
    std::cout << " 结束" << '\n';
}
```

<!-- result:ch09_cerr_endl -->
```text
cout 1 继续
cout 2
cout 3 结束
```

| 写法 | 换行 | 立刻冲缓冲 |
|---|---|---|
| `'\n'` | ✅ | ❌ |
| `std::endl` | ✅ | ✅（等价于 `'\n'` + `flush`） |
| `std::flush` | ❌ | ✅ |

> **本讲义的立场**：日常用 `'\n'`，需要立刻看到输出（调试、崩溃前）才用 `std::endl` / `std::flush`。
> `std::endl` **不是"更高级的换行"**，它多干了一件事——每次冲缓冲都可能是一次系统调用。
> 这个现象在第 08 章第 2.4 节「没人接住会怎样：一个“看不见输出”的实测」讨论过：**程序崩溃时，还躺在缓冲区里的输出会丢**。

### 5.4 格式开关：`<iomanip>`

<!-- example:ch09_iomanip -->
```cpp
#include <iomanip>
#include <iostream>

int main() {
    std::cout << std::hex << 255 << ' ' << std::dec << 255 << '\n';
    std::cout << std::boolalpha << (1 == 1) << ' ' << std::noboolalpha << (1 == 1) << '\n';
    std::cout << std::setw(6) << std::setfill('0') << 42 << '\n';
    std::cout << std::setfill(' ') << std::fixed << std::setprecision(3) << 3.14159265 << '\n';
}
```

<!-- result:ch09_iomanip -->
```text
ff 255
true 1
000042
3.142
```

| 名字 | 作用 | 粘性 |
|---|---|---|
| `std::hex` / `std::dec` / `std::oct` | 进制 | **粘着**，一直有效直到改回来 |
| `std::boolalpha` | `bool` 打印成 `true` / `false` | **粘着** |
| `std::fixed` / `std::scientific` | 浮点记法 | **粘着** |
| `std::setprecision(n)` | 有效位数 / 小数位数 | **粘着** |
| `std::setw(n)` | 下一次输出的最小宽度 | ⚠️ **只对下一次输出有效** |
| `std::setfill(c)` | 填充字符 | **粘着** |
| `std::left` / `std::right` | 对齐 | **粘着** |

> ⚠️ **坑（最容易忘的一条）**：`setw` 是**一次性**的，`setfill` / `setprecision` / `hex` 是**粘着**的。
> 所以"上一个 `setw(6)` 影响了下面几行"这种事不会发生，但"忘了 `std::dec` 回来，
> 后面所有数字都变成十六进制"这种事**经常发生**。上例第 1 行就是显式改回来的样子。

### 5.5 状态位怎么咬人：失败之后，后面的读取全部失效

**这是本节最重要的一段。**

<!-- example:ch09_stream_state -->
```cpp
#include <iostream>
#include <sstream>
#include <string>

int main() {
    std::istringstream in("abc 42 hello");
    int n = -1;
    std::string s;

    in >> n;
    std::cout << n << ' ' << in.fail() << '\n';   // 输入是 "abc"，读整数失败
    in >> s;
    std::cout << '[' << s << "] " << in.fail() << '\n';   // 流已在失败态，s 没被碰

    in.clear();                                    // 只清状态位，不丢缓冲里的字符
    in >> s;
    std::cout << s << '\n';
    in >> n;
    std::cout << n << ' ' << in.eof() << ' ' << in.fail() << '\n';
}
```

<!-- result:ch09_stream_state -->
```text
0 1
[] 1
abc
42 0 0
```

**逐行解释**：

| 输出 | 发生了什么 |
|---|---|
| `0 1` | `in >> n` 想读整数，下一个词是 `abc` → **读取失败**（`fail()` 是 1）。`n` 本来是 `-1`，但打印出来是 **0**，见下方说明 |
| `[] 1` | 流已经在失败态，`in >> s` **一个字符都不动**，`s` 还是空串，`fail()` 仍是 1 |
| `abc` | `clear()` 清掉状态位（**缓冲区里的 `abc` 还在**），这次 `>>` 成功读到 `abc` |
| `42 0 0` | 再读一次拿到 42，`eof()` 是 0、`fail()` 是 0——还没读到末尾 |

> ⚠️ **一个必须说清的细节**：`n` 初始化成 `-1`，本机打印出来却是 **0**。
> 也就是说，**数值提取失败时这个数会被写成 0**，而不是"保持原值"。
> （对照：字符串提取失败时目标**不修改**——第 8.3 节那个 `[sentinel]` 就是证据。）
>
> **结论比具体机制更重要**：**"读到 0"完全可能是"读失败了"**。
> 这两件事只靠看值是分不清的，**只有 `fail()` 说得清**。
> 所以本节要建立的习惯是：
>
> > **数值读数之后，永远查一次流状态，再用那个数。**

> ⚠️ **第二个坑**：**失败态是"粘"的**。一旦 `failbit` 置起，后面每一次 `>>` 都直接失败——
> 这就是"输入一个字母，整个程序开始无限循环打印同一行"的机制：循环条件里那个 `>>` 永远失败，
> 而**循环体里没有清状态、也没有把那个坏字符从缓冲区拿走**，于是原地打转。
> 处理办法是 `clear()`（清状态）**加上** `ignore(...)`（扔掉坏字符），见第 8 节。

### 5.6 `stringstream` 家族：把字符串当流用

| 类型 | 方向 | 典型用途 |
|---|---|---|
| `std::istringstream` | 读 | 把一整行拆成若干字段 |
| `std::ostringstream` | 写 | 用流的格式开关拼字符串 |
| `std::stringstream` | 读写 | 两者都行 |

`.str()` 用来取/设内部那个字符串。**关键用法在第 8 节**：
"先 `getline` 读一整行，再塞进 `istringstream` 拆"是规避 `>>`/`getline` 混用问题的最稳写法。

## 6. 格式化：`printf`、流与 `std::format` 的位置

### 6.1 `printf` 家族：格式串驱动

<!-- example:ch09_printf -->
```cpp
#include <cstdio>

int main() {
    const char* name = "tom";
    int age = 20;
    double pi = 3.14159265;

    std::printf("%-6s|%5d|%.2f\n", name, age, pi);
    std::printf("%06.3f|%x|%o\n", pi, 255, 8);
    std::printf("%lld\n", 4294967297LL);
}
```

<!-- result:ch09_printf -->
```text
tom   |   20|3.14
03.142|ff|10
4294967297
```

| 格式符 | 含义 |
|---|---|
| `%s` | 字符串（**必须是 `const char*`**） |
| `%d` | `int` |
| `%lld` | `long long` |
| `%f` | `double`（`printf` 里没有 `float`，会先提升） |
| `%x` / `%o` | 十六进制 / 八进制 |
| `%-6s` | 左对齐，宽度 6 |
| `%06.3f` | 宽度 6、补 0、保留 3 位小数 |

**`%-6s` 那行是对的**：`printf` 的格式信息全在**字符串里**，和实参是分开的。

### 6.2 那它为什么会出事：格式串和实参是两个独立的东西

**因为编译器无法把 `%d` 和后面的实参类型对上**——格式串只是运行期才解析的一串字符。

<!-- example:ch09_printf_trap -->
```cpp
#include <cstdio>

int main() {
    long long big = 4294967297LL;
    std::printf("%d\n", big);        // 格式串说 int，实参是 long long
}
```

<!-- result:ch09_printf_trap -->
```text
1
```

**期望打印 `4294967297`，实际打印 `1`。** 真实诊断（本机 `/W4`）：

```text
main.cpp(5): warning C4477: “printf”: 格式字符串“%d”需要类型“int”的参数，但可变参数 1 拥有了类型“__int64”
```

**为什么会打印 1**：`%d` 告诉 `printf`"去取一个 4 字节整数"，它从参数区里取了**低 4 字节**；
`4294967297` = `0x1_0000_0001`，低 4 字节就是 `1`。
（这是本机这次运行的结果；**标准对这种失配是未定义行为**，换调用约定、换参数个数、换优化级别都可能给出别的东西。）

<!-- example:ch09_printf_unsafe -->
```cpp
#include <cstdio>
#include <string>

int main() {
    std::string s = "not a pointer";
    std::printf("%s\n", s);          // 把 std::string 对象直接当参数交给可变参数函数
}
```

<!-- result:ch09_printf_unsafe -->
```text
not a pointer
```

真实诊断（两条）：

```text
main.cpp(6): warning C4840: 将类 "std::basic_string<char,std::char_traits<char>,std::allocator<char>>" 作为可变参数函数的参数的不可移植用法
main.cpp(6): warning C4477: “printf”: 格式字符串“%s”需要类型“char *”的参数，但可变参数 1 拥有了类型“std::string”
```

**这一次它"恰好"打印对了**——因为本机 `std::string` 对象布局的头 8 字节正好是个指针（指向缓冲区），
`%s` 就顺着它读了下去。**但这属于未定义行为**：换个实现、换个优化级别、加一个成员，
结果就完全不同。这里的格式串与可变实参不会自动配对检查，前面的诊断正是这种不匹配的具体后果。

> ⚠️ **判据**：`printf` 的安全性由**你手写的那串格式符**保证，编译器只能事后警告（`/W4` 才有）。
> 这两个例子都**编译通过**、都在 `rc=0` 下运行——**它们不是"错误示例"，是"陷阱示例"**。

### 6.3 流：类型安全，但啰嗦

<!-- example:ch09_iostream_format -->
```cpp
#include <iomanip>
#include <iostream>

int main() {
    const char* name = "tom";
    int age = 20;
    double pi = 3.14159265;

    std::cout << std::left << std::setw(6) << name << '|'
              << std::right << std::setw(5) << age << '|'
              << std::fixed << std::setprecision(2) << pi << '\n';
    std::cout << std::setfill('0') << std::setw(6) << pi << std::setfill(' ')
              << '|' << std::hex << 255 << '|' << std::oct << 8 << std::dec << '\n';
}
```

<!-- result:ch09_iostream_format -->
```text
tom   |   20|3.14
003.14|ff|10
```

**对比 `ch09_printf` 的同一行输出**：`tom   |   20|3.14` 一模一样。

| | `printf("%-6s|%5d|%.2f\n", ...)` | `std::cout << std::left << std::setw(6) << ...` |
|---|---|---|
| 你要写几段 | 3 个实参 + 一串格式符 | 一长串 `<<` 和操纵符 |
| 类型检查 | ❌ 编译器和格式串对不上（只能警告） | ✅ 编译期就检查 |
| 格式与数据的位置 | 全在格式串里，一眼看到全貌 | 混在表达式里，长语句难读 |
| 恢复默认 | 不用管 | ⚠️ **必须记得 `std::dec` / `std::setfill(' ')` 改回来** |

### 6.4 `std::format` 在什么位置（**C++20 起**）

它想同时拿到两边的好处：**像 `printf` 一样把格式集中写成一句话，又像流一样类型安全**。

```cpp
// C++20 起才有：
std::string s = std::format("{:>6}|{:<5}|{:.2f}", name, age, pi);   // 位置参数 + 类型检查
```

**本机实测（这是本节最硬的一条证据）**：同一份源码，`/std:c++17` 编不过，`/std:c++20` 编得过。

```text
--- /std:c++17（本讲义基线）---
  CL_RC=2
  ! ...\include\format(42): warning STL4038: The contents of <format> are available only with C++20 or later.
  ! main.cpp(5): error C2039: "format": 不是 "std" 的成员
  ! main.cpp(5): error C3861: “format”: 找不到标识符
  ! main.cpp(5): error C2593: “operator <<”不明确

--- /std:c++20 ---
  CL_RC=0
  1 + 2 = 3
```

注意这两条：

1. **连头文件都在替编译器说话**：`STL4038: ... available only with C++20 or later`。
2. **`format` 那条错误是"不是 std 的成员"**——不是"少写了头文件"，而是"这个标准版本里根本没有这个东西"。
   第 01 章第 7 节讲过怎么用 `/std:` 开关，第 13 章第 8.1 节把 `std::format` 列在 C++20 地图里。

### 6.5 取舍表：什么时候用哪个

| | `printf` 家族 | 流（`<<` + `<iomanip>`） | `std::format`（**C++20 起**） |
|---|---|---|---|
| **标准版本** | C 起就有（`<cstdio>`） | C++98 起 | **C++20 起**；本机 `/std:c++17` 下不可用（已实测） |
| **类型安全** | ❌ 不检查，只能靠 `/W4` 事后警告 | ✅ 编译期检查 | ✅ 编译期检查格式串 |
| **格式集中度** | ✅ 一行看全 | ❌ 混在 `<<` 链里 | ✅ 一行看全 |
| **位置参数** | ❌ 只能按顺序 | ❌ 只能按顺序 | ✅ `{0}` `{1}` 可重排、可重复 |
| **性能** | 通常最快 | 慢一些（`iostream` 有同步与虚函数开销） | 介于两者之间，通常明显快于流 |
| **状态污染** | 无（格式全在调用点） | ⚠️ `hex`/`setfill` 粘着，会漏到后面的输出 | 无 |
| **本机实测证据** | `ch09_printf`（正确用法）／`ch09_printf_trap`、`ch09_printf_unsafe`（两个陷阱） | `ch09_iostream_format` | 特殊探针 B 的两份诊断 |
| **什么时候选它** | 对齐 C 接口、日志格式、判题机要求、极致性能 | 默认选择（类型安全 + 不用记格式符） | **等你上了 C++20 再说** |

> **本讲义的立场**：**正文代码默认用流**。`printf` 该认识（读别人的代码、写 C 接口时都会遇到），
> 但"用 `printf` 换一点性能"在有 `std::format` 之前，代价是**类型安全**，不划算。

## 7. 文件读写与 RAII

### 7.1 最小例子：写出去、读回来

<!-- example:ch09_file_roundtrip -->
```cpp
#include <fstream>
#include <iostream>
#include <string>

int main() {
    {
        std::ofstream out("ch09_demo.txt");     // 构造即打开
        std::cout << out.is_open() << '\n';
        out << "line one\n" << "line two\n" << 42 << ' ' << 3.5 << '\n';
    }                                           // 析构即关闭并落盘

    {
        std::ifstream in("ch09_demo.txt");
        std::string line;
        int n = 0;
        while (std::getline(in, line)) {
            std::cout << ++n << ':' << line << '\n';
        }
        std::cout << in.eof() << '\n';
    }

    {
        std::ifstream in("ch09_demo.txt");
        std::string word;
        std::cout << "按空白切分:";
        while (in >> word) {
            std::cout << ' ' << word;
        }
        std::cout << '\n';
    }
}
```

<!-- result:ch09_file_roundtrip -->
```text
1
1:line one
2:line two
3:42 3.5
1
按空白切分: line one line two 42 3.5
```

**这个程序真的在磁盘上产生了一个文件**——探针记录显示，编译目录里除了 `main.obj` 还多了一个
`ch09_demo.txt`。所以：

- 正文里的示例用**相对路径**（`"ch09_demo.txt"`），它落在程序的工作目录里；
- 按本项目的规矩，探针和验收脚本的工作目录都在 `tmp\` 下，**不会污染仓库**；
- 第 01 章第 12.3 节讲过的那个坑在这里同样成立：**Windows 路径里的 `\` 在 C++ 字符串里是转义字符**。

**读法**：

| 代码 | 含义 |
|---|---|
| `std::ofstream out("name.txt");` | 构造 = 打开（默认截断/新建） |
| `out.is_open()` | 真的打开了吗 |
| `while (std::getline(in, line))` | **按行**读，读到 `\n` 为止（不含 `\n`） |
| `while (in >> word)` | **按空白**读（空格、`\t`、`\n` 都算分隔符） |
| `in.eof()` | 打印 `1`：最后一次读撞到了文件末尾 |
| `{ ... }` 这两个花括号 | **不是装饰**：它们决定 `out` / `in` 什么时候析构，也就决定文件什么时候关闭 |

### 7.2 RAII：为什么不需要手写 `close()`

`std::ofstream` / `std::ifstream` 的析构函数会关闭文件。这就是 RAII：

```text
构造 std::ofstream  →  打开文件（拿到句柄）
使用 out << ...     →  写数据（先进缓冲区）
离开作用域 / 对象析构 →  冲缓冲 + 关闭句柄
```

**这条链的价值在于"三条退出路径都安全"**：正常走到块尾、中途 `return`、抛异常展开——
三种情况下析构函数都会跑。第 07 章第 3 节和第 12 章第 7 节把这个机制讲透了，这里只是它最日常的一个应用。

| 资源 | 谁拥有 | 什么时候释放 |
|---|---|---|
| 文件句柄 | `std::ofstream` / `std::ifstream` 对象 | 对象析构时 |
| 字符缓冲区 | `std::string` 对象 | 对象析构时 |
| `std::stringstream` 的内部串 | 那个流对象 | 对象析构时 |

**所以不要写这种代码**：

```cpp
std::ofstream out("a.txt");
// ... 一路写
out.close();              // ← 不是错，但为什么要有这一行？
                          //   如果中间 return 或抛异常，这行就被跳过了
```

> **判据**：**只要有一个类型能替你管住资源，就不要手写成对的 open/close。**
> 第 12 章第 7 节给这条判据起过名字："手写成对调用是最常见的设计缺陷来源"。

### 7.3 打开失败怎么检查（**这就是真会出错的地方**）

**关键事实**：`std::ifstream` 打开失败时**不抛异常**，它只是把流置成失败态。

<!-- example:ch09_file_open_fail -->
```cpp
#include <fstream>
#include <iostream>
#include <string>

int main() {
    std::ifstream in("ch09_no_such_file.txt");
    std::cout << in.is_open() << ' ' << in.fail() << ' ' << (!in) << '\n';

    std::string line;
    std::cout << static_cast<bool>(std::getline(in, line)) << '\n';
    std::cout << in.fail() << '\n';

    std::ofstream out("ch09_no_such_dir/x.txt");
    std::cout << out.is_open() << ' ' << out.fail() << '\n';
}
```

<!-- result:ch09_file_open_fail -->
```text
0 1 1
0
1
0 1
```

| 输出 | 含义 |
|---|---|
| `0 1 1` | `is_open()` 是 0；`fail()` 是 1；`!in` 也是 1（**`if (!in)` 就能判**） |
| `0` | 从没打开的流里 `getline` 返回失败 |
| `1` | `fail()` 仍然是 1 |
| `0 1` | 往一个**不存在的目录**里建文件也是同样结果：`is_open() == 0` |

**三种检查方式，都行，选一种用**：

| 写法 | 说明 |
|---|---|
| `if (!in) { ... }` | 最常用，等价于 `if (in.fail())` |
| `if (in.is_open()) { ... }` | 语义最直白 |
| `if (in) { ... } else { ... }` | 需要 else 分支时 |

> ⚠️ **坑**：**不检查就直接用**。这是"程序没输出、也没报错"最常见的原因——
> 打开失败了，后面的 `getline` 全部静默失败，你的变量保持原样（还记得第 5.5 节吗），
> 程序若无其事地跑完。**判据：文件流构造之后，第一件事就是检查状态。**

**想让失败"吵起来"**：可以打开异常掩码。

<!-- example:ch09_file_exceptions -->
```cpp
#include <fstream>
#include <iostream>

int main() {
    std::ifstream a("ch09_no_such_file.txt");
    std::cout << "默认: is_open=" << a.is_open() << " fail=" << a.fail() << '\n';

    std::ifstream b;
    b.exceptions(std::ios::failbit);
    try {
        b.open("ch09_no_such_file.txt");
        std::cout << "没抛\n";
    } catch (const std::ios_base::failure& e) {
        std::cout << "抛了 ios_base::failure: " << e.what() << '\n';
    }
}
```

<!-- result:ch09_file_exceptions -->
```text
默认: is_open=0 fail=1
抛了 ios_base::failure: ios_base::failbit set: iostream stream error
```

| 做法 | 失败时 | 什么时候合适 |
|---|---|---|
| 默认（检查状态） | 静默置位 | 大多数情况，尤其"文件可能不存在"是正常业务时 |
| `exceptions(std::ios::failbit)` | 抛 `std::ios_base::failure` | 打开失败**就是异常情况**，且调用方已经用 `try` 包着（第 08 章第 2 节） |

> ⚠️ **注意异常消息 `"ios_base::failbit set: iostream stream error"` 是库自己写的英文**，
> 和 `stoi` 的消息一样，**不要拿它做判断**。

### 7.4 缓冲、`flush` 与 `close` 的区别

**"写进流"不等于"落到磁盘上"。** 这中间隔着缓冲区。

<!-- example:ch09_file_flush -->
```cpp
#include <cstdio>
#include <fstream>
#include <iostream>

std::streamoff file_len(const char* path) {
    std::ifstream in(path, std::ios::binary);
    in.seekg(0, std::ios::end);
    return in.tellg();
}

int main() {
    const char* path = "ch09_flush_demo.txt";
    std::ofstream out(path);
    out << "abc";
    std::cout << file_len(path) << '\n';
    out.flush();
    std::cout << file_len(path) << '\n';
    out.close();
    out << "x";                       // 对已关闭的流写：不崩，但置位失败状态
    std::cout << out.fail() << '\n';
    std::remove(path);
}
```

<!-- result:ch09_file_flush -->
```text
0
3
1
```

| 输出 | 含义 |
|---|---|
| `0` | `out << "abc"` 之后**文件还是 0 字节**——数据躺在流的缓冲区里 |
| `3` | `flush()` 之后才真的写下去 |
| `1` | 对**已经 `close()` 的流**继续写：程序不崩，但 `fail()` 变成 1 |

**这张输出把"三层"分得很清楚**：

```text
你的 out << "abc"
    ↓  （① 流对象的缓冲区，flush 之前数据就在这里）
文件系统的页缓存
    ↓  （② 操作系统缓冲，close 不保证物理写入磁盘）
磁盘
```

**三个操作的准确含义**：

| 操作 | 做什么 |
|---|---|
| `out.flush()` | 把**①**推给操作系统 |
| `out.close()` | 先 flush，再释放文件句柄 |
| 析构 | 先 close（如果还开着） |

> ⚠️ **坑**：`out.close()` 之后**流对象还在**，只是它不再连着任何文件。
> 继续 `out << "x"` 不会崩，但什么也不会写进去，而且会把 `failbit` 置起（本机实测 `fail() == 1`）。
> **判据：`close()` 之后不要再碰这个流，或者干脆不要写 `close()`，交给析构。**

**打开模式**（默认值不是唯一选择）：

| 标志 | 含义 |
|---|---|
| `std::ios::in` / `std::ios::out` | 可读 / 可写（`ifstream` / `ofstream` 自带） |
| `std::ios::app` | 追加，不截断 |
| `std::ios::trunc` | 截断（`ofstream` 默认） |
| `std::ios::binary` | 二进制模式（不做换行转换） |
| `std::ios::ate` | 打开后立刻定位到末尾 |

多个标志用 `|` 连：`std::fstream io("a.txt", std::ios::in | std::ios::out | std::ios::binary);`

> ⚠️ **`std::ios::binary` 在 Windows 上不是可选项**：文本模式会把你写出去的 `\n` 变成 `\r\n`。
> 读二进制文件（图片、你自己定义的数据文件）必须加它，否则字节数对不上。**这条与第 7.5 节的"字节数"直接相关。**

### 7.5 读写文本的两种姿势

| 想要 | 用 |
|---|---|
| 一行一行（保留行结构） | `std::getline(in, line)` |
| 一个词一个词（按空白切） | `in >> word` |
| 整体读成一个大字符串 | `std::string all((std::istreambuf_iterator<char>(in)), {});` |
| 一个字节一个字节 | `in.get(c)` / `in.read(buf, n)`（配 `std::ios::binary`） |

**选哪个取决于"换行是不是数据的一部分"**：配置行、CSV 行 → `getline`；
数字表、按列解析 → `>>`。

## 8. 输入解析的坑：`>>` 与 `getline` 混用

### 8.1 现象：输入了名字，程序说名字是空的

<!-- example:ch09_mix_getline -->
```cpp
#include <iostream>
#include <string>

int main() {
    int age = 0;
    std::string name;
    std::cin >> age;                // 只吃数字，'\n' 留在缓冲里
    std::getline(std::cin, name);   // 这一次只读到那个 '\n'
    std::cout << age << " [" << name << "] " << name.size() << '\n';
}
```

<!-- stdin:ch09_mix_getline -->
```text
42
Zhang San
```

<!-- result:ch09_mix_getline -->
```text
42 [] 0
```

**输入里明明有 `Zhang San`，`name` 却是空串，长度 0。** 探针记录显示喂进去的原始字节是
`34 32 0A 5A 68 61 6E 67 20 53 61 6E 0A`（`"42\nZhang San\n"`）——**没有丢数据，是读的位置不对**。

### 8.2 机制：`>>` 把分隔符留下了

```text
std::cin >> age 做完之后，缓冲区是这样：

  已消费 ──▶  '4'  '2'
  还留着 ──▶  '\n'  'Z'  'h'  'a'  'n'  'g'  ' '  'S'  'a'  'n'  '\n'
                ↑
                └─ 这就是那个"吞不下去也不属于数字"的字符

std::getline(std::cin, name) 的规则是：
    "从当前位置读，直到遇到 '\n' 为止；'\n' 被消费掉，但不放进结果里"
于是它读到的第一个字符就是 '\n' → 结果为空串 → 长度 0
```

**关键认识**：`>>` 是"**跳过前导空白、读到下一个空白前停下**"——**它不消费那个分隔它的空白**。
而 `getline` 是"**读到 `\n` 为止**"，两者对"空白"的处理方式不一样，接在一起就错位了。

**这条坑的判据很好记**：**`>>` 之后紧跟 `getline`，第一个 `getline` 拿到的几乎永远是空串。**

再跑一次就看得更清楚（同一个输入）：

<!-- example:ch09_mix_getline2 -->
```cpp
#include <iostream>
#include <string>

int main() {
    int age = 0;
    std::string first, second;
    std::cin >> age;
    std::getline(std::cin, first);     // 第一次拿到空串
    std::getline(std::cin, second);    // 第二次才是你想读的那一行
    std::cout << age << '[' << first << "] [" << second << ']' << '\n';
}
```

<!-- stdin:ch09_mix_getline2 -->
```text
42
Zhang San
```

<!-- result:ch09_mix_getline2 -->
```text
42[] [Zhang San]
```

**`first` 是空的，`second` 才是 `Zhang San`。** 这直接证明了"那一次 `getline` 只是把换行吃掉了"。

### 8.3 更隐蔽的一种：读失败之后 `getline` 什么都不做

<!-- example:ch09_mix_fail -->
```cpp
#include <iostream>
#include <string>

int main() {
    int age = 0;
    std::string line = "sentinel";
    std::cin >> age;                  // 输入不是数字，读取失败
    std::cout << age << ' ' << std::cin.fail() << '\n';
    std::getline(std::cin, line);     // 流已在失败态，getline 立刻失败、不碰 line
    std::cout << '[' << line << "] " << std::cin.fail() << '\n';
    std::cin.clear();
    std::getline(std::cin, line);
    std::cout << '[' << line << ']' << '\n';
}
```

<!-- stdin:ch09_mix_fail -->
```text
abc
Zhang San
```

<!-- result:ch09_mix_fail -->
```text
0 1
[sentinel] 1
[abc]
```

**第二行是本节的第二个知识点**：`getline` **一个字符都没动**——`line` 还是那个哨兵 `"sentinel"`，
而且 `fail()` 还是 1。所以：

> ⚠️ **判据**：**"字符串是空的"有两种完全不同的来源**：
> ① `getline` 真的读到了一行，而那一行恰好是空的（第 8.1 节）；
> ② **流已经在失败态，`getline` 立刻失败、不碰目标**（这一节，`line` 保持原值）。
> 两者都会给你一个"空/没变"的字符串，**只有查 `fail()` 分得清**。
> 这条和第 5.5 节的结论是同一条，只是换了个更常见的场景。

**第三行**：`clear()` 之后 `getline` 读到了 `abc`——**那个坏字符一直在缓冲区里没被拿走**。
这也是为什么"只 `clear()` 不够"：`clear()` 清状态位，不清缓冲区。

### 8.4 三种正确的写法

**写法一：`ignore` 掉那一行剩下的内容**

<!-- example:ch09_mix_fix_ignore -->
```cpp
#include <iostream>
#include <limits>
#include <string>

int main() {
    int age = 0;
    std::string name;
    std::cin >> age;
    std::cin.ignore(std::numeric_limits<std::streamsize>::max(), '\n');
    std::getline(std::cin, name);
    std::cout << age << " [" << name << ']' << '\n';
}
```

<!-- stdin:ch09_mix_fix_ignore -->
```text
42
Zhang San
```

<!-- result:ch09_mix_fix_ignore -->
```text
42 [Zhang San]
```

`ignore(n, delim)` = 丢掉最多 `n` 个字符，或者直到碰到 `delim` 为止。
`std::numeric_limits<std::streamsize>::max()` 是"足够大"，保证一定丢到换行为止。

**写法二：先读整行，再在内存流里拆（最不容易错）**

<!-- example:ch09_mix_fix_line -->
```cpp
#include <iostream>
#include <sstream>
#include <string>

int main() {
    std::string line;
    std::getline(std::cin, line);      // 一次读一整行
    std::istringstream iss(line);
    int age = 0;
    std::string name;
    iss >> age >> name;                // 在内存流里拆，cin 不受影响

    std::getline(std::cin, line);      // cin 仍然干净，可以继续读整行
    std::cout << age << ' ' << name << " [" << line << ']' << '\n';
}
```

<!-- stdin:ch09_mix_fix_line -->
```text
42 Zhang San
last line
```

<!-- result:ch09_mix_fix_line -->
```text
42 Zhang [last line]
```

> ⚠️ **为什么它最不容易错**：`cin` **从头到尾只被 `getline` 碰**，
> 那些"空白怎么处理"的细节全被关进了 `istringstream` 里。混用问题在结构上就不会发生。

**写法三：`std::ws` 吃掉前导空白**

<!-- example:ch09_mix_fix_ws -->
```cpp
#include <iostream>
#include <string>

int main() {
    int age = 0;
    std::string name;
    std::cin >> age;
    std::getline(std::cin >> std::ws, name);   // ws 吃掉前导空白，包括 '\n'
    std::cout << age << " [" << name << ']' << '\n';
}
```

<!-- stdin:ch09_mix_fix_ws -->
```text
42
Zhang San
```

<!-- result:ch09_mix_fix_ws -->
```text
42 [Zhang San]
```

> ⚠️ **`std::ws` 会把前导空格也吃掉**。如果用户的名字开头真的有空格有意义（少见但存在），
> 这个写法会改掉数据。要精确保留，用写法一或写法二。

### 8.5 三种写法怎么选

| 写法 | 优点 | 缺点 | 什么时候用 |
|---|---|---|---|
| `ignore` | 改动最小，一行搞定 | 只丢"到换行为止"，要自己确认分隔符 | 混合读少量数值 + 一行文本 |
| 先 `getline` 再 `istringstream` | **结构化**，`cin` 不被混用 | 多一个对象，多一次拷贝 | **默认推荐**：按行读结构化输入 |
| `getline(cin >> ws, s)` | 最简洁 | 会吃掉有意义的前导空白 | 确定前导空白没有意义时 |

> **一条通用判据**：**同一个输入流上，不要一会儿 `>>` 一会儿 `getline`。**
> 二选一：要么全程 `>>`（接受"空白都算分隔符"），要么全程 `getline` + 内存流拆。

## 9. 编码：源文件、执行字符集与终端代码页

**这一节要区分三件经常被混成一件的事**：

| # | 是什么 | 什么时候发生 | 出错的症状 |
|---|---|---|---|
| 1 | **源文件编码** | **编译期**，编译器需要读懂你的 `.cpp` | **编译不过**（一堆和中文毫无关系的语法错误） |
| 2 | **执行字符集** | **编译期**，编译器决定往程序里塞什么字节 | 编译过，但字符串的**字节**不是你以为的那串 |
| 3 | **终端代码页** | **运行期**，显示程序输出的那个程序怎么解释字节 | 程序对了，**屏幕上却是乱码** |

**1 和 2 是编译期的事，3 是运行期的事。** 这就是为什么"加了 `/utf-8` 就都好了"这句话只说对了一半——
它解决的是 1 和 2（第 9.1、9.2 节），而 3 取决于你**在哪儿看输出**（第 9.4 节）。

### 9.1 本机事实：代码页 936，以及不加 `/utf-8` 会怎样

**本机控制台活动代码页是 936（GBK）**，实测：

```text
chcp 原始输出: 'Active code page: 936'
```

MSVC 默认会**按系统代码页解释源文件**。所以一份 UTF-8 编码、含中文注释和中文串的 `.cpp`，
不加 `/utf-8` 就是下面这个结局（真实诊断，逐字抄自探针）：

```text
main.cpp(1): warning C4819: 该文件包含不能在当前代码页(936)中表示的字符。请将该文件保存为 Unicode 格式以防止数据丢失
main.cpp(6): error C2001: 字符串字面量中的换行符
main.cpp(6): error C3688: 文本后缀“锛乗n”无效；未找到文文本运算符或文本运算符模板“operator """"锛乗n”
main.cpp(7): error C2143: 语法错误: 缺少“;”(在“}”的前面)
```

**统计：1 条 warning + 3 条 error，编译不通过。**

**怎么读这四条**（这一段和第 01 章第 12.1 节讲的是同一个坑，这里补上"为什么"）：

```text
你的文件里（UTF-8）        编译器以为的（GBK）
"你好，"   = E4 BD A0 E5 A5 BD    ← 它按 GBK 两个字节一个字重新分组
换行符 '\n' 前的字节         → 某个字节被当成了 '\'（续行/转义符）
                                  → 于是"该行没结束" → C2001"字符串里的换行符"
                                  → 后面一串字符被当成"文本后缀" → C3688
                                  → 括号对不上 → C2143
```

**关键判据**：**报错位置和真正的问题离得很远**。
报 `C2001` 说"字符串里有换行"，真因是"源文件编码标错了"。遇到"这个错误在这行根本没道理"时，
先怀疑环境，别死磕那一行。

**处理**：加 `/utf-8`。它等价于同时指定"源是 UTF-8"和"执行字符集也是 UTF-8"。

### 9.2 执行字符集：加 `/utf-8` 之后，中文字符串是什么字节

<!-- example:ch09_encoding_cn -->
```cpp
#include <cstdio>
#include <iostream>
#include <string>

int main() {
    std::string name = "张三";
    std::cout << "你好，" << name << "！\n";
    std::cout << name.size() << '\n';
    for (unsigned char c : name) {
        std::printf("%02X ", static_cast<unsigned>(c));
    }
    std::printf("\n");
}
```

<!-- result:ch09_encoding_cn -->
```text
你好，张三！
6
E5 BC A0 E4 B8 89 
```

> ⚠️ 上面 `result` 块最后一行**结尾有一个空格**——那是 `printf("%02X ")` 在最后一个字节后面留下的，
> 逐字比对会看到它。这不是笔误。

| 输出 | 含义 |
|---|---|
| `你好，张三！` | 中文源代码 + 中文字符串输出**正常**（`/utf-8` 解决的就是这个） |
| `6` | 「张三」两个汉字 === **6 个字节**：`char` 是字节，不是字符 |
| `E5 BC A0 E4 B8 89 ` | 这就是 UTF-8 编码的实际字节：`张` = `E5 BC A0`，`三` = `E4 B8 89` |

**这张输出说明了三件事**：

1. **`std::string` 的长度是字节数，不是字符数。** `name.size()` 给 6，而不是 2。
   （所以"取前 3 个字符"在这种字符串上会切碎一个汉字——这是第 10 章讲算法时要注意的事。）
2. **UTF-8 是变长编码**：一个汉字 3 字节，一个 ASCII 字符 1 字节。
3. **`/utf-8` 让"源"和"执行"两件事统一成 UTF-8**，所以字符串里的字节就是你写下的 UTF-8。

**那"源"和"执行"能不能分别指定**？能。实测四种开关组合的输出字节：

| 编译器开关 | 程序写出的字节 | 按 UTF-8 解 | 按 GBK 解 |
|---|---|---|---|
| `/utf-8` | `E4 B8 AD E6 96 87` | `'中文'` ✅ | 失败（illegal multibyte sequence） |
| `/source-charset:utf-8` | `D6 D0 CE C4` | 失败（invalid continuation byte） | `'中文'` ✅ |
| `/source-charset:utf-8 /execution-charset:utf-8` | `E4 B8 AD E6 96 87` | `'中文'` ✅ | 失败 |
| `/source-charset:utf-8 /execution-charset:gbk` | `D6 D0 CE C4` | 失败 | `'中文'` ✅ |

**读法**：`/utf-8` = `/source-charset:utf-8` + `/execution-charset:utf-8`。
只写前一半时，**执行字符集跟随系统代码页 → 输出的是 GBK 字节**（`D6 D0 CE C4` 正是「中文」的 GBK 编码）。

> **这就是"源文件编码"和"执行字符集"是两件事**的硬证据：
> 两份程序源码完全一样、都能编过，**写出来的字节却不是同一串**。

### 9.3 宽字符：`wchar_t` 是另一条路（而且更麻烦）

<!-- example:ch09_encoding_sizes -->
```cpp
#include <iostream>

int main() {
    std::cout << sizeof(char) << ' ' << sizeof(wchar_t) << ' '
              << sizeof(char16_t) << ' ' << sizeof(char32_t) << '\n';
    std::cout << static_cast<unsigned>(u'中') << '\n';
    std::cout << static_cast<unsigned>(U'中') << '\n';
}
```

<!-- result:ch09_encoding_sizes -->
```text
1 2 2 4
20013
20013
```

| 类型 | 本机 `sizeof` | 含义 |
|---|---|---|
| `char` | 1 | 一个**字节**。UTF-8 用它，一个汉字要 3 个 |
| `wchar_t` | **2** | ⚠️ **在 Windows 上是 16 位**；在 Linux 上通常是 4 字节。标准只要求"能表示实现支持的最大字符集" |
| `char16_t` | 2 | UTF-16 码元（C++11 起，`u"..."`） |
| `char32_t` | 4 | UTF-32 码元（C++11 起，`U"..."`） |
| `u'中'` / `U'中'` | 20013 | 「中」的 Unicode 码位是 `U+4E2D` = 20013 |

> ⚠️ **坑（平台差异）**：`sizeof(wchar_t)` 在 Windows 是 2、在 Linux 通常是 4。
> 所以**任何假设 `wchar_t` 宽度、或者假设"一个 `wchar_t` 就是一个字符"的代码都不可移植**。
> 这条和第 02 章第 3.1 节那个 `sizeof(long double)` 的坑是同一类：**标准没定死，实现说了算**。

**那 `std::wcout` 能直接打印中文吗？** 本机实测：**不能，而且失败得很安静**。
把 `std::wcout << L"宽字符输出: " << L"中文" << L'\n';` 的输出重定向到文件后：

| 写法 | stdout 字节数 | 按 GBK 解 |
|---|---|---|
| 只用 `std::wcout`（默认 C locale） | **0** | —— **什么都没写出来** |
| 先 `std::setlocale(LC_ALL, "")` 再 `std::wcout` | 18 | `宽字符输出: 中文`（GBK 字节 `BF ED D7 D6 ...`） |
| 先 `std::cout << "1 ..."`，再 `std::wcout`，再 `imbue` | 26 | 只有窄流那两行；**宽流的两次输出全部消失** |

**读法**：

1. **默认状态下 `std::wcout` 写不出中文，而且不报错**——因为它要按当前 locale 的转换规则把
   `wchar_t` 变成字节，而默认的 "C" locale 处理不了这个字符，于是流置失败位，输出全部丢弃。
2. **`std::setlocale(LC_ALL, "")` 之后能写出来，但写的是 GBK 字节**（跟随系统代码页）——
   这就是一开始说的第 3 件事（终端代码页）在起作用。
3. **宽流和窄流混用还会出问题**：一旦 `wcout` 进入失败态，后面的 `imbue` 也救不回来。

> ⚠️ **判据**：**入门阶段不要用 `wchar_t` / `std::wcout` 做中文 IO。**
> 它是 Windows API（`...W` 系列函数）和少数国际化场景需要的东西，
> 但它的宽度、locale 依赖、与窄流混用的行为都充满平台差异。
> **UTF-8 的 `std::string` + `/utf-8` 才是本讲义的基线做法。**

### 9.4 第 3 件事：终端代码页（这是**运行期**的事）

前面所有的字节都是"程序写出去的"。**这些字节最后显示成什么，取决于读它的那个程序按什么编码解。**

```text
程序（已按 /utf-8 编译，写出 UTF-8 字节 E4 B8 AD E6 96 87）
        │
        ├─▶ 重定向到文件 ──▶ 文件里就是这 6 个字节（探针实测确认）
        │
        └─▶ 交给终端 ──▶ 终端按【它的活动代码页】解释这 6 个字节
                          ├─ 按 UTF-8 解 → 屏幕显示「中文」
                          └─ 按 GBK   解 → 屏幕显示乱码
```

**本机活动代码页是 936（GBK）**，所以：

- **在 cmd 里直接跑一个输出 UTF-8 字节的程序，中文会显示成乱码**——程序没错，是看的人按错了码。
- **本讲义所有探针输出里的中文都是正常的**，因为探针脚本在跑之前把
  `[Console]::OutputEncoding` 设成了 UTF-8（这是本仓库的既有做法，见 `_维护须知.md` 第二节）。

> ⚠️ **无法在本轮实测的部分（诚实标注在第 12 节）**：**探针自己改了终端的解码方式**，
> 所以"不改任何设置、直接在 cmd 里看会看到什么乱码"这个具体的乱码串，**本轮没有采到**。
> 你可以这样自己验（**不依赖本讲义**）：
>
> ```powershell
> # 1) 看当前活动代码页
> chcp
> # 2) 编译一个输出中文的程序（用 /utf-8），在 cmd 里直接运行它，看显示什么
> # 3) 再 chcp 65001 之后运行同一个 exe，对比显示
> ```
>
> **判据**：如果同一个 `.exe` 在两种代码页下显示不同，就证明"终端代码页"是运行期独立的一件事。

**两个额外提醒**：

| 现象 | 原因 |
|---|---|
| 把输出重定向到文件，中文是对的；在终端里看是乱码 | 这正是"字节没问题、解码方式有问题"的典型症状 |
| 用 `printf` / `cout` 打印中文时混着 `\r\n` | Windows 文本模式会做换行转换（第 7.4 节讲 `std::ios::binary` 时提过） |

### 9.5 一个隐藏的输入字符：文件开头的 BOM

**先说一个本轮实测的反面结论**：`Python 3.13.15` 的
`Path.write_text("42\n", encoding="utf-8")` **不写 BOM**（本机实测字节是 `34 32 0D 0A`），
只有 `encoding="utf-8-sig"` 才会写（`EF BB BF 34 32 0D 0A`）。
**所以不要把"Python 写文件会带 BOM"当成事实**——这取决于产生文件的是哪个工具、哪个开关。

**但 BOM 真的会咬人**：很多 Windows 程序（记事本"另存为 UTF-8"就是典型）**会**在文件开头写下
`EF BB BF` 这三个字节。而 **`cin` 和 `ifstream` 都不会跳过它**——它就是输入的第一个字符。

下面这段程序和前面 `ch09_mix_getline` 是同一个形状，只是输入文件开头多了三个字节：

<!-- example:ch09_bom_int -->
```cpp
#include <iostream>
#include <string>

int main() {
    int n = -1;
    std::string s;
    std::cin >> n;
    std::getline(std::cin, s);
    std::cout << n << ' ' << std::cin.fail() << ' ' << '[' << s << ']' << '\n';
}
```

<!-- stdin:ch09_bom_int -->
```text
42
Zhang San
```

<!-- result:ch09_bom_int -->
```text
42 0 []
```

**注意这一份输入是不带 BOM 的**（探针记录的字节就是 `34 32 0A 5A 68 61 6E 67 20 53 61 6E 0A`），
所以 `>>` 正常读到 42，而紧跟的 `getline` 只读到那个换行符 → 空串（`fail` 是 0）。
**这一块是给自动比对用的基线。**

**带 BOM 的那一次只能在探针里看**（`tmp/ch09_probe_result.txt` 的 `x_bom_first_int`）：

```text
--- stdin（原始字节）--- EF BB BF 34 32 0A 5A 68 61 6E 67 20 53 61 6E 0A
--- stdout ---
n=0 fail=1 []
```

**同一份"人类可读内容"，只因为开头多了三个字节，第一次数值提取直接失败**：

| 输入开头 | `>> n` 的结果 |
|---|---|
| `34 32`（`42`） | `n = 42`，`fail = 0` |
| `EF BB BF 34 32`（BOM + `42`） | **`fail = 1`** |

> ⚠️ **这个实验为什么没有 `example` 标记**：Markdown 代码块里表示不出那三个不可见字节，
> 写不进去（这一节初稿曾试图直接嵌进去，实测发现写文件时 BOM 字符被丢掉了）。
> 想自己复现，用一行 Python 就够了：
>
> ```python
> open("input.txt", "wb").write(b"\xef\xbb\xbf42\nZhang San\n")
> ```
>
> 然后把 `ch09_bom_int` 编译出来的 `main.exe < input.txt` 跑一遍，对比上面那张表。

> ⚠️ **两个教训**：
>
> 1. **输入数据里可能有你看不见的字符**。程序读到的第一个字符未必是你以为的那个。
>    用十六进制看一眼输入文件，比盯着代码猜快得多。
> 2. **"读整数失败"和"读到 0"分不清**——第 5.5 节说过这件事，这里是它在真实数据上的再现：
>    带 BOM 时打印的是 `n=0`，而它初始化成 `-1`，**只有 `fail=1` 说得清发生了什么**。
>
> 处理：要么让产生文件的一方**不写 BOM**；要么在程序里先检查并跳过那三个字节。

## 10. 本章自测

**1.** `const char* p = "abc";` 和 `char arr[] = "abc";` 这两行里，`sizeof(p)` 和 `sizeof(arr)` 各是多少？为什么？

<details><summary>答案</summary>

本机（64 位）实测：`sizeof(p)` 是 **8**，`sizeof(arr)` 是 **4**。

- `p` 是**指针**，`sizeof` 量的是地址的大小（本机 8 字节），和它指向几个字符无关。
- `arr` 是**数组**，`"abc"` 初始化它时会写入 `'a' 'b' 'c' '\0'`，所以是 4 个 `char`。

**更重要的延伸**：`sizeof(arr)` 只在 `arr` **还是数组**时有效。
一旦它作为函数参数（退化成指针），`sizeof` 就变成 8 了——第 06 章第 6.2 节讲的就是这个"退化"。

**判据**：`sizeof` 量的是"这个名字代表的对象的类型大小"，而数组和指针是两种不同的类型。
</details>

**2.** 为什么 `p == q`（两个 `"abc"` 字面量）不能用来判断两个字符串内容相同？

<details><summary>答案</summary>

因为它比的是**地址**，不是内容。

```cpp
const char* p = "abc";
const char* q = "abc";
p == q;                  // 比地址：结果由实现决定（本机是 0）
std::strcmp(p, q) == 0;  // ✅ 比内容
```

**本机实测输出是 `0`**（不相等）——但**换一个编译器可能合并字符串字面量而给出 1**。
所以这行代码不只是"错"，而是"**结果不确定**"，属于**实现定义/未指定行为**。

**正确写法**：C 风格用 `strcmp(...) == 0`；C++ 风格就把它们存成 `std::string`，
`==` 会被重载成比较内容。
</details>

**3.** 下面这段代码有问题吗？会打印什么？属于哪一类错误？

```cpp
#include <string>
#include <string_view>
#include <iostream>

std::string_view make() {
    std::string local = "hello";
    return local;
}

int main() {
    std::string_view v = make();
    std::cout << v << '\n';
}
```

<details><summary>答案</summary>

**有问题，属于未定义行为（生存期类）。**

`make()` 里的 `local` 是局部对象，函数返回时**已经析构**——它占的存储已经不是你的了。
返回的 `string_view` 仍然记着那块地址和长度，于是 `main` 里打印的是**已释放的存储**。

**它"看起来能工作"**：本机实测同类示例里 `bad.size()` 打印出了 `22`（正确的长度），
因为长度字段在对象销毁前就抄进视图里了。**这恰恰是最危险的地方**——它让你以为代码是对的。

**修法**：
- 返回 `std::string`（拥有者必须活过视图）；
- 或者让被指对象由调用方提供：`std::string_view make(std::string& owner)`。

**判据**：`string_view` 的生命周期必须**严格短于**它指向的对象。跨函数返回视图，几乎总是错的。
</details>

**4.** `std::string_view::substr` 和 `std::string::substr` 有什么本质区别？

<details><summary>答案</summary>

- `std::string::substr(pos, n)` **返回一个新的 `std::string`**：分配内存、拷贝字符，**O(n)**。
- `std::string_view::substr(pos, n)` **返回一个新的视图**：只改首地址和长度，**不拷贝字符，O(1)**。

本机实测 `ch09_sv_basic` 里，`sv.substr(0, 5)` 得到的 `word` 与 `sv` 的 `data()` **相同**（打印 `1`）——
证明没有拷贝，两个视图指着同一块缓冲区。

**这也是 `string_view` 的价值**：切分大文本时几乎零成本。
**代价**：视图不拥有数据，所以它必须比数据活得短（上一题）。
</details>

**5.** 为什么说"读到 0"不能证明"读成功了"？

<details><summary>答案</summary>

因为**读取失败时，数值提取会把这个数置为 0**（而字符串提取则不修改目标）。

看第 5.5 节的实测：`std::istringstream in("abc 42 hello"); int n = -1; in >> n;`
打印出来 `n` 是 **0**（不是 -1），而 `fail()` 是 **1**。

**所以判据是**：

```cpp
int n = 0;
if (std::cin >> n) {
    // ✅ 这里用 n 是安全的
} else {
    // 读失败了，n 不可信
}
```

**同类事实**：`getline` 失败时**不修改**目标字符串（实测 `[sentinel] 1`，字符串还是哨兵值）。

**为什么这条重要**：输入是外部数据，格式永远可能有意外。把"值"和"流状态"分开检查，
是让程序在坏输入下还能报错而不是静默算错的关键。
</details>

**6.** 为什么 `cin >> age` 之后的 `getline` 拿到的是空串？给两种修法。

<details><summary>答案</summary>

因为 `>>` 读数字时**读到数字结束就停，把分隔它的那个换行符留在缓冲区里**。
`getline` 的规则是"读到 `\n` 为止"，于是它读到的第一个字符就是那个 `\n`，结果自然是空串。

本机实测（输入 `"42\nZhang San\n"`）：输出 `42 [] 0`——名字是空的，长度 0。
再跑一次 `getline` 就拿到 `Zhang San`（实测 `42[] [Zhang San]`）。

**修法一：`ignore` 掉那一行剩下的内容**

```cpp
std::cin >> age;
std::cin.ignore(std::numeric_limits<std::streamsize>::max(), '\n');
std::getline(std::cin, name);
```

**修法二（推荐）：全程用 `getline`，再在内存流里拆**

```cpp
std::string line;
std::getline(std::cin, line);
std::istringstream iss(line);
iss >> age >> name;
```

**修法三**：`std::getline(std::cin >> std::ws, name);`——但会连有意义的前导空格一起吃掉。

**判据**：同一个流上不要混用 `>>` 和 `getline`。
</details>

**7.** 打开一个不存在的文件，`std::ifstream in("nope.txt");` 会怎样？怎么正确检查？

<details><summary>答案</summary>

**它不抛异常**，只是把流置成失败态。本机实测（`ch09_file_open_fail`）：

```text
0 1 1        ← is_open() = 0，fail() = 1，!in = 1
0            ← 从没打开的流里 getline 失败
1            ← fail() 仍是 1
0 1          ← 往不存在的目录建文件：同样 fail
```

**正确检查**（三选一，语义等价）：

```cpp
if (!in) { /* 打开失败 */ }
if (in.fail()) { /* 同上 */ }
if (in.is_open()) { /* 成功 */ }
```

**为什么"不检查"很危险**：后面每一次读都静默失败，变量保持原样，程序若无其事地跑完——
你只会看到"程序没输出"，不知道该去查哪里。

**想让失败抛异常**：`in.exceptions(std::ios::failbit);` 之后 `open` 失败会抛
`std::ios_base::failure`（实测消息是 `ios_base::failbit set: iostream stream error`，
**这是库自己写的文本，别拿它做判断**）。
</details>

**8.** `out << "abc";` 之后立刻去读那个文件，为什么长度是 0？

<details><summary>答案</summary>

因为数据还躺在**流对象的缓冲区**里，没有落到文件上。本机实测（`ch09_file_flush`）：

```text
0     ← 写完 "abc"，文件 0 字节
3     ← flush() 之后才是 3 字节
1     ← close() 之后再写的，会把 fail() 置起
```

**三个操作的准确区别**：

| 操作 | 做什么 |
|---|---|
| `flush()` | 把流缓冲推给操作系统 |
| `close()` | 先 flush，再释放文件句柄 |
| 析构 | 如果还开着，等价于 close |

**由此得到两条实践规则**：
1. **别写裸的 `out.close()`**——交给析构，异常路径也安全（RAII）。
2. **`close()` 之后不要再碰这个流**：不崩，但什么也不会写，而且 `fail()` 会变成 1。
</details>

**9.** `std::printf("%d\n", big)` 里 `big` 是 `long long`（值 4294967297），会怎样？这属于哪一类问题？

<details><summary>答案</summary>

**编译只给一条警告**（本机 `/W4` 实测）：

```text
main.cpp(5): warning C4477: “printf”: 格式字符串“%d”需要类型“int”的参数，但可变参数 1 拥有了类型“__int64”
```

**运行结果本机实测是 `1`**（不是 4294967297）：`%d` 让 `printf` 只取低 4 字节，
而 `4294967297` = `0x1_0000_0001`，低 4 字节就是 `1`。

**归属**：这是**未定义行为**（格式串与实参类型不匹配），不是"输出格式不对"。
本机这次给出 `1` 只是当前调用约定下的结果，换成参数更多、参数类型不同、换编译器都可能不同。

**根因**：格式串是**运行期才解析的一串字符**，编译器没法在类型系统里把 `%d` 和实参联系起来，
只能在 `/W4` 下事后警告。**这正是 `std::format`（C++20 起）想解决的问题**：
它把格式串在编译期解析、并把类型检查做进模板里。

**对比**：同样一行用流写 `std::cout << big;` 会打印 `4294967297`，因为 `<<` 是编译期重载决议。
</details>

**10.** 本机控制台活动代码页是 936。一个已经用 `/utf-8` 编译好的程序输出中文字符串，
在 cmd 里直接运行显示乱码——是程序错了吗？

<details><summary>答案</summary>

**不一定。这时要分清三件事**：

| # | 是什么 | 什么时候 |
|---|---|---|
| 1 | 源文件编码 | 编译期 |
| 2 | 执行字符集 | 编译期 |
| 3 | **终端代码页** | **运行期** |

**"能编过、字符串字节也对，但显示乱码"就是第 3 件事**：
程序写出的是 UTF-8 字节（本机实测 `E4 B8 AD E6 96 87` = 「中文」），
而终端按 **GBK（代码页 936）**去解这些字节 → 乱码。

**怎么确认是终端的问题**：把输出**重定向到文件**，用十六进制看一眼。
如果文件里的字节是对的，程序就没问题，问题在"谁在读这些字节"。

**怎么自己验**：

```powershell
chcp                    # 看当前代码页（本机是 936）
.\main.exe              # 直接运行，观察是否乱码
chcp 65001              # 切成 UTF-8
.\main.exe              # 同一个 exe 再跑一次，对比
```

同一个 `.exe` 在两种代码页下显示不同，就证明这是运行期的事。

> **本讲的诚实边界**：探针脚本自己把 `[Console]::OutputEncoding` 设成了 UTF-8，
> 所以**本轮没有采到"默认 cmd 下具体会显示成什么乱码串"**（见第 12 节）。
> 上面这段"怎么自己验"是可执行的验证路径，不是我实测过的输出。
</details>

## 知识结构回收

不是"本章总结"，而是把这章挂回整张地图。

**你现在会的（按数据流的顺序）**：

```text
① 内存里怎么表示一段文字
   const char*（地址 + 靠 '\0' 收尾）  →  std::string（拥有缓冲区）  →  string_view（只看不拥有）
                         ↑ 三者的关系在第 1.5 节那张表里定死

② 文字怎么和别的类型互换
   stoi / stod（字符串→数，靠异常报错）   to_string / ostringstream（数→字符串）

③ 文字怎么进出程序
   流 = 缓冲区 + 状态位  →  cin / cout / cerr / stringstream  →  ifstream / ofstream（RAII 管句柄）
   →  printf（格式串，类型不安全）/ 流（类型安全）/ std::format（C++20 起，两者兼得）

④ 这一路上四个真实的坑
   >> 与 getline 混用      → 第 8 节
   流失败态是粘的          → 第 5.5 节
   string_view 悬垂        → 第 3.2 节
   源文件编码 vs 终端代码页 → 第 9 节
```

**三条贯穿全书的线在这章的样子**：

| 线 | 在本章的体现 |
|---|---|
| **谁拥有资源** | `std::string` 拥有缓冲区、`fstream` 拥有文件句柄，都用 RAII 归还；`string_view` / `const char*` **不拥有**，所以它们有悬垂风险 |
| **生存期** | 第 3.2 节那个悬垂例子，本质就是第 06 章第 8 节「栈与堆：对象存在哪里、活多久」讲的规律换了个对象 |
| **"看起来等价"的陷阱** | `p == q` 比地址、`to_string` 固定 6 位小数、`setw` 一次性而 `setfill` 粘着、`>>` 与 `getline` 对空白的处理不同——**四组都给了对比表** |

下一章是 **`10_容器与算法.md`**（覆盖表见 [`00_知识点总览.md`](00_知识点总览.md) 第 9 层）。

为什么是它：这一章你已经反复用到了"一串东西"——`std::string` 是**一串字符**、
`std::string_view` 是**一段只读的字符**、`vector` 前面几章也露过脸。
你还没有正式学过"怎么遍历一串东西""怎么在一串东西里查找排序"，
而这两件事在 `std::string` 上你已经用过它们的字符串特化版（`find` / `substr`）。
下一章把 `find` / `substr` 背后的那套东西（**迭代器 + 算法**）正式讲清楚：
`std::string` 会作为"容器的一个特例"重新出现一次。
