>

## 三、第一步：定"唯一主分类轴"（**这一步不能省**）

> **同一级标题必须属于同一个分类维度。** 这是本项目最核心的一条规矩。

**做法**：

1. 先写出这一章要解决的核心问题（一句话）
2. 列出**可选的分类维度**（至少三个），例如：按语法入口分 / 按机制分 / 按用途分 / 按难度分
3. **选定唯一一个**当主轴，说明为什么其它不行
4. 把每个知识点**归类**到：入口 / 共用规则 / 独有能力 / 机制 / 用途 / 特例 / 进阶
5. **只看你排出来的目录，能不能看懂这一章的知识结构？** 不能就回去改目录，**别开始写正文**

**反面教材**（混了三根轴，禁止）：

```text
3.1 f-string           ← 语法入口
3.2 小数精度            ← 显示功能
3.3 str.format()       ← 语法入口
3.4 底层 __format__     ← 底层机制
```

**正确做法**（先分轴，再展开）：

```text
格式化
├─ 格式化入口        （f-string / format / %）
├─ 共用格式规则      （精度 / 宽度 / 对齐 / 进制）
├─ 各入口独有能力
└─ 底层机制          （__format__）
```

**样板章怎么做的**：第 02 章的主轴是"**一个命名对象从创建到使用需要确定哪些信息**"，
于是顺序是 对象/类型/值（是什么）→ 类型系统（装什么）→ 声明定义（怎么引进名字）→
初始化（怎么给初值）→ 推导与限定符 → 作用域 → 转换 → 命名空间 → 字面量 → 风格。

## 五、第三步：按样板写正文

### 5.1 章首结构（三样，顺序固定）

```markdown
# NN · 章节标题

> 覆盖表条目：X.1 xxx ｜ X.2 xxx ｜ ...
>
> 一句话说明这一章要解决什么。

> **本章目录**
>
> - [0. ...](#0.%20...)
> - ...
> - [N. 本章自测](#N.%20本章自测) 🔧
> - [N+1. 本章覆盖对账](#N+1.%20本章覆盖对账) 🔧
> - [N+2. 诚实标注](#N+2.%20诚实标注) 🔧

---

## 0. 先记住的 N 件事        ← 推荐。给整章的"锚点"，最后一条要是最容易踩的坑
```

### 5.2 锚点规则（**机检会查，写错就报**）

```
锚点文本 = `##` 后面的标题原文，其中：
    空格    → %20
    ( 和 )  → \( 和 \)
    其余字符（中文、`、：、/、、、「」）原样保留
🔧 必须写在链接外面
```

规则出处是 Obsidian 本体源码（已核实）：`replace(/ /g,"%20").replace(/([()])/g,"\\$1")`。

> ⚠️ **`|` 在标题里会导致锚点处理有歧义**——**不要在 `##` 标题里用竖线**。

### 5.3 正文写法（六条硬要求）

1. **先给最小具体例子，再抽象**。不要用纯符号开场。
2. **每个知识点分开写 What / How / Why / Under the hood 四层**，不要混在一段里。
3. **关键语法符号要在当前语境交代清楚**。样板章第 1 节把 `::` 的两种用法列了表；
   你也要交代你这一章涉及的符号（`*` `&` `->` `.` `[]` `()` `{}` 等）。
4. **相近概念主动给对比表**，不要并列写几段定义。
5. **讲执行流程**：涉及控制的章节要写"程序先做什么、再跳到哪里"。
   样板章第 8.2 节有一段 `执行轨迹` 的代码块，**照这个形式来**。
6. **坑要写清"程序实际怎么解释它"以及错误属于哪一类**
   （语法 / 类型 / 控制流 / 作用域 / 链接 / **未定义行为**）。

### 5.4 代码块标记（**判据很重要**）

```markdown
<!-- example:chNN_键名 -->
```cpp
...
```

<!-- result:chNN_键名 -->
```text
真实输出
```
```

| 标记 | 用途 |
|---|---|
| `<!-- result:key -->` | 逐字全等比对 |
| `<!-- run-expect:key -->` | 前缀匹配（**尽量别用**，见下） |
| `<!-- stdin:key -->` | 喂输入 |
| ```` ```cpp compile-fail ```` | 断言"必须编译失败" |

**判据：这一段能不能单独存成一个 `main.cpp`，编译后得到确定的输出？**

- 能 → **加标记**
- 不能（片段、伪代码、汇编清单、诊断文本、多文件示例）→ **不加**，保持普通 ```` ```cpp ````

> ⚠️ **输出里含不确定内容时（路径、时间、地址），不要用 `run-expect` 打折——直接不加标记。**
> 这是 Codex 在实战中纠正我的地方：**输出不确定的示例不该进自动基线**。
> 需要展示它就跑一次，把真实结果以普通 ```` ```text ```` 贴在旁边，并说明它为什么不能自动比对。

### 5.5 章末三件验收物（缺一件即未完成）

**（1）本章自测**：5～10 题，`<details><summary>答案</summary>` 折叠答案。
**至少一题考 UB / 实现定义 / 平台差异**——C++ 里这是最该考的地方。

**（2）本章覆盖对账**：

```markdown
| 覆盖表条目 | 本文章节 |
|---|---|
| X.1 知识点名 | 第 N 节 |
```

**每一条都要指到正文里真实存在的小节。** 判据是"**正文里找得到**"，不是"表里写了"。

**（3）诚实标注**：

```markdown
| 说法 | 状态 | 怎么自己验 |
|---|---|---|
| xxx | ✅ 本轮实测 | 跑哪个示例 |
| yyy | ⚠️ 未实测（说明为什么） | 怎么验 |
```

**这一张表是"哪些话你可以信"的清单。** 凡是探针没跑到的，**必须标 ⚠️**，不许含糊过去。

## 八、交回时要报告什么

```text
【写了什么】文件名 + 节数 + 一句话说主轴
【实测证据】探针脚本路径 + 编译验证的数字（块数 / 通过 / 不符合 / 警告总数）

**不要**写"已全面检查，没有发现问题"。要说"`verify_cpp.py` 12 块、全部一致、0 不符合、共 4 条警告"。
