## 0. 先记住的七件事

1. **一个函数由两部分组成：调用者需要知道的（名字、参数类型、返回类型）和不需要知道的（怎么实现的）。** 这部分叫**声明**（declaration），也就是常说的**函数原型**（function prototype）。

   ```cpp
   int add(int a, int b);        // 声明：到此为止，编译器知道的全部
   ```

2. **声明可以有很多份，定义只能有一份。** 这条规则在"一个 `.cpp` 内部"和"整个程序"两个尺度上都成立，只是后果不同（第 1 节讲局部，第 9 节讲全局）。
3. **参数默认按值传递，也就是会拷贝一份。** 函数里改形参，改的是副本，调用者的实参一点没动。
4. **`inline` 的现代含义跟"内联展开"没关系。** 它的实际作用是"**允许多个翻译单元里存在同一份定义**"；要不要真的把函数体展开成指令，现在的优化器自己会决定。
5. **重载看的是参数列表，返回类型不算数。** `int f();` 和 `double f();` 不是重载，是同名冲突。
6. **lambda 的捕获列表决定闭包对象里装的是"副本"还是"引用"。** 按引用捕获局部变量、然后拿它活过那个局部变量的作用域，得到的是一块已经回收的内存——这是**未定义行为**。
7. **递归每深入一层就压一个栈帧，栈是有限的。** 递归写错方向不是"跑得慢"，是**进程直接被杀掉**。本章第 6 节有真实的退出码。

> 如果只记一条，记第 7 条。它和"未初始化变量读出来是垃圾值"不一样：那还只是读到错的数据，**栈溢出是程序当场死掉**。

## 1. 函数的三件套：声明、定义、调用

第 02 章第 4 节已经讲过变量的"声明 vs 定义"。函数把同一组概念摆得更清楚，因为**函数可以不写函数体就先用**。

### 1.1 最小例子：先用后写

<!-- example:ch05_decl_def_call -->
```cpp
#include <iostream>

int add(int a, int b);        // 声明（原型）

int main() {
    std::cout << add(2, 3) << '\n';
    std::cout << add(add(1, 2), 3) << '\n';
}

int add(int a, int b) {       // 定义
    return a + b;             // 返回
}
```

<!-- result:ch05_decl_def_call -->
```text
5
6
```

**执行轨迹**（本章的规矩：讲清程序到底先做什么）：

```text
1. main 里遇到 add(2, 3)
2. 编译器查已经见过的声明：int add(int, int)  ← 只看第 3 行就够了
3. 检查参数：2、3 都是 int → 与形参 int、int 匹配
4. 检查用途：结果被 << 用掉，int 能直接打印 → 编译期检查通过
5. 生成一条"调用 add"的指令（此时 add 的函数体在哪还没关系）
   ── 以上都发生在编译期 ──
6. 运行到这一行：把 2、3 交给 add，跳到 add 的代码
7. add 执行 return a + b，把 5 交回
8. 回到 main 的第 6 行，继续做 << 打印
9. 第二行同理，只是参数里本身又嵌了一次 add 调用（先算里层）
```

**第 6 步跳到哪儿，是链接器的工作**（第 01 章第 5 节讲过链接的三件事）。编译 `main` 的时候，编译器并不需要看到 `add` 的机器码——它只要知道"有这么个函数、签名是这样"。把"知道有"和"知道怎么做"分开，正是函数能拆到多个文件里的前提。

### 1.2 一个函数定义由六块组成

以第 1.1 节那个 `add` 为例，从左到右逐块对照：

| 块 | 本例子里的内容 | 作用 | 能不能省 |
|---|---|---|---|
| 返回类型 | `int` | 交回给调用者的东西的类型 | ❌ 不能省（C++ 里） |
| 名字 | `add` | 调用时写的标识符 | ❌ |
| 形参列表 | `(int a, int b)` | 调用者必须按几个、什么类型的值来 | `()` 表示不要参数 |
| 函数体 | `{ return a + b; }` | 具体怎么算 | 声明里没有它 |
| `return` 语句 | `return a + b;` | 把值交回并结束这一次调用 | 返回 `void` 时可以不写 |
| `;` | 跟在 `}` 后面那行**没有** | 见下方 ⚠️ | — |

> ⚠️ **坑（语法类）**：**函数定义后面不要加分号。**
> ```cpp
> int add(int a, int b) { return a + b; }    // ✅
> int add(int a, int b) { return a + b; };   // ⚠️ 多余的 ;
> ```
> 多出来那个 `;` 是一个"空声明"，编译器一般只是忽略它。但如果你**以为定义自带分号**，那么在写类定义的时候就会习惯性在 `}` 后面加 `;`——那一条在第 07 章里是**必须加的**（`};`），而**在普通函数后面是错的**。两种 `}` 的规矩不一样，别靠手感。

### 1.3 符号对照：这一章会反复出现的几个符号

| 符号 | 在本章语境里读作 | 例 |
|---|---|---|
| `()` | 两条不同的意思，看位置：**跟在名字后面**是"调用"；**在声明里**是"形参列表" | `add(1, 2)` vs `int add(int, int)` |
| `&` | 声明一个**引用**（不是取地址） | `void f(int& x)` |
| `*` | 声明一个**指针**类型 | `int (*p)(int, int)` |
| `->` | 写返回类型时替代 `return` 的位置，或访问指针指向的成员 | `[](int x) -> int { return x; }` |
| `[]` | 在 lambda 里是**捕获列表** | `[x](int y) { return x + y; }` |
| `::` | 限定名字在哪个命名空间里（第 02 章第 8 节） | `std::function` |

> **最容易混的是第一条**：`f(x)` 在不同位置分别表示"调用 f"和"f 接受一个 x 类型的参数"。读代码时先用"它出现在名字左边还是右边"分一次，再判断。

### 1.4 调用点写错一个参数，编译器会拦住

调用一个函数时，编译器要检查三件事：**参数个数、参数类型能不能接受、返回值有没有被正确使用**。三件事各有对应诊断。这是"静态类型语言在函数上收的第一笔钱"。

<!-- example:ch05_fail_wrong_arity -->
```cpp compile-fail
int add(int a, int b) { return a + b; }

int main() {
    return add(1);
}
```

真实诊断（MSVC 14.51，`/W4`，本机实测）：

```text
main.cpp(4): error C2660: “add”: 函数不接受 1 个参数
```

**注意它说的是"函数不接受 1 个参数"，而不是"少给了 b"。** 编译器在**调用点**只知道签名，它把整句话当作一个"参数列表不匹配"的事件来报。

### 1.5 没有声明就想调用

<!-- example:ch05_fail_call_before_decl -->
```cpp compile-fail
int main() {
    return add(1, 2);
}

int add(int a, int b) { return a + b; }
```

真实诊断：

```text
main.cpp(2): error C3861: “add”: 找不到标识符
```

**这里最该注意到的是：`add` 明明就在下面几行写着。** 编译器的名字查找是**从上往下顺序做的**，它在第 2 行时还没见过 `add`，所以报"找不到标识符"（identifier not found），而不是"没有定义"。

> ⚠️ **判据**：`C3861`（找不到标识符）和 `LNK2019`（无法解析的外部符号）看起来都是"没找到函数"，但**归属完全不同**：
> - `C3861` 是**编译期**的**名字查找**失败：编译器不知道有这么个名字。修法是把声明往上挪，或写进头文件。
> - `LNK2019` 是**链接期**的**符号解析**失败：编译器知道有这么个名字（声明见过了），但整个程序里没有它的定义。修法是把那个 `.cpp` 加进编译。
>
> **先看错误前缀**：`C` 开头是编译器，`LNK` 开头是链接器（第 01 章第 8 节讲过怎么读诊断）。

## 2. 默认实参：少写一个参数时发生什么

**默认实参**（default argument）让函数的一部分参数可以省略。它解决的是一个很常见的需求：**大部分调用只用得上前几个参数，只有少数调用需要调整后面的。**

### 2.1 最小例子

<!-- example:ch05_default_arg -->
```cpp
#include <iostream>

int power(int base, int exp = 2) {
    int r = 1;
    for (int i = 0; i < exp; ++i) {
        r *= base;
    }
    return r;
}

int main() {
    std::cout << power(5) << '\n';
    std::cout << power(2, 10) << '\n';
}
```

<!-- result:ch05_default_arg -->
```text
25
1024
```

**读法**：`power(5)` 和 `power(5, 2)` 是**同一个函数的两次调用**，不是两个函数。默认实参不是重载的语法糖在编译期展开成另一个函数，而是"**调用点少写的那个实参，编译器替你填上**"。

### 2.2 关键机制：默认实参在调用点求值

这一条经常被忽略，而且它能直接咬人。看一个默认实参**带副作用**的例子：

<!-- example:ch05_default_arg_eval -->
```cpp
#include <iostream>

int counter = 0;
int next() { return ++counter; }

void report(int value, int tag = next()) {
    std::cout << value << ' ' << tag << '\n';
}

int main() {
    report(10);
    report(20);
    report(30, 0);
    report(40);
}
```

<!-- result:ch05_default_arg_eval -->
```text
10 1
20 2
30 0
40 3
```

**三个观察**：

| 调用 | 打印的 `tag` | 说明 |
|---|---|---|
| `report(10)` | 1 | 第一次省略 → 调用了一次 `next()` |
| `report(20)` | 2 | **又**调用了一次（不是复用了上次的 1） |
| `report(30, 0)` | 0 | 显式给了，`next()` **根本没被调用**（所以 `counter` 还是 2） |
| `report(40)` | 3 | 从 2 递增到 3 |

**所以"默认值"这个名字有点误导**：被省略的实参是在**每次调用时**重新求值的表达式，不是一份预先算好的常量。`next()` 一共被调用了 3 次。

> ⚠️ **坑（语义类）**：把默认实参写成"每次都应该一样的东西"，但它其实每次都重算。
> 比如 `void log(const std::string& msg, std::size_t stamp = now());`——每个省略 `stamp` 的调用都会取**当时**的时间。
> 这有时正是你要的（时间戳），有时是 bug（你以为它是"函数定义时定下的默认值"）。
> **判据**：默认实参是一个**表达式**，它的求值发生在**调用点**，用的是**调用点能看见的名字**。

### 2.3 三条硬规则

**规则一：默认实参必须靠右排。**

<!-- example:ch05_fail_default_nontrailing -->
```cpp compile-fail
int g(int a = 1, int b) {
    return a + b;
}

int main() {
    return g(1, 2);
}
```

真实诊断：

```text
main.cpp(1): error C2548: “g”: 缺少形参 2 的默认实参
```

**为什么**：如果允许 `int g(int a = 1, int b)`，那么写 `g(5)` 时编译器无法判断 5 是给 `a` 还是给 `b`（实参是按位置从左边开始填的）。**"靠右"规则是"按位置传参"这个设计的直接后果。**

**规则二：同一个参数的默认值只能给一次**（通常在声明里给）。

<!-- example:ch05_fail_default_redefined -->
```cpp compile-fail
int h(int a, int b = 2);

int h(int a, int b = 2) {
    return a + b;
}

int main() {
    return h(1);
}
```

真实诊断：

```text
main.cpp(3): error C2572: “h”: 重定义默认参数 : 参数 1
```

**正确写法**是只在声明里给一次：

```cpp
int h(int a, int b = 2);              // ✅ 默认值给在这里
int h(int a, int b) { return a + b; } // 定义里不再重复
```

> **为什么偏要这样**：一个函数的声明可以在多个翻译单元里各出现一次（第 9 节讲）。如果每次都给默认值，不同翻译单元可能给出**不同的默认值**，那"省略参数时用哪个"就没人说得清了。标准干脆规定：**同一个参数在同一个作用域里只能被指定一次默认值。**

**规则三：默认实参不能参与重载决议的"区分"。**

```cpp
void f(int a, int b = 0);
void f(int a);              // ⚠️ 这两者不是"能共存的重载"
f(1);                       // 编译错误：调用不明确
```

**因为 `f(1)` 两个都能接受**：前者用默认值，后者精确匹配。编译器不认为"用了默认值的那个更差"——它认为两个候选同样可行，于是报 `C2668`（第 3 节会看到这条诊断的原文）。

> **判据**：**默认实参是"调用时可以少写"，不是"声明了一个新函数"。** 想让"少写"区分出行为，应该用重载，不要用默认实参叠默认实参。

## 3. 函数重载与重载决议入门

**重载**（overloading）指**同一个名字对应多个函数**，靠参数列表区分。它不是"一个函数根据参数类型做不同的事"（那是动态行为），而是**编译期就从多个候选里挑定一个**。

### 3.1 最小例子

<!-- example:ch05_overload_basic -->
```cpp
#include <iostream>

void show(int x)         { std::cout << "int " << x << '\n'; }
void show(double x)      { std::cout << "double " << x << '\n'; }
void show(const char* s) { std::cout << "cstr " << s << '\n'; }

int main() {
    show(1);
    show(1.5);
    show("hi");
    show('a');
}
```

<!-- result:ch05_overload_basic -->
```text
int 1
double 1.5
cstr hi
int 97
```

**最后一行是本节第一个关键点**：`show('a')` 打印的是 `int 97`，也就是**调用了 `show(int)`**。

**为什么不是 `show(const char*)`（`char` 和 `char` 都是一字节）？** 因为在这三个候选里，`char` 到 `int` 是**整型提升**（第 02 章第 9 节），而 `char` 到 `const char*` **压根不是合法转换**。所以候选其实只剩两个：`int` 和 `double`；而 `char → int` 是提升、`char → double` 是浮点-整数转换，前者更优。

### 3.2 重载决议：编译器按什么挑

编译器选版本的正式过程叫**重载决议**（overload resolution）。入门阶段够用的模型只有三步：

```text
第 1 步  找出候选：所有可见的、同名的函数
第 2 步  筛出可行：实参个数和类型能转换过去的
第 3 步  比出最优：按转换的"代价"分级，越不需要转换越好
         └─ 有唯一的更优者 → 选它
         └─ 没有更优者、或有两个并列最优 → 报错（C2668 调用不明确）
```

**转换的代价从优到劣，入门只需要记住前两级：**

| 级别 | 名字 | 例（实参 `int`，形参如左） |
|---|---|---|
| 1（最优） | **精确匹配** | `int` 形参收 `int` 实参 |
| 1（并列最优） | **提升 / 精确匹配的变体** | `int → long`？不是；但 `char → int` 是提升，与精确匹配同级优先 |
| 2（次优） | **转换**（conversion） | `int → double`、`int → long`、`unsigned → int` |
| 3（最劣） | 用户定义的转换、省略号 `...` | 第 07、13 章才涉及 |

**"精确匹配优先于转换"是这一节最该带走的一句。** 拿它去解释第 3.1 节的输出就全通了。

### 3.3 用一组实参把这条规则验出来

<!-- example:ch05_overload_rank -->
```cpp
#include <iostream>

void f(int)    { std::cout << "int" << '\n'; }
void f(long)   { std::cout << "long" << '\n'; }
void f(double) { std::cout << "double" << '\n'; }

int main() {
    f(1);
    f(1L);
    f(1.0f);
    f(1.0);
    f('a');
}
```

<!-- result:ch05_overload_rank -->
```text
int
long
double
double
int
```

**逐行读这张表**：

| 调用 | 实参类型 | 选中的版本 | 为什么 |
|---|---|---|---|
| `f(1)` | `int` | `f(int)` | 精确匹配 |
| `f(1L)` | `long` | `f(long)` | 精确匹配 |
| `f(1.0f)` | `float` | `f(double)` | 没有 `f(float)`；`float → double` 是**浮点提升**，比 `float → int` 的转换更优 |
| `f(1.0)` | `double` | `f(double)` | 精确匹配 |
| `f('a')` | `char` | `f(int)` | `char → int` 是**整型提升**，压过 `char → long` 和 `char → double` 这两个转换 |

> ⚠️ **坑（类型类）**：注意 `std::cout <<` 打印 `long` 和 `int` 看起来一样，但**选中的是不同函数、可能做不同的事**。
> 如果你的重载里有 `f(long)` 做了和 `f(int)` 完全不同的事（比如一个当时间戳、一个当数量），
> 那么一个**字面量后缀写漏**（`1` 而不是 `1L`）就会静默走到另一个实现上。
> **处理**：让重载各版本**语义一致**（做同一件事的不同类型版本），不要用重载去区分"语义完全不同的操作"——那种情况该取两个不同的名字。

### 3.4 返回类型不参与重载

这是一个必须点名的规则，因为它违反直觉：**两个函数只有返回类型不同，不算重载，算重复定义。**

<!-- example:ch05_fail_return_type_overload -->
```cpp compile-fail
int f() { return 1; }
double f() { return 1.0; }

int main() {
    return static_cast<int>(f());
}
```

真实诊断：

```text
main.cpp(2): error C2556: “double f(void)”: 重载函数与“int f(void)”只是在返回类型上不同
main.cpp(2): error C2371: “f”: 重定义；不同的基类型
main.cpp(5): error C2440: “static_cast”: 无法从“int (__cdecl *)(void)”转换为“int”
```

**第二条 `C2371` 就是"这不算重载，算重定义"的正式说法。**（前两条是根因，第三条是连带的：`f` 已经变成一个"没被成功声明的名字"，后面用它自然也不对。）

**为什么不参与**：看调用点 `f()`。**调用者写调用时不写返回类型**（写了也没用，因为返回值可能直接丢掉、或拿去参与别的运算）。既然调用点分不出你要哪个版本，标准就不能允许这种重载——否则 `f()` 永远无法决议。

> **判据**：**重载靠的是"调用点能看见的区别"。** 返回类型在调用点不可见，所以不算；参数列表在调用点可见，所以算。

### 3.5 两个都同样可行，就是错误

<!-- example:ch05_fail_ambiguous_nullptr -->
```cpp compile-fail
void g(long)       {}
void g(long long)  {}

int main() {
    g(0);           // int 到 long 与 int 到 long long 都是转换：没有更优者
    return 0;
}
```

真实诊断（把 `note` 行也抄下来，它是这条错误最有用的部分）：

```text
main.cpp(5): error C2668: “g”: 对重载函数的调用不明确
main.cpp(2): note: 可能是“void g(__int64)”
main.cpp(1): note: 或    “void g(long)”
main.cpp(5): note: 尝试匹配参数列表“(int)”时
```

**注意 `note` 行**：MSVC 会把"我考虑过哪几个候选"列出来。**这类 `note` 是解决重载问题的第一手材料**——它直接告诉你候选集合，你就不必猜了。

**为什么会不明确**：`int → long` 和 `int → long long` 都是"整型转换"，**标准不给它们分高下**，所以两个候选并列最优。

<!-- example:ch05_fail_ambiguous_call -->
```cpp compile-fail
#include <iostream>

void f(int)  { std::cout << "int" << '\n'; }
void f(long) { std::cout << "long" << '\n'; }

int main() {
    f(1u);
}
```

真实诊断：

```text
main.cpp(7): error C2668: “f”: 对重载函数的调用不明确
```

**`1u` 是 `unsigned int`**，它到 `int` 和到 `long` 都是转换，同样并列。

> ⚠️ **坑（类型类）**：`f(1u)` 报"不明确"，可你在源码里写的时候**看不出 `1` 和 `1u` 有多大区别**。
> 这是"字面量的类型"（第 02 章第 12 节）与"重载决议"两件事撞在一起的结果。
> **处理**：一个函数如果既有 `int` 版本又有 `long` 版本，就顺手把 `unsigned`/`long long` 版本也补上，
> 或者一开始就只留一个版本、让调用方显式 `static_cast`。

### 3.6 `nullptr` 与 `0`：一个必须实测才敢写的例子

`0` 在 C++ 里有一种特殊身份：它既是 `int` 字面量，又**是空指针常量**（null pointer constant）。这让"传 `0` 到底走了哪个重载"变成一个真问题。`nullptr` 是 C++11 起引入的、类型为 `std::nullptr_t` 的**专门的空指针字面量**（第 02 章第 12 节列过它的类型）。

实测先摆出来——**同一次编译、同一组重载，三种实参走到三个不同的版本**：

<!-- example:ch05_nullptr_zero_pick -->
```cpp
#include <iostream>

void f(int value)        { std::cout << "int " << value << '\n'; }
void f(const char* text) { std::cout << "cstr " << (text ? text : "(null)") << '\n'; }

int main() {
    const char* p = nullptr;
    f(p);           // p 的类型就是 const char*：精确匹配
    f(nullptr);     // nullptr 能转成 const char*，不能转成 int（见下面那个例子）
    f(0);           // 0 是 int 字面量：精确匹配 int
    f(NULL);        // NULL 在 MSVC 上就是 0，于是同样选了 int
}
```

<!-- result:ch05_nullptr_zero_pick -->
```text
cstr (null)
cstr (null)
int 0
int 0
```

**这张输出表本身就是一条规则**：

| 实参 | 选中的重载 | 为什么 |
|---|---|---|
| `const char* p` | `f(const char*)` | 精确匹配 |
| `nullptr` | `f(const char*)` | `nullptr` **不能**转成 `int`（它不是整数），只能走指针这一条 |
| `0` | `f(int)` | `0` 是 `int` 字面量，**精确匹配**压过"`0` 当空指针常量"那条路 |
| `NULL` | `f(int)` | **本机 MSVC 上 `NULL` 就展开成 `0`**，所以命运和上一行一样 |

**换一组重载，`nullptr` 的落点就变了**——因为它能转成 `bool`，而 `bool` 是整型：

<!-- example:ch05_nullptr_bool -->
```cpp
#include <iostream>

void g(bool flag) { std::cout << "bool " << flag << '\n'; }
void g(int value)  { std::cout << "int " << value << '\n'; }

int main() {
    g(nullptr);
    g(0);
}
```

<!-- result:ch05_nullptr_bool -->
```text
bool 0
int 0
```

**`g(nullptr)` 选了 `bool`，`g(0)` 选了 `int`。** 两条规则合起来解释得通：`nullptr` 到 `bool` 是标准转换、到 `int` 不是；`0` 到 `int` 是精确匹配、到 `bool` 是转换。

> ⚠️ **坑（类型类）**：**`f(0)` 和 `f(nullptr)` 可能不是同一个意思。**
> 在 `f(int)` / `f(const char*)` 这一组里，`f(0)` 走整数、`f(nullptr)` 走指针；
> 如果你想表达"空指针"，写 `0` **意思对但会选错版本**。
> **处理**：**要空指针就写 `nullptr`，永远不要用 `0` 或 `NULL`。** 这不是风格洁癖，它会真的改变运行时行为。
>
> **另一面**：正因为 `0` 有两重身份，**它不会报错**——你得到的是一个能编过、跑得通的程序，只是走错了分支。这比编译错误难查得多。

## 4. 参数传递：默认是传值（以及为什么不能只讲传值）

覆盖表在这一条里特意加了一句"**以及为什么不能只讲传值**"。原因很直接：**只见识过传值的写法，你会得出"函数拿不到调用者的东西"这个错误结论**，然后开始到处用全局变量。所以本节分两半：**先把传值讲透**，再**说清本章到此为止的边界在哪、后面的章节补什么**。

### 4.1 传值：函数拿到的是一个副本

<!-- example:ch05_pass_by_value -->
```cpp
#include <iostream>

void bump_value(int x) {
    ++x;
}

int main() {
    int n = 1;
    bump_value(n);
    std::cout << n << '\n';
}
```

<!-- result:ch05_pass_by_value -->
```text
1
```

**执行轨迹**：

```text
1. main 里 n 这块存储里是 1
2. 调用 bump_value(n) → 拿 n 的值（1）去初始化形参 x
   └─ 形参 x 是 main 看不到的、另一块存储
3. ++x 改的是那块新存储 → 它变成 2
4. 函数结束 → x 那块存储被回收
5. 回到 main，读 n → 还是 1
```

**关键认识**：**形参是函数自己的局部对象**，只是**用实参的值初始化**它。这就解释了为什么改了没用。

### 4.2 "拷贝一份"对基本类型和多成员对象不是一回事

`int` 的拷贝就是个机器字，你感觉不到代价。但**值传递是"拷贝整个对象"的意思**，对类类型是实打实的开销。下面用两个打印语句把"到底拷贝了几次"数出来：

<!-- example:ch05_pass_copy_count -->
```cpp
#include <iostream>

struct Tracer {
    Tracer() { std::cout << "ctor" << '\n'; }
    Tracer(const Tracer&) { std::cout << "copy" << '\n'; }
};

void by_value(Tracer) {
    std::cout << "in by_value" << '\n';
}

void by_ref(const Tracer&) {
    std::cout << "in by_ref" << '\n';
}

int main() {
    Tracer t;
    std::cout << "--- by_value ---" << '\n';
    by_value(t);
    std::cout << "--- by_ref ---" << '\n';
    by_ref(t);
}
```

<!-- result:ch05_pass_copy_count -->
```text
ctor
--- by_value ---
copy
in by_value
--- by_ref ---
in by_ref
```

**输出里 `copy` 只出现了一次，位置就在 `by_value` 之前**：

| 调用 | 发生了什么 | 输出 |
|---|---|---|
| `Tracer t;` | 默认构造 | `ctor` |
| `by_value(t)` | **拷贝构造一份**，再进函数 | `copy`、`in by_value` |
| `by_ref(t)` | 没有拷贝，直接进去 | 只 `in by_ref` |

> ⚠️ **坑（性能类）**：**"传值会不会有代价"取决于类型，不取决于函数写得多短。**
> 一个 `Tracer` 只含一个 `int` 时你看不出差别；但一个含 10 万个元素的 `std::vector` 按值传参，
> 每次调用都会**分配并复制 10 万个元素**。这类代码在读的时候完全看不出来贵。
> **判据**：**传值 = 拷贝构造一次。** 心里把每次按值传参翻译成"这里会拷一份"，就够了。

> 📌 **本章的边界（覆盖表那句话的落点）**：下面两件事**本章不讲**，因为它们各自需要一整节的前置知识：
>
> | 要讲的东西 | 去哪看 |
> |---|---|
> | **引用传递**：`void f(int& x)` 为什么不拷贝、能改回调用者 | [`06_引用、指针与内存.md`](06_引用、指针与内存.md) 第 2 节「引用」 |
> | **`const T&` 与移动**：只读又不拷贝的传参方式，以及"拷贝能不能免掉" | [`12_移动语义与资源管理.md`](12_移动语义与资源管理.md) |
>
> **本章你只需要带走一句判断**：**"默认是传值（会拷贝）"知道了，"想要不拷贝"的路在第 06 章和第 12 章。**
> 中间这段距离不要用全局变量去填——那是把问题换个地方藏起来。

### 4.3 引用传递长什么样（只放位置，不展开）

为了不让你误以为"函数改不了调用者"，这里给最小对照。**下面这个例子是第 06 章的内容，此处只作为"路标"出现。**

<!-- example:ch05_pass_by_ref -->
```cpp
#include <iostream>

void bump_value(int x) { ++x; }
void bump_ref(int& x)  { ++x; }

int main() {
    int a = 1, b = 1;
    bump_value(a);
    bump_ref(b);
    std::cout << a << ' ' << b << '\n';
}
```

<!-- result:ch05_pass_by_ref -->
```text
1 2
```

`a` 还是 1，`b` 变成了 2。**同一个 `++x`，两个结果不同**——区别只在形参类型里那个 `&`。

> 为什么 `&` 一加就完全变了、它和指针是什么关系、什么时候该用哪个：
> 见 [`06_引用、指针与内存.md`](06_引用、指针与内存.md) 第 2 节与第 4 节。

## 5. 返回：值是怎么交回调用者的

### 5.1 三种出口，一个函数

一个函数可以有多个 `return`，但**执行到其中任何一个就结束了这一次调用**。这不是"跳到函数末尾"，而是**当场把值交回去，后面的代码不再执行**。

<!-- example:ch05_return_early -->
```cpp
#include <iostream>

int classify(int x) {
    if (x < 0) {
        return -1;
    }
    if (x == 0) {
        return 0;
    }
    return 1;
}

void print_all(int x) {
    std::cout << x << " -> " << classify(x) << '\n';
}

int main() {
    print_all(-7);
    print_all(0);
    print_all(9);
}
```

<!-- result:ch05_return_early -->
```text
-7 -> -1
0 -> 0
9 -> 1
```

**这种"能提前返回就提前返回"的写法叫早返回（early return）**，它比层层 `else` 嵌套更容易读：函数从上往下一路读下来，每个 `return` 都是一个可以独立验收的出口。

### 5.2 `return` 是"把值交给调用者"，不是"打印出来"

这是初学者最容易混的一处：**函数自己不负责输出，它负责算出一个值；输出是调用者的事。**

```text
int classify(int)        只做一件事：算出一个 int 并交回
print_all(int)           拿到那个 int，负责打印
main                     负责决定打印哪几个输入
```

**分开的好处**：`classify` 现在可以被别处复用——可以拿去比较、可以存进变量、可以喂给另一个函数，而"打印"这个副作用只发生在 `print_all` 里。如果一个函数既算又打印，你就**没法在不打印的情况下使用它的结果**。

> **判据**：**返回值是函数的"输出接口"，打印是副作用。** 两者混在一个函数里，这个函数就只能被"照着原样用一次"。
> 这也是为什么标准库的算法（第 10 章）都只返回值、不打印。

### 5.3 忘了 `return` 会怎样

标准里有一条专门的规定：**一个有返回类型的函数（非 `main`）如果执行到了末尾而没有 `return`，是未定义行为。** `main` 是唯一例外（它相当于隐式 `return 0`）。

```cpp
int f(bool flag) {
    if (flag) {
        return 1;
    }
    // flag 为 false 时走到这里：没有 return → UB
}
```

> ⚠️ **坑（未定义行为类）**：这不是"返回一个垃圾值"，而是**程序已经不合规**（第 02 章第 5.4 节讲过的那个区别）。
> 优化器有权假设这条路径不会被执行，从而把调用方的代码改得你不认识。
> **处理**：**把编译警告当东西看**。MSVC 在 `/W4` 下对这类漏 `return` 会给警告；但**警告不是判据，写全 `return` 才是**。

## 6. 递归与调用栈

**递归**（recursion）是函数直接或间接调用自己。它不是一个特殊的语法，**就是普通的函数调用**——只不过被调用的那个函数恰好是它自己。所以理解递归的关键，是理解每一次调用都发生了什么。

### 6.1 最小例子：阶乘

<!-- example:ch05_fact_recursion -->
```cpp
#include <iostream>

long long fact(int n) {
    if (n <= 1) {
        return 1;
    }
    return n * fact(n - 1);
}

int main() {
    for (int i = 1; i <= 10; ++i) {
        std::cout << fact(i) << '\n';
    }
}
```

<!-- result:ch05_fact_recursion -->
```text
1
2
6
24
120
720
5040
40320
362880
3628800
```

**一个递归函数必须有两个部分**，缺一个就出错：

| 部分 | 本例 | 缺了会怎样 |
|---|---|---|
| **基线条件**（base case） | `if (n <= 1) return 1;` | 永远不返回 → 无限递归 → 栈溢出（6.4 节实测） |
| **递推步**（recursive step） | `fact(n - 1)` | 不调用自己就不是递归了 |

**并且递推步必须真的"变小"**：`fact(n)` 调的是 `fact(n - 1)`，参数在往基线方向走。如果写成 `fact(n)`（参数没变），基线条件永远轮不到。

### 6.2 调用栈：每一层调用有一帧

**调用栈**（call stack）是运行期维护的一块内存区域，用来记录"现在执行到谁、算完了要回到哪"。**每进入一次函数调用，就压入一个栈帧（stack frame）；每返回一次，就弹出一个。**

以 `fact(3)` 为例，把压栈/弹栈的顺序画出来：

```text
main 调用 fact(3)
├─ 压入 fact(3) 的帧           n=3, 等 fact(2) 的结果
│  ├─ 压入 fact(2) 的帧        n=2, 等 fact(1) 的结果
│  │  ├─ 压入 fact(1) 的帧     n=1 → 基线条件命中，return 1
│  │  └─ 弹出 fact(1) → 2 收到 1，算出 2*1 = 2，return 2
│  └─ 弹出 fact(2) → 3 收到 2，算出 3*2 = 6，return 6
└─ 弹出 fact(3) → main 收到 6
```

**栈帧里装的是**：形参（`n` 的副本）、函数内部的局部变量、以及**返回地址**（"算完了回到哪一行"）。这就是为什么"每层调用的 `n` 互不干扰"——**它们是三块不同的存储**，和第 4.1 节的传值是一个道理。

> **读法**：递归最适合"**问题可以缩小成同形状的更小问题**"的场合（阶乘、树遍历、二分）。
> 它**不是**为了省代码——它的每一次调用都有压栈开销（第 6.5 节的实测会把这份开销量化出来）。

### 6.3 递归的代价：同一个子问题被算很多次

<!-- example:ch05_fib_calls -->
```cpp
#include <iostream>

int calls = 0;

int fib(int n) {
    ++calls;
    if (n < 2) {
        return n;
    }
    return fib(n - 1) + fib(n - 2);
}

int main() {
    for (int n = 5; n <= 15; n += 5) {
        calls = 0;
        std::cout << n << ' ' << fib(n) << ' ' << calls << '\n';
    }
}
```

<!-- result:ch05_fib_calls -->
```text
5 5 15
10 55 177
15 610 1973
```

**读最后一列**：`n` 从 5 涨到 15（只涨了 3 倍），调用次数从 15 涨到 1973（涨了 130 倍）。这就是"**重叠子问题**"——`fib(3)` 会被反复重算。

| `n` | 结果 | 调用次数 |
|---|---|---|
| 5 | 5 | 15 |
| 10 | 55 | 177 |
| 15 | 610 | 1973 |

**增长得比 `n` 快得多。** 这类递归（朴素斐波那契）的调用次数约按 1.618^n 增长，`n = 40` 就已经慢到不能用。修法有两类：**加缓存（记忆化）**或**改成循环（自底向上）**。这是算法话题，本章只指出"递归不等于高效"这一点。

### 6.4 栈溢出：递归写错的真实后果

栈的大小是**固定的、有限的**（Windows 上默认 1 MB 左右，由可执行文件的属性决定）。递归深度超过这个额度，就会踩到栈外的内存——**进程被操作系统直接终止。**

写一个必然溢出的递归（没有基线条件），看真实后果：

```cpp
#include <iostream>

int depth = 0;

void dive() {
    ++depth;
    dive();
}

int main() {
    dive();
    std::cout << depth << '\n';
}
```

**编译时先给了一条警告**（这是本节最有价值的证据之一，本机实测）：

```text
main.cpp(8) : warning C4717: “dive”: 如递归所有控件路径，函数将导致运行时堆栈溢出
```

**`C4717` 说的是"所有控件路径"**——编译器做了控制流分析，发现**不管走哪条路都会递归下去**，于是肯定溢出。**注意它只是警告**：程序照样可以生成，你照样能运行它。

**运行的真实结果**（本机实测）：

```text
（stdout 无任何输出）
退出码：3221225725
```

**退出码 3221225725 是 `0xC00000FD`**，即 Windows 的 `STATUS_STACK_OVERFLOW`。**这就是"栈溢出"在操作系统层面的样子**：
进程不是"返回一个错误"，而是**被异常终止**。

**注意 `std::cout << depth` 一个字都没打印出来。** 因为 `dive()` 从来没返回过，那行代码根本没执行到。

> ⚠️ **坑（未定义行为 / 平台差异类）**：**"栈溢出"这个说法没有可移植的精确边界。**
> - 多深会溢出**取决于**：栈的默认大小（Windows 约 1 MB / Linux 常见 8 MB）、每帧占多少字节（取决于编译器优化、参数个数、局部变量）、以及编译选项。
> - **本机的实测数字只对本机有效。** 同样的递归代码在另一台机器上可能在更浅或更深的地方才崩。
> - 而且**溢出不保证被检测到**：不一定每次都得到 `0xC00000FD`，行为本身就是未定义的。
>
> **处理**：**不要靠"大概够深"来设计递归。** 深度可能随输入增长的递归，要么改成迭代，要么显式限制深度并在超限时**报告错误**（第 08 章的错误处理）。

**给一个量级参照**：本机实测一个"每层只递归一次、带一个 `long long` 形参"的递归，深度 **1000 和 10000 都能正常返回**：

```text
1000
10000
```

**把 6.4 和这段放在一起看**，得到的判断是：**几万层以内通常没事，上百万层一定有事，中间那段取决于机器和编译选项。** 所以"能跑多少层"不是一个可以写进代码的常量。

### 6.5 递归 vs 循环：不是"高级"和"低级"

| | 递归 | 循环 |
|---|---|---|
| 谁维护状态 | **调用栈**（每层一帧） | 你自己写的变量 |
| 每步开销 | 压栈 + 弹栈 + 返回地址 | 一次跳转、几次算术 |
| 可读性 | 结构同型的问题（树、分治）更直白 | 线性推进的问题更直白 |
| 风险 | 深度不可控时**栈溢出**；重叠子问题时**爆炸** | 边界写错时死循环或漏算（第 04 章） |
| 什么时候选 | 问题**天然**是"同形状的更小问题" | 其它情况 |

> **判据**：**先想清楚"这个问题的状态是什么、每步怎么变小"，再决定用递归还是循环。**
> 不要因为"递归看起来更聪明"就选递归——`fact` 写成循环同样清楚，而且没有深度上限。

## 7. 函数指针：把函数当成一个值

前面几节里，函数总是**在调用点被直接写出来**。但有些场合需要**把"要调用哪个函数"推迟到运行期再决定**（比如"按用户选的规则排序"）。这就需要一个能存"函数"的东西。

**函数指针**（pointer to function）就是这样一个值：**存的是函数的地址**。它的类型由**返回类型 + 参数列表**决定。

### 7.1 最小例子：同一个调用，换不同的函数进去

<!-- example:ch05_func_ptr -->
```cpp
#include <iostream>

int add(int a, int b) { return a + b; }
int sub(int a, int b) { return a - b; }

int apply(int (*op)(int, int), int a, int b) { return op(a, b); }

int main() {
    int (*p)(int, int) = &add;
    std::cout << p(2, 3) << '\n';
    p = sub;
    std::cout << p(9, 4) << '\n';
    std::cout << (*p)(9, 4) << '\n';
    std::cout << apply(add, 1, 2) << '\n';
    auto q = &sub;
    std::cout << q(9, 4) << '\n';
}
```

<!-- result:ch05_func_ptr -->
```text
5
5
5
3
5
```

**逐行拆开这张输出，它把函数指针的四个语法点全占了**：

| 代码 | 输出 | 讲的是什么 |
|---|---|---|
| `int (*p)(int, int) = &add;` | — | **声明语法**：`(*p)` 的括号不能省。省了就成了"返回 `int*` 的函数声明" |
| `p(2, 3)` | 5 | 函数指针**可以像函数名一样直接调用** |
| `p = sub;` | — | 指针**可以改绑**（这是它和引用最大的区别之一，第 06 章第 4 节） |
| `p(9, 4)` | 5 | **调用的是 `sub`**：9−4 = 5 |
| `(*p)(9, 4)` | 5 | **先解引用再调用**，和上一行等价 |
| `apply(add, 1, 2)` | 3 | **函数名直接当值传**：隐式转成函数指针。注意 `&` 在这里可省 |
| `auto q = &sub;` | 5 | 用 `auto` 避开那段难写的类型 |

> ⚠️ **坑（语法类）**：**`int (*p)(int, int)` 里那对括号是必须的。**
> - `int (*p)(int, int);` → p 是**函数指针**
> - `int *p(int, int);` → p 是**函数**，返回 `int*`
>
> 两行只差一对括号，含义完全不同。**读函数指针声明的办法是从内往外读**：先看 `*p`（p 是指针），再看右边 `(int, int)`（指向一个收两个 int 的函数），最后看左边 `int`（返回 int）。

> 📌 **`(*p)(...)` 和 `p(...)` 都能用**：函数指针的调用语法允许直接省掉 `*`。两种写法等价，选定一种在项目里统一即可。

### 7.2 函数指针装不下"带状态的东西"

函数指针只存一个地址，所以它**只能指向一个普通函数**。下面这类东西它都装不下：

- **带捕获的 lambda**（要存捕获的副本，第 8 节）
- **绑定了一部分参数的函数**（`std::bind`）
- **成员函数 + 对象**的组合（第 07 章）

**`std::function` 就是为这件事存在的**：它是一个**通用的"可调用对象"容器**（`<functional>`）。掏出来的东西可以直接当函数用，代价是**多了一层间接和一份存储**。

<!-- example:ch05_std_function -->
```cpp
#include <functional>
#include <iostream>

int add(int a, int b) { return a + b; }

int main() {
    std::function<int(int, int)> f = add;
    std::cout << f(2, 3) << '\n';

    int factor = 10;
    f = [factor](int a, int b) { return (a + b) * factor; };
    std::cout << f(2, 3) << '\n';

    std::cout << std::boolalpha << static_cast<bool>(f) << '\n';
    f = nullptr;
    std::cout << static_cast<bool>(f) << '\n';
}
```

<!-- result:ch05_std_function -->
```text
5
50
true
false
```

**这个例子的重点是第三件事**：`f` **可以被赋空**（`f = nullptr`），而且**能问它是不是空的**。

| 观察 | 说明 |
|---|---|
| `f = add;` 然后 `f(2, 3)` 得 5 | 普通函数能装进去 |
| `f = [factor](...)` 得 `(2+3)*10 = 50` | **带捕获的 lambda 也能装进去**——函数指针做不到 |
| `static_cast<bool>(f)` → `true` | 有目标，可用 |
| `f = nullptr;` 后 → `false` | 空状态可检测，**这一点比函数指针安全** |

**空 `std::function` 被调用会怎样**：抛 `std::bad_function_call`（第 08 章讲异常）。所以"能检测是否为空"是有实际价值的。

### 7.3 定位：什么时候用哪个

<!-- example:ch05_func_ptr_vs_std_function -->
```cpp
#include <functional>
#include <iostream>

int square(int x) { return x * x; }

int run_ptr(int (*op)(int), int v) { return op(v); }
int run_func(const std::function<int(int)>& op, int v) { return op(v); }

int main() {
    std::cout << sizeof(&square) << '\n';
    std::cout << run_ptr(square, 7) << '\n';
    std::cout << run_func(square, 7) << '\n';
    int captured = 3;
    auto lam = [captured](int x) { return x * captured; };
    std::cout << run_func(lam, 7) << '\n';
    std::cout << run_func([](int x) { return x + 1; }, 7) << '\n';
}
```

<!-- result:ch05_func_ptr_vs_std_function -->
```text
8
49
49
21
8
```

| 行 | 输出 | 说明 |
|---|---|---|
| `sizeof(&square)` | **8** | **函数指针就是一个 8 字节地址**（64 位程序） |
| `run_ptr(square, 7)` | 49 | 函数指针版本能用 |
| `run_func(square, 7)` | 49 | `std::function` 版本也能用 |
| `run_func(lam, 7)` | 21 | **只有 `std::function` 能收带捕获的 lambda**（3×7）。`run_ptr` 收不了 |
| `run_func([](int x){...}, 7)` | 8 | 不捕获的 lambda 也行（7+1） |

**取舍表**：

| | 函数指针 | `std::function` |
|---|---|---|
| 能装普通函数 | ✅ | ✅ |
| 能装带捕获的 lambda | ❌ | ✅ |
| 能装成员函数调用 | ❌（第 07 章） | ✅ |
| 能表示"空" | ✅（空指针） | ✅（可检测） |
| 大小 | 一个地址（本机 8 字节） | **更大**（通常十几个到几十字节，视实现） |
| 调用开销 | 一次间接跳转 | 一次间接跳转 **+ 类型擦除的额外转发**（通常还可能有堆分配） |
| 类型 | 精确（`int(*)(int)`） | 统一（`std::function<int(int)>`） |

> **判据（怎么选）**：
> - **能用函数指针就用函数指针**：它更小、更快、类型更精确。
> - **需要装 lambda / 需要统一类型就上 `std::function`**：尤其是把回调存进容器、存进成员变量、或跨接口边界传递时。
> - **性能敏感的路径上要留意 `std::function` 的开销**：它做的是"类型擦除"，可能带来分配。
>   替代方案（模板参数、函数指针）在第 11 章与第 13 章会展开。
>
> **这一节只给定位。** `std::function` 的完整用法与它的实现方式不在本章范围。

## 8. lambda 表达式与捕获列表

上一节留下了一个洞：**`std::function` 能装带捕获的 lambda，那 lambda 到底是什么？** lambda 是 C++11 起引入的、**在表达式里就地写一个函数对象**的语法。

**它的核心不是"匿名函数"这个说法，而是"捕获列表"**：lambda 能把外层作用域里的变量**装进自己身上**，于是它不再是一个纯函数地址，而是一个**带状态的对象**。

### 8.1 三个部件：`[]` `()` `{}`

<!-- example:ch05_lambda_basic -->
```cpp
#include <iostream>

int main() {
    auto add = [](int a, int b) { return a + b; };
    std::cout << add(2, 3) << '\n';

    int base = 10;
    auto add_base = [base](int x) { return base + x; };
    std::cout << add_base(5) << '\n';

    int counter = 0;
    auto inc = [&counter]() { ++counter; };
    inc();
    inc();
    std::cout << counter << '\n';

    auto no_capture = []() { return 7; };
    std::cout << no_capture() << '\n';
}
```

<!-- result:ch05_lambda_basic -->
```text
5
15
2
7
```

**把语法按块拆开**（这是 lambda 的正式形状）：

```text
[捕获列表]  (形参列表)  -> 返回类型  { 函数体 }
   ↑            ↑            ↑           ↑
 装哪些外部变量  和普通函数一样  可省      和普通函数一样
                              （编译器从 return 推）
```

| 部件 | 本例 | 说明 |
|---|---|---|
| `[]` | `[base]`、`[&counter]`、`[]` | **捕获列表**。`[]` 表示不捕获任何外部变量 |
| `()` | `(int x)` | 形参列表。无参时可以省成 `[]{}` |
| `->` | 本例全用省略形式 | 返回类型。**省略时编译器按 `return` 语句推导**；多个 `return` 类型不一致会报错 |
| `{}` | `{ return base + x; }` | 函数体 |
| `auto add = ...` | — | **lambda 的类型是唯一的、匿名的**，所以只能用 `auto` 接（或用 `std::function` 装） |

**四个观察**：

1. `add(2, 3)` = 5：**不捕获的 lambda 和普通函数用起来一样**。
2. `add_base(5)` = 15：`[base]` 把 `base` 的**值**装了进去，之后 `base` 就算改了也不影响它。
3. `inc(); inc(); counter` = 2：`[&counter]` 捕获的是**引用**，所以改的是外面那个 `counter`。
4. `no_capture()` = 7：不需要外部状态时，捕获列表留空。

### 8.2 捕获列表全表（本节的核心对比）

| 写法 | 名字 | 装进闭包对象的是什么 | 能改到外面吗 | 风险 |
|---|---|---|---|---|
| `[]` | 无捕获 | 什么都不装 | — | 无。这类 lambda **能转成函数指针** |
| `[x]` | 按值捕获 | `x` 的一份**副本** | ❌ 改副本，外面不动 | 大对象会拷贝（第 4.2 节同一个道理） |
| `[&x]` | 按引用捕获 | `x` 的**引用** | ✅ 直接改外面那个 | **生命周期**：`x` 死了它就悬垂 |
| `[=]` | 隐式按值 | 函数体里用到的所有外部变量的副本 | ❌ | 容易在不知情的情况下拷贝大对象 |
| `[&]` | 隐式按引用 | 函数体里用到的所有外部变量的引用 | ✅ | **最容易出悬垂**：哪些变量被捕获了看不出来 |
| `[x, &y]` | 混合 | 各自按规则 | 只有 `y` 能改 | 需要你逐个说清 |
| `[z = y * 2]` | 初始化捕获（C++14 起） | **一个叫 `z` 的新变量**，初值是 `y*2` | ❌ | 无（但要知道它不是"捕获了 y"） |

**先看一张实测的输出，它把"值捕获"和"引用捕获"的差别摆在一起**：

<!-- example:ch05_lambda_capture -->
```cpp
#include <iostream>

int main() {
    int x = 1;
    auto byval = [x]() { return x; };
    auto byref = [&x]() { return x; };
    x = 99;
    std::cout << byval() << ' ' << byref() << '\n';

    int v = 1;
    auto bump = [v]() mutable { return ++v; };
    std::cout << bump() << ' ' << bump() << ' ' << v << '\n';
}
```

<!-- result:ch05_lambda_capture -->
```text
1 99
2 3 1
```

**第一行 `1 99` 是本节最该看懂的一行**：

```text
x 从 1 改成 99
  ├─ byval() 里装的是【创建 lambda 那一刻】的 x，也就是 1    → 打印 1
  └─ byref() 里装的是 x 这个对象本身，读的时候是 99         → 打印 99
```

**"按值捕获拷贝的时机"是 lambda 创建的那一刻，不是调用的那一刻。** 这和默认实参在调用点求值（第 2.2 节）**正好相反**，两件事别记混。

**第二行 `2 3 1` 引入了 `mutable`**：按值捕获的变量默认在 lambda 体内是 `const` 的（因为闭包对象的 `operator()` 默认是 `const` 成员函数）。加 `mutable` 才能改那个副本。注意打印顺序：

| 表达式 | 值 | 说明 |
|---|---|---|
| `bump()` | 2 | 改的是**闭包对象里那份副本**，1 → 2 |
| `bump()` | 3 | 同一个闭包对象，所以记忆住了上一行的 2 → 3 |
| `v` | **1** | **外面那个 `v` 从头到尾没被碰过** |

**所以 `mutable` 的按值捕获给了你一个"私有的小状态"**：它能在多次调用之间保持，但不影响外部变量。

### 8.3 初始化捕获：装一个你自己造的值

<!-- example:ch05_lambda_init_capture -->
```cpp
#include <iostream>

int main() {
    int y = 5;
    auto byinit = [z = y * 2]() { return z; };
    std::cout << byinit() << '\n';

    auto bycopy = [=]() { return y; };
    auto byref  = [&]() { return y; };
    y = 50;
    std::cout << bycopy() << ' ' << byref() << '\n';
}
```

<!-- result:ch05_lambda_init_capture -->
```text
10
5 50
```

| 写法 | 打印 | 说明 |
|---|---|---|
| `[z = y * 2]` | 10 | 闭包里有一个**新变量 `z`**，值是 `y*2` 算出来的 10。**`z` 不是 `y` 的别名，也不跟 `y` 联动** |
| `[=]` | 5 | 隐式按值：捕获创建时刻的 `y`（那个 5） |
| `[&]` | 50 | 隐式按引用：读的是改过之后的 `y` |

> **`[=]` / `[&]` 的取舍**：
> - **`[=]` 安全但可能贵**：不会悬垂，但可能悄悄拷贝一个大对象（比如整个 `std::vector`）。
> - **`[&]` 便宜但危险**：不拷贝，但只要闭包活过了被捕获变量，就是悬垂。
> - **本讲义的立场**：**默认逐个显式写 `[x]` / `[&x]`**。理由是这句——**捕获列表是你唯一能看出"这个 lambda 依赖什么、会改什么"的地方**。
>   `[&]` 把这些信息藏起来了：读代码的人得先通读函数体，才能知道到底捕获了哪几个变量，从而才能判断它会不会悬垂。

### 8.4 捕获列表的坑：按引用捕获 + 超出作用域 = 悬垂

**这是 lambda 最容易出的、也最危险的一类错误。** 危险在于：它**编译通过、常常还能打印出"看起来对"的值**，然后在你最想不到的时候变成别的数字。

下面是本章实测到的最有价值的一条证据。同一个程序，我跑了两次，**两次打印的数字不一样**：

```cpp
#include <iostream>

int main() {
    auto make = [](int seed) {
        int local = seed;
        return [&local]() { return local; };   // 按引用捕获了一个局部变量
    };
    auto f = make(42);
    std::cout << f() << '\n';                  // 读已经销毁的对象：UB
}
```

本机实测输出（**两次运行**）：

```text
第一次运行：42
第二次运行：34
（上一轮采集时另一个时间点跑出来的还是 83）
```

**三次运行，两个不同的数字，而且都不是"稳定地错"。** 这正是"未定义行为"的样子——**不是"随机数"，是"程序已经没有任何保证"**（第 02 章第 5.4 节辨析过这个区别）。

**机制**：

```text
1. make(42) 被调用 → 它的局部变量 local 在【make 的栈帧】里
2. 返回的 lambda 对象里装的是 &local（一个地址），不是 42
3. make 返回 → 栈帧弹出 → 那块存储【被回收】
4. f() 被调用 → 顺着那个地址读
   └─ 那块存储现在归谁？栈上后来放了什么？——没人知道
```

**为什么这次打印出 42（"看起来是对的"）**：那块栈存储虽然"已经回收"，但**内容还没来得及被覆盖**，所以侥幸读出了原值。**这是最坏的情况**——它让你以为代码是对的。

**怎么改**：把 `[&local]` 改成 `[local]`，让闭包**拷一份**进去。

### 8.5 修法：改成按值捕获

<!-- example:ch05_lambda_byvalue_safe -->
```cpp
#include <iostream>

int main() {
    auto make = [](int seed) {
        int local = seed;
        return [local]() { return local; };    // 按值捕获：拷贝进闭包对象
    };
    auto f = make(42);
    auto g = make(7);
    std::cout << f() << ' ' << g() << '\n';
}
```

<!-- result:ch05_lambda_byvalue_safe -->
```text
42 7
```

**改完之后**：`f` 和 `g` 各自持有一份**自己的副本**，`make` 的栈帧有没有弹出都不影响它们。输出稳定。

> ⚠️ **坑（未定义行为类）**：按引用捕获局部变量、并让闭包活过那个变量，**编译器不会救你**。
> - 它**不报错**（语法和类型都合法）；
> - 它**常常不警告**（本机 `/W4` 对这个例子一条警告都没有，实测）；
> - 它**可能打印出正确的结果**（因为栈内存还没被覆盖，实测出现过 42）。
>
> **处理**：
> 1. **闭包要离开作用域（被返回、被存进容器/成员），一律按值捕获**（或用初始化捕获造一份新值）。
> 2. `[&]` 只在"闭包的生命周期严格短于被捕获变量"时用——典型场景是**当场传给算法**（第 10 章）：`std::sort(v.begin(), v.end(), [&](int a, int b){...})`，`sort` 返回时闭包就死了。
> 3. **看住了还不行**：这类错误属于**生命周期/未定义行为类**，不是类型类。编译器管不到，只能靠你自己在写捕获列表时想清楚"它比被捕获的变量活得久吗"。

### 8.6 `mutable` 状态：一个能记住东西的小计数器

<!-- example:ch05_lambda_mutable_state -->
```cpp
#include <iostream>

int main() {
    auto counter = [n = 0]() mutable { return ++n; };
    std::cout << counter() << counter() << counter() << '\n';

    int shared = 0;
    auto byref = [&shared]() { return ++shared; };
    byref();
    byref();
    std::cout << shared << '\n';
}
```

<!-- result:ch05_lambda_mutable_state -->
```text
123
2
```

**第一行 `123` 的关键在于 `counter` 是一个对象，不是一个函数**：

```text
counter 这个闭包对象里有一个 n（初值 0）
counter() → n 变 1，返回 1
counter() → n 变 2，返回 2   ← 记住上一次了
counter() → n 变 3，返回 3
```

**这就是"闭包是一个带状态的对象"的直接证据。** 它和上一节 `std::function` 能装带捕获的 lambda 是同一件事的两面：

| | 状态存在哪 | 谁能看见 |
|---|---|---|
| 普通函数 | 只能放全局/静态变量 | 所有调用者共享 |
| 闭包对象 | **存在闭包对象自己身上** | 只有这一份闭包 |

**对比左下角**：`byref` 改的是外面的 `shared`（打印 2），**改动是外部的**；`counter` 改的是自己的 `n`，**外部完全看不到**。同一个 `++`，两种可见性。

> ⚠️ **一个容易忽略的求值顺序问题**：这一行里三个 `counter()` 的求值顺序在 C++17 里是确定的：
> **从左到右**。所以本机稳定打印 `123`（不会变成 `321` 或 `213`）。
>
> **⚠️ 但要说清为什么**：**这不是"因为 `<<` 是左结合"**——结合性管的是"谁和谁先结合成一组"，
> 求值顺序管的是"谁先被求值"，**两件事不一样**（第 03 章第 7 节整节就在讲这个区分）。
> 这里的左到右来自 C++17 专门为 `<<` / `>>` 这类运算符规定的求值顺序规则。
>
> **对照组**：把这一行换成 `int s = counter() + counter() + counter();`，
> 虽然 `+` 同样左结合，但**它的操作数求值顺序是不指定的**：
> 编译器可以先算最右边那个，于是 `n` 从 0 直接被读成初值，`s` 会得到别的结果。
> **同一份闭包，换个运算符就从"确定"变成"不指定"。**
> 求值顺序的完整规则见
> [`03_表达式、运算与转换.md`](03_表达式、运算与转换.md) 第 7 节「优先级、结合性，和求值顺序——三件不同的事」。

### 9.1 先建一个能工作的三文件程序

**目录结构**（`stats.h` / `stats.cpp` / `report.cpp` / `main.cpp`）：

```cpp
// ===== stats.h =====
#ifndef STATS_H
#define STATS_H

int sum(const int* data, int n);      // 声明：头文件只放声明
inline int square(int x) {            // inline 定义：可以进头文件
    return x * x;
}

#endif
```

```cpp
// ===== stats.cpp =====
#include "stats.h"

int sum(const int* data, int n) {     // 定义：只放一个 .cpp
    int total = 0;
    for (int i = 0; i < n; ++i) {
        total += data[i];
    }
    return total;
}
```

```cpp
// ===== report.cpp =====
#include "stats.h"

int sum_of_squares(const int* data, int n) {
    int total = 0;
    for (int i = 0; i < n; ++i) {
        total += square(data[i]);     // 用到头文件里的 inline 函数
    }
    return total;
}
```

```cpp
// ===== main.cpp =====
#include <iostream>
#include "stats.h"

int sum_of_squares(const int* data, int n);

int main() {
    int data[4] = {1, 2, 3, 4};
    std::cout << sum(data, 4) << '\n';
    std::cout << sum_of_squares(data, 4) << '\n';
}
```

**编译命令**（本机实测，`vcvars64.bat` 已初始化）：

```powershell
cl /nologo /std:c++17 /EHsc /W4 /utf-8 main.cpp stats.cpp report.cpp /Fe:app.exe
```

**编译器的完整输出**（这是 `cl` 自己打印的，不是程序的输出）：

```text

```

**程序的输出**：

```text

```

**怎么读这两段**：

| `main.cpp` / `stats.cpp` / `report.cpp` | **编译器** | 逐个翻译单元编译（第 01 章第 10 节讲过翻译单元） |
| `正在生成代码...` | **编译器** | 进入代码生成阶段 |
| `10` / `30` | **程序** | `sum` 得 1+2+3+4 = 10；`sum_of_squares` 得 1+4+9+16 = 30 |

### 9.2 头文件里放函数定义会怎样（真跑一次）

把 9.1 的 `stats.h` 换成一个**直接写函数体、没有 `inline`** 的版本：

```cpp
// ===== util.h =====
int add(int a, int b) {      // 普通函数定义写进头文件
    return a + b;
}
```

`math_utils.cpp` 和 `main.cpp` **都** `#include "util.h"`：

```cpp
// ===== math_utils.cpp =====
#include "util.h"

int twice(int x) {
    return add(x, x);
}
```

```cpp
// ===== main.cpp =====
#include <iostream>
#include "util.h"

int twice(int x);

int main() {
    std::cout << add(2, 3) << ' ' << twice(5) << '\n';
}
```

**命令**：

```powershell
cl /nologo /std:c++17 /EHsc /W4 /utf-8 main.cpp math_utils.cpp /Fe:app.exe
```

**完整输出**（本机实测）：

```text
main.cpp
math_utils.cpp
正在生成代码...
math_utils.obj : error LNK2005: "int __cdecl add(int,int)" (?add@@YAHHH@Z) 已经在 main.obj 中定义
app.exe : fatal error LNK1169: 找到一个或多个多重定义的符号
```

**注意三件事**：

1. **编译阶段一声不响就过了**——`main.cpp` 和 `math_utils.cpp` **各自都是合法的 C++**。每个翻译单元单独看都没问题。
2. **报错前缀是 `LNK`**，发生在**链接阶段**（第 01 章第 8 节）。
3. **报的是符号名 `?add@@YAHHH@Z`**，不是源码里的 `add`。这是**名字修饰**（name mangling）的结果——链接器眼里只有修饰后的符号（第 01 章第 4 节）。

**根因**：预处理是**文本替换**（第 01 章第 3 节）。`#include "util.h"` 把那段函数体**复制**进每个包含它的文件：

```text
main.cpp        ──include──→  有了 add 的定义  ──编译──→  main.obj 里有 ?add@@YAHHH@Z
math_utils.cpp  ──include──→  有了 add 的定义  ──编译──→  math_utils.obj 里也有
                                                          ↓
                                              链接器：同一个符号出现两次 → LNK2005
```

### 9.3 修法一：加 `inline`

**这是 `inline` 在今天的真实用途。** 把 `util.h` 改成：

```cpp
// ===== util.h =====
inline int add(int a, int b) {   // inline：允许多个翻译单元里有同一份定义
    return a + b;
}
```

**同样的命令、同样的两个 `.cpp`**，本机实测：

```text
main.cpp
math_utils.cpp
正在生成代码...
```

**编译链接全部通过，程序的输出**：

```text
5 10
```

（`add(2,3)` = 5，`twice(5)` = `add(5,5)` = 10。）

**`inline` 在这里做的事，就是"**允许**"两个字**：它告诉编译器和链接器"**这个函数在多个翻译单元里各有一份定义是正常的，它们是同一个函数，请合成一份**"。所以：

> **`inline` 的现代含义 = ODR 豁免（允许重复定义）。**
> **不是** = "请把这个函数内联展开成指令"。

**为什么"建议内联展开"那层含义已经不重要了**：现代优化器对**任何**函数（不管你有没有写 `inline`）都会自己判断"展开它划不划算"——函数小、调用频繁就展开，函数大就不展开。**你写的 `inline` 现在基本只影响链接行为，不影响优化器的决定。**

| 说法 | 对不对 |
|---|---|
| "加 `inline` 就会把函数体展开进调用点" | ❌ **错。** 优化器自己决定，你无权要求 |
| "加 `inline` 允许同一份定义出现在多个翻译单元里" | ✅ **对。这是它今天的实际作用** |
| "`inline` 只是个给优化器的提示" | ❌ 过时。它现在是**关于链接的规则** |
| "类内定义的成员函数自动是 `inline`" | ✅ 对（第 07 章）。这也是为什么头文件里的类成员函数不报 `LNK2005` |

> ⚠️ **注意"展开"这件事不可观测**：本章所有示例都是 `/Od`（默认不优化）编译的，
> **"有没有真的内联展开"没有任何工具输出支撑**，本讲义**不做任何关于"某函数被展开了"的断言**。
> 要自己看，得读汇编或看优化报告——那是第 13 章的范围。

### 9.4 修法二：声明放头文件，定义放一个 `.cpp`

**这是更常用的选择，也是能给出更短编译依赖的方式。** 即 9.1 节那个 `stats.h` / `stats.cpp` 的写法：

```cpp
// util.h        ← 头文件只放声明
int add(int a, int b);

// util.cpp      ← 定义只放一个 .cpp
int add(int a, int b) { return a + b; }
```

**两种修法的取舍**：

| | 加 `inline`（定义进头文件） | 声明/定义分离（定义进 `.cpp`） |
|---|---|---|
| 改动量 | 一行 | 要新建一个 `.cpp`，并把它加进编译命令 |
| 函数体能被优化器看到 | ✅ 每个翻译单元都能看到它 | ❌ 跨翻译单元调用时看不到（除非开 LTO） |
| 改函数体后的重编译量 | **所有包含该头文件的文件都要重编** | **只重编那一个 `.cpp`** |
| 适用场景 | **小函数**（几行、访问器、工具函数） | **大函数、实现细节会常改的函数** |
| 编译命令 | 不用改 | **必须记得把它加进 `cl` 的参数**（否则 `LNK2019`） |

> **判据**：**"小、稳定、到处要用" → `inline` 进头文件；"大、会改、只有一部分地方用" → 定义放 `.cpp`。**
> 这条判断没有标准答案，但**两个常见的坏结果**要避开：
> - 把大函数都写成 `inline` 塞进头文件 → 改一行要重编整个项目。
> - 忘了把 `.cpp` 加进编译命令 → 报 `LNK2019`（第 01 章第 10 节有这条诊断的原文）。

### 9.5 ODR 入门：两条规则，两个尺度

**ODR** 是 One Definition Rule（单一定义规则）的缩写。入门阶段需要分清**两条**：

| 规则 | 说的是 | 违反的后果 | 在哪一层暴露 |
|---|---|---|---|
| **ODR（单个翻译单元）** | 同一个翻译单元里，一个函数只能有一个定义 | **编译错误**（`C2084` / `C2371`，见第 3.4 节） | 编译期，编译器管 |
| **ODR（整个程序）** | 整个程序里，一个非 `inline` 函数/变量只能**被定义一次** | **链接错误**（`LNK2005`） | 链接期，链接器管 |
| **ODR（`inline` 函数的要求）** | 一个 `inline` 函数在各翻译单元里的定义**必须逐字相同** | **未定义行为，且没有任何诊断** | **谁都不管** ⚠️ |

**第 9.2 节那个 `LNK2005` 就是第二条的实例**：

```text
main.cpp        ──→  main.obj        里有 ?add@@YAHHH@Z
math_utils.cpp  ──→  math_utils.obj  里也有 ?add@@YAHHH@Z
                     链接器：这个符号被定义了两次 → LNK2005
```

**第三条最值得单独警惕**，因为它**不会报错**：

```cpp
// bad.h
inline int compute(int x) { return x + 1; }
```

如果在某个 `.cpp` 里这个头文件被包含时，`compute` 的**函数体不一样**（比如因为宏、因为两份不同版本的头文件），那么：

- 编译器看不出问题（它在**一个翻译单元内**工作，看不到别的翻译单元）；
- 链接器看不出问题（它只比符号名，`inline` 函数的符号本来就可以重复）；
- 于是**程序里哪个定义被用上，是不确定的** → **未定义行为**。

> ⚠️ **坑（未定义行为类 + 无诊断）**：`inline` 函数的 ODR 违反是**唯一一类本章讨论的、三个工具都不报错的错误**。
> **它连 `LNK2005` 都不给你**——`inline` 本来就是拿来豁免那个检查的。
> **处理**：`inline` 函数的定义**只写一份**（放在头文件里，让所有翻译单元看到**同一份文本**）。
> 不要用宏去改变 `inline` 函数的函数体——那是主动制造 ODR 违反。
>
> **本讲义的态度**：这一类错误的**具体表现形式我没有实测**（见第 13 节诚实标注），所以我**不贴运行结果**。
> 但"它是 UB"这一条是标准规定，不需要实测。

### 9.6 `static` 是另一条路（提一句，不展开）

头文件里的变量/函数加 `static` 会让它获得**内部链接**（internal linkage）：**每个翻译单元各拿一份独立副本**，互不冲突，也不会报 `LNK2005`。

```cpp
// counter.h
static int counter = 0;      // 内部链接：每个翻译单元拿到的是一份独立副本
```

**本机实测**（`main.cpp` 和 `a.cpp` 都包含它，`a.cpp` 里的 `bump_a()` 给**它自己那份**加 1）：

```text
0 0
0 1
```

**这两行输出的含义**：`main.cpp` 看到的 `counter` 和 `a.cpp` 里的 `counter` 是**两个不同的对象**——`a.cpp` 把自己那份加到了 1（所以 `get_a()` 返回 1），而 `main.cpp` 那份**始终是 0**。

> ⚠️ **坑（链接类）**：**"每个文件各有一份"通常不是你想要的。**
> 计数器、缓存、单例这类东西，一旦被 `static` 复制成多份，会表现为"**改了但看起来没改**"——
> 一种极难查的 bug。头文件里的 `static` 变量是 C 语言时代留下的写法，在 C++ 里请换成：
> - **`inline` 变量**（C++17 起）：一份共享，且能进头文件（第 02 章第 4.2 节提过它的位置）
> - 或者干脆只在一个 `.cpp` 里定义

## 10. 断言与前置/后置条件的写法

函数是有**契约**的：调用者要满足某些条件，函数才能正常工作。**前置条件**（precondition）是"调用者必须保证的事"，**后置条件**（postcondition）是"函数承诺交出的事"。

这一节讲三件事：**契约怎么用文字和代码表达**、**`assert` 能替你把哪一部分变成检查**、**它为什么不能替全部**。

### 10.1 先看一个真实的失败：除数是 0

`divide(a, b)` 的前置条件是"`b != 0`"。不检查会怎样？整数除零是**未定义行为**（不是抛异常，不是返回 0）。

**给函数加上断言**，把前置条件写进代码：

<!-- example:ch05_assert_ok -->
```cpp
#include <cassert>
#include <iostream>

int divide(int a, int b) {
    assert(b != 0 && "divisor must not be zero");
    return a / b;
}

int main() {
    std::cout << divide(10, 2) << '\n';
    static_assert(sizeof(int) == 4, "this note assumes 32-bit int");
    std::cout << "ok" << '\n';
}
```

<!-- result:ch05_assert_ok -->
```text
5
ok
```

**这里面有两件不同的东西，它们的名字只差一个 `static`，但做的事完全不同**：

| | `assert` | `static_assert` |
|---|---|---|
| 什么时候检查 | **运行期**（程序跑起来才检查） | **编译期**（编译时检查） |
| 检查什么 | 任意**运行期**表达式 | 必须是**编译期常量表达式** |
| 失败的表现 | **运行期调用 `abort()`，进程终止** | **编译失败**，程序根本生成不出来 |
| 能不能被关掉 | ✅ **能被 `NDEBUG` 关掉**（10.3 节） | ❌ 关不掉，永远生效 |
| 头文件 | `<cassert>` | **不需要头文件**（是关键字） |
| 本章给多少 | 完整（本节） | **只给位置**（第 11 章「模板与泛型」与第 13 章会展开） |

### 10.2 `assert` 失败的真实样子

**断言失败和 `return` 一个错误码完全不是一回事**：它会**直接终止进程**。本机实测：

```cpp
#include <cassert>

int main() {
    int x = 1;
    assert(x == 2);
    return 0;
}
```

**真实输出**（这一段来自 **stderr**，不是 stdout）：

```text
Assertion failed: x == 2, file main.cpp, line 5
退出码：3221226505
```

**读这两行**：

| 内容 | 含义 |
|---|---|
| `Assertion failed: x == 2` | 直接把**没成立的表达式原文**打出来了 |
| `file main.cpp, line 5` | 精确到**文件和行号**——这是断言最有用的部分 |
| 退出码 `3221226505` | 即 `0xC0000409`（`STATUS_STACK_BUFFER_OVERRUN`，MSVC 的 `abort()` 走这个异常码），说明**进程是被异常终止的**，不是正常返回 |

> ⚠️ **注意"没有输出"和"有输出"的区别**：**断言失败的信息走 stderr，而且进程立刻死掉**。
> 这意味着断言之前如果往 `std::cout` 写的东西还在缓冲区里，**可能一个字都不会出现**——
> 这个现象在 [`01_从源代码到运行.md`](01_从源代码到运行.md) 第 11 节「调试：没有图形界面时怎么办」里有专门的实测，
> 那里也给了 `std::cerr` 这个无缓冲的排错手段。
> **调试断言失败时，先看 stderr，不要只盯着 stdout。**

### 10.3 `NDEBUG`：断言会被关掉——这带来一个陷阱

`assert` 是一个**宏**，它的开关是宏 `NDEBUG`（No DEBUG）。**定义了 `NDEBUG`，`assert(...)` 会被替换成什么都不做。**

本机实测（用 `/DNDEBUG` 编译）：

```cpp
#include <cassert>
#include <iostream>

int main() {
    int x = 0;
    assert(++x > 0);
    std::cout << x << '\n';
}
```

```text
（不开 NDEBUG）输出：1
（开 NDEBUG）  输出：0
```

**同一个程序，两种结果**。因为开 `NDEBUG` 后那一行整个消失了，`++x` **根本没执行**。

> ⚠️ **坑（未定义行为 / 语义类）——这是本节最该记住的一条**：**`assert` 里的表达式会在发布版本里被整个删掉。**
> 所以：
> ```cpp
> assert(++x > 0);          // ❌ 荒谬但合法：x 的自增依赖断言是否启用
> assert(read_file(p));     // ❌ 更糟：文件只在调试版本里被读
> assert(free(p), "ok");    // ❌ 释放内存也因为 NDEBUG 消失
> ```
> **处理（一条硬规矩）**：**`assert` 里只放"没有副作用的纯判断"，绝不放函数调用中带副作用的表达式。**
> 判据很简单：**把 `assert(...)` 整行删掉，程序的行为应该完全不变。** 如果变了，那行断言就是错的。
>
> **为什么标准允许这样设计**：断言的定位是"**开发期自检**"，不是"错误处理"。开发期要能一条开关全关掉，
> 所以它必须能被替换成"空"。**需要"发布版本也保留"的检查，不能用 `assert`**——要用真正的错误处理（第 08 章）。

### 10.4 用 `assert` 的写法：先写清楚契约

**断言的价值一半在"检查"，另一半在"把契约写出来给读代码的人看"。** 一个规范的写法长这样：

```cpp
// 前置条件：data 至少有 n 个元素；n >= 0
// 后置条件：返回值是 data[0] + ... + data[n-1]；n == 0 时返回 0
int sum(const int* data, int n) {
    assert(data != nullptr);   // 前置：指针有效
    assert(n >= 0);            // 前置：长度非负
    int total = 0;
    for (int i = 0; i < n; ++i) {
        total += data[i];
    }
    assert(total >= 0 || n == 0);   // 后置：此处只是示意；一般不这样写后置
    return total;
}
```

**几个配套的表达手段**：

| 想表达 | 写法 | 说明 |
|---|---|---|
| 前置条件的**文字说明** | 注释写在函数上方（如上） | ✅ **总是要写**，断言关掉之后注释还在 |
| 运行期检查 | `assert(cond)` | 开发期自检；发布版会消失 |
| **带说明的**运行期检查 | `assert(cond && "说明文字")` | 见下方 ⚠️ |
| 编译期检查 | `static_assert(cond, "说明文字")` | 关不掉 |
| 需要**发布版也保留**的检查 | 真正的错误处理（抛异常 / 返回错误码） | 第 08 章 |

> **关于 `assert(b != 0 && "divisor must not be zero")` 这个写法**：
> 字符串字面量在条件里**恒为真**（非空指针），所以 `cond && "文字"` 的真假**完全由 `cond` 决定**——
> 它不影响判断，只在断言失败时**把那段文字一起打印出来**（上面 10.2 节的实测输出里就能看到 `Assertion failed:` 后面跟的是表达式原文）。
> **这是 C 语言时代传下来的技巧**，能用；但要知道它是"用逻辑与把文字挂上去"，不是语言支持的特性。

### 10.5 前置/后置条件该检查到什么程度

**不是所有条件都值得断言。** `assert` 有成本（运行期多一次判断），而且**它不是给用户看的错误信息**（一句话、一个文件行号，不适合终端用户）。判断表：

| 条件的性质 | 该用什么 |
|---|---|
| **程序内部的逻辑不变量**（"这里链表一定非空"） | ✅ `assert`。违反了就是**你的程序有 bug** |
| **来自外部输入**（用户输入、文件内容、网络数据） | ❌ **不能用 `assert`**。用真正的错误处理（第 08 章）——外部输入不合法是**正常情况**，不是 bug |
| **编译期就能确定的事实**（"`int` 是 4 字节"） | ✅ `static_assert` |
| **性能敏感的循环内** | ⚠️ 慎用。`assert` 在发布版会消失，但**调试版会变慢** |
| **"这个函数要求非空指针"** | ✅ `assert(p != nullptr)`。传空指针是**调用者的错** |

> **一条判据**：**`assert` 的失败信息是给"写这个程序的人"看的，不是给"用这个程序的人"看的。**
> 所以它适合"**不可能发生，除非我写错了**"的条件；不适合"**可能发生，需要优雅处理**"的条件。

### 10.6 `[[nodiscard]]`：把"别忘了用返回值"写进契约

有一种契约不是关于参数的，而是关于**返回值**的："**这个函数的返回值必须被使用，忽略它就是 bug。**" C++17 起可以用 `[[nodiscard]]` 表达它。

<!-- example:ch05_nodiscard -->
```cpp
#include <iostream>

[[nodiscard]] int compute() {
    return 42;
}

int main() {
    compute();
    std::cout << compute() << '\n';
}
```

<!-- result:ch05_nodiscard -->
```text
42
```

**编译时有一条警告**（本机实测）：

```text
main.cpp(8): warning C4834: 放弃具有 [[nodiscard]] 属性的函数的返回值
```

| 观察 | 说明 |
|---|---|
| 程序**照常运行**，输出 42 | 它是**警告**，不是错误 |
| 警告精确指向第 8 行 | 就是丢掉返回值的那一行 |
| 第二次调用（`std::cout << compute()`）不报 | 返回值被用掉了 |

> **什么时候该标 `[[nodiscard]]`**：返回值是**唯一成果**、丢掉就没意义的函数。
> 典型场景：错误码（`if (write(...) != OK)`）、分配结果、以及所有"查询"类函数。
> 本章的 `compute` 只是个演示，真实代码里 `[[nodiscard]]` 最常出现在**返回错误状态**的函数上（第 08 章）。

## 11. 本章自测

**1.** 下面两个声明有什么区别？哪个能编过？

```cpp
int add(int a, int b);
int add(int a, int b) { return a + b; }
```

<details><summary>答案</summary>

**都能编过，而且可以同时出现在一个文件里**——但**顺序不能反**。

- 第一行是**声明**（函数原型）：只告诉编译器"有这么个函数、签名是这样"。
- 第二行是**定义**：给出函数体，也就是"怎么做"。

**声明可以有很多份，定义只能有一份**（第 1.2 节、第 9.5 节）。在这个例子里它们恰好等价于只写第二行——**声明在这里是多余的**，因为定义本身就包含了声明的作用。

**声明真正有用的时候**是：定义在别的地方（另一个 `.cpp`，第 9.1 节），或者定义在下面而你上面就要调用（第 1.1 节）。

**判据**：**有函数体的是定义，没有的是声明。** 一个函数只有声明而没有定义，编译能过、链接会报 `LNK2019`（第 1.5 节）。
</details>

**2.** 为什么下面这段代码编译不过？

```cpp
int g(int a = 1, int b) {
    return a + b;
}
```

<details><summary>答案</summary>

**因为默认实参必须靠右排。**

真实诊断（本机实测）：
```text
main.cpp(1): error C2548: “g”: 缺少形参 2 的默认实参
```

**根因**：实参是**按位置从左往右**填进形参的。如果允许 `g(5)`，编译器无法判断 5 是给 `a` 还是给 `b`——**这个位置歧义无法解决**，所以标准直接禁止。

**正确写法**是把有默认值的参数放到**最后**：`int g(int b, int a = 1);`

这一条和"默认实参在调用点求值"（第 2.2 节）是两条独立的规则：前者管**语法位置**，后者管**求值时机**。
</details>

**3.** `f(0)` 和 `f(nullptr)` 在这组重载里会分别调用哪个？为什么？

```cpp
void f(int value);
void f(const char* text);
```

<details><summary>答案</summary>

- **`f(0)` → `f(int)`**：`0` 是 `int` 字面量，**精确匹配**，压过"`0` 可以当空指针常量"这条转换路径。
- **`f(nullptr)` → `f(const char*)`**：`nullptr` 的类型是 `std::nullptr_t`，它**不能转成 `int`**（不是整数），所以 `f(int)` 甚至不是可行候选，只剩指针版本。

**本机实测输出**（第 3.6 节）：
```text
cstr (null)
cstr (null)
int 0
int 0
```
（第一行是 `const char* p = nullptr` 的显式版本，第四行是 `f(NULL)`。）

**这个坑的危险之处**：`f(0)` **不会报错**，它会静默走到整数版本。如果你本意是传空指针，程序会跑起来、还会输出东西，只是走错了分支。

**修法**：**要空指针就写 `nullptr`。** 另外注意 `NULL` 在本机 MSVC 上就是 `0`，所以它和 `f(0)` 命运相同（第 3.6 节的实测）。

**更深一层**：`nullptr` 能转成 `bool`（`bool` 是整型），所以换一组重载 `g(bool)` / `g(int)`，`g(nullptr)` 会选 `bool`（第 3.6 节第二个实测）。
</details>

**4.** 第 4.2 节的 `Tracer` 例子为什么只在 `by_value` 的时候打印一次 `copy`？这个观察对写代码有什么实际影响？

<details><summary>答案</summary>

**因为默认的参数传递方式是传值，传值 = 用实参拷贝构造一份形参。**

```text
by_value(t)  → 拷贝构造一份 Tracer  → 打印 copy
by_ref(t)    → 形参是 const Tracer&，不拷贝 → 没有 copy
```

本机实测输出：
```text
ctor
--- by_value ---
copy
in by_value
--- by_ref ---
in by_ref
```

**实际影响**：**"传值 = 拷贝整个对象"是一个和对象大小成正比的代价**，而且**在调用点完全看不出来**。

一个只含 `int` 的 `Tracer` 看不出差别；换成含 10 万个元素的 `std::vector`，每次调用都分配 + 复制 10 万个元素。**函数写得很短 ≠ 调用很便宜。**

**本章的边界**：怎么**避免**这个拷贝（引用传递、`const T&`、移动）是第 06 章与第 12 章的内容（第 4.2 节的边界表）。**本章只需要带走"默认会拷贝"这个判断**，别用全局变量去绕。
</details>

**5.** 下面这个 lambda 返回出去以后能用吗？为什么？

```cpp
auto make() {
    int local = 42;
    return [&local]() { return local; };
}
```

<details><summary>答案</summary>

**不能用——这是未定义行为。**

**机制**：`[&local]` 在闭包对象里装的是**指向 `make` 栈帧里那个 `local` 的地址**，不是 42。`make` 一返回，它的栈帧就被弹出，那块存储被回收；之后调用闭包就是**读一块已经不属于你的内存**。

**本机实测的"最危险的证据"**（第 8.4 节）：同一个程序跑两次，**分别打印出 `42` 和 `34`**（更早一次采集还出现过 `83`）。

**为什么 `42` 那次最危险**：那块栈存储还没被别的代码覆盖，所以**侥幸读出了原值**，看起来"代码是对的"。

**关键点：编译器不会救你。**
- 不报错（语法和类型都合法）；
- 本机 `/W4` **一条警告都没有**（实测）；
- 结果还可能"看起来正确"。

**修法**：改成**按值捕获** `[local]`，让闭包拷一份进去（第 8.5 节第一个实测，输出稳定为 `42 7`）。

**判据**：**闭包要活过被捕获的变量，就必须按值捕获。** `[&]` 只在"闭包当场用完就死"（比如传给 `std::sort` 的比较函数）时才安全。
</details>

**6.** 第 6.4 节那个 `dive()` 程序，编译时给了什么警告？运行结果是什么？这两件事说明了什么？

<details><summary>答案</summary>

**编译警告（本机实测）**：
```text
main.cpp(8) : warning C4717: “dive”: 如递归所有控件路径，函数将导致运行时堆栈溢出
```

**运行结果（本机实测）**：
```text
（stdout 无任何输出）
退出码：3221225725
```

`3221225725` = `0xC00000FD` = Windows 的 `STATUS_STACK_OVERFLOW`。

**这两件事说明三点**：

1. **编译器能做控制流分析**：`C4717` 说的是"**所有**控件路径都会递归"，也就是它**证明**了必然溢出。
2. **但证明归证明，它只是警告**：程序照样生成了，你照样能运行它。**编译器不会替你阻止 UB。**
3. **"栈溢出"的表现是进程被操作系统终止**，不是"函数返回一个错误值"。所以 `std::cout << depth` 一个字都没打印——那行根本没执行到。

**为什么这道题值得记**：它同时是**未定义行为**和**平台差异**的例子——多深会溢出取决于栈大小、每帧字节数、编译选项（第 6.4 节的坑）。
</details>

**7.** 为什么 `int f();` 和 `double f();` 不构成重载？

<details><summary>答案</summary>

**因为在调用点分不出来。** 调用者写的是 `f()`——**返回类型不出现在调用里**。

真实诊断（本机实测）：
```text
main.cpp(2): error C2556: “double f(void)”: 重载函数与“int f(void)”只是在返回类型上不同
main.cpp(2): error C2371: “f”: 重定义；不同的基类型
```

`C2371`（重定义）就是"**这不叫重载，这叫同一函数的两个定义**"的正式说法。

**背后的原则**：**重载靠的是"调用点能看见的区别"。**
- 参数列表 → 调用点看得见 ✅
- 返回类型 → 调用点看不见 ❌

**那 `f()` 的返回值类型怎么定？** 由 `f` 唯一的那份定义决定。想去区分"同一个名字、不同返回类型"，请取两个不同的名字。
</details>

**8.** 第 9 节里，把头文件中的函数定义加上 `inline` 之后，`LNK2005` 就消失了。**`inline` 是让编译器把函数体展开到调用点了吗？**

<details><summary>答案</summary>

**不是。** 这个理解是很多教程里的过时说法。

**`inline` 的实际作用是 ODR 豁免**：它告诉编译器和链接器"**这个函数在多个翻译单元里各有一份定义是允许的，它们是同一个函数，合成一份**"。

所以：

| 说法 | 对不对 |
|---|---|
| "加 `inline` 就要求把函数体展开进调用点" | ❌ 错。优化器自己决定要不要展开，你无权要求 |
| "加 `inline` 允许同一份定义出现在多个翻译单元" | ✅ **对。这是它今天的实际作用** |

**为什么"展开"那层含义过时了**：现代优化器对**任何**函数（不管有没有 `inline`）都会评估展开划不划算——函数小、调用频繁就展开，函数大就不展开。你写的 `inline` 现在基本只影响**链接行为**。

**本机证据**（第 9.2 / 9.3 节，两次真实编译）：
```text
（不加 inline）math_utils.obj : error LNK2005: "int __cdecl add(int,int)" (?add@@YAHHH@Z) 已经在 main.obj 中定义
（加了 inline）  编译链接全部通过，程序输出 5 10
```

**并且要注意**：本章示例都是不优化（`/Od`）编译的，**"有没有真的展开"没有任何工具输出支撑**——所以本讲义对"某个函数被展开了"不做任何断言（第 9.3 节的 ⚠️）。
</details>

**9.** 下面这个 `assert` 会在发布版本里变成什么？为什么说它是个 bug？

```cpp
int x = 0;
assert(++x > 0);
std::cout << x << '\n';
```

<details><summary>答案</summary>

**在定义了 `NDEBUG` 的版本里，整行 `assert(++x > 0);` 会被替换成"什么都不做"，于是 `++x` 根本不执行。**

**本机实测（第 10.3 节）**：
```text
（不开 NDEBUG）输出：1
（开 NDEBUG）  输出：0
```

**同一个程序、两种结果**——因为 `x` 的自增值**依赖断言是否启用**。

**为什么是 bug**：断言里放了**副作用**。断言的定位是"**开发期自检**"，发布版会被整个删掉，所以**任何"程序正常运行需要做的事"都不能放在 `assert` 里面**。

**硬规矩**：**`assert` 里只放没有副作用的纯判断。**

**自检判据**：**把整行 `assert(...)` 删掉，程序行为应该完全不变。** 变了就是写错了。

**顺带区分**：`static_assert` 是编译期检查，**关不掉**；本章只给位置，展开在第 11 章与第 13 章。
</details>

**10.** 第 6.4 节的实测说"本机深度 1000 和 10000 都能正常返回，而无限递归崩在 `0xC00000FD`"。**能不能由此得出"本机递归安全深度是 10000"这个结论？**

<details><summary>答案</summary>

**不能。** 这是本章最该考的一道"实现定义 / 平台差异"题。

**为什么不能**：

1. **每帧占多少字节不固定**：取决于形参和局部变量的总量、编译器的优化（开了 `/O2` 之后栈帧常常变小，因为变量被塞进寄存器）、以及调用约定。本机那个例子的"每帧一个 `long long`"和别的函数的帧大小**完全不是一回事**。
2. **栈大小不固定**：Windows 默认约 1 MB，Linux 常见 8 MB，还可以由可执行文件属性或线程属性改。
3. **同一个二进制在不同机器上行为也可能不同**：栈用量还受运行环境影响。
4. **而且那 10000 这个数字来自"能正常返回"**——它只说明**没崩**，不是"安全上限"。真正的边界在 10000 和"崩掉"之间的某个地方，**本讲义没有测出那个点**（第 13 节诚实标注里点名了）。

**正确的处理方式**：**不要靠"大概够深"来设计递归。**
- 深度**由输入决定**的递归，先算它的**最坏深度**；
- 最坏深度可能很大的，改成**迭代**，或**显式限制深度**并在超限时**报告错误**（第 08 章的错误处理）；
- 确实要用深递归的，才去调栈大小——而那是平台相关的配置，不能写进可移植代码。

**这道题的更大意义**：C++ 里很多"实测出来是这样"的结论，**边界是"实现定义"而不是"标准保证"**。把实测数字当保证用，就是本章第 6.4 节那个坑的翻版。
</details>
