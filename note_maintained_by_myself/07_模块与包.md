# 07 · 模块与包

> 覆盖表条目：5.1 `import` / `from ... import` ｜ 5.2 `if __name__ == "__main__"`
> ｜ 5.3 包与 `__init__.py` ｜ 5.4 模块搜索路径与 `sys.path` ｜ 5.5 标准库概览
>
> 这一章解决**代码怎么跨文件复用**这件事。
> `import` 不是"引用一个文件"，它是**运行时执行一段代码并缓存结果**——
> 大半的"导入怪问题"都源于没意识到这一点。

---

## 0. 先记住五件事

1. **`import` 会执行被导入模块的顶层代码**，而且**只执行一次**（结果缓存在 `sys.modules` 里）。
   第二次 `import` 只是把缓存里的模块对象再绑一次名字。
2. **`__name__` 在"直接运行"时是 `"__main__"`，在"被导入"时是模块名**。
   这就是 `if __name__ == "__main__":` 存在的全部理由。
3. **搜索模块时先看内置模块，再按 `sys.path` 列表一项项找**。
   `sys.path` 的**第一项**决定"优先找谁"，而它**随启动方式变化**（脚本目录 / 当前目录 / 空串）。
4. **你自己目录里的 `json.py` 会盖掉标准库的 `json`**——因为 `sys.path[0]` 通常排在标准库前面。
   内置模块（如 `math`）盖不掉。
5. **相对导入（`from . import x`）只在"这个文件是包的一部分被导入"时有效**。
   直接 `python 包/文件.py` 跑它 → `ImportError: attempted relative import with no known parent package`。

## 1. `import` / `from ... import`（覆盖 5.1）

本章的实验都在系统临时目录下做的（一个隔离的测试目录），**没有在笔记目录里留下任何 `.py` 文件**。
下面出现的路径都是临时目录，你照着在自己机器上建同名文件即可。

### 1.1 四种写法

```python
import math                     # 最常用：导入模块，用 math.sqrt 访问
import math as m                # 起别名
from math import sqrt           # 只拿一个名字
from math import sqrt as sq     # 给这个名字起别名


print("import math 后要写全名:", math.sqrt(9))    # 3.0
print("别名 m:", m.sqrt(9))                       # 3.0
print("from math import sqrt:", sqrt(9))          # 3.0
print("别名 sq:", sq(9))                          # 3.0
```

**这四种写法指向的是同一个模块对象**，不会产生第二份：

```python
import sys

print("math is sys.modules['math'] ->", math is sys.modules["math"])   # True
print("math.sqrt is m.sqrt ->", math.sqrt is m.sqrt)                   # True
```

**怎么选**：

| 写法 | 什么时候用 | 代价 |
|---|---|---|
| `import math` | 默认选择 | 每次要写 `math.` 前缀 |
| `import numpy as np` | 名字长、社区有约定俗成的缩写 | 缩写得让所有人认识（`np`、`pd` 是共识） |
| `from math import sqrt` | 只用一两个函数，且**名字不会歧义** | `sqrt` 这名字很明确，但 `from os import path` 就不明确 |
| `from math import sqrt as sq` | 名字和本地变量/别的模块撞了 | 多一层需要记住的映射 |

**一条实用判据**：`from X import Y` 之后，读代码的人看到 `Y` **不知道它从哪来**。
所以只对"大家都认识"的名字用（`sqrt`、`dataclass`、`Path`），
不确定就写 `import X` + `X.Y`。

### 1.2 为什么不推荐 `from math import *`

它把模块里所有"公开名字"倒进当前命名空间。实测一下倒进来多少：

```python
ns = {}
exec("from math import *", ns)
keys = sorted(k for k in ns if not k.startswith("__"))
print("导入进来的名字个数:", len(keys))    # 62
print("前 20 个:", keys[:20])
# ['acos', 'acosh', 'asin', 'asinh', 'atan', 'atan2', 'atanh', 'cbrt', 'ceil', 'comb',
#  'copysign', 'cos', 'cosh', 'degrees', 'dist', 'e', 'erf', 'erfc', 'exp', 'exp2']
print("pi 在不在:", "pi" in ns)             # True
```

`math` 只是个小模块就带来 **62 个名字**。三个问题：

1. **你根本不知道带进来了什么**，也无法一眼看出某个名字是谁提供的
2. **容易撞车**：`from math import *` 带来的 `e` 会盖掉你自己的 `e`
3. **它在函数体里是 `SyntaxError`**（只有模块顶层允许）——这是 Python 故意的限制

**唯一的正当场合**：交互式调试时图省事（`>>> from math import *`）。
**任何要保存下来的 `.py` 文件都不该写它。**

**例外是包自己的 `__init__.py`**：包作者会用 `__all__` 明确控制 `from pkg import *` 带出什么
（见 3.3 节）。那是"作者设计好的公开接口"，跟"随便倒库"不是一回事。

### 1.3 `import a.b.c` 之后名字是什么

这是最容易搞错的一点。假设目录是这样（`pkg_a/` 和 `pkg_a/sub/` 下都有 `__init__.py`）：

```
pkg_a/
├── __init__.py
└── sub/
    ├── __init__.py
    └── leaf.py         # 里面有 VALUE = "leaf 里的值"
```

```python
import pkg_a.sub.leaf

print("pkg_a 存在:", "pkg_a" in dir())                     # True
print("pkg_a.sub.leaf.VALUE =", pkg_a.sub.leaf.VALUE)      # leaf 里的值
```

**`import a.b.c` 只在当前命名空间绑定 `a`**，`b` 和 `c` 都不绑定——
实测 `print(sub)` 和 `print(leaf)` 分别报 `NameError: name 'sub' is not defined` /
`NameError: name 'leaf' is not defined`。

**但你可以从 `pkg_a` 一路点下去**（`pkg_a.sub.leaf.VALUE`），因为导入子模块时，
Python 会把每个子模块**挂到它的父模块上**当作属性。

想直接拿到子模块或里面名字，用 `from`：

```python
from pkg_a.sub import leaf      # 现在 leaf 这个名字有了
from pkg_a.sub.leaf import VALUE  # 或者直接拿里面的名字
```

> ⚠️ **坑**：以为 `import a.b.c` 就能直接用 `b` 或 `c`
> **现象**：`NameError: name 'b' is not defined`。
> **原因**：`import a.b.c` 只把**最外层名字 `a`** 绑进当前命名空间。
> **处理**：要么写全 `a.b.c.x`，要么 `from a.b import c`。
> 报错里的那个名字一眼就能看出你漏了哪一层。

### 1.4 导入会执行模块顶层代码（实测）

建立两个文件：

```python
# sideeffect.py
"""一个带顶层副作用的模块。"""
print("[sideeffect] 模块顶层代码开始执行")
print("[sideeffect] __name__ =", __name__)
VALUE = 42
print("[sideeffect] VALUE 已定义:", VALUE)
print("[sideeffect] 模块顶层代码执行结束")
```

```python
# main_idem.py
print("--- 第 1 次 import ---")
import sideeffect

print("--- 第 2 次 import ---")
import sideeffect

print("--- 第 3 次 import ---")
import sideeffect
```

`python main_idem.py` 的真实输出：

```
--- 第 1 次 import ---
[sideeffect] 模块顶层代码开始执行
[sideeffect] __name__ = sideeffect
[sideeffect] VALUE 已定义: 42
[sideeffect] 模块顶层代码执行结束
--- 第 2 次 import ---
--- 第 3 次 import ---
```

**两个结论一起看**：

1. **导入确实执行了顶层代码**（那四行打印发生了）
2. **但只执行了一次**——第 2、3 次 `import` 什么都没打印

### 1.5 导入是幂等的：`sys.modules` 缓存

**为什么只执行一次**：Python 把已加载的模块缓存在一个 dict 里——`sys.modules`。
导入时先查这个 dict，命中就直接返回缓存对象，**不重新执行文件**。

```python
import sys

print("sys.modules['sideeffect'] is sideeffect ->",
      sys.modules["sideeffect"] is sideeffect)     # True
print("VALUE =", sideeffect.VALUE)                 # 42
```

`is` 为 `True`——**全局只有一个模块对象**，所有 `import` 语句拿到的是同一个。

> **这条推翻了几个常见误解**：
> - "我在两个文件里都 `import utils`，会不会加载两次？" → **不会**，第二次拿缓存。
> - "模块里的全局变量在 A 文件改、B 文件能看见吗？" → **能**，因为是同一个对象。
>   但**不要这么做**——那是隐式全局状态，调试时是噩梦。

**缓存是按"模块名"而不是按"文件路径"键的**。所以同一个文件用两种名字导入
（比如 `import json` 和 `import 本地/json.py`）会是**两个不同的模块对象**——
这正是 4.4 节那个"同名覆盖"坑的另一面，也是 2.3 节"自导入执行两次"的原因。

### 1.6 `from` 导入的名字可以本地覆盖

```python
import math
import sys

math = "我把它改成一个字符串了"       # 这行只改本地名字
print(math)                                        # 我把它改成一个字符串了
print("但 sys.modules['math'] 没变:", sys.modules["math"].sqrt(16))   # 4.0

import math as math2
print("再 import 一次拿回模块:", math2.sqrt(16))    # 4.0
```

**`math = ...` 只是把这个本地名字重新绑定**，`sys.modules` 里的模块对象毫发无损。
这也说明：**模块名就是普通变量名**，跟第 4.4 节的"命名与绑定"规则完全一致。

### 1.7 循环导入

**循环导入** = A 导入 B，B 又导入 A。这是真实项目里最常见的结构性问题之一。

**情形一：顶层只互相 `import` → 能跑完。**

```python
# a.py
print("[a] 顶层开始")
import b
print("[a] 导入 b 成功")


def func_a():
    return "a 的函数"


print("[a] 顶层结束")
```

```python
# b.py
print("[b] 顶层开始")
import a
print("[b] 导入 a 成功")


def func_b():
    return "b 的函数"


print("[b] 顶层结束")
```

`python a.py` 的真实输出：

```
[a] 顶层开始
[b] 顶层开始
[a] 顶层开始          ← 注意：a 被"重新进入"了，但没重跑完
[a] 导入 b 成功
[a] 顶层结束
[b] 导入 a 成功
[b] 顶层结束
[a] 导入 b 成功
[a] 顶层结束
```

**读这段输出**：`a.py` 开始跑 → 遇到 `import b` → `b.py` 开始跑 → `b.py` 遇到 `import a`
→ 此时 `a` **已经在 `sys.modules` 里**（虽然还没执行完），所以 `import a` **立刻返回那个半成品模块**
→ `b.py` 继续跑完 → 回到 `a.py` 继续跑完。

**关键点**：`b.py` 拿到的 `a` 是**还没执行完的** `a`。它之所以没报错，是因为
`b.py` 在顶层**只是 `import a`，没有访问 `a` 的任何属性**。

**情形二：在顶层访问对方的属性 → `AttributeError`。**

```python
# a2.py
print("[a2] 顶层开始")
import b2
print("[a2] 拿到 b2.func_b 的引用：", b2.func_b)      # ← 这里访问了


def func_a():
    return "a2 的函数"


print("[a2] 顶层结束")
```

```python
# b2.py
print("[b2] 顶层开始")
import a2
print("[b2] 尝试用 a2.func_a：", a2.func_a)           # ← 这里访问了


def func_b():
    return "b2 的函数"


print("[b2] 顶层结束")
```

`python a2.py` 的真实输出：

```
[a2] 顶层开始
[b2] 顶层开始
[a2] 顶层开始
Traceback (most recent call last):
  File "a2.py", line 3, in <module>
    import b2
  File "b2.py", line 3, in <module>
    import a2
  File "a2.py", line 5, in <module>
    print("[a2] 拿到 b2.func_b 的引用：", b2.func_b)
                                          ^^^^^^^^^
AttributeError: module 'b2' has no attribute 'func_b' (consider renaming
'...\\b2.py' if it has the same name as a library you intended to import)
```

**为什么**：`b2` 这时也还是半成品——它卡在 `import a2` 那一行，下面的 `def func_b` 还没执行，
所以 `b2` 这个模块对象上**还没有 `func_b` 这个属性**。

**情形三：`from ... import` 形式 → `ImportError`（更早就炸）。**

```python
# c.py
print("[c] 顶层开始")
from d import func_d
print("[c] 拿到 func_d:", func_d)


def func_c():
    return "c 的函数"


print("[c] 顶层结束")
```

```python
# d.py
print("[d] 顶层开始")
from c import func_c
print("[d] 拿到 func_c:", func_c)


def func_d():
    return "d 的函数"


print("[d] 顶层结束")
```

`python c.py` 的真实输出：

```
[c] 顶层开始
[d] 顶层开始
[c] 顶层开始
[d] 顶层开始
[c] 顶层开始
Traceback (most recent call last):
  File "c.py", line 3, in <module>
    from d import func_d
  File "d.py", line 3, in <module>
    from c import func_c
  File "c.py", line 3, in <module>
    from d import func_d
ImportError: cannot import name 'func_d' from 'd' (consider renaming
'...\\d.py' if it has the same name as a library you intended to import)
```

`from d import func_d` 要求 `d` 里**此刻**已经有 `func_d` 这个属性——而它没有。

**修法：把 `import` 挪进函数，用到时才导。**

```python
# a3.py
print("[a3] 顶层开始")
# 顶层不导入 b3，避免循环


def func_a():
    import b3                 # 用时才导入
    return "a3 -> " + b3.func_b()


print("[a3] 顶层结束")

if __name__ == "__main__":
    print("调用结果:", func_a())
```

```python
# b3.py
print("[b3] 顶层开始")
import a3
print("[b3] 导入 a3 成功")


def func_b():
    return "b3 的函数"


print("[b3] 顶层结束")
```

`python a3.py` 的真实输出：

```
[a3] 顶层开始
[a3] 顶层结束
[b3] 顶层开始
[a3] 顶层开始
[a3] 顶层结束
[b3] 导入 a3 成功
[b3] 顶层结束
调用结果: a3 -> b3 的函数
```

**能跑通的原因**：`a3.py` 顶层**不导入** `b3`，所以 `b3.py` 被导入时 `a3` 已经**完全执行完**了。
`import b3` 被推迟到 `func_a()` 真的被调用时，那时 `b3` 早就准备好了。

> ⚠️ **坑**：循环导入
> **现象**：`AttributeError: module 'b2' has no attribute 'func_b'` 或
> `ImportError: cannot import name 'func_d' from 'd'`，而且**报错位置看起来很莫名**（在一个 import 行上）。
> **原因**：两个模块互相导入，其中一个拿到的是**还没执行完的半成品模块**，
> 半成品上自然没有后面才定义的东西。
> **处理**（按优先级）：
> 1. **首选：去掉循环依赖**。抽出一个第三方模块，让 A 和 B 都导入它。
>    循环导入通常是"职责划分不清"的症状，改结构比改导入方式更有价值。
> 2. 把 `import` 挪进函数（延迟到运行时）。
> 3. 顶层只用 `import X`（不用 `from X import 名字`）——它不要求属性此刻存在。

## 2. `if __name__ == "__main__"`（覆盖 5.2）

### 2.1 真的要建两个文件才能看清

```python
# greetmod.py
"""演示 __name__ 在两种场合的值。"""
print("这个文件被加载了，__name__ =", __name__)


def add(a, b):
    return a + b


def main():
    print("main() 执行：add(1, 2) =", add(1, 2))


if __name__ == "__main__":
    main()
```

```python
# use_greetmod.py
"""导入 greetmod，观察 __name__ 与是否执行 main。"""
print("--- 准备 import greetmod ---")
import greetmod

print("--- import 完成 ---")
print("从外面看到的 greetmod.__name__ =", greetmod.__name__)
print("调用它的函数:", greetmod.add(10, 20))
```

**三种运行方式，实测输出：**

```bash
# ① 直接运行
python greetmod.py
```

```
这个文件被加载了，__name__ = __main__
main() 执行：add(1, 2) = 3
```

```bash
# ② 被别的文件 import
python use_greetmod.py
```

```
--- 准备 import greetmod ---
这个文件被加载了，__name__ = greetmod
--- import 完成 ---
从外面看到的 greetmod.__name__ = greetmod
调用它的函数: 30
```

**注意 `main()` 那一行没出现**——`if` 条件不成立，所以没执行。

```bash
# ③ 用 -m 当模块跑
python -m greetmod
```

```
这个文件被加载了，__name__ = __main__
main() 执行：add(1, 2) = 3
```

**`-m` 和"直接运行"在这件事上效果一样**（都是 `__main__`），区别在 `sys.path[0]`（见第 4 节）。

| 运行方式 | `__name__` 的值 | `if` 里执行吗 |
|---|---|---|
| `python greetmod.py` | `"__main__"` | ✅ |
| `python -m greetmod` | `"__main__"` | ✅ |
| `import greetmod` | `"greetmod"` | ❌ |

### 2.2 为什么必须写

**不写的话，任何 `import utils` 都会顺带执行你写在底部的测试代码。**

```python
# utils_bad.py —— 反面例子
def add(a, b):
    return a + b


print("跑一下看看：", add(1, 2))      # ← 忘了放进 if 里
```

别人 `import utils_bad`，屏幕上莫名其妙出现 `跑一下看看： 3`。
更糟的情况：底部代码是"读一个配置文件""连一个数据库""启动一个服务"——
**import 一个模块不该有这种副作用**。

**推荐结构**（这就是标准写法）：

```python
"""模块的 docstring：一句话说明这个模块干什么。"""
import os
import sys


def add(a, b):
    """把两个数加起来。"""
    return a + b


def main():
    """命令行入口：所有"跑起来才有意义"的代码放这里。"""
    print(add(1, 2))


if __name__ == "__main__":
    main()
```

四个要点：

1. **import 放最上面**（PEP 8 的约定：标准库 → 第三方 → 自己的模块，分组空行隔开）
2. **业务逻辑写在函数里**，不写在顶层
3. **`main()` 收拢所有"执行型"代码**
4. **`if __name__ == "__main__": main()`** 放在**文件最后**

### 2.3 一个顺带挖出来的坑：直接运行的文件能被自己 import

```python
# selfimport.py
print("顶层开始，__name__ =", __name__)
import selfimport
print("import 自己之后 __name__ =", __name__)
print("selfimport.__name__ =", selfimport.__name__)
```

`python selfimport.py` 的真实输出：

```
顶层开始，__name__ = __main__
顶层开始，__name__ = selfimport
import 自己之后 __name__ = selfimport
selfimport.__name__ = selfimport
顶层开始，__name__ = __main__
import 自己之后 __name__ = __main__
selfimport.__name__ = selfimport
```

**顶层代码执行了两次**，而且是**两个不同的模块对象**：

- 一个是 `__main__`（`python selfimport.py` 加载的那份）
- 一个是 `selfimport`（被 `import selfimport` 加载的那份）
- 它们**共享同一个 `.py` 文件，但是两个独立的对象、各自的全局变量互不相通**

**加 `if __name__ == "__main__":` 就能防住**：`selfimport` 那份的 `__name__` 是 `"selfimport"`，
条件不成立，顶层那些代码就不会跑第二遍。

> ⚠️ **坑**：模块的顶层代码被执行了两次（或"改了一个文件里的全局变量，另一个文件读不到"）
> **现象**：`import 自己`、或"同一个文件既当脚本跑又被 import"时，顶层副作用重复发生。
> **原因**：直接运行的文件其模块名是 `__main__`；被 import 时用文件名的模块名。
> **两个名字 → `sys.modules` 里两条记录 → 两个模块对象 → 顶层代码跑两遍。**
> **处理**：**永远把执行型代码放进 `if __name__ == "__main__":` 里。**
> 这是它除了"避免 import 时跑测试"之外的第二个作用。

## 3. 包与 `__init__.py`（覆盖 5.3）

### 3.1 目录即包

**模块** = 一个 `.py` 文件。
**包** = 一个**目录**，里面放模块（以及子包）。

最经典的目录结构（这种叫 **src 布局**，另一种是"平铺布局"——模块直接放项目根下）：

```
myproject/
├── pyproject.toml
├── src/
│   └── mypkg/                ← 包
│       ├── __init__.py       ← 包的"入口文件"
│       ├── models.py
│       ├── utils.py
│       └── sub/              ← 子包
│           ├── __init__.py
│           └── deep.py
└── tests/
    └── test_utils.py
```

对应的导入写法：

```python
import mypkg                 # 导入包本身（执行 __init__.py）
import mypkg.models          # 导入包里的模块
from mypkg import models     # 同上，绑定 models 这个名字
from mypkg.models import User          # 导入模块里的名字
from mypkg.sub.deep import helper      # 导入子包里的模块里的名字
```

`src/` 布局的好处：**逼你从"已安装的包"角度思考**，避免"因为在当前目录就碰巧能 import"的假象。
（这一层属于工程话题，`00_知识点总览.md` 第四节把它划到了不展开的范围，这里只提名字。）

### 3.2 `__init__.py` 的三件事

建一个包，`__init__.py` 里写点东西：

```python
# plainpkg/__init__.py
print("[plainpkg.__init__] 执行")
__version__ = "1.0"
HIDDEN = "不想被 * 带出去"
__all__ = ["helper", "__version__"]
from . import helper
```

```python
# plainpkg/helper.py
NAME = "helper"


def hi():
    return "hi from helper"
```

```python
# plainpkg/_internal.py
SECRET = "内部实现"
```

```python
import plainpkg

print("plainpkg.__file__ =", plainpkg.__file__)
# ...\plainpkg\__init__.py
print("plainpkg.__path__ =", plainpkg.__path__)
# [...\plainpkg]
print("plainpkg.__version__ =", plainpkg.__version__)      # 1.0
print("plainpkg.helper.NAME =", plainpkg.helper.NAME)      # helper
print("plainpkg.helper.hi() =", plainpkg.helper.hi())      # hi from helper
print("有 helper 吗:", hasattr(plainpkg, "helper"))        # True
print("有 _internal 吗:", hasattr(plainpkg, "_internal"))  # False
```

**第一行输出就是 `[plainpkg.__init__] 执行`**——证明 `__init__.py` 被当作"导入包"时执行的代码。

**三件事**：

| 作用 | 说明 |
|---|---|
| **① 标记这个目录是常规包** | 有它就按"常规包"处理（和命名空间包的区别见 3.4） |
| **② 它的代码在导入包时执行** | 可以放初始化：版本号、预导入子模块、做环境检查 |
| **③ 可以用 `__all__` 控制 `from pkg import *`** | 见 3.3 |
| 附：`__path__` | 包对象有 `__path__`（**模块对象没有**），它是"这个包的子模块去哪找"的目录列表 |

**`__init__.py` 可以是空的**——那也是一种正当写法（只用来标记"这是常规包"）。
**但更好的做法**是把它当"包的公开门面"：把想让用户用的名字在这里 import 进来。

**为什么 `_internal` 没有出现在 `plainpkg` 上**：因为 `__init__.py` 里只 `from . import helper`，
**没有** import `_internal`。**`__init__.py` 里 import 什么，包里就有什么。**

### 3.3 `__all__` 控制 `from pkg import *`

```python
ns = {}
exec("from plainpkg import *", ns)
exported = sorted(k for k in ns if not k.startswith("__") or k == "__version__")
print("exported:", exported)                  # ['__version__', 'helper']
print("HIDDEN 进来了吗:", "HIDDEN" in ns)      # False
```

因为 `__init__.py` 里写了 `__all__ = ["helper", "__version__"]`，
所以 `import *` **只带出这两个名字**，`HIDDEN` 被挡住了。

**没有 `__all__` 会怎样**：`import *` 会带出所有**不以 `_` 开头**的名字。
所以：

- **想让名字不被 `*` 带出** → 用 `_` 开头（约定）
- **想精确控制** → 写 `__all__`（显式）
- **`__all__` 也可以给模块用**（不只是包）

> **这是"给包作者的工具"**，不是给使用者的。你写业务代码时只需要知道
> "`from pkg import *` 带出来的东西是包作者选过的"，其余按 1.2 节的原则——别用它。

### 3.4 命名空间包（没有 `__init__.py`）

**新问题**：如果目录里**没有** `__init__.py`，它还能是包吗？

**能。** 从 **3.3 版开始**（**未实测起始版本**，官方记 3.3；本机 3.13.15 实测可用）
这种东西叫**命名空间包**（namespace package）。

```python
import nspkg        # nspkg/ 目录里没有 __init__.py，只有 mod.py

print("nspkg =", nspkg)
# <module 'nspkg' (namespace) from ['...\\nspkg']>
print("has __file__?", hasattr(nspkg, "__file__"))     # True
print("__file__ =", nspkg.__file__)                    # None   ← 注意是 None
print("__path__ =", list(nspkg.__path__))              # ['...\\nspkg']
print("__loader__ =", nspkg.__loader__)
# <_frozen_importlib_external.NamespaceLoader object at 0x...>

import nspkg.mod

print("nspkg.mod.MARK =", nspkg.mod.MARK)              # nspkg.mod
```

**怎么认出来它是命名空间包**：

| 特征 | 常规包 | 命名空间包 |
|---|---|---|
| `__init__.py` | 有 | **没有** |
| `__file__` | 指向 `__init__.py` 的路径 | **`None`** |
| `__loader__` | `SourceFileLoader` | **`NamespaceLoader`** |
| `print(模块)` | `<module 'x' from '...'>` | `<module 'x' (namespace) from [...])` |
| `__path__` | 一个目录 | 一个目录列表（可以**多个**目录） |

**它解决什么问题**：让**多个不同的目录**共同组成一个包。

```
site-packages/
├── company_core/          ← 没有 __init__.py
│   └── logging_utils.py
└── company_extra/         ← 没有 __init__.py
    └── auth_utils.py
```

装了这两个包之后，`import company_core.logging_utils` 和 `import company_extra.auth_utils`
都能用——假设它们被放在**同一个父目录**下，就能组合成一个命名空间包（这是
"把一个大项目拆成多个可独立发布的包，但共享一个顶层包名"的常见做法）。

**实务上的取舍**：

| 用常规包（有 `__init__.py`） | 用命名空间包 |
|---|---|
| 绝大多数情况。**默认选这个** | 需要"多个目录拼一个包"（大厂内部多团队共享顶层包名） |
| 可以写初始化代码、可以用 `__all__` | 不能写初始化代码（没有那个文件） |
| 结构一目了然：有 `__init__.py` 就是包 | **容易误判**：忘了建 `__init__.py`，包就"看起来能 import 但少了初始化" |

> ⚠️ **坑**：忘了建 `__init__.py`
> **现象**：包居然能 import，但 `__init__.py` 里本该做的事（注册、版本号、预导入）全没发生；
> 或者反过来说"我明明是常规包，怎么 `pkg.子模块` 报 `AttributeError`"。
> **原因**：没有 `__init__.py` 的目录会被当成**命名空间包**，它**不会执行任何初始化代码**。
> **处理**：想要常规包就**建一个 `__init__.py`（空的也行）**。
> 用 `hasattr(pkg, "__file__") and pkg.__file__ is None` 可以验证自己拿到的是不是命名空间包。

### 3.5 相对导入

**相对导入**用点号表示"相对于我所在的包"：

```python
from . import cousin            # 同一层（同一个包里）的模块
from .. import sibling          # 上一层的模块
from .sub import deep           # 子包里的模块
```

**`from ..` 的 `..` 数量 = 往上走几层。** 一个点 = 当前包，两个点 = 父包。

实测（目录：`usepkg/` 和 `usepkg/sub/` 都有 `__init__.py`）：

```python
# usepkg/sub/deep.py
from . import cousin
from .. import sibling


def report():
    return (cousin.C, sibling.S)
```

```python
from usepkg.sub import deep

print("deep.report() =", deep.report())
# ('我是 usepkg.sub.cousin', '我是 usepkg.sibling')
print("deep 的 __package__ =", deep.__package__)     # usepkg.sub
print("deep 的 __name__ =", deep.__name__)           # usepkg.sub.deep
```

**它靠 `__package__` 定位**——`__package__` 是 `usepkg.sub`，所以 `from .. import sibling`
解析成 `usepkg.sibling`。

**关键限制：相对导入只在"包内被导入"时有效。**

```bash
python usepkg/sub/deep.py          # 直接跑这个文件
```

```
Traceback (most recent call last):
  File "...\usepkg\sub\deep.py", line 1, in <module>
    from . import cousin
ImportError: attempted relative import with no known parent package
```

**原因**：直接 `python 文件.py` 时，那个文件的 `__name__` 是 `"__main__"`、`__package__` 是 `None`——
**没有"父包"这个概念**，`from .` 里的那个点没有落脚处。

**正确跑法**：用 `-m` 从**包的上一层**跑。

```bash
python -m usepkg.sub.deep          # 在 usepkg 的父目录下执行
```

这时模块以 `usepkg.sub.deep` 的身份被加载，`__package__` 是 `usepkg.sub`，相对导入就能解析。

> ⚠️ **坑**：直接运行包内的文件，报 `attempted relative import with no known parent package`
> **现象**：编辑器里点了"运行当前文件"，就报这个。
> **原因**：直接跑文件时 `__package__` 是 `None`，相对导入找不到参照。
> **处理**：用 `python -m 包.子包.模块` 从**包的父目录**跑；
> 或者给这个文件加一个"绝对导入"的入口层（把执行型代码放到包外面的脚本里）。

**绝对导入 vs 相对导入**：

| | 绝对导入 `from mypkg.utils import f` | 相对导入 `from .utils import f` |
|---|---|---|
| 可读性 | 一眼看出是哪个包 | 要结合当前文件位置才知道 |
| 改包名 | 全都要改 | 不用改（相对位置没变） |
| 复制文件到别处 | 直接能用 | 可能坏掉（相对位置的包变了） |
| 直接运行文件 | 能跑（只要包在 `sys.path` 里） | **不能跑** |

**建议**：**包内部用相对导入**（这是 PEP 8 的倾向：绝对导入更清晰，但相对导入在包内更稳）；
**测试和入口脚本用绝对导入**。两者都不要混着用来同一个模块。

### 3.6 子模块不会自动出现在父包里

```python
import usepkg

print("先只导入 usepkg，有 sub 吗:", hasattr(usepkg, "sub"))
```

```
AttributeError: module 'usepkg' has no attribute 'sub'
```

```python
import usepkg.sub

print("导入 usepkg.sub 之后:", usepkg.sub)
# <module 'usepkg.sub' from '...\usepkg\sub\__init__.py'>
```

**`import 包` 只执行 `__init__.py`，不会自动导入子模块**（除非 `__init__.py` 自己 import 了）。

想"导入包就能用子模块"，就在 `__init__.py` 里预先导入：

```python
# usepkg3/__init__.py
from . import sub
```

```python
import usepkg3

print("usepkg3.sub 直接可用:", usepkg3.sub.Y)     # 2
```

> **取舍**：预导入方便，但**会让 `import 包` 变慢**（连带加载所有子模块），
> 还可能与别的子模块形成循环导入。常见做法是给一个"常用的那几个"预导入，
> 而不是全导。

## 4. 模块搜索路径与 `sys.path`（覆盖 5.4）

### 4.1 搜索顺序：内置模块 → `sys.path`

写 `import x` 时，Python 按这个顺序找：

1. **`sys.modules` 缓存**（在第 1.5 节讲过）——命中就直接返回，不往下走
2. **内置模块**（`sys.builtin_module_names` 里的那些，编译进解释器了）
3. **`sys.path` 列表里的目录**，**从左到右**一项项找

```python
import sys
import math

print("sys.builtin_module_names 前 10 个:", sys.builtin_module_names[:10])
# ('_abc', '_ast', '_bisect', '_blake2', '_codecs', '_codecs_cn', '_codecs_hk',
#  '_codecs_iso2022', '_codecs_jp', '_codecs_kr')
print("math 有没有 __file__：", hasattr(math, "__file__"))    # False
print("math:", math)                                          # <module 'math' (built-in)>
```

**内置模块没有 `__file__`**（它的代码不在文件里，在解释器里）。
这是快速判断"某个模块是不是内置的"的方法。

> **顺序很重要**：内置模块**在 `sys.path` 之前**。
> 所以你在项目目录放一个 `math.py`，**`import math` 拿到的还是内置的 math**——
> 实测 `hasattr(math, "FAKE")` 为 `False`（4.4 节有完整实验）。
> 但标准库的**纯 Python 模块**（`json`、`os` 的一部分）是在 `sys.path` 里找的，**能被盖掉**。

### 4.2 `sys.path[0]` 是什么：四种模式实测

`sys.path` 的第一项**随启动方式变化**。这是最容易搞混的一点，逐一实测：

**① 脚本模式（`python script.py`）→ 脚本所在目录的绝对路径**

在 `%TEMP%\dsh_path\` 下建 `showpath.py`，然后**从别的目录**调用它：

```bash
cd %TEMP%
python %TEMP%\dsh_path\showpath.py
```

```python
import sys

print(repr(sys.path[0]))
```

```
'C:\\Users\\Wang\\AppData\\Local\\Temp\\dsh-uCJMDY\\dsh_path'
```

**注意：不是当前工作目录，是脚本所在目录。** 这条非常重要——
它意味着"在项目根目录下 `python src/main.py`"时，`src/` 会被加进 `sys.path`，
而项目根目录**不在** `sys.path` 里（除非你额外处理）。

完整列表（本机实测）：

```
[0] 'C:\\...\\dsh_path'                                    ← 脚本所在目录
[1] 'C:\\...\\Python313\\python313.zip'                    ← 标准库 zip（一般不用）
[2] 'C:\\...\\Python313\\DLLs'
[3] 'C:\\...\\Python313\\Lib'                              ← 标准库
[4] 'C:\\...\\Python313'
[5] 'C:\\...\\Python313\\Lib\\site-packages'                ← 第三方包
```

**② `python -c "..."` → 空字符串 `''`**

```bash
python -c "import sys; print(repr(sys.path[0]))"
```

```
''
```

**空字符串的含义是"当前工作目录"**（在 import 的那一刻）。

**③ REPL（`python` 直接进去）→ 同样是 `''`**

**④ `python -m 模块` → 当前工作目录的绝对路径**

建一个 `mmod2.py`，先用 `-m` 从**别处**跑（需要 `PYTHONPATH` 帮忙找到它），
观察 `path[0]`：

```bash
# 在别的工作目录下，用 -m
python -m mmod2
```

```
path[0] = 'C:\\Users\\Wang\\AppData\\Local\\Temp\\dsh-uCJMDY'      ← 当前工作目录（绝对路径）
cwd     = C:\\Users\\Wang\\AppData\\Local\\Temp\\dsh-uCJMDY
__file__= C:\\...\\dsh_path\\mmod2.py                              ← 但文件其实在子目录里
```

**对比脚本模式（同一个文件、同一个工作目录）**：

```bash
python C:\...\dsh_path\mmod2.py
```

```
path[0] = 'C:\\...\\dsh_path'      ← 脚本所在目录
cwd     = C:\\Users\\Wang\\AppData\\Local\\Temp\\dsh-uCJMDY
__file__= C:\\...\\dsh_path\\mmod2.py
```

**这是 `-m` 和直接跑文件最本质的区别**：

| | `python script.py` | `python -m pkg.mod` |
|---|---|---|
| `sys.path[0]` | **脚本所在目录**的绝对路径 | **当前工作目录**的绝对路径 |
| `__name__` | `"__main__"` | `"__main__"` |
| `__package__` | `None`（所以相对导入不行） | 模块所属的包（所以相对导入行） |

> **实用推论**：想跑包里的模块、并且让它内部的相对导入工作 → **用 `-m`，并在包的父目录下执行**。
> 这正好是 3.5 节那个坑的正解。

**⑤ 从标准输入读代码（`... | python -`）→ 当前工作目录**（本机实测）。

### 4.3 `PYTHONPATH` 环境变量

`PYTHONPATH` 让你**手动往 `sys.path` 里插目录**。它插在 `sys.path[0]` **之后**、标准库之前。

```powershell
$env:PYTHONPATH = "C:\Windows"
python -c "import sys; print(sys.path[:4])"
```

```
['', 'C:\\Windows', 'C:\\...\\Python313\\python313.zip', 'C:\\...\\Python313\\DLLs']
```

**位置就是 `[1]`**（`[0]` 是空串=当前目录）。这说明 `PYTHONPATH` 优先级**高于标准库**——
所以它也能用来覆盖标准库模块（危险）。

**三个实测细节：**

**① Windows 上用 `;` 分隔。用 `:` 会被当成一个整体路径。**

```powershell
$env:PYTHONPATH = "C:\Windows:C:\Users"   # ← 这是 Linux 写法
python -c "import sys; print(sys.path[:4])"
```

```
['', 'C:\\Windows:C:\\Users', 'C:\\...\\python313.zip', 'C:\\...\\DLLs']
```

**`C:\Windows:C:\Users` 成了一个条目**（而 Windows 路径里本来就可能含 `:`，比如 `C:`）。
Python 用 `os.pathsep` 来切分，本机实测 `os.pathsep` 是 `';'`：
所以**必须写 `C:\Windows;C:\Users`**。

**② 重复条目会被去重。**

```powershell
$env:PYTHONPATH = "C:\Windows;C:\Windows"
python -c "import sys; print(sys.path.count(r'C:\Windows'))"
```

```
1
```

**③ 不存在的目录也会被加进去**（不报错，只是永远匹配不到）。

```powershell
$env:PYTHONPATH = "C:\no\such\dir\here"
python -c "import sys; print(sys.path[:3])"
```

```
['', 'C:\\no\\such\\dir\\here', 'C:\\...\\python313.zip']
```

> ⚠️ **诚实标注（未实测）**：**在 Git Bash 里 `PYTHONPATH` 该用 `:` 还是 `;`，我没有实测。**
> 原因是本沙箱环境里 Git Bash 起不来：执行 `bash -lc ...` 时报
> `bash.exe: *** fatal error - couldn't create signal pipe, Win32 error 5`（信号管道的创建被拒绝）。
> 按常识推断：Git Bash 下 `PYTHONPATH` 传给的是 **Windows 版 `python.exe`**，
> 它读的是 `os.pathsep`（`;`）。MSYS 有时会把 `:` 形式自动转成 Windows 路径列表，
> 但那属于 MSYS 的路径转换行为，**我没有验证过，请以实测为准**。
> **稳妥做法**：在 Windows（含 Git Bash）里一律用 `;`。
> 设置方式：
> ```powershell
> # PowerShell（只影响当前窗口）
> $env:PYTHONPATH = "C:\my\libs"
> # PowerShell（永久，需要重开终端）
> [Environment]::SetEnvironmentVariable("PYTHONPATH", "C:\my\libs", "User")
> ```
> ```bash
> # Git Bash（只影响当前窗口）
> export PYTHONPATH="/c/my/libs"        # ← 但分隔符该用什么，本机未实测
> ```

### 4.4 同名文件覆盖标准库的坑（实测）

**这是本节最有价值的坑。** 建两个文件：

```python
# json.py —— 我自己写的，名字叫 json
"""这是我的 json.py —— 它会抢走标准库 json 的名字。"""


def dumps(obj):
    return "我是假的 dumps，输入是: " + repr(obj)
```

```python
# test_json.py
import json

print("json 是从哪来的：", json.__file__)
print("json.dumps 的结果:", json.dumps({"a": 1}))
```

`python test_json.py` 的真实输出：

```
json 是从哪来的： C:\Users\Wang\AppData\Local\Temp\dsh-uCJMDY\dsh_shadow\json.py
json.dumps 的结果: 我是假的 dumps，输入是: {'a': 1}
```

**标准库的 `json` 被完全盖掉了。** 原因：脚本模式下 `sys.path[0]` 是脚本所在目录，
而它在标准库前面，所以先找到了你的 `json.py`。

**用 `-c` 也一样**（`path[0]` 是空串=当前目录）：

```bash
python -c "import json; print(json.__file__)"
```

```
C:\Users\Wang\AppData\Local\Temp\dsh-uCJMDY\dsh_shadow\json.py
```

**两种避开方式，都实测有效：**

```bash
# ① -P 参数：不把"当前目录/脚本目录"加进 sys.path
python -P -c "import json; print(json.__file__)"
```

```
C:\Users\Wang\AppData\Local\Programs\Python\Python313\Lib\json\__init__.py
```

```powershell
# ② PYTHONSAFEPATH 环境变量（和 -P 效果一样）
$env:PYTHONSAFEPATH = "1"
python -c "import json; print(json.__file__); print(repr(__import__('sys').path[0]))"
```

```
C:\Users\Wang\AppData\Local\Programs\Python\Python313\Lib\json\__init__.py
'C:\\Users\\Wang\\AppData\\Local\\Programs\\Python\\Python313\\python313.zip'
```

注意第二行：`path[0]` 已经**不是空串了**，直接变成了标准库的 zip。
（`-P` / `PYTHONSAFEPATH` 是 **3.11+** 才有的，**未实测起始版本**。）

**但内置模块盖不掉**——放一个 `math.py`：

```python
# math.py（假的）
FAKE = 1
print("假 math 被导入")
```

```bash
python -c "import math; print(math); print(hasattr(math,'FAKE'))"
```

```
<module 'math' (built-in)>
False
```

**假的 `math.py` 连被执行都没执行**（没有那行打印）——因为内置模块在第 1 步就命中了。

> ⚠️ **坑**：自己的文件名撞上标准库/第三方库
> **现象**：`import json` 报 `AttributeError: module 'json' has no attribute 'loads'`，
> 或者行为完全不对；也可能是"我 `pip install` 了却 import 不到正确的东西"。
> **原因**：`sys.path[0]`（脚本目录 / 当前目录）**排在标准库前面**，同名文件被优先找到。
> **处理**：
> 1. **别用这些名字当文件名**：`json.py` `os.py` `sys.py` `re.py` `random.py` `test.py` `email.py` `types.py` `copy.py` `select.py` `time.py`——以及你自己的第三方依赖名。
> 2. 已经撞了 → **改名**（最干净的解法）。
> 3. 只是想确认"到底导入了哪个" → `print(模块.__file__)`，一行诊断。
> 4. 临时验证 → `-P` 或 `PYTHONSAFEPATH=1`。
> **注意内置模块（`math` `sys` `itertools`…）盖不掉**，它们比 `sys.path` 更早命中——
> 所以"我放了个 `math.py`，怎么没用"是正常现象。

### 4.5 `site-packages` 在哪、`__pycache__` 是什么

```python
import sys
import sysconfig
import site

print("stdlib:", sysconfig.get_paths()["stdlib"])
# C:\...\Python313\Lib
print("purelib (site-packages):", sysconfig.get_paths()["purelib"])
# C:\...\Python313\Lib\site-packages
print("site.getsitepackages():")
for p in site.getsitepackages():
    print("  ", p)
#   C:\...\Python313
#   C:\...\Python313\Lib\site-packages
print("user site:", site.getusersitepackages())
# C:\Users\Wang\AppData\Roaming\Python\Python313\site-packages
```

| 目录 | 放什么 |
|---|---|
| `...\Python313\Lib` | **标准库**（随解释器一起装） |
| `...\Python313\Lib\site-packages` | **第三方包**（`pip install` 装到这里） |
| `%APPDATA%\Python\Python313\site-packages` | **用户级**第三方包（`pip install --user`） |
| `...\Python313\DLLs` | 扩展模块（`.pyd`）、DLL |

**虚拟环境会插进来两项**（本机实测 `.venv` 的 3.14.7）：

```
[5] 'C:\\Users\\Wang\\Desktop\\git\\.venv'
[6] 'C:\\Users\\Wang\\Desktop\\git\\.venv\\Lib\\site-packages'
```

这就是"为什么虚拟环境里装的东西不会污染全局、也不会看见全局的"——
**`.venv` 的 `site-packages` 插在路径更前面的位置**。

> **怎么区分一个模块是标准库还是第三方**：
> ```python
> import sys
>
> print("json" in sys.stdlib_module_names)    # True
> print("numpy" in sys.stdlib_module_names)   # False
> ```
> `sys.stdlib_module_names` 是本机实测有 **290** 个顶层名字的集合
> （**未实测起始版本**，官方记 3.10+）。
> 另一个方法是看路径里有没有 `site-packages`。

**`__pycache__` 是什么**：Python 把 `.py` 编译成字节码之后，会缓存成 `.pyc` 文件放在
`模块同目录/__pycache__/` 下，下次导入直接读缓存，跳过编译。

实测（`import sideeffect` 之后）：

```
__pycache__/
└── sideeffect.cpython-313.pyc      （558 字节）
```

文件名里的 `cpython-313` 是**解释器标签**（`sys.implementation.cache_tag` 实测为 `cpython-313`）。
**换一个 Python 版本，`.pyc` 不会被复用**（标签不同），这就是"升级 Python 后第一次跑会慢一点"的原因。

**一个重要细节：主脚本自己不生成 `__pycache__`。**
实测：`python mmod_main.py` 之后目录里**没有** `__pycache__`；
而 `python -c "import sideeffect"` 之后 `sideeffect.cpython-313.pyc` 出现了。
因为主脚本只执行一次，缓存它没有意义。

> **`.gitignore` 里该忽略 `__pycache__/` 和 `*.pyc`** ——它们是**本地生成物**，
> 换机器/换 Python 版本就废了。这和第 01 章 4.5 节说 `.venv/` 不能提交是同一个道理。

### 4.6 为什么"改 `sys.path`"是坏做法

**它确实"能用"**——实测：

```python
import sys

sys.path.append(r"C:\...\dsh_pkg\plainpkg")
import helper

print("导入到了:", helper.__file__)
# C:\...\dsh_pkg\plainpkg\helper.py
```

往 `sys.path` 里 `append` 一个目录，那个目录里的模块就能 import 了。

**但这是坏做法，四个理由：**

| 问题 | 说明 |
|---|---|
| **依赖运行位置** | 路径通常写成相对路径或硬编码绝对路径。换台机器、换个工作目录就断 |
| **导入顺序变得不可预测** | `sys.path.insert(0, ...)` 会让某个目录**盖掉**标准库或已装好的包。你今天能跑，同事机器上不能 |
| **隐藏了真实的依赖关系** | 正常 import 的模块，工具（打包器、IDE、`pip`）能分析出依赖图。运行时改路径的模块，**工具看不见** |
| **顺序敏感、难以调试** | 同一个项目里两处 `sys.path.append`，谁先执行决定导入谁。这种 bug 极难查 |

**正当替代方案：**

| 你的需求 | 正确做法 |
|---|---|
| 项目内部模块互相导入 | 用**包 + 绝对导入**（`from mypkg.utils import f`），从项目根跑 |
| 想让项目根进 `sys.path` | 装成包：`pip install -e .`（可编辑安装） |
| 脚本要跑到别的目录的模块 | 用 `PYTHONPATH` 环境变量（显式、外部可见、不污染代码） |
| 真的需要动态加载 | 用 `importlib`（明确表达"这是动态的"），而不是偷偷改路径 |

> **唯一的例外场合**：一次性脚本、教学演示、或者写"启动引导"代码（在 `-m` 之前把根目录塞进去）。
> 即使这样，也要**在文件顶部集中写、并注释说明为什么**，
> 不要散落在各个函数里。

## 5. 标准库概览（覆盖 5.5）

> **本节只做概览。完整的模块索引（一行 + 一句话 + 官方链接）在 `99_标准库索引.md`。**
> 这一节解决的是"我该往哪个方向找"，不是"这个模块怎么用"。

### 5.1 分层印象

标准库大体可以按"你什么时候会遇到它"分五层：

| 层 | 你会用它做什么 | 代表模块 |
|---|---|---|
| **① 语言基础设施** | 几乎所有代码都会碰 | `sys` `os` `types` `builtins` `warnings` `traceback` |
| **② 日常工具** | 处理数据、文本、时间、文件 | `json` `re` `datetime` `pathlib` `math` `random` `collections` `itertools` `functools` |
| **③ 工程化** | 写命令行工具、记录日志、写测试 | `argparse` `logging` `unittest` `csv` `sqlite3` `subprocess` `shutil` `tempfile` |
| **④ 网络与并发** | 联网、并行 | `urllib` `http` `socket` `email` `smtplib` `threading` `multiprocessing` `asyncio` `concurrent.futures` |
| **⑤ 生态接口** | 跟其他系统/格式打交道 | `hashlib` `base64` `struct` `zipfile` `xml` `html` `enum` `dataclasses` `typing` |

**一层层往下用的频率递减**：前两层几乎每天都用，第 ⑤ 层按需查。

### 5.2 "batteries included" 的取舍

Python 号称 **"batteries included"**（自带电池）——很多语言要靠第三方包才能做的事，
Python 标准库直接给你。

**好处**：装完 Python 就能写 HTTP 服务（`http.server`）、读写 JSON/CSV/SQLite、
压缩解压、算哈希、发邮件——**不用先解决依赖问题**。教学和原型开发极省事。

**代价（这才是要点）**：

| 代价 | 例子 |
|---|---|
| **有些模块"够用但不好用"** | `urllib` vs `requests`——后者的人机体验好一个数量级 |
| **有些模块是几十年前的设计** | `smtplib` `xml.dom` 的 API 风格陈旧 |
| **有些已被官方移除** | `cgi` / `cgitb` 在 3.13 被移除（`00_知识点总览.md` 第四节点名过） |
| **标准库必须非常保守** | 加新模块要走 PEP，所以最流行的工具往往**不在**标准库里 |

**所以"标准库 vs 第三方"的判断依据**：

| 用标准库 | 用第三方 |
|---|---|
| 功能**正好够用**（读个 JSON、写个 CSV） | 标准库的方案**要写很多胶水代码**才能用 |
| 不想引入依赖（脚本、教学、CI） | 项目本来就有一堆依赖 |
| 需要长期稳定（标准库 API 极少破坏性变更） | 需要现代 API、更好的错误信息、更好的性能 |
| 安全敏感、不想多一个供应链风险点 | 社区事实标准（`requests` `numpy` `pandas`） |

**一条经验**：**先花 10 分钟查标准库有没有**（`99_标准库索引.md` 就是为这个准备的），
**没有或明显难用，再上第三方。**

### 5.3 最常用的十个（一两句）

| 模块 | 一句话 |
|---|---|
| **`os` / `pathlib`** | 路径、目录、环境变量。**新代码优先 `pathlib`**（`Path("a") / "b"` 比 `os.path.join` 可读），但读老代码要认识 `os.path` |
| **`sys`** | 解释器本身：`sys.argv`（命令行参数）、`sys.path`、`sys.version_info`、`sys.exit()`、`sys.stdout` |
| **`json`** | 读写 JSON。`json.dumps` / `json.loads` 管字符串，`json.dump` / `json.load` 管文件。**注意没有 `s` 的那两个才是文件版** |
| **`re`** | 正则表达式。写对了极省事，写错了极难看——建议配注释和测试 |
| **`datetime`** | 日期时间。新手最大的坑是 **"朴素时间 vs 带时区时间"**（naive vs aware），详细在 `12_并发与网络.md` |
| **`collections`** | `defaultdict`（省掉"键不存在就初始化"的三行）、`Counter`（计数）、`deque`（两端快的队列）、`namedtuple` |
| **`itertools`** | 迭代器工具箱：`chain`（接起来）、`groupby`（分组）、`combinations` / `permutations`（组合排列）、`count` / `cycle` |
| **`functools`** | `lru_cache`（缓存，第 06 章 8.3 节用过）、`partial`（预填参数）、`wraps`（装饰器必备，第 06 章 7.3 节）、`reduce` |
| **`random`** | 随机数。**要可复现就先 `random.seed(1)`**（实测：同一个 seed 得到同一串 `[18, 73, 98, 9, 33]`）。**要安全用途（生成密码、令牌）不能用它**，用 `secrets` |
| **`argparse`** | 写命令行工具：位置参数、可选参数、`--help`、自动报错。`01_入门与环境.md` 3.5 节提过它 |

**完整索引（官方 Module Index 里挑出的可用项，含一句话说明和官方链接）
在第 `99_标准库索引.md`。需要找某个功能的模块时，去那里按关键词翻。**

### 5.4 第三方生态与"标准库 vs 第三方"

Python 的第三方生态（PyPI，见 `01_入门与环境.md` 第 5 节）是它最大的优势，
也是最大的认知负担——**同一个问题通常有三个以上的库**。

**几个事实上的"标准答案"**（不是标准库，但几乎所有项目都在用）：

| 领域 | 标准库方案 | 社区事实标准 |
|---|---|---|
| HTTP 请求 | `urllib.request` | `requests` |
| 数据表 | 无 | `pandas` |
| 数值数组 | 无（`array` 只是同类型数组） | `numpy` |
| 命令行 | `argparse` | `click` / `typer` |
| 测试 | `unittest` | `pytest` |
| 数据校验 | 无 | `pydantic` |
| 包管理 | `venv` + `pip` | `uv`（本仓库就用它，见 `01` 第 4.7 节） |

**判断流程**：

1. **标准库够用吗？** → 够就用标准库（少一个依赖）
2. **社区事实标准是哪个？** → 用那个（文档、Stack Overflow 答案、招人时对方会）
3. **它维护活跃吗？** → 看最近发布时间、issue 响应、有没有替代品在取代它
4. **`00_知识点总览.md` 第四节划到"不展开"的领域**（Web 框架、数据科学、
   机器学习、爬虫、GUI、打包部署）**各有独立的技能栈**，不在这份笔记的范围里。

10. 为什么"在代码里 `sys.path.append(...)`"是坏做法？给出两种正当替代方案。

<details>
<summary>答案</summary>

1. **执行一次。** 导入时 Python 先查 `sys.modules` 缓存，第一次导入后模块对象被存进去，
   第二次直接返回缓存，不重新执行文件。验证方式：
   `import sys; print(sys.modules["sideeffect"] is sideeffect)` → `True`（同一个对象）。
2. 只多了 **`pkg_a`**。`import a.b.c` 只把最外层名字 `a` 绑进当前命名空间。
   `sub` 和 `leaf` 都**不能**直接用（`NameError`），但可以从 `pkg_a` 点下去
   （`pkg_a.sub.leaf`），因为导入子模块时 Python 会把子模块挂到父模块的属性上。
3. **`from b import func_b` 更早炸**，报 `ImportError: cannot import name 'func_b' from 'b'`。
   因为它在导入时**立刻要求 `b` 里已经有 `func_b` 这个属性**；而 `b` 这时还没执行完。
   顶层只 `import b` 不访问属性，所以能在"半成品模块"上安全通过。
4. `python greetmod.py` → `"__main__"`；`import greetmod` → `"greetmod"`；
   `python -m greetmod` → 也是 `"__main__"`（`-m` 把模块当主程序跑）。
5. **顶层代码会执行两次**，而且产生**两个独立的模块对象**（一个叫 `__main__`、
   一个叫文件名的模块名），各自的全局变量互不相通。
   避免方法：把所有执行型代码放进 `if __name__ == "__main__":` 里。
6. **能**——它会被当成**命名空间包**（3.3+，本机实测可用）。
   这时候 `__file__` 是 **`None`**，`__loader__` 是 `NamespaceLoader`，
   并且 **`__init__.py` 的初始化代码不会执行**（因为没有那个文件）。
7. 直接跑文件时：`sys.path[0]` 是**该文件所在目录**（`usepkg/sub`），
   `__name__` 是 `"__main__"`、`__package__` 是 `None` → 相对导入没有参照。
   用 `-m` 时：`sys.path[0]` 是**当前工作目录**（即包的父目录），
   `__name__` 是 `"__main__"` 但 `__package__` 是 `usepkg.sub`（模块以包成员身份加载）→ 相对导入能解析。
   用 `-m` 必须在包的父目录执行，否则找不到包。
8. **`json.py` 会盖掉标准库的 `json`**；**`math.py` 不会**。
   因为 `math` 是**内置模块**（编译进解释器，`hasattr(math, "__file__")` 是 `False`），
   它在搜索顺序里排在 `sys.path` **之前**；而 `json` 是 `sys.path` 里的纯 Python 包，
   而 `sys.path[0]`（脚本目录/当前目录）排在标准库目录前面。
   用 `python -c "import json; print(json.__file__)"` 能一眼看出导入了哪个。
9. **用 `;`**（本机实测 `os.pathsep` 是 `';'`）。
   用 `:` 的话整串 `C:\Windows:C:\Users` 会被当成**一个**目录条目加进 `sys.path`
   （因为它不含 `;`），永远不会匹配到任何模块。
   另外实测：重复条目会被去重；不存在的目录也会被加进去（不报错）。
10. 坏做法的四个理由：依赖运行位置（换机器/换目录就断）、导入顺序不可预测
    （`insert(0, ...)` 会盖掉标准库或已装好的包）、隐藏真实依赖关系（打包器和 IDE 看不见）、
    顺序敏感难调试。
    正当替代：① **装成包**——`pip install -e .`（可编辑安装），让依赖关系显式化；
    ② **用 `PYTHONPATH` 环境变量**——外部可见、不污染代码；
    ③ 真的需要动态加载就用 `importlib`，明确表达意图。

</details>
