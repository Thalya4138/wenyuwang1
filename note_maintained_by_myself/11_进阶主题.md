## 0. 先记住五件事
1. **`for` 不认 `list`，只认 `__iter__`。** 任何实现了 `__iter__` 的对象都能被 `for` 遍历。
2. **迭代器是"一次性的游标"。** 一个 `list` 能遍历无数次，一个迭代器只能一次。
3. **生成器 = 会暂停的函数。** 调用它**一行代码都不执行**，只造出一个对象。
4. **装饰器的本质是"函数进、函数出"**，`@` 只是把这个动作写成一行。
5. **GIL 只保证"同一时刻一个线程跑字节码"**，所以纯计算多用线程不会变快；
   但 IO 等待时会主动放锁，所以多线程对 IO 密集仍然有用。

## 1. 可迭代对象与迭代器协议（覆盖 9.1）
### 1.1 先看现象：`for` 凭什么能工作

```python
for x in [10, 20]:          print("list:", x, end=" ")
for x in "ab":              print("str :", x, end=" ")
for x in {"a": 1, "b": 2}:  print("dict:", x, end=" ")
for x in {1, 2}:            print("set :", x, end=" ")
for x in range(2):          print("range:", x, end=" ")
print()
```

```
list: 10 list: 20 str : a str : b dict: a dict: b set : 1 set : 2 range: 0 range: 1
```

**这五种类型的共同点是什么？** 不是"都是容器"（`range(10**10)` 不存任何东西），
也不是"都有 `len`"（生成器就没有）。共同点是：
**它们都实现了 `__iter__`（或者退一步，实现了 `__getitem__`）。**

### 1.2 手写一个可迭代对象（实测）
规范说法是：**能被 `for` 遍历的东西叫"可迭代对象"（iterable），
它的义务是"能交出迭代器"。** 而"迭代器"的义务是"能交出下一个"。

```python
class Countdown:
    """可迭代对象：每次 __iter__ 返回一个全新的迭代器"""

    def __init__(self, start):
        self.start = start

    def __iter__(self):
        print("      [Countdown.__iter__ 被调用]")
        return CountdownIterator(self.start)

class CountdownIterator:
    """迭代器：自己记住走到哪了"""

    def __init__(self, start):
        self.current = start

    def __iter__(self):
        return self          # 迭代器的 __iter__ 返回自己

    def __next__(self):
        if self.current <= 0:
            raise StopIteration
        self.current -= 1
        return self.current + 1

cd = Countdown(3)
print("type(cd) =", type(cd).__name__)
print("hasattr(cd, '__next__') =", hasattr(cd, "__next__"), " <- 可迭代对象不一定有 __next__")

print("第一次 for:")
for n in cd:
    print("      ", n)
print("第二次 for（__iter__ 每次给新迭代器）:")
for n in cd:
    print("      ", n)
```

```
type(cd) = Countdown
hasattr(cd, '__next__') = False  <- 可迭代对象不一定有 __next__
第一次 for:
      [Countdown.__iter__ 被调用]
       3
       2
       1
第二次 for（__iter__ 每次给新迭代器）:
      [Countdown.__iter__ 被调用]
       3
       2
       1
```

**三条规则**：

| 角色 | 必须实现 | 职责 |
|---|---|---|
| **可迭代对象** | `__iter__` | 返回一个迭代器 |
| **迭代器** | `__next__`（+ `__iter__` 返回自己） | 返回下一个值，或抛 `StopIteration` |

`for` 干的事就是（伪代码，不是能直接跑的 Python）：

```text
_it = iter(可迭代对象)      # 调 __iter__
while True:
    try:
        x = next(_it)        # 调 __next__
    except StopIteration:
        break
    处理 x
```

**`StopIteration` 不是错误，是控制流。** 它是迭代器在说"我讲完了"，
`for` 把它接住然后正常结束。所以你在 `for` 里**永远看不到**这个异常。

### 1.3 `iter()` / `next()` 内建（实测）

```python
it = iter(cd)
print("type(iter(cd)) =", type(it).__name__)
print("iter(it) is it =", iter(it) is it)
print("next(it) =", next(it), next(it), next(it))
try:
    next(it)
except StopIteration:
    print("第 4 次 next() -> StopIteration")
print("next(it, '默认值') =", next(it, "默认值"), " <- 给默认值就不抛异常了")
```

```
type(iter(cd)) = CountdownIterator
iter(it) is it = True
next(it) = 3 2 1
第 4 次 next() -> StopIteration
next(it, '默认值') = 默认值  <- 给默认值就不抛异常了
```

**`next(it, 默认值)` 值得记住**：它等价于 `try: next(it) except StopIteration: 默认值`，
在读迭代器时能省掉一层 `try`。

### 1.4 迭代器是一次性的（本机实测）
**这是"可迭代对象"和"迭代器"最重要、也最容易踩的区别。**

```python
nums = [1, 2, 3]
it2 = iter(nums)
print("list(it2) 第一次 =", list(it2))
print("list(it2) 第二次 =", list(it2), " <- 空的！")
print("list(nums) 两次 =", list(nums), list(nums), " <- list 本身没问题")

z = zip([1, 2, 3], "abc")
print("list(z) 第一次 =", list(z), " 第二次 =", list(z))
m = map(str.upper, "abc")
print("list(m) =", list(m), " 再来一次 =", list(m))

r = range(3)
print("iter(r) is r =", iter(r) is r, " list(r) 两次 =", list(r), list(r))
```

```
list(it2) 第一次 = [1, 2, 3]
list(it2) 第二次 = []  <- 空的！
list(nums) 两次 = [1, 2, 3] [1, 2, 3]  <- list 本身没问题
list(z) 第一次 = [(1, 'a'), (2, 'b'), (3, 'c')]  第二次 = []
list(m) = ['A', 'B', 'C']  再来一次 = []
iter(r) is r = False  list(r) 两次 = [0, 1, 2] [0, 1, 2]
```

| | 可迭代对象（`list` / `range` / `str` / `dict`） | 迭代器（`zip` / `map` / `filter` / 生成器 / 文件对象） |
|---|---|---|
| `__iter__` 返回 | **一个新的迭代器** | **自己**（`iter(it) is it` 是 `True`） |
| 能否反复遍历 | ✅ 能 | ❌ **只能一次** |
| 有 `__next__` | 通常没有 | 有 |

> ⚠️ **坑**：`zip` / `map` / `filter` 返回的都是**迭代器**（Python 3 才这样）。
>
> 现象：
> ```python
> pairs = zip(a, b)
> print(list(pairs))     # 有内容
> print(list(pairs))     # [] —— 空的
> ```
> 原因：迭代器只有一个内部游标，第一次遍历已经把它推到末尾了。
> 处理：需要多处使用时**先 `list(...)` 固化**，或者每次重新生成。
>
> **判断依据**：看到一个变量可能是迭代器时，问自己"我要遍历几次"。
> 多于一次就 `list()` 一下——代价是内存，收益是不会莫名其妙得到空结果。

### 1.5 老式协议：只实现 `__getitem__` 也能被 `for` 遍历（实测）

```python
class OldStyle:
    def __getitem__(self, i):
        if i >= 3:
            raise IndexError
        return i * 10

print([v for v in OldStyle()])     # [0, 10, 20]
```

```
[0, 10, 20]
```

这是 Python 2 时代的遗留规则：**没有 `__iter__` 时，`iter()` 会退化成
"从下标 0 开始不停 `obj[0]`、`obj[1]`…直到 `IndexError`"**。
你知道这条规则是为了**读懂老代码**，**新代码不要依赖它**——
它的报错是 `IndexError` 而不是 `StopIteration`，语义不清、也更慢。

### 1.6 `StopIteration` 在生成器里是控制流，泄漏出来会变 `RuntimeError`（实测）

```python
def gen():
    yield 1
    return "结束了"      # 这个值不会变成 yield 的值

g = gen()
print("next(g) =", next(g))
try:
    next(g)
except StopIteration as e:
    print("第二次 next -> StopIteration，它的 value =", repr(e.value))

def bad_gen():
    it = iter([1])
    while True:
        yield next(it)          # 第二次 next(it) 会抛 StopIteration

g2 = bad_gen()
print("next(g2) =", next(g2))
try:
    next(g2)
except RuntimeError as e:
    print("-> RuntimeError:", e)
```

```
next(g) = 1
第二次 next -> StopIteration，它的 value = '结束了'
next(g2) = 1
-> RuntimeError: generator raised StopIteration
```

**两个知识点**：

1. `return 值` 在生成器里**不会**变成 `yield` 的值，而是挂到
   `StopIteration.value` 上（`yield from` 和 `await` 会用到它）。
2. **在生成器里让 `StopIteration` 冒泡出来，解释器会把它转成 `RuntimeError`。**
   这是 PEP 479 定的规则，在 Python 3.7 之后成为默认行为
   （**具体哪个版本从"警告"变成"报错"，本机未逐版本实测**）。

> ⚠️ **坑**：写生成器时手写 `while True: yield next(迭代器)` 会得到
> `RuntimeError: generator raised StopIteration`。
> 原因：`StopIteration` 被设计成"只属于迭代协议的控制流"，
> 让它穿过生成器边界会把"我讲完了"和"我出错了"混为一谈，
> 而 `for` 循环会把它当成"正常结束"——那样真实的错误就被吞了。
> 处理：**用 `for` 遍历，或者给 `next` 兜底**：
> ```python
> def good_gen():
>     for v in [1, 2]:
>         yield v
> ```

### 1.7 怎么判断"手上是什么"

```python
from collections.abc import Iterable, Iterator

print(isinstance([1], Iterable), isinstance([1], Iterator))     # True False
print(isinstance(iter([1]), Iterator))                          # True
print(isinstance((i for i in [1]), Iterator))                   # True
```

```
True False
True
True
```

`collections.abc.Iterator` 就是"有 `__next__` 和 `__iter__`"的正式名字。
**记忆口诀：`Iterable` 是"能借出游标"，`Iterator` 是"游标本身"。**

官方文档：<https://docs.python.org/3/library/stdtypes.html#iterator-types>
——这一页用一两句话定义了迭代器协议，重点看它怎么描述
"一旦 `__next__` 抛了 `StopIteration`，后面每次调用都必须继续抛"这条一致性要求。

## 2. 生成器与 `yield`（覆盖 9.2）
### 2.1 先看问题：用 `list` 返回全部结果
假设要算"前 n 个平方数"。最直白的写法：

```python
import tracemalloc

def first_n_squares_list(n):
    result = []
    for i in range(1, n + 1):
        result.append(i * i)
    return result

tracemalloc.start()
sq = first_n_squares_list(200_000)
cur, peak = tracemalloc.get_traced_memory()
tracemalloc.stop()
print("list 版：len =", len(sq), " 峰值内存 =", f"{peak / 1024 / 1024:.1f} MB")
```

```
list 版：len = 200000  峰值内存 = 7.7 MB
```

20 万个整数花了 7.7 MB。**如果调用者只是想把它们加起来呢？**
那这 7.7 MB 完全是浪费——我们做了一个列表，遍历一遍，然后扔掉。

### 2.2 改成生成器（实测对比）

```python
def first_n_squares_gen(n):
    for i in range(1, n + 1):
        yield i * i

tracemalloc.start()
g = first_n_squares_gen(200_000)
cur, peak = tracemalloc.get_traced_memory()
tracemalloc.stop()
print("生成器版：type =", type(g).__name__, " 峰值内存 =", f"{peak / 1024:.1f} KB")

tracemalloc.start()
total = sum(first_n_squares_gen(200_000))
cur, peak = tracemalloc.get_traced_memory()
tracemalloc.stop()
print("完整遍历 200000 个：峰值内存 =", f"{peak / 1024:.1f} KB", " 和 =", total)
```

```
生成器版：type = generator  峰值内存 = 0.2 KB
完整遍历 200000 个：峰值内存 = 0.4 KB  和 = 2666686666700000
```

| | `list` 版 | 生成器版 |
|---|---|---|
| 峰值内存（20 万项） | **7.7 MB** | **0.4 KB** |
| 内存与 n 的关系 | 线性增长 | **恒定** |
| 调用方什么时候拿到值 | 全部算完才开始 | 立刻，要一个算一个 |

**`yield` 的作用**：函数里出现 `yield` 之后，这个函数就**不再是普通函数**，
而是一个"**生成器函数**"。调用它不会执行函数体，只会返回一个生成器对象。

### 2.3 调用生成器函数不执行任何代码（实测）
**这是理解生成器最关键的一条。**

```python
def noisy_gen():
    print("      [函数体开始执行]")
    yield 1
    print("      [yield 之后]")
    yield 2
    print("      [函数体结束]")

print("调用 noisy_gen() ...")
gen = noisy_gen()
print("拿到的对象 =", gen)
print("type =", type(gen).__name__, " 是迭代器吗 =", hasattr(gen, "__next__"))
print("第一次 next():")
print("   返回值 =", next(gen))
print("第二次 next():")
print("   返回值 =", next(gen))
try:
    next(gen)
except StopIteration:
    print("第三次 next() -> StopIteration")
```

```
调用 noisy_gen() ...
拿到的对象 = <generator object noisy_gen at 0x000001B36F3177C0>
type = generator  是迭代器吗 = True
第一次 next():
      [函数体开始执行]
   返回值 = 1
第二次 next():
      [yield 之后]
   返回值 = 2
      [函数体结束]
第三次 next() -> StopIteration
```

（`0x...` 那个地址每次运行都不同，**只有"是个 `generator object`"这件事有意义**。）

**注意第一行和第二行的顺序**：`调用 noisy_gen()` 打印了，
但 `[函数体开始执行]` 直到**第一次 `next()`** 才出现。

三条推论：

1. **调用生成器函数 = 造对象，不干活。** 所以"生成器里的代码有 bug"
   在调用处不会暴露，要等到真正迭代时。
2. **每次 `next()` 从上次 `yield` 的地方继续**，局部变量都还在。
   函数不"重新开始"，而是"接着跑"。
3. 函数体执行完（或遇到 `return`）时抛 `StopIteration`。

### 2.4 惰性求值的好处与代价
**好处**（三条，都很实在）：

- **省内存**：内存恒定，跟数据量无关。处理 10 GB 日志和 10 KB 日志占用的内存一样。
- **能表达"无限序列"**：`itertools.count()` 没有尽头，但生成器能一直吐。
- **能提前退出**：`for x in gen: if 找到了: break` —— 后面的元素**根本不会被计算**。

第三条经常被忽略，但它是"`any(...)`/`next(...)` 比列表推导快"的原因。

**代价**（也必须知道）：

- **不能 `len()`**：不知道长度。
- **不能索引**：`gen[3]` 报 `TypeError`。
- **不能回退**：只能往前走。
- **只能遍历一次**（下一节实测）。

**判断依据**：要"一次性流过"就用生成器；要"反复访问、随机访问、知道长度"
就用 `list`。**不要为了"显得高级"把明明要多次访问的东西写成生成器。**

### 2.5 生成器只能遍历一次（实测）

```python
g3 = first_n_squares_gen(3)
print("第一次 list =", list(g3))
print("第二次 list =", list(g3))
print("再 for 一次:")
for v in g3:
    print("      ", v)
print("（什么都没打印）")

g4 = first_n_squares_gen(3)
print("sum 一次 =", sum(g4), " sum 第二次 =", sum(g4))
```

```
第一次 list = [1, 4, 9]
第二次 list = []
再 for 一次:
（什么都没打印）
sum 一次 = 14  sum 第二次 = 0
```

> ⚠️ **坑**：`sum(g4)` 第二次返回 **0**，而不是报错。
> **这是最阴的地方**：空序列的和是 0，是一个"看起来合理"的答案。
> 如果你的代码在别处已经遍历过这个生成器，你就会静默拿到 0，
> 然后把它当成真实结果用下去。
> 处理：生成器不要跨函数传来传去（"谁负责遍历"必须明确）；
> 需要复用就先 `list()`。

### 2.6 生成器表达式

```python
import sys

lst = [i * i for i in range(5)]
gex = (i * i for i in range(5))
print("列表推导 =", lst)
print("生成器表达式 =", gex)
print("list(生成器表达式) =", list(gex))
print("sys.getsizeof([i for i in range(1000)]) =", sys.getsizeof([i for i in range(1000)]), "字节")
print("sys.getsizeof((i for i in range(1000))) =", sys.getsizeof((i for i in range(1000))), "字节")
print("sum(i*i for i in range(5)) =", sum(i * i for i in range(5)))
print("max(len(w) for w in ['a','bbb','cc']) =", max(len(w) for w in ["a", "bbb", "cc"]))
print("','.join(str(i) for i in range(3)) =", ",".join(str(i) for i in range(3)))
```

```
列表推导 = [0, 1, 4, 9, 16]
生成器表达式 = <generator object <genexpr> at 0x000001B36F3BA740>
list(生成器表达式) = [0, 1, 4, 9, 16]
sys.getsizeof([i for i in range(1000)]) = 8856 字节
sys.getsizeof((i for i in range(1000))) = 192 字节
sum(i*i for i in range(5)) = 30
max(len(w) for w in ['a','bbb','cc']) = 3
','.join(str(i) for i in range(3)) = 0,1,2
```

（`0x...` 地址每次不同；`8856` / `192` 这两个**字节数是稳定的**，
因为它们只取决于元素个数和解释器版本的内部布局。）

**写成 `( ... )` 而不是 `[ ... ]` 就是生成器表达式。**
`sys.getsizeof` 那两行是同一件事的两个写法：8856 字节 vs 192 字节。

**"直接传给 `sum`/`max`/`join` 时可以省掉一层括号"**——
`sum(i*i for i in range(5))` 这种写法你要会读，它是最常见的生成器表达式用法。

### 2.7 生成器 vs 列表推导：取舍表
| | 列表推导 `[...]` | 生成器表达式 `(...)` |
|---|---|---|
| 求值时机 | **立刻**，全部算完 | **惰性**，要一个算一个 |
| 内存（1000 项） | 8856 字节（**∝ n**） | 192 字节（**恒定**） |
| 能否 `len` / 索引 / 反复遍历 | ✅ 都能 | ❌ 都不能/只能一次 |
| 能否中途 `break` 省下后面的计算 | ❌ 全都算过了 | ✅ 后面根本不计算 |
| 适合 | 要复用、要索引、项数不大 | 一次性流过、数据量大、可能提前退出 |

**判断依据**：看调用方对这份数据做了什么。

- `for x in ...` / `sum(...)` / `any(...)` / `max(...)` / `",".join(...)`
  → **用生成器表达式**，白省内存。
- `result[0]` / `len(result)` / `sorted(...)` 之后再多次用 / `return` 给外部
  → **用列表推导**。

**注意一个假取舍**：`sorted(生成器)` 和 `sorted(列表)` 内存差不多——
因为 `sorted` 内部本来就要把全部元素装进一个列表。这时用哪个都行。

### 2.8 `send()`：双向生成器
`yield` 不只是"往外吐值"，它还是一个**表达式**，能接收值。这让你能写出
"协程"的雏形。

```python
def echo():
    received = None
    while True:
        received = yield received
        print("      生成器收到:", received)

e = echo()
print("第一次必须用 next() 或 send(None) 启动：next(e) =", next(e))

e2 = echo()
try:
    e2.send("x")
except TypeError as ex:
    print("还没启动就 send ->", type(ex).__name__, ":", ex)

print("e.send('hello') =", e.send("hello"))
print("e.send('world') =", e.send("world"))

def running_sum():
    total = 0
    while True:
        n = yield total
        if n is None:
            break
        total += n
    return total

acc = running_sum()
print("累加器：启动 =", next(acc), " send(10) =", acc.send(10), " send(5) =", acc.send(5))
try:
    acc.send(None)
except StopIteration as ex:
    print("send(None) 结束，最终值 =", ex.value)
```

```
第一次必须用 next() 或 send(None) 启动：next(e) = None
还没启动就 send -> TypeError : can't send non-None value to a just-started generator
      生成器收到: hello
e.send('hello') = hello
      生成器收到: world
e.send('world') = world
累加器：启动 = 0  send(10) = 10  send(5) = 15
send(None) 结束，最终值 = 15
```

**注意那两行的先后顺序**：`生成器收到: hello` **先于** `e.send('hello') = hello`。
因为 `e.send("hello")` 这个调用**先执行完**（过程中生成器打印了一行），
`print` 才拿到返回值去打印。这不是打印错位，是 Python 求值顺序的正常结果。

> ⚠️ **坑**：**生成器必须先"启动"才能 `send` 非 `None` 的值。**
> 现象：`TypeError: can't send non-None value to a just-started generator`。
> 原因：第一次 `next()` 之前，生成器还停在函数开头，
> 没有任何 `yield` 表达式可以接收你的值。
> 处理：先 `next(g)` 或 `g.send(None)` 一次。

**`send` 的现实用法**：状态机、以及 `asyncio` 底层的协程实现。
**但今天的异步代码请直接用 `async def` / `await`**，
手写 `send` 驱动的协程是"知道有这回事"就够了。

### 2.9 `yield from`、`close()`、`throw()`

```python
def inner():
    yield "a"
    yield "b"

def outer_loop():
    for x in inner():
        yield x

def outer_from():
    yield from inner()
    yield "c"

print("for 版 =", list(outer_loop()), " yield from 版 =", list(outer_from()))

def resource_gen():
    print("      [打开资源]")
    try:
        yield 1
        yield 2
    finally:
        print("      [关闭资源]   <- finally 保证一定执行")

rg = resource_gen()
print("next =", next(rg))
rg.close()
try:
    next(rg)
except StopIteration:
    print("close() 之后 next -> StopIteration")
```

```
for 版 = ['a', 'b']  yield from 版 = ['a', 'b', 'c']
      [打开资源]
next = 1
      [关闭资源]   <- finally 保证一定执行
close() 之后 next -> StopIteration
```

**`yield from 可迭代对象` 等价于"`for x in 可迭代对象: yield x`"，但多做两件事**：
它把 `send` / `throw` 转发给子生成器，并把子生成器的 `return` 值当作
`yield from` 表达式的值。**手工写 `for` 循环做不到这两件事。**

**`close()` 会在 `yield` 处抛 `GeneratorExit`**，
所以生成器里的 `try/finally` 一定会执行。**这就是"生成器能安全持有资源"的原因**
——你可以把"打开文件、逐行 yield、`finally` 里关闭"写成生成器，
调用方 `break` 出来时 `close()` 由 GC 或 `with` 触发。

`throw(异常)` 则是在 `yield` 处抛进任意异常，用于向生成器里"注入错误"。
两者都属于协程机制的一部分，日常业务代码很少直接用。

### 2.10 指路：`itertools` 是生成器的天然搭档
生成器负责"**怎么产出**"，`itertools` 负责"**产出之后怎么加工**"。
`count` / `cycle` / `repeat` / `chain` / `islice` / `groupby` 这些**都返回迭代器**，
所以它们能零成本地串起来：

```python
import itertools

# 无限序列 -> 切片 -> 加工，全程不建列表
print(list(itertools.islice((x * x for x in itertools.count(1)), 5)))    # [1, 4, 9, 16, 25]
```

```
[1, 4, 9, 16, 25]
```

上面这行代码**没有创建任何中间列表**，`count()` 是无限的也照样能跑。
具体工具见下一节。

## 3. 装饰器进阶（覆盖 9.3）
### 3.1 回顾：装饰器就是"函数进、函数出"
`@deco` 加在函数上，**完全等价于**在函数定义之后写一行 `f = deco(f)`。

```python
def deco(func):
    def wrapper(*args, **kwargs):
        print("   调用前")
        r = func(*args, **kwargs)
        print("   调用后")
        return r
    return wrapper

@deco
def add(a, b):
    return a + b

print(add(1, 2))
```

```
   调用前
   调用后
3
```

`add` 这个名字现在绑定的是 `wrapper`，真正的原函数被 `wrapper` 的闭包
（`func` 这个自由变量）抓着。

### 3.2 不加 `functools.wraps` 会丢什么（实测）
**这是装饰器最容易忽略的一步。** 上面那个写法丢掉了原函数的"身份信息"。

```python
import functools
import inspect

def bad_deco(func):
    def wrapper(*args, **kwargs):
        return func(*args, **kwargs)

    return wrapper

def good_deco(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        return func(*args, **kwargs)

    return wrapper

@bad_deco
def add_bad(a: int, b: int = 0) -> int:
    """把两个数加起来。"""
    return a + b

@good_deco
def add_good(a: int, b: int = 0) -> int:
    """把两个数加起来。"""
    return a + b

for f, tag in ((add_bad, "没加 wraps"), (add_good, "加了 wraps")):
    print(f"{tag}:")
    print(f"   __name__   = {f.__name__!r}")
    print(f"   __doc__    = {f.__doc__!r}")
    print(f"   __qualname__ = {f.__qualname__!r}")
    print(f"   __wrapped__ = {getattr(f, '__wrapped__', '没有')!r}")
    print(f"   signature  = {inspect.signature(f)}")
```

```
没加 wraps:
   __name__   = 'wrapper'
   __doc__    = None
   __qualname__ = 'bad_deco.<locals>.wrapper'
   __wrapped__ = '没有'
   signature  = (*args, **kwargs)
加了 wraps:
   __name__   = 'add_good'
   __doc__    = '把两个数加起来。'
   __qualname__ = 'add_good'
   __wrapped__ = <function add_good at 0x0000016BB5FDBEC0>
   signature  = (a: int, b: int = 0) -> int
```

（`__wrapped__` 后面那个 `0x...` 地址每次运行都不同，
**有意义的是"它指向原函数 `add_good`"**，不是那个地址本身。）

**对照着看，丢了四样东西**：

| 属性 | 丢了会怎样 |
|---|---|
| `__name__` | 报错信息里全是 `wrapper`，日志里所有被装饰的函数都叫一个名字 |
| `__doc__` | `help()` 和自动文档（Sphinx / FastAPI 的接口文档）看不到说明 |
| `__qualname__` | 变成 `bad_deco.<locals>.wrapper`，IDE 跳转、`repr` 都不对 |
| **`inspect.signature`** | 变成 `(*args, **kwargs)` —— **这是最要命的** |

**为什么签名最关键**：FastAPI / Flask / `pydantic` / `functools.singledispatch`
这些库**靠 `inspect.signature` 读参数来决定行为**（把哪个参数当路径变量、
哪个当查询参数、怎么校验类型）。签名一旦变成 `*args, **kwargs`，
这些库全部失灵。IDE 的参数提示、类型检查器也一起废掉。

`functools.wraps` 做的事就是**把 `__module__` / `__name__` / `__qualname__` /
`__annotations__` / `__doc__` 从原函数复制到 `wrapper` 上，
并设置 `__wrapped__ = 原函数`**。`inspect.signature` 看到 `__wrapped__`
就会去读原函数的签名。

> ⚠️ **坑**：**写装饰器不加 `functools.wraps` 的代价不是"不好看"，
> 而是"静默破坏别的库"。** 现象通常不是报错，而是
> "接口文档里参数没了"、"IDE 不提示了"、"类型检查器不检查了"。
> 处理：**只有一个规矩——只要写装饰器，第一件事就是加
> `@functools.wraps(func)`。**
>
> 顺带一个实测细节：`wraps` 也把 `wrapper.__dict__` 更新成原函数的 `__dict__`
> 副本，所以你在**装饰器之后**挂到函数上的自定义属性不会丢。

### 3.3 带参数的装饰器：为什么必须三层
先看目标写法：

```python
@repeat(3)
def say(name):
    return f"hi {name}"
```

**关键是先想清楚这三行到底被翻译成什么。** `@` 后面不是函数名，
而是一个**调用** `repeat(3)`：

```
@repeat(3)
def say(...)
```

等价于（这不是能直接运行的 Python，只是把 `@` 写法展开）：

```text
say = repeat(3)(say)
```

**这一个等号就把"为什么三层"解释完了**：`repeat(3)` 必须返回一个
"能接收函数、并返回新函数"的东西，也就是**第二层**。

```python
def repeat(times):
    """第 1 层：收装饰器自己的参数 times"""

    def decorator(func):
        """第 2 层：收被装饰的函数"""

        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            """第 3 层：收调用时的实参"""
            results = []
            for _ in range(times):
                results.append(func(*args, **kwargs))
            return results

        return wrapper

    return decorator

@repeat(3)
def say(name):
    return f"hi {name}"

print(say("王"), say.__name__, inspect.signature(repeat), type(repeat(3)).__name__)
```

```
['hi 王', 'hi 王', 'hi 王'] say (times) function
```

**三层各自的角色**：

| 层 | 收什么 | 什么时候被调用 | 返回什么 |
|---|---|---|---|
| 第 1 层 `repeat(times)` | 装饰器**自己的参数** | 写 `@repeat(3)` 时 | 第 2 层函数 |
| 第 2 层 `decorator(func)` | **被装饰的函数** | `@` 生效时（导入模块时） | 第 3 层函数 |
| 第 3 层 `wrapper(*a, **k)` | **调用时的实参** | 每次调用 `say(...)` 时 | 原函数的返回值 |

**对比"不带参数的装饰器"只有两层**（`deco(func)` 收函数 → 返回 `wrapper`）。
多一层就是因为"**先要用参数把装饰器本身配置出来**"。

> ⚠️ **一个容易犯的错**：把第 1 层和第 2 层的参数写反。
> `@repeat` （不带括号）会把**函数**传给 `times`，然后 `range(函数)` 报
> `TypeError`。**判断依据**：装饰器名后面有括号 → 你写的是三层；
> 没括号 → 两层。这是两种不同的装饰器，不能混用。

### 3.4 装饰器叠加顺序（实测）

```python
def a_deco(func):
    print("   [a_deco 正在装饰]", func.__name__)

    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        print("      -> 进入 a")
        r = func(*args, **kwargs)
        print("      <- 离开 a")
        return r

    return wrapper

def b_deco(func):
    print("   [b_deco 正在装饰]", func.__name__)

    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        print("      -> 进入 b")
        r = func(*args, **kwargs)
        print("      <- 离开 b")
        return r

    return wrapper

@a_deco
@b_deco
def hello():
    print("      *** 真正的 hello 函数体 ***")

print("现在调用 hello():")
hello()
```

```
   [b_deco 正在装饰] hello
   [a_deco 正在装饰] hello
现在调用 hello():
      -> 进入 a
      -> 进入 b
      *** 真正的 hello 函数体 ***
      <- 离开 b
      <- 离开 a
```

**两个方向，要分开记**：

| 阶段 | 顺序 |
|---|---|
| **装饰时**（模块导入时） | **从下往上**：先 `b_deco(hello)`，再 `a_deco(结果)` |
| **调用时** | **从上往下进、从下往上出**：a 先进，b 后进，b 先出，a 后出 |

**记法**：`@a` `@b` 叠在函数上，等价于 `hello = a_deco(b_deco(hello))`。
从里往外读，所以**下面的先执行**。

**为什么调用时是"a 先进"**：因为 `a_deco` 是最后包上去的，
最终绑定 `hello` 的是 a 的 `wrapper`，所以调用先进入它。

**实际意义**：这个顺序决定了"哪个装饰器在最外层"。
比如：

```python
@timed          # 想测"包括重试在内的总耗时"
@retry(times=3)
def fetch():
    ...
```

对比：

```python
@retry(times=3)  # 想"每次重试都分别计时"
@timed
def fetch():
    ...
```

**判断依据**：**最外层的是"最后写的那个 `@`"（最上面那个）**。
想要"把整个过程包起来"的装饰器（计时、日志、缓存）写在**上面**；
想要"针对单次调用"的装饰器写在**下面**。

### 3.5 类装饰器
装饰器不一定是函数——**任何"接收一个函数并返回一个可调用对象"的东西**都行。
一个只实现了 `__call__` 的类就满足：

```python
class CountCalls:
    def __init__(self, func):
        self.func = func
        self.n = 0
        functools.update_wrapper(self, func)     # 等价于给 __call__ 加 wraps

    def __call__(self, *args, **kwargs):
        self.n += 1
        print(f"   第 {self.n} 次调用 {self.func.__name__}")
        return self.func(*args, **kwargs)

@CountCalls
def greet(name):
    return f"hi {name}"

print(greet("王"), greet("李"))
print("计数 =", greet.n, " 名字 =", greet.__name__)
```

```
   第 1 次调用 greet
   第 2 次调用 greet
hi 王 hi 李
计数 = 2  名字 = greet
```

**类装饰器的取舍**：

| | 函数装饰器 | 类装饰器 |
|---|---|---|
| 保存状态 | 要用闭包变量或 `nonlocal` | **`self.xxx` 天然可以** |
| 可读性 | 嵌套三层以后开始绕 | 平铺直叙 |
| 能否加方法 | 不能 | 可以（比如给装饰结果加个 `.reset()`） |
| 开销 | 小 | 每次调用多一层 `__call__` |

**判断依据**：装饰器**需要记状态**（调用次数、缓存、最近一次耗时）时，
类装饰器更清楚。注意类装饰器要用 **`functools.update_wrapper(self, func)`**，
它和 `@functools.wraps` 的作用一样（`wraps` 是给函数用的）。

> ⚠️ 用类装饰器时，`self.func` 就是原函数。**别把 `__call__` 的参数
> 和 `__init__` 的参数搞混**——`__init__` 在"装饰时"跑一次，
> `__call__` 在"每次调用时"跑。

### 3.6 `functools.lru_cache`：最有用的内置装饰器
**它是"记忆化（memoization）"的现成实现**：同样的参数第二次调用直接返回缓存结果。

```python
import time

@functools.lru_cache(maxsize=None)
def fib(n):
    return n if n < 2 else fib(n - 1) + fib(n - 2)

t0 = time.perf_counter()
print("fib(120) =", fib(120))
print("耗时 =", f"{(time.perf_counter() - t0) * 1000:.2f} ms")

@functools.lru_cache(maxsize=2)
def small(n):
    print("      真正计算", n)
    return n * 2

for i in (1, 2, 3, 1):
    print("     small(%d) = %d" % (i, small(i)))
print("small.cache_info() =", small.cache_info())
small.cache_clear()
print("cache_clear 之后 =", small.cache_info())
```

```
fib(120) = 5358359254990966640871840
耗时 = 0.12 ms
      真正计算 1
     small(1) = 2
      真正计算 2
     small(2) = 4
      真正计算 3
     small(3) = 6
      真正计算 1
     small(1) = 2
small.cache_info() = CacheInfo(hits=0, misses=4, maxsize=2, currsize=2)
small.cache_clear() = CacheInfo(hits=0, misses=0, maxsize=2, currsize=0)
```

**朴素递归的 `fib(120)` 要算到宇宙热寂，加了缓存 0.12 ms。**
`maxsize=2` 那段演示了"LRU 淘汰"：`small(1)` 最后又被重新计算了一次，
因为中间算 2 和 3 时把 1 挤出去了。

| 参数 / 方法 | 作用 |
|---|---|
| `maxsize=None` | 缓存不设上限（等价于 `functools.cache`） |
| `maxsize=n` | 只留最近 n 个，多了按 LRU 淘汰 |
| `typed=True` | 把 `1` 和 `1.0` 当不同参数（默认 `False`） |
| `.cache_info()` | 看命中/未命中次数 |
| `.cache_clear()` | 清空缓存（**改过外部状态后必须调它**） |

**四条使用纪律**：

1. **参数必须可哈希**（实测 `TypeError: unhashable type: 'list'`）。
   要缓存列表参数就先转成 `tuple`。
2. **函数必须是"纯"的**——同样输入永远同样输出。
   有副作用的函数（打日志、改文件、发请求）缓存起来会改变程序行为。
3. **它会永久持有参数和返回值的引用。** 用大对象当参数时，
   缓存会把这些大对象一直留在内存里——这是真实的内存泄漏来源。
   所以生产代码通常写 `maxsize=128` 而不是 `None`。
4. **缓存是进程内的。** 多进程/多机不共享，重启就没了。

`functools.cache` 是 `lru_cache(maxsize=None)` 的简写，
实测 `cached_fact.cache_info()` 返回 `CacheInfo(hits=0, misses=20, maxsize=None, currsize=20)`。

### 3.7 两个能直接用的实用装饰器
**计时**（`try/finally` 保证"函数抛异常也打印耗时"）：

```python
def timed(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        t0 = time.perf_counter()
        try:
            return func(*args, **kwargs)
        finally:
            dt = (time.perf_counter() - t0) * 1000
            print(f"      {func.__name__} 耗时 {dt:.2f} ms")

    return wrapper

@timed
def slow_sum(n):
    return sum(i * i for i in range(n))

print("结果 =", slow_sum(1_000_000))
```

```
      slow_sum 耗时 91.22 ms
结果 = 333332833333500000
```

（耗时每次不同；用 `time.perf_counter()` 而不是 `time.time()`，
因为前者是单调时钟，不受系统时间调整影响。）

**重试**（只重试指定类型的异常，次数用完就把最后一个异常抛出去）：

```python
def retry(times=3, delay=0.0, exceptions=(Exception,)):
    def decorator(func):
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            last = None
            for attempt in range(1, times + 1):
                try:
                    return func(*args, **kwargs)
                except exceptions as e:
                    last = e
                    print(f"      第 {attempt}/{times} 次失败：{type(e).__name__}: {e}")
                    if attempt < times and delay:
                        time.sleep(delay)
            raise last

        return wrapper

    return decorator

calls = {"n": 0}

@retry(times=4, delay=0.01)
def flaky():
    calls["n"] += 1
    if calls["n"] < 3:
        raise ConnectionError("假装网络不通")
    return f"第 {calls['n']} 次成功"

print("结果 =", flaky())

calls2 = {"n": 0}

@retry(times=2)
def always_fail():
    calls2["n"] += 1
    raise RuntimeError(f"第 {calls2['n']} 次还是不行")

try:
    always_fail()
except RuntimeError as e:
    print("全部重试完仍失败 ->", e)
```

```
      第 1/4 次失败：ConnectionError: 假装网络不通
      第 2/4 次失败：ConnectionError: 假装网络不通
结果 = 第 3 次成功
      第 1/2 次失败：RuntimeError: 第 1 次还是不行
      第 2/2 次失败：RuntimeError: 第 2 次还是不行
全部重试完仍失败 -> 第 2 次还是不行
```

**这个重试装饰器有三个值得学的设计**：

1. **`exceptions=(Exception,)` 是可配置的**——只重试"可恢复"的异常
   （网络超时、`ConnectionError`）。**不要重试 `ValueError`、`KeyError` 这类
   "代码写错了"的异常**，重试一万次也不会好，只是浪费时间。
2. **`raise last` 保留了原始异常**（还有它的 traceback）。
   别写 `raise RuntimeError("重试失败")`——那会丢掉真正的错误原因。
3. **`times` 的计数是"总尝试次数"**，不是"重试次数"。
   `times=4` 表示最多调用 4 次。**这个语义要在文档字符串里写清楚**，
   否则调用方会把 `times=4` 理解成"重试 4 次 = 最多 5 次调用"。

## 4. `functools` / `itertools` / `collections`（覆盖 9.4）
> **这一节是本章性价比最高的部分。**
> 这三个模块里的东西，"知道"和"不知道"的差距不是"多会几个函数"，
> 而是**同一件事你写 15 行、别人写 1 行，而且别人的更快更不容易错**。

### 4.1 `functools`
**`partial`：把一个参数固定下来**

```python
import functools
import operator

def power(base, exp):
    return base**exp

square = functools.partial(power, exp=2)
hex2int = functools.partial(int, base=16)
log = functools.partial(print, flush=True)

print(square(5), functools.partial(power, exp=3)(3))
print(square.func.__name__, square.keywords)
print(hex2int("ff"))
log("      这行是 log() 打的")
```

```
25 27
power {'exp': 2}
255
      这行是 log() 打的
```

**它解决什么问题**：很多 API 要的是"一个单参数函数"
（`map` / `sort(key=...)` / 回调）。你的函数有多个参数，
`partial` 就是一个不用写 lambda 的"提前绑参数"工具。

**`partial` vs `lambda` 的取舍**：

| | `functools.partial` | `lambda` |
|---|---|---|
| 关键字参数 | ✅ `partial(f, exp=2)` | ✅ `lambda x: f(x, exp=2)` |
| 可内省（`.func` / `.keywords`） | ✅ | ❌ |
| 能 pickle / 跨进程传 | ✅ | ❌ |
| 能写任意逻辑 | ❌ 只能绑参数 | ✅ 任意表达式 |
| 可读性 | 好 | 简单场景好，复杂场景绕 |

**判断依据**：只是"绑几个参数"用 `partial`（更好调试、能内省）；
需要做**计算或分支**时用 `lambda`。

**`reduce`：把二元运算摞起来**

```python
print(functools.reduce(lambda a, b: a + b, [1, 2, 3, 4]))        # 10
print(functools.reduce(operator.mul, [1, 2, 3, 4]))              # 24
print(functools.reduce(operator.mul, [1, 2, 3, 4], 10))          # 240
try:
    functools.reduce(lambda a, b: a + b, [])
except TypeError as e:
    print("空序列不给初值 -> TypeError:", e)
print("空序列给初值 ->", functools.reduce(lambda a, b: a + b, [], 0))
```

```
10
24
240
空序列不给初值 -> TypeError: reduce() of empty iterable with no initial value
0
```

**什么时候真的该用 `reduce`**：`sum` / `max` / `min` / `math.prod` 覆盖不了的
**自定义折叠**（比如"按顺序合并一堆字典"、"把一串变换函数套起来"）。
**能用 `sum` 就用 `sum`**——可读性高得多。

**`total_ordering`：只写两个比较方法，自动补齐另外四个**

```python
@functools.total_ordering
class Version:
    def __init__(self, major, minor):
        self.major, self.minor = major, minor

    def __eq__(self, other):
        return (self.major, self.minor) == (other.major, other.minor)

    def __lt__(self, other):
        return (self.major, self.minor) < (other.major, other.minor)

    def __repr__(self):
        return f"v{self.major}.{self.minor}"

v1, v2 = Version(1, 2), Version(1, 10)
print(v1 < v2, v1 <= v2, v1 > v2, v1 >= v2, v1 == v2)

class NoOrdering:
    def __init__(self, v):
        self.v = v

    def __lt__(self, other):
        return self.v < other.v

print("不写 total_ordering 时 > 的结果 =", NoOrdering(1) > NoOrdering(2))
```

```
True True False False False
不写 total_ordering 时 > 的结果 = False
```

**注意最后一行：`>` 没有报错，返回了 `False`。** 这不是 total_ordering 的功劳——
是 Python 的 fallback 规则："`a > b` 找不到 `__gt__` 时，
**试 `b.__lt__(a)`**"。这里 `NoOrdering(2) < NoOrdering(1)` 是 `False`，
所以 `>` 也返回 `False`。**副作用是**：`1 > 2` 和 `1 < 2` 同时为 `False`，
看起来"合理"，但如果 `__lt__` 写得不自洽（比如只比了 `v` 而 `__eq__` 比了别的字段），
就会出现 `a < b`、`a > b`、`a == b` **全为假**的诡异状态。

> **判断依据**：值对象（版本号、坐标、金额）用 `total_ordering`，
> 只实现 `__eq__` 和 `__lt__`，剩下四个交给它。省掉的是"抄四遍同样的比较逻辑"，
> 而抄四遍正是最容易写出不一致的地方。

**`singledispatch`：按第一个参数的类型分发（"函数重载"）**

```python
@functools.singledispatch
def describe(x):
    return f"我不认识 {type(x).__name__}"

@describe.register
def _(x: int):
    return f"整数 {x}"

@describe.register
def _(x: str):
    return f"字符串 {x!r}，长度 {len(x)}"

@describe.register(list)
def _(x):
    return f"列表，{len(x)} 个元素"

print(describe(1), "|", describe("abc"), "|", describe([1, 2]))
print(describe(1.5), "|", describe((1, 2)), "|", describe(True))
print("注册表 =", {k.__name__: v.__name__ for k, v in describe.registry.items()})
```

```
整数 1 | 字符串 'abc'，长度 3 | 列表，2 个元素
我不认识 float | 我不认识 tuple | 整数 True
注册表 = {'object': 'describe', 'int': '_', 'str': '_', 'list': '_'}
```

**四个要点**：

1. **基础实现（`@singledispatch` 那个）是兜底**，没匹配到类型时用它。
   **必须有一个兜底**，否则未注册类型直接 `NotImplementedError`。
2. **按第一个参数的类型分发**，后面的参数不参与。
3. **按 MRO 找最近匹配**：`describe(True)` 走了 `int` 分支，
   因为 `bool` 是 `int` 的子类（**这是个真实的坑**，
   要区分 bool 就得显式 `@describe.register(bool)`）。
4. **它比 `if isinstance(...)` 链条好在"开放"**：
   别的模块可以给你的函数加新的类型支持，你不用改原来的代码。

**判断依据**：`isinstance` 分支超过三个、或者需要让外部扩展时，
`singledispatch` 更清楚。只有两种情况时，`if/elif` 就够。

**`lru_cache` / `cache`** 已在 3.6 节讲过，这里不重复。

### 4.2 `itertools`
**无限迭代器：`count` / `cycle` / `repeat`**

```python
import itertools

print(list(itertools.islice(itertools.count(10, 3), 5)))          # [10, 13, 16, 19, 22]
print(list(itertools.islice(itertools.cycle("AB"), 7)))           # ['A','B','A','B','A','B','A']
print(list(itertools.repeat("x", 4)))                            # ['x','x','x','x']
print(list(itertools.islice(itertools.repeat("y"), 3)))           # ['y','y','y']
print("repeat 给 times 参数时不是无限的:", len(list(itertools.repeat(0, 3))))
```

```
[10, 13, 16, 19, 22]
['A', 'B', 'A', 'B', 'A', 'B', 'A']
['x', 'x', 'x', 'x']
['y', 'y', 'y']
repeat 给 times 参数时不是无限的: 3
```

> ⚠️ **坑**：这三个**默认是无限的**。`list(itertools.count())` 会一直跑到
> 内存耗尽或进程被 kill。**永远配 `islice` / `zip` / `break` 用。**

**`chain`：把多个可迭代对象接起来（零拷贝）**

```python
print(list(itertools.chain([1, 2], [3], [4, 5])))
print(list(itertools.chain.from_iterable([[1, 2], [3]])))
print(list(itertools.chain("ab", "cd")))
```

```
[1, 2, 3, 4, 5]
[1, 2, 3]
['a', 'b', 'c', 'd']
```

`chain(*iterables)` 收一串可迭代对象；
`chain.from_iterable(一个可迭代对象，元素是可迭代对象)` 收**一个**。
**"我手上有一个列表的列表"时用后者**（不需要 `*` 展开，内存友好）。
**它不是 `+`**：`[1,2] + [3]` 会**建新列表**，`chain` 只是"依次遍历"。

**`islice`：只对迭代器有效的切片**

```python
print(list(itertools.islice(range(100), 5, 10)))          # [5, 6, 7, 8, 9]
print(list(itertools.islice(range(100), 0, 20, 5)))       # [0, 5, 10, 15]
print(list(itertools.islice(range(100), 3)))              # [0, 1, 2]
try:
    list(itertools.islice(range(100), -3, None))
except ValueError as e:
    print("负数不行 -> ValueError:", e)
```

```
[5, 6, 7, 8, 9]
[0, 5, 10, 15]
[0, 1, 2]
负数不行 -> ValueError: Indices for islice() must be None or an integer: 0 <= x <= sys.maxsize.
```

**为什么需要它**：切片语法 `x[2:5]` 要求 `x` 支持 `__getitem__`，
而**迭代器/生成器没有下标**。`islice` 就是"流式版的切片"。
**限制**：不支持负数（不能从尾部算，因为流式数据不知道哪里是尾）。

**`groupby`：分组——但必须先排序**

```python
rows = [("水果", "苹果"), ("蔬菜", "白菜"), ("水果", "香蕉"), ("蔬菜", "萝卜"), ("水果", "橘子")]

print("不排序：")
for key, group in itertools.groupby(rows, key=lambda r: r[0]):
    print(f"   {key}: {[g[1] for g in group]}")

print("先排序：")
for key, group in itertools.groupby(sorted(rows, key=lambda r: r[0]), key=lambda r: r[0]):
    print(f"   {key}: {[g[1] for g in group]}")

groups = []
for key, group in itertools.groupby(sorted(rows, key=lambda r: r[0]), key=lambda r: r[0]):
    groups.append((key, group))
print("事后读：", [(k, list(g)) for k, g in groups])
```

```
不排序：
   水果: ['苹果']
   蔬菜: ['白菜']
   水果: ['香蕉']
   蔬菜: ['萝卜']
   水果: ['橘子']
先排序：
   水果: ['苹果', '香蕉', '橘子']
   蔬菜: ['白菜', '萝卜']
事后读： [('水果', []), ('蔬菜', [])]
```

**两个坑叠在一起，这是 `groupby` 最有价值的一段：**

> ⚠️ **坑一：`groupby` 不做全局分组，只把"相邻的相同 key"聚在一起。**
> 现象：同一个 key 出现好几组（上面的"水果"出现三次）。
> 原因：`groupby` 是**流式**的——它只看"当前元素的 key 和上一个是否相同"。
> 这样设计是为了能处理无限流、且内存恒定。
> 处理：**先按同一个 key 排序**（`sorted(..., key=...)`），相同 key 才会相邻。
> **判断依据**：`groupby` 的输出里同一个 key 出现多于一次 = 你忘了排序。
>
> ⚠️ **坑二：`group` 也是迭代器，出了这一轮循环就失效。**
> 现象：把 `group` 存起来事后再读，读到空列表（实测上面最后一行）。
> 原因：`groupby` 在内部**推进主迭代器**来产生下一个分组，
> 所以一旦你请求下一个分组，前一个 `group` 就作废了。
> 处理：**在循环体内当场消费掉**（转成 `list` / `dict` / 求和），
> 像上面那样写：
> ```python
> result = {key: [g[1] for g in group]
>           for key, group in itertools.groupby(sorted(rows, key=lambda r: r[0]),
>                                               key=lambda r: r[0])}
> ```

**组合工具：`product` / `combinations` / `permutations`**

```python
print(list(itertools.product("AB", "12")))
print(list(itertools.product("AB", repeat=2)))
print(list(itertools.combinations("ABC", 2)))
print(list(itertools.combinations_with_replacement("AB", 2)))
print(list(itertools.permutations("ABC", 2)))
print("C(5,2) =", len(list(itertools.combinations(range(5), 2))),
      " P(5,2) =", len(list(itertools.permutations(range(5), 2))),
      " 5^2 =", len(list(itertools.product(range(5), repeat=2))))
```

```
[('A', '1'), ('A', '2'), ('B', '1'), ('B', '2')]
[('A', 'A'), ('A', 'B'), ('B', 'A'), ('B', 'B')]
[('A', 'B'), ('A', 'C'), ('B', 'C')]
[('A', 'A'), ('A', 'B'), ('B', 'B')]
[('A', 'B'), ('A', 'C'), ('B', 'A'), ('B', 'C'), ('C', 'A'), ('C', 'B')]
C(5,2) = 10  P(5,2) = 20  5^2 = 25
```

| 函数 | 选几个 | 顺序重要吗 | 能重复吗 | 数量 |
|---|---|---|---|---|
| `product` | 每个位置独立选 | 重要 | 可以 | n^k |
| `combinations` | 选 k 个 | **不重要** | 不行 | C(n,k) |
| `combinations_with_replacement` | 选 k 个 | 不重要 | **可以** | C(n+k-1,k) |
| `permutations` | 选 k 个排 | **重要** | 不行 | n!/(n-k)! |

> ⚠️ **性能坑**：这些是**组合爆炸**的。`permutations(range(10))` 是 3628800 个，
> `permutations(range(15))` 是 **1.3 万亿个**。它们返回迭代器（惰性）是对的，
> 但你在后面加 `list()` 就完了。
> **判断依据**：先估算数量级（`math.comb` / `math.perm` / `math.factorial`
> 可以在写代码前算一下），再决定能不能 `list()`。

**`accumulate`：累积（前缀和、前缀积、前缀最大值）**

```python
print(list(itertools.accumulate([1, 2, 3, 4])))
print(list(itertools.accumulate([1, 2, 3, 4], operator.mul)))
print(list(itertools.accumulate([1, 2, 3, 4], max)))
print("initial 参数 ->", list(itertools.accumulate([1, 2, 3], initial=100)))
```

```
[1, 3, 6, 10]
[1, 2, 6, 24]
[1, 2, 3, 4]
[100, 101, 103, 106]
```

**`accumulate` 是"保留每一步"的 `reduce`。** 前缀和、运行最大值、
"从起点走的最短距离"都是它的用例。`initial=` 是 3.8+ 加的
（**本机 3.13 实测可用**，具体哪个版本引入未逐版本验证）。

**另外六个常用的（一行一个）**

```python
print(list(itertools.pairwise("ABCD")))
print(list(itertools.zip_longest("AB", "123", fillvalue="-")))
print(list(itertools.compress("ABCD", [1, 0, 1, 0])))
print(list(itertools.dropwhile(lambda x: x < 3, [1, 2, 3, 4, 1])))
print(list(itertools.takewhile(lambda x: x < 3, [1, 2, 3, 4, 1])))
print(list(itertools.starmap(pow, [(2, 3), (3, 2)])))
a, b = itertools.tee([1, 2, 3])
print(list(a), list(b))
```

```
[('A', 'B'), ('B', 'C'), ('C', 'D')]
[('A', '1'), ('B', '2'), ('-', '3')]
['A', 'C']
[3, 4, 1]
[1, 2]
[8, 9]
[1, 2, 3] [1, 2, 3]
```

| 函数 | 干什么 | 典型场合 |
|---|---|---|
| `pairwise(s)` | 相邻两项配对 | 算相邻差值、找相邻相同项 |
| `zip_longest` | 按最长的 zip，缺的补 `fillvalue` | 对齐长度不等的序列 |
| `compress(data, sel)` | 按 `sel` 的真假筛 `data` | 用布尔掩码筛选 |
| `dropwhile(pred)` | **开头**满足条件的一直丢，之后全留 | 跳过文件头、跳过空行 |
| `takewhile(pred)` | **开头**满足条件的留，之后全停 | 读"直到分隔符为止" |
| `starmap(f, its)` | `f(*args)` 版 `map` | 参数已经在元组里 |
| `tee(it, n)` | 把一个迭代器**裂成 n 个** | 需要遍历两遍但不想 `list()` |

> ⚠️ **`dropwhile` / `takewhile` 容易记反**：
> 它们看的是**开头的一段**，不是"整个序列里符合条件的项"。
> 实测 `dropwhile(x<3, [1,2,3,4,1])` 给 `[3,4,1]`（末尾的 `1` 留着），
> `takewhile(x<3, [1,2,3,4,1])` 给 `[1,2]`（后面的不看了）。
> **想要"整个序列里筛选"用 `filter` / 列表推导，不是这两个。**
>
> ⚠️ **`tee` 的坑**：它内部会**缓存**没被读完的数据，
> 所以如果两个分支消费速度差很多，内存会一直涨。
> 数据量小时用它很方便；数据量大时老老实实 `list()` 两次或重新生成。

### 4.3 `collections`
**`Counter`：计数（去重统计的一站式工具）**

```python
from collections import Counter

words = "the quick brown fox jumps over the lazy dog the fox".split()
c = Counter(words)
print(c.most_common(3))
print("c['the'] =", c["the"], " c['不存在的词'] =", c["不存在的词"], " <- 不抛 KeyError，返回 0")

c2 = Counter("aabbb")
print(sorted(c2.elements()), "| total =", Counter("aabbb").total())
c2.subtract("abb")
print("subtract('abb') 后 =", c2, "（允许负数）")
print("+ =", Counter("aab") + Counter("abb"), " - =", Counter("aab") - Counter("abb"))
print("& =", Counter("aab") & Counter("abb"), " | =", Counter("aab") | Counter("abb"))
```

```
[('the', 3), ('fox', 2), ('quick', 1)]
c['the'] = 3  c['不存在的词'] = 0  <- 不抛 KeyError，返回 0
['a', 'a', 'b', 'b', 'b'] | total = 5
subtract('abb') 后 = Counter({'a': 1, 'b': 1}) （允许负数）
+ = Counter({'a': 3, 'b': 3})  - = Counter({'a': 1})
& = Counter({'a': 1, 'b': 1})  | = Counter({'a': 2, 'b': 2})
```

**`Counter` 的四个关键行为**：

1. **`c[不存在的键]` 返回 `0`，不抛 `KeyError`。** 这是它和 `dict` 最大的区别
   （也是"用 `Counter` 就不用写 `if k not in c`"的原因）。
2. **`most_common(n)` 直接给你排序结果**——手写要 `sorted(c.items(), key=..., reverse=True)`。
3. **运算会丢零和负数**：`Counter("aab") - Counter("abb")` 里 `b` 变成 `-1`，
   结果里就没有 `b` 了。**要保留负数用 `subtract()` 而不是 `-`。**
4. **`elements()` 会把每个元素按计数重复吐出**（计数为负的会跳过）。

**`defaultdict`：给"缺的键"一个默认值**

```python
from collections import defaultdict

d = {}
try:
    d["a"].append(1)
except KeyError as e:
    print("普通 dict 的痛点 -> KeyError:", e)

dd = defaultdict(list)
for k, v in [("水果", "苹果"), ("蔬菜", "白菜"), ("水果", "香蕉")]:
    dd[k].append(v)
print("defaultdict(list) 分组 =", dict(dd))

counts = defaultdict(int)
for ch in "hello":
    counts[ch] += 1
print("defaultdict(int) 计数 =", dict(counts))

dd2 = defaultdict(list)
print("dd2['新键'] =", dd2["新键"], " 现在 dd2 里有 =", dict(dd2))
dd3 = defaultdict(list)
dd3.get("x")
_ = "x" in dd3
print("get/in 之后 dd3 =", dict(dd3), "（.get 和 in 不会触发创建）")
try:
    defaultdict([])
except TypeError as e:
    print("defaultdict([]) ->", type(e).__name__, ":", e)
```

```
普通 dict 的痛点 -> KeyError: 'a'
defaultdict(list) 分组 = {'水果': ['苹果', '香蕉'], '蔬菜': ['白菜']}
defaultdict(int) 计数 = {'h': 1, 'e': 1, 'l': 2, 'o': 1}
dd2['新键'] = []  现在 dd2 里有 = {'新键': []}
get/in 之后 dd3 = {} （.get 和 in 不会触发创建）
defaultdict([]) -> TypeError : first argument must be callable or None
```

**四个要点**：

1. **`defaultdict(list)` 让"分组"从 4 行变成 1 行**，
   省掉的是 `if k not in d: d[k] = []` 这个固定仪式。
2. **`dd[k]` 会就地创建条目**（副作用！），而 `.get(k)` 和 `k in dd` 不会。
   **这个区别很重要**：如果你只是想"看一眼"，用 `.get()`，
   否则你会往字典里塞一堆空列表——如果之后要 `len(dd)` 或遍历，结果就错了。
3. **`default_factory` 必须是可调用对象**（`list` 而不是 `list()`）。
4. `defaultdict(int)` 就是 `Counter` 的轻量版（但不能 `most_common`）。

**`deque`：双端队列（两端插入删除都是 O(1)）**

```python
from collections import deque
import timeit

dq = deque([1, 2, 3])
dq.append(4)
dq.appendleft(0)
print(dq, "| pop =", dq.pop(), "popleft =", dq.popleft(), "剩下", dq)
dq.extend([9, 9])
dq.extendleft([8, 8])
print("extend/extendleft 后 =", dq)
dq.rotate(2)
print("rotate(2) 后 =", dq)
dq.rotate(-2)
print("rotate(-2) 复原 =", dq)

dq2 = deque(maxlen=3)
for i in range(6):
    dq2.append(i)
print("maxlen=3 的 deque append 0..5 =", dq2)

t_list = timeit.timeit("x.insert(0, 1)", setup="x=list(range(1000))", number=10000)
t_deque = timeit.timeit("x.appendleft(1)", setup="from collections import deque; x=deque(range(1000))", number=10000)
print(f"头部插入 10000 次：list.insert(0,..) = {t_list*1000:.1f} ms, deque.appendleft = {t_deque*1000:.1f} ms")
```

```
deque([1, 2, 3]) | pop = 4 popleft = 0 剩下 deque([1, 2, 3])
extend/extendleft 后 = deque([8, 8, 1, 2, 3, 9, 9])
rotate(2) 后 = deque([9, 9, 8, 8, 1, 2, 3])
rotate(-2) 复原 = deque([8, 8, 1, 2, 3, 9, 9])
maxlen=3 的 deque append 0..5 = deque([3, 4, 5], maxlen=3)
头部插入 10000 次：list.insert(0,..) = 24.7 ms, deque.appendleft = 0.2 ms
```

**为什么必须知道 `deque`**：`list.insert(0, x)` 和 `list.pop(0)` 都是
**O(n)**（要把后面所有元素整体搬一格），`deque` 两端都是 **O(1)**。
上面的实测：**约 120 倍**。（具体数字随机器和负载变化，但量级差距是结构性的；
`list.insert(0,..)` 那一列我两次跑分别得到 26.2 / 24.7 ms。）

**`maxlen` 是最实用的特性**：它让 `deque` 自动变成"**固定长度的滑动窗口**"
——满了以后 `append` 会自动从另一头丢。写"最近 N 条日志/最近 N 个请求耗时"时，
不用自己判断长度再 `popleft`。

**`namedtuple`：带字段名的元组**

```python
from collections import namedtuple

Point = namedtuple("Point", ["x", "y"])
p = Point(3, 4)
print(p, p.x, p[0], isinstance(p, tuple))
px, py = p
print("解包 =", px, py, "| _replace =", p._replace(x=30))
print("_asdict =", p._asdict(), type(p._asdict()).__name__, "| _fields =", p._fields)
print("_make =", Point._make([7, 8]), "| defaults:", namedtuple("Q", "a b", defaults=[0, 0])(1))
```

```
Point(x=3, y=4) 3 3 True
解包 = 3 4 | _replace = Point(x=30, y=4)
_asdict = {'x': 3, 'y': 4} dict | _fields = ('x', 'y')
_make = Point(x=7, y=8) | defaults: Q(a=1, b=0)
```

**`namedtuple` 的三个身份**：它是 tuple（能解包、能索引、可哈希）、
是"带名字的记录"（`p.x` 比 `p[0]` 可读）、
是**不可变**的（`_replace` 返回新对象，原对象不变）。

**和 `dataclass` 的取舍**：

| | `namedtuple` | `dataclass` |
|---|---|---|
| 可变性 | **不可变** | 默认**可变**（`frozen=True` 可改成不可变） |
| 内存 | **更小**（就是 tuple） | 稍大（每实例一个 `__dict__`，除非用 `slots=True`） |
| 能否解包 / 当 tuple 用 | ✅ | ❌ |
| 默认值 / 类型提示 | `defaults=` / 无类型提示 | ✅ 都有 |
| 能否加方法 | 要子类化 | ✅ 直接写 |
| 适合 | 坐标、数据库行、函数多返回值 | 业务对象、需要默认值和方法 |

**判断依据**：**"这只是一个数据元组"用 `namedtuple`；
"这是一个有行为的对象"用 `dataclass`。**
需要放进 `set`/当 `dict` 键（要求可哈希）时，`namedtuple` 更省事。

**`OrderedDict`：3.7 之后它还差在哪**

```python
from collections import OrderedDict

d1 = {"a": 1, "b": 2, "c": 3}
od = OrderedDict([("a", 1), ("b", 2), ("c", 3)])
print("dict 顺序 =", list(d1), " OrderedDict 顺序 =", list(od))
od.move_to_end("a")
print("move_to_end('a') 后 =", list(od))
od.move_to_end("a", last=False)
print("move_to_end('a', last=False) 后 =", list(od))
print("普通 dict 有 move_to_end 吗 =", hasattr({}, "move_to_end"))
print("OrderedDict 之间比顺序 =", OrderedDict([("a", 1), ("b", 2)]) == OrderedDict([("b", 2), ("a", 1)]))
print("普通 dict 之间比顺序 =", {"a": 1, "b": 2} == {"b": 2, "a": 1})
print("OrderedDict == 普通 dict =", OrderedDict([("a", 1)]) == {"a": 1})
```

```
dict 顺序 = ['a', 'b', 'c']  OrderedDict 顺序 = ['a', 'b', 'c']
move_to_end('a') 后 = ['b', 'c', 'a']
move_to_end('a', last=False) 后 = ['a', 'b', 'c']
普通 dict 有 move_to_end 吗 = False
OrderedDict 之间比顺序 = False
普通 dict 之间比顺序 = True
OrderedDict == 普通 dict = True
```

**背景**：Python 3.7 起，**普通 `dict` 也保证插入顺序**
（3.6 是 CPython 的实现细节，3.7 写进了语言规范——**本机 3.13 实测保序**）。
所以 `OrderedDict` 失去了"唯一的保序字典"这个身份。

**它现在还差在哪（三条真实区别）**：

1. **`move_to_end(k, last=True/False)`**——普通 `dict` **没有**。
   要把一个键挪到队首/队尾，只能 `del d[k]; d[k] = v`（而且会打乱顺序语义），
   或者重建整个字典。**这是现在用 `OrderedDict` 最硬的理由**（做 LRU 缓存时).
2. **`popitem(last=False)`** 从头部弹——普通 `dict` 的 `popitem()` 只从尾部。
3. **相等性判定不同**：两个 `OrderedDict` 之间 `==` **比较顺序**（实测 `False`），
   普通 `dict` 之间 `==` **不比较顺序**（实测 `True`）。
   而 `OrderedDict == dict` 是 `True`（跨类型比较退化成普通 dict 比较）。
   → **反过来说：如果你需要"顺序不同就算不同"，`OrderedDict` 才有意义。**

**判断依据**：`json.dumps` / 遍历 / 序列化这些"保序"需求，
**普通 `dict` 就够了**（这也是 3.7 之后大多数代码不再 `import OrderedDict` 的原因）。
只有用到 `move_to_end` / `popitem(last=False)` / 顺序敏感的 `==` 时才需要它。

**`ChainMap`：多层字典的"联合视图"（提一句）**

```python
from collections import ChainMap

defaults = {"color": "red", "size": "M"}
user = {"color": "blue"}
cm = ChainMap(user, defaults)
print(cm["color"], cm["size"])
cm["size"] = "L"
print("写只落在第一个 map:", user, defaults)
```

```
blue M
写只落在第一个 map: {'color': 'blue', 'size': 'L'} {'color': 'red', 'size': 'M'}
```

**它不合并字典，只是"按顺序查"。** 读的时候从第一个 map 找到就用；
**写的时候只写第一个**。典型用途就是上面这个：
"**命令行参数 > 环境变量 > 默认配置**"的优先级查找。

### 4.4 一句话总结本节
| 场景 | 别写 | 用 |
|---|---|---|
| 给函数绑几个参数 | `lambda x: f(x, 2)` | `functools.partial(f, 2)` |
| 递归/重复调用的纯函数 | 自己写缓存字典 | `@functools.lru_cache` |
| 值对象的比较 | 手写 6 个比较方法 | `@functools.total_ordering` |

| 拼接多个序列 | `a + b + c`（建新列表） | `itertools.chain` |
| 迭代器切片 | 做不到 | `itertools.islice` |
| 分组统计 | `dict` + `if k not in d` | `Counter` / `defaultdict` |

| 固定长度滑动窗口 | 手动判断长度 | `deque(maxlen=n)` |
| 轻量记录类型 | 手写 `__init__` / `__eq__` | `namedtuple` / `dataclass` |
| "参数 > 环境 > 默认"查找 | 层层 `if` | `ChainMap` |

## 5. 类型提示深入（覆盖 9.5）
> 先说三句大实话：
>
> 1. **类型提示不改变运行时行为。** 写错了 Python 照样跑，只有类型检查器
>    （mypy / pyright / ruff）和 IDE 会告诉你。
> 2. **所以它的价值在"给读代码的人和工具看"**，不在"给解释器看"。
> 3. **本节的例子都在 3.13 上实测过**，但**"某个写法是哪个版本引入的"我只标注
>    确定的部分，不确定的一律写"未实测"**。

### 5.1 `Optional[X]` 与 `X | None`
先看一个真实的函数：查用户，查不到返回 `None`。

```python
from typing import Optional, Union

def old(uid: int) -> Optional[str]:
    return "王" if uid == 1 else None

def new(uid: int) -> str | None:
    return "王" if uid == 1 else None

print(Optional[str] == Union[str, None])       # True
print(Optional[str] == (str | None))           # True
print(old(1), new(2))                          # 王 None
print(Optional[str].__args__)                  # (str, NoneType)
```

```
True
True
王 None
(<class 'str'>, <class 'NoneType'>)
```

**`Optional[X]` 就是 `Union[X, None]` 的简写，两者实测相等。**
`X | None` 是"用 `|` 运算符写联合类型"，本机 3.13 可用
（**这个语法是 3.10 引入的，本机未逐版本实测**）。

> ⚠️ **坑**：**`Optional[X]` 不是"这个参数可以不传"，而是"这个值可以是 `None`"。**
>
> ```python
> def needs_arg(x: int | None) -> None: ...
> needs_arg()
> ```
> ```
> TypeError : needs_arg() missing 1 required positional argument: 'x'
> ```
> **"可以不传"要靠默认值**：`def f(x: int | None = None)`。
> 这个误解很常见，因为英文 `Optional` 听起来像"可选参数"。

**什么时候用哪个**：

| | `Optional[X]` | `X \| None` |
|---|---|---|
| 可读性 | 啰嗦，且容易误解成"可选参数" | **更短、语义直白** |
| 需要 `from typing import` | ✅ | ❌ |
| 运行时求值 | 一直是对象 | `X \| None` 在 3.10+ 才合法 |
| 写在字符串注解里 | 都可以 | 都可以 |

**判断依据**：**新代码用 `X | None`**（少一个 import、语义清楚）。
只有在需要兼容 3.9 及更早、或者代码库里已经统一用 `Optional` 时才用旧写法。

### 5.2 `Union` 与 `Callable`

```python
from typing import Callable

print(Union[int, str].__args__)                # (<class 'int'>, <class 'str'>)
print(Union[int, str] == (int | str))          # True

def apply_twice(f: Callable[[int], int], x: int) -> int:
    return f(f(x))

print(apply_twice(lambda v: v + 1, 5))         # 7
print(Callable[[int], int].__args__)           # (<class 'int'>, <class 'int'>)
print(Callable[..., int])                      # typing.Callable[..., int]
```

```
(<class 'int'>, <class 'str'>)
True
7
(<class 'int'>, <class 'int'>)
typing.Callable[..., int]
```

**`Callable[[参数类型...], 返回类型]`** 的读法：
**方括号里第一个列表是参数，第二个是返回值。**
`Callable[[int, str], bool]` = "收一个 int 和一个 str，返回 bool"。

**三个要点**：

1. **`...`（省略号）表示"参数不限"**：`Callable[..., int]`。
   这比不写注解好（明确说了"我接受任意可调用对象"），
   比 `Callable[[int], int]` 宽松（不误报）。
2. **`Callable` 不能精确表达关键字参数和默认值。**
   `def f(a: int, *, b: str = "")` 的精确类型在 `typing` 里没有对应写法，
   只能用 `Callable[..., X]` 或 `Protocol`（5.6 节）。
3. **`Union[int, str]` 和 `int | str` 等价**（实测 `True`），
   所以 `isinstance(x, int | str)` 能用（本机实测返回 `True`），
   `issubclass(bool, int | str)` 也能用。

### 5.3 抽象类型：为什么参数该注解成 `Iterable` 而不是 `list`
**先看一个实测事实：注解根本不拦人。**

```python
from typing import Iterable, Sequence

def total(xs: list) -> int:
    return sum(xs)

def total_ok(xs: Iterable[int]) -> int:
    return sum(xs)

for data in ([1, 2, 3], (1, 2, 3), {1, 2, 3}, (i for i in (1, 2, 3)), range(1, 4)):
    print(f"{type(data).__name__:10} sum = {sum(data)}")
```

```
list       sum = 6
tuple      sum = 6
set        sum = 6
generator  sum = 6
range      sum = 6
```

**`total(xs: list)` 和 `total_ok(xs: Iterable[int])` 对上面五种输入都能跑**
（因为注解不检查）。但**类型检查器**会：

- 传 `tuple` 给 `total(xs: list)` → **报错**（mypy: `Argument 1 has incompatible type "tuple[int, int, int]"; expected "list[Any]"`）。
- 传 `tuple` 给 `total_ok(xs: Iterable[int])` → **通过**。

**所以注解写 `list` 的代价是"白白限制了自己函数的适用范围"**，
而且这个代价不体现在运行时，只体现在"用户被 IDE 画红线"。

**取舍：参数用宽的类型，返回值用具体的类型。**

```python
def show_first(xs: Sequence[int]) -> int:
    return xs[0]

try:
    show_first({1, 2, 3})
except TypeError as e:
    print("传 set 给 Sequence 注解的函数 ->", type(e).__name__, ":", e)
```

```
传 set 给 Sequence 注解的函数 -> TypeError : 'set' object is not subscriptable
```

**这个报错说明了注解的"契约"意义**：`Sequence` 承诺"有 `len`、能索引、能切片"
（实测它的 MRO 是 `(Sequence, Reversible, Collection)`），
而 `set` 没有下标——所以**这个函数本来就要求 `Sequence`，注解写对了**。
如果你写 `Iterable[int]` 而函数体里用了 `xs[0]`，注解就是**错的**
（虽然运行时会因为传进来的恰好是 list 而通过）。

**常用抽象类型对照表**：

| 类型 | 承诺 | 典型实现 | 什么时候用它注解参数 |
|---|---|---|---|
| `Iterable[T]` | 能 `for` | list / tuple / set / dict / 生成器 / 文件 | **只需遍历一遍**（最宽，首选） |
| `Sequence[T]` | 能 `for` + `len` + 索引 + 切片 | list / tuple / str / range | 需要 `len` 或按下标取 |
| `Mapping[K, V]` | 能 `d[k]` + `keys`/`items`/`values` | dict / `ChainMap` | 只读字典（**不要写 `dict`**） |
| `MutableMapping[K, V]` | 上面 + 能赋值 | dict / `defaultdict` | 会改这个字典 |
| `Set[T]` | 集合运算 | set / frozenset | |
| `Iterator[T]` | 有 `__next__` | 生成器 / `zip` 结果 | 你**会消费**它（且只一次） |

**判断依据（三条）**：

1. **参数尽量宽**：只要能遍历，就 `Iterable[T]`。这样调用方可以传生成器，
   内存立刻省下来。
2. **返回值尽量具体**：返回 `list` 就写 `list[int]`（Python 3.9+ 支持内置类型下标，
   本机实测可用）。调用方需要知道"能索引、能 `len`、能改"。
3. **`Mapping` 比 `dict` 好**：写 `dict` 会让"传个 `ChainMap` 或 `OrderedDict`"
   被类型检查器拦下来，而它们本来就是 dict 的替代品。

> ⚠️ **一个真坑**：本机实测 `typing.Sequence.__mro__` **取不到**
> （`AttributeError: __mro__`），要用 `collections.abc.Sequence`。
> **`typing` 里那些名字（`typing.Sequence` / `typing.Iterable` / `typing.Mapping`）
> 是别名对象，不是真正的类**；需要 `isinstance` 或 `__mro__` 时
> 一律从 `collections.abc` 导入。

### 5.4 `TypeVar` 手写泛型函数
**问题**：下面这个函数想表达"给我一个什么东西，我给你同类型的一个东西"。
写 `Any` 会丢掉这个关系，写具体类型又只能管一种。

```python
from typing import TypeVar

T = TypeVar("T")

def first(xs: Iterable[T]) -> T:
    for x in xs:
        return x
    raise ValueError("空序列")

print(first([1, 2, 3]), first(["a", "b"]), first((1.5, 2.5)))
```

```
1 a 1.5
```

**`T` 的作用是把"入参的类型"和"返回值的类型"绑在一起**：
传给 `first` 一个 `list[int]`，类型检查器就知道返回的是 `int`；
传 `list[str]` 就知道返回 `str`。**同一个 `TypeVar` 名字 = 同一个类型。**

**`TypeVar` 的两个修饰**：

```python
TNum = TypeVar("TNum", int, float)            # 受限：只能是列出的类型
TBound = TypeVar("TBound", bound=Sequence)    # 有上界：必须是 Sequence 的子类

def double(x: TNum) -> TNum:
    return x * 2

def head(xs: TBound):
    return xs[0]

print("double(3) =", double(3), " double('a') =", double("a"), " <- 运行时没人管")
print("head((1, 2)) =", head((1, 2)))
```

```
double(3) = 6  double('a') = aa  <- 运行时没人管
head((1, 2)) = 1
```

**注意 `double("a")` 返回 `"aa"` —— 运行时不拦！**
`TypeVar("TNum", int, float)` 只是告诉类型检查器"这里只该传 int/float"。
**这是类型提示最重要的心态**：它是**静态文档**，不是运行时守卫。
要运行时校验就得用 `isinstance` + 抛异常（或者 `pydantic` 这类库）。

**`T`、`TNum`、`TBound` 的区别**：

| 写法 | 含义 | 类型检查器反应 |
|---|---|---|
| `TypeVar("T")` | 任意类型，但**同一次调用内必须一致** | 传 int 就把返回当 int |
| `TypeVar("TNum", int, float)` | 只能是 int 或 float | 传 str 报错 |
| `TypeVar("TBound", bound=Sequence)` | 必须是 `Sequence` 或其子类 | 传 set 报错 |

**判断依据**：**先用裸 `TypeVar("T")`。**
只有你真要限制取值范围时才加约束——加了约束会严格限制调用方，
而且类型检查器会对"函数体里能不能用某个方法"提出更细的要求。

### 5.5 `Generic` 基类：给类加类型参数

```python
from typing import Generic

T = TypeVar("T")

class Stack(Generic[T]):
    def __init__(self) -> None:
        self._items: list[T] = []

    def push(self, item: T) -> None:
        self._items.append(item)

    def pop(self) -> T:
        return self._items.pop()

    def __len__(self) -> int:
        return len(self._items)

s: Stack[int] = Stack()
s.push(1)
s.push(2)
print(s.pop(), len(s))
print(Stack.__orig_bases__)
print(Stack[int].__args__)
print("运行时 Stack[int] 依然是 Stack =", type(Stack[int]()))
```

```
2 1
(typing.Generic[~T],)
(<class 'int'>,)
运行时 Stack[int] 依然是 Stack = <class '__main__.Stack'>
Stack[int].__orig_bases__ -> AttributeError: __orig_bases__
```

**`Generic[T]` 让你能写 `Stack[int]` 这种"带参数的类型"。**
好处是类型检查器知道 `push(1)` 之后 `pop()` 出来是 `int`。

**三个实测事实**：

1. `Stack[int]` 在**运行时依然是 `Stack`**（`type(Stack[int]())` 给 `<class 'Stack'>`），
   下标只是"给检查器看的信息"。
2. `Stack[int].__args__` 是 `(<class 'int'>,)`，能取出来。
3. **`Stack[int].__orig_bases__` 取不到**（本机实测 `AttributeError`），
   要写 `Stack.__orig_bases__`。

**Python 3.12+ 的另一种写法**是 `class Stack[T]:`（PEP 695 类型参数语法），
它和 `Generic[T]` 的运行时行为几乎一样，但多出一个 `__type_params__`。
**下面 5.6 节已在本机（3.13.15）逐条实测了这套新语法。**

### 5.6 `type` 语句与 PEP 695 泛型语法（**3.12+**，本机 3.13.15 已实测）

> **版本门槛**：`type X = ...` 语句、`class C[T]:`、`def f[T]()` **全部是 3.12 引入的**
> （PEP 695）。**本机是 3.13.15，所以这一节全部是实测结果，没有"未实测"标记。**
> 但要知道：**3.11 及以下跑这些语法会直接 `SyntaxError`**（见本节最后的对照表）。

#### 5.6.1 最小例子：`type` 语句造出什么

老写法就是一句赋值：`Vector = list[float]`。新写法多一个 `type` 关键字：

```python
type Vector = list[float]
type Pair[T] = tuple[T, T]          # 类型别名也可以是泛型
type Simple = int

print("type(Vector) =", type(Vector))
print("Vector        =", Vector)
print("Vector.__name__  =", Vector.__name__)
print("Vector.__value__ =", Vector.__value__)
print("Pair.__value__   =", Pair.__value__)
print("Simple.__value__ =", Simple.__value__)
print("Vector.__type_params__ =", Vector.__type_params__)
print("Pair.__type_params__   =", Pair.__type_params__)
```

```
type(Vector) = <class 'typing.TypeAliasType'>
Vector        = Vector
Vector.__name__  = Vector
Vector.__value__ = list[float]
Pair.__value__   = tuple[T, T]
Simple.__value__ = <class 'int'>
Vector.__type_params__ = ()
Pair.__type_params__   = (T,)
```

**实测结论（这是本节最关键的一条）**：
**`type Vector = list[float]` 造出来的是一个 `typing.TypeAliasType` 对象，不是 `list[float]` 本身。**
`isinstance(Vector, typing.TypeAliasType)` 实测是 `True`，`type(Vector).__module__` 是 `typing`。

**这个对象有三个有用的属性**（`dir(Vector)` 实测就是这三个）：

| 属性 | 是什么 | 实测值 |
|---|---|---|
| `.__name__` | 别名自己的名字（字符串） | `'Vector'` |
| `.__value__` | **别名指向的真实类型** | `list[float]` |
| `.__type_params__` | 类型参数元组；非泛型别名是空元组 | `()` / `(T,)` |

> ⚠️ **坑**：`Vector != list[float]`。
> 实测 `Vector == list[float]` 是 **`False`**，`Vector is list[float]` 也是 `False`。
> 原因：`TypeAliasType` 是一个**独立的运行时对象**，它只是"指向"`list[float]`，
> 并不等于它。**判断依据**：想让运行时比较相等，就别用 `type` 语句——
> 用普通赋值 `Vector = list[float]`（那样 `Vector == list[float]` 才是 `True`）。
> **`type` 语句的价值在静态检查器那一侧，不在运行时比较。**

`.__value__` 是**惰性求值**的，这带来一个真实的好处：

```python
type Later = NotDefinedYet          # 名字此刻还不存在

print("定义成功了，Later.__name__ =", Later.__name__)
try:
    print(Later.__value__)
except NameError as e:
    print("访问 __value__ ->", type(e).__name__, ":", e)

try:
    Plain = NotDefinedYet2           # 普通赋值对比
except NameError as e:
    print("普通赋值 -> NameError:", e)

class NotDefinedYet:
    pass

type Later2 = NotDefinedYet
print("Later2.__value__ =", Later2.__value__)
```

```
定义成功了，Later.__name__ = Later
访问 __value__ -> NameError : name 'NotDefinedYet' is not defined
普通赋值 -> NameError: name 'NotDefinedYet2' is not defined
Later2.__value__ = <class '__main__.NotDefinedYet'>
```

**注意第一行：`type Later = NotDefinedYet` 定义成功了**，尽管 `NotDefinedYet` 当时不存在。
报错被推迟到**访问 `__value__` 那一刻**。
而普通赋值 `Plain = NotDefinedYet2` 立即 `NameError`。

**判断依据**：这让你能在**定义顺序自由**的情况下写类型别名
（互相引用的两个类型、先写别名后写类），代价是错误从"定义处"推迟到"使用处"。

#### 5.6.2 三种别名写法的对照（实测）

```python
import typing

type A_new = list[float]                    # PEP 695
A_plain = list[float]                       # 普通赋值
A_annot: typing.TypeAlias = list[float]     # 显式标注 TypeAlias

for name, obj in (("type 语句", A_new), ("普通赋值", A_plain), ("TypeAlias 标注", A_annot)):
    print(f"{name:14} type={type(obj).__name__:14} ==list[float]={obj == list[float]}")
print("A_new.__value__ =", A_new.__value__)
print("普通赋值有 __value__ 吗 =", hasattr(A_plain, "__value__"))
```

```
type 语句        type=TypeAliasType  ==list[float]=False
普通赋值           type=GenericAlias   ==list[float]=True
TypeAlias 标注   type=GenericAlias   ==list[float]=True
A_new.__value__ = list[float]
普通赋值有 __value__ 吗 = False
```

| 写法 | 运行时对象类型 | `== list[float]` | 有 `__value__` | 类型检查器 | 版本 |
|---|---|---|---|---|---|
| `type A = list[float]` | **`TypeAliasType`** | **`False`** | ✅ | ✅ 认得 | **3.12+** |
| `A = list[float]` | `GenericAlias` | `True` | ❌ | ⚠️ 也能认，但和"普通变量赋值"无法区分 | 全部 |
| `A: TypeAlias = list[float]` | `GenericAlias` | `True` | ❌ | ✅ 明确告诉检查器这是别名 | 3.10+（`TypeAlias` 引入版本未逐版本实测） |

**普通赋值那种写法的问题是**：类型检查器看到一个模块级变量 `A = list[float]`，
它**无法确定**你是想声明一个类型别名，还是只想用一个临时变量。
`TypeAlias` 标注和 `type` 语句都是在消除这个歧义。
**`type` 语句的额外好处**：别名能被当成真正的类型参数化使用
（`type Pair[T] = ...`，普通赋值做不到泛型别名）。

#### 5.6.3 别名能不能 `isinstance` / 能不能实例化（实测）

**预期是 `TypeError`，实测确认了，而且报错信息是三条不同的。**

```python
type Vector = list[float]
type Pair[T] = tuple[T, T]

print("Vector 能放进 dict 吗 =", {"v": Vector})      # 当值用：可以

try:
    Vector()                                        # 实例化
except Exception as e:
    print("Vector()          ->", type(e).__name__, ":", e)
try:
    print(isinstance([1.0], Vector))                # 普通别名
except Exception as e:
    print("isinstance(Vector) ->", type(e).__name__, ":", e)
try:
    print(isinstance((1, 2), Pair[int]))            # 泛型别名下标
except Exception as e:
    print("isinstance(Pair[int]) ->", type(e).__name__, ":", e)
try:
    print(isinstance(1, Vector | None))             # 联合里的别名
except Exception as e:
    print("isinstance(Vector|None) ->", type(e).__name__, ":", e)
```

```
Vector 能放进 dict 吗 = {'v': Vector}
Vector()          -> TypeError : 'typing.TypeAliasType' object is not callable
isinstance(Vector) -> TypeError : isinstance() arg 2 must be a type, a tuple of types, or a union
isinstance(Pair[int]) -> TypeError : isinstance() argument 2 cannot be a parameterized generic
isinstance(Vector|None) -> TypeError : isinstance() arg 2 must be a type, a tuple of types, or a union
```

**逐条结论**：

| 操作 | 结果 | 为什么 |
|---|---|---|
| 当值传递/放进容器 | ✅ 可以 | 它就是个普通对象 |
| `Vector(...)` 实例化 | ❌ `TypeError: 'typing.TypeAliasType' object is not callable` | 别名不是类 |
| `isinstance(x, Vector)` | ❌ `TypeError: isinstance() arg 2 must be a type, ...` | `TypeAliasType` 不是类 |
| `isinstance(x, Pair[int])` | ❌ `TypeError: ... cannot be a parameterized generic` | 下标泛型也不能用于检查 |
| `isinstance(x, Vector \| None)` | ❌ 同上第一条 | 联合里含别名也不生效 |

> ⚠️ **坑**：**类型别名一律不能用于 `isinstance` / `issubclass`。**
> 现象：`TypeError`（不是"返回 False"）。
> 原因：别名是**给静态检查器看的**，运行时它不是类。
> 处理：要运行时检查就用真正的基础类型——`isinstance(x, list)`，而不是
> `isinstance(x, Vector)`。**想"校验形状"就用 5.8 节的 `TypedDict` + 手写检查，
> 或者上 `pydantic` 这类库**，别指望类型别名。

#### 5.6.4 PEP 695 的泛型类与泛型函数（实测，把旧的"未实测"消掉）

```python
T = typing.TypeVar("T")


class NewStack[T]:                       # PEP 695 新语法
    def __init__(self) -> None:
        self._items: list[T] = []

    def push(self, item: T) -> None:
        self._items.append(item)

    def pop(self) -> T:
        return self._items.pop()

    def __len__(self) -> int:
        return len(self._items)


class OldStack(typing.Generic[T]):       # 经典写法
    def __init__(self) -> None:

    def pop(self) -> T:
        return self._items.pop()

    def __len__(self) -> int:
        return len(self._items)


def first_new[T](xs: list[T]) -> T:      # PEP 695 泛型函数
    return xs[0]


def first_old(xs: list[T]) -> T:
    return xs[0]


for name, cls in (("新 class Stack[T]", NewStack), ("旧 Generic[T]", OldStack)):
    print(f"{name}: __type_params__ = {getattr(cls, '__type_params__', '没有')}")
    print(f"   __orig_bases__ = {getattr(cls, '__orig_bases__', '没有')}")
    print(f"   __parameters__ = {getattr(cls, '__parameters__', '没有')}")
    inst = cls()
    inst.push(1)
    inst.push(2)
    print(f"   实例化 pop/len = {inst.pop()}, {len(inst)}")
    print(f"   cls[int] = {cls[int]}, type = {type(cls[int]).__name__}")

print("first_new.__type_params__ =", first_new.__type_params__)
print("first_new([10, 20]) =", first_new([10, 20]), first_new(["a", "b"]))
print("新写法 __annotations__ =", first_new.__annotations__)
print("旧写法 __annotations__ =", first_old.__annotations__)
```

**实测结论：两套写法在运行时的行为是一样的**——

| | 新 `class C[T]:` | 旧 `Generic[T]` |
|---|---|---|
| `__type_params__` | **`(T,)`** ✅ | `()`（空） |
| `__orig_bases__` | `(typing.Generic[T],)` | `(typing.Generic[~T],)` |
| `__parameters__` | `(T,)` | `(~T,)` |
| `__annotations__` 里的 T 显示 | `T` | `~T` |

> **注意 `__type_params__` 只有新写法有。** 依赖它的工具（运行时内省框架、
> 文档生成器）**在旧写法上会拿到空元组**——这是新语法的一个实质优势。

也不用把它塞进 `Generic[...]`。

#### 5.6.5 什么时候用新语法，什么时候必须留老写法

| 场合 | 选择 | 理由 |
|---|---|---|
| 新项目，只跑 3.12+ | **用 `type` / `class C[T]` / `def f[T]`** | 更短、泛型别名只有新语法能写、`__type_params__` 对工具友好 |
| 要支持 3.11 及以下 | **必须用老写法** | 新语法在 3.11 上是 `SyntaxError`，不是"运行不了"而是"文件都读不进来" |
| 维护老代码 | **跟着老代码写** | 混两套风格会让 `T` 的来源不统一（一个在 `__type_params__`，一个在 `__parameters__`） |
| 需要运行时**比较**别名和原类型相等 | 老写法（普通赋值） | `type` 语句产的别名 `== list[float]` 是 `False` |
| 需要 `isinstance` 检查 | 都不用别名 | 别名一律不能用于 `isinstance` |
| 需要泛型**别名**（`Pair[T] = tuple[T,T]`） | **只有新语法能做到** | 老写法只能写非泛型别名 |

**判断依据（一句话）**：**看你要支持的 Python 最低版本。**
最低版本 ≥ 3.12 就统一用新语法；否则一律老写法，不要混。
**"文件都读不进来"这点值得强调**：新语法是语法层面的，
在 3.11 上连 `import` 你那个模块都会失败，不是"某个功能不可用"。

> ⚠️ **本机测不了的**（照规范标注）：
> **3.11 及以下跑 `type X = int` 到底报什么**，本机是 3.13.15，**无法实测**。
> 按 PEP 695 的定位它应该是 `SyntaxError`，但**我没有在 3.11 上验证过**，
> 所以不把它当已确认的事实——验证方法是装一个 3.11 跑同一段代码。

官方文档：<https://docs.python.org/3/reference/simple_stmts.html#the-type-statement>
——`type` 语句在 "Simple statements" 一节里，它规定了语法形式
（`type` 别名只能出现在模块级、类体、函数体里）和语义。
另一页是 `typing.TypeAliasType`：
<https://docs.python.org/3/library/typing.html#typing.TypeAliasType>
——本节用的 `__name__` / `__value__` / `__type_params__` 三个属性的权威说明在这里。

### 5.7 `Protocol`：鸭子类型的静态版本（和 `abc` 对比）
**问题**：我写了个函数，它只要求"传进来的东西有 `area()` 方法"。
用 `abc.ABC` 表达这个要求，就要求所有实现者**显式继承**我的基类——
但 `Circle` 是别人的代码，我不能改它。

```python
from typing import Protocol, runtime_checkable

class HasArea(Protocol):
    def area(self) -> float: ...

class Circle:
    def __init__(self, r: float) -> None:
        self.r = r

    def area(self) -> float:
        return 3.14159 * self.r**2

class NotAShape:
    def area(self) -> float:
        return 0.0

def print_area(shape: HasArea) -> None:
    print(f"      area = {shape.area():.2f}")

print_area(Circle(2))
print_area(NotAShape())
```

```
      area = 12.57
      area = 0.00
```

**`Circle` 完全没有继承 `HasArea`，类型检查器却认为它合法**——
因为它有 `area()`。**这就是"结构化类型"（structural typing）：
不看继承关系，只看有没有那些方法。** 它正是 Python 运行时"鸭子类型"的静态版本。

**对比 `abc.ABC`**：

```python
from abc import ABC, abstractmethod

class Shape(ABC):
    @abstractmethod
    def area(self) -> float: ...

class Circle2(Shape):
    def area(self):
        return 1.0

class Triangle:
    def area(self):
        return 1.0

try:
    Shape()
except TypeError as e:
    print("抽象类不能实例化 ->", type(e).__name__, ":", e)
print("isinstance(Circle2(), Shape) =", isinstance(Circle2(), Shape))
print("isinstance(Triangle(), Shape) =", isinstance(Triangle(), Shape))
```

```
抽象类不能实例化 -> TypeError : Can't instantiate abstract class Shape without an implementation for abstract method 'area'
isinstance(Circle2(), Shape) = True
isinstance(Triangle(), Shape) = False
```

| | `abc.ABC` | `Protocol` |
|---|---|---|
| 判定依据 | **继承关系**（名义类型） | **有没有那些方法**（结构类型） |
| 实现者要做什么 | **必须显式继承** | 什么都不用做 |
| 运行时 `isinstance` | 默认就能用 | **要加 `@runtime_checkable`** |
| 能否阻止实例化 | ✅ 抽象方法没实现就 `TypeError` | ❌ 不管 |
| 能否改别人的类 | ❌ 改不了 | ✅ 只要方法对就行 |
| 适合 | 框架自己的类层次、要强制实现 | **描述"我需要什么能力"，尤其是要接受别人的类时** |

> ⚠️ **`Protocol` 必须加 `@runtime_checkable` 才能 `isinstance`。**实测：
> ```python
> @runtime_checkable
> class HasAreaRuntime(Protocol):
>     def area(self) -> float: ...
>
> print(isinstance(Circle(1), HasAreaRuntime))    # True
> print(isinstance("字符串", HasAreaRuntime))      # False
> ```
> ```
> True
> False
> ```
> **而且这个 `isinstance` 只看"方法名在不在"，不看签名**——
> `area(self, x)` 也会被判为 `True`。所以它只适合"粗略检查"。

**判断依据**：

- **定义一个类层次、要强制子类实现某些方法** → `abc.ABC`（这是它的本职）。
- **描述"我这个函数需要什么能力"，尤其要接受我改不了的类** → `Protocol`。
- 老代码里"用 `raise NotImplementedError` 假装抽象"是两者的廉价替代品，
  **但它在错误时机才报错**（实例化时/调用时），而 `abc` 在实例化时就拦住了，
  `Protocol` + 静态检查器在写代码时就拦住了。

### 5.8 `TypedDict` / `Literal` / `Final` / `Any` / `Self` / `NewType`
**`TypedDict`：给字典的形状起个名字**

```python
from typing import NotRequired, TypedDict

class Movie(TypedDict):
    title: str
    year: int
    rating: float

class Config(TypedDict):
    name: str
    debug: NotRequired[bool]

m: Movie = {"title": "某片", "year": 2026, "rating": 8.5}
print(m, isinstance(m, dict))
r = Movie(title="只有标题", year=1, rating=1.0, 多出来的=1)
print("多传一个键，运行时报错了吗 ->", type(r).__name__, r)
print(Movie.__annotations__)
print(Config.__annotations__)
```

```
{'title': '某片', 'year': 2026, 'rating': 8.5} True
多传一个键，运行时报错了吗 -> dict {'title': '只有标题', 'year': 1, 'rating': 1.0, '多出来的': 1}
{'title': <class 'str'>, 'year': <class 'int'>, 'rating': <class 'float'>}
{'name': <class 'str'>, 'debug': typing.NotRequired[bool]}
```

**`TypedDict` 运行时就是 `dict`**（`isinstance(m, dict)` 是 `True`），
它在类型检查器眼里才是"有固定键和值的字典"。

> ⚠️ **坑（本机实测，和我最初的预期相反）**：
> **`TypedDict` 在运行时完全不检查键。**
> 我用关键字语法多传了一个 `多出来的=1`，**没有报错**——
> 返回的就是一个普通的 `dict`，多出来的键原样在里面。
> 缺键、错类型同样都不会报错（`Movie(title="只有标题")` 也照样成功）。
>
> 原因：`TypedDict` 只生成 `__annotations__` 给静态检查器看，
> **它不生成任何运行时校验代码**。
>
> 处理：**别把 `TypedDict` 当运行时校验用。** 想要运行时校验必须
> （1）手写检查函数，或者（2）上 `pydantic` / `attrs` 这类真会校验的库。
> **判断依据**：`TypedDict` 的价值是"让类型检查器和 IDE 帮你发现错键"，
> 不是"在运行时拦住错数据"。

**什么时候用它**：**对接 JSON / API 响应**。
`json.loads` 返回的永远是 `dict[str, Any]`——`Any` 会传染，
后面全是"未检查"。用 `TypedDict` 断言它的形状，就能把类型检查找回来。
**代价就是上面那条坑：这个"断言"只在静态检查时有效，跑起来一点保护都没有。**

**`Literal`：枚举式的字面值**

```python
from typing import Literal

def set_level(level: Literal["debug", "info", "error"]) -> str:
    return f"级别设为 {level}"

print(set_level("info"))
print(set_level("随便写"), " <- 运行时不报错，类型检查器才会拦")
```

```
级别设为 info
级别设为 随便写  <- 运行时不报错，类型检查器才会拦
```

**`Literal` 适合"只能是这几个值"的参数**（比如日志级别、`mode`、算法名）。
它比 `Enum` 轻（不用定义类、调用方直接传字符串），
比 `str` 精确（IDE 能补全候选值）。
**代价是运行时不校验**——真要在运行时拦，就得写 `if level not in (...): raise ValueError`。

**`Final`：标记"这个不该被改"**

```python
from typing import Final

MAX_RETRY: Final = 3
print(MAX_RETRY)
MAX_RETRY = 5           # 运行时不拦
print("改完 =", MAX_RETRY)

class Config2:
    version: Final[str] = "1.0"

print(Config2.version)
```

```
3
改完 = 5
1.0
```

**`Final` 也只是给检查器看的**（实测运行时可改）。
它的价值在于**代码评审和 IDE**：别人看到 `Final` 就知道"改这个要慎重/要一起改别处"。
**注意一个易错点**：`Final` 后面**不需要**类型注解也能用（`MAX_RETRY: Final = 3`
会被推断成 `Final[int]`），**但类属性上必须写成 `x: Final[str] = "1.0"` 这种形式**。

**`Any`：放弃检查，而且会传染**

`Any` 的语义是"任何类型，且**从这里出来的值不再检查，赋给它的值也不检查**"。
所以它会**沿着数据流扩散**：一个函数标了 `Any`，
它的返回值传下去之后，下游所有操作都失去检查。

**判断依据**：`Any` 只在"和没有类型注解的动态代码打交道"时是必要的
（比如读一个第三方库返回的 `dict[str, Any]`）。
**能写具体类型就别写 `Any`**——它等于把类型提示的价值清零。

**`Self`：链式调用/工厂方法的正确返回类型**

```python
import typing

print("typing.Self 存在吗 =", hasattr(typing, "Self"))
print(typing.Self)

class Builder:
    def set_name(self, name: str) -> typing.Self:
        self.name = name
        return self

    def set_age(self, age: int) -> typing.Self:
        self.age = age
        return self

class SubBuilder(Builder):
    def set_extra(self, x: int) -> typing.Self:
        self.extra = x
        return self

b = SubBuilder().set_name("王").set_age(20).set_extra(1)
print("链式调用 =", b.name, b.age, b.extra, type(b).__name__)
```

```
typing.Self 存在吗 = True
typing.Self
链式调用 = 王 20 1 SubBuilder
```

**`Self` 解决的问题**：如果 `set_name` 标的是 `-> "Builder"`，
那么 `SubBuilder().set_name("王").set_extra(1)` 就会被类型检查器报错
（因为 `.set_name()` 返回的是 `Builder`，没有 `set_extra`）。
**标 `-> Self` 检查器就知道"返回的是调用者的那个类型"**。

**`Self` 是 3.11 引入的**（`typing.Self`）——
**本机 3.13 实测存在**，但"具体是 3.11 引入"这一条**我没有逐版本验证**，
所以算**未实测**。需要兼容 3.10 及更早时，旧写法是"泛型 `TypeVar` + `bound`"，
啰嗦得多。

**`NewType`：给基本类型起个"语义名字"**

```python
from typing import NewType

UserId = NewType("UserId", int)
u = UserId(42)
print(u, type(u).__name__, isinstance(u, int), UserId)
```

```
42 int True __main__.UserId
```

**`NewType` 运行时就是一个恒等函数**（`type(u)` 是 `int`，`isinstance(u, int)` 是 `True`），
但类型检查器会把 `UserId` 和 `int` 当成**不同类型**——
所以你没法把"订单 ID"误传给"用户 ID"。

**它和 `TypeAlias` 的区别**：`UserId = int`（普通别名）检查器认为两者完全一样；
`NewType("UserId", int)` 认为两者**不兼容**（要显式转换）。
**判断依据**：有多个语义不同但底层类型相同的值时（钱数、ID、坐标），
`NewType` 能挡住真实的"传错参数"bug。

### 5.9 `TYPE_CHECKING` 与避免循环导入
**问题**：`a.py` 要 `import b`，`b.py` 又要 `import a` → 循环导入。
但很多时候，我们**只是在注解里需要那个类型**，运行时完全不需要。

```python
from typing import TYPE_CHECKING

print("运行时 TYPE_CHECKING =", TYPE_CHECKING)

if TYPE_CHECKING:
    from decimal import Decimal       # 只给类型检查器看，运行时不执行

def price(x: int) -> int:
    return x
```

```
运行时 TYPE_CHECKING = False
```

**`TYPE_CHECKING` 在运行时是 `False`，在类型检查器眼里是 `True`。**
所以写在 `if TYPE_CHECKING:` 里的 `import` **运行时不会执行**。

**两个用途**：

1. **打破循环导入**：只在注解里用到的类型放进 `if TYPE_CHECKING:`。
2. **加快启动**：导入很重的模块（`pandas`、`torch`）只为写注解时，
   这个技巧能让程序启动时不加载它。

配合的写法是**把注解写成字符串**（或者用 `from __future__ import annotations`，
见 5.10）：因为 `if TYPE_CHECKING:` 里的名字运行时不存在，
直接写 `def f(x: Decimal)` 会在定义时求值报 `NameError`。

### 5.10 运行时获取注解：`__annotations__` 与 `get_type_hints`（实测）
**类型提示不是"注释"，它真的挂在对象上。**

```python
from typing import get_type_hints

def annotated(a: int, b: "str", c: list[int] = None) -> bool:
    """演示用函数"""
    return True

print(annotated.__annotations__)
print(get_type_hints(annotated))
print("__annotations__['b'] 是", type(annotated.__annotations__["b"]).__name__)
print("get_type_hints 里的 b 是", get_type_hints(annotated)["b"])
```

```
{'a': <class 'int'>, 'b': 'str', 'c': list[int], 'return': <class 'bool'>}
{'a': <class 'int'>, 'b': <class 'str'>, 'c': list[int], 'return': <class 'bool'>}
__annotations__['b'] 是 str
get_type_hints 里的 b 是 <class 'str'>
```

**关键区别**：

| | `obj.__annotations__` | `typing.get_type_hints(obj)` |
|---|---|---|
| 字符串注解 | **保持原样**（`'str'` 是字符串） | **求值**成真类型（`<class 'str'>`） |
| 前向引用（还没定义的名字） | 保持字符串 | 当场求值 → 可能 `NameError` |
| 继承来的注解 | 不含 | **会沿着 MRO 合并** |
| 需要 import 吗 | 不需要 | 要 `from typing import get_type_hints` |

**注解在定义时就被求值了**（除非写成字符串）：

```python
try:
    def forward() -> Undefined:      # noqa: F821
        pass
except NameError as e:
    print("直接写未来才会定义的名字 -> NameError:", e)
```

```
直接写未来才会定义的名字 -> NameError: name 'Undefined' is not defined
```

**所以"想引用还没定义的类型"必须写成字符串**：`def f() -> "Undefined": ...`。

**注解挂在哪**（实测）：

```python
print(Movie.__annotations__)
COUNT: int = 0
RATE: Final = 1.0
print("模块级 __annotations__ =", __annotations__)
```

```
{'title': <class 'str'>, 'year': <class 'int'>, 'rating': <class 'float'>}
模块级 __annotations__ = {'s': __main__.Stack[int], 'm': <class '__main__.Movie'>, 'MAX_RETRY': typing.Final, 'MODULE_LEVEL': <class 'int'>, 'COUNT': <class 'int'>, 'RATE': typing.Final}
```

（`'s'` 是 5.5 节的 `s: Stack[int] = Stack()`，`'m'` 是 `m: Movie = {...}`，
`'MAX_RETRY'` / `'MODULE_LEVEL'` / `'COUNT'` / `'RATE'` 都是模块级变量——
**只要写了 `名字: 类型`（哪怕就是普通赋值），它就会被记进 `__annotations__`**。）

| 注解位置 | 怎么取 |
|---|---|
| 函数参数/返回值 | `f.__annotations__` / `get_type_hints(f)` |
| 类属性 | `Cls.__annotations__` |
| 模块级变量 | 模块的 `__annotations__`（函数里就是 `globals()['__annotations__']`） |

**谁在用它**：`dataclasses`（决定字段）、`pydantic`（生成校验器）、
`FastAPI`（生成参数校验和文档）、`typing.get_type_hints`、
以及各种 ORM 和 CLI 框架。**这就是"写类型提示有回报"的真正原因**——
不是解释器在用，是一堆工具在用。

### 5.11 `from __future__ import annotations` 的作用（实测）

```python
from __future__ import annotations

import typing

def f(a: int, b: NotDefinedYet) -> AlsoNotDefined:      # noqa: F821
    return None

print(f.__annotations__)
print("全是字符串吗 =", [type(v).__name__ for v in f.__annotations__.values()])
try:
    typing.get_type_hints(f)
except NameError as e:
    print("get_type_hints 时才炸 ->", type(e).__name__, ":", e)
print("有 __annotate__ 吗 =", hasattr(f, "__annotate__"))
```

```
{'a': 'int', 'b': 'NotDefinedYet', 'return': 'AlsoNotDefined'}
全是字符串吗 = ['str', 'str', 'str']
get_type_hints 时才炸 -> NameError : name 'NotDefinedYet' is not defined
有 __annotate__ 吗 = False
```

**这一行 `from __future__ import annotations` 让所有注解变成字符串**（实测
`{'a': 'int', 'b': 'NotDefinedYet', 'return': 'AlsoNotDefined'}`）。

**它带来三个好处**：

1. **不会因为"引用还没定义的名字"而 `NameError`**——
   函数定义能成功，错误推迟到 `get_type_hints` 那一刻。
2. **打破循环导入**（不用再写 `if TYPE_CHECKING:` 也能引用）。
3. **性能**：注解不求值，模块导入更快（微小的收益）。

**代价**：**运行时想用注解就必须走 `get_type_hints()`**，
而且那时候才可能报错。所以"靠 `__annotations__` 做运行时逻辑"的库
（`pydantic` 等）要么调 `get_type_hints`，要么要求用户别开这个开关。

**版本情况（诚实标注）**：

- `from __future__ import annotations` 本身在 3.7+ 可用（**本机 3.13 实测可用**）。
- **Python 3.14 的 PEP 649 会改变注解的求值时机**（引入函数的 `__annotate__`）。
  本机实测 `hasattr(f, "__annotate__")` 是 `False`，因为**本机是 3.13**。
  **3.14 上的行为我没有实测**，所以不写成事实。

| 返回自身类型 | `Self`（3.11+） | ❌ |
| 底层同类型但语义不同 | `NewType("UserId", int)` | ❌ |
| 只给检查器的 import | `if TYPE_CHECKING:` | —— |
| 全部延迟求值 | `from __future__ import annotations` | —— |

**官方文档**：
- `typing` 模块：<https://docs.python.org/3/library/typing.html>
  ——很长，当手册查。重点看开头的"Type aliases / NewType / Generics / Protocol"。
- `abc` 模块：<https://docs.python.org/3/library/abc.html>
  ——短，重点看 `ABCMeta` 和 `abstractmethod` 的组合效果（5.6 节实测了"实例化就报错"）。
- `collections.abc`：<https://docs.python.org/3/library/collections.abc.html>
  ——**`isinstance` 和 `__mro__` 要用这一页的类型**，不是 `typing` 里的别名。

## 6. GIL 是什么、为什么存在（覆盖 9.6）
> **本节是概念级的。** 目的是让你"不再对多线程有错误期待"，
> 而不是教你怎么绕开 GIL 做优化。实现细节（切换间隔、
> `sys.setswitchinterval`、`PyThreadState`）不展开。

### 6.1 先给反例：两个线程做纯计算并不更快（实测）

```python
import threading
import time

def cpu_work(n):
    """纯 Python 计算：数数"""
    total = 0
    for i in range(n):
        total += i * i
    return total

N = 3_000_000

t0 = time.perf_counter()
cpu_work(N)
cpu_work(N)
t_single = time.perf_counter() - t0
print(f"1) 单线程顺序做两份 : {t_single:.3f} s")

results = []

def worker():
    results.append(cpu_work(N))

t0 = time.perf_counter()
ths = [threading.Thread(target=worker) for _ in range(2)]
for t in ths:
    t.start()
for t in ths:
    t.join()
t_thread = time.perf_counter() - t0
print(f"2) 两个线程各做一份 : {t_thread:.3f} s")
print(f"   -> 提速比 = {t_single / t_thread:.2f}x  （1.0 上下说明没快）")
```

```
1) 单线程顺序做两份 : 0.242 s
2) 两个线程各做一份 : 0.257 s
   -> 提速比 = 0.94x  （1.0 上下说明没快）
```

**这台机器有 32 个 CPU 核，但两个线程做同样的活，一点没变快（还慢了一点点）。**
如果"线程 = 并行"，这里应该接近 2.0x。

**原因就是 GIL。** 换两个**进程**（不共享 GIL）就会快，
但本机在这个受限沙箱里 `multiprocessing.Pool` 直接
`PermissionError: [WinError 5]`（创建管道被拒），所以这里只给结论。
用 `subprocess` 起两个干净的解释器进程实测时，
两个子进程各自报告的内部耗时几乎相同（`['1.312', '1.464']`），
但我在这台被沙箱限制的机器上测到的 wall time 不稳定，
**所以"进程能真并行"这一条我只给原理，不拿本机数字当证据。**

### 6.2 GIL 的定义
**GIL = Global Interpreter Lock，全局解释器锁。**

**它保证：同一时刻，一个 CPython 进程里只有一个线程在执行 Python 字节码。**

三个限定词很重要：

| 限定 | 意思 |
|---|---|
| **CPython** | 这是 CPython 的实现细节，不是 Python 语言的规定。Jython / IronPython 没有 GIL |
| **字节码** | 锁保护的是"执行 Python 字节码"这件事。见 6.4：调 C 函数时可能放锁 |
| **一个进程** | 多进程各自有独立的 GIL，互不影响 |

**所以"Python 的多线程是假的"这个说法错了一半**——
线程是真的（OS 线程、真的在切换），但**它们不能同时跑 Python 字节码**。

### 6.3 为什么存在：引用计数不是线程安全的
CPython 管理内存靠**引用计数**：每个对象有一个计数器，
多一个人引用它就 +1，少一个就 -1，减到 0 立刻释放。

```python
import sys

a = []
print("刚创建时引用计数 =", sys.getrefcount(a) - 1)   # 减 1 是因为 getrefcount 自己算一次
b = a
print("赋值给 b 之后 =", sys.getrefcount(a) - 1)
del b
print("del b 之后 =", sys.getrefcount(a) - 1)
```

```
刚创建时引用计数 = 1
赋值给 b 之后 = 2
del b 之后 = 1
```

**引用计数的修改不是原子操作。** `x = a` 这行在底层要做：

1. 读 `a` 的引用计数
2. 加 1
3. 写回去
4. 让变量 `x` 指向 `a`

**这是典型的"读-改-写"，两个线程交错就会丢更新**：

```
线程1 读到 1
线程2 读到 1            <- 线程1 还没写回去
线程1 写回 2
线程2 写回 2            <- 丢了 1 次 +1
结果：计数是 2，实际有 3 个引用
```

**计数少算了会导致提前释放**（对象还在用就被回收）——
这是**内存不安全**，会段错误、会读到垃圾数据。

**那怎么办？两个方案**：

| 方案 | 代价 |
|---|---|
| 给每个对象的引用计数都配一把小锁 | 每次赋值、每次传参都要加锁解锁 → **慢到不可用** |
| **给整个解释器配一把大锁（GIL）** | 简单、单线程性能几乎不损失；代价是**多线程不能并行跑字节码** |

**CPython 选了第二个。** 这是历史选择（1990 年代单核机器，
多线程并行根本不是需求），而且它有一个巨大的好处：
**C 扩展的作者不用操心线程安全**——只要拿着 GIL，
所有 Python 对象都是安全的。这是 NumPy、lxml、数据库驱动
能大批量存在的原因之一。

**这就是"为什么存在"的完整答案**：
**它不是设计失误，是为了"简单 + 单线程快 + C 扩展好写"付出的代价。**

### 6.4 对谁有影响、对谁没影响
**这是本节最实用的一张表。**

| 任务类型 | GIL 的影响 | 为什么 | 该用什么 |
|---|---|---|---|
| **纯 Python 计算**（循环、递归、字符串处理） | ❌ **完全无加速** | 全程在跑字节码，锁无法释放 | 多进程 / C 扩展 / 换算法 |
| **IO 等待**（文件、网络、数据库、`sleep`） | ✅ **基本线性加速** | 等待时**主动释放 GIL**，别的线程能跑 | 多线程 / `asyncio` |
| **调用 C 扩展的重活**（NumPy、`hashlib`、`zlib`） | ⚠️ **看情况** | 有些 C 函数会**周期性释放** GIL，有些不会 | 看具体库；NumPy 大多数放、`hashlib` 部分放 |
| **混合（抓网页 + 解析）** | ⚠️ 解析部分是瓶颈 | 抓的时候并行，解析的时候串行 | 多线程抓 + 多进程解析 |

**两个实测**：

**IO 等待会放锁**（`time.sleep` 就是最纯粹的"等"）：

```python
DELAY = 0.5

def io_work():
    time.sleep(DELAY)

t0 = time.perf_counter()
io_work()
io_work()
a = time.perf_counter() - t0

t0 = time.perf_counter()
ths = [threading.Thread(target=io_work) for _ in range(2)]
for t in ths:
    t.start()
for t in ths:
    t.join()
b = time.perf_counter() - t0
print(f"IO 单线程两次 sleep(0.5) = {a:.3f}s   两个线程 = {b:.3f}s   提速 {a / b:.2f}x")
```

```
IO 单线程两次 sleep(0.5) = 1.001s   两个线程 = 0.502s   提速 1.99x
```

**1.99x —— 接近完美并行。** 这就是"IO 密集多线程有用"的硬证据。

**C 扩展要具体看**（`hashlib.sha256` 的重活**没有**加速）：

```python
import hashlib

M = 200_000

def hash_work(n):
    d = b"x" * 1024
    for _ in range(n):
        hashlib.sha256(d).digest()

t0 = time.perf_counter()
hash_work(M)
hash_work(M)
c = time.perf_counter() - t0
t0 = time.perf_counter()
ths = [threading.Thread(target=hash_work, args=(M,)) for _ in range(2)]
for t in ths:
    t.start()
for t in ths:
    t.join()
d = time.perf_counter() - t0
print(f"sha256 单线程两份 = {c:.3f}s   两个线程 = {d:.3f}s   提速 {c / d:.2f}x")
```

```
sha256 单线程两份 = 0.320s   两个线程 = 0.336s   提速 0.95x
```

**0.95x，没有加速。** 这纠正了一个流传很广的说法："只要在 C 里就会放 GIL"。
**放不放 GIL 是每个 C 函数自己决定的**，`hashlib` 对我们这种"小块数据反复调用"
的场景没有放（**具体某个函数放不放锁需要查该函数的文档或源码，本机没有逐函数实测**）。

> ⚠️ **结论**：**"用了 C 扩展就能并行"是错的。** 想确认的话，
> 唯一可靠的办法是**实测**：跑单线程和多线程两遍，看是否接近 2x。

**还有一个必须知道的点：GIL 不保证你的代码是线程安全的。**

```python
counter = {"v": 0}

def bump(n):
    for _ in range(n):
        counter["v"] += 1

K = 200_000
ths = [threading.Thread(target=bump, args=(K,)) for _ in range(2)]
for t in ths:
    t.start()
for t in ths:
    t.join()
print(f"counter['v'] += 1 两个线程各 {K} 次 -> {counter['v']}（期望 {2 * K}）")
```

```
counter['v'] += 1 两个线程各 200000 次 -> 400000（期望 400000）
```

**这次结果是对的**——但这**不代表这段代码安全**。
`counter["v"] += 1` 在字节码层面是好几条指令（取 `counter`、
按下标取值、加一、按下标存回），中间**完全可能被切走**。
这次没出错是因为"操作足够快，切换间隔（默认 0.005 秒）内跑完了"。

> ⚠️ **坑**：**"GIL 会让 `+=` 安全"是错的。**
> 实测这次恰好没错，但同样的代码在数据量更大、
> 或者机器负载不同的时候就会出错。**判断依据**：
> 只信"GIL 保证单个字节码指令原子"这一条；
> 多个指令组成的"读-改-写"（`+=`、`append` 之后再 `len`、
> 先 `if k in d` 再 `d[k]`）**都不安全**，必须用 `threading.Lock`。
> 具体怎么加锁见 `12_并发与网络.md`。

### 6.5 绕过 GIL 的三条路
| 方式 | 怎么做 | 代价 |
|---|---|---|
| **多进程** | `multiprocessing` / `concurrent.futures.ProcessPoolExecutor` | 进程间**数据要序列化**（pickle），启动慢，共享内存麻烦 |
| **C 扩展里放锁** | 让重活发生在会放 GIL 的 C 代码里（NumPy 的向量运算、某些压缩/哈希） | 要选对库，而且要实测确认真的放锁 |
| **自由线程构建** | 3.13 起有**实验性**的 `python3.13t` "no-GIL" 构建 | **未实测**；生态兼容性未知，不是默认构建 |

**关于第三条（诚实标注）**：3.13 引入了实验性的**自由线程（free-threaded）**
构建，其解释器可以在运行时真正并行执行字节码。
**本机装的是标准的 3.13.15，不是自由线程构建**——
一个证据是实测 `sys._is_gil_enabled()` 返回 `True`
（这个函数存在本身说明解释器支持"关 GIL"的概念，
**但这个构建里 GIL 是开着的**）。
**自由线程构建在 3.13 上的实际表现、以及对第三方库的影响，我没有实测，
所以不写成事实。** 想知道的话要另装 `python3.13t` 并跑同一份压测。

### 6.6 该选什么：一张决策表
| 你的瓶颈是 | 首选 | 为什么 |
|---|---|---|
| **等待网络/磁盘/数据库** | `asyncio`（IO 大、连接多）或 `threading`（IO 少、逻辑简单） | 等待时放 GIL，并发真的有效 |
| **纯 Python 计算** | `multiprocessing` / `ProcessPoolExecutor` | 每个进程一个 GIL，真并行 |
| **数值计算** | NumPy 的**向量化**（不是多线程） | 向量化把循环推给 C，一次调用算几百万个元素，比多线程快几个数量级 |
| **IO 多但逻辑是同步库**（`requests` 等） | 线程池 | `requests` 不异步，线程池是最短路径 |
| **就是想把 GIL 去掉** | 3.13+ 自由线程构建（**未实测**） | 生态兼容性风险自担 |

**最后一句最重要的取舍**：
**先解决算法，再考虑并发。** 一个 O(n²) 的纯 Python 循环
换成 `numpy` 向量化通常快几十到几百倍；同一份代码改成多进程最多快 N 倍（N = 核数），
而且带来序列化开销和调试难度。**"加线程"应该是最后才考虑的手段。**

`asyncio`、`concurrent.futures`、正则、`datetime`、`socket`。

   为什么返回值反而该写具体类型？

    "两个线程各 `sleep(0.5)`"呢？这两个数字分别说明了 GIL 的什么性质？

<details>
<summary>答案</summary>

1. 先 `iter(obj)`（调 `__iter__`）拿到迭代器，然后反复 `next(迭代器)`（调 `__next__`）。
   拿不到下一个时迭代器抛 `StopIteration`，`for` 把它接住并正常结束循环。
   **它不算错误，是因为它是"迭代协议的一部分"**——迭代器用它表达"我讲完了"。
   所以 `for` 里永远看不到这个异常；也**不能在生成器里让它冒泡出去**
   （会被转成 `RuntimeError: generator raised StopIteration`）。

2. **可迭代对象的 `__iter__` 每次返回一个全新的迭代器**；
   **迭代器的 `__iter__` 返回它自己**（`iter(it) is it` 为 `True`）。
   所以可迭代对象能反复遍历，迭代器只有一个游标、只能用一次。
   `zip` 在 Python 3 返回的是迭代器，第一次 `list()` 已经把它推到末尾，
   第二次得到 `[]`。处理办法是先 `list()` 固化。

3. 本机实测（20 万项）：`list` 版 **7.7 MB**，生成器版 **0.2 KB**（空转）
   到 **0.4 KB**（完整遍历一遍）。
   生成器的内存和 n 无关，因为它**一次只持有当前这一个值**——
   局部变量就那几个（`n`、`i`），栈帧大小固定。
   而 `list` 要存 n 个对象 + 列表槽位，内存 ∝ n。

4. **一行都不执行。** 调用生成器函数只是**创建一个生成器对象**，
   函数体要等到第一次 `next()` / `for` 才跑（本机实测：打印
   `调用 noisy_gen()` 之后没有 `[函数体开始执行]`）。
   调试上的意外：**生成器里的代码有 bug，在"调用处"不会暴露**，
   会在"迭代处"报错，而那往往离调用处很远（甚至是别人遍历的）。
   所以"我调了这个函数但什么都没发生"经常是因为忘了遍历它。

5. 丢 `__name__`（变 `'wrapper'`）、`__doc__`（变 `None`）、
   `__qualname__`（变 `'bad_deco.<locals>.wrapper'`）、
   以及 **`inspect.signature`**（变 `(*args, **kwargs)`）。
   **关键是签名**：FastAPI / pydantic 这类库靠 `inspect.signature`
   读参数来决定"哪个参数是路径变量、哪个要校验什么类型"。
   签名一变成 `*args, **kwargs`，这些库就完全没法工作——
   而且通常不是抛异常，而是"参数莫名其妙不见了"，很难排查。
   `functools.wraps` 会复制那些属性并设置 `__wrapped__`，
   让 `inspect.signature` 去读原函数。

6. 因为 `@repeat(3)` 后面**是个调用**，展开式是（这行本身不能单独运行，`repeat` 是上文定义的装饰器）：

```text
say = repeat(3)(say)
```

   所以 `repeat(3)` 必须返回"能接收函数的东西"（第 2 层），
   第 2 层再返回真正的包装函数（第 3 层）。
   第 1 层收装饰器参数，第 2 层收被装饰函数，第 3 层收调用实参。
   **装饰阶段从下往上**：先 `b_deco(hello)`，再 `a_deco(结果)`
   （实测先打印 `[b_deco 正在装饰]`，再 `[a_deco 正在装饰]`）。
   调用阶段则是"a 先进、b 后进，b 先出、a 后出"。

7. **`groupby` 是流式的**：它只把"相邻的相同 key"聚在一起，
   不看全局。所以同一个 key 在输入里出现多次、中间夹了别的 key 时，
   会产生多组（实测"水果"出现三次）。
   解决：先 `sorted(data, key=同一个key函数)`。
   **`group` 也是迭代器**，`groupby` 靠推进主迭代器来产生下一个分组，
   所以出了循环体 `group` 就作废——把 `(key, group)` 存起来事后再读，
   得到的是 `[('水果', []), ('蔬菜', [])]`（空列表）。
   必须**在循环体内当场消费**（转 `list` 或写进 dict）。

8. `Counter` 多给的：
   （1）`c[不存在的键]` 返回 `0` 而不是 `KeyError`；
   （2）`most_common(n)` 直接给排序结果；
   （3）支持 `+` `-` `&` `|` 集合式运算（**注意 `-` 会丢掉 0 和负数**，
   要保留负数得用 `subtract()`）；
   （4）`elements()` 和 `total()`。
   `deque` 的价值：**两端插入/删除都是 O(1)**，而 `list.insert(0, x)` /
   `list.pop(0)` 是 O(n)。本机实测头部插入 10000 次：
   `list.insert(0,..)` **26.2 ms**，`deque.appendleft` **0.2 ms**（约 130 倍）。
   另外 `deque(maxlen=n)` 自动实现固定长度滑动窗口。

9. 因为注解写 `list` 时，**类型检查器**会对传 `tuple` / `set` / 生成器
   的调用报错——而你的函数体（比如 `sum(xs)`）其实对它们都能工作。
   这是"白白限制了自己函数的适用范围"，代价是调用方看到红线。
   写 `Iterable[int]` 表示"我只需要能遍历"，让调用方能传生成器（省内存）。
   返回值反过来：调用方需要知道"能不能索引、能不能 `len`、能不能改"，
   所以返回 `list` 就写 `list[int]`，写 `Iterable[int]` 会让调用方不敢用下标。

10. **纯计算：0.94x**（单线程 0.242 s，双线程 0.257 s）——不但没快，还略慢。
    **`sleep`：1.99x**（单线程 1.001 s，双线程 0.502 s）——接近完美并行。
    这两个数字说明 GIL 的两面：
    （1）**同一时刻只有一个线程在跑 Python 字节码**，所以纯计算双线程
    只能交替执行、总量不变，还多了切换和调度开销（所以 ≤1.0）；
    （2）**等待 IO 时线程会主动释放 GIL**，另一个线程能立刻接手，
    所以等待可以被完全重叠（所以接近 2.0）。
    结论：**"多线程对 IO 密集有用、对 CPU 密集没用"不是玄学，是这两条机制的直接后果。**

</details>

| 3.14 的 PEP 649（`__annotate__`）对注解的影响 | **未实测**（本机 3.13，实测 `hasattr(f, "__annotate__")` 是 `False`） | 3.14 上跑 5.11 节的脚本 |
| 生成器里 `StopIteration` 从"警告"变"报错"的确切版本 | **未实测**（3.13 实测是 `RuntimeError`） | 在 3.6 / 3.7 上跑 1.6 的 `bad_gen` |

**两条环境限制**：

1. **本机运行在受限沙箱里**，`multiprocessing.Pool` 无法创建管道
   （`PermissionError: [WinError 5]`），所以**所有"多进程"的实测都做不了**。
   6.1 / 6.5 里关于多进程的部分只给原理，没有本机数字。
2. GIL 相关的**性能数字**（0.94x / 1.99x / 0.95x）是在这台
   **32 核、但可能同时在跑别的东西**的机器上测的。
   关键结论（"纯计算不加速" / "IO 等待能并行"）是稳定的，
   **具体百分数不要当基准**——要结论请在你自己的目标机器上重跑。
