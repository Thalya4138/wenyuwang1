>
> 这一章解决一个问题：**代码不出错的时候怎么写都行，出错的时候怎么办。**
> 上一章讲的是"怎么把数据和操作组织起来"，这一章讲"**出错时信息往哪儿走、谁来接**"。
> 附带一个更值钱的技能：**看懂报错信息**——这是自学 Python 时最省时间的一项能力。

## 0. 先记住六件事

1. **异常是控制流，不是"程序坏了"。** `raise` 就是把控制权往上层扔，让知道怎么处理的那一层处理。
2. **`else` 是"try 里没出错才跑"，`finally` 是"无论如何都跑"。** 两者经常被搞混。
3. **`except Exception` 和裸 `except:` 不是一回事。** 裸 `except` 连 `Ctrl+C` 都吞（第 1.4 节）。
4. **`except` 的顺序：子类必须写在父类前面。** 写反了，子类那支就是永远不会执行的死代码。
5. **`assert` 会在 `python -O` 下被整条删掉**，所以它**不能用来校验用户输入**（第 4 节）。
6. **traceback 从下往上读**：最后一行才是"什么错 + 什么消息"，上面是"怎么走到这一步的"。

## 1. `try` / `except` / `else` / `finally`（覆盖 7.1）

### 1.1 先看不用异常的时候

```python
# 用"返回特殊值"表示出错
def divide(a, b):
    if b == 0:
        return None          # 用 None 表示"算不了"
    return a / b


print(divide(10, 2))    # 5.0
print(divide(10, 0))    # None

# 用异常表示出错：调用者不处理就会拿到完整的错误信息
def divide2(a, b):
    return a / b


print(divide2(10, 2))   # 5.0
divide2(10, 0)          # ZeroDivisionError: division by zero（完整 traceback 见第 5.1 节）
```

**异常的设计意图**：正常路径的代码保持干干净净（不用一层层 `if` 检查），
出错时用一个**独立的通道**把信息送到能处理它的地方。
这个通道长什么样、怎么读，是第 5.1 节的内容。

用返回 `None` 表示出错的问题在于：**调用者必须记得检查**。
忘了检查，`None` 就会被当成正常值一路往下传，
错误最终在离源头很远的地方爆出来，而且信息完全指不到真正的源头。

### 1.2 最小例子：四段各管什么

```python
def demo(x):
    print(f"--- 传入 {x} ---")
    try:
        print("  [try] 开始")
        result = 100 / x
        print("  [try] 算完了")
    except ZeroDivisionError:
        print("  [except] 抓到除零错误")
        result = None
    else:
        print("  [else] 没出错才跑，result =", result)
    finally:
        print("  [finally] 无论如何都跑一遍")
    return result


print(demo(4))
print()
print(demo(0))
```

真实输出：

```
--- 传入 4 ---
  [try] 开始
  [try] 算完了
  [else] 没出错才跑，result = 25.0
  [finally] 无论如何都跑一遍
25.0

--- 传入 0 ---
  [try] 开始
  [except] 抓到除零错误
  [finally] 无论如何都跑一遍
None
```

| 段 | 什么时候执行 | 干什么用 |
|---|---|---|
| `try` | 总是 | 放"可能出错的代码"（尽量只放这一件事） |
| `except 某异常` | 出现**匹配的**异常时 | 处理它 |
| `else` | `try` 里**没出任何异常** | 放"只有成功后才该做的事" |
| `finally` | **无论如何**（包括 `return`、`break` 出去了） | 清理：关文件、还连接、放锁 |

**为什么需要 `else`**：把"可能出错的代码"和"成功后的后续代码"分开。
如果你把后续代码也放进 `try`，那它抛出的异常会被**同一个 `except` 捕获**，
你会把一个 bug 当成"正常业务错误"处理掉。

**`try` 里 `return` 了，`finally` 还会跑**：

```python
def with_return():
    try:
        print("  [try] 准备 return")
        return "try 的返回值"
    finally:
        print("  [finally] return 也没拦住我")


print(with_return())
```

```
  [try] 准备 return
  [finally] return 也没拦住我
try 的返回值
```

> **`finally` 的执行时机是"离开这个 `try` 语句之前"**，不管你是怎么离开的。

### 1.3 ⚠️ `finally` 里有 `return` 会覆盖

```python
# finally_return.py
def f():
    try:
        raise ValueError("我本来要被抛出去的")
    finally:
        return "finally 说了算"


print("调用结果：", f())
print("异常没了")
```

真实输出：

```
调用结果： finally 说了算
异常没了
```

**异常被无声地吞掉了，函数还正常返回了一个值。** `finally` 里的 `return`
会覆盖 `try` 里的返回值，也会吃掉正在抛出的异常。

> ⚠️ **坑**：**永远不要在 `finally` 里写 `return` / `break` / `continue`。**
> Python 3.14 起这种写法在部分场景会给出警告（**这条我没有实测 3.14 的行为，本机是 3.13.15**），
> 但不管哪个版本，**行为本身就已经是错的**：它让"发生了异常"这件事凭空消失。
> `finally` 只放清理代码。

### 1.4 裸 `except:` 的坏处（实测）

`except:` 什么都不写 = 捕获 `BaseException` 的所有子类，**包括 `Ctrl+C`**：

```python
def bare():
    try:
        raise KeyboardInterrupt()      # 模拟用户按了 Ctrl+C
    except:                            # ← 裸 except
        print("裸 except 说：我抓到了点什么")


bare()
print("程序还在跑 —— 用户按的 Ctrl+C 被无声吞掉了")
```

```
裸 except 说：我抓到了点什么
程序还在跑 —— 用户按的 Ctrl+C 被无声吞掉了
```

对比只抓 `Exception`：

```python
def specific():
    try:
        raise KeyboardInterrupt()
    except Exception:
        print("永远走不到这里")


try:
    specific()
except KeyboardInterrupt:
    print("只抓 Exception 时，KeyboardInterrupt 会继续往外冒 —— 这才是对的")


print(issubclass(KeyboardInterrupt, Exception))   # False
print(issubclass(SystemExit, Exception))          # False
print(issubclass(KeyboardInterrupt, BaseException))  # True
print(issubclass(ValueError, Exception))          # True
```

真实输出：

```
只抓 Exception 时，KeyboardInterrupt 会继续往外冒 —— 这才是对的

False
False
True
True
```

**`KeyboardInterrupt` 和 `SystemExit` 不是 `Exception` 的子类**（它们在 `BaseException` 下另一支，
见第 2 节）。所以：

- `except Exception:` **不会**吞掉 `Ctrl+C` 和 `sys.exit()` —— 这是你要的。
- `except:` **会**吞掉 —— 用户按了 `Ctrl+C` 想停下，程序却继续跑；
  写脚本时更糟：你以为按了 `Ctrl+C`，其实脚本还在后台默默干活。

> ⚠️ **坑**：裸 `except:` 还会吞掉**你自己的编程错误**——
> `NameError`、`AttributeError`、`TypeError` 这些是 bug，不是"预期中的业务错误"。
> 被吞掉之后你看到的是"程序跑完了但结果不对"，而不是"第 37 行变量名拼错了"。
> **一律写 `except Exception:`，或者更具体。**

### 1.5 ⚠️ 多个 `except` 的顺序

规则：**Python 从上往下逐个试，第一个匹配上的就执行，后面的不再看。**
所以**子类必须写在父类前面**：

```python
class MyError(ValueError):
    pass


def wrong():
    try:
        raise MyError("我是 ValueError 的子类")
    except ValueError:          # 父类写在前面 —— 会先匹配上
        print("  被 ValueError 接走了（子类专门的处理没机会跑）")
    except MyError:
        print("  被 MyError 接走了")


def right():
    try:
        raise MyError("我是 ValueError 的子类")
    except MyError:             # 子类写在前面
        print("  被 MyError 接走了")
    except ValueError:
        print("  被 ValueError 接走了")


print("顺序写错：")
wrong()
print("顺序写对：")
right()
```

```
顺序写错：
  被 ValueError 接走了（子类专门的处理没机会跑）
顺序写对：
  被 MyError 接走了
```

顺序错了不会报错，只是**行为不是你要的**。更极端的情况是子类那支变成死代码：

```python
def dead():
    try:
        raise MyError("x")
    except Exception:           # 把所有东西都接了
        print("  被 Exception 接走")
    except MyError:             # 永远不可能执行
        print("  这行是死代码")


dead()      # 被 Exception 接走
```

> ⚠️ **坑**：`except Exception:` 放在最前面，会把后面所有更具体的分支全变成死代码。
> **顺序原则：越具体越靠前，兜底的放最后。**

### 1.6 `as e`、`.args`、`str(e)`

```python
try:
    raise ValueError("分数超范围", 120)
except ValueError as e:
    print(type(e))            # <class 'ValueError'>
    print(str(e))             # ('分数超范围', 120)
    print(repr(e))            # ValueError('分数超范围', 120)
    print(e.args)             # ('分数超范围', 120)
    print(e.args[0])          # 分数超范围
    print(e.args[1])          # 120
```

真实输出：

```
<class 'ValueError'>
('分数超范围', 120)
ValueError('分数超范围', 120)
('分数超范围', 120)
分数超范围
120
```

**单个参数是常态**，`str(e)` 就是那个参数本身：

```python
try:
    int("abc")
except ValueError as e:
    print(str(e))
    print(e.args)
    # invalid literal for int() with base 10: 'abc'
    # ("invalid literal for int() with base 10: 'abc'",)
```

两个要点：

- **`e.args` 永远是元组**。构造异常时传几个参数，就有几个元素。
  传一个 → `str(e)` 就是它；传多个 → `str(e)` 是它们的 `repr` 拼起来（上面那个 `('分数超范围', 120)`）。
- **`as e` 的 `e` 出了 `except` 块就没了**（Python 主动删掉，避免循环引用拖住 traceback）：

```python
try:
    pass
except ValueError as e:
    pass
print("e" in dir())    # False
print(e)               # NameError: name 'e' is not defined
```

**需要留到后面用就自己存一份**：`except ValueError as e: saved = e`。

> 3.11 起异常对象多了个 `add_note()`，可以挂"补充上下文"，
> 它会出现在 traceback 末尾、而 `str(e)` 里看不到：

```python
import traceback

try:
    raise ValueError("原始信息")
except ValueError as e:
    e.add_note("补充上下文：这个值是用户输入的")
    print(str(e))                 # 原始信息
    traceback.print_exc()
```

```
原始信息
Traceback (most recent call last):
  File "note_demo.py", line 4, in <module>
    raise ValueError("原始信息")
ValueError: 原始信息
补充上下文：这个值是用户输入的
```

> 本机 3.13.15 实测可用。**`add_note` 是 3.11 新增的**，
> 我**没有在 3.10 及更低版本上验证过它的缺失表现**，标注为未实测旧版本。

三个**必须记住的位置**：

1. **`Exception` 和 `KeyboardInterrupt` / `SystemExit` / `GeneratorExit` 是兄弟**，
   后三者直接挂在 `BaseException` 下。
2. `OSError` 是**文件/系统相关异常的父类**，`FileNotFoundError` / `PermissionError`
   都在它下面——所以 `except OSError:` 能一次接住所有"操作系统层面的事"。
3. `LookupError` 是 `IndexError` / `KeyError` 的父类。

### 2.2 为什么 `KeyboardInterrupt` 在 `Exception` 之外

这是**设计决定**，而且它解释了第 1.4 节那个坑：

- `KeyboardInterrupt`：用户按 `Ctrl+C`。
- `SystemExit`：代码调了 `sys.exit()` 或 `raise SystemExit`。
- `GeneratorExit`：生成器被 `close()` 了。

这三件事的共同点：**它们不是"程序出错了"，而是"要求程序停下来"。**
如果它们继承自 `Exception`，那么任何一句 `except Exception:`
（比如"处理网络请求失败"）都会把用户的 `Ctrl+C` 拦住——
你会遇到"按了 `Ctrl+C` 没反应，只能关进程"的惨状。

所以 Python 把它们放在 `Exception` **外面**，并规定：
**`except Exception:` 不接它们，只有裸 `except:` 和 `except BaseException:` 才接。**

> **结论：想接"业务上的错误"就写 `except Exception:`。
> 想接"所有能让程序停下来的东西"才写 `except BaseException:`——
> 后者在正常代码里几乎只是"我要在最顶层记录日志然后退出"这一种场合。**

### 2.3 常见异常速查

下面每一行都在本机实跑过，消息是真实输出：

```python
def show(label, fn):
    try:
        fn()
    except Exception as e:
        print(f"{label:<26} -> {type(e).__name__}: {e}")


show("int('abc')", lambda: int("abc"))
show("'a' + 1", lambda: "a" + 1)
show("len(3)", lambda: len(3))
show("{}['x']", lambda: {}["x"])
show("[1,2][9]", lambda: [1, 2][9])
show("'x'.nope", lambda: "x".nope)
show("1/0", lambda: 1 / 0)
show("open('不存在.txt')", lambda: open("这个文件不存在.txt"))
show("__import__('不存在')", lambda: __import__("绝不存在的模块名"))
show("None + 1", lambda: None + 1)
show("int(None)", lambda: int(None))
show("int('3.5')", lambda: int("3.5"))
```

真实输出：


> 所以 `except ImportError:` 也能接住它。
> ② `KeyError` 的 `str(e)` 是 `'x'`（**带引号**），因为 `str(e)` 走的是
> `e.args[0]` 的 `repr`。想拿到不带引号的键名要用 `e.args[0]`。

### 2.4 ⚠️ `TypeError` 与 `ValueError` 的区别

这是最容易混的一对。分界线只有一条：

> **`TypeError`：你给我的东西"种类"就不对，我根本没法开工。**
> **`ValueError`：种类没问题，但这个"值"不合法。**

```python
def safe_int(text):
    if not isinstance(text, str):
        raise TypeError(f"需要 str，收到 {type(text).__name__}")   # 类型不对
    if not text.strip().lstrip("+-").isdigit():
        raise ValueError(f"{text!r} 不是一个整数字面量")            # 类型对，值不对
    return int(text)


print(safe_int("42"))    # 42
safe_int("abc")          # ValueError: 'abc' 不是一个整数字面量
safe_int(42)             # TypeError: 需要 str，收到 int
safe_int(None)           # TypeError: 需要 str，收到 NoneType
```

最典型的对照是**同一个 `int()` 的两种错误**：

```
int(None)     -> TypeError : int() argument must be a string, a bytes-like object or a real number, not 'NoneType'
int('abc')    -> ValueError: invalid literal for int() with base 10: 'abc'
```

**判断口诀**：`None` 传进去报 `TypeError`（它不是字符串/数字）；
`'abc'` 传进去报 `ValueError`（它是字符串，只是内容不是数字）。

> ⚠️ **坑**：`int('3.5')` 报的是 **`ValueError` 不是 `TypeError`**——
> `'3.5'` 确实是字符串（类型对），只是它不是一个合法的**整数字面量**（值不对）。
> `int('3.5')` 想成功必须先 `float('3.5')` 再 `int(...)`。

### 2.5 EAFP vs LBYL

两种风格：

- **LBYL**（Look Before You Leap，先看再跳）：先检查条件，再动手。
- **EAFP**（Easier to Ask Forgiveness than Permission，先做再求原谅）：
  先做，出错再处理。这是 Python 社区更常用的风格。

```python
data = {"name": "小明", "age": 18}

# LBYL
if "score" in data:
    score = data["score"]
else:
    score = 0
print("LBYL 结果：", score)      # 0

# EAFP
try:
    score = data["score"]
except KeyError:
    score = 0
print("EAFP 结果：", score)      # 0
```

EAFP 在"检查和执行之间状态会变"的场合更稳（多线程/网络尤其明显），
因为**它只有一次动作**，不存在"检查通过、动手时已经不成立"的窗口。

但 EAFP 有一个真实代价，我在本机量过（20 万次循环）：

```
全是正常输入时    EAFP 0.016s / LBYL 0.024s
全是异常输入时    EAFP 0.114s / LBYL 0.010s
```

（同样两行数字连跑两次都在这个量级：正常路径 EAFP 更快，异常路径 EAFP 慢 10 倍以上。）

**结论（可操作的选型依据）**：

| 情况 | 选 |
|---|---|
| 异常是**罕见**的（正常流程不抛） | **EAFP**，代码更短、正常路径更快 |
| 异常是**常态**（比如解析一堆用户输入，一半是脏数据） | **LBYL**，先检查，别把异常当流程控制 |
| 检查和执行之间**可能被别人改状态** | **EAFP**（原子性更好） |
| "异常"其实是**预期内的正常分支** | 用 `if` / `dict.get()` / `getattr(obj, "x", 默认值)` |

> ⚠️ **坑**：**别用异常做日常流程控制。**
> 上面那组数字就是理由——异常的构造和 traceback 生成有真实开销。
> 标准库里的 `dict.get(k, 默认值)`、`getattr(o, "a", 默认值)`、
> `str.isdigit()` 这类方法就是为了让你**不用**依赖异常。

## 3. `raise` 与自定义异常（覆盖 7.3）

### 3.1 `raise` 的三种形态

```python
# 1) raise 一个异常实例（最常用）
raise ValueError("这是我自己抛的")
# ValueError: 这是我自己抛的

# 2) raise 一个异常类（Python 帮你实例化，消息是空的）
raise ValueError
# ValueError

# 3) 在 except 里裸 raise —— 原样重抛，保留原始 traceback
try:
    try:
        raise ValueError("原始错误")
    except ValueError:
        print("先做点别的（比如记日志），再裸 raise 重抛")
        raise
except ValueError as e:
    print("外面又抓到了：", e)
```

```
先做点别的（比如记日志），再裸 raise 重抛
外面又抓到了： 原始错误
```

**`raise` 不带参数只能出现在 `except` 块里**，意思是"把当前正在处理的异常原样再抛出去"。
它的价值是：**你可以做点事（记日志、转成自己的异常类型）然后决定继续往外抛**。

> 对比 `raise e`：效果类似但会**额外加一层位置信息**（traceback 里多一个"从这行重新抛出"的帧）。
> **在 `except` 块里重抛就用裸 `raise`。**

### 3.2 `raise ... from ...`：异常链（真实 traceback）

底层出错 → 上层包一个更懂业务的异常，同时**保留原因**：

```python
# chain_raise.py
def read_age(text):
    try:
        return int(text)
    except ValueError as e:
        raise ValueError(f"{text!r} 不是合法年龄") from e


read_age("十八")
```

真实 traceback：

```

The above exception was the direct cause of the following exception:

Traceback (most recent call last):
  File "chain_raise.py", line 9, in <module>
```

**`The above exception was the direct cause of the following exception:`**
——这就是 `from e` 的效果。它对应的属性是 **`e.__cause__`**。

不写 `from` 会怎样？Python 仍然会把两个异常都打印出来，但措辞变了：

```python
# implicit_chain.py
def read_age(text):
    try:
        return int(text)
    except ValueError:

```

```
During handling of the above exception, another exception occurred:

Traceback (most recent call last):
  File "implicit_chain.py", line 9, in <module>
    read_age("十八")
    ~~~~~~~~^^^^^^^^
  File "implicit_chain.py", line 6, in read_age
    raise ValueError(f"{text!r} 不是合法年龄")
ValueError: '十八' 不是合法年龄
```

| 写法 | traceback 里的措辞 | 对应属性 | 含义 |
|---|---|---|---|
| `raise 新 from 旧` | The above exception was the **direct cause** of... | `新.__cause__ = 旧` | "我**故意**因为旧异常才抛新的" |
| 不写 `from`（在 `except` 里抛） | **During handling** of the above exception... | `新.__context__ = 旧` | "我处理旧异常时**又**出事了" |
| `raise 新 from None` | 只显示新异常 | `新.__cause__ = None` 且抑制 `__context__` | "别看底层的了，我就是要用新的盖掉" |

> **实用判断**：你在 `except` 里**主动**把一个异常翻译成另一个 → 用 `from e`。
> 你**不希望**调用者看到底层细节（比如库的对外接口要稳定）→ `from None`。

### 3.3 自定义异常

```python
class AppError(Exception):
    """本项目所有自定义异常的基类。"""


class ValidationError(AppError):
    def __init__(self, field, value, reason):
        self.field = field
        self.value = value
        self.reason = reason
        # 调父类 __init__，把消息交给它保存，str(e) 才有内容
        super().__init__(f"字段 {field} 校验失败：{reason}（收到 {value!r}）")


def check_age(v):
    if not isinstance(v, int):
        raise ValidationError("age", v, "必须是整数")
    if v < 0:
        raise ValidationError("age", v, "不能为负数")
    return v


print(check_age(18))              # 18

try:
    check_age(-3)
except ValidationError as e:
    print(e)                      # 字段 age 校验失败：不能为负数（收到 -3）
    print(e.field, e.value, e.reason)   # age -3 不能为负数
    print(e.args)                 # ('字段 age 校验失败：不能为负数（收到 -3）',)

try:
    check_age("十八")
except AppError as e:             # 用基类一把抓
    print(type(e).__name__, "/", e)
    # ValidationError / 字段 age 校验失败：必须是整数（收到 '十八'）
```

真实输出：

```
18
字段 age 校验失败：不能为负数（收到 -3）
age -3 不能为负数
('字段 age 校验失败：不能为负数（收到 -3）',)
ValidationError / 字段 age 校验失败：必须是整数（收到 '十八'）
```

**四条约定**：

1. **继承 `Exception`，不要继承 `BaseException`。**
   继承 `BaseException` 的东西会被 `except Exception:` **漏掉**——
   于是调用者只写了 `except Exception:` 就接不住你的异常，
   而这种"接不住"表现为**程序直接崩**，非常难排查。`BaseException` 那一支是
   留给"要求程序停下来"的信号（第 2.2 节）用的，不是给你放的业务错误。
2. **建一个项目级的基类**（这里的 `AppError`）。调用者可以
   `except AppError:` 一把接住所有"这个库抛的错"，同时又能对具体子类单独处理。
3. **一定要调 `super().__init__(消息)`**。不调的话 `str(e)` 是空字符串，
   日志里只会有一行"某某异常"，什么信息都没有。
4. **额外字段就挂在 `self` 上**（`field` / `value` / `reason`）。
   调用者不用去解析错误消息字符串，直接 `e.field` 拿结构化数据。

> **什么时候该自定义**：
> ① 调用者需要**按错误类型分别处理**（而不是按消息文本判断）；
> ② 需要**携带结构化信息**；
> ③ 想把底层异常（`KeyError`、`OSError`）翻译成本领域的语言。
> **否则直接用内置的 `ValueError` / `TypeError` / `RuntimeError` 就够**——
> 造一堆只抛一次的自定义异常是负担。

## 4. `assert` 断言（覆盖 7.4）

### 4.1 语法与最小例子

```python
def half(n):
    assert n % 2 == 0, f"{n} 不是偶数"
    return n // 2


print(half(10))     # 5
half(7)             # AssertionError: 7 不是偶数
```

语法：`assert 条件 [, 失败时的消息]`。条件为假时抛 `AssertionError`。
`assert` 是**语句**，不是函数——`assert(x, "msg")` 那种写法写的是
"断言这个元组为真"，而元组永远为真，**断言会失效**。要写 `assert x, "msg"`。

### 4.2 ⚠️ `python -O` 会把断言整条删掉（实测对比）

同一个文件，两次运行：

```python
# assert_demo.py
import sys

print("优化开关 __debug__ =", __debug__)


def half(n):
    assert n % 2 == 0, f"{n} 不是偶数"
    return n // 2


print("half(10) =", half(10))

try:
    half(7)
except AssertionError as e:
    print("AssertionError:", e)
else:
    print("half(7) 没有报错 —— 说明断言被关掉了")


def side_effect():
    print("  [副作用函数被调用了]")
    return True


assert side_effect()
print("断言后面的代码正常执行")
```

```
$ python assert_demo.py
优化开关 __debug__ = True
half(10) = 5
AssertionError: 7 不是偶数
  [副作用函数被调用了]
断言后面的代码正常执行

$ python -O assert_demo.py
优化开关 __debug__ = False
half(10) = 5
half(7) 没有报错 —— 说明断言被关掉了
断言后面的代码正常执行
```

**注意最后两行**：`-O` 下连 `assert side_effect()` 里的**函数调用都没发生**
（`[副作用函数被调用了]` 一行都没有）。`assert` 是**整条语句**被删掉，
不只是跳过检查。`-OO` 的结果和 `-O` 一样（本机实测）。

`__debug__` 是内置常量：
`-O` / `-OO` 下为 `False`，否则为 `True`。**断言以外的东西不受影响**：

```python
def half(n):
    if n % 2 != 0:
        raise ValueError(f"{n} 不是偶数")
    return n // 2


try:
    half(7)
except ValueError as e:
    print("raise 版：", e)      # raise 版： 7 不是偶数

print("__debug__ =", __debug__)
```

```
$ python -O assert_vs_raise.py
raise 版： 7 不是偶数
__debug__ = False
```

**`raise` 不受 `-O` 影响。** 这是"断言 vs 显式检查"最硬的一条区别。

### 4.3 ⚠️ 断言不是输入校验（反例）

```python
# assert_input.py
def withdraw(balance, amount):
    # 错误示范：把"用户输入"当成"内部不变式"来断言
    assert amount > 0, "取款金额必须为正"
    assert amount <= balance, "余额不足"
    return balance - amount


print(withdraw(100, 30))     # 70
print(withdraw(100, -50))    # 正常跑：AssertionError
```

```
$ python assert_input.py
70
Traceback (most recent call last):
  File "assert_input.py", line 11, in <module>
    print(withdraw(100, -50))
          ~~~~~~~~^^^^^^^^^^
  File "assert_input.py", line 4, in withdraw
    assert amount > 0, "取款金额必须为正"
           ^^^^^^^^^^
AssertionError: 取款金额必须为正

$ python -O assert_input.py
70
150        ← 余额从 100 变成 150：取 -50 等于存了 50
```

**`-O` 下这行代码直接创造了一个 bug**：取负数等于存钱。
而这不是"用户输入太奇怪"，是**这类校验本来就不该用 `assert` 写**。

> ⚠️ **坑（本节最重要的一条）**：
> **凡是"外部世界给的数据"和"业务规则"，一律用 `if ... raise`，不要用 `assert`。**
> 因为 `assert` 在别人用 `python -O` 跑你的代码时会**静默消失**——
> 你写的所有防御都没了，而且没有任何提示。
> 生产环境用 `-O` 是常见做法（省内存、去掉 docstring），你必须假定它会发生。

### 4.4 断言的正确用途：内部不变式

`assert` 该表达的是：**"如果这行代码执行到这里，那么某件事按我的设计必然成立；
如果不成立，说明我自己的代码写错了。"**

```python
def median(sorted_values):
    """传入已排序的序列，返回中位数。"""
    assert sorted_values == sorted(sorted_values), "调用者必须传已排序的序列"
    assert len(sorted_values) > 0, "空序列没有中位数"
    n = len(sorted_values)
    if n % 2:
        return sorted_values[n // 2]
    return (sorted_values[n // 2 - 1] + sorted_values[n // 2]) / 2


print(median([1, 2, 3, 4]))     # 2.5
print(median([1, 2, 3]))        # 2
```

这两个断言的特点是：

- 它们检查的是**调用者和被调用者之间的契约**，出问题说明**写代码的人搞错了**，
  不是"用户输入不合法"。
- 即使 `-O` 把它们删掉，程序的行为也**依然正确**（只是少了一层开发期的保护）——
  因为"按设计传进来的数据本来就该是排序好的"。

**`assert` 和 `raise` 的取舍**：

| | `assert` | `if ... raise` |
|---|---|---|
| `-O` 下 | **消失** | 保留 |
| 语义 | "这不可能发生，发生了就是我的 bug" | "这**可能**发生，我准备好了处理" |
| 消息 | 只给开发者看 | 可能给用户/日志看 |
| 用什么异常 | `AssertionError` | 具体的 `ValueError` / 自定义异常 |
| 正确用途 | 内部不变式、开发期自检、调试 | 输入校验、业务规则、对外接口 |

> **一句话**：`assert` 是**开发期**的"我自己没写错吧"，
> `raise` 是**运行期**的"这个输入我不接受"。两者不能互换。

## 5. 调试：读 traceback 与 `pdb`（覆盖 7.5）

### 5.1 先教读 traceback：从下往上读

```python
# traceback_demo.py
def average(numbers):
    total = sum(numbers)
    return total / len(numbers)      # 空列表时 len() == 0


def report(scores):
    avg = average(scores)
    return f"平均分 {avg:.1f}"


def main():
    data = [90, 85, 77]
    print(report(data))
    print(report([]))               # ← 这里会炸


main()
```

真实输出（本机 Python 3.13.15）：

```
平均分 84.0
Traceback (most recent call last):
  File "traceback_demo.py", line 19, in <module>
    main()
    ~~~~^^
  File "traceback_demo.py", line 16, in main
    print(report([]))               # ← 这里会炸
          ~~~~~~^^^^
  File "traceback_demo.py", line 9, in report
    avg = average(scores)
  File "traceback_demo.py", line 5, in average
    return total / len(numbers)      # 空列表时 len() == 0
           ~~~~~~^~~~~~~~~~~~~~
ZeroDivisionError: division by zero
```

逐部分拆解：

| 部分 | 含义 |
|---|---|
| `Traceback (most recent call last):` | **"最后一行是最近发生的事"** → **所以要倒着读** |
| `File "...", line 19, in <module>` | 出错时正在执行哪个文件的第几行、在哪个函数里 |
| `in <module>` | 模块级（不在任何函数里）的代码 |
| 缩进的 `main()` | 那一行的**源代码** |
| `~~~~^^` | **指示符**：圈出这一行里"具体是哪个表达式"出的错 |
| 最后一行 | **异常类型 + 消息**——先看这一行 |

**读的顺序（本节最实用的三个动作）**：

1. **先看最后一行**：`ZeroDivisionError: division by zero`——
   什么样的错、错在什么上。这一步就能排除掉一大半猜测。
2. **再从下往上找第一个"你认识的自己写的文件"**：那是错误**真正发生**的位置。
3. **顺着往上读调用链**：`main` → `report` → `average`，
   配合每一帧的源码行，就知道**是什么数据一路走到这里变成了空列表的**。

**指示符怎么读**（`~~^~~` 是 3.11 之后新增的精确指示）：

```
    return total / len(numbers)
           ~~~~~~^~~~~~~~~~~~~~
```

- `^` 指向**真正出事的最小单位**——这里是 `/` 这个除法运算符。
- `~` 圈出**参与这个运算的两个操作数**：`total` 和 `len(numbers)`。
- 3.11 之前只有一列 `^`，没有波浪线。**看到 `~` 就知道本机是 3.11+。**

再看"函数返回值参与运算"时指示符的宽度差别：

```python
# traceback_demo2.py
def convert(text):
    return int(text) + 1


print(convert("12"))
print(convert("十二"))
```

真实输出：

```
13
Traceback (most recent call last):
  File "traceback_demo2.py", line 7, in <module>
    print(convert("十二"))
          ~~~~~~~^^^^^^^^
  File "traceback_demo2.py", line 3, in convert
    return int(text) + 1
           ~~~^^^^^^
ValueError: invalid literal for int() with base 10: '十二'
```

第一帧的 `~~~~~~~^^^^^^^^` 圈的是 `convert("十二")`——**调用这个函数的那一小段**；
第二帧的 `~~~^^^^^^` 圈的是 `int(text)`——**真正抛异常的那个调用**。
**顺着指示符的宽度看，就能分清是哪一层出的错。**

> **一个值得知道的显示细节（本机 3.13 实测）**：像 `return f()` 这种"整行就是一个裸函数调用"的帧，
> Python 有时**只打印 `File` 行、不打印源码行和指示符**（上面的 `report` 帧就是这样）。
> 这不是少了信息——**行号还在**，去那一行看就知道了。

**`SyntaxError` 的格式不一样**（它在代码执行之前就被发现，所以没有调用链）：

```python

    print("不会执行")
```

```

           ^

```

注意三点：**没有 `Traceback (most recent call last):` 开头**；
只有一个 `File` 行；指示符指向**缺少冒号的位置**。

> ⚠️ **坑（Windows 特有）**：`SyntaxError` 里的 `File` 路径取决于你怎么调用解释器。
> `python syn.py` 会显示**完整绝对路径**（Windows 上可能很长，
> 所以本章的输出我都改写成短名）；如果代码是从字符串编译的
> （`exec`、Jupyter、某些 IDE 的运行器），会显示成 `<string>`。
> **路径长不代表出错文件不是你的——先看文件名。**
>
> 另一个更常见的"假报错"：**文件编码不对**。如果 `.py` 被存成了 GBK（旧编辑器默认值），
> Python 3 按 UTF-8 读会报 `SyntaxError: Non-UTF-8 code starting with ...`，
> 而且行号指到中文那一行。处理见 `01_入门与环境.md` 第 6 节——把文件另存为 UTF-8。

### 5.2 `python -m pdb script.py`：外部启动调试器

进入后是 `(Pdb)` 提示符。常用命令（这是最小可用集）：

| 命令 | 缩写 | 作用 |
|---|---|---|
| `n` | next | 执行**下一行**（不进入函数内部） |

| `where` / `w` | —— | 打印当前调用栈（比 `l` 更关心"我怎么到这儿的"） |
| `q` | quit | 退出 |

本机实测的一段会话（`(Pdb)` 后面是我输入的命令，其余是程序的输出）：

三个读法：

- **`>` 开头那一行**是"现在停在哪"：文件、行号、**所在函数**（`divide()` 里的括号就是函数名）。
- **`->` 指向即将执行的那一行**（不是刚执行过的）。
- **`l` 里的 `B->`**：`B` 表示这一行有断点。
- **`p a / b` 报错但调试器没退出**——`p` 只是求值，异常被 pdb 接住了，
  你正好借此**在停下来的时候验证猜想**。

> ⚠️ **坑（Windows）**：pdb 显示的路径是**绝对路径**且是反斜杠形式
> （`c:\users\...\debug_me.py`）。在 Git Bash 里跑也一样。
> 这没有坏影响，只是看起来很吵；`b` 命令里如果用路径，也要照抄这种形式。

> **`python -m pdb` 会从头开始**：它停在脚本的第一行，所以你必须
> 自己 `b` 断点 + `c`（或者一路 `n`/`s` 走）。**这正是它和 `breakpoint()` 的核心区别。**

### 5.3 `breakpoint()`：在代码里留一个断点

```python
    return total * 2


print(compute(3, 4))
print("程序结束")
```

直接运行就会在那一行停下（本机实测）：

```

(Pdb) c
14
程序结束
```

- **`breakpoint()` 是内置函数**（3.7+），它调用的东西由环境变量 **`PYTHONBREAKPOINT`** 决定——
  默认是 `pdb.set_trace()`。
- **`PYTHONBREAKPOINT=0` 可以让所有 `breakpoint()` 变成空操作**（本机实测）：

```bash
$ PYTHONBREAKPOINT=0 python bp_demo.py
14
程序结束
```

**这就是 `breakpoint()` 比 `import pdb; pdb.set_trace()` 好的地方**：
留一个在代码里，平时用 `PYTHONBREAKPOINT=0` 一键关掉，
不用改代码、不用记得删。

| | `python -m pdb script.py` | 代码里插 `breakpoint()` |
|---|---|---|
| 停在哪 | **第一行** | 你插的那一行 |
| 要不要改代码 | 不用 | 要（插一行） |
| 什么时候用 | 不知道问题在哪、想从启动就开始看 | **已经知道大概是哪一段**，想在现场看变量 |
| 怎么关掉 | 不启动就不进 | `PYTHONBREAKPOINT=0` |
| 能不能提交到仓库 | —— | **最好别**，或者配上面那个环境变量当"开发模式开关" |

### 5.4 `python -i`：进到报错现场

`-i` 的意思是"脚本跑完（或跑崩）后**不要退出**，直接落到交互式提示符，
而且**模块级的变量都还在**"：

```python
# crash.py
import json

data = {"name": "小明", "score": 91}
text = json.dumps(data)

print("先做一些正常的事：", text)
result = 100 / 0          # ← 在这里炸
print("到不了这里")
```

```bash
$ python -i crash.py
先做一些正常的事： {"name": "\u5c0f\u660e", "score": 91}
Traceback (most recent call last):
  File "crash.py", line 8, in <module>
    result = 100 / 0          # ← 在这里炸
             ~~~~^~~
ZeroDivisionError: division by zero
>>> print("data =", data)
data = {'name': '小明', 'score': 91}
>>> print("type(text) =", type(text))
type(text) = <class 'str'>
>>> quit()
```

**你能在崩了之后直接检查当时的状态**——不用加 `print`、不用重跑。
这是 `01_入门与环境.md` 第 3.4 节提到的 `-i`，这里补上它在调试里的实际用法。

> ⚠️ **坑**：`-i` 里能看到的只是**模块级**的名字。
> 如果错误发生在函数内部，那个函数的局部变量（`a`、`b`、`result`）
> **不在交互命名空间里**，你只能看到全局的。
> 想看局部变量 → 用 `breakpoint()` 停在函数内部，或者 `python -m pdb`。
> （实测确认过这一点：`-i` 之后 `print(x)` 会报 `NameError: name 'x' is not defined`，
> 因为 `x` 是函数里的局部变量。）

### 5.5 `traceback` 模块：自己打印 traceback

程序里捕获了异常但想**保留完整现场**（比如写日志、上报）时用它：

```python
import traceback

try:
    1 / 0
except ZeroDivisionError:
    # format_exc() 返回字符串（适合写日志）
    print(traceback.format_exc())
    # 或者直接打到 stderr（适合调试）
    traceback.print_exc()
```

`traceback.format_exc()` 返回和真 traceback **一模一样的字符串**（含源码行和指示符），
所以你在日志文件里看到的内容和你直接在终端看到的没区别。
**`print_exc()` = 把 `format_exc()` 的结果写到 `sys.stderr`。**

> 只有在"我确实接住了这个异常、但要把它记下来"时才用。
> **不要**写成：
> ```python
> try:
>     do_something()
> except Exception:
>     traceback.print_exc()      # 打完之后异常就没了 → 上层以为成功了
> ```
> 要么处理完 `raise` 重抛，要么明确决定"这里吞掉是安全的"。

### 5.6 额外一节：异常组 `except*`（3.11+，本机实测）

**问题**：有些操作会**同时产生多个错误**（对一批数据做校验、并发里多个任务都失败）。
`raise` 一次只能抛一个异常，只能"抛第一个"或者"打包成一个字符串"——两者都会丢信息。

Python 3.11 引入了 **`ExceptionGroup`（异常组）+ `except*`**：

```python
import sys

print("Python 版本：", sys.version.split()[0])     # 3.13.15

# 1) 手工造一个异常组
eg = ExceptionGroup(
    "批量校验失败",
    [ValueError("年龄不是数字"), TypeError("名字必须是字符串")],
)
print(eg.message)                 # 批量校验失败
print(len(eg.exceptions))         # 2
for e in eg.exceptions:
    print(type(e).__name__, ":", e)
# ValueError : 年龄不是数字
# TypeError : 名字必须是字符串
print(isinstance(eg, BaseException))   # True
```

**`except*` 的分类处理**：**每一个匹配的分支都会跑**（普通 `except` 只跑第一个匹配的）：

```python
try:
    raise ExceptionGroup(
        "批量校验失败",
        [ValueError("年龄不是数字"), TypeError("名字必须是字符串"), ValueError("分数超范围")],
    )
except* ValueError as eg1:
    print("[ValueError 支] 收到", len(eg1.exceptions), "个：")
    for e in eg1.exceptions:
        print("   ", e)
except* TypeError as eg2:
    print("[TypeError 支] 收到", len(eg2.exceptions), "个：")
    for e in eg2.exceptions:
        print("   ", e)
```

真实输出：

```
[ValueError 支] 收到 2 个：
    年龄不是数字
    分数超范围
[TypeError 支] 收到 1 个：
    名字必须是字符串
```

注意：**`eg1` 本身还是一个 `ExceptionGroup`**（不是单个 `ValueError`）——
它被"裁剪"成了只含 `ValueError` 的子组，所以要用 `eg1.exceptions` 再遍历。

**普通 `except` 面对异常组时，把它当成一个整体**：

```python
try:
    raise ExceptionGroup("两个错误", [ValueError("a"), TypeError("b")])
except Exception as e:
    print(type(e).__name__)     # ExceptionGroup
    print(str(e))               # 两个错误 (2 sub-exceptions)
```

> ⚠️ **坑**：`except Exception:` **能**接住 `ExceptionGroup`，
> 但你拿到的是一个"包"，得自己进去翻 `.exceptions`——
> 而那些子异常是 `ValueError` 还是 `TypeError`，你在这个 `except` 里分不出来。
> 要用 `except*`，或者自己写递归遍历。

**`except*` 只认领自己那一类，剩下没人认领的会重新抛出**：

```python
# part_unhandled.py
try:
    raise ExceptionGroup("批量失败", [ValueError("a"), TypeError("b")])
except* ValueError:
    print("ValueError 这一支处理完了；TypeError 没人管")
```

真实输出（程序最后**非零退出**）：

```
ValueError 这一支处理完了；TypeError 没人管
  + Exception Group Traceback (most recent call last):
  |   File "part_unhandled.py", line 7, in <module>
  |     raise ExceptionGroup(
  |     ...<2 lines>...
  |     )
  | ExceptionGroup: 批量失败 (1 sub-exception)
  +-+---------------- 1 ----------------
    | TypeError: b
    +------------------------------------
```

**没接住的异常组的 traceback 长得和普通的不一样**：用 `+` / `|` 画成树，
每个子异常占一个分支。这是 3.11+ 的新格式。

**嵌套组会被 `except*` 展平着捞**——`except* TypeError` 能穿透到内层组里把 `TypeError` 认领出来：

```python
try:
    raise ExceptionGroup(
        "外层",
        [ValueError("直接错"), ExceptionGroup("内层", [TypeError("嵌套错")])],
    )
except* TypeError as eg3:
    for x in eg3.exceptions:
        print(type(x).__name__, ":", x)
        # 注意：这里拿到的是"被裁剪后剩下的组"，不是裸的 TypeError 本身
        # ExceptionGroup : 内层 (1 sub-exception)
except* ValueError:
    # 这一支也必须写：except* 只"认领"自己那一类，剩下没人认领的会重新抛出
    print("ValueError 那一支也写了，才不会让程序带着未处理的异常退出")
```

真实输出：

```
ExceptionGroup : 内层 (1 sub-exception)
ValueError 那一支也写了，才不会让程序带着未处理的异常退出
```

> **注意这个反直觉之处**：`eg3.exceptions` 里躺着的**可能还是 `ExceptionGroup`**
> （因为原来的嵌套结构被保留了，只是外层组被裁剪成只剩 `TypeError` 那一支）。
> 想拿到最底层的裸异常，得自己递归下去，或者用 `eg3.subgroup(...)`——
> **`subgroup()` 本节没有实测，不声称它的行为。**

**类型关系**（本机实测）：

```python
print(ExceptionGroup.__name__)                           # ExceptionGroup
print(issubclass(ExceptionGroup, BaseExceptionGroup))     # True
print(issubclass(ExceptionGroup, Exception))              # True
```

`ExceptionGroup` 只能装 `Exception` 的子类（业务错误用这个）；
`BaseExceptionGroup` 还能装 `KeyboardInterrupt` 这种"要求程序停下"的东西。

> **什么时候真的用得上**：并发里多个任务同时失败（`asyncio.TaskGroup` 会自动抛异常组）、
> 对一批**互相独立**的数据项做校验、解析多个字段时想一次性报出所有问题。
> 单个操作只会出一处错的场合**不需要它**——用普通 `try/except` 更简单。
>
> **版本要求**：`except*` 和 `ExceptionGroup` 都是 **3.11 新增**。
> **本机 3.13.15 实测可用；我没有在 3.10 上验证过它报什么语法错误**，标注为未实测。

   为什么需要 `else`（把它写进 `try` 末尾不行吗）？

**2. 下面这个函数调用后，异常会怎么样？为什么这是个坑？**

```python
def f():
    try:
        raise ValueError("x")
    finally:
        return "ok"
```

3. `except:` 和 `except Exception:` 的区别是什么？举一个"前者会害你"的具体场景。
4. `except ValueError:` 写在 `except MyError:` 前面（`MyError` 是 `ValueError` 的子类），
   会发生什么？报错吗？
5. `KeyError` 和 `IndexError` 的共同父类是什么？`FileNotFoundError` 的父类是什么？
6. `int(None)` 和 `int('abc')` 分别报什么异常？为什么不一样？
7. `raise ValueError("a") from KeyError("b")` 抛出去之后，
   最外层 traceback 里会多出哪句话？这个原因存在哪个属性上？
8. 为什么自定义异常**不该**继承 `BaseException`？会造成什么具体后果？
9. 一份代码里写了 `assert amount > 0`，另一个同事用 `python -O` 跑会怎样？
   什么场合才该用 `assert`？
10. 读 traceback 应该从哪一头开始读？最后一行包含哪些信息？
    `~~~~~~^~~~~~~~~~~~~~` 里的 `~` 和 `^` 各是什么意思？

<details>
<summary>答案</summary>

1. `try` 总是执行（放可能出错的代码）；`except` 在出现**匹配的**异常时执行；
   `else` 在 `try` 里**没出任何异常**时执行；`finally` **无论如何**都执行
   （包括 `return` / `break` 离开时）。
   `else` 的意义是**把"成功后要做的后续代码"隔离在 `try` 之外**——
   写进 `try` 里的话，它抛出的异常会被同一个 `except` 抓走，
   等于把一个 bug 当成业务错误处理掉了。
2. **异常被吞掉，函数正常返回 `"ok"`。** 因为 `finally` 里的 `return`
   会覆盖正在抛出的异常（第 1.3 节实测）。所以 `finally` 里**永远不要**写
   `return` / `break` / `continue`。
3. `except:` 捕获的是 `BaseException` 的**所有**子类，包括 `KeyboardInterrupt`、
   `SystemExit`、`GeneratorExit`；`except Exception:` 不包括这三个。
   场景：用户在跑一个长任务时按 `Ctrl+C` 想停下，裸 `except:` 把它接住并继续跑，
   用户以为停了、其实还在跑（第 1.4 节实测）。另一个场景：裸 `except:` 会吞掉
   `NameError`、`AttributeError` 这类**你自己的编程错误**。
4. **不报错，但行为不是你想要的**：`MyError` 会被前面的 `ValueError` 分支接走，
   专门处理 `MyError` 的那一段永远不执行（死代码）。
   规则是**子类必须写在父类前面**，最具体的放最上面，兜底的放最后。
5. 共同父类是 **`LookupError`**。`FileNotFoundError` 的父类是 **`OSError`**
   （所以 `except OSError:` 能接住所有文件/系统相关的错误）。
6. `int(None)` → **`TypeError`**（`None` 这个**类型**就不是字符串/数字，没法开工）；
   `int('abc')` → **`ValueError`**（`'abc'` 的类型是对的，是它作为整数字面量**值不合法**）。
   口诀：类型不对 → `TypeError`；类型对但值不对 → `ValueError`。
7. 会多出一句 **`The above exception was the direct cause of the following exception:`**。
   原因存在新异常的 **`__cause__`** 属性上（`新.__cause__ is 旧`）。
   不写 `from` 时措辞变成 `During handling of the above exception, another exception occurred:`，
   存在 **`__context__`** 上。
8. 因为 `except Exception:` **接不住** `BaseException` 的子类。
   调用者写了 `except Exception:` 就抓不到你的异常，表现为**程序直接崩**（未捕获异常），
   而且崩的信息看起来跟你没关系、非常难排查。
   正确做法是继承 `Exception`，并在项目里建一个公共基类。
9. 那些 `assert` **会被整条删掉**（不是跳过判断，是连里面的函数调用都不执行），
   所有防御静默消失。如果 `assert amount > 0` 保护的是"取款金额"这种业务规则，
   `-O` 下负数取款就会被当成合法操作执行（第 4.3 节实测出"取负数等于存钱"）。
   **正确用途**：内部不变式——"按我的设计，执行到这里这件事必然成立，
   不成立就是我自己写错了"，而且删掉它程序行为依然正确。
10. **从下往上读**（`most recent call last` = 最后一行是最近发生的）。
    最后一行 = **异常类型 + 消息**，这是最先该看的一行。
    `^` 指向真正出事的最小单位（比如 `/` 运算符）；
    `~` 圈出参与这个运算的操作数。3.11+ 才有 `~` 这种精确指示。

</details>
